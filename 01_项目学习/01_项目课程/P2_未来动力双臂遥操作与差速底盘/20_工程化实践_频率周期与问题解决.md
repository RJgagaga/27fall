## 1. 从零到上线：需求、选型、架构、里程碑

### 1.1 需求拆解

CV 的概述一句话：*dual-arm and chassis control, covering VR teleoperation, leader–follower teaching and base motion control, all validated on real hardware through the ROS2-CAN execution chain.* 把它拆成可验收的需求（验收口径来自 README 自查表 #19）：

| 编号 | 需求 | 验收标准（本项目取值） |
|---|---|---|
| R1 | VR 遥操作：手柄动，末端按比例跟 | 末端稳态误差 <5 mm；近奇异不暴冲（关节速度不超过限值） |
| R2 | 主从示教：手拖主臂很轻，从臂同步 | 主臂悬停漂移小；从臂 RMS 误差约 0.01 rad；端到端约 30 ms |
| R3 | 底盘：遥控与自动两种模式，轮速闭环，里程计 | 2 m 直线横偏 <5 cm；5 m 往返距离误差约 2% |
| R4 | 全部走 ROS 2–CAN 链，在真机上验证 | 方向与编码器一致、不触限位 |
| R5 | 安全：失联不乱动、可随时停 | 100 ms 冻结 / 500 ms 失能；`/cmd_vel` 300 ms 归零 |
| R6 | 可复现：出问题能回放 | 每次真机运行有 rosbag 与参数快照 |

非功能需求同样重要：不能把手臂或人撞坏（R5）、换人换机器能跑（R6）、改一个参数不会悄悄破坏别的功能（回归）。

### 1.2 方案选型（每个选择都有“为什么”）

| 决策点 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 遥操作映射 | 相对位姿 + 离合器 | 绝对映射 | 起步不跳；范围不匹配；见 [02 章](./02_VR遥操作的相对位姿映射.md) |
| IK | Mink（MuJoCo + QP） | 解析 IK、KDL 数值 IK、MoveIt | 7 自由度冗余 + 双臂 + 限位约束需要 QP 统一表达；Mink 配置量小 |
| 奇异处理 | 阻尼最小二乘 + 速度约束 | 奇异规避、截断 SVD | 连续、实现简单；见 [04 章](./04_逆运动学_雅可比_奇异性与阻尼最小二乘.md) |
| 动力学 | URDF + KDL（参考代码 Pinocchio） | 在线辨识 | URDF 已有、够用；辨识成本高 |
| 主臂控制 | 纯力矩（MIT 帧，$K_p=0$） | 导纳控制 | 电机内环 kHz 级，延迟最小；见 [06 章](./06_URDF_KDL动力学与重力补偿.md) |
| 从臂控制 | MIT 位置 + 速度前馈 | 力矩环 | 电机内置 PD，上位机只更新五个数 |
| 通信 | ROS 2 话题 + SocketCAN | 直接 Python 调用 | 节点解耦，可录包回放 |
| 底盘速度环 | 板端 PID（编码器 rpm） | 只用驱动器内环 | 需要显式的闭环与限幅；与 CV 一致 |
| 数据记录 | rosbag + 参数快照 | 手写日志 | 可回放，可复现 |

选型的共同原则：**能用现成件解决的不自己写（Mink、电机库、底盘 CAN 框架），自己写的只写“胶水和保护”**——相对映射、限幅、超时、标定、集成。

### 1.3 架构

```text
L5 任务/遥操作层   VR 采集端(团队)  ──►  相对位姿映射 + 目标限幅(我)
L4 算法层          Mink 约束 IK(我配置)   主臂重力补偿(我整定)   底盘运动学/里程计(我)
L3 ROS 2 层        话题 / 定时器 / QoS / 目标年龄
L2 驱动层          硬件节点 + XArmController(团队) / 底盘桥接节点
L1 总线层          SocketCAN can0 can1 (1 Mbit/s) / 板端 FDCAN1 FDCAN2
L0 电机/驱动器     DM 电机 MIT 内环 / 轮驱动器速度环与电流环
```

每层只和相邻层说话；**每层都有自己的限幅与失效动作**（10 章第 9、10 节）。

### 1.4 里程碑与迭代（约 13 周，本项目取值的节奏）

| 周 | 里程碑 | 交付与验收 | 风险与处理 |
|---|---|---|---|
| W1–W2 | 环境、读码、安全规程 | 能读写一个电机；急停位置、上电姿态、限位写成一页安全规程 | 电机/总线不通 → 先单电机排除 |
| W3–W4 | 底盘线 | 运动学 + 里程计 + 板端 PID 单轮闭环 → 双轮 → 遥控 → 自动；标定轮径轮距 | 符号链、字节序（09 章） |
| W5–W7 | 主从线 | URDF 动力学 → 重力补偿 → 符号测试 → 比例 0.5→0.8 → 从臂跟踪与增益整定 | 符号反、末端关节漂移 |
| W8–W10 | VR 线 | 相对映射 → Mink 单臂 → 双臂 → 限位与速度约束 → 目标限幅 | 轴映射、近奇异、dt 与实际频率 |
| W11 | 联调 | 三条线共用硬件节点与超时规则；全链路 rosbag | 周期抖动、话题名、单位 |
| W12–W13 | 验收与文档 | 指标复测、回归脚本、接口文档、遗留问题清单 | 参数散落 → 统一 YAML |

迭代原则：**先单点、后串联；先低增益、后全增益；先空载、后带载；每一阶段都有可复现的通过判据**。

## 2. 各层频率与周期设计

### 2.1 总表（本项目取值）

| 层 / 环 | 频率 | 周期 | 为什么是这个值 |
|---|---|---|---|
| 电机内环（位置 / 电流） | kHz 量级（厂家固件） | <1 ms | 非项目可控，我只更新五个数 |
| 主臂重力补偿循环 | 约 200 Hz（190~200） | 5 ms | 手拖很慢，重力项变化慢；瓶颈是 Python + 回包等待；总线负载仅 36% |
| 从臂指令下发 | 100 Hz | 10 ms | 与目标发布同步；再快没有新信息 |
| IK 循环 | 约 120 Hz（配置步长 5 ms） | 约 8 ms | QP 求解 + 消息收发所限；下取整到 100 Hz 发布 |
| ROS 2 目标发布 | 100 Hz | 10 ms | VR 数据 90 Hz，再快是重复数据 |
| VR 位姿 | 约 90 Hz | 11 ms | 头显刷新率，非项目可控 |
| 底盘板速度环 | 200 Hz | 5 ms | 与里程计门限一致；电机机械响应时间常数几十毫秒，5 ms 足够 |
| 底盘里程计积分 | 200 Hz | 5 ms | 同上；`ratio` 常量按 5 ms 推导 |
| `/cmd_vel` | 20–50 Hz | 20–50 ms | 导航级速度命令，不需要更快 |
| `/odom` 发布 | 50 Hz | 20 ms | 板端 200 Hz 积分，降采样发布 |
| SBUS 遥控 | 约 70–140 Hz | 7–14 ms | 接收机决定 |
| rosbag 记录 | 关节 100 Hz；诊断 10 Hz；文本日志 1 Hz | — | 按信息量分级 |

### 2.2 取舍的几条规则

**规则 1：命令频率不应高于信息源频率，也不必高于被控对象带宽的若干倍。** VR 数据 90 Hz，IK 以 100–120 Hz 运行已经足够；机械臂手拖带宽约 1–2 Hz，100 Hz 是约 50 倍，足够平滑。

**规则 2：内环要比外环快 3–10 倍，且彼此错开。** 电机内环 kHz → 我的指令 100–200 Hz → 目标 100 Hz → VR 90 Hz，基本满足“越靠近硬件越快”。

**规则 3：总线负载保持在 50% 以内。** 每臂 16 帧/周期、1.78 ms：200 Hz 时 36%，100 Hz 时 18%；底盘 5 ms 周期约 9%。这给了重发与错误帧的余量。

**规则 4：采样周期决定离散增益的有效含义。** `pid.c` 没有显式乘 $dt$，增益绑定调用周期，所以板端 PID 必须在固定 5 ms 门限下运行（09 章 4.3、11.1），否则同一组 $K_p,K_i$ 在不同周期下是不同的控制器。

**规则 5：配置的频率与实测频率要分开记录。** Mink 的 $dt=5$ ms 是积分步长，实测循环约 120 Hz；若混为一谈，关节每步位移被少算约 40%，跟随会变慢（03 章“dt 提示”）。

### 2.3 日志频率的设计

- **高频（100 Hz）**：关节目标、关节状态、回读力矩 → 体积小（14 个 double × 100 Hz ≈ 11 kB/s），可全程记录；
- **中频（10 Hz）**：$\sigma_{min}$、QP 状态、目标年龄、实测循环周期、总线错误计数；
- **低频（1 Hz）**：文本日志（模式切换、告警）；
- **事件触发**：越限、超时、失败计数跳变时立即写一条带时间戳的事件。

记录时用**接收时刻**和**发布时刻**两个时间戳，延迟可以事后算。

### 2.4 一个手算例子：采样频率与延迟对稳定性的影响（教学推算）

把从臂一个关节简化为：电机内环把位置误差变成加速度，外部看起来像一个带延迟的二阶系统。控制律 $\tau=K_p e+K_d\dot e$，惯量 $J$。离散实现里，指令延迟 $D$ 等于“发布周期的一半（平均等待）+ 总线往返 + 内环响应”。经验判据：延迟造成的相位滞后 $\varphi\approx\omega_c D$ 应小于约 $30^\circ$，其中 $\omega_c$ 为开环穿越频率。

取教学数值：$\omega_c=2\pi\times5\ \text{Hz}=31.4$ rad/s（手臂跟随的期望带宽 5 Hz），总延迟 $D=30$ ms：

$$\varphi=31.4\times0.030=0.94\ \text{rad}\approx54^\circ$$

已经超过 30°，说明把期望带宽定到 5 Hz 过于激进；把 $\omega_c$ 降到 $2\pi\times2\ \text{Hz}=12.6$ rad/s，$\varphi=12.6\times0.030=0.38$ rad $\approx22^\circ$，在可接受范围。这就是为什么本项目的从臂增益不能无限加大（见 [07 章](./07_主从跟踪与MIT电机接口.md) 的延迟与饱和部分），也是为什么每一次把延迟从 45 ms 降到 30 ms（优化 3）都会换来更高的可用增益。反过来，把发布频率从 100 Hz 提到 200 Hz，平均等待只减少 2.5 ms，对 30 ms 的总延迟贡献很小——**降延迟要先动大头（电机内环响应、低通滤波），而不是盲目提高频率**。

### 2.5 上机前检查清单（本项目取值）

1. 急停位置确认、周围无人、手臂工作空间内无障碍；
2. CAN：两端终端电阻、`ip link` 状态、错误计数为 0、回包能收齐 8 个；
3. 配置：增益取 10%–20%，限速为正常值的一半，参数文件哈希已记录；
4. 关节表：方向 / 零位 / 限位与上一次一致，单关节小幅度测试通过；
5. 超时：目标年龄 100 / 500 ms、`/cmd_vel` 300 ms 的保护已启用，**手动断开上游验证一次**；
6. 录包：rosbag 已启动，磁盘空间充足；
7. 退出：`finally` 路径已测试（Ctrl+C 后手臂渐降而不是下坠）；
8. 通过判据：本次要测的指标和回归项已写在纸上。

## 3. 抖动、延迟预算与调度

### 3.1 抖动从哪里来

| 来源 | 量级（典型） | 处理 |
|---|---|---|
| Python `time.sleep` | 约 1 ms 级 | 按**绝对时刻**睡眠：`wait = t0 + (k+1)·dt − now`（v2 `arm_control` 就这么做），抖动不累积 |
| ROS 2 定时器 + executor | 1–几 ms | 硬件节点独占一个回调组，避免与重回调（如日志）串行 |
| Linux 调度 | 几 ms（负载高时更大） | 硬件节点设实时优先级（`chrt -f 50`，本项目取值）；IK 节点保持默认；CPU 调频固定为 performance |
| `recv_all` 等待 | ≤10 ms | 超时设为周期的一半；超时计数告警 |
| CAN 仲裁 | <0.2 ms | 总线负载低，影响小 |
| 板端轮询 | 任务全速轮询，周期不受控 | 用 `HAL_GetTick` 门限（09 章） |

### 3.2 端到端延迟预算（教学推算，来自 10 章 7.3）

| 环节 | 时间 |
|---|---|
| VR 采样（90 Hz，平均半个周期） | 5.5 ms |
| 局域网传输 | 3–5 ms |
| IK 求解循环 | 约 8 ms |
| 硬件节点定时器等待（平均半周期） | 5 ms |
| CAN 往返 | 约 2 ms |
| 电机内环响应 | 15–20 ms |
| **合计** | **约 40–45 ms（VR 线）；主从线约 30 ms** |

预算的用途：**当体验“发飘”时，先看哪一段超预算**，而不是全部重调。

### 3.3 线程与优先级

- 硬件节点（定时器 100 Hz + CAN 收发）：高优先级（`SCHED_FIFO 50`，本项目取值），独占一个核（`taskset`）；
- IK / 映射节点：普通优先级；它只产生目标，不直接碰总线；
- 日志与可视化：低优先级（`nice 10`），并降采样；
- 主从线的重力补偿循环：单独进程，一条总线一个线程（v2 的 `_run_parallel` 就是这个思路），GIL 在 I/O 等待时释放。

板端没有 RTOS 优先级可设（自研协作调度），所以靠“**中断里只搬数据，主循环里做计算**”来控制时延：FDCAN 与 UART 回调只拷贝数据并置位，所有处理在任务里完成。

## 4. 优化过程（六次，每次六步）

> 记法：现象 → 度量方法 → 瓶颈 → 改动 → 前后对比（本项目取值）→ 回归验证。

### 优化 1：IK 循环频率

- **现象**：VR 目标发布 100 Hz，但手臂动作有“一顿一顿”的感觉；日志显示 IK 输出间隔不均匀。
- **度量**：每个周期用 `time.perf_counter()` 打点，统计平均周期、95 分位和最大值，同时打印目标年龄。
- **瓶颈**：每周期同时做了 QP 求解、MuJoCo 可视化刷新和较多打印；渲染占去相当一部分时间。
- **改动**：渲染降到 10 Hz；复用 Mink `Configuration` 与任务对象，避免每周期重新构造；打印降到 1 Hz；QP 用 warm start（沿用上一周期解）。
- **前后**：循环频率由约 70 Hz 提到约 120 Hz；95 分位周期由约 14 ms 降到约 10 ms。
- **回归**：回放同一段录制的手柄轨迹，两次的末端轨迹最大差 <1 mm；“伸向边界”的近奇异测试仍通过。

### 优化 2：重力补偿循环频率与手感

- **现象**：主臂拖动时“发涩”，有轻微卡顿；循环频率约 120 Hz。
- **度量**：每秒打印一次平均循环频率与最大周期；同时记录回读力矩的变化率。
- **瓶颈**：每周期 `recv_all` 最多等 10 ms；逐关节 Python 循环计算摩擦；每周期打印。
- **改动**：打印改 1 Hz；摩擦模型用 numpy 向量化；预分配 `MITParam` 列表；两臂各一线程各管一条总线。
- **前后**：约 120 Hz → 约 190~200 Hz；拖动手感更连贯。
- **回归**：悬停漂移（松手 5 s 内 <2°）、符号测试、各姿态下重复；确认补偿比例仍为 `[1,1,1,1,1,1,0.8]`。

### 优化 3：主从端到端延迟

- **现象**：快速摆动主臂时，从臂明显滞后，像“跟在后面追”。
- **度量**：主臂做一次快速小幅阶跃，同一时间轴画主从关节角，读 10%–50% 处时间差。
- **瓶颈**：①从臂只发位置，没有速度前馈；②速度低通偏强；③发布与硬件节点定时器相位不同步，平均多等半个周期。
- **改动**：加入速度前馈（`vel` 取主臂速度并低通）；低通系数调大一点，减小滞后；硬件节点定时器与发布同源触发。
- **前后**：端到端由约 45 ms 降到约 30 ms；运动中滞后由约 4–5 个周期降到约 3 个周期。
- **回归**：稳态误差仍 <0.02 rad；RMS 误差约 0.01 rad；观察速度噪声没有引入抖动。

### 优化 4：底盘周期与里程计精度

- **现象**：5 m 往返的里程计误差随 CPU 负载变化，同一参数两次结果不同。
- **度量**：在板端记录相邻两次里程计积分的 `HAL_GetTick` 间隔，看是否稳定在 5 ms。
- **瓶颈**：任务全速轮询，PID 与发送节拍不固定；里程计常量按固定 5 ms 推导。
- **改动**：板端速度环与里程计共用 5 ms 门限；上位机侧统一按 200 Hz 的假设处理回报。
- **前后**：5 m 往返距离误差由约 4% 降到约 2%；两次重复的差由约 1.5% 降到 <0.5%。
- **回归**：直线 5 m、原地转 10 圈各 3 次，对比均值；切换模式时速度命令清零。

### 优化 5：CAN 往返时间

- **现象**：双臂同时运行时偶发回包超时，周期抖动。
- **度量**：`candump -td` 看每个周期内 16 帧的时间分布；统计 `recv_all` 超时次数。
- **瓶颈**：两臂原先在同一线程里顺序“发 8 帧 → 等 8 帧 → 再另一臂”，总耗时叠加。
- **改动**：两臂分别在各自线程、各自总线并行；发送阶段连续发完再统一接收（不要发一帧收一帧）。
- **前后**：每周期总线占用由约 3.2 ms 降到约 1.8 ms；回包超时由每分钟数次降到 0。
- **回归**：30 分钟连续运行无超时；两条臂互不影响（人为让一条总线断开，另一条正常）。

### 优化 6：日志体积与掉帧

- **现象**：长时间录包文件很大，回放时偶有缺失。
- **度量**：看 bag 大小增长率和丢消息计数。
- **瓶颈**：把调试用的高维诊断量也以 100 Hz 录入；磁盘写入与控制争抢 CPU。
- **改动**：三级频率（100 / 10 / 1 Hz）；录包进程降低优先级；压缩。
- **前后**：每小时体积减小到原来的约 1/4；掉帧消失。
- **回归**：用 bag 回放复现案例 4 的近奇异事件，指标可读。

> **共同方法**：**先度量、后改动；一次只改一件事；改完用同一回归集复测**。这六次优化没有一个是“凭感觉”改的。

## 5. 工程问题与解决（14 个）

每个问题：背景 → 根因 → 解决 → 预防。（与 [11 章故障案例](./11_调试与故障案例.md) 互补：那里是“故障”，这里是“工程流程”。）

**问题 1（联调）：关节顺序和单位不一致。** 背景：算法节点发 14 维数组，硬件节点解读错一位就“两条臂对调”。根因：口头约定。解决：写一页接口文档（话题名、类型、顺序、单位、频率、超时），硬件节点启动时检查数组长度；双方各写一个“接口自检”脚本。预防：接口变更必须改文档并通知。

**问题 2（联调）：坐标系约定不一致。** 背景：VR 采集端、IK 端、底盘板各有自己的轴向。根因：没有统一参考。解决：画一张坐标系对照图（XR、基座、板子里程计），换算写成单元函数并测试（10 章 11.3 的 $x_r=y_b,\ y_r=-x_b,\ \text{yaw}_r=-z$）。预防：每个跨团队接口给出一个“已知输入 → 已知输出”的样例。

**问题 3（版本管理）：依赖版本漂移。** 背景：Mink / MuJoCo 小版本升级后默认参数或行为变化，同一配置结果不同。根因：未锁版本（README 自查表 #5：Mink 为 0.0.x、未锁定）。解决：`requirements.txt` 固定版本，镜像里冻结；面试只讲原理、不断言某版本的默认行为。预防：重新做时第一天就锁依赖，并把版本号写进 bag 元数据。

**问题 4（版本管理）：配置与代码混在一起提交。** 根因：调参直接改源码。解决：参数全部进 YAML，Git 里分代码与配置变更两类提交；每次真机测试打 tag 并记录对应配置哈希。预防：CI 里检查“没有硬编码增益”。

**问题 5（参数管理）：同一参数在多处定义。** 背景：$K_p/K_d$ 在 IK、驱动、示例脚本里各一份，改了一处另一处不变（读码里就有 `RIGHT_KD` 两份不同的例子）。解决：统一从一个参数文件读取，并在启动时打印生效值。预防：每个参数只有一个“事实来源”。

**问题 6（仿真到实机）：符号、零位与限位差异。** 背景：仿真里正常的目标，在实机上方向反或越限。根因：URDF 零位、电机零位、正方向三者不一致；两套限位（MECH_LIM 与 URDF）不同。解决：建立一张“关节—URDF 轴—电机方向—零位偏置—限位”的表，单关节小幅度测试逐个标定；零位偏置通过两臂摆到同一标定姿态来测（量级 <0.03 rad）。预防：新关节、新电机先过这张表。

**问题 7（仿真到实机）：先低增益再全增益。** 解决：第一次上机所有增益取 10%–20%，限速取一半，空载、人在急停旁；逐步放开。预防：把“放开顺序”写进检查清单。

**问题 8（安全）：上电和下电的冲击。** 背景：使能瞬间电机以当前编码器位置为起点，若目标很远会猛弹；下电瞬间手臂下坠（`gravity_comp.py` 的 `finally` 直接失能）。解决：使能 → 等 0.2 s → 先移到已知姿态 → 再进入目标模式；退出走力矩渐降（每步 ×0.85，60 步，约 0.6 s）。预防：退出路径与进入路径同等对待。

**问题 9（安全）：失联策略。** 解决：分层看门狗（10 章第 10 节）；明确“冻结”与“失能”的区别和阈值（100 / 500 ms）；`/cmd_vel` 300 ms 归零；对读码发现的固件心跳缺陷，不依赖它，在上位机侧兜底。预防：每个看门狗做“被喂 → 状态更新”“超时 → 动作”两个单测，评审时问“这个标志在哪里被写”。

**问题 10（日志与复现）：出了问题复现不了。** 解决：每次真机运行自动录 rosbag + 参数快照 + Git 哈希 + 机器标识；复现时用 bag 回放驱动算法节点。预防：没有 bag 的实验不算数据。

**问题 11（测试方法）：没法自动测硬件。** 解决：三层测试——①纯函数单测（$R_a$ 正交、旋转更新、MIT 打包越界、坐标换算）；②硬件在环短测（单关节小幅度、符号、限位）；③回归脚本（伸向边界、悬停漂移、2 m 直线）。预防：每次改动至少跑①，改参数跑②③。

**问题 12（调试）：周期不是配置的那个。** 见优化 1、2：配置 200 Hz，实测 120 Hz。解决：所有循环打印实测周期；积分用实测时间戳。预防：把“实测周期”作为默认日志字段。

**问题 13（热与电流）：长时间重力补偿的电机温升。** 背景：主臂持续输出重力矩，肩部大电机温度上升。解决：回包里有温度字节（以电机手册为准），以 1 Hz 记录；告警阈值取 60 ℃，达到 70 ℃ 降低补偿比例并提示休息（本项目取值）；机械上让主臂的休息姿态靠近重力平衡位。预防：连续运行测试时记录温度曲线。

**问题 14（符号链）：镜像轮 PID 正反馈。** 见 [09 章 11.3](./09_STM32H7_FDCAN底盘固件解读.md)。解决：PID 在统一正方向下计算，只在输出处翻转；反馈与给定保持同一符号约定。预防：单轮闭环先做，双轮再合并；任何“取负”都要写注释说明在哪一层。

## 6. 团队协作与冲突解决

### 6.1 分工与接口

团队里有机械、电气、VR 采集端维护者、底盘固件框架维护者、电机库维护者。我负责的模块在 README 自查表 #18 中写明：相对映射与 Mink 配置、主臂补偿与从臂增益、差速运动学 / 轮速 PID / 里程计 / ROS 2 集成。**协作的核心是接口**：先对齐“话题名、类型、单位、顺序、频率、超时”，再各自开发。

### 6.2 典型分歧与处理

| 分歧 | 双方立场 | 处理 |
|---|---|---|
| 安全限位谁负责 | 算法侧认为驱动应兜底；驱动侧认为算法应保证 | 定为**分层限幅**，每层各自负责自己的层，并在文档里写清阈值 |
| 增益谁调 | 电气同事和我都改过同一组 $K_p/K_d$ | 一个人是参数文件的“所有者”，其他人通过提交请求改；每次改动写原因 |
| 是否信任固件心跳 | 固件维护者认为够用；我读码发现它不会触发 | 我给出复现步骤（断开上位机，观察 `host_online`），固件侧同意后续修；短期我在上位机侧加超时 |
| 坐标系约定 | VR 端、IK 端各用各的 | 开 15 分钟对齐会，画一张图，签字（即记录进文档） |
| 先上全增益还是先低增益 | 同事想快 | 以安全规程为准：第一次上机低增益；用“出问题的代价”说服，而不是争论 |

### 6.3 冲突解决的几条做法

1. **用数据说话**：给出可复现的步骤和日志，而不是“我觉得”；
2. **把分歧变成可检验的问题**：“断开上位机，车会不会停”比“心跳逻辑对不对”更容易达成一致；
3. **承认边界**：不是自己的代码，提供证据与建议，由负责人决定；
4. **小步合入**：改动小、可回滚，评审成本低；
5. **留痕**：接口、阈值、决定写进文档，避免口头约定。

## 7. 经验教训

1. **周期要显式，不能靠“代码跑得快/慢”**；配置频率与实测频率分开记录。
2. **所有“默认动作”都要写成显式代码**：失联、失败、退出；“保持”不等于“安全”。
3. **先量后改，一次只改一件事，用同一回归集复测。**
4. **符号与单位是集成 bug 的第一来源**：写接口文档，写自检脚本。
5. **版本和参数要有唯一事实来源**；锁依赖，参数进配置文件。
6. **读码发现是风险清单，不是成果**；与职责相关的兜底做在自己的节点里，其余如实上报。
7. **分层限幅，越靠近硬件越简单越硬。**
8. **从低增益、空载、有人守着急停开始。**
9. **没有 bag 的实验不算数据**；复现靠 bag + 参数快照 + 哈希。
10. **如果重来**：第一天就锁依赖版本、第一周就搭好回归脚本、给从臂加重力前馈、给里程计融合 IMU yaw、把“实测周期”放进默认日志。

## 8. 工程化英文面试问答（12 个）

**Q1. Walk me through how you took the project from zero to running on hardware.**

> I started from the requirements in measurable terms: end-effector error under five millimetres, a stable leader–follower pair, a base that drives straight, and safe behaviour on lost links. Then I picked existing tools for the heavy parts, such as Mink and the motor library, and wrote the glue and protection myself. I built the base first because it is the simplest chain, then the leader–follower, then VR, and I always went single joint, low gain, no load first. In the last weeks I integrated everything on one hardware node and wrote regression scripts.

中文：把需求量化（末端误差 <5 mm、主从稳定、底盘直行、失联安全）；重活用现成工具（Mink、电机库），胶水与保护自己写；先底盘、再主从、再 VR；总是先单关节、低增益、空载；最后集成到同一硬件节点并写回归脚本。

- *L2：Why that order?* The base has the shortest chain and exposed sign and byte-order problems early, which saved time on the arms. *（底盘链最短，早暴露符号与字节序问题，给手臂省时间。）*

**Q2. How did you choose the loop rates?**

> I worked from the physics and the interfaces. The motor inner loop runs in kilohertz in the vendor firmware, my commands go at 100 to 200 hertz, VR data arrives at about 90 hertz, so sending faster than 100 adds no information. The base speed loop and odometry share a 5 millisecond period. I also kept the CAN bus load under 50 percent, for example about 36 percent per arm at 200 hertz.

中文：从物理与接口出发：电机内环 kHz、我的命令 100–200 Hz、VR 约 90 Hz，所以超过 100 Hz 没有新信息；底盘速度环与里程计共用 5 ms；总线负载 <50%，如每臂 200 Hz 约 36%。

- *L2：What if the loop is slower than the configured step?* The solver integrates a 5 millisecond step, so at 120 hertz the joints move less per cycle than intended and tracking feels slow; so I log the real period. *（求解器按 5 ms 积分，120 Hz 时每周期位移偏小，跟随变慢，所以记录实测周期。）*

**Q3. How do you manage jitter?**

> I sleep to absolute times rather than relative delays so errors do not accumulate, give the hardware node a real-time priority and its own core, and keep heavy work such as logging and visualisation at low priority and low rate. On the microcontroller I move work out of the interrupts: they only copy data, and the task does the processing.

中文：按绝对时刻睡眠使误差不累积；硬件节点用实时优先级和独立核；日志与可视化低优先级低频；单片机中断里只搬数据，处理放任务里。

- *L2：Did you use a real-time kernel?* No; a standard kernel with a real-time priority for the hardware node was enough at 100 hertz. *（没有；100 Hz 下标准内核加实时优先级足够。）*

**Q4. Describe an optimisation you made.**

> The gravity-compensation loop ran at about 120 hertz and the arm felt sticky. I printed the loop period, found the reply wait, per-joint Python loops and printing dominated, so I cut printing to once a second, vectorised the friction term, preallocated the command objects and gave each arm its own thread and bus. The loop reached about 190 to 200 hertz. Then I reran the hover-drift and sign tests to check nothing had changed.

中文：重力补偿循环约 120 Hz、手感发涩；打印周期发现回包等待、逐关节 Python 循环与打印占主导；改打印为 1 Hz、摩擦向量化、预分配命令对象、每臂独立线程与总线；提到约 190–200 Hz；再跑悬停漂移与符号测试确认无变化。

- *L2：How did you know it was the reply wait?* The period matched ten milliseconds of timeout plus compute; shortening the wait changed the period one-for-one. *（周期约等于 10 ms 超时加计算；缩短等待，周期同步变化。）*

**Q5. How do you make sure an optimisation does not break behaviour?**

> A fixed regression set: replay a recorded hand trajectory and compare the end-effector path to within a millimetre, stretch to the boundary to check joint speed, hover for drift, and drive a two-metre line. I only change one thing at a time.

中文：固定回归集：回放录制轨迹对比末端路径 <1 mm、伸向边界查关节速度、悬停查漂移、2 m 直线；一次只改一件事。

**Q6. How did you deal with simulation-to-real differences?**

> I made a table per joint: URDF axis, motor direction, zero offset and limits, and calibrated each with a small single-joint test. The first run on hardware used ten to twenty percent of the gains, half the speed limits, no load, and someone at the emergency stop. Zero offsets, measured by putting both arms in the same calibration pose, were under 0.03 radian.

中文：逐关节建表：URDF 轴、电机方向、零位、限位，用小幅度单关节测试标定；第一次上机增益取 10–20%、限速减半、空载、人在急停旁；零位通过两臂摆到同一标定姿态测得，<0.03 rad。

- *L2：What differed most?* Signs and the two sets of joint limits. *（符号和两套关节限位。）*

**Q7. How did you handle safety?**

> In layers. Targets are limited in space and rate; the solver has joint bounds; the hardware node checks target age, freezing after 100 milliseconds and disabling after 500; the base zeroes on a 300 millisecond command timeout; the motors disable themselves after about a second of bus silence. Start-up aligns the arm to a known pose first, and shutdown ramps torque down instead of cutting it.

中文：分层：目标空间与速率限制；求解器关节界；硬件节点看目标年龄（100 ms 冻结、500 ms 失能）；底盘 300 ms 命令超时归零；电机总线静默约 1 s 自失能；启动先对齐已知姿态，关机渐降力矩而不是直接断。

- *L2：Why ramp down?* An abrupt disable lets the arm fall under gravity. *（直接失能手臂会因重力下坠。）*

**Q8. How do you handle versions and parameters?**

> Parameters live in a YAML file with one owner, not in the code, and each hardware test is tagged with the config hash. Dependencies are pinned. I should say honestly that we did not pin the Mink version at first, so I only claim principles, not version-specific defaults; next time I would pin on day one.

中文：参数放 YAML、有唯一所有者；每次硬件测试打 tag 并记配置哈希；依赖锁版本。坦率说 Mink 版本起初没锁，所以我只讲原理而非某版本的默认；下次第一天就锁。

**Q9. How do you test things you cannot unit-test?**

> Three layers: pure-function unit tests for things like the axis mapping, rotation update, MIT packing at the boundaries and the odometry frame conversion; short hardware-in-the-loop checks per joint; and regression runs on the whole robot. Every fixed fault leaves a reproduction step and a pass criterion.

中文：三层：纯函数单测（轴映射、旋转更新、MIT 打包边界、里程计坐标换算）；单关节硬件在环短测；整机回归；每个修复留复现步骤与通过判据。

**Q10. How do you log and reproduce a bad run?**

> Every real run records a rosbag with targets, joint states and diagnostics at tiered rates, plus the parameter snapshot, the git hash and the measured loop periods. I can replay the bag through the algorithm nodes to reproduce a problem.

中文：每次真机运行录 rosbag（目标、关节状态、分级频率诊断）+ 参数快照 + git 哈希 + 实测周期；可把 bag 回放进算法节点复现问题。

- *L2：What is the minimum you would never skip?* The measured loop period and the target age. *（实测周期与目标年龄。）*

**Q11. Tell me about a disagreement in the team.**

> The firmware owner thought the host heartbeat rule was enough, but reading the code I saw its flag is never updated. I did not argue; I wrote a short reproduction — disconnect the host and watch the counter — and showed it. We agreed the firmware would be fixed later, and in the meantime I added a 300 millisecond command timeout on the host side.

中文：固件负责人认为心跳规则够用，我读码发现标志位从不更新；不争论，写出复现（断开上位机看计数器）并演示；同意固件后续修，期间我在上位机侧加 300 ms 超时。

- *L2：What if they had disagreed?* I would still protect my own node and document the risk for the owner to decide. *（仍保护自己的节点并记录风险，由负责人决定。）*

**Q12. What would you do differently next time?**

> Pin dependencies on day one, build the regression scripts in the first week, add gravity feed-forward on the follower so it does not need a high gain, fuse an IMU yaw into the wheel odometry, and log the measured loop period by default.

中文：第一天锁依赖、第一周建回归脚本、给从臂加重力前馈以免高增益、把 IMU yaw 融入轮式里程计、默认记录实测循环周期。

- *L2：Which is most valuable?* The regression scripts, because they make every later change cheaper to check. *（回归脚本，因为让之后每次改动都更便宜地验证。）*

## 9. 速记 / 自测 / 链接

### 要点速记

1. 流程：需求量化 → 现成件 + 自写胶水与保护 → 先单点后串联 → 先低增益后全增益 → 回归。
2. 频率：电机内环 kHz → 命令 100–200 Hz → 目标 100 Hz → VR 90 Hz；底盘速度环与里程计 5 ms。
3. 总线负载 <50%：每臂 16 帧/周期≈1.78 ms，200 Hz 约 36%。
4. 抖动：绝对时刻睡眠、实时优先级、日志低优先级、中断只搬数据。
5. 优化六步：现象、度量、瓶颈、改动、前后、回归；一次只改一件事。
6. 14 类工程问题：接口、坐标、版本、参数、仿真到实机、安全、日志、测试。
7. 分歧用数据与复现解决，承认边界，留痕。
8. 配置频率 ≠ 实测频率；默认动作显式；读码发现 ≠ 成果。

### 自测题

1. 为什么命令频率不应高于信息源频率？（更快的命令只是重复数据，不增加信息，反而占资源）
2. 每臂 200 Hz 的总线负载是多少？（16 帧 × 111 µs × 200 ≈ 36%）
3. 为什么按绝对时刻睡眠？（误差不累积，周期平均值准确）
4. 板端 PID 为什么必须固定周期？（没有显式乘 dt，增益绑定调用周期）
5. “先低增益”的具体做法？（增益 10%–20%、限速减半、空载、人在急停旁）
6. 回归集包含什么？（回放轨迹对比、伸向边界、悬停漂移、2 m 直线）
7. 分层限幅各层是什么？（目标端、IK、硬件节点、底盘板、电机/驱动器）
8. 如果重来，最先做的三件事？（锁依赖、建回归脚本、默认记录实测周期）
