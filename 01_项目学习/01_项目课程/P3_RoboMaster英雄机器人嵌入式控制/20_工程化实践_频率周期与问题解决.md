## 1. 项目从零到上线：需求、选型、架构、里程碑

### 1.1 需求：从比赛任务到控制需求

英雄机器人的任务（见 [01 章](./01_RoboMaster比赛背景与英雄机器人任务.md)）是：在裁判系统限制热量、底盘功率和弹速的前提下，用 42 mm 大弹丸稳定命中。把它翻译成电控需求，是整个项目的起点：

| 比赛任务 | 电控需求 | 量化目标（本项目取值） |
|---|---|---|
| 稳定瞄准、跟踪移动目标 | 云台角度稳、响应快、跟随视觉目标 | 外环带宽 4–5 Hz，匀速目标稳态滞后小于 0.5° |
| 每发弹丸都有效 | 弹速一致、不超限 | 弹速 15.7–16.0 m/s，离散约 ±0.3 m/s |
| 连续供弹不卡 | 拨盘定步长、可检测堵转 | 单发约 150 ms，堵转 1 s 内识别 |
| 机动同时不触发功率惩罚 | 功率估计与缩放 | 功率上限取裁判值减 5 W，缓冲能量不跌破 10 J |
| 不失控、不伤人 | 安全状态与离线检测 | 关键源 50–100 ms 内判离线并 RELAX |
| 队内多人协作 | 清晰接口、可复现 | 板间帧、视觉帧定义成文；每次调参可回溯 |

> **提示**：面试里先讲"需求量化"比先讲算法更有说服力：你不是"调了一个 PID"，而是为明确的指标选了方案。

### 1.2 方案选型

| 决策 | 备选 | 选择与理由 |
|---|---|---|
| 主控 | 开发板 C 型（F407）／自研板／H7 | 开发板 C 型（STM32F407IGH6，168 MHz，带 FPU，两路 CAN，BMI088 板载）：成熟、队内已有驱动、省去硬件风险 |
| 板数 | 单板／双板 | 双板（云台板＋底盘板）：云台和底盘机械上分离，滑环走线少，各自 CAN1 负载低；代价是需要定义板间协议并处理失联 |
| 操作系统 | 裸机＋定时器中断／FreeRTOS | FreeRTOS：多个事件源（IMU、DBUS、裁判、视觉）与周期任务并存，通知与队列使同步清晰；代价是调度抖动与栈开销 |
| 姿态估计 | 模块自带／Mahony／Madgwick／Kalman | Mahony：计算量小、参数少（Kp、Ki），可解释；无磁力计，yaw 只做相对使用 |
| 云台控制 | 单环 PID／串级 PID／模型控制 | 串级 PID：陀螺直接给角速度，免微分，扰动抑制强，调参顺序明确 |
| 摩擦轮控制 | PID／变增益／滑模 | 先 PID，随着连发掉速问题暴露，迭代到变增益再到滑模（见 [08 章](./08_从PID到变增益PID再到滑模控制.md)）|
| 功率控制 | 简单限速／功率模型＋缩放 | 模型＋缩放：统一缩放四轮速度，保持运动方向 |
| 视觉通信 | 串口／USB CDC | USB CDC 虚拟串口，帧头＋CRC，视觉 100 Hz 下行、电控 200 Hz 上行 |

选型的共同原则：**先选能量化验证的方案；每次升级方案都要有一个能度量的现象作为理由**。这条原则贯穿后面的迭代记录。

### 1.3 架构

```text
   遥控器 DR16 ──DBUS──┐                              ┌── 视觉小电脑（USB CDC）
   裁判系统 ──UART──────┤                              │
                        v                              v
   ┌────────────────── 云台板 (F407) ──────────────────┐
   │ INS(1kHz) | Gimbal+Shoot(3ms) | Detect(10ms) | USB/Decode │
   └───────┬─────────────────────────────┬─────────────┘
           │CAN1: yaw/pitch GM6020,        │CAN2 (1 Mbps): 0x301 @100Hz → / ← 0x302 @50Hz
           │摩擦轮×2, 拨盘 (M3508)          v

        云台、发射机构               │ Chassis(3ms) | Detect(10ms) | 裁判解析 │
```

数据流的三条主线（详见 [02 章](./02_整机电控架构与数据流.md)）：**操作/视觉目标 → 云台与发射；云台相对角 → 底盘跟随；裁判功率与缓冲 → 底盘缩放**。

## 2. 频率与周期总设计

### 2.1 总表

| 层 | 事件／任务 | 周期或频率 | 触发方式 | 说明 |
|---|---|---|---|---|
| 传感器 | BMI088 陀螺／加速度计 | 约 1 kHz 数据率 | DMA 完成中断 → 任务通知 | INS 任务被通知唤醒；执行约 0.25 ms |
| 传感器 | 电机反馈（每个电机） | 1 kHz | CAN 接收中断 | 解码在回调中完成，只写缓存与时间戳 |
| 控制 | 云台＋发射任务 | 约 3 ms（约 333 Hz） | 循环内三处 1 tick 延时 | 外环、内环在同一次调用内顺序执行 |
| 控制 | 底盘任务 | 约 3 ms（约 333 Hz） | 同上 | 运动学、功率缩放、轮速 PID |
| 通信 | CAN 命令帧（0x200、0x1FF） | 约 333 Hz | 控制任务末尾发送 | 帧间加 1 tick 间隔，避免占满邮箱 |
| 通信 | DBUS 遥控 | 约 71 Hz（14 ms 一帧） | UART 空闲中断＋DMA | 一帧 18 字节 |
| 通信 | 裁判系统 | 50 Hz 量级（各类消息不同） | UART 空闲中断＋DMA | 功率、缓冲、弹速、热量 |
| 通信 | 视觉 → 电控 | 100 Hz | USB CDC 接收通知 | 目标误差角＋时间戳＋fire_command |
| 通信 | 电控 → 视觉 | 200 Hz | 云台任务内分频 | 当前姿态、四元数、弹速、模式 |
| 通信 | 板间 0x301（云台→底盘） | 100 Hz | 云台任务分频 | vx、vy、底盘模式、相对 yaw |
| 通信 | 板间 0x302（底盘→云台） | 50 Hz | 底盘任务分频 | 弹速、热量、功率上限、缓冲能量、底盘 IMU pitch |
| 监控 | detect 离线检测 | 10 ms | 周期任务 | DBUS／视觉／板间 100 ms，电机 50 ms |
| 外围 | UI／LED／电容 | 20–100 ms | 周期任务 | 最低优先级 |
| 日志 | 调试日志（RTT／串口） | 不阻塞控制任务，批量输出 | 低优先级任务 | 控制任务只写环形缓冲 |

> **面试要点**：这张表里最重要的是第一行与"控制"两行的对照——**传感器约 1 kHz，控制任务约 333 Hz**。你不是在说"控制频率 1 kHz"；你说的是"姿态更新约 1 kHz，控制任务约 3 ms"。

### 2.2 为什么是 3 ms：它是怎么形成的

控制任务循环里有三处 `vTaskDelay(1)`（tick 为 1 ms）：读取反馈之后、计算之后、发送之后各一处。每处至少等一个 tick 边界，所以一圈约 3 ms（见 [03 章 4.2 节](./03_FreeRTOS任务设计与时序.md)）。这是**先有现象、后有设计**的典型例子：

1. 起初这三处延时是为了避免 CAN 邮箱被占满、让出 CPU；
2. 调参是在这个周期下完成的，增益里已经吸收了周期（PID 没有显式乘 dt，见 [12 章](./12_数字PID实现.md)）；
3. 一旦周期被"设计"成 3 ms，就不应该随手改动。改动周期等于换了一套增益。

所以我们的做法是：**在 3 ms 下把所有环整定一次，周期作为参数记录在版本里；任何改变任务延时的提交都要回归云台阶跃与扰动测试。**

### 2.3 为什么不一味追求更快

更快的周期有收益也有代价：

| 周期 | 收益 | 代价 |
|---|---|---|
| 1 ms（1 kHz） | 延迟小、相位裕度大 | CAN 命令帧 1 kHz：云台板负载升到约 78%；CPU 利用率翻倍；任务切换开销占比大 |
| 3 ms（333 Hz） | CAN 负载约 63%；CPU 约 50%；足够 35 Hz 内环 | 采样与带宽之比约 9.5，处在经验下沿；延迟是 1 ms 方案的 3 倍 |
| 5 ms（200 Hz） | 负载低 | 采样与带宽比降到 5.7，35 Hz 内环不可行，需降带宽 |

结论：3 ms 是一个在 CAN 负载、CPU、相位裕度之间取到的可接受点；若要把内环带宽再提高，**先把周期固定并缩短**（例如用 `vTaskDelayUntil` 做 2 ms 固定周期），而不是先调增益。

## 3. 延迟预算、CPU 利用率与 CAN 负载（手算）

### 3.1 云台内环的延迟预算

目标：回答"采样到指令生效，总共多久，对 35 Hz 内环有多大的相位代价"。取值（设计取值）：

| 环节 | 平均 (ms) | 最坏 (ms) | 说明 |
|---|---|---|---|
| IMU 数据年龄（含 INS 计算约 0.25 ms） | 0.5 | 1.0 | 数据率 1 kHz，异步读取最新值 |
| 控制任务内：读反馈到发送命令 | 2.0 | 3.0 | 三处 1 tick 延时中的两处位于其间 |
| CAN 传输＋电调响应 | 0.3 | 0.5 | 111 µs 帧时间加驱动处理 |
| 纯延迟合计 | 2.8 | 4.5 | 0.5+2.0+0.3；最坏 1.0+3.0+0.5 |
| 零阶保持（半个采样周期） | 1.5 | 1.5 | $T/2$ |

相位滞后 $\phi=360^\circ f\,T_d$。取纯延迟 2.8 ms、频率 35 Hz：$\phi_d=360\times35\times0.0028=35.3^\circ$；零阶保持 $360\times35\times0.0015=18.9^\circ$；合计约 **54°**。[12 章](./12_数字PID实现.md) 只统计了控制任务内的 2 ms 与零阶保持（合计约 44°），这里把传感器数据年龄与 CAN／电调也算入，所以更大。结论一致：**35 Hz 已接近这个周期下的上限**，继续提高内环带宽会使相位裕度不足、出现高频嗡鸣。

### 3.2 CPU 利用率

用设计取值做利用率估算（教学推算，执行时间见 [03 章](./03_FreeRTOS任务设计与时序.md) 任务表）：

| 任务／中断 | 执行时间 | 频率 | 利用率 |
|---|---|---|---|
| INS | 0.25 ms | 1 kHz | 25% |
| 云台＋发射 | 0.3 ms | 333 Hz | 10% |
| 底盘（仅底盘板） | 0.2 ms | 333 Hz | 6.7% |
| CAN 接收中断（5 个电机反馈） | 约 5 µs/帧 | 5 kHz | 2.5% |
| 视觉解码＋裁判解析 | 约 0.1 ms | 150 Hz | 1.5% |
| detect | 0.05 ms | 100 Hz | 0.5% |
| UI／LED／电容 | 1 ms | 20 Hz | 2% |
| 合计（云台板） | | | 约 **42%**（再加调度开销约 5%，即 **约 47%**） |

按经验，实时系统的总利用率保持在 50%–70% 以下，留给突发（USB 大包、日志）。我们的云台板大约 47%，有余量；这也是我们没有急着把所有东西搬到 DMA 链上的原因。

### 3.3 CAN 总线负载

单帧名义 111 位，1 Mbps 下 111 µs（最坏 135 µs）。

**云台板 CAN1（5 个电机：yaw、pitch、左右摩擦轮、拨盘）**：

- 反馈：5 帧 × 1 kHz × 111 µs = 555 µs／ms，即 55.5%；
- 命令：0x200（摩擦轮＋拨盘）与 0x1FF（GM6020）各约 333 Hz，即 2 × 333 × 111 µs = 74 µs／ms，即 7.4%；
- 合计约 **63%**（最坏填充 $5\times135+2\times0.333\times135=765$ µs，约 76%）。

**如果命令也按 1 kHz 发送**：命令占 2 × 111 = 222 µs，合计 777 µs，即 **78%**（最坏约 95%）。这就是命令帧按控制周期（约 333 Hz）而不是 1 kHz 发送的原因，见第 5 节的优化 6。

**底盘板 CAN1（4 个 M3508）**：反馈 4 × 111 = 444 µs；命令 0x200 约 333 Hz，约 37 µs；合计约 **48%**。

**板间 CAN2**：0x301 为 8 字节 × 100 Hz，0x302 为 8 字节 × 50 Hz，共 150 帧／s，约 16.7 kbps，**低于 2%**。

> **提示**：CAN 负载的手算，面试时可以在白板上做；关键是写出"帧数 × 帧时间 ÷ 1 s"。

## 4. 云台、发射、底盘各环的频率与取舍

### 4.1 云台

```text
目标(100 Hz, 视觉/遥控) ──低通+限速──> 外环 P (3 ms) ──> 内环 PI (3 ms) ──> CAN 0x1FF
                                           ^                  ^
                          IMU 姿态 (1 kHz, 取最新)      IMU 陀螺 (1 kHz, 取最新)
```

| 项 | 取值 | 取舍 |
|---|---|---|
| 外环 | 比例，yaw Kp=28、pitch Kp=25 (1/s)；限幅 240／120 °/s | 近似一阶，带宽 $\approx K_p/2\pi$：yaw 4.5 Hz，pitch 4.0 Hz |
| 内环 | PI，yaw 3200／10，pitch 2800／8；积分限幅 3000；输出限幅 30000 | 带宽约 30–40 Hz；受 54° 相位代价与电流限幅限制 |
| 内外环频率比 | 同一周期内调用，靠增益分离 | 内环带宽约为外环 7–8 倍，处于 6–8 倍设计范围 |
| 视觉目标 | 100 Hz 输入，一阶低通＋限速 | 目标更新（10 ms）慢于控制（3 ms），中间保持上次值，不做外推 |
| 前馈 | 重力约 3500；视觉速度前馈 0.6 | 前馈降低反馈的负担，也降低对高增益的需要 |

**为什么外环不更快**：外环若超过内环带宽的 1/4（即约 9 Hz），二阶近似下阻尼比降到 0.5 以下，出现超调并受内环延迟影响而失稳；4–5 Hz 同时满足"跟得上人手遥控与匀速目标"和"留足裕度"。

### 4.2 发射

| 回路 | 周期 | 取值 | 说明 |
|---|---|---|---|
| 摩擦轮速度环 | 3 ms | 滑模：c=5、ρ=2、ε=1，输出限幅 10000 | 掉速后恢复约 60–80 ms，约 20–27 个控制周期 |
| 弹速反馈 | 事件（每发后更新） | >16.0 m/s 减 50 rpm；<15.7 m/s 加 50 rpm | 慢速外层修正，不是闭环；依赖裁判上报延迟 |
| 拨盘位置环 | 3 ms | Kp=0.1，输出限幅 2500 rpm | 目标为累计计数 |
| 拨盘速度环 | 3 ms | Kp=8、Ki=0.3，电流限幅 10000 | 内环 |
| 堵转判据 | 3 ms 检查，窗口 1000 ms | 残余误差 >5000 计数 | 约 333 个周期的持续判断 |
| 发射状态机 | 3 ms | READY／FIRE／SHOOT_FAIL 等 | 热量门＋间隔门（500 ms） |

恢复 60–80 ms 对应的是约 20–27 个周期，足以让速度环完成一次完整调节；若周期太慢（例如 10 ms），一次恢复只有 6–8 个样本，滑模的切换会变得粗糙，抖振变大。

### 4.3 底盘

| 回路 | 周期 | 取值 | 说明 |
|---|---|---|---|
| 轮速环 | 3 ms | PID，M3508（19.2:1），转子限速 8000 rpm | 电流环在 C620 电调内 |
| 功率估计与缩放 | 3 ms | 模型常数 R0=0.0512、K0=0.0019、P0=16.4817；上限取裁判值减 5 W | 裁判功率 50 Hz，相邻 6–7 个周期不更新 |
| 缓冲能量门 | 3 ms | 60 J 满；<30 J 额外压缩；<10 J 强降到 0.3 倍 | 由裁判 50 Hz 值驱动 |
| 缩放恢复斜率 | 每周期 +0.01 | 约 0.3 s 回到 1 | 下降立即，恢复渐进 |
| 底盘跟随 | 3 ms | Kp=4.0、Kd=0.2，输出限 6 rad/s，死区 2° | 输入为 0x301 里的相对角 |
| 小陀螺 | 3 ms | 约 3.5 rad/s，周期 1.8 s | 功率紧时 wz 先降 |

**重要的异步问题**：裁判功率 50 Hz（20 ms），而控制 3 ms，意味着功率反馈在 6–7 个周期内是"旧值"。我们的做法是用本地电机反馈（电流与转速，1 kHz 更新）经模型预测功率需求，裁判值只作修正与上限依据；所以功率估计的新鲜度由本地反馈保证，而不是裁判。

## 5. 赛季迭代：八次优化的完整过程

每次优化按"现象 → 度量方法 → 瓶颈 → 改动 → 前后对比 → 回归验证"书写。数字是本项目设计取值（与自查表一致），不是实测记录。

### 优化 1：摩擦轮连发掉速 → 弹速离散（PID → 变增益 PID → 滑模 → 弹速反馈）

- **现象**：连发时第 2、3 发弹速偏低，离散约 ±1 m/s，偶尔低于有效射程要求；也有个别发接近 16 m/s 上限。
- **度量方法**：同时记录左右轮转速（CAN 反馈）、裁判上报弹速（每发一条）、电池电压；对每发计算"出膛时刻轮速"；统计 30 发的均值与离散。
- **瓶颈**：每发弹丸带走动能，轮速跌落约 600–900 rpm；PID（Kp=12、Ki=0.2）恢复约 120 ms，几乎吃满约 150 ms 的射击间隔。瓶颈不是噪声而是**恢复速度与负载扰动**。
- **改动**：(1) 变增益 PID，$K_p=\log_{10}(8|e|)+5$：大误差处增益大，恢复快一些，但近零误差处增益过低或过高；(2) 滑模（c=5、ρ=2、ε=1，限幅 10000）；(3) 加弹速分档反馈（>16.0 减 50 rpm，<15.7 加 50 rpm）。
- **前后对比**：恢复 120 ms → 60–80 ms；离散 ±1 → ±0.3 m/s；赛前实测 15.2–16.0 m/s；满电曾 2 次 16.2 m/s，引入下调后不再超限。
- **回归验证**：每次改动后跑"30 发连发"脚本，要求离散不大于 ±0.4 m/s、最大不超 16.0；并在低电量（电压低约 1 V）下重跑一次。

### 优化 2：拨盘堵转检测与恢复

- **现象**：大弹丸偶发卡在拨盘与弹道之间，电机堵转发热，射击中断。
- **度量方法**：记录拨盘目标计数与实际计数的残余误差、电流、温度。
- **瓶颈**：只看电流会误判（起步电流本来就大），只看位置没有时间判据会误判慢速；必须"误差＋持续时间"。
- **改动**：残余误差 >5000 计数且持续 >1000 ms 判堵转；反向 52450 计数（两格）只试一次；再失败进入 SHOOT_FAIL，停止发射并上报。
- **前后对比**：此前卡弹后需要手工断电；此后偶发卡弹 1–2 s 内自动恢复，持续卡死则明确失败而不是烧电机。
- **回归验证**：台架人为卡弹 10 次，成功恢复次数；人为长期卡死，确认只反退一次并进入失败态；回归时同时验证 RELAX 零电流。

### 优化 3：yaw 在 ±180° 跳变

- **现象**：自瞄切换或目标越过 ±180° 时，云台突然反向大转。
- **度量方法**：记录目标角、反馈角、误差；复现越界。
- **瓶颈**：目标滤波对角度做算术平均，179° 与 −179° 平均成 0°；误差未折回。
- **改动**：误差统一折到 (−180°, 180°]；滤波用 sin／cos 分别低通再 atan2；视觉丢失 100 ms 后目标角保持当前值。
- **前后对比**：越界处的突跳消失。
- **回归验证**：加入"绕圈"测试：目标以 30 °/s 匀速绕圈 3 圈，误差全程连续、绝对值不超过 2°。

### 优化 4：视觉跟踪滞后（速度前馈）

- **现象**：目标匀速横移时枪口落在目标后面，反向时冲过头。
- **度量方法**：让目标以 20 °/s 运动，用时间戳对齐视觉帧与电控回传姿态，计算"枪口与目标真实位置的差"。
- **瓶颈**：两部分——视觉延迟 30–50 ms（40 ms 内目标多走 0.8°）；纯 P 外环对斜坡输入的稳态误差 $v/K_p$。
- **改动**：延迟补偿放在视觉侧（时间戳＋回传姿态）；电控侧只对目标做一阶低通与限速，并速度前馈系数 0.6（取小于 1，避免放大视觉速度噪声）。外环 Kp 也由较低值提到 yaw 28，使 4.5 Hz 的带宽和斜坡滞后同时满足：$20/28=0.71°$，加 0.6 前馈后 $(1-0.6)\times20/28=0.29°$。
- **前后对比**：稳态滞后 0.71° → 0.29°（教学推算，与 [11 章](./11_调试与实战故障案例.md) 一致）。
- **回归验证**：匀速靶与反向靶各跑一次；要求滞后不超过 0.5°、反向过冲不超过 1°。

### 优化 5：功率限制触发后底盘抖动

- **现象**：功率限制触发时，缩放因子在 1 与小值之间来回跳，底盘一顿一顿。
- **度量方法**：记录缩放因子 $k$、裁判功率、缓冲能量；看 $k$ 的时间序列。
- **瓶颈**：缩放下降和恢复对称，功率回落后立刻回弹，再次超限，形成振荡。
- **改动**：下降立即生效，恢复限斜率每周期 +0.01（约 0.3 s 回到 1）；底盘跟随加 2° 死区，避免在功率压缩时 wz 来回抖动。
- **前后对比**：$k$ 的来回翻转消失，缓冲能量最低值从约 8 J 提升到约 25 J（设计取值）。
- **回归验证**：满载机动＋小陀螺 60 s，要求缓冲能量最低值大于 10 J。

### 优化 6：CAN 命令帧按控制周期发送

- **现象**：联调视觉时偶发 CAN 发送失败计数增加，电机反馈偶有丢帧。
- **度量方法**：统计发送邮箱满的次数、接收帧计数差、总线负载（逻辑分析仪或 CAN 分析仪）。
- **瓶颈**：控制周期内多次发送命令（遥控、板间帧、命令帧叠加），云台板负载估算在最坏情形接近 95%。
- **改动**：同组电机命令合并为一帧，每控制周期只发一次（约 333 Hz，而不是 1 kHz）；帧间加 1 tick 间隔；板间帧分频到 100／50 Hz。
- **前后对比**：云台板 CAN1 负载 78% → 63%；发送失败计数归零。
- **回归验证**：连续运行 10 分钟，发送失败计数为 0，反馈帧间隔最大值小于 3 ms。

### 优化 7：IMU 零偏与恒温

- **现象**：开机后 yaw 缓慢漂移，比赛后段云台指向偏。
- **度量方法**：静置 10 分钟，记录 yaw 变化；改变环境温度对比。
- **瓶颈**：陀螺零偏随温度漂移；启动标定的零偏在温度变化后失效。
- **改动**：加热电阻 PID 把 IMU 恒温在 40 °C；上电静止采 2000 个样本求零偏；未启用磁力计，yaw 只做相对使用。
- **前后对比**：静置漂移约 1 °/min 量级（约 0.017 °/s）。
- **回归验证**：每次上电后做 2 分钟静置检查；漂移超过 0.05 °/s 则重新标定。

### 优化 8：积分限幅与卡住后的过冲

- **现象**：云台被卡住（或被手按住）后松开，会大幅过冲。
- **度量方法**：人为按住云台 3 s 后松开，记录积分状态与角度。
- **瓶颈**：无积分限幅时积分累到约 17000，松手后需很久才释放。
- **改动**：内环积分限幅 3000；RELAX 清积分与历史。
- **前后对比**：过冲显著减小，释放时间由约 1 s 降到不到 0.2 s（教学仿真口径）。
- **回归验证**：每次改内环参数后重做"按住－松开"测试。

> **面试要点**：讲优化时，一定要先说**度量方法**。"我先看数据，再动参数"比"我把 Kp 调大了"更能体现工程素养。

| # | 类别 | 问题 | 定位 | 解决 |
|---|---|---|---|---|
| 1 | 联调 | 板间 CAN 帧字节序不一致，底盘收到的 vx 为乱码 | 逻辑分析仪看原始帧，对照两端定义 | 帧定义写成共享头文件，小端固定，加版本字节 |

| 7 | 安全与保护 | 电机过热保护 | 读温度字节 | 温度超限降低电流限幅；SHOOT_FAIL 停止拨盘 |
| 8 | 日志与复现 | 赛场上现象无法复现 | 缺少日志 | 控制任务写环形缓冲，低优先级任务批量输出；关键事件（离线、堵转、缩放）带时间戳 |
| 9 | 测试方法 | 改一处影响另一处，没人知道 | 无回归 | 建立固定回归清单（阶跃、扰动、连发、满载机动），每次发布前全跑 |
| 10 | 实时性 | 用调试器断点停住后，恢复时所有电机被判离线 | 对比断点前后时间戳 | 调试时关闭离线检测或使用半主机输出；断点后重新使能 |
| 11 | 栈与内存 | 偶发 HardFault，只在视觉开启时出现 | 打开栈水位检查 | 解码任务栈从 256 words 加到 512；高水位监控输出 |
| 12 | 命名坑 | `given_current` 与 `give_current` 混用，写入了反馈量 | 阅读代码与单步调试 | 命名规范化：反馈用 `fdb_`，命令用 `cmd_`；见 [11 章案例 8](./11_调试与实战故障案例.md) |
| 13 | 硬件 | 电机偶发离线 | 万用表与观察 | 偏线重压、供电线加粗、加滤波电容；离线检测兜底（见 STAR 4） |

### 6.1 问题 5 展开：仿真到实机

仿真和实机的差异常被低估。我们的做法是：仿真的第一步不是调参，而是**让仿真和实机的时间结构一致**：控制周期 3 ms，反馈延迟 2 ms，电流环用一阶近似（时间常数约 4 ms），命令限幅与实机相同。在这个仿真里调出的参数，到实机上只需要微调。反过来，如果仿真里是 1 ms 无延迟，调出的滑模增益到实机就会抖。

### 6.2 问题 8 展开：日志与复现

日志的设计原则：

1. 控制任务**只写**环形缓冲，不做格式化、不阻塞；
2. 低优先级任务批量输出，输出带宽远低于总线带宽，不影响控制；
3. 关键事件（离线、堵转、缩放触发、模式切换）写入"事件日志"，附时间戳；
4. 日志头写入固件哈希与参数版本，保证"现象 ↔ 版本 ↔ 参数"可对应；
5. 赛场用的是精简日志，台架调试用完整日志，两者通过宏切换。

### 6.3 问题 9 展开：测试方法

测试分四层：

| 层 | 内容 | 频率 |
|---|---|---|
| 单元（PC 上） | PID、滤波、运动学函数，Python 或 C 对拍 | 每次改算法 |
| 台架 | 单机构阶跃、扰动、连发 | 每次改参数 |
| 整机 | 满载机动、跟随、小陀螺、联调视觉 | 每个里程碑 |
| 回归清单 | 固定 12 项，全部通过才能发布 | 每次发布前 |

回归清单（设计取值）：(1) 云台 30° 阶跃；(2) 云台推扰动；(3) 越界绕圈；(4) 连发 30 发弹速统计；(5) 人为卡弹；(6) 满载机动缓冲能量；(7) 遥控断开；(8) 视觉断开；(9) 板间断开；(10) 电机断线；(11) 上电静置漂移；(12) 10 分钟连续运行的总线计数。

## 7. 赛场与赛前调试

### 7.1 赛前一周

- 冻结功能，只改参数与 bug；每次改动对应一个提交；
- 完整回归清单每天跑一遍；
- 两套电池各做一次弹速测试，记录满电与低电压下的差异（满电曾出现 16.2 m/s，因此下调逻辑必须在）；
- 备份全部参数与固件，标记比赛版本。

### 7.2 赛场当天流程

| 时间点 | 动作 | 目的 |
|---|---|---|
| 到场 | 检查接线、插头、CAN 终端电阻 | 偏线是最常见的离线原因 |
| 候场 | 上电，静置 2 分钟，检查 yaw 漂移与 IMU 恒温 | 保证零偏标定有效 |
| 候场 | 电机方向与零位自检 | 搬运可能碰歪线或机构 |
| 候场 | 弹速测试 10 发，核对 15.7–16.0 m/s | 场地电压与电池状态可能不同 |
| 候场 | 安全态测试：拔遥控、断视觉 | 确认 RELAX 有效 |
| 上场前 | 固件版本核对（日志头哈希） | 保证上的就是测试过的版本 |
| 场间 | 只做必要修复，不改参数 | 避免引入新变量 |

### 7.3 赛中与赛后

- 赛中遇到异常：先看事件日志，再决定是否需要在场间处理；不在场间改控制算法；
- 赛后：下载日志，写一份"事件—原因—处理"记录，把有价值的现象沉淀成回归项。

### 7.4 一个典型的场间处理

某场后发现拨盘偶发堵转，事件日志显示连续两次堵转后进入 SHOOT_FAIL。分析：弹丸批次偏大。处理：场间只放宽该批弹丸不进弹道的清理，不改阈值；赛后再评估是否需要把反退步数或时间窗调整，并加入回归项。这体现了赛场上"只修不改"的纪律。

## 8. 版本管理与参数管理

### 8.1 Git 规范

| 项 | 做法 |
|---|---|
| 分支 | main（可比赛）、dev（集成）、feature/xxx（单一功能） |
| 提交 | 小而单一；参数改动单独提交；信息写"改什么＋为什么＋验证了什么" |
| 标签 | 每个里程碑一个；比赛固件打 `match-YYYYMMDD` 标签并冻结 |
| 评审 | 涉及共享接口（板间帧、视觉帧、任务周期）的改动需要另一人看 |
| 禁止 | 在 main 上直接提交；赛前最后两天合并新功能 |

### 8.2 参数管理

所有可调参数集中在一个头文件，按机构分段（云台、发射、底盘、功率、检测）。每个参数有：名称、单位、默认值、含义。每次调参的日志头写入"提交哈希＋参数文件哈希"。好处：任何一条日志都能还原当时的固件与参数。

### 8.3 硬件版本

接线、电调固件版本、电机 ID 表也要登记。不同车（英雄车、3V3 车）的 ID 与限幅不同，用编译宏区分，避免把一辆车的参数烧到另一辆。**3V3 比赛是团队成绩**；我的贡献是把同一套控制代码和调参流程移植到参赛车上，并在赛前调参。

### 8.4 发布清单

1. 回归清单 12 项通过；
2. 参数文件哈希、固件哈希写入发布记录；
3. 版本标签已创建；
4. 备份到两个位置；
5. 场地上用的就是标签版本。

## 9. 团队分工与冲突解决

### 9.1 分工

| 角色 | 职责 | 与我的接口 |
|---|---|---|
| 机械 | 结构、云台、发射机构、底盘 | 减速比、转动惯量、零位、极限位置 |
| 视觉 | 目标检测、跟踪、预测 | USB 协议：目标相对云台的误差角＋时间戳；我回传姿态与弹速 |
| 策略／操作 | 战术、遥控习惯 | 模式定义、灵敏度 |
| 电控（我负责三类回路） | 云台、发射、底盘 | 与其他电控成员的任务划分与板间协议 |

### 9.2 三个冲突与解决

**冲突 1：延迟补偿归谁**

- 视觉认为"电控应根据延时往前预测"，电控认为"视觉有时间戳，应该由视觉预测"。
- 解决：用同一匀速靶，分别试"视觉补偿"与"电控外推"，比较稳态滞后；视觉侧补偿的滞后更小，且电控外推会放大噪声。结论写入接口文档：视觉补偿，电控只低通＋限速。

**冲突 2：机械要求极限行程，电控担心撞限位**

- 机械希望 pitch 行程尽量大；电控发现极限处会撞机械限位导致电流堵转。
- 解决：电控加软限位（在机械限位内收 2°），机械在限位处加缓冲；双方在文档中共同登记限位角。

**冲突 3：赛前改参数 vs 冻结**

- 操作手希望赛前一天再提高灵敏度；电控希望冻结。
- 解决：把灵敏度作为遥控参数（运行时可调、不改固件），固件冻结；操作手在遥控参数范围内自由调整。

### 9.3 协作的做法

- 接口写成文档，改接口必须通知；
- 联调用"同一个测试"比较方案，避免意见之争；
- 记录决策与原因，赛后复盘时可追溯；
- 对不是自己写的模块，如实说明理解范围，不夸大贡献。

## 10. 经验教训

1. **周期是控制器的一部分**：先固定周期、再整定增益；改周期等于换一套参数。
2. **先度量后改动**：每次改动都要有"前、后"数据；没有数据的改动不要合并。
3. **安全态要先于功能**：RELAX、离线检测、限幅在功能之前完成。
4. **接口用数据和文档解决**：冲突时用同一测试比较，而不是争论。
5. **仿真要与实机同构**：时间结构（周期、延迟）一致，才有意义。
6. **版本与参数可追溯**：任何现象都能还原到固件与参数。
7. **赛场只修不改**：场间不改算法，只做可控的修复。
8. **诚实标注**：写明哪些是设计取值、哪些是实测；记不清就用模板，不编数字。
9. **留余量**：CAN 负载、CPU、相位裕度都要留余量，突发总会来。
10. **把现象沉淀成回归项**：每个故障都应该变成一个回归测试。

## 11. 12 个工程化英文面试问答

**Q1. How did you decide the control frequency?**

- **L1**: "Our control task ran at about 3 milliseconds, around 333 hertz. It came from three one-tick delays in the loop, and then I tuned all the gains at that period, so it became part of the design. The attitude task runs separately at about 1 kilohertz."
- **L2** — *Why not faster?* "A 1 kilohertz command rate would raise the gimbal board's CAN load from about 63 to 78 percent and double the CPU load. At 3 milliseconds the sampling is about ten times the 35 hertz inner bandwidth, the lower end of the usual rule."
- **L3** — *What would you do to go faster?* "I would first fix the period with `vTaskDelayUntil` and measure jitter, and only then raise the inner gains."

中文：约 3 ms/333 Hz，由三处 1 tick 延时形成，在此周期下整定；1 kHz 会让 CAN 负载 63%→78%；要更快先固定周期并测抖动。

**Q2. How did you budget latency for the gimbal inner loop?**

- **L1**: "I added the sensor data age, about half a millisecond on average, the in-loop delay from reading feedback to sending the command, about 2 milliseconds, and the CAN plus driver, about 0.3 milliseconds. That is about 2.8 milliseconds."
- **L2** — *What does it cost?* "At 35 hertz, 2.8 milliseconds is about 35 degrees of phase; the zero-order hold adds about 19, so about 54 degrees in total."
- **L3** — *What did you conclude?* "That 35 hertz is near the limit at this period; to go higher I need a shorter fixed period, not just more gain."

中文：数据年龄+环内 2 ms+CAN/电调≈2.8 ms；35 Hz 处 35°+ZOH 19°≈54°；已近上限。

**Q3. How did you estimate the CAN bus load?**

- **L1**: "A standard frame is about 111 bits, 111 microseconds at 1 Mbps. On the gimbal board there are five motors reporting at 1 kilohertz plus two command frames at about 333 hertz, so about 63 percent."
- **L2** — *What is the worst case?* "With worst-case bit stuffing, 135 microseconds per frame, about 76 percent."
- **L3** — *What did you change to keep it low?* "I merged the commands of a motor group into one frame and sent them once per control cycle, and divided the board-to-board frames to 100 and 50 hertz."

中文：111 µs/帧；云台板 63%（最坏 76%）；命令合并并按控制周期发，板间分频。

**Q4. Walk me through one optimization from symptom to regression test.**

- **L1**: "Continuous fire: the muzzle speed spread was about plus or minus 1 metre per second. I logged wheel speed, reported bullet speed and battery voltage per shot, and found the wheel dipped 600 to 900 rpm and recovered in about 120 milliseconds."
- **L2** — *What did you change?* "PID to variable-gain PID to sliding mode, then a slow muzzle-speed correction."
- **L3** — *How did you prevent regressions?* "A 30-shot test with a spread limit of plus or minus 0.4 metres per second and a 16.0 cap, repeated at low battery voltage."

中文：现象→日志度量→恢复 120 ms→改控制器→30 发回归测试（±0.4、上限 16.0、低电量复测）。

**Q5. How do you debug on a competition day?**

- **L1**: "A fixed checklist: wiring, calibration, motor directions, muzzle-speed test, safe-state test. Between matches I only repair; I don't change algorithms."
- **L2** — *Why not change parameters?* "Every change is a new variable, and I cannot validate it properly between matches."
- **L3** — *Give an example.* "After a jam in a match, the event log showed two failures and the fail state. I cleaned the feed path and left the thresholds as they were, and evaluated the thresholds after the competition."

中文：固定清单；场间只修不改；例子：堵转后只清理，赛后评估阈值。

**Q6. How did you manage versions and parameters?**

- **L1**: "Git with feature branches, a tag per milestone and a frozen tag for competition builds. All tunable parameters live in one header."
- **L2** — *How do you reproduce a result?* "Every log header has the firmware hash and the parameter file hash."
- **L3** — *What about two people editing parameters?* "Parameter changes are separate commits with a reason, and shared interface changes need a second reviewer."

中文：分支+标签+冻结；参数集中；日志头写哈希；参数改动单独提交。

**Q7. How did you handle the simulation-to-real gap?**

- **L1**: "I made the simulation share the real timing: 3 millisecond period, 2 millisecond delay, a first-order current loop and the same limits."
- **L2** — *What was the symptom without that?* "A sliding-mode gain tuned in an ideal 1 millisecond simulation chattered on the robot."
- **L3** — *What did you change?* "A larger boundary layer and re-tuned gains in the realistic simulation, then fine-tuned on the robot."

中文：仿真先对齐时间结构；理想仿真调出的滑模在实机抖；加大边界层、在真实结构仿真中重调。

**Q8. How did you build in safety?**

- **L1**: "A relax state with zero command and cleared integrators, offline detection with timeouts, output and integral limits, and a default of relax at power-up."
- **L2** — *What are the timeouts?* "50 milliseconds for motor feedback and 100 for the remote, vision and the inter-board link."
- **L3** — *What would you add?* "A latched fail state with a current cut-off for the feeder after the second jam."

中文：RELAX、离线超时、限幅、上电默认 RELAX；改进=二次堵转后锁存并断流。

**Q9. What was the hardest integration problem?**

- **L1**: "Vision integration: the latency and who compensates for it. The frames had CRC errors and a 30 to 50 millisecond delay."
- **L2** — *How was it resolved?* "Vision compensates using timestamps and our attitude feedback; control only low-passes and rate-limits."
- **L3** — *How did you decide?* "We ran the same constant-velocity target test for both options and compared steady lag."

中文：视觉延迟与归属；视觉用时间戳补偿，电控低通限速；用同一测试比较。

**Q10. Tell me about a conflict in the team.**

- **L1**: "Mechanical wanted the largest pitch range; I found the gimbal hit the stop and the motor stalled."
- **L2** — *What did you do?* "I added a soft limit two degrees inside the mechanical stop, and mechanical added a damper; we registered the limit angles in a shared document."
- **L3** — *What did you learn?* "Agree on numbers in a shared document and test both sides' concerns with data."

中文：pitch 行程冲突；软限位收 2°+机械缓冲；共享文档登记限位。

**Q11. How do you test a controller change?**

- **L1**: "A fixed regression list of twelve items: steps, disturbances, wrap-around, burst firing, jam, full-load manoeuvres, link failures, drift and a long run."
- **L2** — *What is checked in the long run?* "Bus error and drop counters, and the maximum frame gap."
- **L3** — *What did you add after a failure?* "Every field failure becomes a regression item so it cannot return unnoticed."

中文：12 项回归清单；长跑检查总线计数；故障沉淀为回归项。

**Q12. What would you do differently?**

- **L1**: "Fix the control period with explicit dt from the beginning, move CAN transmission to a dedicated task, and log from day one."
- **L2** — *Why the period first?* "Because every loop and several hard-coded constants depend on it."
- **L3** — *How would you verify?* "Measure the period with a GPIO pin, rerun the regression list and compare logs with the old build."

中文：从一开始固定周期+显式 dt、独立发送任务、尽早日志；先做周期；用实测+回归验证。

## 本章要点速记

1. 从需求出发量化指标，再选方案；每次升级方案必须有可度量的现象。
2. 传感器约 1 kHz，控制任务约 3 ms（约 333 Hz），不说 1 kHz。
3. 延迟预算：约 2.8 ms 纯延迟＋零阶保持，35 Hz 处约 54° 相位代价。
4. CAN 负载：云台板约 63%、底盘板约 48%、板间低于 2%；命令按控制周期发。
5. 外环带宽≈Kp/2π：yaw 28 对应 4.5 Hz，pitch 25 对应 4.0 Hz；内环约 30–40 Hz。
6. 优化四段式：现象、度量、改动、回归。
7. 日志头写固件哈希和参数哈希，使现象可复现。
8. 赛场只修不改，赛后沉淀回归项。
9. 冲突用数据和文档解决；3V3 是团队成绩，我负责移植与调参。
