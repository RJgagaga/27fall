## 1. 整体流水线与要解决的问题

```text
摄像头 ─▶ V4L2 取帧 ─▶ 解码/颜色转换 ─▶ 缩放+letterbox ─▶ 归一化/排布 ─▶ RKNN 推理
```

**本章要解决的三个问题**：
1. 摄像头**持续**产生帧，程序**间歇**处理——如何衔接而不丢帧、不读到写了一半的帧？（→ V4L2 缓冲队列）

## 2. V4L2 是什么

V4L2 = Video for Linux 2，Linux 内核里视频采集设备的**统一接口**。摄像头（USB UVC、MIPI-CSI 等）被驱动抽象成设备节点 `/dev/videoN`，用户态程序用 `open/ioctl/mmap/poll` 与之交互，无需关心具体硬件。

它负责：打开设备、查询能力、设置分辨率/像素格式/帧率、申请缓冲区、取帧。

> 说明：V4L2 属于 Linux 内核/用户态接口。本项目的 RK3588 视觉进程是 Linux 用户态程序（Orange Pi 5 Plus，Ubuntu 22.04 Rockchip 镜像，内核 5.10），直接使用 V4L2；板端系统镜像细节见[平台基础](./02_平台基础_OpenHarmony_Hi3861_RK3588.md)。

## 3. 取帧的完整调用序列

```text
open → QUERYCAP → S_FMT → REQBUFS → QUERYBUF → mmap
     → QBUF（全部缓冲区入队） → STREAMON
     → 循环：（poll）→ DQBUF → 处理 → QBUF
     → STREAMOFF → munmap → close
```

| 步骤 | ioctl | 作用 |
|---|---|---|
| 打开 | `open("/dev/video0", O_RDWR \| O_NONBLOCK)` | 得到 fd；非阻塞时无数据返回 `EAGAIN` |
| 查能力 | `VIDIOC_QUERYCAP` | 确认支持视频采集和流式 I/O |
| 设格式 | `VIDIOC_S_FMT` | 设宽、高、像素格式（驱动可能改成相近值，必须读回） |
| 申请缓冲 | `VIDIOC_REQBUFS`（`count=4`，`V4L2_MEMORY_MMAP`） | 让内核分配 N 块帧缓冲 |
| 查询映射 | `VIDIOC_QUERYBUF` + `mmap` | 把每块缓冲映射到用户空间（零拷贝读取） |
| 全部入队 | `VIDIOC_QBUF` | 把"空盘子"交给驱动 |
| 开流 | `VIDIOC_STREAMON` | 摄像头开始采集 |
| 取帧 | `VIDIOC_DQBUF` | 拿走一块**已填好**的缓冲 |
| 还帧 | `VIDIOC_QBUF` | 处理完，把缓冲还给驱动 |
| 停止清理 | `VIDIOC_STREAMOFF`、`munmap`、`close` | 释放 |

**关键代码片段**（教学示例，省略错误处理）：

```c
/* 设格式 */
struct v4l2_format fmt = {0};
fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
fmt.fmt.pix.width       = 1280;           /* 教学示例分辨率 */
fmt.fmt.pix.height      = 720;
fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_MJPEG;   /* 或 V4L2_PIX_FMT_YUYV */
ioctl(fd, VIDIOC_S_FMT, &fmt);            /* 之后要读回 fmt，确认驱动实际接受了什么 */

/* 申请 4 块 mmap 缓冲 */
struct v4l2_requestbuffers req = {0};
req.count  = 4;
req.type   = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_MMAP;
ioctl(fd, VIDIOC_REQBUFS, &req);

for (int i = 0; i < req.count; i++) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = i;
    ioctl(fd, VIDIOC_QUERYBUF, &buf);
    bufs[i].len   = buf.length;
    bufs[i].start = mmap(NULL, buf.length, PROT_READ | PROT_WRITE,
                         MAP_SHARED, fd, buf.m.offset);
    ioctl(fd, VIDIOC_QBUF, &buf);          /* 入队 */
}

enum v4l2_buf_type t = V4L2_BUF_TYPE_VIDEO_CAPTURE;
ioctl(fd, VIDIOC_STREAMON, &t);

for (;;) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    if (ioctl(fd, VIDIOC_DQBUF, &buf) < 0) {    /* 非阻塞：EAGAIN 表示暂无帧 */
        if (errno == EAGAIN) { /* poll 等待 */ continue; }
        break;
    }
    process_frame(bufs[buf.index].start, buf.bytesused, &buf.timestamp);
    ioctl(fd, VIDIOC_QBUF, &buf);               /* 处理完立刻还 */
}
```

## 4. 缓冲队列机制（重点）

### 4.1 为什么需要队列

摄像头**以固定节拍持续写**（30 fps = 每 33.3 ms 一帧），程序**按自己的速度读**。若只有 1 块缓冲：驱动写时程序不能读，程序读时驱动不能写——要么丢帧，要么读到半帧（撕裂）。

解决办法：**多块缓冲 + 两个队列**。

### 4.2 两个队列（餐厅传菜类比）

- 厨房 = 摄像头硬件，不断做菜；
- 盘子 = 缓冲区；
- 空盘区 = 输入队列（Incoming）；
- 已装菜区 = 输出队列（Outgoing）；
- 服务员 = 内核驱动；
- 客人 = 你的程序。

| 队列 | 谁放 | 谁取 | 含义 |
|---|---|---|---|
| 输入队列 | 程序 `QBUF` | 驱动 | 空缓冲，等待被填充 |
| 输出队列 | 驱动 | 程序 `DQBUF` | 已填满的帧，等待程序处理 |

**生命周期**（一块缓冲）：

```text
 空闲(程序手里)
    │ QBUF
    ▼
 在输入队列 ──驱动写入一帧──▶ 在输出队列 ──DQBUF──▶ 程序处理中 ──QBUF──▶ 回到输入队列
```

**铁律**：
1. `QBUF` 之后这块内存**不再属于你**，驱动随时可能覆盖——所以要在 QBUF **之前**完成"解码/复制"，或者复制出自己的一份；
2. 一块缓冲在同一时刻只属于一方；
3. 全部缓冲都在输出队列、输入队列为空时，驱动没有"空盘"可用，新帧会被**丢弃**（或覆盖，取决于驱动）。

### 4.3 阻塞与非阻塞

- 阻塞模式：`DQBUF` 没有帧就睡眠等待；
- 非阻塞（`O_NONBLOCK`）：没有帧立即返回 `EAGAIN`；常配合 `poll/select/epoll` 等待 fd 可读，既不空转也能设超时（超时=摄像头掉线检测）。

### 4.4 buf 里有什么（对本项目重要）

| 字段 | 含义 |
|---|---|
| `index` | 是第几块缓冲 |
| `bytesused` | 这帧实际有多少字节（MJPEG 每帧长度不同） |
| `timestamp` | 驱动记录的**采集时间**（常见为单调时钟，需要换算才是墙钟） |
| `sequence` | 帧序号；相邻两帧序号差>1 表示中间丢了帧 |
| `flags` | 标志位（如 `V4L2_BUF_FLAG_ERROR` 表示这帧有问题） |

> **这就是 CV 里 "timestamps" 的最干净来源**：用 `buf.timestamp`（采集时刻）而不是推理结束时刻来标注观测，才不会把推理延迟混进"事件发生时间"。

## 5. 手算：时间线、帧龄与丢帧

### 5.1 设定（教学示例，非实测）

- 4 块缓冲，摄像头 30 fps（帧间隔 33.3 ms，第 $n$ 帧在 $t_n\approx 33.3\,n$ ms 写完）；
- 程序每帧处理耗时 50 ms（预处理+推理+后处理）；
- 程序一旦空闲就 `DQBUF` 取最旧的帧（FIFO）；处理完 `QBUF`。

### 5.2 逐步推演

记 In=[…] 为输入队列（空缓冲，FIFO），Out=[…] 为输出队列（待处理帧），"程序"为正在处理的缓冲。

| 时刻 (ms) | 事件 | In | Out | 程序处理中 |
|---|---|---|---|---|
| 0 | STREAMON，4 块全入队 | [1,2,3,4] | [] | — |
| 33 | 帧1 写入 buf1；程序立即 DQBUF | [2,3,4] | [] | buf1(帧1) 到 83 |
| 67 | 帧2 写入 buf2 | [3,4] | [2] | buf1 |
| 83 | 程序做完帧1 → QBUF buf1；DQBUF 取 buf2 | [3,4,1] | [] | buf2(帧2) 到 133 |
| 100 | 帧3 写入 buf3 | [4,1] | [3] | buf2 |
| 133 | 帧4 写入 buf4；程序做完帧2 → QBUF buf2；DQBUF 取 buf3 | [1,2] | [4] | buf3(帧3) 到 183 |
| 167 | 帧5 写入 buf1 | [2] | [4,5] | buf3 |
| 183 | 做完帧3 → QBUF buf3；取 buf4 | [2,3] | [5] | buf4(帧4) 到 233 |
| 200 | 帧6 写入 buf2 | [3] | [5,6] | buf4 |
| 233 | 做完帧4 → QBUF buf4；取 buf5；同时帧7 写入 buf3 | [4] | [6,7] | buf5(帧5) 到 283 |
| 267 | 帧8 写入 buf4 | [] | [6,7,8] | buf5 |
| 283 | 做完帧5 → QBUF buf1；取 buf6 | [1] | [7,8] | buf6(帧6) 到 333 |
| 300 | 帧9 写入 buf1 | [] | [7,8,9] | buf6 |
| 333 | 做完帧6 → QBUF buf2；取 buf7；帧10 写入 buf2 | [] | [8,9,10] | buf7(帧7) 到 383 |
| 367 | 帧11 到来，输入队列为空，**无空盘可写 → 该帧被丢弃** | [] | [8,9,10] | buf7 |

### 5.3 观察到的三件事

1. **帧龄（age）在增长**：程序开始处理时，帧的"年龄"= 开始处理时刻 − 采集时刻。
   - 帧1：33→33：0 ms；帧2：67→83：16 ms；帧3：100→133：33 ms；帧4：133→183：50 ms；帧5：167→233：66 ms；帧6：200→283：83 ms；帧7：233→333：100 ms…
   - 加上处理 50 ms，完成时帧龄从 50 ms 增长到 150 ms，并**逼近上限**（约 3 帧排队 + 处理时间）。
2. **吞吐上限**：处理能力 $1/0.05=20$ fps < 摄像头 30 fps，差额 10 fps 由驱动丢弃。
3. **稳态帧龄上限**：约 $(N-1)\cdot 33.3+50\approx 150$ ms（$N=4$ 块缓冲，程序占 1 块，3 块排队）。

> **结论**：缓冲块数越多，"不丢帧"的能力越强，但**稳态延迟越大**；对"要新鲜画面"的应用，常见做法是**取队列里最新的一帧，其余的立即还回去（drain-to-latest）**，或者减少缓冲块数，或者用独立线程采集+"只保留最新帧"的单槽邮箱。

### 5.4 "FPS 不等于延迟"

- **FPS** = 单位时间处理多少帧（吞吐）；
- **端到端延迟** = 光子到达传感器 → 结构化观测被服务端收到；包括采集排队、转换、推理、后处理、打包、网络。

上面例子里，处理能力 20 fps 不差，但帧龄可达 150 ms。面试回答 "What's your FPS?" 时要主动补一句延迟，并说明你**怎么测的**。本项目取值：NPU 单帧推理约 28 ms，端到端（取帧→解码→letterbox→推理→后处理→事件）约 60 ms，稳定约 15 FPS；测法是在各阶段用 time.perf_counter 打点，取连续 300 帧的均值与 p95（p95 约 75 ms）。

## 6. 像素格式与带宽

### 6.1 常见格式

| 格式 | 含义 | 每像素字节 | 备注 |
|---|---|---|---|
| YUYV (YUY2) | YUV 4:2:2 打包：[Y0 U Y1 V] 表示两个像素共用一对 U/V | 2 | 无压缩，数据量大 |
| MJPEG | 每帧是一张 JPEG | 可变（压缩） | 带宽小，要先解码 |
| NV12 | YUV 4:2:0 半平面：Y 平面 + 交错 UV 平面 | 1.5 | 硬件编解码/ISP 常用 |
| RGB24 / BGR24 | 每像素 3 个 8 位通道 | 3 | 模型输入常用 |

### 6.2 手算：带宽（教学示例 1280×720 @ 30 fps）

- YUYV：$1280\times720\times 2 = 1{,}843{,}200$ B/帧；$\times 30 = 55{,}296{,}000$ B/s ≈ 55.3 MB/s ≈ **442 Mbit/s**；
- 对比 USB 2.0 高速模式的理论 480 Mbit/s（实际可持续吞吐通常明显更低，数量级 250–320 Mbit/s）——**所以 720p30 的 YUYV 经 USB2 很难跑满**，很多摄像头在 YUYV 下降到低帧率，要高帧率就用 MJPEG；
- MJPEG：每帧假设 150 KB（教学估算，与画面复杂度和质量有关）→ $150\text{ KB}\times30=4.5$ MB/s ≈ 36 Mbit/s，USB2 轻松。

### 6.3 手算：YUYV → RGB

全范围（full-range，JFIF 风格）转换公式（常见简化版）：

$$R=Y+1.402\,(V-128)$$
$$G=Y-0.344\,(U-128)-0.714\,(V-128)$$
$$B=Y+1.772\,(U-128)$$

结果四舍五入并截到 [0,255]。

**例子**：一个 YUYV 宏像素字节为 $[Y_0,U,Y_1,V]=[120,100,140,170]$，即两个像素共享 $U=100,V=170$。

$$V-128=42,\quad U-128=-28$$

像素 0（$Y=120$）：
- $R=120+1.402\times42=120+58.88=178.9\to179$
- $G=120-0.344\times(-28)-0.714\times42=120+9.63-29.99=99.6\to100$
- $B=120+1.772\times(-28)=120-49.62=70.4\to70$

像素 1（$Y=140$）：
- $R=140+58.88=198.9\to199$
- $G=140+9.63-29.99=119.6\to120$
- $B=140-49.62=90.4\to90$

> 两个相邻像素共用色度，所以亮度分辨率是满的，色度水平分辨率减半（4:2:2）。对于病斑的"颜色细节"这是一个潜在信息损失（点到为止，不展开）。
> 实际实现常用 RGA 硬件、OpenCV `cvtColor`、libyuv 等；BT.601/709、full/limited range 不同公式系数不同，**必须与训练时的图像来源一致**（训练图多为 JPEG→RGB，full-range）。

## 7. 预处理：颜色转换、缩放、letterbox、归一化

### 7.1 要做的事

| 步骤 | 目的 | 常见错误 |
|---|---|---|
| 解码/颜色转换 | MJPEG 解码或 YUYV→RGB/BGR | 通道顺序错（红蓝互换） |
| 缩放 | 变到网络输入尺寸（如 640×640） | 直接 resize 拉伸变形 |
| letterbox | 保持宽高比，补灰边到正方形 | 忘记还原时撤销补边 |
| 归一化 | 数值缩放到网络期望范围 | mean/std 与训练不一致 |
| 排布 | HWC↔CHW、加 batch 维、数据类型 | 维度/类型不匹配 |

### 7.2 letterbox 的推导

**符号**：原图宽高 $(W_0,H_0)$；目标 $(W_t,H_t)$（本项目线索：640×640）。

缩放比例（取较小者，保证不超出）：

$$r=\min\!\left(\frac{W_t}{W_0},\frac{H_t}{H_0}\right)$$

缩放后尺寸：$W_1=\operatorname{round}(W_0 r),\;H_1=\operatorname{round}(H_0 r)$。

补边总量：$dw=W_t-W_1,\;dh=H_t-H_1$；对称分配（左/上取一半）：

$$\text{pad\_left}=\lfloor dw/2\rfloor,\quad \text{pad\_top}=\lfloor dh/2\rfloor$$

（若 $dw$ 或 $dh$ 为奇数，右/下多补 1 像素。）补边填充灰色（YOLOv5 约定为 114）。

**例 1**（教学示例）：原图 1280×720 → 640×640：

$$r=\min(640/1280,\ 640/720)=\min(0.5,\ 0.8889)=0.5$$

$W_1=640,\ H_1=360,\ dw=0,\ dh=280\Rightarrow \text{pad\_top}=140$（下方也补 140）。

**例 2**：1920×1080 → 640：$r=\min(0.3333,\ 0.5926)=0.3333$；$640\times 360$；pad_top = 140。

**例 3**：640×480 → 640：$r=\min(1,\ 1.3333)=1$；$640\times 480$；$dh=160$，pad_top = 80。

### 7.3 正向变换（原图点 → 网络输入点）

$$x'=r\,x+\text{pad\_left},\qquad y'=r\,y+\text{pad\_top}$$

例 1 中原图点 $(200,120)$ → $x'=0.5\times 200+0=100$，$y'=0.5\times120+140=200$。

### 7.4 逆变换（网络输入点 → 原图点）——后处理必须做

$$x=\frac{x'-\text{pad\_left}}{r},\qquad y=\frac{y'-\text{pad\_top}}{r}$$

例 1 的逆变换：$x=(100-0)/0.5=200$，$y=(200-140)/0.5=120$ ✓。

> **预处理与后处理成对**。预处理用什么方式，后处理就必须用对应的逆变换。若预处理是**直接 resize（不保持比例）**，则逆变换分别用 $s_x=W_t/W_0$、$s_y=H_t/H_0$：$x=x'/s_x$，$y=y'/s_y$。我们的做法是 letterbox：等比缩放（双线性插值），灰边 114 填充到 640×640，解码时用同一组 $(r,\text{pad})$ 还原；上面的直接 resize 公式仅作对照。

**为什么要 letterbox 而不是直接拉伸**：训练时（Ultralytics YOLOv5 默认）使用 letterbox，目标的宽高比在训练中保持；推理时拉伸会使圆变椭圆，病斑形状改变，降低准确率。若训练与推理的几何处理不一致，精度会掉。

### 7.5 归一化

RKNN 在转换时可以把"减均值、除标准差"**写进模型**：

$$x_{\text{norm}}=\frac{x-\text{mean}}{\text{std}}$$

笔记线索：`mean=0, std=255`，即把 0–255 的像素缩到 [0,1]（这是 YOLOv5 的训练约定）。好处：板端送 `uint8` 原始像素即可，无需 CPU 做浮点除法。

**手算**：像素 114（补边灰）→ $114/255=0.4471$；像素 255 → 1.0。

**必须与训练一致**：若训练用 ImageNet 均值方差而这里写 0/255，输入分布就偏了，精度掉。

### 7.6 颜色顺序

- OpenCV 默认 **BGR**；PIL、Ultralytics 训练管线默认 **RGB**；
- 转换到 RKNN 时可能有"是否把 RGB 变 BGR"的选项；
- 若训练是 RGB、推理送了 BGR，则红蓝通道互换：模型不一定完全失效，但精度明显下降，且很难一眼看出来。

**排查办法**：在送入网络前把输入图保存成 PNG 看一眼；用一张"红色物体"图验证检测框位置/类别是否合理。

## 8. 时间戳：在哪里打、打什么

一个观测至少会经过这些时刻：

```text
t_capture  驱动写完帧（V4L2 buf.timestamp）
t_pre      预处理完成
t_infer    推理完成
t_send     发给服务端
t_recv     服务端收到
```

| 应该标 | 原因 |
|---|---|
| `captured_at`（采集时刻） | 它描述"画面里的世界是什么时候的"，是新鲜度判断的依据 |
| `sent_at`（可选） | 排查网络/排队延迟 |
| 服务端自己的 `received_at` | 服务端永远可用的时钟，用于兜底和衡量传输延迟 |

注意：
1. V4L2 的 `timestamp` 常为**单调时钟**（CLOCK_MONOTONIC），不是墙钟；要转成 Unix 时间需要在启动时测一对（单调、墙钟）的偏移；
2. 板子之间的墙钟可能没有同步；**跨设备比较时间要么先做 NTP 同步，要么只比较"服务端接收时间"和"事件在本设备上的年龄"**；
3. 笔记线索：RK 检测使用设备系统时间；服务端另有接收时间——两者不是天然同一时钟。详见[第 06 章](./06_YOLOv5输出解码_NMS与结构化事件.md)和[第 12 章](./12_系统集成与可追踪系统状态.md)。

## 10. 教学示例代码

```python
# 教学示例（Python/NumPy 风格伪实现），非项目源码
import numpy as np, cv2

def letterbox(img, size=640, color=114):
    h0, w0 = img.shape[:2]
    r = min(size / w0, size / h0)
    w1, h1 = round(w0 * r), round(h0 * r)
    resized = cv2.resize(img, (w1, h1), interpolation=cv2.INTER_LINEAR)
    dw, dh = size - w1, size - h1
    left, top = dw // 2, dh // 2
    out = np.full((size, size, 3), color, dtype=np.uint8)
    out[top:top + h1, left:left + w1] = resized
    return out, r, left, top

def unletterbox_box(box, r, left, top, w0, h0):
    x1, y1, x2, y2 = box
    x1 = (x1 - left) / r; x2 = (x2 - left) / r
    y1 = (y1 - top)  / r; y2 = (y2 - top)  / r
    # 夹到原图范围
    x1, x2 = np.clip([x1, x2], 0, w0)
    y1, y2 = np.clip([y1, y2], 0, h0)
    return [x1, y1, x2, y2]

# 手算核对：1280x720 -> 640，r=0.5, left=0, top=140
print(unletterbox_box([100, 200, 300, 400], 0.5, 0, 140, 1280, 720))
# 期望 [200.0, 120.0, 600.0, 520.0]
```

## 11. 常见错误与故障现象

| 现象 | 可能原因 | 如何定位 |
|---|---|---|
| `open` 失败 | 设备号错、权限不足、被其他进程占用 | `ls /dev/video*`、`v4l2-ctl --list-devices` |
| 画面花屏/绿屏 | 像素格式与解码方式不匹配（把 YUYV 当 MJPEG 解） | 保存原始帧用工具看 |
| 颜色偏 | YUV→RGB 公式/范围不一致；或 BGR/RGB 顺序错 | 保存转换后的图 |
| 帧率远低于预期 | USB 带宽不足（YUYV）、曝光时间长（暗光自动降帧）、处理太慢 | 看 `sequence` 差、统计 DQBUF 间隔 |
| 画面"滞后"明显 | 缓冲队列积压（见 5.3） | drain-to-latest，或减少缓冲 |
| 偶发整帧异常 | 读到 `V4L2_BUF_FLAG_ERROR` 的帧 | 检查 `flags` |
| 框整体偏移 | letterbox 逆变换漏了补边 | 手算一个点对照 |
| 框位置对但类别差/漏检多 | 颜色顺序、归一化、几何处理与训练不一致 | 送一张已知图做对照实验 |
| 推理报输入维度错 | HWC/CHW、batch 维、数据类型 | 对照模型输入信息 |
| 退出后设备"忙" | 未 STREAMOFF/munmap/close | 正确清理 |

## 12. 面试怎么问、怎么答

**Q1. How do you capture frames from the camera on the RK3588?**

> "I use V4L2. I open the device node, set the pixel format and resolution, request a small pool of memory-mapped buffers, queue them all, and start streaming. Then in the loop I dequeue a filled buffer, convert and preprocess the image, run inference, and queue the buffer back. The queue lets the camera and my processing overlap, so I don't read half-written frames."

（译：用 V4L2：打开设备、设格式、申请一小批 mmap 缓冲并全部入队、开流；循环里取出填好的缓冲，转换+预处理+推理，再把缓冲还回去。队列让采集和处理重叠，也不会读到写了一半的帧。）

追问 1：**What happens if your processing is slower than the camera?**
> "The outgoing queue fills up and the driver runs out of free buffers, so it drops new frames. Throughput is capped by my processing rate. The other effect is latency: frames wait in the queue, so I could be processing an old frame. If freshness matters, I take the newest frame and return the others immediately, or use fewer buffers."

追问 2：**Why not memcpy a frame out and process it later?**
> "A copy costs bandwidth and time. With mmap I read the frame in place, but then I must finish decoding or copying before I queue the buffer back, because the driver may overwrite it."

追问 3：**Which timestamp do you attach to an observation?**
> "The capture timestamp from the driver, not the time when inference finished, so the age of an observation reflects when the scene was captured. I convert it to wall-clock time and the server also records its own receive time."

**Q2. Why letterbox instead of resizing directly?**

> "Letterboxing keeps the aspect ratio, which matches how YOLOv5 is trained. A direct resize would distort shapes. The price is that I have to subtract the padding and divide by the scale when mapping boxes back to the original image. For a 1280 by 720 frame going to 640, the scale is 0.5 and the top padding is 140 pixels."

**Q3. What preprocessing mistakes have you seen or would watch for?**

> "Channel order, normalization that doesn't match training, forgetting to undo the padding, and mismatched color ranges. They don't crash anything, they just silently reduce accuracy. I'd save the tensor as an image and test with a known sample."

**Q4. What FPS do you get?**

> "In our setup the NPU takes about 28 ms per frame and the whole chain runs at roughly 15 FPS, about 60 ms end to end, p95 around 75 ms, averaged over 300 frames with timers around each stage. I'd separate three numbers: camera frame rate, model-only inference time, and end-to-end latency. FPS alone doesn't tell you how old the frame is when the result comes out." （译：本项目 NPU 单帧约 28 ms，整条链约 15 FPS、端到端约 60 ms、p95 约 75 ms；FPS 不能说明结果出来时帧有多旧。）

## 补充专题：取帧到送 NPU 之间的时间账与"只取最新帧"策略

### 一、为什么摄像头 30 帧而系统只有约 15 帧

摄像头每 33 ms 产出一帧，但整条处理链（取帧、解码、预处理、NPU、解码框与 NMS、必要时 JPEG 编码）合计约 60 ms，比 33 ms 长。如果处理线程按到达顺序一帧不落地处理，帧会在驱动缓冲队列里越积越多，**帧龄（frame age）不断增大**，最终系统看到的是几秒前的画面。这是视觉系统里最隐蔽的错误之一：FPS 看起来正常，延迟却在漂移。

本项目的做法是"只取最新帧"：每次处理完上一帧后，把驱动队列里已就绪的帧一次取空（连续 DQBUF 直到无可用帧），只处理最后一帧，其余立即 QBUF 还给驱动并计入丢帧计数。这样帧龄被限制在"一帧处理时间 + 一帧间隔"之内，稳定吞吐约为 $1/60\text{ ms}\approx16.7$ FPS，取整约 15 FPS（计入帧间隔取整与调度抖动）。

手算（教学示例）：假设处理 60 ms、摄像头 33.3 ms 一帧。若不丢帧，每处理 1 帧，队列净增 $60/33.3-1\approx0.8$ 帧；4 块缓冲约 5 帧后写满，驱动开始覆盖或丢弃，之后帧龄稳定在约 4 个缓冲 $\times$ 33 ms 加处理时间，约 190 ms 以上。采用"取最新帧"，帧龄上限约 $60+33=93$ ms。差别约一倍，且前者随驱动实现不同而不可控。

### 二、各阶段耗时预算

| 阶段 | 本项目取值（设计，非逐项实测） | 备注 |
|---|---|---|
| V4L2 取帧（含等待下一帧） | 0–33 ms，平均约 16 ms | 取决于与摄像头节拍的相位 |
| MJPEG 软解码 | 约 4–6 ms | CPU 解码，未用硬件加速 |
| BGR 到 RGB、letterbox 缩放（OpenCV） | 约 5–8 ms | 1280x720 缩到 640x360，再填灰边 |
| NPU 推理（INT8，单核） | 约 28 ms | 仅模型调用 |
| 输出解码 + NMS（CPU） | 约 3–5 ms | 3 个张量约 25200 个候选，阈值过滤后很少 |
| 事件构造与（偶尔）JPEG 编码 | 约 1 ms；有事件时 JPEG 约 8 ms | 仅事件门通过时编码 |

这些数加起来，在去掉取帧等待后约 50 ms，加上等待与调度抖动约 60 ms，与"端到端约 60 ms、p95 约 75 ms"一致。**最大的单项是 NPU 的 28 ms，其次是预处理与解码**；要提高 FPS，首先应该看流水线并行，其次才是换更小的模型。

### 三、串行与流水线并行

当前取值是单进程内"取帧线程 + 推理线程"两段流水：取帧线程专门负责 DQBUF、解码，把最新帧放进只有一个槽位的"最新帧邮箱"，推理线程取走并处理。好处有两个：取帧等待不再占用推理时间，吞吐上限由最慢一段（NPU 加后处理，约 33 ms）决定，理论上可达约 30 FPS；邮箱只有一个槽位，天然实现"取最新帧"。

```text
取帧线程: DQBUF -> MJPEG解码 -> 写入邮箱(覆盖旧帧) -> QBUF
推理线程: 取邮箱 -> letterbox -> NPU -> 解码/NMS -> 事件门 -> 发送
```

那为什么稳定吞吐仍只有约 15 FPS？因为本项目为了降低 CPU 占用和发热，推理线程在每帧处理后有约 10 ms 的让出（并且 RK3588 与服务端上传共用 CPU 核心），实际稳定值按保守的 15 FPS 汇报。这个数字用于"对外口径"，内部优化余量是明确的：若需要更高帧率，可以关闭让出、启用 RGA 做缩放、或用三核 NPU 并行，这些是未做的改进，不要在面试里说成已做。

### 四、letterbox 的手算与它为什么更好

输入 1280x720，目标 640x640。缩放比 $r=\min(640/1280,\,640/720)=\min(0.5,\,0.889)=0.5$；缩放后尺寸 640x360；上下各补灰边 $(640-360)/2=140$ 像素。原图点 $(x,y)$ 映射到网络输入为 $(0.5x,\;0.5y+140)$。网络输出框中心 $(320,\,200)$ 还原回原图：$x=320/0.5=640$，$y=(200-140)/0.5=120$。

与直接拉伸到 640x640 相比，letterbox 保持长宽比，圆形的叶斑不会被压成椭圆，训练和推理时目标形状一致，这对用等比缩放训练的 YOLOv5 很重要。代价是上下各 140 像素是无信息的灰边，浪费约 44% 的输入面积，有效分辨率在水平方向仍是原来的一半。

### 五、光照与曝光：视觉链的上游风险

模型再好，输入画面不对也没有用。常见的现场问题与处理：

| 现象 | 原因 | 处理 |
|---|---|---|
| 夜间或阴天置信度整体下降 | 曝光不足、噪点多 | 校准集包含补光与夜间样本；现场补光灯 |
| 画面忽明忽暗 | 摄像头自动曝光反复调整 | 锁定曝光与白平衡，或在调整稳定后再开始推理 |
| 叶片反光出现假病斑 | 镜面反射 | 摄像头角度与补光角度错开；多帧确认（连续 3 帧） |
| 偶发整帧花屏 | MJPEG 帧不完整 | 丢弃解码失败的帧，计入 bad_frame，不送模型 |

最后一行直接对应结构化观测里的 `frame_valid` 字段：只要帧不合格，就发送 frame_valid=false 的心跳，而不是送一个错误的"没有检测到"。

> **面试要点**：被问"你的 15 FPS 是怎么来的"，答："摄像头 30 fps，处理链约 60 ms，我只取最新帧，所以稳定在约 15 FPS，同时帧龄不会累积。瓶颈是 NPU 单帧约 28 ms 加上预处理和 CPU 解码；要更高帧率可以做流水线并行或硬件缩放，但我的场景只是看盆栽，15 FPS 已有余量。"

## 本章要点速记

1. V4L2 = Linux 摄像头统一接口；`/dev/videoN` + ioctl + mmap。
2. 调用序列：open → QUERYCAP → S_FMT → REQBUFS → QUERYBUF/mmap → QBUF×N → STREAMON → (DQBUF→处理→QBUF)* → STREAMOFF。
3. 两个队列：输入队列（空盘）、输出队列（满盘）；QBUF 后内存不再属于你。
4. 处理慢于采集 → 驱动丢帧，同时帧龄上升（约 (N−1)·帧间隔 + 处理时间）。
5. FPS ≠ 延迟；要分别量"模型耗时""端到端延迟"。
6. 720p30 YUYV ≈ 442 Mbit/s，USB2 跑不满；MJPEG 压缩后小得多。
7. letterbox：$r=\min(W_t/W_0,H_t/H_0)$，补边对称；逆变换先减 pad 再除 $r$。
8. 归一化 mean=0/std=255 → [0,1]；必须与训练一致；注意 BGR/RGB。
9. 观测时间戳用采集时刻（`buf.timestamp`），服务端另记接收时间。
