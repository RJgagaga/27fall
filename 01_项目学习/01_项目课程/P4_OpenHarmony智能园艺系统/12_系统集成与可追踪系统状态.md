## 1. "系统集成"在这个项目里指什么

CV 原文：

> **System integration**: unified visual observations, environment state and user commands into a traceable system state, orchestrated decisions with a server-side agent and closed the loop through web interaction and device-side irrigation.

拆成四件事：

| 事情 | 含义 | 对应章节 |
|---|---|---|
| 统一输入 | 视觉观测、环境（传感）状态、用户命令进入同一个状态模型 | 本章 2 |
| 可追踪 | 每条信息有来源、时间、ID，决策能回溯 | 本章 3、4 |
| 服务端编排 | Agent/规则按图执行，输出建议或受约束请求 | [10](./10_LangGraph决策链.md) |
| 闭环 | 网页交互 → 命令 → 设备灌溉 → 反馈回到状态 | [11](./11_执行边界_白名单_幂等与设备反馈.md) |

> 集成工作的价值常被低估：每个子系统单独能跑，不代表合在一起正确。真正的难点是**时间、语义和失效**——这正是面试官看重"工程能力"的地方。

## 2. 统一系统状态

### 2.1 设计目标

- **单一事实来源**：网页、Agent、日志看到的是同一份状态；
- **分层**：原始事实（传感/观测/反馈）与派生结论（建议/决策）分开存；
- **带元数据**：来源、时间、序号、有效性；
- **可序列化**：随时可以导出成 JSON 回放。

### 2.2 状态结构（教学示例，字段非项目实测）

```json
{
  "state_version": 1287,
  "generated_at": 1718000130.4,

  "environment": {
    "pot1": {
      "moisture": {"value": 55, "unit": "calibrated_pct", "source": "hi3861-pot1",
                   "seq": 4021, "received_at": 1718000130.1, "age_s": 0.3, "valid": true},
      "pump":     {"reported": "on", "mode": "auto", "last_action_id": "a-0007",
                   "received_at": 1718000130.1, "age_s": 0.3}
    }
  },

  "vision": {
    "plant_1": {
      "latest": {"event_id": "cam0-000873", "captured_at": 1718000129.9, "age_s": 0.5,
                 "detections": [{"class": "lesion", "score": 0.90, "bbox": [200,120,600,520]}],
                 "image_size": [1280,720], "frame_valid": true},
      "confirmed": {"lesion": {"frames": 3, "of": 5, "first_seen": 1718000120.0}}
    }
  },

  "user": {"manual_off": {"active": false, "since": null, "expires_at": null}},

  "commands": [
    {"action_id": "a-0007", "name": "pump_on", "source": "rule_fast_path", "level": "L4",
     "proposed_at": 1718000100.0, "sent_at": 1718000100.1, "acked_at": 1718000100.2,
     "reported_at": 1718000100.4, "trace_id": "t-0412"}
  ],

  "decisions": [
    {"trace_id": "t-0412", "path": ["sensing", "execution"], "inputs": {"moisture": 12, "age_s": 0.8},
     "outcome": "request_pump_on", "rejected": []}
  ],

  "health": {"hi3861-pot1": "online", "rk3588-cam0": "online", "llm": "degraded"}
}
```

### 2.3 谁写、谁读

| 区域 | 唯一写入者 | 读者 |
|---|---|---|
| `environment` | TCP 接收线程（Hi3861 通道） | Agent、前端、日志 |
| `vision` | TCP 接收线程（RK3588 通道）+ 确认器 | Agent、前端 |
| `user` | 执行层（收到用户命令后） | 执行层、Agent |
| `commands` | 执行层 | 前端、日志 |
| `decisions` | 决策链 | 前端、日志、复盘 |
| `health` | 连接管理 | 前端 |

**每个区域只有一个写入者**，可以大幅降低竞争与不一致。

### 2.4 状态 vs 事件 vs 日志

| | 状态（state） | 事件（event） | 日志（log） |
|---|---|---|---|
| 含义 | "现在是什么" | "发生了什么" | "按时间顺序的记录" |
| 更新 | 覆盖 | 追加 | 追加 |
| 用途 | 展示、决策输入 | 触发处理 | 复盘、审计 |

状态由事件更新；日志记录事件与决策，用于**重放**。两者不要混用——只存状态就无法复盘；只存日志就每次要重算现状。

## 3. 时间模型与新鲜度

### 3.1 三类时间

| 时间 | 谁的时钟 | 用途 |
|---|---|---|
| 采集/采样时间 | 设备时钟（V4L2 `buf.timestamp` 等） | 描述"世界在什么时候是这样" |
| 接收时间 | 服务端时钟 | 服务端永远可用，用来兜底和量传输延迟 |
| 决策/命令时间 | 服务端时钟 | 排序、审计、超时 |

线索：Hi3861 传感 JSON 的时间字段在读到的版本里为 0，RK 检测使用设备系统时间，服务端另有接收时间——**它们不是天然同一个时钟**。

### 3.2 每类数据的新鲜度规则（教学取值）

| 数据 | 变化速度 | 使用上限 $T_{\max}$ | 过期后 |
|---|---|---|---|
| 土壤湿度读数 | 慢（分钟级） | 例如 10 s | 视为未知，fast path 不触发；告警"传感过期" |
| 泵状态反馈 | 事件性 | 例如 10 s | 显示"状态未知"，不假设 |
| 视觉观测 | 中（秒级） | 例如 2 s（用于"此刻"判断），数分钟（用于趋势） | 不用于当前动作；仅作历史 |
| 用户 manual_off | 持久直到取消 | 到期时间显式 | 到期→恢复自动 |

> 数值来源：**教学取值**。我们的系统实际取值与上表一致：传感 10 s、泵状态 10 s、视觉观测 2 s（用于“此刻”判断）。

### 3.3 手算：一次融合判断

时刻 $t_{\text{now}}=100.0$ s（服务端时钟）：
- 土壤读数：`received_at=96.8` → age 3.2 s；
- 视觉观测：`received_at=99.7` → age 0.3 s（若再减去设备上报的 `age_at_send=0.25`，估计采集在 99.45，年龄约 0.55 s）。

规则：土壤 $T_{\max}=10$ s → **有效**；视觉 $T_{\max}=2$ s → **有效**。两者可以一起被决策使用。

如果土壤是 $\text{age}=15$ s：无效。则**不能把"15 s 前的湿度 12 + 现在的病斑"拼成"又干又病"的结论**，只能说"传感数据过期，视觉有观测"。

**原则**：融合前先按各自的有效期过滤；融合结果的有效期取各输入的**最小**剩余有效期。

### 3.4 序号与乱序

每个来源有自己的递增 `seq`。服务端：
- `seq` 比已收到的小 → 乱序/重放，丢弃或标记；
- `seq` 跳号 → 丢了消息（TCP 内不应发生，除非重连或设备重启），计数；
- 设备重启 → `seq` 归零，需要用"连接 id/boot id"区分，否则会误判为乱序。

## 4. 追溯：trace_id 与决策记录

### 4.1 目标

能回答："**为什么泵在 14:03:07 开了？**"或"**为什么该浇水时没浇？**"

### 4.2 做法

1. 每个**触发事件**进入系统时分配（或继承）`trace_id`；
2. 决策链各节点把"依据"追加到 `trace`；
3. 命令继承 `trace_id`，并带 `action_id`；
4. 设备反馈带 `last_action_id`；服务端据此把反馈关联回 `trace_id`；
5. 所有日志行都带 `trace_id`。

### 4.3 一段日志（教学示例）

```text
14:03:06.912 [t-0412] ingest   sensor pot1 seq=4021 moisture=12 age=0.3s valid=1
14:03:06.913 [t-0412] graph    sensing  fast_path=1 (moisture 12 < 20, mode=auto, fresh)
14:03:06.914 [t-0412] exec     check pump_on(a-0007): whitelist=ok mode=ok fresh=ok range=ok cooldown=ok -> ACCEPT
14:03:06.915 [t-0412] send     a-0007 pump_on max_s=60 -> pot1
14:03:06.972 [t-0412] ack      a-0007 accepted (L3)
14:03:07.103 [t-0412] state    pot1 pump=on last_action_id=a-0007 (L4)
```

读这段：能一眼看到**输入是什么、走了哪条路径、每项检查的结果、命令到了哪一级**。同样地，"没浇水"的日志会是：

```text
14:10:02.221 [t-0455] exec     check pump_on(a-0011): ... mode=manual manual_off=1 -> REJECT manual_off_priority
```

### 4.4 复盘需要什么

- 保存原始输入（至少是摘要）、决策路径、校验结果、命令级别变化；
- 保存模型版本、阈值配置版本（见第 9 节），否则无法解释"当时为什么这样判"；
- 保存 LLM 的提示词摘要与输出（用于评估，注意隐私与体积）。

## 5. 多源信息的融合与冲突

### 5.1 原则

1. **各管各的物理量**：土壤湿度 → 灌溉；叶片状态 → 病害建议。视觉观测**不直接驱动泵**。
2. **冲突不强行合并**：把冲突作为信息呈现，由规则或人处理；
3. **不确定就保守**：不确定时倾向"通知人/关泵"，而不是"自动浇水"。

### 5.2 冲突表（教学例子）

| 土壤 | 视觉 | 解读 | 系统行为 |
|---|---|---|---|
| 干（12） | 叶片萎蔫（若有该类别） | 一致：缺水 | fast path 开泵 + 建议 |
| 干（12） | 无异常 | 也许刚好缺水 | fast path 开泵 |
| 湿（70） | 病斑 | 病害，不是缺水 | **不开泵**；care 建议检查/隔离 |
| 湿（70） | 萎蔫 | 可能涝或根部问题 | alert 建议检查排水；**不浇水** |
| 传感过期 | 病斑 | 无法判断水分 | alert 传感问题；care 建议；不自动浇水 |
| 无数据 | 无观测 | 摄像头不工作还是没东西？ | 看 `frame_valid` 与心跳 |

### 5.3 多帧确认与趋势（回到视觉）

单帧检测不触发任何"升级"动作，k-of-n 确认（[第 06 章](./06_YOLOv5输出解码_NMS与结构化事件.md)）后才进入 `confirmed`。趋势（如过去 10 分钟土壤持续下降）可由 `history` 提供。

## 6. 八个端到端场景

每一步标出证据级别（L0–L5，见[第 11 章](./11_执行边界_白名单_幂等与设备反馈.md)）。

### S1：土壤很干，自动模式（正常路径）

1. Hi3861 读 ADC，标定 moisture=12 → 滞回：12<56 → 本地开泵（GPIO LOW）→ 上报 `moisture=12,pump=on`；
2. 服务端收到，更新 environment；
3. sensing：12<20 极干，新鲜，auto → fast path → execution：检查通过，但设备已 on → `noop(already_on)`，记录；
4. 前端显示：湿度 12（0.3 s 前）、泵已开（设备报告，L4）；
5. 土壤逐步回升，湿度越过 65 → 本地关泵 → 上报；
**要点**：泵由本地闭环驱动，服务端只是确认并记录。

### S2：湿度正常 + 检出病斑

1. RK3588 连续帧检出 lesion（k-of-n 确认）；
2. 服务端：vision.confirmed 更新；sensing 未命中 → supervisor → care（LLM）→ 建议"检查叶片、隔离"；
3. 前端显示建议（L0 建议）；**无命令**。

### S3：用户在网页点"手动关"，同时土壤很干

1. 用户命令 → 执行层记录 `manual_off.active=true` → 发 `pump_off(user)`；
2. 设备进入 MANUAL，关泵，上报 `mode=manual, pump=off`（L4）；
3. 此时 fast path 命中极干 → `pump_on` 请求 → 检查 7 否决（`manual_off_priority`），记录；
4. 前端提示"手动关闭中，土壤很干"（不隐藏冲突）；
5. 用户取消手动 → 回 AUTO → 本地滞回重新开泵。

### S4：Wi-Fi 断开 2 分钟

1. 设备本地闭环继续；上报失败，设备本地缓存（可选，有限）；
2. 服务端：健康检查 → `hi3861-pot1: offline`，环境数据 age 增长，**过期**；
3. fast path 不再触发（数据过期）；前端显示"离线/数据过期"；
4. 恢复后设备重连，上报最新状态；服务端**重新同步** pump/mode，不假设。

### S5：服务端重启

1. 内存中的去重表、命令表丢失；
2. 设备重连，服务端先**读取** reported 状态；
3. 可能收到重放的事件 → 重复分析一次；命令幂等（action_id）避免二次动作；
4. 若持久化了命令表，则按 desired/reported 对账。

### S6：摄像头断开 / 画面全黑

1. 采集超时或 `frame_valid=false` → RK 进程发空事件心跳带 `frame_valid=false`；
2. 服务端：`vision.health=degraded`；**不得**解读为"植物健康"；
3. 灌溉不受影响。

### S7：重复事件

1. RK 因重传把同一 `event_id` 发了两次；
2. 服务端 `event_id:scope` 去重，第二次在 60 s 内被跳过（计数 `dup_events+1`）；
3. 前端同一画面不重复生成新建议。

### S8：LLM 超时

1. care 节点调用 LLM 超过 $T_{\text{LLM}}$ → 降级为模板建议："检测到 lesion，请检查叶片"；
2. 计数 `llm_timeouts+1`，健康标志 `llm: degraded`；
3. fast path 与灌溉不受影响。

## 7. 启动、重连与降级

### 7.1 启动顺序

1. 服务端启动，状态全为"未知"；
2. 设备连接 → 首次上报 → 状态置为"已知"，带年龄；
3. 前端连接 → 收到全量快照 → 开始增量。

**未知 ≠ 默认值**：启动时 pump 的状态是 `unknown`，不能默认 `off`。

### 7.2 降级矩阵

| 失效 | 灌溉闭环 | 视觉 | 建议 | 前端 | 系统表现 |
|---|---|---|---|---|---|
| Wi-Fi/网络中断 | **继续（本地）** | 继续本地推理，发送失败 | 无新建议 | 显示离线+数据过期 | 恢复后重新同步 |
| 服务端宕机 | **继续** | 继续，发送失败 | 无 | 不可用 | 重启后重新同步 |
| RK3588/摄像头失效 | **继续** | 无观测（`frame_valid=false`） | 无视觉类建议 | 显示视觉离线 | 灌溉与传感仍可用 |
| LLM 不可用 | **继续**；fast path 继续 | 继续 | 降级为模板建议 | 显示 LLM degraded | 功能降级而非停摆 |
| Hi3861 重启 | 重启期间无控制；上电默认关泵 | 继续 | 传感数据过期 | 显示设备重连 | 恢复后重新读取状态 |
| 探头失效 | 设备端传感失效策略：关泵+告警 | 继续 | alert | 显示告警 | 需要人工检修 |

**设计检验**：任何一行的"灌溉闭环"都不应是"停摆或失控"，并且**默认方向是安全（关泵）**。

## 8. 可观测性

### 8.1 关键指标（教学建议）

| 指标 | 含义 | 异常说明 |
|---|---|---|
| `age_s`（每类数据） | 数据年龄 | 链路卡住/设备离线 |
| 每跳延迟 | 采集→推理→发送→接收→决策→广播 | 瓶颈所在 |
| `dropped_events`、队列深度 | 积压与丢弃 | 处理速度不足 |
| `dup_events` | 去重命中 | 设备重发/网络抖动 |
| 命令各级别转化率 L1→L4 | 命令成功率 | 接口不一致/设备拒绝 |
| `rejected` 按理由统计 | 拒绝原因分布 | 策略过严/数据常过期 |
| LLM 超时/校验失败率 | 模型可靠度 | 提示词或模型问题 |
| 继电器切换次数/小时 | 抖振/磨损 | 阈值带或噪声问题 |

### 8.2 手算：端到端延迟预算（教学示例）

| 环节 | 预算 (ms) |
|---|---|
| 采集排队（缓冲队列） | ≤ 150 |
| 预处理 + 推理 + 后处理 | 60（示例） |
| 序列化 + 发送 | 5 |
| Wi-Fi/TCP 传输 | 20 |
| 服务端解析 + 写 DataStore | 5 |
| 规则 fast path | 1 |
| WebSocket 广播 | 10 |
| **合计（规则路径）** | **≈ 251** |
| + LLM care 路径 | + 数百～数千 ms |

据此可以定出视觉新鲜度阈值（应大于正常链路延迟，例如 2 s ≫ 0.25 s），以及"LLM 路径不应出现在需要快速响应的链路上"的结论。我们的实测（time.perf_counter 打点、连续 300 帧均值）约为：取帧到推理结束 60 ms，TCP 到服务端 5–10 ms 量级，服务端入库与广播几毫秒，端到端不到 0.25 s；LLM 路径单次可达 1–3 s，所以它不在快速响应链路上。

## 9. 配置管理

散落在代码里的阈值是故障之源。建议：
- **集中配置**：滞回阈值、fast path 阈值、新鲜度、最长开泵时间、冷却、置信度/NMS 阈值，放在一个配置文件/表里；
- **带版本**：`config_version` 写进每条决策记录；
- **一处修改，多处生效**：Hi3861 端阈值通过下发配置同步，或至少记录"设备端与服务端用的阈值必须保持一致"；
- **注意两层阈值的关系**：设备端的 56/65 是**本地闭环**阈值；服务端的 20 是**极端状态**阈值——二者含义不同，不能混淆，也不能出现互相矛盾（如服务端阈值比设备停止阈值还高，导致反复拉锯）。

## 11. 常见错误与故障现象

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 网页显示状态与设备实际不符 | 展示的是命令状态而非设备报告 | 看确认级别字段 |
| 服务端判传感"来自未来" | 设备时钟快/用设备时间做年龄 | 用接收时间或 age_at_send |
| 重启后泵状态错 | 默认 `off` 假设 | 初始 `unknown`，先读取 |
| 重复建议/重复动作 | 去重缺失或重放无幂等 | `event_id:scope`+`action_id` |
| 视觉与传感拼出矛盾结论 | 混用不同新鲜度的数据 | 融合前过滤 |
| 排查 "为什么没浇水" 无头绪 | 拒绝无记录 | `rejected` 带理由+`trace_id` |
| 服务端与设备阈值不一致 | 配置散落 | 集中配置+版本 |
| 某链路慢却不知哪里 | 无每跳延迟 | 加每跳时间戳与指标 |

## 12. 面试怎么问、怎么答

**Q1. What did "system integration" involve in your project?**

> "Three sources feed one system state: soil readings from the Hi3861, structured detections from the RK3588, and commands from the web UI. The hard parts were time, meaning and failure. Each item carries its source, a capture or receive time, and a sequence or id, so I can judge freshness and trace a decision. I keep sensor readings, observations, recommendations, command requests and device feedback separate, and the UI shows how far a command has been confirmed."

（译：三个来源汇入一个系统状态……难点是时间、语义和失效。每条数据带来源、时间和序号/ID，所以能判断新鲜度并追溯决策。五类信息分开，UI 显示命令确认到哪一级。）

追问 1：**How can you trace why the pump turned on?**
> "Each triggering event gets a trace id. The decision graph appends its path and inputs, the execution layer logs each check, and the command and the device's feedback carry the action id. From the log I can read the sensor value and its age, which path was taken, which checks passed, and what the device reported."

追问 2：**What happens if the server goes down?**
> "Irrigation continues locally on the Hi3861. The pump follows the hysteresis rule and the manual setting. When the server comes back, it doesn't assume the pump state; it reads what the device reports, and commands are idempotent, so replays are safe."

追问 3：**How do you handle clocks across the devices?**
> "I don't assume they're synchronised. The server uses its own receive time for freshness, and devices can send the age at send time measured on their own clock. Events with negative or too large age are rejected."

追问 4：**What would you improve?**
> "Persist the command table and dedup keys across restarts, add end-to-end acknowledgements with action ids if they're missing, put thresholds in one versioned config, and collect per-hop latency metrics. I'd also consider MQTT for a larger number of nodes."

**Q2. Did you test the whole loop on real hardware?**
> "Yes, I ran the full loop on the real devices — soil probe, pump and camera. What I validated is the full loop: the camera event reached the server, the decision produced a constrained request, the device acknowledged it, the pump turned on, and the page showed the state coming back. What I haven't done is a long-duration test."

## 补充专题：从"有数据"到"可信的系统状态"——一致性、健康度与配置版本

### 一、一致性快照：同一时刻的世界

网页和决策链读取的不是三个独立变量，而是一份**一致性快照**（consistent snapshot）：传感、视觉、执行三个子状态在同一把锁内一次拷贝，并带上快照自己的 `snapshot_id` 与 `taken_at`。决策记录保存的是 `snapshot_id` 与摘要，因此事后可以回答"当时系统看到的是什么"。

一致性有两个层次。第一层是前面讲过的撕裂读：同一条消息的字段要一起写一起读。第二层是**跨来源的时间对齐**：传感数据是 3 s 前的，视觉观测是 0.3 s 前的，快照里两者的 age 并列给出，使用者按各自阈值判断。我们**不**强行把它们插值到同一时刻——湿度是慢变量，3 s 前与现在几乎相同；视觉事件本身是离散的。对慢变量做插值反而引入虚假的精度。

### 二、系统健康度：把一堆 age 压成一个可用的结论

网页顶部有一个总体健康标志，规则是把各子系统状态按"最坏者胜出"合并：

| 级别 | 条件 | 含义与行为 |
|---|---|---|
| 绿（normal） | 传感 age 不大于 10 s、泵状态已知、视觉 age 不大于 2 s 或视觉心跳正常、LLM 正常 | 全功能 |
| 黄（degraded） | LLM 超时或视觉心跳缺失，但传感正常 | 仍可自动灌溉；建议降级为模板；UI 标注降级项 |
| 红（critical） | 传感过期或 sensor_fault，或泵状态未知超过 10 s | fast path 禁止开泵；告警；设备本地已关泵；等待人工 |
| 灰（offline） | 设备连接断开 | 所有数据显示为过期，不展示旧值当新值 |

关键点是**没有"空值默认为正常"**：任何一项缺失都会降低总体级别。这是"未知不等于正常"原则的直接落地。

### 三、手算：两个时钟的偏差处理

设备 RK3588 的系统时间与服务端相差未知。RK3588 在发送时在 JSON 里写入 `age_at_send`（发送时刻减采集时刻，同一设备的两个读数相减，不受时钟偏差影响）。服务端收到时刻为 $t_r=1000.00$ s，`age_at_send=0.25` s，则估计采集时刻 $\approx 1000.00-0.25-\delta_{\text{net}}$，其中网络延迟 $\delta_{\text{net}}$ 在局域网内为几毫秒到几十毫秒，可忽略或取一个上界 0.05 s。于是帧龄约 $0.25+0.05=0.30$ s 上界。若发现 `age_at_send` 为负数，或大于 5 s，直接判定该事件时间异常并丢弃，计入 `bad_time` 计数；这比信任设备绝对时间可靠得多。同样的方法用于 Hi3861：它的 timestamp 字段为 0，服务端不使用，全部依赖接收时间与上报周期（2 s）推断新鲜度。

### 四、配置版本：一次修改，多处生效

关键阈值集中在一份带版本的配置里，下面是教学化的片段，字段与取值与 README 自查表一致：

```json
{
  "config_version": 7,
  "device": {"t_on": 56, "t_off": 65, "max_pump_s": 60, "cooldown_s": 120},
  "server": {"fast_dry": 20, "fast_wet": 85, "fresh_sensor_s": 10, "fresh_vision_s": 2},
  "vision": {"score_thr": 0.25, "nms_iou": 0.45, "event_conf": 0.5, "event_frames": 3, "event_gap_s": 5}
}
```

使用规则：每条决策记录带 `config_version`；改动任何一项必须递增版本号并写变更原因；设备端的 `device` 段同步方式是服务端下发后设备回报自己当前的版本号，**不一致就告警**，而不是静默覆盖。设备端和服务端阈值的关系有一条不变量需要在配置加载时检查：`fast_dry < t_on`（20 < 56），否则极端干旱阈值会比本地启动阈值还高，语义混乱；`t_on < t_off`；`max_pump_s` 两侧相同。

### 五、联调检查清单（集成视角）

1. 启动顺序：服务端先于设备，服务端启动日志中状态均为 unknown。
2. 设备首次上报后，网页 3 s 内显示传感值与泵状态。
3. 拔掉 RK3588 网线，6 s 内网页变灰；插回后 30 s 内恢复。
4. 手动点网页"关泵"，设备 ACK 与 reported 在 3 s 内回显。
5. 把土壤探头拔出，设备关泵并上报 sensor_fault，网页变红。
6. 断开 LLM 接口（改错 key），网页变黄，fast path 仍可触发。
7. 重启服务端，设备自动重连，重启期间设备本地灌溉不受影响。
8. 回放一段记录日志，决策结果与记录一致。

这八条覆盖了降级矩阵的每一行，是 V4（实机全链路）验证的核心内容；V5（长时间运行）没有做，是诚实的边界。

> **面试要点**：被问"integration 到底做了什么"，不要说"把模块连起来"。答："我定义了统一系统状态，每个字段带来源、采集时间和年龄；融合前先按各自的新鲜度过滤，缺失不当作正常；决策记录带快照和配置版本，可以回放；降级矩阵保证任何一部分失效灌溉都不会失控。"

## 本章要点速记

1. 集成 = 统一输入 + 可追踪 + 服务端编排 + 闭环；难点是时间、语义、失效。
2. 统一状态：environment / vision / user / commands / decisions / health；每区单一写入者。
3. 状态≠事件≠日志：状态更新靠事件，日志用于复盘。
4. 时间：采集时间、接收时间、决策时间；不假设时钟同步；age 先查有效性。
5. 融合前按各自有效期过滤；结果有效期取最小；过期数据不拼接。
6. trace_id 贯穿事件→决策→命令→反馈；拒绝也记录理由。
7. 未知≠默认：启动/重启后状态 unknown，先读设备报告。
8. 降级矩阵：灌溉闭环在任何一行都不停摆，默认方向是安全（关泵）。
9. 阈值集中配置并带版本；设备端与服务端阈值含义不同、不得矛盾。
10. 诚实：区分"实现了/测试了/实机验证了/长期稳定"。
