## 1. 定位方法：沿数据链二分

P4 的数据链很长，故障现象往往出现在末端（"泵没动""网页不对"），原因却可能在前面任何一环。方法：**在每个边界处观测**，用二分法缩小范围。

```text
探头 → ADC → 标定 → 滞回 → GPIO → 泵
                 └→ 传感JSON → TCP → 重组 → DataStore → 决策 → 执行层 → 命令 → 设备 → 反馈 → 前端
摄像头 → V4L2 → 预处理 → 推理 → 后处理 → 事件 → TCP → 重组 → DataStore → …
```

**每个边界应能"看到"的东西**：

| 边界 | 观测手段 |
|---|---|
| ADC 原始值 | 串口打印 |
| 标定后的湿度、模式、状态、GPIO 电平 | 串口日志 / 万用表量 IN 脚 |
| 设备发出的字节 | 抓包（Wireshark/tcpdump）、服务端十六进制转储 |
| 重组后的帧 | 服务端日志（长度、类型、event_id） |
| DataStore 快照 | 调试接口/日志 |
| 决策路径与拒绝理由 | `trace` 日志 |
| 命令各级别 | L1–L4 时间戳 |
| 预处理后的输入图 | 保存成 PNG |
| 推理原始输出 | 打印形状与若干值 |
| 前端收到的 WebSocket 消息 | 浏览器开发者工具 Network → WS |

**口诀**：*先问数据到了没有，再问对不对，最后问新不新。*

## 2. 故障手册（18 个）

格式：现象 / 根因 / 定位 / 修复 / 预防。

### F1 泵一直开，土壤明明很湿
- **现象**：湿度显示 0 或很低，泵持续开。
- **根因**：探头断线/脱落，ADC 顶到极端值，标定后被 clip 成 0（极干），自动逻辑满足"<56 开"。
- **定位**：串口打印原始 ADC（极端值）；拔插探头对比；看湿度在 0 是否被 clip。
- **修复**：先对**原始 ADC**做有效范围检查，无效则判传感失效→关泵+告警；不要 clip 后使用。
- **预防**：变化率检查、卡死检测、最长连续开泵时间（硬件级兜底）。
- 章节：[03](./03_Hi3861本地灌溉_ADC标定与传感策略.md) §7。

### F2 泵动作方向相反
- **现象**：命令"开"时泵停，"关"时泵转。
- **根因**：低触发继电器，把逻辑 1 直接写成 GPIO 高电平。
- **定位**：用万用表量继电器 IN 脚电平；看 `pump_apply` 的翻译。
- **修复**：逻辑状态与电平分离，仅在一个函数里翻译（开=LOW，关=HIGH）。
- **预防**：上电先写 HIGH 再设为输出；单元测试断言"on → LOW"。
- 章节：[04](./04_Hi3861滞回状态机_继电器与手动优先.md) §6。

### F3 继电器"咔哒"频繁抖振
- **现象**：每秒多次吸合释放，日志中状态来回翻。
- **根因**：单阈值或滞回带 < 噪声；未滤波；$T_{\text{on}}\ge T_{\text{off}}$ 配置错误。
- **定位**：统计切换次数/小时；连续打印读数看抖动幅度。
- **修复**：独立启停阈值（带 > 噪声峰峰值）+ 中位数滤波 + 最短保持时间。
- **预防**：启动时校验配置 $T_{\text{on}}<T_{\text{off}}$；记录切换次数作为指标。

### F4 手动关了，一会儿泵又自己开了
- **现象**：用户关泵后若干周期又开。
- **根因**：退出手动/语音关闭后回到 AUTO，湿度仍低于启动阈值；或自动逻辑未真正暂停。
- **定位**：看模式转换日志；确认 MANUAL 时自动逻辑直接返回。
- **修复**：明确语义：MANUAL_OFF 持续到取消或超时；UI 文案说明。
- **预防**：模式状态机测试：每个转换后的下一周期行为。
- 章节：[04](./04_Hi3861滞回状态机_继电器与手动优先.md) §7.3。

### F5 检测框整体偏移
- **现象**：框的位置与目标有固定偏差，偏移量与补边一致。
- **根因**：letterbox 逆变换漏了 pad，或 scale/pad 用错分辨率。
- **定位**：手算一个点（如 y=200 → (200−140)/0.5=120）对照；在原图上画框。
- **修复**：后处理做 $(x'-\text{pad})/r$ 并夹紧；预处理与后处理共用同一组 $(r,\text{pad})$。
- **预防**：几何变换单元测试（往返恒等）。
- 章节：[05](./05_RK3588边缘视觉_V4L2取帧与预处理.md) §7、[06](./06_YOLOv5输出解码_NMS与结构化事件.md) §7.4。

### F6 检测变差但不报错
- **现象**：漏检变多、类别不稳，无异常。
- **根因**：BGR/RGB 顺序错；归一化与训练不一致；YUV 范围/公式不一致；直接 resize 与训练的 letterbox 不一致。
- **定位**：保存送入网络前的图像；用已知样本（红色物体）对照；与 PC 上 FP32 推理同一张图比较输出。
- **修复**：对齐训练与部署的颜色、范围、几何。
- **预防**：固定一组"金标准图片"的回归测试。

### F7 INT8 后精度明显下降 / 分数全是 0 或 1
- **现象**：FP32 正常，INT8 掉点或分数饱和。
- **根因**：校准集与部署域不符；检测头输出拼在一起共享 scale；离群点拉大步长。
- **定位**：逐层精度分析；比较 FP32/INT8 输出余弦相似度；看哪些层误差大。
- **修复**：换代表性校准集；拆分输出、CPU 解码；敏感层混合精度；必要时 QAT。
- **预防**：量化回归流程：每次转换后在验证集上比 mAP。
- 章节：[07](./07_INT8量化与RKNN转换.md) §8–9。

### F8 JSON 解析间歇失败
- **现象**：偶发 `JSONDecodeError`，大消息更常见，高负载更常见。
- **根因**：一次 `recv` 当一条消息，粘包/半包。
- **定位**：抓包看分段；打印每次 `recv` 长度。
- **修复**：长度前缀 + `recv_exact` 或增量帧解析器（自定界流用括号配对/换行）。
- **预防**：切块测试（逐字节喂入，结果相同）。
- 章节：[08](./08_TCP通信与协议设计.md)。

### F9 服务端内存暴涨/卡死等待
- **现象**：服务端突然占用大量内存或永远等某条消息。
- **根因**：长度字段字节序不一致或数据错位，读出巨大长度；无最大长度保护。
- **定位**：打印帧头十六进制；比较两端字节序。
- **修复**：协议统一网络字节序；`MAX_PAYLOAD` 保护；异常时关闭连接重连。
- **预防**：模糊测试（随机/超长长度字段）。

### F10 网页卡住，所有客户端同时不更新
- **现象**：整个界面冻结几秒，随后一起更新。
- **根因**：事件循环被阻塞调用（同步 LLM/HTTP、`time.sleep`、持锁慢操作）。
- **定位**：监测循环延迟（定时协程测量调度偏差）；`asyncio` debug 模式报告慢回调。
- **修复**：异步客户端或 `run_in_executor`；锁内不做 I/O。
- **预防**：代码审查"循环内禁止阻塞"；加循环延迟告警。
- 章节：[09](./09_服务端_DataStore_WebSocket_asyncio.md) §6。

### F11 偶发崩溃：no running event loop / 数据竞争
- **现象**：随机异常，难以复现。
- **根因**：在非循环线程直接调用 `create_task` / 操作 `asyncio.Queue`。
- **定位**：异常栈中的线程名；确认谁调用。
- **修复**：`call_soon_threadsafe` / `run_coroutine_threadsafe`。
- **预防**：所有跨线程入口集中到一个桥接函数，并有注释与测试。

### F12 事件丢失 / 建议延迟越来越大
- **现象**：高峰期漏事件；LLM 建议延迟持续增长。
- **根因**：处理速度 < 到达速度，队列满丢弃（新的）或积压。
- **定位**：队列深度和 `dropped_events` 指标；$t=\text{容量}/(\lambda-\mu)$ 估算。
- **修复**：合并同类事件、限速、fast path 独立通道、LLM 异步+超时。
- **预防**：容量规划，指标告警。

### F13 LLM 输出非法或越权
- **现象**：解析失败；返回不存在的动作；试图开泵而人工正在关。
- **根因**：无 schema 校验；LLM 被赋予执行权；提示注入。
- **定位**：保存原始 LLM 输出；看校验失败原因。
- **修复**：枚举校验+降级模板；LLM 只产生建议；统一执行层校验。
- **预防**：坏输出用例集；属性测试"manual_off 时永不产生 pump_on"。
- 章节：[10](./10_LangGraph决策链.md) §7、§11。

### F14 旧数据触发动作 / 时钟"来自未来"
- **现象**：基于很旧的读数开泵；或事件年龄为负。
- **根因**：没有新鲜度检查；跨设备时钟相减。
- **定位**：打印每条数据的 age 与来源时钟。
- **修复**：入口过滤；用接收时间或 `age_at_send`；拒绝负年龄。
- **预防**：新鲜度作为执行层强制检查；时间同步。
- 章节：[06](./06_YOLOv5输出解码_NMS与结构化事件.md) §9。

### F15 重复事件导致重复浇水
- **现象**：同一事件触发两次动作，浇水量翻倍。
- **根因**：设备重发/重连重放；去重窗口过期；命令是增量语义。
- **定位**：按 `event_id`/`action_id` 搜日志，看出现次数。
- **修复**：事件去重 + 命令幂等（状态语义+绝对期限+设备端 id 去重）。
- **预防**：重发测试（同一命令发两次，设备只执行一次）。
- 章节：[11](./11_执行边界_白名单_幂等与设备反馈.md) §6–7。

### F16 网页显示"已浇水"但泵没动
- **现象**：UI 状态是已执行，实际没有水。
- **根因**：UI 展示命令状态（L2）当作设备状态（L4）；或命令名/模式不匹配被设备忽略。
- **定位**：设备串口日志是否收到、如何解析；抓包。
- **修复**：UI 显示确认级别；设备回 ack/拒绝理由；契约测试。
- **预防**：联调逐级验证 L1→L5。
- 章节：[11](./11_执行边界_白名单_幂等与设备反馈.md) §2、§9。

### F17 画面滞后 / 掉帧
- **现象**：检测结果对应的是半秒前的画面；FPS 低。
- **根因**：V4L2 缓冲队列积压（处理慢于采集）；USB 带宽不足；曝光时间长。
- **定位**：记录 `buf.sequence` 差、DQBUF 间隔和帧龄。
- **修复**：drain-to-latest；减少缓冲；降低分辨率/改 MJPEG；优化预处理。
- **预防**：监控帧龄指标。
- 章节：[05](./05_RK3588边缘视觉_V4L2取帧与预处理.md) §5。

### F18 服务端重启后状态错误
- **现象**：重启后泵状态显示为关，实际在开；或重复动作。
- **根因**：默认值假设；内存去重/命令表丢失；设备重连后未同步。
- **定位**：对比重启前后的设备报告。
- **修复**：初始 `unknown`；连接后先读 reported；持久化命令表/去重 key；对账。
- **预防**：重启测试（在命令在途时重启服务端）。

## 3. 测试方案

### 3.1 测试金字塔

```text
           ┌───────────────┐
           │ 长时间实机运行 │   少而贵
          ┌┴───────────────┴┐
          │ 台架/硬件在环   │
         ┌┴─────────────────┴┐
         │ 集成（回放/模拟器）│
        ┌┴───────────────────┴┐
        │ 单元（纯函数、表驱动）│  多而快
        └─────────────────────┘
```

### 3.2 各层测什么

| 层 | 对象 | 测试要点 | 输入构造 |
|---|---|---|---|
| 单元 | 标定、滞回、letterbox、IoU/NMS、帧解析、执行层检查、去重 | 边界值（55/56/65/66）、往返恒等、非法输入 | 表驱动；手算期望值 |
| 回放 | 视觉后处理；决策链 | 录制的原始输出/事件序列 → 固定的结构化结果 | 保存的张量/JSON |
| 协议 | 帧解析、重连 | 任意切块、超长长度、乱序、半包、断线 | 模糊测试 + 字节级构造 |
| 决策链 | 路由、fast path、校验 | 每个场景走哪条路径；坏 LLM 输出被拒 | 构造 state；mock LLM |
| 集成 | 事件→决策→命令→设备模拟器 | 各级别转换、拒绝理由、幂等 | 设备模拟器（脚本） |
| 台架 | 真实 Hi3861 + 继电器（无水泵/用灯） | GPIO 极性、上电默认、模式转换 | 万用表、示波器、串口 |
| 实机 | 全链路 | 端到端延迟、断网、重启、长跑 | 日志与指标 |

### 3.3 不变量（safety properties）

用属性测试验证，永远成立：
1. `manual_off.active ⟹ 不存在被接受的自动 pump_on`；
2. `传感无效/过期 ⟹ 不存在由 fast path 产生的 pump_on`；
3. 任意命令集合被重放 N 次，设备最终状态与执行一次相同（幂等）；
4. 上电后 GPIO 默认电平 = 关；
5. 连续开泵时间 ≤ $T_{\max}$；
6. $T_{\text{on}}<T_{\text{off}}$ 的配置校验。

## 4. 可执行测试示例

### 4.1 滞回（表驱动，含边界）

```python
import pytest

def step(state, m, t_on=56, t_off=65):
    if m < t_on:  return True
    if m > t_off: return False
    return state

@pytest.mark.parametrize("seq, init, expected", [
    ([55, 60, 64, 66, 60],        False, [True, True, True, False, False]),
    ([56, 55, 65, 66, 56],        False, [False, True, True, False, False]),
    ([57, 56, 55, 60, 65, 66, 60, 56, 55], False,
        [False, False, True, True, True, False, False, False, True]),
])
def test_hysteresis(seq, init, expected):
    s, out = init, []
    for m in seq:
        s = step(s, m); out.append(s)
    assert out == expected
```

### 4.2 标定与整数边界

```python
def adc_to_m(adc):
    m100 = -5 * adc + 14752
    return max(0, min(100, m100 // 100))

@pytest.mark.parametrize("adc, m", [(2000, 47), (1650, 65), (1630, 66), (2950, 0), (2700, 12)])
def test_cal(adc, m):
    assert adc_to_m(adc) == m
```

### 4.3 letterbox 往返

```python
def forward(x, y, r, left, top): return x * r + left, y * r + top
def inverse(xp, yp, r, left, top): return (xp - left) / r, (yp - top) / r

def test_letterbox_roundtrip():
    r, left, top = 0.5, 0, 140
    xp, yp = forward(200, 120, r, left, top)
    assert (xp, yp) == (100, 200)
    assert inverse(xp, yp, r, left, top) == (200, 120)
```

### 4.4 NMS 与 IoU

def test_nms_thresholds():
    boxes = [[100,100,200,200],[110,105,210,205],[300,300,400,400],[105,100,205,200]]
    scores = [0.9, 0.8, 0.7, 0.6]

### 4.5 帧解析：任意切块

```python
def test_framing_any_chunking():
    msg = HDR.pack(1, 5) + b"hello" + HDR.pack(2, 3) + b"abc"
    for step_ in (1, 2, 3, 5, 7, len(msg)):
        p, got = FrameParser(), []
        for i in range(0, len(msg), step_):
            got += p.feed(msg[i:i+step_])
        assert got == [(1, b"hello"), (2, b"abc")]

def test_framing_rejects_huge_length():
    p = FrameParser()
    with pytest.raises(ValueError):
        p.feed(HDR.pack(1, 10**9))
```

### 4.6 执行层与不变量

```python
def test_manual_off_never_accepts_pump_on():
    for age in (0.0, 1.0, 4.9):
        for moist_extreme in (True, False):
            ctx = Ctx("manual", "off", age, True, "off", 100.0, set())
            d, why = check({"name": "pump_on", "id": f"x{age}{moist_extreme}",
                            "source": "rule", "max_s": 60}, ctx)
            assert d != "accept"

def test_resend_is_idempotent():
    ctx = Ctx("auto", None, 1.0, True, "off", 100.0, set())
    c = {"name": "pump_on", "id": "a1", "source": "rule", "max_s": 60}
    assert check(c, ctx)[0] == "accept"
    ctx.seen_ids.add("a1")                       # 执行后记录
    assert check(c, ctx)[0] == "replay"          # 重发不再执行
```

### 4.7 去重窗口

```python
def test_dedup_window():
    processed = {}
    def seen(eid, scope, now, window=60):
        k = f"{eid}:{scope}"
        t = processed.get(k)
        if t is not None and now - t < window: return True
        processed[k] = now; return False
    assert seen("e1", "sensor", 0)  is False
    assert seen("e1", "sensor", 30) is True
    assert seen("e1", "detect", 30) is False
    assert seen("e1", "sensor", 61) is False
```

### 4.8 设备模拟器（集成测试用）

```python
class FakeDevice:
    """模拟 Hi3861 的命令处理，用于服务端集成测试。"""
    def __init__(self): self.pump = "off"; self.mode = "auto"; self.seen = set()
    def handle(self, cmd):
        if cmd["id"] in self.seen: return {"ack": "dup", "pump": self.pump}
        self.seen.add(cmd["id"])
        if self.mode == "auto" and cmd["name"] in ("pump_on",) and not cmd.get("force"):
            return {"ack": "rejected", "reason": "auto_mode", "pump": self.pump}
        self.pump = "on" if cmd["name"] == "pump_on" else "off"
        return {"ack": "accepted", "pump": self.pump}
```

用它写契约测试：对白名单里的每条命令逐一发送并断言 ack/状态；这正是发现"命令名映射不一致"这类问题的办法。

## 5. 验证阶梯

| 级别 | 含义 | 你能说的话 |
|---|---|---|
| V0 | 代码写完，静态检查通过 | "The code implements …" |
| V1 | 单元/表驱动测试通过 | "The logic is covered by tests …" |
| V2 | 回放/模拟器上集成通过 | "In a replay and with a device simulator …" |
| V3 | 台架：真实 MCU/继电器，GPIO 极性和模式转换验证 | "On the bench I verified …" |
| V4 | 实机全链路跑通（摄像头+泵+网页） | "I ran the full loop on the real hardware …" |
| V5 | 长时间/多场景运行，有数据 | "Over N hours …（必须有数据）" |

**诚实规则**：只说到你确实到达的级别。这个项目是 2024 年 5–8 月完成的个人项目，最高到达 V4（实机全链路），没有 V5 长时间运行。我们真正遇到并解决的 3 个故障如下，面试官最爱追问真实踩过的坑，选真实的比选"看起来漂亮"的更有说服力：

| # | 现象 | 证据来源 | 根因与处理 |
|---|---|---|---|
| 1 | 湿度低于 56 时泵反而不转，上电瞬间泵却短暂吸合 | 万用表量继电器 IN 脚电平、串口日志 | 继电器模块低电平触发，代码把逻辑电平和引脚电平混为一谈。处理：逻辑状态与引脚电平分离，默认输出高，加边界测试 |
| 2 | 网页上检测框整体偏下 | 保存原图叠框对比、手算偏移 | 还原坐标时没有减去 letterbox 的上下灰边 pad。处理：预处理与还原共用同一组 (r, pad)，加往返测试 |
| 3 | 服务端偶发 JSON 解析失败 | Wireshark 抓包看到一条消息被分成两段 | 把 TCP 当成消息流。处理：RK 侧长度前缀，Hi3861 侧括号配对，并用任意切块的测试喂数据 |

## 7. 面试怎么问、怎么答（含 STAR）

**Q1. Tell me about a bug you found in this project and how you debugged it.**

下面是**模板**，请换成你**真实**遇到的问题（至少选一个自己真的碰到过的）：

> **S**ituation: "In my smart gardening project, 【the pump behaved opposite to the command / the boxes were shifted / the JSON parser failed intermittently】."
> **T**ask: "I needed to find where in the chain the problem came from — device, network or server."
> **A**ction: "I checked each boundary in turn. 【例：I probed the relay input with a multimeter and saw the pin was low when the pump was off, so the logic was inverted; the relay is active-low. I separated the logical state from the pin level and translated in one function, and added a test.】"
> **R**esult: "The pump followed the command. I also made GPIO default high at power-up, so a reset can't turn the pump on."

**Q2. How did you test the system?**

> "At several levels. The pure logic — calibration, hysteresis, letterbox, non-maximum suppression, frame parsing and the execution checks — is table-driven and easy to unit-test, including boundary values like 55, 56, 65 and 66. For the vision chain I'd replay saved frames and compare structured outputs. For the protocol I feed bytes in arbitrary chunk sizes. For the loop I use a device simulator, then the real hardware. I'm careful to say which of those I actually completed: the table-driven tests of the pure logic, the chunked-byte tests of the protocol, a device simulator, and then the real hardware for the full loop. I did not run a long-duration test."

**Q3. What was the hardest bug?**
> 选一个与"时间/并发/语义不一致"有关的故事最能体现工程深度：例如"服务端判设备数据来自未来（时钟）""显示已执行但泵没动（确认级别）""跨线程调用偶发崩溃"。务必是真实的。

**Q4. How do you know your safety properties hold?**
> "I state them as invariants — for example, with manual off active, no automatic pump-on is ever accepted; with stale sensor data, the fast path never fires — and test them with property-style tests over many generated states. Hardware-level limits like a maximum run time sit on the device, independent of the server."

**Q5. What would you test next if you had more time?**
> "A long-duration run with metrics for relay switch counts and latency, a fault-injection test that kills the server mid-command, and an FP32 versus INT8 comparison on a labelled validation set."
