## 1. 从需求到方案：选型与取舍

### 1.1 需求

这是 2024 年 5 月到 8 月的个人项目，与华为 ICT 大赛编程赛道（OpenHarmony）相关。用户故事只有一句话：**让盆栽自己判断要不要浇水，并且能发现叶片的异常，告诉我为什么**。拆成工程需求：

| 编号 | 需求 | 类型 | 验收方式 |
|---|---|---|---|
| R1 | 土壤干了自动浇水，浇到合适就停，不抖动 | 功能、安全 | 滞回状态机；台架看继电器切换次数 |
| R2 | 断网、服务端挂了，浇水仍然可用 | 可靠性 | 拔网线测试，本地闭环继续 |
| R3 | 人随时可以手动开关，且人的意图优先 | 安全 | 手动模式下自动逻辑暂停 |
| R4 | 摄像头能识别叶片萎蔫、病斑 | 功能 | 自有验证集 mAP；现场回放 |
| R5 | 视觉识别在边缘设备上实时运行 | 性能 | 约 15 FPS，端到端约 60 ms |
| R6 | AI 给出建议，但不能直接控制泵 | 安全 | 白名单加策略校验加设备反馈 |
| R7 | 每个决策可追溯、可解释 | 可维护 | 统一状态、trace_id、审计记录 |
| R8 | 网页上能看到状态、能下命令 | 交互 | WebSocket 页面 |

### 1.2 选型：每个决定背后的备选和理由

| 决策 | 备选 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| 灌溉控制放哪 | 全放服务端 / 全放 Hi3861 / 分层 | Hi3861 本地闭环加服务端建议 | R2 要求断网可用；泵的安全逻辑必须离执行器最近 | 两处各有一份阈值，需要对齐 |
| 视觉放哪 | 服务端推理 / 板端推理 | RK3588 板端 NPU | 避免把整帧视频上传；延迟低；服务端可无 GPU | 要做量化与交叉编译 |
| 检测模型 | YOLOv5s / YOLOv5n / 其他 | YOLOv5s INT8 | 病斑是小目标，n 型召回更差；s 型在 NPU 上已够快 | 模型约 8 MB，精度略降 |
| 量化 | FP16 / INT8 | INT8 | NPU 原生、吞吐高 | mAP@0.5 从 0.86 到 0.83 |
| 通信 | MQTT / 原生 TCP / HTTP | 原生 TCP 长连接 | 设备少，MCU 上 lwIP 实现简单 | 自己做成帧、重连 |
| 服务端 | 多线程 / asyncio | asyncio 加一个阻塞 TCP 线程 | 网页与 Agent 是 I/O 密集 | 阻塞调用必须隔离 |
| 决策 | 纯规则 / 纯 LLM / 混合 | LangGraph 混合：规则 fast path 加 LLM 节点 | 极端状态要确定、要快；解释性建议才用 LLM | 要写校验与降级 |
| 执行 | LLM 直接下命令 / 经校验 | 建议加命令请求，经白名单与策略 | 安全；可审计 | 多一层映射和契约测试 |

### 1.3 与同类做法的差异

多数"AI 浇花"演示把模型输出直接接到继电器。本项目的差别是三条纪律：本地闭环不依赖网络和 LLM；LLM 的输出只是建议；设备的上报才是执行的证据。这三条每一条都有成本（多写代码、多做测试、多一层延迟），它们换来的是**任何一层失效，都不会让泵失控**。

## 2. 架构与里程碑：四个月怎么走

### 2.1 总体架构（回顾）

```text

 继电器/语音/手动优先   <TCP>  结构化观测(JSON+JPEG)  <TCP>    WebSocket/LangGraph/执行层
     |   8001: JSON 括号配对        8002: 8 字节头 + JSON + JPEG        |
```

### 2.2 里程碑与迭代

时间为设计性的迭代安排，与 5 到 8 月的总周期一致。每个里程碑都有可演示的产出和验收标准：

| 里程碑 | 时间 | 产出 | 验收 |
|---|---|---|---|
| M0 环境与硬件 | 5 月上旬 | OpenHarmony 工具链、Hi3861 烧录、RK3588 系统、摄像头、泵与继电器接线 | 板子能点灯，摄像头能出图，继电器能吸合 |
| M1 本地灌溉 | 5 月中下旬 | ADC 读数、两点标定、中位数滤波、滞回状态机、手动命令 | 台架上湿度跌破 56 开泵，越过 65 关泵，不抖动 |
| M2 视觉链 | 6 月 | V4L2 取帧、letterbox、ONNX 到 RKNN、解码、NMS | 一张图输出正确的框；板上与 PC 结果一致 |
| M3 数据集与量化 | 6 月下旬到 7 月上旬 | 采集约 1800 张叶片图、标注、微调 100 epoch、INT8 校准与验证 | mAP 与 Recall 对比表；现场回放 |
| M4 协议与服务端 | 7 月 | 两条 TCP 通道、DataStore、WebSocket 页面 | 网页实时显示传感与检测，切块测试通过 |
| M5 决策链与执行 | 7 月下旬 | LangGraph 六节点、fast path、校验、白名单、ACK、幂等 | 模拟器上 10 条命令判决用例全过 |
| M6 联调与降级 | 8 月 | 实机全链路、八条联调清单、降级验证 | 到达 V4 |
| M7 收尾与演示 | 8 月下旬 | 文档、演示脚本、赛事答辩材料 | 完整演示一遍不出错 |

迭代原则有两条：**先让最安全的部分能工作**（M1 先于一切），再接上智能的部分；**每一层先用模拟器或回放验证，再接真实上下游**（M5 先用设备模拟器，M6 才上实机）。这样出错时，能知道错在哪一层。

## 3. 各层频率与周期设计

### 3.1 一张总表

| 层 | 过程 | 频率或周期 | 为什么是这个数 |
|---|---|---|---|
| Hi3861 | ADC 采样 | 每 200 ms 一次 | 凑 5 个样本做中位数，本身不追求带宽 |
| Hi3861 | 出湿度值与状态机 | 每 1 s | 土壤是慢过程；1 s 对其带宽余量超过 10 倍 |
| Hi3861 | 上报 | 每 2 s | 新鲜度 10 s 内保证至少 5 次机会 |
| Hi3861 | 最长开泵、冷却 | 60 s、120 s | 保护定时器，见[第 4 章补充](./04_Hi3861滞回状态机_继电器与手动优先.md) |
| Hi3861 | 语音与手动命令 | 事件驱动（UART 中断/收到命令即处理） | 人的意图要最快响应 |
| RK3588 | 摄像头采集 | 30 fps，约 33 ms | 摄像头固有节拍 |
| RK3588 | 推理 | 稳定约 15 FPS，约 67 ms 一帧 | 处理链约 60 ms；只取最新帧 |
| RK3588 | 事件门 | 同类连续 3 帧、conf 不低于 0.5；同类最短间隔 5 s | 压低抖动与带宽 |
| RK3588 | 心跳 | 每 1 s，无图 | 区分"没东西"和"没在看" |
| 服务端 | 传感快照更新 | 随上报，约 0.5 Hz | 来源节拍决定 |
| 服务端 | fast path 评估 | 每次传感更新、每次事件到达 | 规则成本约 1 ms，没理由不每次算 |
| 服务端 | LLM care 路径 | 每个事件最多一次，LLM 并发 1，超时 10 s | 慢且贵；5 s 事件间隔本身限流 |
| 服务端 | WebSocket 推送 | 状态变化即推，空闲时最低 1 s | 网页要"活"，也要探活 |
| 服务端 | ACK 对账 | 每 1 s 扫描待确认命令 | 超时 2、4、8 s，1 s 分辨率足够 |
| 服务端 | 日志 | 异步落盘，每条决策一行 | 不阻塞事件循环 |
| 联调 | 回放 | 非实时，尽快回放 | 测试用 |

### 3.2 一个反复使用的设计原则

频率不是越高越好。每一层的节拍由**它所观测的过程的时间尺度**决定，上下游节拍成整数倍关系：

```text
200 ms 采样 --5个--> 1 s 出值/状态机 --2个--> 2 s 上报 --> 10 s 新鲜度窗口(5个上报)
66 ms 推理帧 --3帧确认--> 事件 --5 s 最短间隔--> Agent 一次分析 --> 秒级建议
```

整数倍关系的好处是：状态机永远读到一个完整窗口的输出，不会读到半个窗口；上报永远包含最新的一次状态机结论。

### 3.3 抖动与它的来源

| 来源 | 影响 | 处理 |
|---|---|---|
| LiteOS-M 任务调度 | 采样周期有几毫秒抖动 | 对 200 ms 周期的中位数几乎无影响，不做特殊处理 |
| Wi-Fi 重传 | 上报到达时间抖动数十到数百毫秒 | 服务端用接收时间与 `seq`，不用到达间隔推断设备周期 |
| 摄像头自动曝光 | 帧间亮度变化，置信度抖动 | 事件门三帧确认 |
| Python GC 与 JPEG 编码 | 偶发单帧变慢（p95 约 75 ms） | 编码放发送线程，推理线程不被打断 |
| LLM 响应时间 | 1 到数十秒，不确定 | 只在慢通路，设 10 s 超时与降级 |

## 4. 延迟预算与带宽预算

### 4.1 视觉到网页的端到端预算

| 环节 | 预算（ms） | 说明 |
|---|---|---|
| 采集排队 | 不超过 33（只取最新帧） | 不做最新帧策略时可达 150 以上 |
| MJPEG 解码、letterbox | 约 10 到 14 | CPU，OpenCV |
| NPU 推理（INT8） | 约 28 | 单核 |
| 解码、NMS、事件构造 | 约 3 到 5 | 先过滤再 NMS |
| 序列化与发送 | 约 5 | JPEG 另算 |
| Wi-Fi 与 TCP | 约 20 | 局域网 |
| 服务端解析、入库、广播 | 约 3 | 见[第 9 章补充](./09_服务端_DataStore_WebSocket_asyncio.md) |
| **合计** | **约 110 到 150 ms** | 规则路径，LLM 路径另计 |

与[第 12 章](./12_系统集成与可追踪系统状态.md)的粗预算（含 150 ms 排队，合计约 251 ms）对比：最新帧策略把排队从 150 ms 压到 33 ms 以内，规则路径从约 250 ms 降到约 150 ms 以内。视觉新鲜度阈值取 2 s，比最慢路径大一个数量级，足够容忍抖动。

### 4.2 传感到泵动作的预算（本地闭环）

这是**最重要的一条延迟链**，因为它决定灌溉的及时性，且不经过网络：

| 环节 | 最坏延迟 |
|---|---|
| 土壤变干到下一个 1 s 出值 | 1 s |
| 状态机判断到 GPIO 写低 | 小于 1 ms |
| 继电器机械吸合 | 约 10 ms |
| 水从出水口到探头（过程时间） | 数十秒，属于被控对象的特性 |

从"读数低于 56"到"泵开"最坏约 1 s，完全可以接受。该链上**没有 Wi-Fi、没有服务端、没有 LLM**，这就是"本地闭环"的意义。

### 4.3 服务端建议链的预算

| 环节 | 典型值 |
|---|---|
| 事件门通过（含三帧确认） | 约 0.3 s |
| 事件入队、Agent 取出 | 毫秒 |
| 规则判断 | 约 1 ms |
| LLM 调用（care 节点） | 1 到 3 s，超时 10 s |
| 校验、执行层检查 | 约 5 ms |
| 发送到设备并 ACK | 约 50 到 300 ms |
| 合计 | 约 2 到 4 s，最坏约 11 s |

这条链讲的是"建议到用户看到"，不是"控制"；它的时间尺度是秒，与病斑、萎蔫这类现象的变化速度（小时到天）相比绰绰有余。

### 4.4 带宽预算

| 流 | 估算 | 说明 |
|---|---|---|
| Hi3861 上报 | 约 60 B/s | 120 字节每 2 s |
| RK3588 心跳 | 约 200 B/s | 每秒一条无图 JSON |
| RK3588 事件 | 峰值约 30 KB/s 每类 | 100 到 150 KB 的 JPEG 每 5 s |
| 若每帧发图（反例） | 约 2.2 MB/s，约 18 Mbit/s | 与 Hi3861 争 2.4 GHz 信道 |
| 网页推送 | 每客户端数 KB/s | 快照 JSON，不含图像 |

## 5. 线程、任务与调度

### 5.1 Hi3861（LiteOS-M）任务划分

| 任务 | 周期或触发 | 优先级（设计取值，数字越小越高） | 说明 |
|---|---|---|---|
| 控制任务（采样加滤波加状态机加 GPIO） | 200 ms 采样，1 s 状态机 | 高 | 最关键，不被任何网络操作阻塞 |
| 语音与手动命令任务 | 串口中断唤醒 | 高 | 人的命令快速生效 |
| 网络任务（上报、收命令、ACK） | 2 s | 中 | 发送失败不影响控制任务 |
| 日志与看门狗喂狗 | 1 s | 低 | 控制任务心跳才喂狗，避免任务死而狗不饿 |

关键纪律：**网络任务永远不阻塞控制任务**；两者之间只通过"最新一条待上报结果"和"命令邮箱"交换数据（深度为 1，新值覆盖旧值），不排队。这样网络再差，控制节拍也不会被拖慢。

### 5.2 RK3588 线程

| 线程 | 职责 | 说明 |
|---|---|---|
| capture | DQBUF、MJPEG 解码、写入最新帧邮箱 | 只做取帧 |
| infer | 取邮箱、letterbox、NPU、解码、NMS、事件门 | 绑定大核（设计取值），NPU 单核运行 |
| sender | 事件和心跳的序列化、JPEG 编码、TCP 发送 | 队列深度 4，队满丢最旧 JPEG |
| watchdog | 监测各线程心跳，帧超时发 frame_valid=false | 区分"没东西"和"没在看" |

### 5.3 服务端

一个 TCP 阻塞线程（板端协议简单，按阻塞读帧）加一个 asyncio 事件循环（WebSocket、Agent、ACK 对账、日志写入）。跨线程用 `call_soon_threadsafe` 投递；DataStore 用短锁；LLM 并发度为 1 的信号量，超时 10 s。

## 6. 优化过程（六次）

每一次优化都按同一个套路：现象 → 度量方法 → 瓶颈 → 改动 → 前后对比 → 回归验证。对比数字为设计取值与教学估算。

### 6.1 优化一：帧龄漂移，改为"只取最新帧"

- **现象**：网页上的检测框总是落后于画面，运行几十秒后落后越来越明显。
- **度量**：在取帧时记录驱动时间戳，在发送前计算 `age_at_send = 当前时刻 - 采集时刻`，打印前 300 帧的趋势。
- **瓶颈**：处理链约 60 ms，大于摄像头的 33 ms 节拍；帧在驱动缓冲队列里积压，帧龄上升直到缓冲写满。
- **改动**：取帧线程把已就绪的帧一次取空，只保留最新一帧，其余立即归还驱动并计 `dropped_frames`。
- **对比**：帧龄从不受控（缓冲写满后约 190 ms 以上）降到不超过约 93 ms，且不再随时间漂移。
- **回归**：用固定视频回放 300 帧，断言 `age_at_send` 的最大值小于 100 ms，且 `dropped_frames` 大于 0（说明丢帧生效）。

### 6.2 优化二：JPEG 编码移出推理线程

- **现象**：事件帧偶发特别慢，p95 偏高。
- **度量**：分别统计"有事件帧"与"无事件帧"的各阶段耗时。
- **瓶颈**：事件帧在推理线程内同步编码 JPEG（约 8 ms），阻塞了下一帧的处理。
- **改动**：推理线程只把原始帧引用和事件交给 sender 线程，编码与发送在 sender 线程完成。
- **对比**：有事件帧的推理线程占用从约 68 ms 降到约 60 ms，p95 回到约 75 ms。
- **回归**：事件内容、JSON 与 JPEG 配对（同一 `event_id`）的集成测试保持通过。

### 6.3 优化三：事件门限流，把带宽降两个数量级

- **现象**：同时有 Hi3861 上报与大量图像上传时，Hi3861 偶发上报超时，网页的传感数据变灰。
- **度量**：抓包统计各端口每秒字节数；看 Hi3861 重连日志。
- **瓶颈**：每帧上传图像约 18 Mbit/s，占满 2.4 GHz 信道。
- **改动**：只在事件门通过时上传 JPEG；无事件只发小心跳；JPEG 质量 80。
- **对比**：平均带宽从约 18 Mbit/s 降到不足 1 Mbit/s；Hi3861 重连次数降到几乎为 0。
- **回归**：事件门单元测试（见[第 6 章补充](./06_YOLOv5输出解码_NMS与结构化事件.md)的帧序列），并确认 `frame_valid=false` 心跳仍然发出。

### 6.4 优化四：FP16 改 INT8

- **现象**：FP16 模型单帧约 45 ms，端到端接近 80 ms，p95 超过 100 ms，帧率接近下限。
- **度量**：同一批图在 FP16 与 INT8 下，分别测 NPU 耗时与 mAP、Recall。
- **瓶颈**：NPU 对 INT8 的吞吐显著高于 FP16，模型体积也大一倍。
- **改动**：使用 200 张校准集转为 INT8，检测头保持分开输出，分数在 CPU 解码。
- **对比**：NPU 约 28 ms；mAP@0.5 从 0.86 降到 0.83；disease_spot Recall 从 0.78 降到 0.73。
- **回归**：余弦相似度逐层检查、mAP 对比表、现场 100 帧回放；事件门触发次数与 FP16 回放相比差别在可接受范围。

### 6.5 优化五：先过滤再 NMS，并用按类别 NMS

- **现象**：解码阶段 CPU 占用偶发飙高，个别帧后处理超过 15 ms。
- **度量**：给解码、过滤、NMS 分别打点。
- **瓶颈**：对 25200 个候选直接做 NMS，复杂度接近平方。
- **改动**：先用 obj 不低于 0.25 过滤，再计算 score 过滤，再做按类别 NMS；用数组化运算替代 Python 循环。
- **对比**：后处理从偶发 15 ms 以上降到稳定 3 到 5 ms。
- **回归**：NMS 手算用例（四个候选的 IoU 手算）作为单元测试，两个不同 IoU 阈值各测一次。

### 6.6 优化六：LLM 调用异步化与超时

- **现象**：一次 LLM 响应慢时，网页全部冻结，心跳超时，浏览器断线。
- **度量**：给事件循环加"循环延迟监视"（定时器预期与实际触发时间之差）；发现阻塞。
- **瓶颈**：使用了同步的 LLM 客户端，在事件循环里阻塞等待。
- **改动**：改为异步客户端，超时设 10 s，并发限制为 1；超时降级为模板建议。
- **对比**：事件循环延迟从最长数秒降到小于 50 ms。
- **回归**：注入 LLM 超时、非法 JSON、缺字段三种故障，断言网页心跳不间断、fast path 照常、降级建议出现。

### 6.7 优化小结

| 次 | 优化 | 指标改善 | 代价 |
|---|---|---|---|
| 1 | 只取最新帧 | 帧龄上限 约 93 ms，不漂移 | 丢帧 |
| 2 | JPEG 移线程 | p95 回到约 75 ms | 多一个线程与队列 |
| 3 | 事件门限流 | 带宽 约 18 到小于 1 Mbit/s | 响应延迟约 0.3 s |
| 4 | INT8 | NPU 45 到 28 ms | mAP 降 0.03 |
| 5 | 先过滤再 NMS | 后处理稳定 3 到 5 ms | 无 |
| 6 | LLM 异步 | 事件循环不再冻结 | 超时降级逻辑 |

## 7. 工程问题与解决（十二个）

下面十二个问题中，前三个是真实踩过的（与自查表和[第 13 章](./13_故障与测试.md)一致）；其余是设计与联调中识别并处理的问题，按"现象、根因、处理、防回归"讲述。

### 问题 1（真实）：继电器低触发，上电即开泵

- 现象：首次台架测试，Hi3861 一上电泵就吸合；湿度低于 56 时反而不转。
- 排查：代码里逻辑状态，万用表量继电器 IN 脚，查模块手册（光耦隔离、低电平触发）。
- 根因：代码把"逻辑开"当成"引脚高"，而模块低电平触发；默认输出为低，等于上电即开。
- 处理：逻辑状态与引脚电平分离，只在一个函数里翻译；初始化先写高再起任务。
- 防回归：台架脚本检查上电后 IN 脚为高；`pump_set(true)` 后为低。

### 问题 2（真实）：检测框整体偏下

- 现象：网页上框整体比物体低约 280 像素。
- 排查：保存原图、画框、手算：缩放比 0.5、上灰边 140，模型空间 y=200 应还原为 (200-140)/0.5=120，代码却给出 400。
- 根因：还原坐标时漏减 pad。
- 处理：预处理和还原共用同一个返回 (r, pad) 的函数。
- 防回归：往返单元测试。

### 问题 3（真实）：TCP 偶发 JSON 解析失败

- 现象：每隔几分钟服务端解析 Hi3861 的 JSON 失败一次。
- 排查：抓包，看到一条消息分两次到，或两条合并到。
- 根因：把一次 recv 当一条消息。
- 处理：RK3588 流用长度前缀；Hi3861 流用括号配对，且能识别字符串内的括号。
- 防回归：随机切块测试。

### 问题 4：阈值两侧不一致

- 现象：联调时服务端以为"湿度 58 还不够湿"，设备却已在 65 才停。
- 根因：服务端和设备端各写了自己的阈值，未对齐。
- 处理：设备端 56/65 与服务端极端阈值 20/85 分开命名、分开含义，写入集中配置并检查不变量（20 小于 56，56 小于 65）。
- 防回归：配置加载时校验不变量，设备上报自己的 `config_version`。

### 问题 5：命令名与设备端不一致

- 现象：网页点开泵，服务端日志显示已发送，泵无反应。
- 根因：服务端枚举 `start/stop`，设备解析 `water_on/water_off`，且设备远程开关只在手动模式下接受。
- 处理：加适配层集中映射，并在设备回 `accepted=false` 时服务端状态置 rejected_by_device。
- 防回归：契约测试（第 11 章补充专题的六条）。

### 问题 6：开泵期间传感失效

- 现象：拔探头后读数变成越界值，泵一直开。
- 根因：只有滞回逻辑，没有传感有效性。
- 处理：raw 大于 3250 或小于 200、连续 3 次读取失败，则 valid=false，关泵并上报 sensor_fault。
- 防回归：注入越界读数的单元测试。

### 问题 7：阴天或夜间置信度下降

- 现象：夜间画面中病斑几乎检不出。
- 根因：校准集和训练集夜间样本太少。
- 处理：补充现场补光与夜间图像，校准集含 50 张现场补光与夜间图；现场补光灯。
- 防回归：验证集按光照分组统计 Recall。

### 问题 8：事件循环冻结

- 现象：LLM 慢时网页冻结（见优化六）。
- 处理与防回归：异步客户端、超时、并发 1、故障注入。

### 问题 9：重复分析同一事件

- 现象：同一病斑触发多次 LLM 调用，建议重复。
- 根因：设备重发或网络抖动，同一事件多次到达。
- 处理：`event_id:scope` 去重，窗口约 60 s，分析前先标记。注意这只是防止重复分析，不是 exactly-once。
- 防回归：重复事件测试，并确认失败路径不会永久吞掉事件。

### 问题 10：人工关泵被自动重新打开

- 现象：用户用语音关泵，下一周期泵又开了。
- 根因：语音关闭让系统回到自动，而湿度仍低于 56。
- 处理：在文档与界面里明确"手动 off 只在手动模式内有效"；网页上用户的"关泵"带超时的 MANUAL_OFF 状态，服务端据此拒绝自动开泵。
- 防回归：模式切换序列测试。

### 问题 11：服务端重启后假设泵关闭

- 现象：服务端重启后立即基于"泵关"发出开泵请求，而泵其实正开着。
- 根因：启动时把未知状态默认成关。
- 处理：启动状态为 unknown，等第一条带 pump 字段的上报再做判断。
- 防回归：重启场景测试。

### 问题 12：LLM 输出看似合法但字段越界

- 现象：LLM 返回的 JSON 能解析，但动作名不在名单、持续时间为负或过大。
- 处理：解析之后还要做枚举与范围校验；失败降级为规则结果。
- 防回归：非法枚举、负数、超大数的用例。

### 问题分类小结

| 类别 | 问题 |
|---|---|
| 硬件与固件 | 1、6 |
| 数据与算法 | 2、7 |
| 协议与接口 | 3、4、5 |
| 并发与状态 | 8、9、11 |
| 安全与人机 | 10、12 |

## 8. 联调过程

联调的目标是把"各层单独正确"变成"整体正确"。我们按**由内向外**的顺序，每次只接入一个新的真实部件，其余部件用模拟器：

| 阶段 | 真实部件 | 模拟部件 | 验证 |
|---|---|---|---|
| J1 | Hi3861、继电器、泵 | 手动串口命令 | 极性、滞回、最长开泵、传感失效 |
| J2 | Hi3861 加服务端 | 视觉用回放 | 上报解析、命令往返、ACK |
| J3 | RK3588 加服务端 | 设备用模拟器 | 长度前缀、JSON 与 JPEG 配对、事件门 |
| J4 | 三者全真实 | 无 | 联调清单八条 |
| J5 | 加网页 | 无 | 网页状态、手动命令、降级显示 |

调试手段：串口日志、万用表、Wireshark 抓包、保存原始帧叠框、`trace_id` 贯穿日志、设备模拟器与回放工具。**每次联调失败，先按数据链二分**：服务端是否生成命令、是否通过校验、设备是否收到、设备是否接受、GPIO 电平、继电器与泵电源。

最后一次完整联调（V4）：摄像头对准盆栽，探头插入土壤，泵连接水管；手动点网页"开泵"，设备 ACK 与泵状态回显；让土壤变干，Hi3861 本地开泵；遮挡镜头，网页显示视觉离线；断网，灌溉继续。一次现场试验观察到土壤读数随浇水从 41 升到 58，这是单次佐证，不是统计结果。**V5 长时间运行没有做**，这是项目的诚实边界。

## 9. 协作与反馈

这是个人项目，协作主要体现在三个方面：

1. **评审与指导**：推荐人傅向华老师亲见过 P4 的演示；大赛答辩这类场合最容易被问到的是“LLM 出错怎么办”和“断网会怎样”。我把这两个问题当作设计需求提前吸收，直接对应降级矩阵和“LLM 只能建议”的约束。
2. **自己与自己的冲突**：做功能的我想要"AI 自动控制"，做安全的我要求"AI 不能直接控制"。解决方式是写下优先级：**安全高于人工，人工高于自动，自动中规则高于 LLM**，并把这条优先级落成代码和测试，而不是留在口头上。
3. **工具与文档**：把协议、阈值、状态机写进文档，作为"单一事实来源"。当固件、边缘视觉、服务端三份代码的行为不一致时，以文档为准，由文档推动改代码，而不是互相猜。

> **面试要点**：被问"个人项目没有团队怎么体现协作"，答："我把自己当作三个角色：固件、视觉、服务端，通过协议文档和契约测试沟通；并且把可预见的评审问题当作需求，比如 LLM 出错怎么办，所以加了校验和降级。"

## 10. 经验教训

1. **先做最安全的部分**：本地闭环先于任何智能部分。
2. **用数字倒推超时**：从新鲜度要求倒推读超时、重试、窗口，而不是拍脑袋。
3. **分清度量对象**：模型耗时与端到端分开；均值与分位数分开。
4. **每个真实缺陷留下一个回归测试**，且输入来自当时抓到的真实数据。
5. **未知不等于默认**：启动、重启、断线时的状态是 unknown。
6. **证据分级**：sent、acked、reported、水真的到达，是四件事。
7. **约束 LLM 而不是信任 LLM**：解析、校验、白名单、降级。
8. **别声称没做过的事**：长时间测试、绝对精度、统计显著性，没有就说没有。

## 11. 十二个工程化英文问答

**Q1. Walk me through how you built this project from scratch.**
> "I started with requirements: automatic watering, offline safety, manual priority, plant-problem detection, and an AI layer that cannot directly drive the pump. I built the safest part first, the Hi3861 local loop, and tested it on the bench. Then the vision chain on the RK3588, then the protocol and server, then the decision chain and execution layer, and finally integration. At each step I used simulators or replays for the neighbours, and only swapped in real hardware one component at a time."
（译：先列需求；先做最安全的本地闭环并台架测试；再做视觉链、协议与服务端、决策与执行层，最后集成；每步先用模拟器或回放，再逐个换成真实部件。）

*L2: Why that order?* > "Because if the local loop is wrong, nothing above it matters, and because debugging is much easier when only one layer is real at a time."（译：本地闭环错了其上都无意义；一次只有一层是真实的时候最容易调试。）

**Q2. How did you choose the frequencies in your system?**
> "Each rate follows the time scale of what it observes. Soil moisture is slow, so I take a sample every 200 milliseconds, use the median of five, and run the state machine once a second. Reports go every 2 seconds, which gives five chances inside the 10-second freshness window. Vision runs at about 15 frames per second because the chain takes about 60 milliseconds, and the event gate turns that into at most one event per class every 5 seconds."
（译：每个频率跟随被观测过程的时间尺度。土壤慢：200 ms 采样、5 个取中位数、1 s 状态机；2 s 上报；视觉约 15 FPS；事件门每类最多 5 s 一个事件。）

*L2: Why not sample faster?* > "Faster sampling only adds noise for a slow process. The 200 ms sampling exists to collect five samples for the median, not for bandwidth."（译：对慢过程采更快只增加噪声；200 ms 是为了凑 5 个样本取中位数。）

**Q3. How do you budget latency?**
> "I split the chain into stages and give each a number. For vision, capture and decode is about 10 to 14 milliseconds, the NPU about 28, post-processing 3 to 5, network about 20, and the server about 3. That is roughly 110 to 150 milliseconds on the rule path. The most important chain, from a dry reading to the pump, never leaves the Hi3861 and is about one second worst case."
（译：分阶段给预算：视觉规则路径约 110–150 ms；最关键的从读数到泵的链路在 Hi3861 内，最坏约 1 s。）

*L2: Where is the real bottleneck?* > "The NPU at about 28 milliseconds, then CPU preprocessing. The server is under 3 milliseconds, so I did not optimise it."（译：瓶颈是 NPU，其次是 CPU 预处理；服务端不足 3 ms，没有优化。）

**Q4. Tell me about a performance optimisation you made.**
> "The detection boxes on the web page lagged more and more. I measured age at send over 300 frames and saw it growing. The processing took about 60 milliseconds, longer than the camera's 33, so frames queued in the driver. I changed capture to drain the queue and keep only the newest frame, counting dropped frames. The age upper bound became about 93 milliseconds and stopped drifting. I added a regression test replaying 300 frames and asserting the maximum age."
（译：框越来越滞后；测 300 帧 age 增长；原因是处理比摄像头慢导致积压；改为只取最新帧并计数；age 上限约 93 ms 不再漂移；加回放回归测试。）

*L2: Isn't dropping frames bad?* > "Not here. A plant does not change in 33 milliseconds, and a stale frame is worse than a missing one. I count drops so I can see if it gets out of hand."（译：这里不是坏事；植物 33 ms 不会变，过期帧比缺帧更糟；计数丢帧以便监控。）

**Q5. How did you decide between accuracy and speed in quantisation?**
> "I compared FP16, INT8 and a smaller model. FP16 was about 45 milliseconds per frame, INT8 about 28, and the nano model was faster but weaker on small lesions. INT8 cost about 0.03 mAP, from 0.86 to 0.83, with the biggest recall drop on disease spots, from 0.78 to 0.73. Since my task works on a time scale of seconds, I kept the INT8 small model and used three-frame confirmation to recover recall instead of using a faster, less accurate model."
（译：比较 FP16、INT8、nano；INT8 精度降 0.03，病斑 Recall 降最多；任务是秒级，因此保留 INT8 小模型，用三帧确认补偿召回。）

*L2: How did you verify INT8 did not break the model?* > "Four steps: numerical alignment against ONNX with cosine similarity, layer-by-layer analysis, task metrics on the same validation set, and a replay of real frames."（译：四步：与 ONNX 数值对齐、逐层分析、同验证集任务指标、真实帧回放。）

**Q6. How do you manage parameters across devices?**
> "Key thresholds live in one versioned configuration, and every decision record carries the config version. The device reports its own version, and a mismatch raises an alert rather than being silently overwritten. I also check invariants at load time: the fast-path dry threshold must be below the local start threshold, and the start threshold below the stop threshold."
（译：关键阈值集中在带版本配置；决策记录带版本；设备回报版本，不一致则告警；加载时检查不变量。）

*L2: What went wrong before that?* > "The server and device each had their own thresholds and disagreed on what counted as dry, which caused confusing behaviour during integration."（译：此前两侧各有阈值，对"干"的定义不同，联调时行为混乱。）

**Q7. How do you test a system with a language model in it?**
> "I make the non-deterministic part replaceable. Rules and execution checks are covered by unit and table-driven tests. The decision chain is tested by replaying recorded observations with recorded model responses, so results are repeatable. Then I inject faults: timeouts, malformed or out-of-range output, and check that the fast path and local irrigation are unaffected."
（译：让不确定部分可替换：规则与执行检查用单元和表驱动测试；决策链用记录的观测加记录的模型响应回放；再做故障注入。）

*L2: How do you know the validation layer works?* > "I feed it outputs that parse correctly but violate the whitelist or ranges, because parsing success is not semantic safety."（译：喂能解析但违反白名单或范围的输出，因为解析成功不等于语义安全。）

**Q8. Describe a hard integration bug.**
> "On the first bench test the pump started the moment the board powered up. I checked the logical state in code, measured the relay input with a multimeter, and read the module datasheet. The module is active-low and my default output was low. I separated logical state from pin level, translated it in one function, set the default high, and added a bench test for power-on defaults."
（译：首次台架上电泵即开；查代码、万用表、手册；模块低触发而默认低；分离逻辑与电平、集中翻译、默认高、加台架测试。）

*L2: What would have happened without the multimeter?* > "I would have kept staring at code that looked correct. Measuring at the boundary is what localises the fault."（译：会继续盯着看似正确的代码；在边界测量才能定位。）

**Q9. How do you reproduce a field failure?**
> "Every decision is written as a JSON line with a trace id, input snapshot summary and config version. I can replay the observation sequence through the decision chain offline. For model calls I replay the recorded responses, so the same input gives the same output."
（译：每个决策写成一行 JSON，含 trace id、输入摘要和配置版本；离线回放观测序列；模型调用回放记录的响应。）

*L2: What cannot you reproduce this way?* > "Hardware timing issues, such as Wi-Fi jitter. For those I use packet captures and bench tests."（译：硬件时序问题如 Wi-Fi 抖动；用抓包和台架。）

**Q10. How do you protect the physical system from software mistakes?**
> "Defence in depth. The server clamps and checks every request, but the device has its own hard limits: 60-second maximum pump time, cooldown, sensor-fault shutdown and a safe power-on default. The device limit is always the floor; the server limit is never looser."
（译：纵深防御：服务端钳位与检查；设备端自有硬限制：60 s 上限、冷却、传感失效关泵、安全上电默认；设备限制是底线。）

*L2: What if the server and device limits disagree?* > "The device wins. That is why the server value must never exceed the device value, and why I check it in a contract test."（译：设备为准；服务端值不得大于设备值；契约测试检查。）

**Q11. How did you handle conflicts between competing goals?**
> "I wanted both autonomy and safety, and they pulled in opposite directions. I wrote a precedence rule: safety over human, human over automation, rules over the model. Then I made it executable in the code and tests, so it was not just a slogan."
（译：自主与安全冲突；写成优先级规则：安全>人工>自动，规则>模型；并落成代码与测试。）

*L2: Give an example where the rule applied.* > "A user switched the pump off by voice while the agent wanted it on. The execution layer rejected the automatic request because of manual priority."（译：用户语音关泵而 agent 想开；执行层因人工优先拒绝。）

**Q12. What would you improve with more time?**
> "Three things. First, a long-running test: I reached the full real-hardware loop but not long-duration validation. Second, persistent command tracking and per-hop latency metrics, so I can see where time goes without a debugger. Third, MQTT for many nodes and an FP32-versus-INT8 benchmark on a larger validation set."
（译：三件事：长时间测试；命令持久化与逐跳延迟指标；多节点用 MQTT，以及更大验证集上的 FP32/INT8 基准。）

*L2: Why is the long run important?* > "Because problems like drift, memory growth, relay wear and Wi-Fi dropouts only show up over hours or days."（译：漂移、内存增长、继电器磨损、Wi-Fi 掉线只在数小时到数天才显现。）

## 本章要点速记

1. 每层频率由被观测过程的时间尺度决定，上下游成整数倍：200 ms、1 s、2 s、10 s。
2. 最关键的延迟链（读数到泵）在 Hi3861 内，最坏约 1 s，不经过网络和 LLM。
3. 视觉规则路径约 110 到 150 ms；瓶颈是 NPU 约 28 ms，服务端不足 3 ms。
4. 只取最新帧；JPEG 不进推理线程；事件门是语义去抖，也是带宽限流。
5. 网络任务永不阻塞控制任务，之间只通过深度为 1 的邮箱交换。
6. 设备端限值是底线，服务端限值不得更宽松。
7. 三个真实故障：继电器极性、letterbox 偏移、TCP 粘包，各留一个回归测试。
8. 验证到 V4，没有 V5，如实说。

## 自测题

1. 为什么土壤采样可以只有 1 Hz 的输出，而视觉要 15 FPS？
2. 把"读数低于 56 到泵开"的最坏延迟逐项列出。
3. 如果不做"只取最新帧"，帧龄会怎样变化？为什么？
4. 事件门的三个参数各自解决什么问题？
5. 为什么网络任务和控制任务之间的邮箱深度是 1？
6. 举出两个必须由设备端而不是服务端保证的安全性质。

**参考要点**：1. 过程时间尺度不同。2. 至多 1 s 出值，加小于 1 ms 判断，加约 10 ms 继电器。3. 逐帧积压直到缓冲写满。4. 连续帧去闪烁，conf 去低质量，间隔去重复与限流。5. 状态类数据只要最新值，避免积压拖慢控制。6. 上电默认关、最长开泵、传感失效关泵。
