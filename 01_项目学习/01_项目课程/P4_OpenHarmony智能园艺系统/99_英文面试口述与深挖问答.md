# 99 英文面试口述与深挖问答

> **一句话定位**：P4 的英文口述稿（30 秒 / 90 秒 / 3 分钟）与 120 个深挖问答（Q1–Q64 速答；Q65–Q120 含 L1/L2/L3 分层追问与译文；含 STAR），按"系统 → 本地控制 → 视觉 → 量化 → 通信 → 服务端 → Agent → 安全执行 → 工程"分组。

## 本章学完你能……

- 流畅说出三个长度的项目介绍，并随时切换。
- 回答 YOLO / 量化 / Agent 可靠性三大 AI 高频主题的追问。
- 遇到没有数据的问题，用诚实模板回答。

## 使用规则

1. 英文只陈述有依据的事实（CV、笔记线索）；具体数值为教材统一设计取值，与实机不一致时以实机为准并同步修改。
2. 记不清具体数字时用：*"I don't have the exact figure in front of me, but the order of magnitude was …"*（仅当你确实有量级印象），或 *"I didn't measure that, so I won't quote a number."*
3. 先结论、后细节；每个答案控制在 20–40 秒。
4. 相关章节见 [README](./README.md)；工程化问答另见 [20 工程化实践](./20_工程化实践_频率周期与问题解决.md)。

## 一、三种长度口述

### 1.1 30 秒

> "My smart gardening system, built in 2024 on OpenHarmony and an RK3588, closes the loop from vision to irrigation. An INT8 YOLOv5 model on the RK3588 turns camera frames into structured observations; a LangGraph decision chain on the server turns observations and soil data into recommendations or constrained requests; and a Hi3861 runs a local pump state machine with separate start and stop thresholds and manual priority. The key idea is that AI proposes, and only validated requests reach the device."

（译：2024 年在 OpenHarmony 和 RK3588 上做的智能园艺系统，打通视觉到灌溉。RK3588 上 INT8 YOLOv5 把帧变成结构化观测；服务端 LangGraph 把观测和土壤数据变成建议或受约束请求；Hi3861 跑本地水泵状态机（独立启停阈值、手动优先）。核心：AI 只提议，只有校验过的请求才到设备。）

### 1.2 90 秒

> "This was my personal project from May to August 2024. The system has three layers. On the Hi3861, a microcontroller, I read a soil moisture probe through the ADC, calibrate it to a moisture index, and run a pump state machine with independent start and stop thresholds, so the relay doesn't chatter. Manual commands always take priority, and the loop keeps working if the network goes down.
> On the RK3588, I built an inference chain: V4L2 capture, preprocessing, a YOLOv5 model converted to INT8 for the NPU, post-processing with thresholds and non-maximum suppression, and finally structured observations with class, confidence, box and timestamp.
> On the server, a LangGraph chain takes soil and vision events. A rule-based fast path handles extreme states without waiting for a language model; other cases go through a supervisor to care or alert nodes. Its output is a recommendation or a constrained request, which must pass whitelist, mode and freshness checks.
> I kept five kinds of information separate: sensor readings, model observations, recommendations, command requests and device feedback, because a displayed request is not proof that the pump ran."

（译略：三层结构；Hi3861 采集标定+滞回+手动优先、断网可用；RK3588 推理链；服务端 LangGraph fast path + 校验；五类信息分开。）

### 1.3 3 分钟

> "Let me walk through the problem first. A potted garden needs watering when the soil is dry, but I also wanted the system to notice plant problems, like lesions, and explain them to the user. Those two needs have very different time scales and risks, which drove the architecture.
> Watering is slow and safety-relevant, so it lives at the edge of the physical world: a Hi3861 reads the probe, applies a calibration, and runs a hysteresis state machine, starting below one threshold and stopping above a higher one, and holding its state in between. It drives an active-low relay, so I separate the logical state from the pin level. Manual mode pauses the automatic logic, so a human always wins. If Wi-Fi or the server fails, irrigation continues.
> Vision is compute-heavy, so it lives on an RK3588 with an NPU. I capture frames through V4L2 with a ring of buffers, convert and letterbox them, run an INT8 YOLOv5 model converted with the RKNN toolkit, decode and filter the outputs, map boxes back to the original image, and publish structured observations with confidence and timestamps over TCP, as a JSON segment and an optional JPEG segment with length prefixes.
> The server collects both streams into a shared, lock-protected state. A blocking thread reads TCP; an asyncio loop runs the WebSocket interface and the agent. The LangGraph chain has a rule-based fast path for extreme states and LLM nodes for interpretation, and every LLM output is parsed and validated. Nothing goes to the device directly: requests pass a whitelist, mode, range and freshness checks, manual-off priority is enforced, commands carry ids so retries are idempotent, and the device's own report is what confirms the pump state.
> What I'm most proud of is the discipline: confidence is not accuracy, deployment is not training, a recommendation is not an action, and a sent command is not a pump that ran. If I did it again I'd add persistent command tracking, MQTT for many nodes, and a proper FP32-versus-INT8 benchmark."

（译略：问题→本地控制→视觉→服务端→安全执行→反思。）

## 二、系统与动机（Q1–Q6）

**Q1. Why three layers?**
> "Each layer does what it's best at. The Hi3861 is close to the actuator and must keep working offline. The RK3588 has the NPU for vision. The server has the resources for aggregation, an LLM and the web interface, and it's allowed to be slow or occasionally down."
（译：各层做擅长的事：Hi3861 近执行器且需离线可用；RK3588 有 NPU；服务端负责汇聚、LLM、界面，可以慢或偶尔宕机。）
追问：*What fails if the server dies?* → "Only recommendations and the UI. Irrigation continues locally."

**Q2. Why not do everything on the RK3588?**
> "It could, but I wanted the irrigation loop isolated from vision failures and cheap per pot. A Hi3861 node is low-power and independent."

**Q3. What does 'autonomous' mean in your CV?**
> "Autonomous local irrigation: the pump loop runs without the network or the LLM. It does not mean the LLM freely controls hardware."

**Q4. What are the five kinds of information?**
> "Sensor readings, model observations, recommendations, command requests and device feedback. None can substitute for another; for example a detection of a lesion is not evidence of dry soil."

**Q5. Which part did you build yourself?**
> "It's a personal project, so I built the full loop. I wrote the Hi3861 irrigation logic, the vision pipeline around the model, the protocol, the server and the agent chain myself. I used the vendor SDK and drivers for the boards, the public COCO weights as the starting point for fine-tuning, and open-source libraries such as OpenCV, websockets and LangGraph."
（译：我自写灌溉逻辑、视觉流水线、协议、服务端与 Agent 链；板级 SDK/驱动、COCO 预训练权重和开源库是现成的。）

**Q6. Where does OpenHarmony come in?**
> "The Hi3861 firmware runs on the OpenHarmony lightweight system, and the project was built for the Huawei ICT Competition's OpenHarmony track, where it won a provincial first prize and a national final third prize."

## 三、本地灌溉（Q7–Q16）

**Q7. Why two thresholds?**
> "A single threshold makes the pump chatter when noise crosses it. With separate start and stop thresholds and memory in between, the relay switches rarely. In a worked example it dropped from potentially thousands of switches an hour to a few dozen."

**Q8. What is hysteresis exactly?**
> "The output depends on both the input and the previous state. Below the start threshold, on; above the stop threshold, off; in between, hold."
追问：*Is it a filter?* → "No. A filter smooths the input; hysteresis shapes the decision. I use both."

**Q9. Which threshold values?** > "The configuration was around 56 to start and 65 to stop on my calibrated scale, with strict comparisons. They're setup-specific, not universal soil values."
（译：约 56 开、65 关，严格比较；只适用于本套设置。）

**Q10. What happens exactly at 65?** > "With strict comparison, 65 is inside the band, so the state is held. It stops only when the value is greater than 65. Integer truncation also shifts the effective switch point by about one percentage point."

**Q11. How does the ADC reading become a moisture value?** > "A linear two-point calibration, dry and wet references, clipped to 0–100. It's a relative index for this probe and soil, not volumetric water content."

**Q12. What if the probe is unplugged?** > "An open circuit can look like very dry soil and keep the pump on. A robust design checks the raw ADC range, rate of change and stuck values, and fails safe by stopping the pump. In our setup there is a basic version: a raw value above 3250 or below 200, or three failed reads in a row, marks the reading invalid, so the pump is stopped and a sensor_fault is reported. A rate-of-change check is still a possible improvement."
（译：本项目做了基本版：raw>3250 或 <200、或连续 3 次读取失败判无效，关泵并上报 sensor_fault；变化率检查可作为改进。）

**Q13. Active-low relay?** > "Logic on means pin low. I keep a logical state and translate in one place, and initialise the pin high so the relay is released at power-up."

**Q14. What does manual priority mean?** > "A manual command always overrides the automatic logic; in manual mode the hysteresis logic is paused. Leaving manual mode hands control back, so if the soil is still dry the pump may restart — I'm explicit about that."

**Q15. Voice trigger?** > "It starts the pump and enters manual mode, then restores automatic mode when the trigger ends. I'd make the wait non-blocking and add a timeout."

**Q16. Other protections?** > "Maximum continuous run time, minimum off time, and a daily limit, independent of any sensor. In our setup the pump is forced off after 60 seconds and then cools down for 120 seconds; a daily limit is something I'd add."
（译：本项目最长开泵 60 s 后强制关并冷却 120 s；每日上限属于可增加项。）

## 四、边缘视觉（Q17–Q27）

**Q17. Walk me through the vision pipeline.** > "V4L2 capture, colour conversion, letterbox resize, normalisation, RKNN inference, decoding, confidence threshold, per-class NMS, mapping boxes back to the original image, then a structured event."

**Q18. Explain V4L2 buffering.** > "I request a few memory-mapped buffers and queue them all. The driver fills them; I dequeue a filled one, process it, and queue it back. After queueing, the buffer belongs to the driver again, so I must finish decoding or copying first."

**Q19. What if processing is slower than the camera?** > "The driver runs out of free buffers and drops frames, and frames wait in the queue so latency grows. With four buffers at 30 fps and 50 ms processing, throughput is 20 fps and frame age approaches about 150 ms. I'd take the newest frame to keep freshness."

**Q20. Why MJPEG vs YUYV?** > "Uncompressed 720p30 YUYV is about 442 Mbit/s, too much for USB 2. MJPEG is compressed, at the cost of a decode step."

**Q21. What is letterboxing?** > "Resize preserving aspect ratio and pad to a square. For 1280×720 to 640, scale 0.5, top padding 140. Inverse: subtract padding, divide by scale."

**Q22. What does YOLOv5 output?** > "Three scales, strides 8, 16, 32, three anchors per cell, 25,200 candidates at 640 input. Each has box offsets, objectness and class scores."

**Q23. How do you decode a box?** > "Sigmoid; centre = (2σ(t) − 0.5 + grid) × stride; size = (2σ(t))² × anchor. Score = objectness × class probability."

**Q24. What is NMS?** > "Sort by score, keep the best, remove boxes with IoU above a threshold with it, repeat, per class. Too high a threshold leaves duplicates; too low deletes neighbouring objects."

**Q25. Is confidence accuracy?** > "No. It's a score for one detection and may not be calibrated. Precision, recall and mAP come from labelled evaluation. A 0.9 detection from an old frame still shouldn't drive an action."

**Q26. Does an empty detection mean healthy?** > "No: occlusion, blur, lighting or a miss. I treat it as 'no observation' and use a frame-valid heartbeat to tell it from a broken camera."

**Q27. What are your mAP and FPS?** > "On our own validation set, mAP at 0.5 is 0.86 in FP32 and 0.83 in INT8. The NPU takes about 28 milliseconds per frame, and the whole chain runs at roughly 15 FPS, about 60 milliseconds end to end, with a p95 around 75. I measured it with timers around each stage over 300 consecutive frames. I keep model time and end-to-end latency separate."
（译：自有验证集 mAP@0.5 FP32 0.86、INT8 0.83；NPU 约 28 ms，整链约 15 FPS、端到端约 60 ms、p95 约 75 ms，分阶段打点连续 300 帧；模型耗时与端到端分开说。）

## 五、量化与 RKNN（Q28–Q36）

**Q28. Explain INT8 quantisation.** > "q = clip(round(x/s) + z); x ≈ s(q − z). Smaller model, integer NPU ops. Error is at most s/2 when nothing saturates."

**Q29. Saturation?** > "Values outside the range are clipped, and the error can be large: with s = 0.1, x = 20 becomes 12.7, an error of 7.3."

**Q30. Symmetric vs asymmetric?** > "Symmetric has zero point 0, good for weights. Asymmetric uses a zero point to cover skewed ranges like ReLU outputs, halving the step in the 0–6 example."

**Q31. Per-channel?** > "Each output channel gets its own scale; in my example a weight of 0.1 had 5.5% error per-tensor and 1.6% per-channel. Usually weights per-channel, activations per-layer."

**Q32. Calibration set?** > "Representative unlabelled images that define activation ranges, preprocessed exactly as at inference. A mismatched set or one outlier can make steps ten times coarser. Ours had 200 images: 150 randomly drawn from the training set and 50 taken on site under supplementary light and at night."
（译：本项目 200 张：训练集随机 150 + 现场补光/夜间 50。）

**Q33. How does integer inference work?** > "Multiply int8 values, accumulate in int32, then requantise with M = s_x s_w / s_y implemented as a fixed-point multiply and shift."

**Q34. Why are detection heads sensitive?** > "Box coordinates reach hundreds while scores are 0–1; sharing a scale (~2.5) turns scores into 0 or 1. So heads are kept separate, with decoding on the CPU, or mixed precision is used."

**Q35. Conversion flow?** > "Export ONNX; RKNN-Toolkit2 on a PC: config for rk3588 with mean 0 and std 255, load ONNX, build with quantisation and a calibration list, export .rknn; run it with the runtime on the board."

**Q36. Did you train the model?** > "Yes, I fine-tuned it. About 1,800 leaf images of potted plants, labelled with LabelImg, split 8 to 2, fine-tuned from public COCO weights for 100 epochs on a PC GPU, three classes: normal, wilting and disease spot. The board only runs the converted INT8 model, and conversion by itself doesn't prove accuracy, so I quote mAP from the validation set."
（译：是，我微调了：约 1800 张叶片图、LabelImg 标注、8:2、COCO 权重微调 100 epoch、PC GPU、三类；板端只跑转换后的 INT8，精度要靠验证集 mAP 说明。）

## 六、通信与服务端（Q37–Q46）

**Q37. Why length prefix?** > "TCP is a byte stream with no message boundaries. A prefix lets the receiver read exactly N bytes, and a max-length check protects against corrupted headers."

**Q38. Half and sticky packets?** > "One message may arrive over several receives, or several in one. A stateful parser handles both: read the header, then read exactly that many bytes, looping."

**Q39. Why separate JSON and JPEG?** > "The JSON is small and decision-critical; the image is large and optional. Separate segments, paired by event id, avoid base64's one-third overhead."

**Q40. Endianness?** > "The protocol fixes network order; reading 100 as little-endian would give about 1.6 billion — that's why the max-length guard exists."

**Q41. Offline detection?** > "Periodic reports as heartbeats, read timeouts, staleness marking, reconnect with exponential backoff."

**Q42. Why asyncio for WebSocket?** > "Many mostly idle connections are cheap as coroutines on one thread, with no locks for shared client lists."

**Q43. Calling the loop from another thread?** > "`run_coroutine_threadsafe` or `call_soon_threadsafe`, because the loop isn't thread-safe; arguments are bound when the coroutine is created."

**Q44. What if a handler blocks?** > "The whole loop freezes: broadcasts, heartbeats, the agent. Use async clients or an executor."

**Q45. Why a lock in the DataStore?** > "The TCP thread is a different thread. Short critical sections, whole-message updates to avoid torn reads, no I/O under the lock."

**Q46. Queue overflow?** > "At 5 events/s in and 0.5/s out, a 100-slot queue fills in about 22 s. I count drops, coalesce per location, rate-limit, and keep the fast path on its own channel."

## 七、Agent 与 LLM 可靠性（Q47–Q56）

**Q47. What is LangGraph and what did you build?** > "A graph over shared state with conditional edges. Six nodes: sensing with the fast path, supervisor, care, alert, execution and skip. It's a hand-designed workflow, not a trained network."

**Q48. Fast path vs skip?** > "Fast path: a clear, extreme condition, go straight to execution checks. Skip: nothing to do, produce nothing."

**Q49. Why not let the LLM decide watering?** > "It's simple, safety-relevant and already handled locally; an LLM adds latency and variability."

**Q50. How do you validate LLM output?** > "Parse into a fixed schema with enumerated actions, length limits; on failure retry once, then fall back to a template and count the failure."

**Q51. Hallucinated action?** > "It isn't in the enumeration or whitelist, so it's rejected. The model has no authority."

**Q52. Prompt injection?** > "Output is only a proposal; untrusted text is kept in a data section; permissions and command names aren't chosen by the model."

**Q53. Is the agent deterministic?** > "The control flow and checks are deterministic and unit-tested; the LLM text is probabilistic and evaluated on a labelled set with a mocked model for flow tests."

**Q54. Memory and RAG?** > "State has working and recent-history fields, and retrieval can add reference text. In our setup the recent-history part is enabled: the last five event summaries go in as short-term context. Long-term memory and vector RAG are not implemented; there is only a keyword fallback over about 20 care notes, top three. Retrieved text never bypasses execution checks."

**Q55. How do you evaluate an LLM agent?** > "Safety invariants by property tests; advice quality by a small labelled set and human review; online metrics such as rejection rate, timeouts and validation failures."

**Q56. LLM down?** > "Fast path and local irrigation are unaffected; care and alert degrade to templates."

## 八、安全执行与工程（Q57–Q64）

**Q57. How does an AI decision become a physical action safely?** > "Proposal, then policy check — whitelist, mode, freshness, range, manual priority — then the device's own rules, then device-reported state. Four different things: recommendation, request, acknowledgement, reported state."

**Q58. User turns pump off while the agent wants on?** > "The user wins; the execution layer rejects automatic on-requests during manual-off and the device pauses automatic logic. Off is always allowed; on must pass every check."

**Q59. Idempotency?** > "Commands carry ids and express a target state with an end time; the device remembers recent ids. 'Water 20 more seconds' resent would become 40."

**Q60. Is your 60-second dedup exactly-once?** > "No. It prevents re-analysis within a window; it's in memory, marked before execution, and doesn't control the device. I rely on at-least-once plus idempotency."

**Q61. How do you know the pump ran?** > "Levels: sent, acknowledged, device-reported, then a moisture rise or flow reading. I claim up to the device-reported state: in a field trial the pump state reported by the device matched what was requested, and the soil reading rose from 41 to 58 during watering. That is one trial, not statistics. We reached V4, the full real-hardware loop, and did not run long-duration tests."
（译：最高声称到设备上报状态一致；一次现场试验土壤读数 41→58，仅单次佐证；到 V4，未做长时间测试。）

**Q62. Clocks across devices?** > "Not assumed synchronised. Server receive time, device age-at-send, reject negative or large ages."

**Q63. Hardest bug (STAR).** > "S: On the first bench test the pump came on the moment the Hi3861 powered up, and the logic seemed reversed. T: find where in the chain the polarity was lost. A: I checked each boundary: the logical state in the code, the pin level with a multimeter, and the relay module's input behaviour. The module is active-low and my default output was low. I separated the logical state from the pin level, translated it in one place, and made the default output high. R: the pump stays off at power-up and in sensor-fault states, and there is a bench test for pin polarity and power-on defaults."
（译：S：首次台架测试上电泵即开。T：找出极性在哪一环丢失。A：逐边界检查，逻辑状态、万用表测引脚、继电器低触发；把逻辑与电平分离并在一处翻译，默认输出高。R：上电与传感失效时泵保持关，并有极性与上电默认测试。）参考素材见 [13 故障与测试](./13_故障与测试.md)。

**Q64. What would you improve?** > "Persist command tracking, one versioned config, MQTT for many nodes, per-hop latency metrics, long-duration tests, and an FP32-versus-INT8 benchmark."

### 完整 STAR 故事（取值表中的 3 个故障，与 [13 故障与测试](./13_故障与测试.md) 的故障表一致）

**故事 1：继电器极性（见 Q63）**

> "S: During the first bench test, the pump started at power-up. T: find where the polarity got lost, because a pump that runs at boot could flood a pot. A: I checked the logical state in the code, then measured the pin with a multimeter, then read the relay module's input spec: optocoupler-isolated and active-low. My default output was low. I separated the logical state from the pin level, translated it in one function, and set the default output high. R: the pump no longer starts at power-up, and a bench test covers pin polarity and power-on defaults."

（译：S：首次台架测试上电泵即开。T：找出极性丢失处。A：逐级检查，模块低触发而默认输出为低；逻辑与电平分离、集中翻译、默认高。R：上电不再开泵，并有台架测试。）

**故事 2：letterbox 框整体偏移**

> "S: On the web page, every detection box sat about 280 pixels too low in the original 1280 by 720 image. T: find whether the model or the geometry was wrong. A: I saved the raw frame, drew the box, and did a hand calculation: with scale 0.5 and a top padding of 140, a model-space y of 200 should map back to (200 − 140) / 0.5 = 120, but my code gave 400, so the padding was not subtracted. I made preprocessing and decoding share one function returning (r, pad), and added a round-trip unit test. R: boxes align with the objects, and the test fails if the geometry drifts."

（译：S：网页上框整体偏下。T：判断是模型还是几何错。A：手算 (200−140)/0.5=120，而代码给出 400，说明未减 pad；预处理与还原共用 (r, pad) 并加往返测试。R：框对齐，几何漂移会被测试捕获。）

**故事 3：TCP 粘包与半包**

> "S: The server occasionally failed to parse the Hi3861's JSON, once every few minutes. T: find out whether the device or the parser was at fault. A: I captured the bytes and saw that one message sometimes arrived in two reads, and sometimes two messages in one. My code had treated one receive as one message. I added a stateful parser: a length prefix for the binary stream from the RK3588, and bracket matching that is aware of braces inside strings for the compact JSON from the Hi3861. I also wrote a test that feeds the same bytes in random chunk sizes. R: the parse failures disappeared, and the chunk test guards against regressions."

（译：S：服务端偶发解析失败。T：判断设备还是解析器。A：抓包发现一条消息分两次到或两条合一；改为有状态解析：RK 流用长度前缀，Hi3861 流用括号配对（字符串内括号感知），并加随机切块测试。R：解析失败消失，切块测试防回归。）

## 十、分层深挖问答（L1 / L2 / L3，共 56 问）

> 格式：**L1** 是 20 到 30 秒的直接回答；**L2** 是面试官最常见的追问；**L3** 是对技术细节的深挖。每问附中文译文。数值均为教材统一设计取值（见 [README 自查表](./README.md)），实机不同以实机为准。涉及外部软硬件规格的说法，如可能与官方资料有出入，已在译文中标"外部事实未核对"。

### 10.1 YOLO 与边缘视觉（Q65 到 Q76）

**Q65. Walk me through what a YOLOv5 model outputs and how you decode it.**
- **L1:** "For a 640 by 640 input there are three detection heads with strides 8, 16 and 32. Each grid cell has three anchors, and each candidate holds four box values, an objectness score and one score per class. With three classes that is 8 numbers per candidate and 25,200 candidates in total."
- **L2 (How many, exactly?):** "3 × (80² + 40² + 20²) = 25,200. I keep the three head outputs separate and decode them on the CPU."
- **L3 (What does decoding do?):** "Apply sigmoid where the exported model hasn't, add the grid offset, scale by stride, and multiply width and height by the anchors. Then score = objectness × class score, filter at 0.25, run per-class NMS, and map the boxes back to the original image."
- 译：三个头步长 8/16/32，每格 3 锚框，每个候选 4 个框值 + obj + 各类分数，共 25200 个候选；三头分开、CPU 解码；L3：sigmoid、网格偏移、步长缩放、锚框、score=obj×cls、0.25 过滤、按类别 NMS、还原原图。

**Q66. Why filter before NMS?**
- **L1:** "NMS compares boxes pairwise, so running it on 25,200 candidates is wasteful. Most have a tiny score, so I drop them first and NMS only sees a few dozen."
- **L2 (What is the cost otherwise?):** "Roughly quadratic in the number of boxes. In my chain the post-processing is stable at about 3 to 5 milliseconds with filtering."
- **L3 (Could filtering hurt?):** "Yes, if the threshold is too high it removes real but weak detections, which cuts recall. That is why I keep the first threshold low at 0.25 and put the stricter 0.5 in the event gate, where I can use time."
- 译：先过滤再 NMS，避免平方级开销；后处理稳定 3–5 ms；L3：阈值过高会降召回，所以第一道取 0.25，严格的 0.5 放在能用时间维度的事件门。

**Q67. Why per-class NMS?**
- **L1:** "A leaf can be wilting and have a spot at the same time. Class-agnostic NMS could suppress one of them because the boxes overlap."
- **L2 (Show me a case):** "A wilting box of 100 by 100 and a spot box of 55 by 50 inside it have an IoU of 0.275, so both survive at 0.45 even without classes. But a larger spot box would exceed 0.45 and be deleted wrongly."
- **L3 (Downside of per-class?):** "The same region can get two labels, which downstream logic must handle. The event gate works per class, so it simply produces two events if both persist."
- 译：叶子可同时萎蔫又有病斑；不分类 NMS 可能误删；例：IoU 0.275 的例子；L3：同一区域可能有两个标签，事件门按类别分别处理。

**Q68. Is confidence the probability that the detection is correct?**
- **L1:** "No. It is objectness times a class score; it reflects the model's relative certainty but it is not calibrated."
- **L2 (How would you check it?):** "Plot precision against confidence threshold on the validation set, or draw a reliability diagram. If 0.8 doesn't give about 80% precision, it isn't calibrated."
- **L3 (What did you do about it?):** "I didn't calibrate it. I used a multi-frame gate instead: three consecutive frames at 0.5 or more. It averages out single-frame noise without needing calibrated probabilities."
- 译：不是；是 obj×类别分数，未校准；L2：画 precision-阈值曲线或可靠性图；L3：没做校准，用三帧事件门平均单帧噪声。

**Q69. Letterbox or direct resize?**
- **L1:** "Letterbox. I scale by the smaller ratio, keeping the aspect ratio, and pad with grey 114. It matches training and avoids distorting leaf shapes."
- **L2 (Show the math):** "1280 by 720 to 640 by 640: ratio 0.5, resized to 640 by 360, 140 pixels of padding top and bottom. A model-space y of 200 maps back to (200 − 140) / 0.5 = 120."
- **L3 (What went wrong once?):** "I forgot to subtract the padding, so boxes sat 280 pixels too low. I fixed it by sharing one function that returns the ratio and padding for both preprocessing and decoding, with a round-trip test."
- 译：用 letterbox（比例 0.5、灰边 140、114 填充）；手算还原 y=120；L3：曾漏减 pad 导致偏下 280 像素，现共用函数 + 往返测试。

**Q70. Why is the disease-spot class the hardest?**
- **L1:** "Spots are small, so their features are fine and easy to miss. In FP32 its recall is 0.78, against 0.93 for normal."
- **L2 (How does quantisation change this?):** "It drops further to 0.73 in INT8, the biggest drop of the three classes, because small, low-amplitude features are more affected by 8-bit steps."
- **L3 (What would you do?):** "More small-object samples, more spot images in the calibration set, a higher input resolution, or mixed precision on sensitive layers. I would not simply lower the threshold, because that increases false alarms."
- 译：病斑小、特征细，FP32 召回 0.78；INT8 降到 0.73；L3：增加小目标样本、校准集病斑图、提高分辨率、混合精度，而不是单纯降阈值。

**Q71. Explain mAP@0.5.**
- **L1:** "For each class I rank detections by confidence, compute precision and recall down the list, take the area under the precision-recall curve, which is AP, and average over classes. A detection counts as correct if its IoU with a ground-truth box is at least 0.5."
- **L2 (Your numbers?):** "0.86 in FP32 and 0.83 in INT8 on my own validation set of about 360 images, the 20% split of roughly 1,800."
- **L3 (Limits of that number?):** "The validation set is small and from the same environment as training, so it is optimistic for new gardens. Frames of the same plant are also similar, so a split by plant or session would be more honest."
- 译：按置信度排序算 P-R 曲线下面积再按类平均；FP32 0.86、INT8 0.83，验证集约 360 张；L3：验证集小且同环境，偏乐观，按植株或会话划分更严谨。

**Q72. How did you choose the thresholds 0.25, 0.45 and 0.5?**
- **L1:** "0.25 for candidate scores and 0.45 for NMS are the usual defaults for this model family. 0.5 with three consecutive frames and a 5-second gap is my event gate, chosen for stability."
- **L2 (How would you tune them?):** "Sweep them on the validation set, plot precision-recall for each class, and choose per-class operating points according to the cost of a miss versus a false alarm."
- **L3 (What is the cost asymmetry here?):** "A missed lesion only delays advice, because the plant changes slowly, while false alarms annoy the user and waste language-model calls. So I lean towards recall at the candidate stage and precision at the event stage."
- 译：0.25/0.45 为常用默认；0.5+三帧+5 s 为事件门；L2：在验证集扫描阈值画 P-R；L3：漏检只是延迟建议，误报打扰用户并浪费调用，所以候选阶段偏召回、事件阶段偏精度。

**Q73. What happens at night or in poor light?**
- **L1:** "Confidence drops and noise rises. I added supplementary light and put 50 night and supplemental-light images into the calibration set."
- **L2 (Did it fully fix it?):** "It improved, but I did not run a systematic lighting study. I'd group the validation set by lighting and report recall for each group."
- **L3 (What about auto exposure?):** "Auto exposure can make brightness oscillate and the confidence flicker. I'd lock exposure and white balance, and the three-frame gate absorbs what remains."
- 译：夜间置信度下降、噪声大；加补光，校准集含 50 张夜间/补光图；没做系统光照研究；L3：自动曝光会让亮度振荡，应锁定曝光与白平衡，三帧门吸收剩余波动。

**Q74. Could your train and validation sets leak?**
- **L1:** "Possibly. I split about 1,800 images 8 to 2, and photos of the same plant at similar times look alike."
- **L2 (Effect?):** "The validation mAP would be optimistic."
- **L3 (Fix?):** "Split by plant or by session, and keep a final test set from a different day and location, touched only once at the end."
- 译：可能；随机 8:2，同一植株相似图会泄漏；验证 mAP 偏乐观；改为按植株或会话划分，并留一份不同日期地点的最终测试集。

**Q75. Why YOLOv5 and not a newer model?**
- **L1:** "At the time I built it, YOLOv5 had a well-trodden path to ONNX and the RKNN toolkit, and a simple output format with separate heads that suits INT8. The system's value is the loop, not the newest detector."
- **L2 (Would you switch?):** "I would evaluate a newer model on the same validation set and the same board, comparing mAP, latency and quantisation behaviour before switching."
- **L3 (What would break if you did?):** "The output layout changes, for example a single tensor with a different channel layout, so decoding, the calibration check and the tests would all need updating."
- 译：当时 YOLOv5 到 ONNX/RKNN 的路径成熟（外部事实未核对），输出格式简单；价值在闭环；换模型需在同验证集和同板比较；输出布局变化会影响解码和测试。

**Q76. Why use a multi-frame event gate?**
- **L1:** "A single frame is noisy. Requiring three consecutive frames at confidence 0.5 or more removes flicker, and the 5-second gap limits repeated events."
- **L2 (Cost?):** "About 0.3 seconds of extra delay, which is negligible against minutes-scale plant changes."
- **L3 (Failure mode?):** "A real object that flickers below 0.5 on alternate frames will never trigger, so I log near-misses to see whether the threshold is too strict."
- 译：单帧有噪声，三帧连续 ≥0.5 去闪烁，5 s 间隔限制重复；代价约 0.3 s；L3：交替低于 0.5 的真实目标永远触发不了，需要记录近失事件检查阈值。

### 10.2 INT8 量化与 RKNN（Q77 到 Q88）

**Q77. Explain INT8 quantisation in one minute.**
- **L1:** "A real value x is mapped to an integer q = clip(round(x / s) + z), and recovered as x ≈ s (q − z). It makes the model smaller and lets the NPU use integer arithmetic."
- **L2 (Error?):** "Without saturation, the error is at most half a step, s/2."
- **L3 (With saturation?):** "Values outside the representable range are clipped, so the error can be large. For s = 0.1 and x = 20, the integer range tops out near 12.7, giving an error of 7.3."
- 译：q=clip(round(x/s)+z)，x≈s(q−z)；无饱和误差 ≤ s/2；有饱和时可很大，例：s=0.1、x=20 被截到约 12.7，误差 7.3。

**Q78. Why is INT8 faster on the NPU?**
- **L1:** "Integer multiply-accumulate units are smaller and more numerous than floating-point ones, and 8-bit data needs a quarter of the memory bandwidth of FP32."
- **L2 (Your numbers?):** "About 28 milliseconds per frame in INT8, and I estimated about 45 for FP16. The model file is about 8 MB."
- **L3 (Is it always faster?):** "Not for layers the NPU doesn't support in INT8; those fall back to the CPU, and the data conversion can cost more than it saves. That is another reason I keep decoding on the CPU in float."
- 译：整数乘加单元小而多，带宽小；INT8 约 28 ms，FP16 估约 45 ms；L3：NPU 不支持的层回落 CPU，转换开销可能抵消收益，所以解码留在 CPU 用浮点。

**Q79. What is a calibration set for?**
- **L1:** "To estimate the activation range of each layer, from which scale and zero point are computed. It needs no labels."
- **L2 (Yours?):** "200 images: 150 random from the training set and 50 from the site under supplementary light and at night."
- **L3 (A pitfall?):** "Preprocessing must match inference exactly. A single outlier image can stretch a range tenfold and make the steps ten times coarser for everything else."
- 译：用来估计各层激活范围；不需标注；本项目 200 张（150+50）；L3：预处理必须与推理一致，一张离群图会让步长粗十倍。

**Q80. Per-tensor versus per-channel.**
- **L1:** "Per-tensor uses one scale for the whole weight tensor; per-channel gives each output channel its own scale. Per-channel is more accurate because channels differ in range."
- **L2 (Example?):** "In my worked example a weight of 0.1 had a 5.5% error per-tensor and 1.6% per-channel."
- **L3 (Why not activations?):** "Per-channel activation scales would complicate the integer pipeline, since channels are mixed in the next layer's accumulation. Weights per-channel, activations per-layer is the usual compromise."
- 译：逐通道精度更高；例：0.1 的误差 5.5%→1.6%；L3：激活逐通道会使下一层累加复杂，所以权重逐通道、激活逐层。

**Q81. Why are YOLO heads sensitive to quantisation?**
- **L1:** "Box coordinates reach hundreds while scores sit between 0 and 1. If they share one scale of about 2.5, scores collapse to 0 or 1."
- **L2 (What did you do?):** "Kept the three heads as separate outputs and decoded on the CPU, with no mixed precision."
- **L3 (Alternative?):** "Keep the last convolution layers in higher precision (mixed quantisation), or split box and score outputs into separate tensors with their own scales."
- 译：框坐标到数百而分数 0–1，共用 scale 会使分数塌缩；本项目三头分开 + CPU 解码；替代：混合量化或框与分数分张量。

**Q82. How do you check that the quantised model is correct?**
- **L1:** "I run the same images through ONNX and RKNN and compare outputs with cosine similarity and maximum absolute error."
- **L2 (Threshold?):** "Above about 0.98 on each head I consider it healthy; below that I use per-layer analysis to find the layer that breaks."
- **L3 (Why both metrics?):** "Cosine similarity ignores overall scale, so a wrong scale by a constant factor could pass. Maximum absolute error catches that."
- 译：同图跑 ONNX 与 RKNN 比较余弦相似度和最大绝对误差；各头高于约 0.98 为健康；余弦对整体尺度不敏感，需配合最大绝对误差。

**Q83. Post-training quantisation versus quantisation-aware training.**
- **L1:** "I used post-training quantisation: no retraining, just a calibration set. QAT simulates quantisation during training and recovers more accuracy but costs more."
- **L2 (When would you move to QAT?):** "If PTQ loses too much on a key class and mixed precision is not enough."
- **L3 (Your loss?):** "0.03 mAP overall and 0.05 recall on spots, which my task tolerates."
- 译：用 PTQ，无需重训；QAT 训练中模拟量化、精度更好但成本高；PTQ 掉太多且混合精度不够时转 QAT；本项目 mAP 降 0.03、病斑召回降 0.05，可接受。

**Q84. What is mixed-precision quantisation?**
- **L1:** "Keep sensitive layers in FP16 and quantise the rest to INT8."
- **L2 (Did you use it?):** "No. The loss was acceptable."
- **L3 (How do you find sensitive layers?):** "Use the per-layer cosine similarity from the toolkit's accuracy analysis and promote the layers where it drops."
- 译：敏感层保持 FP16，其余 INT8；本项目没用；用逐层余弦分析找敏感层并提升其精度。

**Q85. Walk me through the conversion pipeline.**
- **L1:** "Train in PyTorch, export ONNX, convert with RKNN-Toolkit2 on a PC: set the target platform, mean 0 and std 255, load the ONNX, build with quantisation and the calibration list, export the .rknn file. Then run it with the runtime library on the board."
- **L2 (Versions?):** "Toolkit and runtime library are both 1.6.0, with asymmetric 8-bit quantisation, the 'normal' algorithm and optimisation level 3."
- **L3 (Why does version matching matter?):** "The runtime interprets the file format and operators of the toolkit that produced it. A mismatch can give wrong results or load errors, so I record versions with each conversion."
- 译：PyTorch→ONNX→PC 上 Toolkit2 转换→板端运行库；版本均 1.6.0；运行库需匹配生成它的工具包，不匹配会出错，所以记录版本。

**Q86. Does conversion prove accuracy?**
- **L1:** "No. A conversion script shows that deployment works, not that the model is accurate. Accuracy comes from training and validation metrics."
- **L2 (What do you claim?):** "I fine-tuned the model myself and quote mAP from my validation set."
- **L3 (Training details?):** "About 1,800 leaf images labelled in LabelImg, an 8 to 2 split, fine-tuned from COCO weights for 100 epochs on a PC GPU, three classes."
- 译：转换只证明可部署；精度来自训练与验证；我自己微调并引用验证集 mAP；约 1800 张、LabelImg、8:2、COCO 权重微调 100 epoch、三类。

**Q87. Why mean 0 and std 255?**
- **L1:** "The model was trained on pixels scaled to 0–1, so the toolkit divides the uint8 input by 255 internally and I can feed raw bytes."
- **L2 (What if mismatched?):** "Inputs would be off by a constant factor and every score would be wrong, so this must match training."
- **L3 (Channel order?):** "I convert BGR to RGB before sending, because the camera library gives BGR and the model was trained on RGB."
- 译：训练时像素归一到 0–1，工具包内部除以 255，板端直接送 uint8；不匹配则所有分数错；摄像头给 BGR，需转 RGB。

**Q88. What would you benchmark if you had more time?**
- **L1:** "FP32, FP16 and INT8 on the same board and the same validation set, reporting mAP, per-class recall, latency and memory."
- **L2 (Why?):** "My FP16 time is an estimate, so a real comparison would make the trade-off argument stronger."
- **L3 (Add what?):** "Percentile latency under load, because the event gate and JPEG encoding change timing."
- 译：同板同验证集对比 FP32/FP16/INT8 的 mAP、召回、延迟、内存；FP16 时间是估算；再加负载下分位延迟。

### 10.3 Agent 与 LLM 可靠性（Q89 到 Q100）

**Q89. What is your agent, in one sentence?**
- **L1:** "A LangGraph workflow: a shared state flows through six nodes, some deterministic rules and some language-model calls, and its output is a recommendation or a constrained request, never a direct device command."
- **L2 (Which nodes?):** "Sensing, supervisor, care, alert, execution and skip. Sensing, skip and execution don't call the model."
- **L3 (Who decides control flow?):** "The graph does, via conditional edges based on state. The model fills in content but doesn't choose the path."
- 译：LangGraph 工作流，共享状态流经六个节点，规则与 LLM 混合，输出建议或受约束请求；节点为 sensing、supervisor、care、alert、execution、skip；控制流由图决定。

**Q90. Why have a rule-based fast path?**
- **L1:** "For extreme states, the answer is obvious and urgent, and a language model adds latency and randomness. Soil moisture below 20 with fresh data in auto mode requests the pump for at most 60 seconds."
- **L2 (Other branches?):** "Above 85 it raises an alert and doesn't water; with stale or invalid sensor data it alerts and skips."
- **L3 (Is the fast path the safety mechanism?):** "No. The device's local state machine is the safety layer. The fast path is an optimisation on the agent side, and its requests still go through the execution checks."
- 译：极端状态结论明确且紧迫，LLM 增加延迟与随机性；湿度<20 且新鲜且 auto 请求开泵最长 60 s；>85 告警；数据失效告警并跳过；安全层是设备本地状态机。

**Q91. How do you validate language-model output?**
- **L1:** "Ask for JSON with a schema, parse it, then check types, enums, ranges and cross-field consistency. If anything fails, discard the output and fall back."
- **L2 (Example of 'parses but is wrong'?):** "An action name not in the whitelist, a negative duration, or a duration of 600 seconds."
- **L3 (Then?):** "Even valid output only becomes a request; the execution layer checks the whitelist, mode, freshness, range and manual priority again. Parsing success is not semantic safety."
- 译：要求 JSON schema，解析并检查类型、枚举、范围和一致性，失败则丢弃降级；例：不在名单、负数、600 s；合法输出也只是请求，执行层再检查。

**Q92. What if the model hallucinates a tool or action?**
- **L1:** "The whitelist rejects it. The model can only choose from a fixed set, and anything else is logged and dropped."
- **L2 (And a plausible but wrong action?):** "That is harder. Constraints on parameters, mode and freshness limit the damage, and the device's own limits are a last line."
- **L3 (Metrics?):** "I track validation failure rate and rejection reasons. A rising rate means the prompt or model needs attention."
- 译：白名单拒绝；看似合理但错误的动作靠参数、模式、新鲜度约束和设备限值兜底；监控校验失败率与拒绝原因。

**Q93. Could a plant label or user text inject instructions?**
- **L1:** "In principle, any free text that goes into the prompt could. My model inputs are mostly structured fields, such as class names and numbers, and the user's chat is treated as untrusted."
- **L2 (Defence?):** "Output is validated and the model has no direct tools. Even a successfully manipulated model can only produce a request that must pass the checks."
- **L3 (Remaining risk?):** "It could produce misleading advice text. That's why advice and commands are separate and advice does not control the pump."
- 译：自由文本可能注入；我的输入多为结构化字段，用户聊天视为不可信；输出被校验且无直接工具；剩余风险是误导性建议文本，所以建议不控制泵。

**Q94. How do you handle non-determinism?**
- **L1:** "Low temperature, 0.2, and a strict schema. More importantly, the safety-relevant logic doesn't depend on the model."
- **L2 (Testing?):** "I replay recorded observations with recorded model responses, so tests are repeatable."
- **L3 (And live?):** "Log the full prompt, the response and the decision, so I can examine any run afterwards."
- 译：低温 0.2 与严格 schema；安全逻辑不依赖模型；测试回放记录的观测与响应；线上记录完整提示、响应、决策。

**Q95. Did you implement memory or RAG?**
- **L1:** "Only short-term memory: the state holds the last five event summaries as context. Long-term vector memory is not implemented."
- **L2 (And RAG?):** "A keyword fallback over about 20 short plant-care texts, top three results. Not a vector store."
- **L3 (Would you add a vector store?):** "Only after measuring that keyword retrieval fails on real questions. Otherwise it's extra complexity."
- 译：仅短期记忆（最近 5 条事件摘要）；长期向量记忆未实现；关键词降级检索约 20 条护理文本取 top-3；是否上向量库要先测关键词失败再说。

**Q96. What happens when the LLM times out?**
- **L1:** "A 10-second timeout, then a template recommendation. The fast path and local irrigation are unaffected."
- **L2 (Concurrency?):** "One call at a time, through a semaphore, so two decisions don't contradict each other."
- **L3 (Retry?):** "No automatic retry inside the same event, to avoid piling up; the next event triggers a new analysis."
- 译：超时 10 s 后给模板建议，fast path 与灌溉不受影响；并发 1；同一事件内不自动重试，下一事件重新分析。

**Q97. How do you evaluate an agent like this?**
- **L1:** "Separate the layers: rules by unit tests, schema validation by fault injection, advice quality by a small human-rated set, and the system by end-to-end traces."
- **L2 (Metrics?):** "Validation failure rate, fallback rate, rejection reasons, and the conversion of requests into confirmed device state."
- **L3 (Honest limit?):** "I haven't built a large rated benchmark, so I don't make quantitative claims about advice quality."
- 译：分层评估：规则单测、校验故障注入、建议质量小规模人评、端到端追踪；指标含校验失败率、降级率、拒绝原因、请求到设备确认的转化；没有大规模基准，不对建议质量作量化声称。

**Q98. What permissions does the agent have?**
- **L1:** "None over hardware. It can read the shared state and produce a recommendation or a request."
- **L2 (Who can turn the pump on?):** "The execution layer, after checks, and the device after its own checks. A human can always turn it off."
- **L3 (Asymmetry?):** "Moving towards the safe state, off, needs few conditions; moving towards a state with consequences needs all of them."
- 译：对硬件无权限，只能读状态、产生建议或请求；开泵由执行层校验后再由设备自检；人总能关；走向安全状态条件少，走向有后果状态要全部通过。

**Q99. Latency and cost of the LLM path?**
- **L1:** "One to three seconds a call, timeout 10. It's off the control path, so it affects only how soon advice appears."
- **L2 (Limits on calls?):** "Events are limited to one per class every 5 seconds, de-duplicated within about 60 seconds, with concurrency one."
- **L3 (Is dedup exactly-once?):** "No. It prevents repeated analysis within a window; it lives in memory, is marked before analysis, and doesn't affect the device."
- 译：每次 1–3 s，超时 10 s，不在控制路径；事件限流 + 约 60 s 去重 + 并发 1；去重不是 exactly-once，只防重复分析。

**Q100. Where is the human in the loop?**
- **L1:** "At three places: manual mode with priority, a web interface where users see advice and requests, and manual-off that automatic requests cannot override."
- **L2 (Voice?):** "A voice command word switches to manual and starts the pump; the 'off' word returns to automatic."
- **L3 (A trap?):** "After a manual off, returning to auto may restart the pump if the soil is still dry. I explain this clearly rather than claim that off is permanent."
- 译：三处：手动模式优先、网页查看建议、手动关自动不能覆盖；语音词切手动，关词回自动；陷阱：回自动后湿度仍低会再开，如实说明。

### 10.4 工程化与频率（Q101 到 Q110）

**Q101. How did you set the sampling rates?**
- **L1:** "Each follows the time scale of the process. Soil: 200 ms sampling, median of five, one value per second, report every 2 seconds."
- **L2 (Why a median?):** "It rejects spikes, such as a supply dip when the relay clicks. With samples 1635, 1642, 1630, 2100 and 1598 the median is 1635 while the mean is 1721."
- **L3 (Consequence for the state machine?):** "The median gives moisture 65 and the pump stays on; the mean would give 61. Because of truncation, the stop point is at raw 1630 or lower."
- 译：各频率跟随过程时间尺度；中位数抗尖峰，例：中位数 1635 vs 均值 1721；L3：中位数得 65 泵继续，均值得 61；截断使停止点在 raw≤1630。

**Q102. How do you build a latency budget?**
- **L1:** "List the stages, assign each a number, and sum. The vision rule path is about 110 to 150 ms. The key control chain stays inside the Hi3861, at most about one second."
- **L2 (Measure how?):** "Timers around each stage over 300 frames, dropping the first 30, then mean and 95th percentile."
- **L3 (Pitfall?):** "Mixing model time and end-to-end time. I quote 28 ms for the model and 60 ms end to end, and say which is which."
- 译：列阶段、给数字、求和；视觉约 110–150 ms；控制链最坏约 1 s；300 帧打点丢前 30 帧取均值与 p95；常见错误是混用模型耗时与端到端。

**Q103. Why is your frame rate 15 FPS?**
- **L1:** "The camera gives 30, the chain takes about 60 ms, and I keep only the newest frame, so the steady rate is about 15."
- **L2 (How to raise it?):** "Pipeline the stages across threads, use hardware scaling and use more NPU cores."
- **L3 (Do you need to?):** "No. Plants change over minutes, and more frames mostly add heat and bandwidth."
- 译：摄像头 30，处理约 60 ms，只取最新帧，稳定约 15；可流水线、硬件缩放、多 NPU 核；场景不需要。

**Q104. What did you optimise first and why?**
- **L1:** "Frame age drift. A latency that grows over time is worse than a high but stable one."
- **L2 (Fix?):** "Drain the driver queue and keep the newest frame, counting drops."
- **L3 (Result and test?):** "Age bound about 93 ms, and a replay test asserts the maximum age over 300 frames."
- 译：先优化帧龄漂移；排空队列只留最新并计丢帧；上限约 93 ms，用回放测试断言。

**Q105. How do you design task priorities on the MCU?**
- **L1:** "Control and manual-command handling at high priority, networking in the middle, logging low. Networking never blocks control."
- **L2 (How do they communicate?):** "Through one-slot mailboxes: the newest report and the newest command. No queues that can grow."
- **L3 (Watchdog?):** "Only the control task feeds it, so a stuck control loop causes a reset to the safe default."
- 译：控制与手动命令高优先级，网络中，日志低；网络不阻塞控制；通过一格邮箱交换；只有控制任务喂狗，卡死则复位到安全默认。

**Q106. What do you do when a deadline is missed?**
- **L1:** "For soil, a late sample is harmless; for vision I drop the frame; for the LLM I time out and fall back."
- **L2 (Which must never be late?):** "Manual commands and sensor-fault shutdown."
- **L3 (How is that guaranteed?):** "They run at the highest priority and do no network or heavy computation."
- 译：土壤晚一次无害；视觉丢帧；LLM 超时降级；不能晚的是手动命令和传感失效关泵；高优先级且不做网络或重计算。

**Q107. How do you test timing-related behaviour?**
- **L1:** "Inject a clock. State-machine tests use a fake time source, so the 60-second and 120-second timers run in milliseconds."
- **L2 (Example?):** "Feed constant moisture 40 for 60 s and assert forced stop, no restart before 120 s of cooling, and a restart afterwards."
- **L3 (What can't you test this way?):** "Real hardware jitter. That's for bench tests and packet captures."
- 译：注入时钟，60/120 s 定时器毫秒级测完；例：恒定 40 湿度验证强制关、冷却、再开；真实抖动靠台架与抓包。

**Q108. What's your logging strategy?**
- **L1:** "One JSON line per decision with trace id, snapshot summary, config version, checks and outcome, written asynchronously."
- **L2 (Why JSON lines?):** "Easy to grep, easy to replay."
- **L3 (Volume concerns?):** "Images aren't logged continuously; only event JPEGs are kept, and logs rotate."
- 译：每个决策一行 JSON，含 trace id、快照摘要、配置版本、检查与结果，异步写；便于检索与回放；只保存事件 JPEG，日志轮转。

**Q109. How do you handle simulation versus the real device?**
- **L1:** "I built a device simulator for the server tests, but it only proves server logic. GPIO polarity and pump behaviour need the bench."
- **L2 (Verification ladder?):** "V0 to V5. I reached V4, the full real-hardware loop; I did not run V5 long-duration tests."
- **L3 (What did the simulator miss?):** "The relay polarity, because a simulator treats the logical state as the truth."
- 译：模拟器只证明服务端逻辑；GPIO 极性和泵需台架；验证到 V4，未做 V5；模拟器漏掉了继电器极性。

**Q110. How do you make sure your claims are honest?**
- **L1:** "I separate what I measured, what I designed and what I estimated, and I name the verification level I reached."
- **L2 (Example?):** "A single field trial showed moisture rising from 41 to 58 during watering. I call it a single observation, not a statistic."
- **L3 (If asked for a number you don't have?):** "'I didn't measure that, so I won't quote a number, but this is how I would measure it.'"
- 译：区分实测、设计、估算并说明验证级别；例：一次试验 41→58，称单次观察；没有数据则说没测并说明测法。

### 10.5 协议、服务端与执行（Q111 到 Q120）

**Q111. Why a length prefix?**
- **L1:** "TCP is a byte stream. A prefix tells the receiver exactly how many bytes to read for the next message."
- **L2 (Your header?):** "8 bytes: two big-endian 4-byte lengths, for the JSON and the JPEG, followed by the two segments."
- **L3 (Protection?):** "Maximum sizes of about 64 KB for JSON and 2 MB for JPEG; larger values mean a corrupted stream, so I disconnect and reconnect."
- 译：TCP 是字节流，前缀告知读多少；8 字节头 = 两个 4 字节大端长度；设上限 JSON 约 64 KB、JPEG 约 2 MB，超限则断开重连。

**Q112. Why bracket matching for the Hi3861 stream?**
- **L1:** "The device sends compact JSON without a length prefix, so the server finds object boundaries by matching braces, aware of braces inside strings."
- **L2 (Weakness?):** "A corrupted message can mismatch braces, so I add a maximum object size and resynchronise."
- **L3 (Better?):** "Add a length prefix or newline delimiter on the device if I could change the firmware."
- 译：设备发无前缀的紧凑 JSON，服务端用括号配对并识别字符串内括号；弱点是损坏消息，加最大长度并重同步；更好是设备端加长度前缀或换行分隔。

**Q113. How do you detect a dead device?**
- **L1:** "Periodic reports double as heartbeats. A read timeout of three periods, 6 seconds, marks the data stale."
- **L2 (Why 6?):** "Freshness is 10 s and reports are every 2 s, so 6 s tolerates two lost reports and still marks the data stale before it becomes unusable."
- **L3 (Reconnect?):** "Exponential backoff from 1 to 30 seconds, and after reconnecting, the server treats the pump state as unknown until a new report."
- 译：周期上报兼心跳；读超时 3 个周期=6 s 标过期；容忍丢两次；指数退避 1–30 s；重连后泵状态未知，直到新上报。

**Q114. What is idempotency and why does it matter here?**
- **L1:** "Repeating a command has the same effect as sending it once. With retries after lost ACKs, a duplicate must not double the watering."
- **L2 (How?):** "Each command has an id, the device remembers recent ids, and commands express a target state with a deadline."
- **L3 (Why not 'add 20 seconds'?):** "Because a duplicate would make it 40. 'On until time T' is safe to repeat."
- 译：重复发送效果同一次；重试时不能重复浇水；命令带 id、设备记住最近 id、命令表达目标状态加截止时间；增量语义重复会变 40 s。

**Q115. Sent, acknowledged, reported: what's the difference?**
- **L1:** "Sent means it left the server; acknowledged means the device accepted or rejected it; reported means the device's later status shows the pump on."
- **L2 (What's the strongest claim you make?):** "Reported state matches the request, and in one trial the soil reading rose from 41 to 58."
- **L3 (What is not claimed?):** "Flow rate, or that water reached the roots, since I had no flow sensor."
- 译：sent=已发出；acked=设备接受或拒绝；reported=设备状态显示已开泵；最强声称是上报状态一致，一次试验 41→58；无流量传感器，不声称水到根部。

**Q116. How do you treat data freshness?**
- **L1:** "Every datum carries a receive time and an age. Sensors are valid for 10 seconds, pump state 10, vision observations 2."
- **L2 (Combining?):** "Filter each by its own limit before fusing. Never combine a stale moisture reading with a fresh detection into one conclusion."
- **L3 (Clocks?):** "I don't assume the devices share a clock. I use server receive time and the device's age-at-send, and reject negative or huge ages."
- 译：每条数据带接收时间与年龄；传感 10 s、泵 10 s、视觉 2 s；融合前各自过滤；不假设时钟同步，用接收时间和 age_at_send，拒绝负值或过大。

**Q117. What if the server restarts?**
- **L1:** "The device keeps irrigating locally. On restart the state is unknown until the first report."
- **L2 (Pending commands?):** "Lost; I don't replay them blindly."
- **L3 (Improvement?):** "Persist command tracking so the server can reconcile desired and reported state after a restart."
- 译：设备本地继续灌溉；重启后状态未知；待确认命令丢失、不盲目重放；改进：持久化命令跟踪以对账。

**Q118. How do you cross from a thread into asyncio?**
- **L1:** "The TCP thread blocks on receive and hands data to the event loop with call_soon_threadsafe."
- **L2 (Why not touch shared state directly?):** "The store is lock-protected with short critical sections: copy under the lock, do slow work outside."
- **L3 (Biggest risk?):** "A blocking call in the loop, such as a synchronous HTTP call, freezes WebSocket pushes and heartbeats."
- 译：TCP 线程阻塞读，用 call_soon_threadsafe 交给事件循环；存储短锁，锁内拷贝锁外做慢事；最大风险是循环内阻塞调用。

**Q119. How do you handle a slow WebSocket client?**
- **L1:** "Each client has its own small send queue and task. A slow client only drops its own old snapshots."
- **L2 (Queue policy?):** "Depth 10, drop oldest, because the page only needs the latest state."
- **L3 (Extreme?):** "A client that cannot send for 30 seconds is disconnected."
- 译：每客户端独立小队列与任务，慢客户端只丢自己的旧快照；深度 10 丢最旧；30 s 发不出则断开。

**Q120. If you redesigned the transport, what would you choose?**
- **L1:** "For many nodes, MQTT: QoS levels, retained state and last-will for offline detection. For a few devices, raw TCP kept the MCU side small."
- **L2 (Costs of raw TCP?):** "I had to write framing, reconnection, heartbeats and acknowledgements myself."
- **L3 (Security?):** "The LAN link is plaintext and unauthenticated. Beyond a trusted LAN I'd add TLS and tokens, subject to the Hi3861's memory budget."
- 译：多节点用 MQTT（QoS、保留消息、遗嘱）；少量设备原生 TCP 让 MCU 侧简单，代价是自己写成帧、重连、心跳、确认；LAN 明文无认证，超出可信网络需 TLS 与令牌（受内存限制）。

## 本章要点速记

1. 先结论后细节；五类信息、建议≠执行是主线。
2. 没数据就说没测，并给出你会怎么测。
3. AI 方向三大块：YOLO（输出/NMS/置信度）、量化（公式/逐通道/校准/检测头）、Agent 可靠性（校验/白名单/降级/权限）。
4. 具体数值先对照 README 自查表（教材统一设计取值，若与实机不同以实机为准并同步修改），再背答案。
