# 99 英文面试口述与深挖问答

> **一句话定位**：P4 的英文口述稿（30 秒 / 90 秒 / 3 分钟）与 60 个深挖问答（含追问方向与 STAR），按"系统 → 本地控制 → 视觉 → 量化 → 通信 → 服务端 → Agent → 安全执行 → 工程"分组。

## 本章学完你能……

- 流畅说出三个长度的项目介绍，并随时切换。
- 回答 YOLO / 量化 / Agent 可靠性三大 AI 高频主题的追问。
- 遇到没有数据的问题，用诚实模板回答。

## 使用规则

1. 英文只陈述有依据的事实（CV、笔记线索）；`【补全】` 处换成你的真实情况。
2. 记不清具体数字时用：*"I don't have the exact figure in front of me, but the order of magnitude was …"*（仅当你确实有量级印象），或 *"I didn't measure that, so I won't quote a number."*
3. 先结论、后细节；每个答案控制在 20–40 秒。
4. 相关章节见 [README](./README.md)。

## 一、三种长度口述

### 1.1 30 秒

> "My smart gardening system, built in 2024 on OpenHarmony and an RK3588, closes the loop from vision to irrigation. An INT8 YOLOv5 model on the RK3588 turns camera frames into structured observations; a LangGraph decision chain on the server turns observations and soil data into recommendations or constrained requests; and a Hi3861 runs a local pump state machine with separate start and stop thresholds and manual priority. The key idea is that AI proposes, and only validated requests reach the device."

（译：2024 年在 OpenHarmony 和 RK3588 上做的智能园艺系统，打通视觉到灌溉。RK3588 上 INT8 YOLOv5 把帧变成结构化观测；服务端 LangGraph 把观测和土壤数据变成建议或受约束请求；Hi3861 跑本地水泵状态机（独立启停阈值、手动优先）。核心：AI 只提议，只有校验过的请求才到设备。）

### 1.2 90 秒

> "This was my personal project from May to August 2024. The system has three layers. On the Hi3861, a microcontroller, I read a soil moisture probe through the ADC, calibrate it to a moisture index, and run a pump state machine with independent start and stop thresholds, so the relay doesn't chatter. Manual commands always take priority, and the loop keeps working if the network goes down.
> On the RK3588, I built an inference chain: V4L2 capture, preprocessing, a YOLOv5 model converted to INT8 for the NPU, post-processing with thresholds and non-maximum suppression, and finally structured observations with class, confidence, box and timestamp.
> On the server, a LangGraph chain takes soil and vision events. A rule-based fast path handles extreme states without waiting for a language model; other cases go through a supervisor to care or alert nodes. Its output is a recommendation or a constrained request, which must pass whitelist, mode and freshness checks.
> I kept five kinds of information separate: sensor readings, model observations, recommendations, command requests and device feedback, because a displayed request is not proof that the pump ran."

（译略：三层结构；Hi3861 采集标定+滞回+手动优先、断网可用；RK3588 推理链；服务端 LangGraph fast path + 校验；五类信息分开。）

### 1.3 3 分钟

> "Let me walk through the problem first. A potted garden needs watering when the soil is dry, but I also wanted the system to notice plant problems, like lesions, and explain them to the user. Those two needs have very different time scales and risks, which drove the architecture.
> Watering is slow and safety-relevant, so it lives at the edge of the physical world: a Hi3861 reads the probe, applies a calibration, and runs a hysteresis state machine, starting below one threshold and stopping above a higher one, and holding its state in between. It drives an active-low relay, so I separate the logical state from the pin level. Manual mode pauses the automatic logic, so a human always wins. If Wi-Fi or the server fails, irrigation continues.
> Vision is compute-heavy, so it lives on an RK3588 with an NPU. I capture frames through V4L2 with a ring of buffers, convert and letterbox them, run an INT8 YOLOv5 model converted with the RKNN toolkit, decode and filter the outputs, map boxes back to the original image, and publish structured observations with confidence and timestamps over TCP, as a JSON segment and an optional JPEG segment with length prefixes.
> The server collects both streams into a shared, lock-protected state. A blocking thread reads TCP; an asyncio loop runs the WebSocket interface and the agent. The LangGraph chain has a rule-based fast path for extreme states and LLM nodes for interpretation, and every LLM output is parsed and validated. Nothing goes to the device directly: requests pass a whitelist, mode, range and freshness checks, manual-off priority is enforced, commands carry ids so retries are idempotent, and the device's own report is what confirms the pump state.
> What I'm most proud of is the discipline: confidence is not accuracy, deployment is not training, a recommendation is not an action, and a sent command is not a pump that ran. If I did it again I'd add persistent command tracking, MQTT for many nodes, and a proper FP32-versus-INT8 benchmark."

（译略：问题→本地控制→视觉→服务端→安全执行→反思。）

## 二、系统与动机（Q1–Q6）

**Q1. Why three layers?**
> "Each layer does what it's best at. The Hi3861 is close to the actuator and must keep working offline. The RK3588 has the NPU for vision. The server has the resources for aggregation, an LLM and the web interface, and it's allowed to be slow or occasionally down."
（译：各层做擅长的事：Hi3861 近执行器且需离线可用；RK3588 有 NPU；服务端负责汇聚、LLM、界面，可以慢或偶尔宕机。）
追问：*What fails if the server dies?* → "Only recommendations and the UI. Irrigation continues locally."

**Q2. Why not do everything on the RK3588?**
> "It could, but I wanted the irrigation loop isolated from vision failures and cheap per pot. A Hi3861 node is low-power and independent."

**Q3. What does 'autonomous' mean in your CV?**
> "Autonomous local irrigation: the pump loop runs without the network or the LLM. It does not mean the LLM freely controls hardware."

**Q4. What are the five kinds of information?**
> "Sensor readings, model observations, recommendations, command requests and device feedback. None can substitute for another; for example a detection of a lesion is not evidence of dry soil."

**Q5. Which part did you build yourself?**
> "It's a personal project, so I built the full loop: 【补全：哪些是自写、哪些用了现成 SDK/示例/权重】."

**Q6. Where does OpenHarmony come in?**
> "The Hi3861 firmware runs on the OpenHarmony lightweight system, and the project was built for the Huawei ICT Competition's OpenHarmony track, where it won a provincial first prize and a national final third prize."

## 三、本地灌溉（Q7–Q16）

**Q7. Why two thresholds?**
> "A single threshold makes the pump chatter when noise crosses it. With separate start and stop thresholds and memory in between, the relay switches rarely. In a worked example it dropped from potentially thousands of switches an hour to a few dozen."

**Q8. What is hysteresis exactly?**
> "The output depends on both the input and the previous state. Below the start threshold, on; above the stop threshold, off; in between, hold."
追问：*Is it a filter?* → "No. A filter smooths the input; hysteresis shapes the decision. I use both."

**Q9. Which threshold values?** > "The configuration was around 56 to start and 65 to stop on my calibrated scale 【补全确认】. They're setup-specific, not universal soil values."

**Q10. What happens exactly at 65?** > "With strict comparison, 65 is inside the band, so the state is held. It stops only when the value is greater than 65. Integer truncation also shifts the effective switch point by about one percentage point."

**Q11. How does the ADC reading become a moisture value?** > "A linear two-point calibration, dry and wet references, clipped to 0–100. It's a relative index for this probe and soil, not volumetric water content."

**Q12. What if the probe is unplugged?** > "An open circuit can look like very dry soil and keep the pump on. A robust design checks the raw ADC range, rate of change and stuck values, and fails safe by stopping the pump. 【补全：原版是否有这些检查；如果没有，说 I identified it as a failure mode and would add it】."

**Q13. Active-low relay?** > "Logic on means pin low. I keep a logical state and translate in one place, and initialise the pin high so the relay is released at power-up."

**Q14. What does manual priority mean?** > "A manual command always overrides the automatic logic; in manual mode the hysteresis logic is paused. Leaving manual mode hands control back, so if the soil is still dry the pump may restart — I'm explicit about that."

**Q15. Voice trigger?** > "It starts the pump and enters manual mode, then restores automatic mode when the trigger ends. I'd make the wait non-blocking and add a timeout."

**Q16. Other protections?** > "Maximum continuous run time, minimum off time, and a daily limit, independent of any sensor. 【补全：实际有哪些】."

## 四、边缘视觉（Q17–Q27）

**Q17. Walk me through the vision pipeline.** > "V4L2 capture, colour conversion, letterbox resize, normalisation, RKNN inference, decoding, confidence threshold, per-class NMS, mapping boxes back to the original image, then a structured event."

**Q18. Explain V4L2 buffering.** > "I request a few memory-mapped buffers and queue them all. The driver fills them; I dequeue a filled one, process it, and queue it back. After queueing, the buffer belongs to the driver again, so I must finish decoding or copying first."

**Q19. What if processing is slower than the camera?** > "The driver runs out of free buffers and drops frames, and frames wait in the queue so latency grows. With four buffers at 30 fps and 50 ms processing, throughput is 20 fps and frame age approaches about 150 ms. I'd take the newest frame to keep freshness."

**Q20. Why MJPEG vs YUYV?** > "Uncompressed 720p30 YUYV is about 442 Mbit/s, too much for USB 2. MJPEG is compressed, at the cost of a decode step."

**Q21. What is letterboxing?** > "Resize preserving aspect ratio and pad to a square. For 1280×720 to 640, scale 0.5, top padding 140. Inverse: subtract padding, divide by scale."

**Q22. What does YOLOv5 output?** > "Three scales, strides 8, 16, 32, three anchors per cell, 25,200 candidates at 640 input. Each has box offsets, objectness and class scores."

**Q23. How do you decode a box?** > "Sigmoid; centre = (2σ(t) − 0.5 + grid) × stride; size = (2σ(t))² × anchor. Score = objectness × class probability."

**Q24. What is NMS?** > "Sort by score, keep the best, remove boxes with IoU above a threshold with it, repeat, per class. Too high a threshold leaves duplicates; too low deletes neighbouring objects."

**Q25. Is confidence accuracy?** > "No. It's a score for one detection and may not be calibrated. Precision, recall and mAP come from labelled evaluation. A 0.9 detection from an old frame still shouldn't drive an action."

**Q26. Does an empty detection mean healthy?** > "No: occlusion, blur, lighting or a miss. I treat it as 'no observation' and use a frame-valid heartbeat to tell it from a broken camera."

**Q27. What are your mAP and FPS?** > "【补全真实数字与测量方法。】 If I didn't measure: 'I measured model latency but not a full benchmark, so I won't quote an mAP.' I also separate model time from end-to-end latency."

## 五、量化与 RKNN（Q28–Q36）

**Q28. Explain INT8 quantisation.** > "q = clip(round(x/s) + z); x ≈ s(q − z). Smaller model, integer NPU ops. Error is at most s/2 when nothing saturates."

**Q29. Saturation?** > "Values outside the range are clipped, and the error can be large: with s = 0.1, x = 20 becomes 12.7, an error of 7.3."

**Q30. Symmetric vs asymmetric?** > "Symmetric has zero point 0, good for weights. Asymmetric uses a zero point to cover skewed ranges like ReLU outputs, halving the step in the 0–6 example."

**Q31. Per-channel?** > "Each output channel gets its own scale; in my example a weight of 0.1 had 5.5% error per-tensor and 1.6% per-channel. Usually weights per-channel, activations per-layer."

**Q32. Calibration set?** > "Representative unlabelled images that define activation ranges, preprocessed exactly as at inference. A mismatched set or one outlier can make steps ten times coarser. 【补全：张数、来源】."

**Q33. How does integer inference work?** > "Multiply int8 values, accumulate in int32, then requantise with M = s_x s_w / s_y implemented as a fixed-point multiply and shift."

**Q34. Why are detection heads sensitive?** > "Box coordinates reach hundreds while scores are 0–1; sharing a scale (~2.5) turns scores into 0 or 1. So heads are kept separate, with decoding on the CPU, or mixed precision is used."

**Q35. Conversion flow?** > "Export ONNX; RKNN-Toolkit2 on a PC: config for rk3588 with mean 0 and std 255, load ONNX, build with quantisation and a calibration list, export .rknn; run it with the runtime on the board."

**Q36. Did you train the model?** > "【真实回答。】 Either 'I trained it on …' or 'My part was deployment and integration; the weights came from …'. Conversion is not training and doesn't prove accuracy."

## 六、通信与服务端（Q37–Q46）

**Q37. Why length prefix?** > "TCP is a byte stream with no message boundaries. A prefix lets the receiver read exactly N bytes, and a max-length check protects against corrupted headers."

**Q38. Half and sticky packets?** > "One message may arrive over several receives, or several in one. A stateful parser handles both: read the header, then read exactly that many bytes, looping."

**Q39. Why separate JSON and JPEG?** > "The JSON is small and decision-critical; the image is large and optional. Separate segments, paired by event id, avoid base64's one-third overhead."

**Q40. Endianness?** > "The protocol fixes network order; reading 100 as little-endian would give about 1.6 billion — that's why the max-length guard exists."

**Q41. Offline detection?** > "Periodic reports as heartbeats, read timeouts, staleness marking, reconnect with exponential backoff."

**Q42. Why asyncio for WebSocket?** > "Many mostly idle connections are cheap as coroutines on one thread, with no locks for shared client lists."

**Q43. Calling the loop from another thread?** > "`run_coroutine_threadsafe` or `call_soon_threadsafe`, because the loop isn't thread-safe; arguments are bound when the coroutine is created."

**Q44. What if a handler blocks?** > "The whole loop freezes: broadcasts, heartbeats, the agent. Use async clients or an executor."

**Q45. Why a lock in the DataStore?** > "The TCP thread is a different thread. Short critical sections, whole-message updates to avoid torn reads, no I/O under the lock."

**Q46. Queue overflow?** > "At 5 events/s in and 0.5/s out, a 100-slot queue fills in about 22 s. I count drops, coalesce per location, rate-limit, and keep the fast path on its own channel."

## 七、Agent 与 LLM 可靠性（Q47–Q56）

**Q47. What is LangGraph and what did you build?** > "A graph over shared state with conditional edges. Six nodes: sensing with the fast path, supervisor, care, alert, execution and skip. It's a hand-designed workflow, not a trained network."

**Q48. Fast path vs skip?** > "Fast path: a clear, extreme condition, go straight to execution checks. Skip: nothing to do, produce nothing."

**Q49. Why not let the LLM decide watering?** > "It's simple, safety-relevant and already handled locally; an LLM adds latency and variability."

**Q50. How do you validate LLM output?** > "Parse into a fixed schema with enumerated actions, length limits; on failure retry once, then fall back to a template and count the failure."

**Q51. Hallucinated action?** > "It isn't in the enumeration or whitelist, so it's rejected. The model has no authority."

**Q52. Prompt injection?** > "Output is only a proposal; untrusted text is kept in a data section; permissions and command names aren't chosen by the model."

**Q53. Is the agent deterministic?** > "The control flow and checks are deterministic and unit-tested; the LLM text is probabilistic and evaluated on a labelled set with a mocked model for flow tests."

**Q54. Memory and RAG?** > "State has working and recent-history fields, and retrieval can add reference text. 【补全实际实现】. Retrieved text never bypasses execution checks."

**Q55. How do you evaluate an LLM agent?** > "Safety invariants by property tests; advice quality by a small labelled set and human review; online metrics such as rejection rate, timeouts and validation failures."

**Q56. LLM down?** > "Fast path and local irrigation are unaffected; care and alert degrade to templates."

## 八、安全执行与工程（Q57–Q64）

**Q57. How does an AI decision become a physical action safely?** > "Proposal, then policy check — whitelist, mode, freshness, range, manual priority — then the device's own rules, then device-reported state. Four different things: recommendation, request, acknowledgement, reported state."

**Q58. User turns pump off while the agent wants on?** > "The user wins; the execution layer rejects automatic on-requests during manual-off and the device pauses automatic logic. Off is always allowed; on must pass every check."

**Q59. Idempotency?** > "Commands carry ids and express a target state with an end time; the device remembers recent ids. 'Water 20 more seconds' resent would become 40."

**Q60. Is your 60-second dedup exactly-once?** > "No. It prevents re-analysis within a window; it's in memory, marked before execution, and doesn't control the device. I rely on at-least-once plus idempotency."

**Q61. How do you know the pump ran?** > "Levels: sent, acknowledged, device-reported, then a moisture rise or flow reading. I claim up to 【补全】."

**Q62. Clocks across devices?** > "Not assumed synchronised. Server receive time, device age-at-send, reject negative or large ages."

**Q63. Hardest bug (STAR).** > "S: 【真实情境】. T: find where in the chain it broke. A: I checked each boundary — ADC, pin level, bytes on the wire, parsed frames, decision trace. R: 【结果与预防措施】." 参考素材见 [13 故障与测试](./13_故障与测试.md)。

**Q64. What would you improve?** > "Persist command tracking, one versioned config, MQTT for many nodes, per-hop latency metrics, long-duration tests, and an FP32-versus-INT8 benchmark."

## 本章要点速记

1. 先结论后细节；五类信息、建议≠执行是主线。
2. 没数据就说没测，并给出你会怎么测。
3. AI 方向三大块：YOLO（输出/NMS/置信度）、量化（公式/逐通道/校准/检测头）、Agent 可靠性（校验/白名单/降级/权限）。
4. 所有 `【补全】` 先在 README 自查表落实再背答案。
