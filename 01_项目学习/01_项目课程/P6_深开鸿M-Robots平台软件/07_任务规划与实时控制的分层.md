## 1. 要解决什么问题

假设任务计划说："去 A 点，取货，再去 B 点"。要把它变成电机电流，中间要完成很多不同性质的事：

- 决定任务顺序、选择哪台机器人（秒～分钟，可以花很长时间思考，结果可以不确定）；
- 规划路径、避障（百毫秒～秒，需要地图和搜索）；
- 跟踪轨迹、算速度命令（几十毫秒～十几毫秒，必须按固定周期）；
- 闭环控制电机（毫秒～亚毫秒，必须严格确定）。

把它们全塞进一个循环里会怎样？一次路径规划耗时 300 ms，100 Hz 的速度控制就会漏掉 30 个周期，机器人"失控"一小段时间。反过来，把任务规划放进 1 kHz 控制中断里更不可能。**分层的本质：让每一层以自己合适的时间尺度运行，并通过明确的契约交互。**

## 2. 时间尺度金字塔

```text
         慢 / 灵活 / 非确定                                  典型周期 (教学示例)
  ┌───────────────────────────────────────┐
  │ L5 任务层：任务分解、调度、AI 规划     │   事件驱动，秒～分钟
  ├───────────────────────────────────────┤
  │ L4 协同与安全层：分发、策略校验        │   事件驱动，数十毫秒～秒
  ├───────────────────────────────────────┤
  │ L3 行为/路径层：全局/局部规划、跟踪    │   1～20 Hz 常见
  ├───────────────────────────────────────┤
  │ L2 运动控制层：速度/轨迹跟踪、状态管理 │   50～200 Hz 常见
  ├───────────────────────────────────────┤
  │ L1 伺服/驱动层：电机电流/速度环        │   0.5～10 kHz 常见（常在驱动器内）
  └───────────────────────────────────────┘
         快 / 严格 / 确定
```

> 上表数值是**通用经验范围的示意**。本项目具体取值：L5 事件驱动；L4 事件驱动、数十毫秒级；L3 规划 5–10 Hz；L2 速度命令 20–50 Hz、状态发布 20 Hz；L1（MCU 内）100–1000 Hz。

规律：

- **频率每低一个数量级，允许的计算复杂度大约高一个数量级**，但对延迟与抖动的容忍也更高。
- **越靠下，越要求"最坏情况也满足截止时间"（硬实时/准实时）**；越靠上，越允许"平均上够快"。
- **安全责任越靠下越"朴素"**：最底层的限流、限位、急停应该尽量用简单而确定的机制（甚至硬件）实现，不依赖上层正确。

## 3. 为什么必须分层

| 理由 | 说明 |
|---|---|
| 时间尺度不同 | 规划是"尽力而为"，控制是"准时必达" |
| 故障域隔离 | 上层（含 AI）崩溃/卡死，不能拖垮下层 |
| 可替换 | 规划算法可换（A*、TEB、LLM 规划）而控制层不变；硬件可换而规划不变 |
| 可验证 | 下层小而确定，可穷举测试；上层复杂，靠约束与门控 |
| 安全边界 | 高层决策必须经过一道门才能变成物理动作（08 章） |
| 团队分工 | 不同团队/不同语言/不同部署位置 |

对应 CV：*task planning and real-time control are layered* 是 P6 的核心架构原则之一，"安全执行链"正是分层之间的那道门。

## 4. 层间接口设计

### 4.1 接口原则

1. **契约而非调用**：上层给下层的是"带有效期的设定值/目标"，不是"请立刻执行并等我"。下层按自己的节奏消费。
2. **单向主导、双向可见**：命令向下流，状态向上流；下层从不依赖上层的"实时在线"才保持安全。
3. **异步**：上层的慢不能阻塞下层。禁止在控制周期内同步调用上层或网络。
4. **每条消息自描述**：带时间戳、有效期、来源、序号、坐标系。
5. **失败显式**：接口要有"拒绝/过期/不可行"的返回，而不是静默忽略。

### 4.2 三种典型接口形态

| 形态 | 内容 | 适用 | 失联处理 |
|---|---|---|---|
| 连续设定值流（setpoint stream） | $(v_x,v_y,\omega_z)$ + `valid_until` | 速度/位姿跟踪 | 过期自动归零（看门狗） |
| 轨迹/路径（trajectory） | 带时间戳的点序列 + 约束 | 局部轨迹跟踪 | 走完已发布的安全段后停（"短视界"） |
| 目标—反馈—结果（goal/feedback/result） | 目标 + 周期反馈 + 最终结果，可取消 | 导航到点、抓取等长任务 | 目标超时/取消；下层自行收尾到安全状态 |

### 4.3 接口字段示例（教学设计）

```text
Setpoint {
  seq            // 序号，检测丢失/乱序
  stamp          // 生成时间 (统一时间基准)
  valid_until    // 失效时间：到点后视为无效
  frame_id       // 坐标系，通常 base_link
  vx vy wz       // 目标值
  source         // 来源（提案编号 / 控制器 id），用于审计
  mode           // 期望模式 (velocity / hold / stop)
}

ControlFeedback {
  stamp, seq_acked, tracking_error, saturated, mode, health
}
```

字段是典型设计，本项目口径：向下为 Setpoint{stamp、valid_until_ms、source、frame_id、vx、wz、mode、seq}，向上为 Feedback{ack_seq、tracking_err、saturation_flags、state_validity}；与 README 自查表第 14 项一致。

### 4.4 层间的"信任"方向

下层**不信任**上层：设定值必须在能力范围内、新鲜、来自授权来源，否则忽略或限幅。这既是安全要求，也是稳健性要求：上层有 bug 时，下层的"最后一道限幅"（03 章适配器限幅）仍然生效。

## 5. 延迟如何影响控制：手算

为什么不能在控制周期里等上层？因为延迟会吃掉稳定裕度。

**推导**：一个纯延迟 $\tau$ 的传递函数是 $e^{-s\tau}$，幅值恒为 1，相位为 $-\omega\tau$（弧度）。如果回路带宽（增益穿越频率）为 $\omega_c$，则延迟额外引入的相位滞后 $\phi=\omega_c\tau$。系统的相位裕度（phase margin）$PM$ 被削减 $\phi$，若 $PM-\phi\le0$，闭环不稳定。

**手算（教学示例）**：速度环穿越频率 $\omega_c=20$ rad/s（约 3.2 Hz），原相位裕度 $PM=60^\circ$。

- 延迟 $\tau=5$ ms：$\phi=20\times0.005=0.1$ rad $=5.7^\circ$，剩余裕度 $54.3^\circ$，几乎无影响。
- 延迟 $\tau=50$ ms：$\phi=20\times0.05=1.0$ rad $=57.3^\circ$，剩余 $2.7^\circ$，几乎临界，会振荡。
- 延迟 $\tau=60$ ms：$\phi=1.2$ rad $=68.8^\circ>60^\circ$ → 不稳定。

结论：**回路的闭环带宽越高，容忍的延迟越小**；把一个会产生 50 ms 不确定延迟的步骤（网络、规划计算、同步 IPC）放进回路里，等于直接破坏稳定性。这就是"分层 + 异步 + 下层自治"的理论依据。更多请参见 [数字控制与实时性](../../02_基础知识/05_控制理论/08_数字控制与实时性.md)。

## 6. 速率转换与保持

上层以 $f_u$ 产生设定值，下层以 $f_c\gg f_u$ 消费。中间要做**速率转换**。

### 6.1 零阶保持（ZOH）

最简单：下层每个周期读"最新设定值"，在新值到来之前保持不变。优点是简单、延迟小；缺点是设定值阶跃。

### 6.2 插值/平滑

为避免阶跃，下层可对设定值做一阶低通、斜坡（加速度限幅，04 章）、或轨迹插值。

**手算（教学示例）**：上层 5 Hz（$T_u=200$ ms），下层 100 Hz（$T_c=10$ ms），一个上层周期内下层执行 $200/10=20$ 次。设定值从 $v=0.2$ 变到 $0.4$：

- ZOH：下层在第 1 个周期就输出 0.4，加速度限幅负责平滑；
- 线性插值：每个下层周期增加 $(0.4-0.2)/20=0.01$ m/s，20 个周期（200 ms）平滑到达（需要知道下一个目标，会引入至多一个上层周期的延迟）。

选择取决于对延迟 vs. 平滑的取舍；实际中常用"ZOH + 加速度限幅"。

### 6.3 反方向：下层向上层降采样

下层 100 Hz 的状态，上层只需 5 Hz。降采样应在状态管理里做（取最新或取滤波后的值），并保留 `stamp`，不要让上层自己按到达时间抽样（那样会引入抖动）。

## 6.4 速率转换的两个具体陷阱

**陷阱 1：把上层的低速输出直接当作下层的每周期输入**。上层 5 Hz 输出一个速度设定值，下层 100 Hz 运行。若下层每个周期都把设定值原样送给电机，那么上层每次更新时下层看到的是一个阶跃，等价于每 200 ms 给底盘一次冲击。正确做法是 06.2 节的平滑：下层有自己的目标轨迹，每周期按加速度限幅向新设定值靠近。再加一层，设定值带有 `valid_until_ms`，过期则不再执行，而不是"保持到下一次更新"。

**陷阱 2：时间戳在速率转换时丢失**。上层 5 Hz 的位姿，被下层 100 Hz 的控制循环使用时，位姿本身是 200 ms 前的测量，即使它在内存里"刚刚被读到"。如果下层把"读到的时刻"当作"测量的时刻"，就会把 100～200 ms 的陈旧误当成实时。做法：上层设定值与反馈都带测量时间戳，下层根据当前时间计算年龄，超过上限时降级。这与 05 章的"测量时间优先于接收时间"一脉相承。

**手算（教学示例）**：上层 5 Hz 位姿误差为 0.10 m，机器人以 0.5 m/s 前进。位姿年龄平均 100 ms，则位置实际已变化 $0.5\times0.1=0.05$ m。如果不补偿，控制器看到的误差有 50% 来自陈旧。补偿方式：用里程计在测量时刻到当前时刻之间做短时外推，并把外推结果标成"推算值"，窗口不超过几个周期。

**与分层的关系**：分层不是为了好看，而是让每一层在自己的时间尺度上做"最擅长的事"，层间用带时间戳和有效期的接口交换信息。接口里没有时间，分层就只剩名字。

## 7. 上层失联时下层怎么办

"上层"可能是：规划进程崩溃、网络断开、AI 服务超时、操作员掉线。下层需要确定的反应。

### 7.1 两个机制的区别

| 机制 | 防什么 | 触发条件 | 动作 |
|---|---|---|---|
| 有效期（TTL / valid_until） | 设定值本身过期 | 当前时间 > `valid_until` | 视为无效，转入保持/停止 |
| 看门狗（watchdog） | 上层失去"心跳" | 一段时间没有任何新消息/心跳 | 触发故障安全动作 |

有效期是"这条命令什么时候不再有效"，看门狗是"发命令的人还活着吗"。两者互补。

### 7.2 典型降级阶梯（教学设计）

```text
设定值有效                 → 正常跟踪
刚过期（< T1）             → 保持当前速度不变？—— 通常不可取，应改为按受控减速度减速
T1 < 过期 < T2             → 受控减速到停
> T2 或检测到故障         → 停止并进入安全模式（保持刹车/使能关闭，视硬件）
上层恢复                   → 需要一个"确认恢复"步骤，不自动继续旧任务
```

要点：

1. **失联后的动作是预先确定的，不由上层决定。**
2. **减速度要受限**（急停可能导致打滑、货物倾倒）。
3. **恢复需要显式确认**，避免上层恢复后突然执行已陈旧的任务（与 06 章幂等/有效期呼应）。

### 7.3 手算：失联后的停车距离

**教学示例**：速度 $v=0.5$ m/s，看门狗超时 $T_w=0.3$ s（期间仍按原速度运行），制动减速度 $a=1.0$ m/s$^2$。
超时期间位移 $=0.5\times0.3=0.15$ m；制动距离 $=v^2/(2a)=0.25/2=0.125$ m；总停车距离 $=0.275$ m。
所以看门狗超时设置要根据"允许的最大停车距离"反推（见 04 章 7.2 的公式）。

## 8. 实时性：线程、优先级与阻塞

控制层稳定运行的工程要点（典型做法）：

| 要点 | 说明 |
|---|---|
| 周期用绝对时间推进 | 用 `sleep_until(next)` 而不是 `sleep_for(period)`，避免累计漂移 |
| 控制线程高优先级 | 日志、网络 IO 在低优先级线程 |
| 禁止阻塞调用 | 控制周期里不做同步 IPC、不分配大内存、不加可能被低优先级持有的锁（优先级反转） |
| 无锁/短临界区 | 与其他线程交换数据用短锁或原子指针 |
| 测量抖动 | 记录每个周期的实际间隔与执行时间，监控最坏情况 |
| 最坏执行时间（WCET） | 估计一次周期内计算的最大耗时，必须小于周期 |

**周期利用率手算（教学示例）**：周期 10 ms，计算 WCET 为 2 ms，利用率 $=2/10=20\%$。若加入了偶发 8 ms 的阻塞（如日志落盘），最坏利用率 $=100\%$，抖动大——这就是故障 F3（见 [故障案例库](./11_故障案例库.md)）的原型。

OpenHarmony 标准系统基于 Linux 内核时，可使用实时调度策略与优先级（典型能力），但仍要注意：用户态的 GC、内存分配、缺页、IPC 都会产生不确定延迟；高要求的闭环通常放在驱动器/MCU 里，平台层做速度/位姿级控制（参见 [STM32 与 FreeRTOS 项目 P3](../P3_RoboMaster英雄机器人嵌入式控制/README.md) 里对更底层实时回路的做法）。

## 8.5 本项目的线程与进程划分、周期抖动预算（典型设计）

上一节讲了实时性的通用要点。这里落到本项目口径：进程上，设备适配器、状态管理器、策略校验、协同层各自独立进程；线程上，每个进程里"周期性控制或发布线程"与"网络/日志线程"分开。

| 进程 | 周期性线程 | 周期 | 优先级（相对） | 备注 |
|---|---|---|---|---|
| 设备适配器 | CAN 发送/反馈接收 | 10 ms | 高 | 不做同步 IPC、不分配大内存 |
| 状态管理器 | 状态聚合与发布 | 50 ms（20 Hz） | 中 | 订阅各传感器流，发布一致状态 |
| 策略校验 | 事件驱动处理提案 | 事件 | 中 | 本地缓存最新状态快照，不在请求内远程查询 |
| 协同层（M-DDS） | 公告/租约维护 | 1 s | 低 | 回调里只入队，不做重活 |
| 日志线程 | 异步落盘 | 批量 | 最低 | 控制线程只写环形缓冲 |

**抖动预算（教学示例）**：控制周期 10 ms，期望最坏抖动不超过周期的 20%，即 2 ms；计算 WCET 约 2 ms，则最坏响应约 4 ms，利用率 40%，余量足够。如果把日志同步落盘放进控制线程，偶发 8 ms 阻塞会让最坏响应变成 10 ms 以上，直接触发"周期溢出"。判定溢出的做法：线程每周期记录 `actual_period` 与 `exec_time`，连续两个周期超过 1.5 倍周期则上报健康降级（15 章）。

**优先级反转**：低优先级的日志线程持有一把锁，高优先级的控制线程要同一把锁，就会被卡住。典型规避：控制线程与日志线程之间用无锁环形缓冲；必须用锁时使用带优先级继承的互斥量，并保持临界区只做指针交换。

**与端到端延迟的关系**：控制线程周期抖动直接叠加到"命令到执行器"的延迟里。本项目口径的设计预算是小于 100 ms，名义延迟约 10 ms，上限约 30 ms（见 02 章 10.5 节）。预算用完的先后顺序大致是：Wi-Fi 重传 > 线程调度抖动 > 序列化 > 计算。

## 8.6 手算：多源时间尺度下的"最坏响应"

一个典型问题：任务层下发新目标，从发出到机器人底盘开始响应最多要多久？分段累加（教学示例）：

1. 任务层事件到规划层：规划层 5 Hz，最坏等一个周期 200 ms。
2. 规划层输出到速度设定值：速度命令 20 Hz，最坏再等 50 ms。
3. 命令到执行器：设计预算 100 ms。
4. 执行器爬升到目标（加速度限幅 1.0 m/s²，目标 0.5 m/s）：0.5 s。

总计最坏约 0.2 + 0.05 + 0.1 + 0.5 = 0.85 s，而其中真正由"软件延迟"造成的只有 0.35 s，其余是机械响应。判断瓶颈时要先区分"软件延迟"和"物理响应时间"，否则会把加速度限幅造成的 0.5 s 误当成通信慢。

## 9. 教学版 C++ 示例（可编译）

> **教学示例，非项目源码。** 慢速任务线程向快速控制线程交付"带有效期的设定值"。已用 `g++ -std=c++17 -pthread` 编译运行验证。

```cpp
#include <atomic>
#include <chrono>
#include <iostream>
#include <mutex>
#include <thread>

using Clock = std::chrono::steady_clock;   // monotonic clock

struct PlanarVelocity { double vx = 0, vy = 0, wz = 0; };

// Hand-off between the slow task layer and the fast control loop.
class SetpointBox {
 public:
  void Put(const PlanarVelocity& v, Clock::time_point valid_until) {
    std::lock_guard<std::mutex> lk(m_);
    sp_ = v;
    valid_until_ = valid_until;
  }
  PlanarVelocity Get(Clock::time_point now) const {
    std::lock_guard<std::mutex> lk(m_);
    if (now > valid_until_) return PlanarVelocity{};   // expired -> zero command
    return sp_;
  }
 private:
  mutable std::mutex m_;
  PlanarVelocity sp_;
  Clock::time_point valid_until_{};
};

int main() {
  using namespace std::chrono_literals;
  SetpointBox box;
  std::atomic<bool> run{true};

  std::thread control([&] {
    auto next = Clock::now();
    const auto period = 10ms;               // teaching value: 100 Hz
    int tick = 0;
    while (run.load()) {
      next += period;                       // absolute schedule, no drift
      PlanarVelocity sp = box.Get(Clock::now());
      if (tick++ % 20 == 0) std::cout << "vx=" << sp.vx << "\n";
      std::this_thread::sleep_until(next);
    }
  });

  box.Put({0.3, 0, 0}, Clock::now() + 100ms);   // valid for 100 ms only
  std::this_thread::sleep_for(300ms);
  run = false;
  control.join();
}
```

输出为 `vx=0.3` 然后 `vx=0`：第一次打印时设定值有效；200 ms 后（已过 100 ms 有效期）自动回到 0。注意这个例子表达的是**机制**：设定值带有效期、下层自治、下层使用单调时钟、周期用绝对时间推进。生产环境还需要：对过期做"受控减速"而不是瞬间置 0、记录事件、对 `Get` 做无锁或短锁优化。

## 10. 反模式

| 反模式 | 后果 |
|---|---|
| 控制周期里同步调用规划/网络 | 抖动、失稳 |
| 设定值没有有效期 | 上层死了，机器人保持最后速度 |
| 下层信任上层、不做限幅 | 上层 bug 直接变成物理危险 |
| 规划和控制共享一把大锁 | 优先级反转 |
| 上层恢复后自动续跑陈旧任务 | 过期任务被执行 |
| 层间用"状态位轮询"代替事件 | 浪费 CPU，延迟不确定 |
| 把安全逻辑只放在 AI/规划层 | 一旦该层失效，没有后备 |
| 层与层之间传递裸指针/共享可变对象 | 隐蔽的数据竞争 |

## 11. 面试问答

**Q1. Why did you separate task planning from real-time control?**

> They live on different time scales and have different failure modes. Planning may take hundreds of milliseconds and is not deterministic; control must run on a fixed period. If I put them in one loop, a slow plan would stall control. So the upper layer hands down setpoints with a validity time, and the lower layer runs on its own clock and stays safe if the upper layer goes quiet.

译：时间尺度和故障模式不同；上层给带有效期的设定值，下层自治。

追问：接口长什么样？→ 设定值 + `valid_until`、来源、序号；反馈带 `seq_acked`、跟踪误差、饱和标志（教学设计；如有实际接口，用实际的）。

**Q2. What happens when the upper layer crashes while the robot is moving?**

> The setpoint expires and a watchdog fires. The control layer then decelerates in a controlled way and stops; it does not wait for the upper layer. After recovery, the upper layer must explicitly re-confirm before any motion continues, so an old task cannot restart by itself.

**Q3. What is the difference between a validity time and a watchdog?**

> A validity time says when a particular command stops being valid. A watchdog says that the sender has stopped showing signs of life. I use both: the first protects against stale commands, the second against a dead sender.

**Q4. How does delay affect a control loop?**

> A delay adds phase lag of omega times tau at the crossover frequency. With a 20 rad/s crossover, a 50 ms delay costs about 57 degrees, which can eat nearly the whole phase margin. (Numbers here are a textbook example.) That's why I keep unbounded delays — networks, planners, synchronous IPC — out of the control loop.

**Q5. How do you choose the watchdog timeout?**

> From the maximum allowed stopping distance: the distance travelled during the timeout plus the braking distance must be below the safety margin. So I derive it from maximum speed and braking deceleration instead of guessing.

**Q6. Where does your safe-execution chain sit among the layers?**

> Between the task layer and the motion-control layer. Anything the task layer decides has to pass through it before it reaches an actuator. The control layer still keeps its own limits as a second line of defence.

## 12. 本章要点速记

1. 时间尺度金字塔：任务（秒～分钟）→ 协同安全 → 路径（1～20 Hz）→ 运动控制（50～200 Hz）→ 伺服（kHz），数值为通用经验示意。
2. 分层理由：时间尺度、故障隔离、可替换、可验证、安全边界。
3. 层间接口是契约：带有效期的设定值、来源、序号；异步，不在控制周期内等待上层。
4. 延迟吃相位裕度：$\phi=\omega_c\tau$。
5. 速率转换：ZOH + 加速度限幅最常用；降采样在状态管理里做。
6. 有效期防过期命令，看门狗防发送者死亡；失联后动作预先确定且受控减速。
7. 看门狗超时由"最大停车距离"反推。
8. 控制线程：绝对时间周期、高优先级、禁阻塞、监控抖动。
9. 下层不信任上层，保留最后一道限幅。
