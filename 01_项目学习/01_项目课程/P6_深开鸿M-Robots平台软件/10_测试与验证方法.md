## 1. 要解决什么问题

平台软件的特点让它"难测"：

1. **依赖硬件**：每次测试都接真机，慢且危险。
2. **时间相关**：行为依赖时间（超时、陈旧），真实时间让测试不稳定。
3. **分布式**：多进程多设备，竞态与顺序问题偶发。
4. **安全相关**：最重要的恰恰是"异常情况下的行为"，而正常运行时它们很少出现。

所以测试要解决的核心问题是：**如何让异常路径也能被稳定、重复地触发和检查。** 答案是：可测性设计（把硬件、时间、网络隔离成可替换的接口）+ 分层测试 + 故障注入 + 回放。

## 2. 测试金字塔

```text
                    ▲  少而贵
                   ╱ ╲
                  ╱真机╲        真机验证：限速、架空、逐步放开
                 ╱───────╲
                ╱ 半实物/  ╲     HIL/SIL：真实固件或仿真器 + 真实平台软件
               ╱  联调环境   ╲
              ╱───────────────╲
             ╱  集成测试(多模块) ╲  适配器+状态管理+策略链，用假驱动与假时钟
            ╱─────────────────────╲
           ╱  契约/属性/模糊测试      ╲  对接口和规则的系统化检查
          ╱─────────────────────────────╲
         ╱         单元测试               ╲  单个类/函数，毫秒级，成千上万
        ▼  多而便宜
```

| 层 | 测什么 | 替身 | 速度 |
|---|---|---|---|
| 单元 | 校验规则、运动学公式、限幅、状态机 | 无需硬件，注入时钟 | 毫秒 |
| 契约/属性/模糊 | 所有适配器满足接口约定；规则对任意输入不崩溃且遵守不变量 | 假驱动 | 秒 |
| 集成 | 命令从映射器到适配器到假驱动；状态从假驱动到状态管理到策略 | 假驱动 + 假时钟 + 假总线 | 秒 |
| 联调（SIL/HIL） | 真实进程间通信、M-DDS、OH 环境；固件/仿真器在环 | 仿真或硬件在环 | 分钟 |
| 真机 | 整机行为、实际延迟、电气、机械 | 真机（受限） | 时间长，风险高 |

原则：**能在低层测的，不放到高层测**；高层测试只验证低层无法覆盖的整体性质（时序、集成、物理）。

## 3. 单元测试：校验器与策略引擎

### 3.1 要测什么

对 05 章的 `SignalValidator`：

| 用例 | 目的 |
|---|---|
| NaN 输入 → Invalid | 有限值检查 |
| 刚好在陈旧上限 → Valid；多 1 ns → Stale | **边界值** |
| 时间戳相同/倒退 → Suspect | 单调性 |
| frame 不符 → Invalid | 坐标声明 |
| Invalid 样本不更新历史 | 副作用约束 |
| 变化率刚好在上限 | 边界值 |

对 08 章的 `PolicyEngine`：

| 用例 | 目的 |
|---|---|
| 每条规则单独通过/拒绝/修改 | 规则正确性 |
| 规则顺序：限幅在围栏之前 | 顺序性质 |
| 任何规则拒绝则整体拒绝 | deny-wins |
| `stop` 在 EStop/Manual 模式下仍被接受 | 安全动作永远可达 |
| 规则抛异常/超时 → 拒绝 | 默认拒绝 |
| 同一输入重复评估结果相同 | 确定性（可重放的前提） |
| 修改后的命令在能力上限内 | 不变量 |

### 3.2 示例（教学代码，已编译通过）

用极简的断言宏，不依赖框架；项目里更常用 gtest 风格框架，结构一致。

```cpp
#include <cmath>
#include <cstdio>
#include "validator.hpp"   // the SignalValidator from chapter 05 (without main)

static int g_fail = 0;
#define CHECK(cond) do { if (!(cond)) { \
  std::printf("FAIL line %d: %s\n", __LINE__, #cond); ++g_fail; } } while (0)

static SignalValidator Make() {
  return SignalValidator({-1.0, 1.0, 5.0, 50'000'000, "base_link"});
}
constexpr int64_t kT0 = 1'000'000'000;

void TestNaNIsInvalid() {
  auto v = Make();
  CHECK(v.Check({std::nan(""), kT0, "base_link"}, kT0 + 1).validity == Validity::Invalid);
}
void TestStaleBoundary() {
  auto v = Make();
  // exactly at the limit is still Valid; one nanosecond more is Stale
  CHECK(v.Check({0.1, kT0, "base_link"}, kT0 + 50'000'000).validity == Validity::Valid);
  auto w = Make();
  CHECK(w.Check({0.1, kT0, "base_link"}, kT0 + 50'000'001).validity == Validity::Stale);
}
void TestNonMonotonicStamp() {
  auto v = Make();
  v.Check({0.1, kT0 + 10'000'000, "base_link"}, kT0 + 11'000'000);
  CHECK(v.Check({0.1, kT0 + 10'000'000, "base_link"}, kT0 + 12'000'000).validity
        == Validity::Suspect);
}
void TestWrongFrame() {
  auto v = Make();
  CHECK(v.Check({0.1, kT0, "imu_link"}, kT0 + 1).validity == Validity::Invalid);
}

int main() {
  TestNaNIsInvalid(); TestStaleBoundary();
  TestNonMonotonicStamp(); TestWrongFrame();
  std::printf(g_fail ? "FAILED\n" : "all passed\n");
  return g_fail;
}
```

这些测试的价值在于**边界值**（刚好等于上限、多 1 ns）：边界错误（`<` 与 `<=`）是校验逻辑里最常见的 bug。

### 3.3 测试命名与组织

一个测试只验证一件事，名字写成"条件_期望结果"（如 `StaleBoundary_OneNsOver_IsStale`），失败时一眼知道哪里坏了。

## 4. 可测性设计：注入时钟与驱动缝

### 4.1 注入时钟

如果校验器内部直接读系统时间，测试就必须 `sleep` 来等超时：慢且不稳定。解决：**时间作为参数传入**（如 05 章的 `Check(sample, now_ns)`、08 章的 `Context.now_ns`），或注入一个 `IClock` 接口：

```cpp
class IClock {
 public:
  virtual ~IClock() = default;
  virtual int64_t NowNs() const = 0;
};

class FakeClock : public IClock {
 public:
  int64_t NowNs() const override { return now_; }
  void Advance(int64_t ns) { now_ += ns; }
 private:
  int64_t now_ = 0;
};
```

测试里调用 `clock.Advance(60'000'000)` 瞬间"过了 60 ms"，超时、看门狗、陈旧判断都能毫秒级、确定性地测。

### 4.2 驱动缝

03 章的 `IWheelDriver` 就是驱动缝：真实实现访问 CAN；测试用 `FakeWheelDriver` 记录收到了什么命令，供断言：

```text
适配器.SetVelocity({0.3,0,0.5}) → FakeWheelDriver 收到 {4, 8} → 断言
```

### 4.3 为什么这是架构问题而非测试技巧

"能不能测"由接口设计决定。平台的统一能力接口、时间注入、驱动缝，本身就是为可测性设计的；这也是它们和"跨硬件复用"同根：**把变化的东西放在接口后面。**

## 5. 契约测试、属性测试与模糊测试

### 5.1 契约测试

在 04 章第 9 节已列出：对每个适配器运行同一套测试。新增一种硬件时，只要通过契约测试，就有信心它能被上层无差别使用。

### 5.2 属性测试（property-based testing）

不是写具体输入，而是声明**对任意输入都应成立的性质**，由工具随机生成大量输入检验。适合：

| 性质 | 对象 |
|---|---|
| 往返一致：逆运动学再正运动学还原命令 | 运动学换算 |
| 修改后命令的幅值不超过能力上限 | 限幅规则 |
| 对任意提案，引擎不崩溃且输出裁决是三种之一 | 策略引擎 |
| 对同一输入重复评估，输出相同 | 确定性 |
| 输出的轮速向量长度等于轮数 | 适配器 |
| 对任意样本序列，校验器不抛异常 | 状态校验 |

### 5.3 模糊测试（fuzzing）

向解析器/反序列化/提案入口喂随机或变异的字节流，看是否崩溃、越界或进入非法状态。对**暴露在网络上的入口**（提案接收、能力注册、M-DDS 订阅回调）尤其重要，因为它们处理的是不可信输入。

### 5.4 变异测试（mutation testing）一句话

自动对代码做小改动（把 `<=` 改成 `<`），看测试是否能发现。如果测试都过，说明测试不够强。可作为"评估测试质量"的手段。

## 6. 联调：分层集成

联调的原则是**一次只引入一个真实的东西**：

| 阶段 | 真实的 | 假的 | 发现的问题类型 |
|---|---|---|---|
| A | 适配器 + 状态管理 | 驱动、时钟 | 逻辑错误 |
| B | + 真实的 OH 进程与 IPC | 驱动、硬件 | 线程、IPC、权限 |
| C | + M-DDS 跨进程/跨设备 | 硬件 | QoS 匹配、发现、时间同步 |
| D | + 真实驱动与总线（机器人架空或使能关闭） | — | 协议、符号、单位 |
| E | + 整机落地、低速、限幅 | — | 动力学、延迟、真实反馈 |

好处：出问题时能快速定位在哪一层。如果一上来就整机联调，一个问题可能来自十个地方。

**分布式联调的检查清单**：

1. 发现与匹配：各端点是否按预期匹配（QoS 事件）；
2. 时间同步：各设备时间偏移是否在允许范围；
3. 频率与丢帧：状态消息 `seq` 是否连续；
4. 延迟：端到端时延分布（见第 9 节）；
5. 断线重连：拔网线、杀进程后是否自动恢复，状态是否一致；
6. 重启顺序：不同启动顺序（先设备后调度，或相反）都能工作。

## 7. 故障注入

### 7.1 为什么

安全相关代码的价值体现在异常情形。不主动制造异常，就不知道系统能否应对。**故障注入（fault injection）**就是在受控条件下人为制造故障。

### 7.2 故障注入矩阵（典型）

| 故障 | 注入点 | 方法 | 预期行为 |
|---|---|---|---|
| 丢包 | 驱动/DDS | 以概率 $p$ 丢弃 | 状态陈旧检测触发；命令超时；序号检测丢失 |
| 延迟/抖动 | 驱动/网络 | 随机延迟 | 陈旧判断、控制不失稳 |
| 重复 | DDS/命令 | 同一消息发两次 | 幂等去重 |
| 乱序 | DDS | 交换顺序 | 时间戳/序号检查、Suspect |
| 时钟跳变 | 时间源 | 向前/向后跳 | 单调时钟不受影响；同步状态标记 |
| 传感器冻结 | 驱动 | 一直返回同一个值 | 冻结检测 → Suspect |
| NaN/Inf | 驱动 | 注入非有限值 | Invalid，不进入控制 |
| 越界值 | 驱动 | 注入超范围数 | Invalid |
| 驱动错误返回 | 驱动 | 下 N 次返回 HardwareFault | 错误上报、进入安全状态 |
| 上层静默 | 命令源 | 停止发命令 | 看门狗 → 受控停车 |
| 校验器宕机 | 进程 | kill 进程 | 默认拒绝；执行端凭据过期 |
| 进程崩溃重启 | 任意服务 | kill -9 | 重启后状态/去重表/注册恢复；不重复执行任务 |
| 网络分区 | 网络 | 断开链路 | 设备离线判定；恢复后重新发现；不执行过期任务 |
| 能力描述错误 | 注册 | 注入错误上限 | 注册校验/自检发现 |
| 恶意提案 | 提案入口 | 越权、越界、伪造 id | 全部被拒并审计 |

### 7.3 一个故障注入装饰器（教学代码，已编译通过）

利用 03 章的驱动缝，用**装饰器模式**包裹任何驱动并注入故障：

```cpp
#include <random>
#include "capability_demo.hpp"   // IWheelDriver, DiffDriveAdapter, Status ... from chapter 03

// Decorator: wraps a real or fake driver and injects faults.
class FaultyDriver : public IWheelDriver {
 public:
  FaultyDriver(std::shared_ptr<IWheelDriver> inner, double drop_prob, unsigned seed)
      : inner_(std::move(inner)), drop_(drop_prob), rng_(seed) {}

  void FailNext(int n) { fail_remaining_ = n; }

  Status SendWheelSpeeds(const std::vector<double>& w) override {
    ++calls_;
    if (fail_remaining_ > 0) { --fail_remaining_; return Status::HardwareFault; }
    if (dist_(rng_) < drop_) { ++dropped_; return Status::Ok; }  // silently lost frame
    return inner_->SendWheelSpeeds(w);
  }
  int calls() const { return calls_; }
  int dropped() const { return dropped_; }

 private:
  std::shared_ptr<IWheelDriver> inner_;
  double drop_;
  std::mt19937 rng_;                       // fixed seed -> reproducible faults
  std::uniform_real_distribution<double> dist_{0.0, 1.0};
  int fail_remaining_ = 0, calls_ = 0, dropped_ = 0;
};
```

要点：

1. **固定随机种子**：同一个种子复现同一串故障，便于重现 bug。
2. **"静默丢帧"返回 Ok**：模拟现实里总线丢帧发送端并不知道——这正好检验上层是否依赖反馈（状态陈旧）而非"发送成功"。
3. 可以同样包裹时钟、DDS 订阅器、状态源。

### 7.4 在联调环境做故障注入

- 网络层：Linux 的流量控制工具（如 `tc netem`）可以对网卡加延迟、丢包、重复、乱序；
- 进程层：对服务发信号 kill、暂停（SIGSTOP）；
- 时间层：修改系统时间模拟 NTP 跳变；
- 具体工具在 OH 环境中的可用性需要核实：`【待你补全：OH 环境下实际使用的故障注入工具】`。

### 7.5 判定标准

故障注入不是"看会不会出问题"，而是**对每种故障预先写好期望行为**（上表最后一列），实际行为与期望不符才是缺陷。期望行为通常包括：不危险（进入安全状态）、可检测（有告警/事件）、可恢复（故障消失后自动恢复或需明确操作）、可追溯（有日志）。

## 8. 回放与事故复盘

### 8.1 要解决什么

现场出了异常，事后需要回答："当时系统看到了什么？为什么做了那个决定？"实时现场无法重现，所以要**记录输入，离线重放**。

### 8.2 确定性是前提

要重放得出同样的结论，决策代码必须是**确定性的纯函数**：

- 不直接读系统时间（时间作为输入记录下来）；
- 不使用未记录的随机数；
- 不依赖未记录的外部状态（配置、策略版本要一起记）；
- 不依赖线程调度顺序（或把顺序记录下来）。

08 章的策略引擎满足：`Evaluate(proposal, context)` 的输出仅取决于输入。

### 8.3 记录什么

| 记录 | 内容 |
|---|---|
| 输入流 | 状态样本（含 stamp）、提案、模式变化、能力快照 |
| 配置 | 策略版本、规则参数、校验阈值 |
| 输出 | 裁决、规则 trace、凭据、执行事件 |
| 环境 | 软件版本、时间同步状态 |

### 8.4 用途

1. **事故复盘**：把记录喂给离线引擎，得到同样的裁决，再逐条规则看原因。
2. **回归测试**：把历史上出过问题的场景固化成"黄金用例（golden cases）"，每次改规则都跑一遍，防止回退。
3. **策略变更影响评估**：用一周的真实提案流重放"新策略"，对比与旧策略的差异（哪些原本放行的现在拒绝，反之亦然）——这相当于策略的"灰度"。
4. **数据治理参数整定**：重放状态数据，调整陈旧/变化率阈值，统计误报率和漏报率。

### 8.5 手算：阈值评估

**教学示例**：回放 10,000 个状态样本，其中人工标注 120 个真正异常；新阈值下校验器标记了 150 个 Suspect，其中 108 个确为异常。
- 召回率（recall）$=108/120=90\%$；
- 精确率（precision）$=108/150=72\%$；
- 误报 $=150-108=42$ 个。
调严阈值则召回上升、误报也上升，需要在"漏掉真异常"与"频繁误报导致系统不可用"之间折中。（数字为示例。）

## 9. 性能与时延测量

### 9.1 测什么

| 指标 | 含义 |
|---|---|
| 命令路径时延 | 从提案提交到适配器下发（分段测：校验耗时、IPC 耗时、适配器耗时） |
| 状态路径时延 | 从传感器测量时间到上层可见 |
| 周期抖动 | 控制线程实际周期与期望周期的偏差分布 |
| 吞吐 | 每秒可处理提案数、消息数 |
| 资源 | CPU、内存、网络占用 |

### 9.2 看分位数而不是平均值

平均值会被正常值淹没，掩盖尾部。**手算（教学示例）**：20 个时延样本（ms）：
8, 9, 9, 10, 10, 10, 11, 11, 12, 12, 12, 13, 13, 14, 15, 16, 18, 22, 35, 120。

- 平均值 $=380/20=19$ ms；
- 中位数（p50，第 10 个）$=12$ ms；
- p95（最近秩法：$\lceil0.95\times20\rceil=19$ 个）$=35$ ms；
- p99/最大（第 20 个）$=120$ ms。

平均 19 ms 看起来不错，但最坏 120 ms 足以让看门狗误触发。**安全相关的时序要求关注尾部（p99、最大值）**。

### 9.3 测量方法

1. 在消息中带时间戳，在接收端比较（需要时间同步；同机比较用同一单调时钟最可靠）；
2. 在关键点打点（trace），事后统计；
3. 在长时间运行（浸泡测试，soak test）中观察是否有泄漏、延迟漂移、偶发尖刺。

CV 没有给出任何时延数据，面试时不要编造：`【待你补全：如果有实测的延迟/频率数据，写出来源和测量方法；没有就不要说具体数字】`。

## 10. 真机验证的安全流程

1. **架空/断使能**：先让轮子离地或电机不使能，只验证命令和反馈方向、符号、单位是否正确（麦轮符号、关节方向最容易错）。
2. **低限幅**：把速度、加速度上限调到最低，确认限幅有效。
3. **急停就位**：测试前确认硬件急停可用，手边有人。
4. **逐步放开**：速度、加速度、范围逐级上调，每级验证后再继续。
5. **围栏与场地**：先在空旷场地，设置软件围栏；再逐步引入障碍与多机。
6. **看门狗验证**：运行中故意中断上层，观察是否受控停车，测量实际停车距离，与计算值对比（07 章公式）。
7. **记录一切**：真机日志同时用于回放。
8. **回归**：每次改动固件/参数/规则，重复关键安全用例。

> 原则：**安全功能必须在真机上被证实有效**，而不仅仅是在仿真里通过。看门狗、限幅、围栏这类功能，要真的触发一次看它是否生效。

## 11. 验收标准与证据

"测试通过"需要一个可以对别人讲清楚的口径：

| 项 | 验收口径（教学示例） |
|---|---|
| 复用 | 契约测试对所有已支持适配器通过 |
| 状态 | 注入的每类坏数据都被标为非 Valid，且不进入控制 |
| 安全链 | 黄金用例集 100% 符合期望；所有旁路尝试被拒绝并有审计 |
| 故障 | 故障注入矩阵每项的期望行为得到验证 |
| 回放 | 记录的场景离线重算结果一致 |
| 真机 | 看门狗/限幅/围栏均实际触发验证过一次 |

面试里不要宣称"全部覆盖"，除非确实如此；更稳妥的表述是"我们覆盖了哪些类别，哪些仍主要靠人工/真机检查"。`【待你补全：你们的验收口径与实际覆盖情况】`

## 12. 面试问答

**Q1. How did you test the state-validation and policy logic?**

> I kept them as deterministic functions of their inputs — time is passed in rather than read from the system — so I could unit-test the boundaries: exactly at the staleness limit, one tick over, a repeated timestamp, a wrong frame, NaN. For the policy chain I tested each rule, the rule order, and the property that any rejection wins and that stop is always allowed. `【把实际做过的测试替换进去】`

译：把它们做成输入的确定性函数，时间作为参数，便于测试边界。

**Q2. How do you test code that depends on real hardware?**

> I put the hardware behind an interface. The adapter talks to a driver interface, and in tests that's a fake driver which records commands. For fault tests I wrap the fake in a decorator that drops, delays or fails calls with a fixed random seed, so any failure is reproducible. Then the hardware stage only checks what simulation cannot — signs, units, real latency.

**Q3. What is fault injection and which faults did you consider?**

> Deliberately creating faults in a controlled way to check the system's behaviour. I considered lost, delayed, duplicated and reordered messages, clock jumps, frozen or NaN sensors, driver errors, a silent upper layer, a crashed process and a network partition. For each, I define the expected safe behaviour in advance, and a deviation is the bug.

**Q4. How would you investigate a bad decision from yesterday?**

> Replay. The decision logic is deterministic, and I record its inputs — state samples, proposals, the policy version — so I can feed them back offline and see the rule trace that produced the decision. The same replay is useful for regression: incidents become golden test cases.

**Q5. How do you know latency is acceptable?**

> I look at the tail, not the average. In a toy example with a 19 ms mean, the worst sample can still be 120 ms, which would trip a watchdog. I measure by timestamps on the common clock and look at p95, p99 and the maximum. `【如无实测数据，不要说数字】`

**Q6. How do you verify the watchdog really works?**

> By triggering it on the real robot at low speed: stop the upper layer on purpose, measure the stopping distance, and compare it with the calculated distance from timeout, speed and braking deceleration.

## 13. 本章要点速记

1. 金字塔：单元 → 契约/属性/模糊 → 集成 → 联调 → 真机，能低层测就不上高层。
2. 可测性设计：时间注入、驱动缝、纯函数式决策。
3. 单元测试重边界值（等于上限、多一个单位）、顺序、副作用、确定性。
4. 契约测试保证"复用"；属性测试验证不变量；模糊测试守住不可信入口。
5. 联调一次只引入一个真实的东西。
6. 故障注入：先写期望行为再注入；固定随机种子便于复现。
7. 回放要求确定性；用于复盘、回归、策略影响评估。
8. 时延看 p95/p99/最大，不看平均。
9. 真机：架空 → 低限幅 → 急停就位 → 逐步放开 → 真正触发安全功能。
