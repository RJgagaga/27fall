# 11 故障案例库：14 个平台软件的典型故障，怎么定位、怎么修、怎么预防

> 一句话定位：面试官爱问 "Tell me about a bug you found" 和 "What went wrong and how did you debug it?"。这一章给出 14 个**平台软件里典型、真实会发生的故障**，每个都按"现象—根因—定位—修复—预防—怎么讲"整理，帮你建立排障思路和讲故事的素材库。

> **重要声明**：这些是**通用工程场景的典型案例**，用来训练分析能力，**不是 P6 项目的实测复盘**。面试时，请从中挑出你**真正遇到过**或能说明"我在设计时就是为了避免这个"的案例，并用你的真实经历替换细节。千万不要把别人的案例说成"我们遇到的"。可以这样安全地讲：*"A typical failure in this kind of system is ...; the design reason for X is to prevent it."* 你真正遇到的故障请记入：`【待你补全：你在 P6 中真实遇到并解决的 2–3 个问题（现象、根因、定位、修复、结果）】`。

## 1. 排障方法论

### 1.1 先分方向，再分层

平台软件的数据有两个方向：**命令向下**、**状态向上**。症状出现时先问：是"命令没到达/没生效"，还是"状态不对/不可信"？

```text
命令向下:  提案 → 校验 → 映射 → 适配器 → 驱动 → 总线 → 电机
状态向上:  电机/传感器 → 总线 → 驱动 → 适配器 → 状态管理 → 订阅者 → 任务层
```

**二分法**：在链路中间选一个观测点（例如适配器入口），看数据是否正确。正确 → 问题在下游；错误 → 问题在上游。每次折半。

### 1.2 五个固定问题

对任何故障，依次问：

1. **能复现吗？**（频率：必现/偶现/只在特定条件）
2. **哪一层先出现异常？**（看第一条异常日志的时间）
3. **时间对吗？**（时间戳、顺序、延迟、超时）
4. **坐标/单位对吗？**
5. **最近改了什么？**（配置、版本、部署顺序）

### 1.3 区分三类根因

| 类别 | 例子 | 特征 |
|---|---|---|
| 确定性逻辑 bug | 符号、单位、边界 | 必现，可用单元测试复现 |
| 时序/并发 bug | 竞态、死锁、抖动 | 偶现，与负载有关 |
| 环境/配置/分布式 | QoS 不匹配、时钟、网络 | 与部署有关，换环境表现不同 |

## 3. 案例 F1–F14

### F1 订阅方收不到状态：QoS 不兼容

- **现象**：任务层订阅 `robot/state`，看不到任何数据；而用抓包看，设备端确实在发。
- **根因**：设备端以 `BEST_EFFORT` 发布，订阅端默认 `RELIABLE`。请求—提供规则下，写端提供的可靠性弱于读端请求 → **不匹配**，中间件不建立连接，也不报错到业务层。
- **定位**：查看端点匹配状态/不兼容 QoS 事件；对比两端 QoS 配置；用工具列出 Topic 的写端、读端及其 QoS。
- **修复**：订阅端改为 `BEST_EFFORT`（状态类的正确选择），或写端提升到 `RELIABLE`（若业务需要）。
- **预防**：为每类 Topic 定义**统一的 QoS 配置档**（profile）集中管理；启动期自检匹配并告警；契约测试里加"QoS 兼容性"用例。
- **怎么讲**：*"A typical silent failure in DDS is incompatible QoS: the topic exists, the traffic exists, but the endpoints never match. I standardise QoS profiles per topic type and check matching at startup."*

### F2 位姿周期性跳变：墙上时钟被校时

- **现象**：机器人位姿估计每隔一段时间突然跳一下，或出现负的 dt 导致控制异常。
- **根因**：状态时间戳/周期计算用了系统墙上时钟（real-time），NTP 校时让时钟回拨或前跳几十毫秒。
- **定位**：日志里找 dt 异常（负值或极大值）；与系统校时事件对时；检查哪些代码调用了墙上时钟。
- **修复**：间隔、超时、陈旧判断改用单调时钟；跨设备对时通过专门的同步映射。
- **预防**：代码规范：禁止在周期/超时逻辑里使用墙上时钟；时间戳单调性检查（05 章）；故障注入"时钟跳变"用例（10 章）。
- **怎么讲**：*"Timestamps must be on a monotonic base for intervals; a wall clock that gets corrected by NTP makes dt negative."*

### F3 控制抖动：控制线程被阻塞

- **现象**：速度控制偶发抖动，示波器/日志显示控制周期有尖刺（例如期望 10 ms，偶尔 40 ms）。
- **根因**：控制线程里调用了**同步 IPC**（对端慢）、打印日志（落盘）、分配大内存，或等待被低优先级线程持有的锁（优先级反转）。
- **定位**：在每个周期记录开始/结束时间并统计周期分布；用调试/追踪工具查看线程阻塞点；逐一注释可疑调用做二分。
- **修复**：控制线程内只做计算与非阻塞的数据交换；日志、IPC 放到异步线程；共享数据用短临界区或原子指针交换；调整优先级并避免优先级反转（优先级继承锁，视平台支持）。
- **预防**：设计规则（07 章第 8 节）；周期抖动监控与告警；在测试里设置周期抖动门限。
- **怎么讲**：*"Control jitter is almost always a blocking call in the loop. I measure the period distribution first, then bisect the calls inside the loop."*

### F4 传感器掉线后机器人继续"平稳"运动：缺少陈旧检测

- **现象**：某个反馈（例如轮速）线断了，机器人没有报警，反而继续按旧状态运动，直到撞到东西。
- **根因**：驱动层在读取失败时返回**上一次的值**（或 0），状态管理没有年龄/有效性检查，控制器认为反馈正常。
- **定位**：对比反馈时间戳与当前时间；看反馈的序号 `seq` 是否停止增长；看值是否完全不变（冻结）。
- **修复**：读失败不返回旧值而是返回错误；状态管理增加陈旧与冻结检测；陈旧后按分级降级（保持→限速→停车）；策略校验拒绝依赖陈旧状态的动作。
- **预防**：05 章的有效性规则；故障注入"传感器冻结/掉线"；"不允许静默保持旧值"写入驱动适配器规范。
- **怎么讲**：*"The dangerous failure is the one that looks normal. Staleness is a first-class property in my state model, so downstream code can't mistake an old value for a live one."*

### F5 横移变旋转：麦轮符号表错

- **现象**：下发纯横移命令 $v_y$，机器人却原地旋转（或前进变斜行）。
- **根因**：麦轮四个轮的正方向、安装方向（滚子方向 X 型/O 型）与运动学公式默认假设不一致，符号表错了一个或几个。
- **定位**：架空车轮，逐个轮子下发小速度，观察实际旋转方向与预期是否一致；对照"纯前进/纯横移/纯旋转"三个基础命令的预期轮速符号。
- **修复**：把每个轮子的符号和顺序做成**配置**，按标定结果修正；加上往返一致性测试（04 章）。
- **预防**：新底盘接入的标准流程中必含"架空逐轮符号测试"；适配器的单元测试覆盖三个基础运动。
- **怎么讲**：*"Mecanum sign errors turn translation into rotation. I verify the three basic motions with the wheels off the ground before anything else."*

### F6 设备重连后执行了过期任务

- **现象**：设备断网 10 分钟后恢复，立即执行了 10 分钟前的"前进"任务。
- **根因**：任务 Topic 用了 `TRANSIENT_LOCAL`，重连后历史样本被回放；任务没有有效期，设备端也没有幂等/去重。
- **定位**：对比任务 `issued_at` 与执行时间；查看设备端去重表；检查 Topic QoS。
- **修复**：任务带 `valid_until`，设备执行前检查；DDS `Lifespan` 使样本过期；设备端以 `task_id` 去重；重连后先同步状态再接收任务，并要求上层显式确认恢复。
- **预防**：08 章幂等 + 有效期 + 凭据时效；故障注入"网络分区后恢复"用例。
- **怎么讲**：*"Durable QoS replays history to late joiners, which is useful for registration but dangerous for commands. Commands need a validity time and idempotent IDs."*

### F7 策略校验被旁路

- **现象**：审计日志里出现设备在运动，但没有对应的提案/决策记录。
- **根因**：为方便调试，保留了一个直连适配器的接口（测试服务或旧版代码路径），生产环境未关闭。
- **定位**：对比设备执行事件与提案记录，找出没有 `proposal_id` 的命令；检查谁拥有适配器的访问权限。
- **修复**：适配器只接受带有效凭据的命令；调试接口在生产构建中移除或需要特殊授权并记录；权限收紧。
- **预防**：08 章"唯一通道"原则；定期做"旁路审计"：所有执行事件必须能关联到提案；构建配置区分调试/生产。
- **怎么讲**：*"A gate is only as strong as its bypasses. I make the actuator side reject commands without a valid ticket, and I audit every execution against a proposal ID."*

### F8 速度差 1000 倍：单位错误

- **现象**：下发 0.3 m/s，机器人以约 0.0003 或 300 倍的速度动作。
- **根因**：某适配器将 mm/s 当作 m/s，或把转速（rpm）与 rad/s 混淆；减速比被重复乘或遗漏。
- **定位**：在适配器入口和出口各打印一次；用已知输入（例如纯前进 0.3）手算期望轮速并对比；检查配置里的单位注释。
- **修复**：接口固定 SI 单位；适配器在入口处唯一一次转换；字段名带单位后缀（`_mps`、`_rad`）；配置校验。
- **预防**：契约测试的往返一致性；能力描述里的范围检查能发现数量级错误（超大值被限幅或拒绝）。
- **怎么讲**：*"Unit errors are cheapest to catch at interface boundaries, so I put units in field names and test against hand-computed values."*

### F9 偶发整体卡死：回调内加锁 + 同步调用死锁

- **现象**：系统运行数小时后某个服务无响应，其他服务调用它超时。
- **根因**：服务内部在持有锁 A 的情况下发起对另一个服务的**同步 IPC**，而对端又回调到本服务，需要锁 A；形成环路等待（死锁）。或者回调线程与调用线程以相反顺序获取两把锁。
- **定位**：对卡死进程抓线程栈（所有线程的调用栈）查看谁等谁；画等待图找环。
- **修复**：禁止在持锁时做阻塞调用；统一锁顺序；回调只投递事件到队列，由拥有者线程处理；设置 IPC 超时。
- **预防**：编码规范；静态/动态检测（线程检测工具）；压力测试与浸泡测试。
- **怎么讲**：*"Deadlocks usually come from holding a lock across a call you don't control. I keep callbacks light and never call out while holding a lock."*

### F10 看门狗误停或不停：超时取值不当

- **现象**：（a）网络稍有抖动机器人就频繁停车；（b）上层死掉后机器人继续冲了很远。
- **根因**：（a）超时短于合理的抖动上限；（b）超时过长，或看门狗被"任何消息"喂狗，包括无关的心跳。
- **定位**：统计命令到达间隔的分布，看 p99 与超时的关系；检查"喂狗"的触发条件；真机测试实际停车距离。
- **修复**：由停车距离反推上限（04 章 7.2），由抖动 p99 确定下限，在两者之间取值；只有**有效的新命令**才喂狗；分级降级而非一刀切。
- **预防**：参数文档化并由公式生成；故障注入"上层静默"用例；真机验证实际停车距离。
- **怎么讲**：*"The watchdog timeout is bounded from above by stopping distance and from below by network jitter; I don't guess it."*

### F11 能力声明与实际不符

- **现象**：策略校验放行了命令，设备却无法执行或超限运行；或者一个未授权设备注册后获得任务。
- **根因**：能力描述由硬编码/复制粘贴而来（例如把另一型号的上限抄过来），没有与设备自检对照；注册没有认证，任何节点都能声明能力。
- **定位**：对比能力描述与设备手册/实测；检查注册来源与审计记录。
- **修复**：能力来自设备配置与自检；注册校验（版本、范围合理性）并认证；策略仍以设备侧限幅做最后保护。
- **预防**：接入新设备的验收清单含"能力描述核对"；注册审计；纵深防御。
- **怎么讲**：*"Policy is only as good as the capability data it reads, so registration is validated and authenticated, and the adapter clamps independently."*

### F12 障碍物整体偏移：外参方向用反

- **现象**：雷达看到的障碍物位置与真实位置相差固定偏移或镜像；机器人要么撞到"看不见"的障碍，要么避开不存在的物体。
- **根因**：传感器到 base 的外参把 $T^{base}_{sensor}$ 与 $T^{sensor}_{base}$ 弄反，或欧拉角顺序错。
- **定位**：用一个已知位置的物体（例如摆在正前方 1 m）看点云出现在哪里；单独测试纯平移、纯旋转外参。
- **修复**：统一命名约定（`T_target_source`），在状态管理中集中应用外参；加单元测试验证已知点变换。
- **预防**：05 章的坐标规则；把外参作为带版本的配置并有校验示例点。
- **怎么讲**：*"Frame bugs hide because every number looks plausible. I test with a known object at a known place."*

### F13 集群上电后很久才互相发现：多播与发现风暴

- **现象**：20 台设备同时上电，需要几十秒甚至更久才互相发现，期间任务分发失败；Wi-Fi 下尤其明显。
- **根因**：无线网络对多播支持差/丢包；发现流量集中爆发；每个参与者与所有其他参与者交换端点信息。
- **定位**：抓包看发现报文的重传与丢失；统计发现完成时间随设备数的变化。
- **修复**：改用静态对等列表或发现服务器；错开启动；通过 Partition/Domain 切分；调整发现周期。
- **预防**：规模测试（逐步增加设备数）；在文档里写明推荐的组网方式。
- **怎么讲**：*"Discovery cost grows roughly with the square of participants, and multicast is unreliable on Wi-Fi, so I would test scaling early and consider a discovery server."*

### F14 回执丢失后重发，机器人多走一段

- **现象**：一次"前进 0.5 m"，网络回执丢失，调度器超时重发，机器人最终走了 1.0 m。
- **根因**：动作是**相对动作**且执行端没有幂等去重；"至少一次"重发造成重复执行。
- **定位**：对比 `proposal_id`，发现同一个提案被执行了两次；查看去重表是否存在。
- **修复**：设备端按 `proposal_id` 去重；动作类型改为绝对目标（"到达 x=2.0"）；未知结果时先读状态再决定是否重提。
- **预防**：08 章 11.2；故障注入"回执丢失"用例；相对动作类型默认不允许重试。
- **怎么讲**：*"Distributed systems can't tell a lost command from a lost acknowledgement, so I assume at-least-once delivery and make execution idempotent."*

## 4. 排障需要的可观测性

| 手段 | 记录什么 | 对应故障 |
|---|---|---|
| 结构化日志 | 时间戳（单调 + 墙上）、模块、设备、提案 id、规则 trace | 全部 |
| 序号与时间戳 | 每条状态/命令带 `seq`、`stamp` | F2 F4 F6 F13 |
| 周期统计 | 控制周期实际间隔与执行时间分布 | F3 F10 |
| 匹配状态/QoS 事件 | 端点匹配、不兼容事件、存活租约丢失 | F1 F13 |
| 线程栈快照 | 卡死时全部线程调用栈 | F9 |
| 审计链 | proposal → decision → execution → feedback | F6 F7 F14 |
| 健康状态 | 每设备在线、陈旧、错误计数 | F4 F11 |
| 抓包 | 网络层行为 | F1 F13 |
| 录制与回放 | 现场输入 | 全部（复盘） |

> 日志也有成本：控制线程里同步写日志会引发 F3。日志应异步、有速率限制、关键事件用事件计数器。

## 5. 如何把案例讲成 STAR

模板（英文口述 60–90 秒）：

- **S**ituation：一句话说明系统与背景（*"On a multi-robot platform, state from several sensors feeds the motion layer."*）
- **T**ask：你的责任（*"I was responsible for making the state consistent and trustworthy."*）
- **A**ction：具体做了什么，**2–3 个关键动作**，包含诊断方法（*"I traced timestamps, found X, changed Y, added test Z."*）
- **R**esult：结果与量化/定性证据；**没有数字就不要编**（*"After that, the issue didn't reappear in later runs; I also added a regression test."*）
- **Learning**：学到了什么，如何影响后续设计。

例子（F4，改写为"设计动机"版本，真实性以你的经历为准）：

> Situation: In a platform that feeds sensor state into motion control, one risk is a sensor that fails silently. Task: I was asked to give the motion and task layers a state they can trust. Action: I made timestamps and validity part of every state value, added staleness and frozen-value checks, and defined what each consumer must do when a value is stale. Result: downstream code no longer mistakes an old value for a live one, and the policy check can reject actions that depend on stale state. Learning: the dangerous failure is the one that looks normal.

译：当传感器静默失效是风险；我让时间戳与有效性成为每个状态量的一部分，加入陈旧与冻结检测并规定下游行为；结果是下游不会把旧值当作实时值。

## 6. 面试问答

**Q1. Tell me about a difficult bug you debugged.**

> `【用你真实的经历回答。】` If I have to describe a class of problem rather than one incident: inconsistent state between sensors, where timing or frames didn't line up, so the controller reacted to something that wasn't true. My approach is to split the system into the command direction and the state direction, find the first layer where the data goes wrong, and then check time, frame and units at that point.

追问：你怎么确认修好了？→ 加回归测试（黄金用例或故障注入用例），在真机上重复触发条件。

**Q2. How do you debug something that happens once in a few hours?**

> I add observability first — sequence numbers, timestamps and period statistics — and keep the system running with recording on, so when it happens I can replay the inputs. Intermittent problems are usually timing, concurrency or environment, so I look for blocked threads, lock orders and network conditions, and I try to reproduce it with fault injection and a fixed seed.

**Q3. What is the most dangerous kind of failure in a robot platform?**

> The silent one that looks normal: stale data presented as live, a wrong unit that is still in range, or a gate that can be bypassed. They don't crash anything; they just make the robot confidently do the wrong thing. That's why I make validity explicit and audit every execution against an approved proposal.

**Q4. What went wrong when you first mapped commands to hardware?**

> `【如实回答。】` A typical early problem is sign and unit conventions per wheel or joint, so I validate the three basic motions with the wheels off the ground, and I made sign tables configuration rather than code.

**Q5. How do you stop the same bug from coming back?**

> By turning it into a test: a golden case for a policy decision, a fault-injection case for a failure mode, or a contract test for an adapter. A fix without a test is only a hope.

## 7. 本章要点速记

1. 排障先分方向（命令/状态），再二分分层，一次引入一个观测点。
2. 五个固定问题：复现、哪层先错、时间、坐标/单位、最近改动。
3. 三类根因：确定性逻辑、时序并发、环境/配置/分布式。
4. 14 个典型故障：QoS 不兼容、墙上时钟、控制线程阻塞、无陈旧检测、麦轮符号、过期任务重放、策略旁路、单位错误、死锁、看门狗取值、能力声明不实、外参反向、发现风暴、非幂等重发。
5. 最危险的是"看起来正常"的静默故障。
6. 每个修复要变成一个测试。
7. 案例是通用素材，讲给面试官时要用你真实的经历替换。
