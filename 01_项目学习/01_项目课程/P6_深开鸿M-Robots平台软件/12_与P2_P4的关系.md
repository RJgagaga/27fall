## 2. 共通的思想：决策与执行之间的边界

三个项目在"谁决策、谁执行、怎样保证决策不会直接伤害物理世界"上有同一个结构：

```text
        决策方（可能不确定、可能出错、可能很聪明）
              │  结构化的"请求/提案"  （不是直接命令）
              ▼
        ┌─────────────────────┐
        │  边界：校验·约束·降级 │   ← 默认拒绝；基于可信状态
        └─────────────────────┘
              │  受约束的命令
              ▼
        执行方（自带限幅·看门狗·状态机·人工优先）
              │
              ▼
        物理世界 ──▶ 状态/反馈 ──▶ 回到决策方（闭环、可追溯）
```

六条共通原则：

1. **提议与执行分离**：决策方只能请求，不能直接驱动。
2. **请求是结构化、受约束的**（枚举 + 数值 + 单位 + 有效期），不是自由指令。
3. **执行端不全信上层**：有自己的限幅、阈值、状态机、超时。
4. **人工/安全优先**：人工覆盖、急停高于自动决策。
5. **状态要可信、可追溯**：时间戳、来源、置信度/有效性。
6. **闭环**：结果回到决策方，使用"状态证据"而不是"发送成功"。

规模不同，严谨程度不同：P4 是单人小系统，边界较轻；P6 是平台级，边界需要身份、凭据、审计、分布式语义。

## 3. P2 与 P6 的关系

### 3.1 P2 是一个具体机器人上的"命令 → 轮速 → 反馈"实例

P2 里你做的底盘链路（CV 事实）：

```text
机体速度命令 (v, ω) → 差速运动学 → 左右轮目标速度 → PID（编码器反馈）→ CAN → 电机
                                              ▲                           │
                                              └────── 编码器反馈 ─────────┘
                                   轮子运动 → 里程计（遥操作与自主两种模式）
```

P6 的 03/04 章里：

```text
统一命令 PlanarVelocity → 适配器(差速/麦轮…)内的运动学 → 轮速 → 驱动 → 总线
```

可以看到 **P2 的"差速运动学 + 轮速目标"就是 P6 差速适配器内部做的事**；区别在于抽象层次：

| 方面 | P2 | P6 |
|---|---|---|
| 范围 | 一台具体机器人，一个固定接口 | 多种硬件，需要统一接口 |
| 命令接口 | 自己决定的 ROS2 话题/消息 | 统一能力接口 + ROS/ROS2 映射 |
| 运动学 | 差速（写死或参数化） | 差速、麦轮、阿克曼等多适配器 |
| 状态 | 编码器 → 里程计 | 多源状态标准化（时间/坐标/有效性） |
| 安全 | 限幅、遥操作/自主模式 | 提案→校验→执行→回传 |

**怎么讲**："In the Future Power internship, I built the chain for one robot — body velocity to wheel targets, PID with encoder feedback, odometry. At Kaihong the question was how to make that kind of code independent of the particular hardware, which led to the capability model and the adapters."（P2 先做具体，P6 做抽象。时间顺序也对：P2 在 2026.03–05，P6 在 2026.06 之后。）

### 3.2 两个具体的对照点

**(1) 差速运动学**：P2 与 03 章 8.1 完全同一组公式 $v_{L,R}=v\mp\omega L/2$。面试官若追问 P6 里的差速，你可以用 P2 的真实经验作底，说"the kinematics are the same; in the platform they live inside an adapter behind a common interface"。

**(2) 遥操作与自主两种模式**：P2 的轮子运动要同时服务遥操作和自主。在 P6 里这个"来源冲突"被一般化为**模式 + 优先级 + 所有权**（08 章 5.4、5.8）：遥控优先时拒绝自主提案，或自主提案要显式接管。P2 里你体验到的"两种来源同时给底盘命令"的问题，正是平台层做仲裁的动机。

### 3.3 P2 的"限幅、反馈"思想在 P6 的位置

- 轮速 PID 的输出饱和（P2/P1/P3 都有）与 03 章"适配器最后一道限幅"同源；
- 编码器反馈 → 里程计，是 05 章状态管理要标准化的典型数据（时间戳与坐标一致性）；
- ROS2-CAN 链路上的"命令超时"概念对应 07 章的有效期与看门狗。

## 3.4 对照：P2 的看门狗/限幅与 P6 的命令看门狗是同一件事吗

表面上相似，实际层次不同，面试时可以分清楚：

| 维度 | P2（单机器人底盘） | P6（平台命令网关） |
|---|---|---|
| 触发条件 | 遥操作心跳超时、遥控信号丢失 | 命令在有效期内未收到新值（本项目约 200 ms，连续 2 次判定） |
| 动作 | 目标速度置零，PID 积分清零，平滑减速 | 目标置零并减速，回执写 TIMEOUT，健康降级 |
| 位置 | 控制链路内部，靠近驱动 | 执行网关，对所有设备类型统一 |
| 依据 | 车速、减速度、场地 | 设备档位里的最大速度、制动距离、下发周期 |
| 可复用性 | 针对这台底盘调好 | 参数随设备类型从配置加载，逻辑统一 |

**关键洞察**：P2 里"积分清零"是控制器细节；到了 P6，平台不知道每个设备内部的控制器长什么样，只能规定接口契约（超时必须停、停必须平滑、回执必须出），这就是"能力模型 + 契约测试"的价值。一个在 P2 里手写的保护，在 P6 里变成了所有适配器必须通过的一条测试。

## 4. P4 与 P6 的关系

### 4.1 P4 是 P6 思想的"微缩版"

| P4 的元素（CV 事实） | P6 的对应 | 含义 |
|---|---|---|
| 观测带**置信度与时间戳** | 状态带 stamp 与有效性（05 章） | 数据要自带可信度信息 |
| 决策链有**规则快速通道**处理极端状态 | 策略校验的确定性规则；反应式安全层 | 极端情况不等 Agent 慢速推理，由确定性规则先行 |
| 向执行层给出**结构化建议或受约束的请求** | 动作提案（08 章第 3 节） | 决策方只能提议 |
| 设备侧**水泵状态机**，**独立起停阈值** | 执行端自保护、迟滞 | 执行端有自己的稳定闭环 |
| **人工优先覆盖** | 模式检查、人工模式拒绝自主提案 | 人高于自动 |
| 统一为**可追溯的系统状态** | 审计链与状态管理 | 事后能解释 |
| 通过 Web 交互与设备侧执行闭环 | 状态回传、闭环 | 结果回到决策方 |

### 4.2 迟滞（hysteresis）：独立启停阈值为什么重要

P4 的水泵控制："soil-moisture-driven pump state machine ... with independent start/stop thresholds and manual-priority override for a stable local closed loop"。

**问题**：如果只有一个阈值 $\theta$（湿度 $<\theta$ 开泵，$\ge\theta$ 关泵），湿度在阈值附近有测量噪声，水泵会频繁开关（chatter），损伤泵、浪费水。

**迟滞方案**：开泵阈值 $\theta_{on}$、关泵阈值 $\theta_{off}$，且 $\theta_{on}<\theta_{off}$：

$$\text{state}_{k+1}=\begin{cases}\text{ON}, & \text{if } m_k<\theta_{on}\\ \text{OFF}, & \text{if } m_k>\theta_{off}\\ \text{state}_k, & \text{otherwise}\end{cases}$$

**手算（教学示例数值，非 P4 实测）**：$\theta_{on}=30\%$，$\theta_{off}=45\%$。湿度序列（%）：32, 29, 31, 33, 40, 46, 44, 43。

| $k$ | $m_k$ | 规则 | 状态 |
|---|---|---|---|
| 0 | 32 | 在 30–45 之间，保持（初始 OFF） | OFF |
| 1 | 29 | $<30$ | ON |
| 2 | 31 | 在中间，保持 | ON |
| 3 | 33 | 中间，保持 | ON |
| 4 | 40 | 中间，保持 | ON |
| 5 | 46 | $>45$ | OFF |
| 6 | 44 | 中间，保持 | OFF |
| 7 | 43 | 中间，保持 | OFF |

如果只有单一阈值 30%：k=1 开、k=2 关、……在噪声下反复切换。迟滞用"死区"吸收了噪声。

**与 P6 的联系**：这是"执行端自带稳定性逻辑"的最小示例。P6 里同样思想用在：陈旧判断的进入/退出阈值不同（避免状态在 Valid/Stale 间抖动），设备在线/离线判定的租约与恢复条件不同，降级模式的进入与恢复要有迟滞。

### 4.3 "规则快速通道"与 P6 的关系

P4 里的"rule-based fast path for extreme states"，意思是：当环境状态极端（例如严重缺水或高温），不必等 LangGraph 的慢速决策，直接由规则处理。对应 P6 的两条经验：

1. **确定性规则优先于学习/生成型决策**，尤其在极端或安全相关情形；
2. **反应式的、简单的、快速的路径**应与**审慎的、复杂的、慢速的路径**并存，类似 07 章的分层：快层保证底线，慢层追求更优。

### 4.4 与 AI 风险一章的呼应

PS 里写："how to interpret a detector's confidence, when a learned policy should yield to a rule, and how to keep a physical actuator safe when the decision module is uncertain"。这三个问题恰好在 P6 得到了更系统的工程回答：置信度/有效性进入状态；策略校验是"让位给规则"的制度化；执行链在决策不确定时保护执行器（09 章）。

## 4.5 P4 的迟滞与 P6 的"进入快、退出慢"

P4 的水泵状态机用独立的启动与停止阈值，避免在边界上频繁开关；P6 里有三处相同的思想：设备在线/离线判定（租约 3 s，重上线需完整同步），健康状态切换（进入 Degraded 连续 2 次，退出需连续 5 次），命令看门狗（连续 2 次判定）。共同特征是：**对"变坏"反应快，对"变好"反应慢，并且用计数或时间吸收噪声**。

可以用下面的话来讲：*In the garden pump I used separate on and off thresholds; in the platform I use the same shape for liveliness and health. Falling into a degraded state should be quick; coming back should have to be earned.* 译：园艺系统的水泵里我用了独立的启停阈值；平台里存活与健康也是同一个形状：进入降级应该快，恢复则必须"挣回来"。

注意边界：P4 是个人项目的小规模原型，只能说"思想相通"，不能说"P4 是平台的前身"。

## 5.5 旁证的使用边界与一个对照

P1、P5、P7 提供的是"同一类现象在别的系统里的样子"，不是 P6 的实现依据：

- P5 的定位漂移与位姿跳变，往往来自时间戳、坐标系、运动方向不一致，这正是 P6 状态管理要在入口处统一的东西；
- P7 的平衡异常追到"状态不一致、力矩限幅、触地切换"，说明状态可信度直接影响控制行为，与 P6 的有效性分级对应；
- P1 的限幅与安全兜底（初始化、输出限幅、倒地保护）对应 P6 网关里的限幅与降级阶梯。

用法：被问到"你怎么知道这样设计有必要"时，用一个旁证说明"我在别的系统里见过没做会怎样"，然后回到 P6 的设计；不要把旁证项目的数值或结论当成 P6 的数据。

## 7. 一条诚实的成长叙事

> *Small to large.* In a gardening system I learned that a decision module — even a simple rule or an agent — should not drive an actuator directly, so the pump had its own state machine with its own thresholds and a manual override. At Future Power I built the control chain for one robot, from body velocity to wheel speed to encoder feedback. At Kaihong the question became: how do you make that kind of code independent of the hardware, and how do you make sure that whatever decides — a scheduler, an operator or an AI planner — can't bypass the safety boundary? That led to the capability model, the state standardisation and the proposal–policy–execution–feedback chain.

译：从小到大：园艺系统让我懂得决策模块不应直接驱动执行器；在未来动力我做了单机器人的控制链；在深开鸿的问题变成如何让这类代码独立于硬件，并确保任何决策者都绕不过安全边界。

注意：这条叙事是一个**框架**，不要说成"我设计了三代一脉相承的架构"。诚实的说法是："these experiences shaped how I think about the problem"。

## 7.5 三个项目的失败模式对照：同一类错误在不同尺度上的样子

把 P2、P4、P6 放在一起看，最有价值的不是"都有一条边界"，而是"同一类失败在三个尺度上长得不一样，但处理思路相同"。

| 失败模式 | P2（单机器人底盘） | P4（小型园艺系统） | P6（多机器人平台） |
|---|---|---|---|
| 命令源失联 | 遥操作断线，底盘应停下 | 服务器决策不可达，本地规则兜底 | 调度器失联，命令看门狗触发停车 |
| 数据陈旧 | 编码器反馈延迟，PID 积分异常 | 土壤湿度读数卡住，泵长开 | 状态超过 3 个周期，标记 STALE 并拒绝依赖它的提案 |
| 重复指令 | 手柄抖动重复下发 | 用户连点"浇水" | 重连后任务重复下发，用 idem_key 去重 |
| 越界参数 | 速度超过设备上限，限幅 | 浇水时长超过上限，被约束 | 提案超出档位范围，Modify 或 Reject |
| 来源冲突 | 手动与自动抢控制 | 手动优先于自动 | 手动/急停优先，同一机器人唯一任务所有者 |

**怎么用这张表**：面试官问"你在 P6 学到的东西是从哪来的"，可以挑一行讲。比如"重复指令"：在 P2 里它是手柄的物理抖动，在 P4 里是前端的重复点击，在 P6 里变成了"至少一次投递带来的必然重复"。三个尺度，越到平台层，这类问题越不是偶发，而是**机制的必然结果**，所以要用幂等（idem_key）这种机制性手段，而不是靠"别重复发"。

## 7.6 一棵可能被追问的"成长叙事"树与回答骨架

**主干问题**：*How did your earlier projects prepare you for the platform work?*

骨架（约 60 秒）：

1. 事实：P2 让我在真实硬件上走通了"目标 → 轮速 → 编码器反馈 → 里程计"这条链；P4 让我第一次把"AI 决策"和"设备执行"分开，并用本地规则做兜底。
2. 抽象：这两件事合起来就是 P6 的核心：决策方只提议，执行方保留约束权；约束要基于可信状态。
3. 差别：P2、P4 里我是在一个具体系统内部手写这些约束；P6 要求把它们做成可复用的接口（能力模型）和机制（策略校验、幂等）。
4. 诚实：P6 里很多是团队平台提供的基础，我负责的是 CV 里写的那四块；对于内部实现细节，我讲设计思路。

**常见分叉追问与回应**：

| 追问 | 回应要点 |
|---|---|
| P4 只是个小原型，和平台差距很大吧？ | 承认规模差距；强调学到的是边界思想和迟滞、规则快速通道，P6 是把它系统化 |
| 为什么 P2 的限幅经验能用到平台？ | 限幅发生的位置不同：P2 在控制环内，P6 在网关；但依据都是设备能力与停车距离 |
| 你最大的成长在哪？ | 从"让一个机器人动起来"到"让一类机器人以同样方式被安全地驱动"，思维从点到面 |

英文版回答骨架：*In P2 I made one robot's command-to-wheel chain work on real hardware. In P4 I separated an AI decision from a device's execution. The platform job asks me to generalise both: a capability model so the chain is reusable, and a gate so the separation is enforced rather than hoped for.* 译：P2 里我让一台机器人的命令到轮子的链路在真实硬件上跑通；P4 里我把 AI 决策和设备执行分开；平台工作要求我把两者一般化：用能力模型让链路可复用，用门让这种分离被强制执行而不是寄希望于自觉。

## 8. 面试问答

**Q1. How are your projects connected?**

> The common thread is the boundary between decision and execution. In the gardening system the agent could only recommend or request, and the pump had its own state machine. In the Future Power internship I built one robot's chain from velocity command to wheel speeds with encoder feedback. At Kaihong I worked on making that kind of chain hardware-independent and gating plans before they reach actuators.

追问：具体哪些想法从 P4 带到 P6？→ 结构化请求、规则优先、执行端自保护、人工优先、可追溯状态。

**Q2. Did your P2 chassis work help with the platform?**

> Yes. The differential-drive kinematics and the wheel-speed loop I built there are exactly what a differential-drive adapter needs inside. Having done it on real hardware helped me see which parts are hardware-specific — wheel radius, track width, signs, limits — and which should be in the common interface.

**Q3. Why did you use two thresholds in the pump controller?**

> With one threshold, noise around the threshold would toggle the pump rapidly. Two thresholds create a dead band: it turns on below the lower value and off above the higher value, and holds in between, which gives a stable local loop. In P4 the pump turned on below a soil-moisture value of 56 and off above 65, so there was a band of about nine units in between.

**Q4. Is the gardening system similar to a safety chain?**

> At small scale, yes, in spirit: structured requests from the decision layer, a rule path for extreme states, and device-side logic that keeps the actuator safe. The platform version adds identity, policy rules, execution tickets, audit and distributed semantics. I would not claim the gardening system has that rigour.

**Q5. Which of your projects taught you most about inconsistent state?**

> The navigation and the wheel-legged projects: in navigation I dealt with drift and pose jumps from timing and frame inconsistencies, and in the wheel-legged robot I traced balance anomalies back to state inconsistency. That's why at the platform level I wanted timestamps, frames and validity to be standardised in one place.

## 9. 本章要点速记

1. 三项目共通：决策与执行之间有一道边界；决策方只能请求；执行端自保护；人工优先；状态可信、可追溯；闭环。
2. P2 是具体实例：差速运动学 + 轮速 PID + 里程计 = P6 差速适配器内部的事；P6 的新增价值是抽象、统一与状态标准化。
3. P4 是微缩版：置信度/时间戳观测、规则快速通道、结构化请求、水泵状态机、人工优先、可追溯状态。
4. 迟滞：$\theta_{on}<\theta_{off}$ 的死区吸收噪声；P6 里陈旧/在线判定也需要迟滞。
5. P1/P5/P7 提供了"状态不一致伤控制"的第一手经验。
6. 讲叙事要诚实：这些经验塑造了思路，不是一个预先设计的三代架构。
