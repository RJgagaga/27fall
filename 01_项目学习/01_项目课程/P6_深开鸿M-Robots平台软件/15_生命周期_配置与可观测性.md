## 1. 启动、就绪与关闭

**问题**：服务相互依赖（运动服务依赖状态服务，校验器依赖能力注册）。随意启动会出现"启动期的空窗"：命令到来时状态还没有。

| 概念 | 含义 | 用途 |
|---|---|---|
| liveness（存活） | 进程是否还在运行并响应心跳 | 重启崩溃的服务 |
| readiness（就绪） | 是否已具备处理请求的条件（依赖就绪、首帧状态 Valid、配置加载完成） | 决定是否接任务 |

典型启动顺序：驱动/总线 → 适配器 Init → 状态管理（等待首帧 Valid）→ 能力注册 → 策略校验 → 对外开放任务接口。**未就绪时对提案的默认回应是拒绝（reason: NOT_READY）。**

优雅关闭（逆序）：停止接收新提案 → 让执行器受控停车（`Stop()` 幂等）→ 回执 Aborted → 注销能力/dispose 公告 → 释放资源。崩溃则靠租约与看门狗兜底。

重启后的恢复：去重表、凭据、占用关系是否持久；恢复后先同步状态，再接任务；不自动续跑旧任务（见 [11 F6](./11_故障案例库.md)）。

## 2. 配置作为数据

配置（轮半径、限幅、符号表、外参、陈旧阈值、策略规则）不应硬编码，原因：换硬件不改代码；可审计；可版本化。

要点：

1. **Schema 校验**：加载时检查类型、范围、单位后缀，非法配置拒绝启动（fail early）。
2. **版本与哈希**：配置带版本号和哈希，写入审计与能力记录（`config_hash`，见 06 章）。
3. **来源分级**：设备出厂配置、现场标定、策略配置，权限不同。
4. **热更新风险**：运行中改限幅/规则可能引入不一致；安全相关配置应在安全状态下切换、原子替换、可回滚，先影子运行。
5. **默认值保守**：缺失项取更安全的值或拒绝启动。
6. **单一事实来源**：能力描述、适配器限幅、策略上限来自同一份设备配置，避免三处不一致（[11 F11](./11_故障案例库.md)）。

## 3. 健康模型

每个组件报告 `Ok / Degraded / Fault`；整体健康由聚合规则决定：关键组件的最差状态，非关键组件最多拉到 Degraded。

教学示例（已编译运行：相机 Fault 但非关键 → 整体 Degraded；轮速反馈 Fault → 整体 Fault）：

```cpp
#include <algorithm>
#include <string>
#include <vector>

enum class Health { Ok = 0, Degraded = 1, Fault = 2 };
struct Component { std::string name; bool critical; Health health; };

Health Aggregate(const std::vector<Component>& cs) {
  Health overall = Health::Ok;
  for (const auto& c : cs) {
    Health h = c.critical ? c.health : std::min(c.health, Health::Degraded);
    overall = std::max(overall, h);
  }
  return overall;
}
```

整体健康流向：策略校验（Degraded 时限速、Fault 时只允许 stop）、任务层（不派任务给 Fault 设备）、运维告警。为避免状态抖动，进入与恢复条件应有迟滞（见 [12 章](./12_与P2_P4的关系.md)）。

---

## 3.5 健康检查项清单（典型设计）

| 组件 | 存活检查 | 就绪检查 | 降级条件 |
|---|---|---|---|
| 设备适配器 | 进程心跳 1 s | 设备自检通过、能力已注册、CAN 反馈在新鲜度内 | 反馈延迟超过 2 个周期 |
| 状态管理器 | 进程心跳 1 s | 所有关键输入首帧到达、外参已加载 | 任一关键输入 STALE |
| 策略校验 | 进程心跳 1 s | 策略版本已加载并校验通过、状态快照新鲜 | 状态快照缺失（默认拒绝，stop 放行） |
| 协同层 | 租约 3 s | 本机已发布公告、已完成一次状态同步 | 对端数量骤降或 QoS 不匹配 |
| 日志与指标 | 缓冲区未满 | 磁盘空间足够 | 缓冲区丢弃计数增长 |

**设计要点**：存活检查很轻（进程还在、心跳还在），就绪检查要反映"能干活"。把就绪检查做得过重，会让重启期间被反复判为不可用；做得过轻，又会把没准备好的设备放进任务调度。每个检查项都要有超时，检查本身不能阻塞控制线程。

---

**检查频率的取舍**：存活检查每秒一次，就绪检查在状态变化时触发，再加 5 s 的周期复核。检查过密会占用 CPU 并放大抖动，过疏又发现太晚。检查失败必须带原因，使告警直接指向具体检查项，而不是只说"不健康"。检查本身有超时，且不得运行在控制线程里。检查结果和原因随健康消息一起发布，便于运维面板与自动化告警使用同一份数据。

## 4. 日志、指标与追踪

| 手段 | 内容 | 注意 |
|---|---|---|
| 结构化日志 | 单调时间、模块、设备、proposal_id、规则 trace、级别 | 异步写，限速，避免拖慢控制线程 |
| 指标 | 计数器：提案数、拒绝数（按原因码）、陈旧次数、重复命中；直方图：命令路径时延、周期抖动；仪表：在线设备数 | 看 p95/p99/最大 |
| 追踪 | 一个 proposal_id 贯穿提案→决策→执行→回传 | 与审计链一致 |
| 事件 | 模式切换、看门狗触发、QoS 不匹配 | 关键事件不被限速丢弃 |

**手算（示例）**：一分钟内 600 条提案，拒绝 30 条，其中 STATE_STALE 21 条。拒绝率 $5\%$；STALE 占拒绝的 $70\%$ → 应优先排查状态链路而非规则。

最小指标集建议：拒绝率（分原因码）、状态陈旧率、看门狗触发次数、周期抖动 p99、命令端到端 p99、重复命中数、在线设备数。

## 5. 版本、兼容与回滚

- **能力与消息带版本**：新增字段向后兼容；旧端遇到未知字段忽略。
- **滚动升级**：混合版本共存期，确保新旧消息互通；先升级读端后升级写端（或相反，视变更方向）。
- **策略与代码分离**：规则可单独版本化、回滚。
- **回滚预案**：保留上一版本与配置；回滚也要过冒烟测试。
- **兼容测试**：契约测试扩展到"旧适配器 × 新接口"。

## 5.5 展开讲解：启动状态机、配置样例与升级演练

前面几节是概念与要点。这一节把它们落到一个可以在白板上复现的完整例子，按"问题—符号—推导—手算—在本项目里怎么用—常见错误—面试问答—自测"的顺序走一遍。以下取值是本项目的设计级口径，不是实测。

### 5.5.1 启动状态机与超时

**要解决什么问题。** 平台由多个独立进程组成（设备适配器、状态管理器、能力注册表、策略校验服务、执行网关、协同层）。如果各自随意启动，就会出现窗口期：协同层已经在对外公告"我可以接任务"，但状态管理器还没有收到首帧有效状态；或者执行网关已经开放，而策略校验服务还没有加载规则。窗口期里发生的任何命令，要么被错误放行，要么被错误拒绝。

**状态机。** 对每个进程，本项目用同一个小状态机：

```text
INIT --依赖就绪--> STARTING --自检通过--> READY --收到关闭信号--> DRAINING --受控停车完成--> STOPPED
  |                    |                      |
  +---依赖超时---------+---自检失败-----------+--运行期故障--> FAULT --重启策略--> INIT
```

- `INIT`：加载配置并校验 schema，不对外提供服务。
- `STARTING`：连接依赖（总线、下游进程），等待首帧 Valid 状态；这一步有超时。
- `READY`：对外宣告 readiness，可以接受提案。
- `DRAINING`：停止接收新提案，让执行器受控停车，回执 ABORTED，注销能力。
- `FAULT`：运行期故障，向上汇报；按重启策略（最多重试 3 次，退避 1 s、2 s、4 s）回到 `INIT`。

**启动顺序与超时（本项目取值）。**

| 步骤 | 组件 | 等待条件 | 超时 |
|---|---|---|---|
| 1 | 总线与驱动 | CAN/串口设备节点出现 | 5 s |
| 2 | 设备适配器 | 自检通过（读到一帧反馈） | 3 s |
| 3 | 状态管理器 | 各关键信号首帧 Valid | 3 s |
| 4 | 能力注册表 | 全部适配器已注册 | 2 s |
| 5 | 策略校验服务 | 策略 YAML 校验通过、版本号已记录 | 2 s |
| 6 | 执行网关 | 能验到校验服务签发的测试票据 | 2 s |
| 7 | 协同层 | 加入 Domain、发出第一次公告 | 2 s |

**手算。** 最坏情况下全部步骤用满超时，总启动时间为 $5+3+3+2+2+2+2=19$ s；典型情况下每步远小于超时，整体在几秒量级。这个数字有用：它决定了"上电后多久才能给机器人派第一个任务"，也决定了联调脚本的等待时间。若某一步超时，整个机器人保持 `FAULT` 并上报，而不是"半启动"地对外公告。

**在本项目里怎么用。** 协同层的发现公告只在步骤 7 才开始，因此"在网络上被看到"天然晚于"已就绪"，这和 06 章把 Discovered / Registered / Active 分开是同一个思想。

**常见错误。**

- 把"进程在跑"当成"能干活"：liveness 与 readiness 混为一谈。
- 超时设成无限：依赖永远起不来时，系统静默地卡住，没有任何告警。
- 启动期间允许 stop 以外的任何命令：stop 在任何阶段都应被接受。

**面试问答。**

> **Q**: How do you make sure the robot doesn't accept tasks before it's ready?
>
> **A**: Every process has a small state machine, and the robot advertises itself only after the last step in a fixed start-up order: drivers, adapters, state manager with a valid first frame, registry, policy checker, gateway, and finally the coordination layer. Each step has a timeout; if one fails, the robot stays in a fault state and reports it instead of half-starting.
>
> 译：每个进程有小状态机，按固定顺序启动，最后一步才由协同层对外公告；每步有超时，失败则保持故障并上报，而不是半启动。

### 5.5.2 一份配置样例

下面是一份设备描述的设计级样例（YAML），用来说明"配置即数据"。数值是本项目口径。

```yaml
schema_version: 3
device_id: base_diff_01
kind: mobile_base
frames:
  base: base_link
  laser: laser_link
  imu: imu_link
extrinsics:
  laser_link: {x: 0.12, y: 0.0, z: 0.18, yaw: 0.0}
  imu_link:   {x: 0.0,  y: 0.0, z: 0.05, yaw: 0.0}
limits:
  max_linear_mps: 0.8
  max_angular_rps: 1.5
  max_linear_acc: 1.0
  max_angular_acc: 2.0
command:
  rate_hz: 20
  watchdog_ms: 200
  consecutive_misses: 2
staleness:
  imu_ms: 30
  odom_ms: 60
  lidar_ms: 300
passthrough: [cmd_vel]
```

**读这份配置时要注意的几件事。**

1. `schema_version` 让加载器知道用哪一版校验规则；未知版本拒绝启动。
2. 限幅只写在这里一份，能力描述、适配器限幅、策略上限都从它派生，避免 11 章里"三处不一致"的故障。
3. `watchdog_ms` 与 `rate_hz` 的比值是 4，符合 14 章 W13 的反推；`consecutive_misses: 2` 来自 11 章问题 3 的修复。
4. 外参只在状态管理器入口应用一次；换一台传感器安装位置不同的车，只改这里。
5. `passthrough: [cmd_vel]` 表示只有连续速度命令走"直通加网关限幅"，其余命令走完整提案链。

**手算：配置哈希的用途。** 设配置文件在现场被人改过一次，哈希由 `a1f3` 变为 `9c07`。能力记录里带有 `config_hash`，协同层比较发现两台"同型号"机器人的哈希不同，就能在调度前提示"这两台配置不一致"。这是用一个 4 字符的值替代人工对照文件，说明版本与哈希的价值。

**常见错误。** 配置里写了单位却没有校验（把 m/s 写成 mm/s）；配置缺项时取"方便的默认值"而不是"保守的默认值"；热更新限幅时没有原子替换，导致控制周期中读到一半旧值一半新值。

### 5.5.3 一次滚动升级的演练

**问题。** 策略从 `policy.v3` 升到 `policy.v4`（比如新增一条规则），在 8 台机器人上如何不中断地完成？

**步骤与推理。**

1. **影子模式**：先让 v4 在旁路运行，只记录它会做出的判决，不影响执行；对比 v3 与 v4 的判决差异。
2. **差异评估**：若在回放的一小时流量里 v3 拒绝 30 条、v4 拒绝 60 条，则多出的 30 条需要逐条解释；它们是不是真的该拒绝？
3. **灰度**：先升级 1 台，再 2 台，再其余；每一阶段观察拒绝率、陈旧率、看门狗触发次数。
4. **回滚预案**：保留 v3 文件与哈希；回滚后也跑冒烟用例（stop 永远允许、已知危险提案被拒绝）。
5. **混合版本期**：两个版本的校验同时存在于车队中，因此提案消息里要带 `policy_version`，审计才能解释"同一提案在两台机器上结果不同"。

**手算。** 回放 3600 条提案，v3 拒绝 30 条（0.83%），v4 拒绝 60 条（1.67%）。拒绝率翻倍。若其中 28 条新增拒绝可以归因于新增规则本意，另 2 条是误伤，则误伤率为 $2/3600\approx0.06\%$，需要修规则后再进入灰度。

**常见错误。** 直接全量替换；升级只测"通过的情况"不测"应该拒绝的情况"；没有记录策略版本号，出问题后无法回放。

**面试问答。**

> **Q**: How would you roll out a new policy version safely?
>
> **A**: I'd run it in shadow mode first and compare its decisions with the current version on recorded traffic, explain every difference, then roll it out to one robot, then a few, watching the rejection rate and watchdog triggers. Each decision records the policy version so the audit can explain differences during the mixed-version period, and the previous version stays ready for rollback.
>
> 译：先影子模式在录制流量上对比判决并解释每个差异，再灰度到 1 台、几台，观察拒绝率与看门狗；每次判决记录策略版本，回滚版本随时可用。

## 5.6 健康聚合与告警阈值：为什么需要迟滞与观察窗口

健康模型只有"Ok / Degraded / Fault"三个值还不够，关键是**什么时候切换**。如果每次检查都直接按当前值切换，状态会在边界上抖动，告警风暴随之而来。

**设计要点（本项目口径，设计级）**：

1. **进入快、退出慢**：进入 Degraded 只需要连续 2 次检查失败；退出需要连续 5 次检查通过。好处是真实故障不被拖延，偶发的好值不会让状态来回翻转。这与 12 章的迟滞思想相同。
2. **观察窗口**：指标类告警用滑动窗口，例如"60 s 窗口内状态陈旧率超过 5%"，而不是"出现过一次陈旧"。
3. **分级响应**：Degraded 时策略把最大速度降到档位的一半；Fault 时只允许 stop 与恢复类提案；设备 OFFLINE 时任务层不再向它派任务。
4. **去重与限速**：同一类告警在 60 s 内只上报一次，附计数；关键事件（看门狗触发、模式切换）不受限速影响。

**手算（教学示例）**：陈旧率检查每秒一次，真实陈旧率在阈值附近随机波动，单次检查超阈值概率 0.5。无迟滞时，每秒都有约一半概率切换状态，一分钟内期望切换约 30 次。采用"进入需连续 2 次、退出需连续 5 次"后，进入概率约 $0.5^2=25\%$ 每个窗口，退出概率 $0.5^5\approx3\%$，状态会稳定停留在 Degraded，直到陈旧率真正下降，一分钟内切换次数降到个位数。数字是示意，思路是：用状态机吸收噪声，而不是在告警层做过滤。

## 5.7 配置漂移：现象、定位与预防

**现象**：同一版本的程序，在两台机器人上表现不同——A 车正常，B 车偶发停车。

**定位步骤**：

1. 先比对"生效配置"而不是"配置文件"。启动时把解析后的生效配置（含默认值填充结果）与配置版本号、内容哈希打印到日志。
2. 对比两台设备的哈希。若不同，用结构化差异工具逐项比较，常见根因是某个字段在 B 车上被手工改过（例如看门狗改成了 100 ms）。
3. 若哈希相同，再查环境：时钟同步状态、网络质量、外参文件。

**预防**：

| 手段 | 说明 |
|---|---|
| 配置即代码 | 配置文件进版本库，变更走评审 |
| 启动校验 | schema 校验 + 范围校验（看门狗不得小于下发周期的 2 倍） |
| 哈希上报 | 设备周期性上报配置哈希，平台侧发现不一致告警 |
| 热加载需签名 | 策略类配置变更要带签名与版本号（08 章） |
| 变更留痕 | 每次变更写审计，含操作人与原因 |

**一个典型 bug 的复盘**：某次发布中，新版本为了降低日志量，把 `status_rate` 默认值从 20 Hz 改成 10 Hz，却没有同步改陈旧上限。结果状态发布周期 100 ms，而陈旧上限仍按 20 Hz 计算为 150 ms，只剩 1.5 个周期的容忍，偶发调度抖动就把状态判成 STALE。根因是两个参数存在隐含依赖。修复是把陈旧上限改为"由发布周期派生"，不再独立配置，并在配置校验里加入依赖检查。教训：能推导出来的参数，不要让它独立存在。

## 5.8 可观测性的最小闭环：从一个指标到定位一条提案

假设监控显示"拒绝率从 2% 升到 9%"。定位过程：

1. 指标按原因码拆分：E_STALE 占 80%。
2. 按设备拆分：集中在设备 `lidar-02`。
3. 取该设备最近的状态流，看 age 分布，发现 p95 从 40 ms 涨到 280 ms，接近 300 ms 的上限。
4. 用 proposal_id 关联日志，确认拒绝发生在状态管理器的新鲜度检查。
5. 追到链路：该设备所在 Wi-Fi 信道拥塞，丢包升高。
6. 处理：短期降低该设备的发布频率并放宽上限；长期换信道/有线。回归：用 netem 复现同等丢包，确认拒绝率回到基线。

这个闭环能走通，前提是日志字段统一、指标有原因码维度、每条提案可以追踪。

## 6. 面试问答

**Q1. What is the difference between liveness and readiness?**

> Liveness says the process is running; readiness says it can actually handle requests — dependencies up, first valid state received, configuration loaded. Until a service is ready, proposals get a "not ready" rejection rather than being half-processed.

**Q2. How do you manage configuration safely?**

> As validated, versioned data: schema checks on load, a hash recorded in the audit trail, conservative defaults, and one source of truth for limits so capability descriptions, adapters and policy don't disagree. Safety-related changes are swapped atomically, tried in shadow mode and can be rolled back.

**Q3. How do you summarise the health of a robot?**

> Each component reports ok, degraded or fault; critical components set the overall level, non-critical ones cap at degraded. The policy layer uses it: degraded means lower limits, fault means only stop is accepted.

**Q4. Which metrics matter most?**

> Rejection rate by reason code, staleness rate, watchdog triggers, control-period jitter at the tail, end-to-end command latency at p99, and duplicate hits. They show whether the system is healthy before a failure becomes visible. In our setup these are counters exposed through a state-snapshot query and written to structured logs.
