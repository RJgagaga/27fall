## 1. 从零到上线：需求、选型、架构与里程碑

### 1.1 需求：先把"要解决的问题"说成可验收的句子

平台要解决的是异构多机器人协同：不同底盘、不同传感器、不同控制器，被统一的运动代码和统一的任务调度驱动。把这句话拆成可验收的需求（本项目口径，设计级）：

| 编号 | 需求 | 验收方式 |
|---|---|---|
| R1 | 新增一种底盘只需写适配器并声明能力，上层不改 | 契约测试通过；上层用例零修改 |
| R2 | ROS/ROS2 运动命令能驱动任意已注册底盘 | 同一组 Twist 序列在两种底盘上轨迹等价 |
| R3 | 运动层与任务层读到的状态时间、坐标、有效性一致 | 有效性规则表用例全绿；回放对比 |
| R4 | 设备上下线、能力变更对任务层可见，延迟小于数秒 | 发现与租约用例；掉线判定约 3 s |
| R5 | 任何任务计划不经校验不得变成物理动作 | 绕过测试：直接向执行网关发无票据命令必被拒 |
| R6 | 命令到执行器的端到端延迟预算小于 100 ms | 逐跳时间戳统计第 99 分位 |
| R7 | 故障可定位、可复现 | 提案全链路可追踪；日志可回放 |

需求里有"可验收"三个字是关键：面试官问"你怎么知道做好了"，你要能回到验收方式。

### 1.2 方案选型：三个主要决策及理由

**决策 1：能力模型 vs 直接适配 ROS 消息。** 备选方案 A 是在每个上层模块里直接适配各类底盘的消息；方案 B 是引入统一能力模型。选 B 的理由：设备种类 × 上层模块的组合是乘法关系，B 把它变成加法；代价是需要设计并维护接口。详见 [03](./03_统一能力模型与设备抽象.md)。

**决策 2：ROS/ROS2 接入用桥接适配节点，而不是平台内部原生支持。** 理由：桥接节点只做话题与能力命令的互转，不放业务逻辑，ROS1 通过 ros1_bridge 转入同一个 ROS2 适配节点，两套共用一份映射逻辑。代价是多一跳（约 2 ms 量级）。详见 [04](./04_ROS_ROS2命令映射与跨硬件复用.md)。

**决策 3：校验做成独立服务，执行网关只认票据。** 理由：库函数可被绕过，独立进程加票据让绕过需要突破进程边界；代价是多一次 IPC，约 1 ms。详见 [08](./08_安全执行链.md)。

### 1.3 架构：五层与双向数据流

向下：任务/规划 → 动作提案 → 策略校验 → 运动接口（能力模型）→ 驱动适配器 → 底层驱动。向上：硬件反馈 → 状态管理 → M-DDS 回传 → 任务层。进程上，设备适配器、状态管理器、策略校验、协同层各自独立；这样任何一个崩溃不会带走其他部分，并且每个边界都是一个可以观测、可以注入故障的点。

### 1.4 里程碑与迭代（典型节奏）

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| M0 接口冻结 | 能力模型字段、状态消息字段、提案/回执字段文档化 | 与上下游评审通过 |
| M1 单设备跑通 | 一种底盘：命令 → 适配器 → 驱动，带限幅与看门狗 | 契约测试绿；急停用例通过 |
| M2 第二种设备 | 第二种底盘，验证复用 | 同一组上层用例零修改通过 |
| M3 状态管理 | 时间戳、坐标系、有效性、陈旧降级 | 规则表用例与回放通过 |
| M4 协同 | 发现、注册、状态同步、任务分发 | 3 台台架联调；掉线重连用例通过 |
| M5 安全链 | 提案-校验-执行-回传，幂等、审计 | 绕过测试、故障注入通过 |
| M6 加固与上线 | 灰度、监控、回滚预案 | 冒烟测试、指标看板就绪 |

我自己的口径：**每个里程碑的退出条件都是"可运行的测试"，而不是"代码写完"**。当前进展（自查表第 28 项）：能力模型与状态管理已集成并在用；M-DDS 协同在多机台架联调中；安全执行链已接入调度器路径、仍在补测试用例与审计字段。

## 2. 各层频率与周期总表

下表是全文统一口径（与 README 自查表第 13 项一致）。**频率不是越高越好**：每层的频率由它要处理的物理过程、网络能力和下游需求共同决定。

| 层/环节 | 频率或周期 | 定频还是事件 | 取值依据 |
|---|---|---|---|
| 任务层 | 约 1 Hz 量级，事件驱动 | 事件 | 任务以秒到分钟计，没有必要定频 |
| 规划层 | 5～10 Hz | 定频 | 环境变化与计算量折中 |
| 速度/轨迹命令 | 20 Hz 默认，可到 50 Hz | 定频 | 比底盘响应快一个量级，又不压垮网络 |
| 状态发布 | 20 Hz | 定频 + 变化触发 | 运动层以上消费者足够 |
| IMU 采样 | **100 Hz** | 定频 | 全项目统一口径 |
| 里程计/轮速反馈 | 50 Hz | 定频 | 与速度环匹配 |
| 2D 激光 | 10 Hz | 定频 | 设备本身限制 |
| 设备公告 | 1 s（租约 3 s） | 定频 | 掉线判定约 3 个周期 |
| 适配器到 CAN | 100 Hz 重复发送最新目标 | 定频 | 丢一帧不致命 |
| MCU 底层控制 | 100～1000 Hz | 定频 | 电机伺服需求 |
| 日志/指标 | 异步批量 | 批量 | 不得拖慢控制线程 |

### 2.1 选频率的五条原则

1. **下层至少比上层快 3～5 倍**，使保持/插值有意义（07 章）。
2. **消费者决定发布频率**：没人需要 100 Hz 状态，就不要把 100 Hz 发上网络。
3. **网络带宽要核算**：$B=N_{dev}f(S_{payload}+S_{overhead})$。20 个设备、20 Hz、250 B 负载、60 B 开销约 124 kB/s，约 1 Mbit/s；留 3～5 倍余量应对重传和发现流量。
4. **由周期派生的参数不单独配置**：陈旧上限 = 3 个周期，Deadline ≈ 2 个周期，看门狗 ≈ 4 个下发周期。周期改了，它们自动跟着变，避免漂移（见第 10 节问题 6）。
5. **每个频率都要对应一个度量**：周期抖动 p99、丢帧率、年龄分布。

### 2.2 CAN 总线负载估算（教学示例）

经典 CAN 8 字节数据帧，500 kbit/s 时一帧约 130 位（含填充与帧间隔的保守估计），单帧约 0.26 ms。假设一条总线上：4 个电机各 100 Hz 发控制帧、4 个电机各 100 Hz 回反馈帧，共 800 帧/s，总线占用 $800\times0.26\text{ ms}=208\text{ ms/s}\approx21\%$。这个量级留有余量；如果误把控制帧提高到 1 kHz，占用升至约 100%，会出现仲裁失败和丢帧。教训：**提高频率前先算总线占用**，并保留 50% 以下的常态负载。

## 3. 多源传感器时间戳与时钟同步

### 3.1 要解决的问题

IMU（100 Hz）、里程计（50 Hz）、激光（10 Hz）三类数据来自不同设备，各有各的采样时刻和传输延迟。把"到达时刻"当作"测量时刻"，会把几十毫秒的传输延迟当成物理量。位姿跳变、融合发散、控制振荡，很多根源在此（P5 里就遇到过类似现象，见 [12](./12_与P2_P4的关系.md) 的旁证）。

### 3.2 本项目的做法（设计级）

1. **设备内部用单调时钟**（CLOCK_MONOTONIC）打戳，只用于间隔、超时和年龄计算。
2. **优先测量时间**：驱动能拿到硬件采样时间就用它；只有接收时间时，减去标定过的固定延迟，并把来源标为"弱时间"。
3. **跨设备用 NTP 对齐**到局域网时间服务器，量级约几毫秒到十几毫秒；**不使用 PTP**；**控制回路不依赖跨设备时间**，跨设备比较只用于日志与粗对齐。
4. **入口一次性处理**：状态管理器在入口检查时间戳是否单调、有无重复、有无来自未来；之后各层只用统一后的 `stamp`、`age_ms`。
5. **不同频率的对齐**：需要融合时，对高频数据在低频数据的时间点插值；插值公式 $x(t)=x_a+\frac{t-t_a}{t_b-t_a}(x_b-x_a)$，外推只允许很短窗口并标注"推算值"。

### 3.3 手算：NTP 与对齐误差

NTP 往返：$t_1=50.000$，$t_2=50.040$，$t_3=50.042$，$t_4=50.030$（单位 s，教学示例）。往返延迟 $\delta=(t_4-t_1)-(t_3-t_2)=0.030-0.002=0.028$ s；偏移 $\theta=\frac{(t_2-t_1)+(t_3-t_4)}{2}=0.026$ s；不确定度上界 $\delta/2=0.014$ s。含义：即使这样对齐，两台设备的时间比较仍有 14 ms 量级的不确定性。对 100 Hz 的 IMU（周期 10 ms），这相当于一个多周期，所以**不能拿跨设备时间去做 IMU 级的融合**，这也是第 3 点"控制回路不依赖跨设备时间"的理由。

### 3.4 陈旧判定与降级

陈旧上限取传感器周期的 3 倍：IMU 100 Hz → 30 ms，里程计 50 Hz → 60 ms，激光 10 Hz → 300 ms。再与回路延迟预算取较紧者。超限后的处理是分级的：先保持（短时）→ 降级（限速）→ 安全动作（停车），并拒绝依赖它的提案。冻结检测：连续 5 帧完全相同视为传感器卡死，标 Suspect。

### 3.5 时钟回拨事件复盘

现象：某设备被校时服务器校正后，墙上时钟回拨约 200 ms，其状态流被判为 STALE，调度器暂停向它派任务。度量：对比该设备的单调时钟间隔（正常）和墙上时间戳（出现负间隔）。瓶颈：状态管理器用了设备上报的墙上时间戳计算年龄。改动：年龄计算改为以接收时间（本机单调时钟）锚定，设备上报的时间戳仅作参考；时间戳倒退时标记 Suspect 并上报健康事件。回归：时钟跳变故障注入用例（向前、向后各一次）全部通过。这是自查表第 26 项的第二个问题。

## 4. 状态发布频率与控制命令周期

### 4.1 状态为什么是 20 Hz

状态管理器订阅 100 Hz 的 IMU、50 Hz 的里程计，聚合成一条带时间戳、frame、validity 的状态，发布频率 20 Hz。理由：运动层以上的消费者（规划 5～10 Hz、策略校验、任务层）不需要更高的速率；需要原始速率的回路（比如本机的速度环）直接在本地读取，不经过网络。**用"20 Hz 聚合 + 本地原始读取"代替"100 Hz 全网广播"**，网络负载降为原来的约 1/5。

此外加入"变化触发"：当有效性等级变化、关键标志位变化（如急停、模式切换）时，立刻额外发一条，不等下一个周期。这样既保证平稳时的低负载，又保证关键事件的低延迟。

### 4.2 命令周期与平滑线程

速度命令默认 20 Hz（周期 50 ms）。映射与限幅线程按固定周期推进（教学示例为 20 ms），每个周期取最新的未过期命令作为目标，再按加速度限幅推进：$v_k=v_{k-1}+\mathrm{clip}(v^*_k-v_{k-1},\pm a_{max}T_s)$。适配器每 10 ms 把最新目标重复发送到 CAN，MCU 内部再用 100～1000 Hz 的伺服环执行。**三个周期不同，但每一级都"保持上一个目标"，并有有效期兜底。**

### 4.3 命令看门狗：周期、超时与停车距离

看门狗约 200 ms，约为 20 Hz 下发周期的 4 倍，并要求连续 2 次判定，所以最长约 250 ms 进入减速停车。停车距离：$d=vT_w+\frac{v^2}{2a}$，以 $v=0.8$ m/s、$T_w=0.25$ s、$a=1.0$ m/s² 计，$d=0.2+0.32=0.52$ m。该值必须小于设备档位给出的安全距离，否则要降低速度档位或缩短超时。

为什么是 4 倍：2 倍太敏感，Wi-Fi 抖动一次就停车；8 倍则失联后冲得太远。4 倍是折中，具体取值随设备类型放在配置文件，并由停车距离校验。

### 4.4 一个常见追问：能不能把状态 20 Hz 和命令 20 Hz 做成同步的

不建议。命令由上层驱动，状态由设备驱动，二者各自定频，通过时间戳关联，而不是靠"同一拍"。同步意味着一方等另一方，一方抖动会拖慢另一方。

## 5. DDS QoS 与延迟、丢包

### 5.1 按数据性质选 QoS（设计取值）

| 数据 | 可靠性 | 持久性 | 历史 | 其他 | 理由 |
|---|---|---|---|---|---|
| 高频状态 | BestEffort | Volatile | KeepLast(1) | Deadline ≈ 2 倍周期（20 Hz 时 100 ms） | 旧值无价值，重传徒增延迟 |
| 能力/健康 | Reliable | TransientLocal | KeepLast(1) | | 晚加入者要拿到最新记录 |
| 任务命令/回执 | Reliable | Volatile | KeepLast(10) | | 不可丢，但不回放旧命令 |
| 设备公告 | Reliable | TransientLocal | KeepLast(1) | Liveliness 租约 3 s | 掉线检测 |

### 5.2 丢包下的行为推演（教学示例）

假设链路丢包率 10%，各包独立：

- **高频状态（20 Hz，BestEffort）**：每秒丢约 2 条。消费者最多连续丢失 $n$ 条的概率 $0.1^n$：连续 3 条（150 ms）为 0.1%。陈旧上限按 3 个周期取（对 20 Hz 状态约 150 ms，见下述预算），所以偶发丢包不会触发 STALE，连续 3 条以上才会。
- **公告（1 s，租约 3 s）**：租约内有 3 次公告，全部丢失概率 $0.1^3=0.1\%$，每次租约窗口约千分之一的误判掉线率。如果设备多（50 个端点），每分钟的窗口数多，会出现偶发误判。对策：租约放宽到 4 个周期（$10^{-4}$），或掉线判定后做一次主动探测再置 OFFLINE。
- **任务命令（Reliable）**：底层重传保证最终到达，但延迟增加；应用层再加带上限的重试和幂等键（第 6 节）。

### 5.3 延迟：从哪里来

一条 DDS 消息的端到端延迟 = 序列化 + 本机调度 + 网络（Wi-Fi 排队与重传）+ 反序列化 + 订阅端回调调度。其中最不稳定的是 Wi-Fi 重传与调度抖动。度量方法：发布端和订阅端都在入口/出口记录单调时钟，同机两个进程可直接相减；跨设备则使用往返测量（ping-pong），取一半作为单向近似，并明确这是近似。

### 5.4 QoS 不匹配：一个高频排查点

症状：订阅端"没有任何报错，但收不到数据"。常见原因是请求/提供不兼容，例如发布端 BestEffort、订阅端 Reliable。排查顺序：先看 QoS 不匹配事件，再看 Domain/分区，再看类型和 Topic 名，最后看防火墙与多播。把 QoS 不匹配事件接入健康模型（15 章），使它出现在监控里，而不是靠人偶然发现。

### 5.5 发现与规模

同一网段内多播公告为主，多播被禁用的网络用静态对等列表兜底；设计规模约 5～10 台机器人、每台 3～6 个设备，共约 30～60 个端点。端点级发现关系数 $N(N-1)/2$：50 个端点约 1225 个，启动瞬间会有发现风暴，所以设备上电后随机延迟 0～2 s 再公告，避免同时上电造成拥塞。规模显著变大时需改用发现服务器。

## 6. 任务分发的超时与重试

### 6.1 状态机与超时（设计取值）

回执阶段：RECEIVED → ACCEPTED/REJECTED → EXECUTING → DONE/FAILED/ABORTED。各阶段的调度器侧超时：

| 阶段 | 超时 | 超时后的动作 |
|---|---|---|
| 发出 → RECEIVED | 500 ms | 带退避重试，同一 idem_key |
| RECEIVED → ACCEPTED/REJECTED | 2 s | 查询状态；仍无结果则重试 |
| ACCEPTED → EXECUTING | 5 s | 查询机器人状态；异常则取消并重新分派 |
| EXECUTING → 终态 | 由任务类型决定（导航类约 30 s 内必须有进度回执） | 无进度则判定任务悬挂，升级 |

### 6.2 重试策略

最多重试 3 次，退避间隔约 0.5 s、1 s、2 s，并加少量随机抖动；全部失败后任务标为 UNKNOWN，升级给人或对账流程。重试不是"更用力地发"，而是在**至少一次投递**语义下配合**幂等**，保证重复无害。

### 6.3 幂等与去重窗口

机器人按 idem_key 去重。去重表保留时间约为提案有效期的 2 倍（默认 60 s）：**去重窗口必须长于最长重试窗口**。重试总时间约 $0.5+1+2=3.5$ s 加各次等待回执的时间，远小于 60 s，所以覆盖。去重表在内存，每 5 s 快照到本地文件；进程重启后先静默一个有效期窗口再接新提案，避免重启后把仍有效的旧提案当成新提案重复执行。

### 6.4 所有权与冲突

每台机器人同一时刻只有一个任务所有者，高优先级可抢占，急停永远最高。两个调度器同时给同一机器人派任务，串行化裁决，后到者收到带原因码的拒绝，而不是排队等待（14 章 S1）。

### 6.5 为什么不做"恰好一次"

分布式系统里无法在不可靠网络上提供严格的恰好一次；工程上用"至少一次 + 幂等"达到"效果上恰好一次"。这条结论在面试里很加分，因为它显示你知道问题的本质。

## 7. 安全执行链的延迟预算

### 7.1 逐段预算（设计取值，教学示例）

| 段 | 名义 | 上限 | 说明 |
|---|---|---|---|
| ① 提案从来源到校验服务 | 2 ms | 10 ms | 同机 IPC 或局域网 |
| ② 校验（七类规则） | 2 ms | 5 ms | 本地状态快照，规则预编译 |
| ③ 签发票据（HMAC-SHA256） | 0.2 ms | 1 ms | 短时凭据，运动类约 2 s，导航目标类约 30 s |
| ④ 网关验票 + 限幅 + 平滑 | 1 ms | 2 ms | |
| ⑤ 映射 + 适配器编码 | 1 ms | 3 ms | |
| ⑥ CAN 发送 + MCU 取用 | 2 ms | 10 ms | 取决于 MCU 周期 |
| 名义合计 | 约 8 ms | 约 31 ms | |
| 预留余量 | | 约 69 ms | Wi-Fi 重传、调度抖动、GC/缺页 |
| 设计预算 | | 小于 100 ms | |

**说明**：这是"设计预算"，不是实测。面试里的正确说法是：*the design budget for command-to-actuator is under 100 ms; I'd verify it with per-hop timestamps and look at the 99th percentile.*

### 7.2 校验为什么不会成为瓶颈

① 校验器本地缓存状态快照（订阅状态 Topic，而不是在请求里远程查询）；② 规则预编译成数据结构；③ 日志异步，审计写环形缓冲；④ 提案有上限的速率限制，避免规划器反复提交把校验服务压垮。校验耗时与规则数、状态查询方式有关，把"远程查询"改成"本地快照"是最大的一次优化（见第 9 节优化 2）。

### 7.3 预算超支时的处理顺序

先看是哪一段（逐跳时间戳）；再看是名义值变大还是尾部变长（p50 vs p99）；尾部变长通常是调度抖动或重传，名义值变大通常是代码改动。不要先去改预算，而是先找原因。如果确实需要放宽，要回到停车距离公式重算，并经评审。

## 8. 线程、优先级与调度

### 8.1 划分原则

进程：设备适配器、状态管理器、策略校验、协同层各自独立。线程：每个进程里"周期性控制或发布线程"和"网络/日志线程"分开；控制线程不做阻塞 I/O、不做大内存分配、不拿可能被低优先级线程长期持有的锁。

### 8.2 周期推进与抖动度量

周期线程用绝对时间推进（`sleep_until(next)`），而不是 `sleep_for(period)`，避免累计漂移。每个周期记录 `actual_period` 与 `exec_time`，统计 p50、p99、最大值。判定：连续两个周期超过 1.5 倍周期（例如 10 ms 周期的线程出现 17 ms、19 ms）→ 上报健康降级。

### 8.3 利用率与余量

10 ms 周期、WCET 约 2 ms，利用率 20%；允许抖动 2 ms 时最坏响应约 4 ms。如果让日志同步落盘进入控制线程，偶发 8 ms 阻塞使最坏响应逼近周期，这是 11 章故障 F3 的原型。控制线程只写无锁环形缓冲，日志线程在最低优先级异步落盘。

### 8.4 优先级反转

低优先级线程持锁、高优先级线程等锁、中优先级线程抢占，高优先级线程被间接拖住。规避：避免共享锁；必须用锁时用带优先级继承的互斥量，临界区只做指针交换。

### 8.5 OpenHarmony 下的现实

标准系统基于 Linux 内核时可以使用实时调度策略和优先级，但用户态的缺页、内存分配、IPC 仍会带来不确定延迟。**高要求的闭环放在 MCU 或驱动器里，平台层只做速度/位姿级的目标**。这是 07 章分层的实时性理由。

## 9. 五次优化过程

> 以下每一次优化都按"现象 → 度量方法 → 瓶颈 → 改动 → 前后对比 → 回归验证"书写。数字是设计级取值，用来示范工程方法，**不是实测**。

### 优化 1：状态发布从 100 Hz 全量广播改为 20 Hz 聚合 + 变化触发

- **现象**：3 台台架联调时 Wi-Fi 延迟的尾部明显变长，状态陈旧告警偶发。
- **度量**：统计各 Topic 的带宽占比与订阅端数据年龄分布。
- **瓶颈**：IMU 状态以 100 Hz 全量发到网络，而消费者只需要 20 Hz 以内。
- **改动**：状态管理器聚合成 20 Hz，关键事件变化触发即时发布；需要原始速率的回路改为本地读取。
- **前后对比（设计级）**：状态流量降为约 1/5；订阅端数据年龄 p99 由约 90 ms 降到约 45 ms。
- **回归**：陈旧判定用例、急停事件延迟用例、回放对比全部通过。

### 优化 2：策略校验由"请求内远程查状态"改为"本地状态快照"

- **现象**：校验耗时的第 99 分位偏高，在状态服务繁忙时会超过 10 ms。
- **度量**：在校验入口、出口打单调时钟时间戳，分段统计规则计算与状态查询耗时。
- **瓶颈**：新鲜度规则每次请求都通过 IPC 去查状态服务。
- **改动**：校验服务订阅状态 Topic，维护本地快照，记录快照年龄；快照超过陈旧上限则默认拒绝（stop 仍放行）。
- **前后对比（设计级）**：校验耗时 p50 约 4 ms → 2 ms，p99 约 12 ms → 4 ms。
- **回归**：状态服务重启 3 s 情景（14 章 S2）、校验器宕机情景（S8）、全量规则表用例通过。

### 优化 3：控制线程周期推进与优先级

- **现象**：速度输出偶发"打嗝"，里程计显示速度出现周期性小台阶。
- **度量**：记录线程每周期的实际间隔，画直方图，发现 10 ms 周期偶尔出现 18 ms。
- **瓶颈**：线程用 `sleep_for` 累计漂移，且与日志线程共享互斥量。
- **改动**：改为 `sleep_until` 绝对时间；日志改为无锁环形缓冲 + 异步线程；控制线程提升优先级。
- **前后对比（设计级）**：周期抖动 p99 约 8 ms → 1.5 ms，最大值不再超过 1.5 倍周期。
- **回归**：高负载（日志洪泛）压力用例；周期溢出监控无告警。

### 优化 4：设备上电的发现风暴

- **现象**：多台机器人同时上电时，发现耗时长达十几秒，部分设备被误判离线。
- **度量**：抓包统计启动后前 10 s 的发现报文数量；统计各设备注册完成时间。
- **瓶颈**：多个设备在同一时刻公告，多播与重传叠加。
- **改动**：上电后随机延迟 0～2 s 再公告；公告抖动；租约内收到任意一次公告都续租；多播禁用网络用静态对等兜底。
- **前后对比（设计级）**：发现完成时间由约 12 s 降到约 4 s；误判离线次数降为零。
- **回归**：同时上电 10 次重复；单设备掉线重连用例。

### 优化 5：日志从同步落盘改为异步批量，并加字段规范

- **现象**：出问题时日志不全，且打开详细日志后控制周期被拖慢。
- **度量**：对比开启不同日志级别时的周期抖动和日志丢失计数。
- **瓶颈**：同步落盘 + 日志格式不统一，难以按 proposal_id 关联。
- **改动**：异步批量；统一字段（单调时间、模块、设备、proposal_id、seq、规则 trace）；关键事件不被限速丢弃；其他事件按级别限速。
- **前后对比（设计级）**：开最详细日志级别时周期抖动 p99 几乎不变；定位一次拒绝的耗时由约半小时降到几分钟。
- **回归**：日志洪泛下关键事件仍完整；字段 schema 校验。

## 10. 十二个工程问题与解决

| # | 问题 | 现象 | 根因 | 解决 | 预防 |
|---|---|---|---|---|---|
| 1 | 重连后任务被重复下发 | 同一任务执行两次 | 至少一次投递 + 无去重 | idem_key 去重，窗口 2 倍有效期 | 契约测试加"重复提案" |
| 2 | 设备时钟回拨 | 状态被误判 STALE | 用设备墙上时间计算年龄 | 以接收时间锚定，标 Suspect | 时钟跳变故障注入 |
| 3 | 看门狗在 Wi-Fi 抖动时误触发 | 机器人走走停停 | 超时太接近下发周期 | 超时设为周期 4 倍 + 连续 2 次判定 | 停车距离公式校核 |
| 4 | 联调时订阅端收不到状态 | 无报错无数据 | QoS 不兼容 | 对齐 QoS；接入不匹配事件 | 启动自检 + 健康事件 |
| 5 | 同版本两台机器人行为不同 | A 正常 B 偶发停车 | B 的看门狗被手工改过 | 配置哈希对比，回滚 | 配置即代码 + 哈希上报 |
| 6 | 改了发布频率后陈旧误判 | STALE 频发 | 陈旧上限独立配置，未同步 | 上限由周期派生 | 配置依赖检查 |
| 7 | 仿真通过实机失败 | 仿真里转向正确，实机反向 | 实机轮子安装方向与符号表不同 | 符号表放设备配置，契约测试加"原地左转" | 每种底盘必过方向用例 |
| 8 | 校验规则升级后拒绝率翻倍 | 大量 E_LIMIT | 新规则单位按 m/s 写成 cm/s | 影子模式回放对比；回滚 | 规则变更先影子、再灰度 |
| 9 | 调试日志拖慢控制 | 打开日志后抖动 | 同步落盘 | 异步环形缓冲 | 周期抖动监控 |
| 10 | 重启后旧提案被重复接受 | 重启后车辆动了一下 | 去重表在内存，重启丢失 | 定期快照 + 重启后静默一个有效期 | 重启场景用例 |
| 11 | 同时上电发现很慢 | 部分设备被判离线 | 发现风暴 | 随机延迟公告 | 同时上电重复测试 |
| 12 | 接口变更破坏下游 | 调度器编译失败 | 新增字段改变了默认语义 | 变更说明先行 + 过渡期双版本 | 能力版本协商，契约测试保旧 |

### 10.1 分类整理：这些问题属于哪几类

- **时间类**（2、3、6）：时钟、超时、周期派生。
- **投递语义类**（1、10）：至少一次、幂等、重启。
- **配置类**（4、5、6、7、8）：QoS、版本、单位、符号、哈希。
- **资源与调度类**（9、11）：日志、发现风暴。
- **协作类**（12）：接口变更。

这个分类本身就是一个很好的面试回答：被问到"最常见的问题是哪几类"时，你能给出结构，而不是列流水账。

### 10.2 展开三个问题

**问题 7（仿真到实机）**。仿真里的底盘模型符号约定是"左轮正转为前进"，实机一侧电机安装方向相反，所以同一个正速度，实机一侧轮子反转。现象是直线走成了原地转或方向反。度量：用最小动作（只发左轮）观察编码器符号；对比仿真与实机编码器的符号表。解决：把每个电机的方向符号与减速比放入设备描述 YAML，适配器统一应用；契约测试增加"原地左转/前进/后退"三个方向用例，对每种底盘都必须跑。教训：仿真通过只证明接口形状正确，不证明符号约定与实机一致。

**问题 8（规则变更）**。规则中把某个最大速度写成了 80（单位 cm/s）而非 0.8（m/s），上线后几乎所有提案被判越界。发现方式是监控的拒绝率按原因码拆分后，E_LIMIT 骤增。处理：先回滚策略版本（策略与代码分离，回滚只需切换版本号），再用影子模式回放前一天的流量，对比新旧规则的判决差异，定位到单位错误。预防：规则文件的 schema 里加单位字段并校验；新规则先影子运行，再灰度到少数设备。

**问题 10（重启）**。校验服务重启后，内存中的去重表丢失，一条仍在有效期内的导航提案被重复投递而再次接受。解决方式有两层：定期快照到本地文件，重启后先静默一个有效期窗口；同时执行端也保留自己的去重，**去重不能只靠一处**。

## 11. 联调过程

### 11.1 台架与分层联调

联调台架：3 台小车加仿真。顺序是 **仿真 → 单机 + 模拟对端 → 3 台台架**。每一步都跑同一组契约测试和回放输入，出现差异就回退一步定位。

### 11.2 联调日历（典型一周）

| 日 | 内容 | 产出 |
|---|---|---|
| 周一 | 冒烟：启动顺序、发现与注册、版本与配置哈希核对 | 启动清单、配置差异表 |
| 周二 | 状态链：时间戳、有效性、陈旧降级；NTP 偏移记录 | 年龄分布图 |
| 周三 | 命令链：映射、限幅、看门狗；原地左转/前进/后退方向用例 | 方向用例结果 |
| 周四 | 故障注入：tc netem 加延迟与丢包、杀进程、时钟跳变、重复提案 | 故障矩阵与预期对照 |
| 周五 | 安全链：绕过测试、规则表、审计字段检查 | 问题清单与修复计划 |

### 11.3 故障注入矩阵（节选）

| 注入 | 参数 | 预期 |
|---|---|---|
| 延迟 | 50 ms、100 ms、200 ms | 命令链不误停；状态年龄上升但不超限 |
| 丢包 | 5%、10%、30% | 状态偶发丢失不触发 STALE；30% 时进入降级 |
| 杀进程 | 校验服务、状态管理器 | 默认拒绝；stop 放行；看门狗停车 |
| 时钟跳变 | 向前/向后 | 单调时钟不受影响；跨设备时间标记同步异常 |
| 重复提案 | 同 idem_key 发两次 | 只执行一次，第二次返回已有结果 |

### 11.4 联调中的沟通方式

每次联调前先写"本轮目标与通过标准"；联调中所有现象用 proposal_id、seq 和单调时间记录，不凭印象描述；联调后当天整理问题清单，标明归属（我的模块、平台、驱动、测试）。**归属清楚，才不会互相等待。**

| 驱动同事 | 稳定的适配接口 | 接口变更先出说明，给迁移期 |
| 调度/上层应用 | 任务回执和错误码的语义 | 文档化原因码；提供模拟器便于他们本地测试 |
| 测试同事 | 可重复的用例与回放数据 | 提供假时钟、假设备与录制工具 |
| 硬件/底盘同事 | 符号、限幅、安装方向的真实参数 | 联调前核对设备描述 YAML |
| 导师 | 方向性决策和优先级 | 每周一次进展同步；带着建议提问 |

流程上：代码通过合并请求（PR）评审后合入；每日简短站会；跨模块接口变更先写接口说明再改代码。

### 12.3 冲突解决：一个典型情景

**情景**：调度器一侧希望提案超时从 2 s 放宽到 10 s，理由是网络不稳；我这边认为放宽会让过期动作更容易执行。
**做法**：先问清楚真实需求（是偶发网络抖动，还是任务本身就长）；然后把两个方案的代价量化：放宽到 10 s 意味着去重窗口要到 20 s 以上，TOCTOU 窗口也扩大；而对运动类提案，有效期应更短，对导航目标类可以更长。最后提出折中：按动作类型区分有效期（运动类约 2 s，导航目标类约 30 s），并加重试，而不是统一放宽。把决定和理由写进接口说明，由导师确认。
**要点**：对事不对人；用数字而不是形容词；给折中方案；决定写下来。

### 12.4 向上沟通：汇报的结构

"目标—现状—问题—方案—需要的支持"。例如"状态陈旧误判：现状是联调时 STALE 偶发；原因是上限与周期没有联动；方案是上限由周期派生；需要平台同事确认发布周期不会被动态调整"。

## 13. 经验教训

1. **先写验收方式，再写代码**。每个需求都要有一个"如何证明"的测试。
2. **边界上的假设是故障主因**：时间、坐标系、重复投递、默认值、单位、符号。
3. **能推导出来的参数不要独立配置**：陈旧上限、Deadline、看门狗都由周期派生。
4. **先度量，再优化**。每次优化都写出现象、度量方法和回归。
5. **保守默认**：缺失字段采用保守档位，不要默认放开。
6. **日志字段统一比日志量大重要**：proposal_id、seq、单调时间贯穿全链路。
7. **仿真通过不等于实机通过**：符号、安装方向、延迟特性必须在实机验证。
8. **说清楚不知道的**：没有测过的数字不说成实测；被追问内部细节时，转到"如何测、如何判断"。
9. **接口变更先出说明**，并给过渡期。
10. **门不是万能的**：它限定动作包络，不保证决策质量；需要和输入隔离、人工确认、独立硬件保护配合。

## 14. 十二个英文面试问答（含 L2 追问）

> 每题含 L1 回答、L2 追问回答，并附中文译文。所有数值为"设计取值"，用 *in our design, roughly*。

**Q1. How did you take this project from nothing to something running?**

> I started by turning the goal into acceptance tests: a new base needs only an adapter, ROS commands drive any registered base, and no plan reaches hardware without a gate. Then I froze the interfaces, got one device working end to end, added a second to prove reuse, and only then added state management, coordination and the safety chain. Each milestone exited on a test passing, not on code being written.

译：我先把目标变成验收测试：新底盘只需写适配器、ROS 命令能驱动任何已注册底盘、任何计划不经门不能到硬件。然后冻结接口，先打通一个设备，再加第二个证明复用，之后才加状态管理、协同和安全链。每个里程碑以测试通过为退出条件，而不是代码写完。

- **L2.** *Why add the second device so early?*
> Because one device cannot prove an abstraction; it only proves a wrapper. The second device is where the interface either holds or reveals what I had leaked from the first.

译：因为一个设备只能证明封装，不能证明抽象；第二个设备才会检验接口是否站得住，或暴露我从第一个设备泄漏进接口的东西。

**Q2. How fast does each layer run and why?**

> In our design the task layer is event driven, planning runs at five to ten hertz, velocity commands at twenty, state is published at twenty, the IMU is sampled at one hundred hertz, and the microcontroller loops run at one hundred to one thousand. Each lower layer is several times faster than the one above, and each rate is set by what its consumers need and by the network budget, not by what is possible.

译：我们的设计里任务层事件驱动，规划 5 到 10 Hz，速度命令 20 Hz，状态发布 20 Hz，IMU 100 Hz，MCU 回路 100 到 1000 Hz。每个下层比上层快数倍，每个速率由消费者需求和网络预算决定，而不是由"能做到多快"决定。

- **L2.** *How do you check a rate is right?*
> I measure period jitter and data age at the consumer. If the 99th percentile jitter is within a fraction of the period and age stays under the staleness limit, the rate is adequate; if not, I look for the bottleneck before raising anything.

译：我在消费端测周期抖动和数据年龄。若第 99 分位抖动在周期的一小部分以内且年龄低于陈旧上限，则速率合适；否则先找瓶颈，而不是先提速率。

**Q3. How do you handle multi-source timestamps?**

> Stamps come from a monotonic clock, preferably the measurement time. Across devices I align with NTP, which gives roughly ten milliseconds of uncertainty, so no control loop depends on cross-device time. For fusion I interpolate to a reference time and I never extrapolate beyond a short window without marking the value as estimated.

译：时间戳来自单调时钟，优先测量时间。跨设备用 NTP 对齐，不确定度约十毫秒，所以没有控制回路依赖跨设备时间。融合时插值到参考时间，不在很短窗口之外外推，除非把值标为推算值。

- **L2.** *What did you do when a device's clock jumped back?*
> The age was being computed from the device's wall-clock stamp, so the sample looked stale. I anchored age on the local receive time, marked backwards stamps suspect and raised a health event, then added clock-jump fault injection to the test suite.

译：年龄原先由设备的墙上时间戳计算，样本因此看起来陈旧。我改为以本机接收时间为锚，把倒退的时间戳标为可疑并上报健康事件，然后在测试里加入时钟跳变故障注入。

**Q4. Why is state published at twenty hertz when the IMU is at one hundred?**

> Consumers above the motion layer do not need more, and broadcasting one hundred hertz would load the network for no benefit. The state manager aggregates at twenty hertz and publishes immediately on important changes; loops that need the raw rate read it locally.

译：运动层以上的消费者不需要更多，100 Hz 全网广播只会无谓增加网络负担。状态管理器按 20 Hz 聚合，重要变化即时发布；需要原始速率的回路在本地读取。

- **L2.** *What did it change?*
> In our design the state traffic dropped to about a fifth, and the data age at subscribers improved because queues stopped building up. I would say that as a design expectation and then confirm it by measuring age percentiles.

译：在我们的设计里状态流量降到约五分之一，订阅端的数据年龄也因队列不再堆积而改善。我会把它说成设计预期，再用年龄分位数去验证。

**Q5. How do you choose the command period and the watchdog?**

> The command period comes from the base's response and the network; twenty hertz by default. The watchdog is derived from stopping distance: distance travelled during the timeout plus braking distance must fit inside the safety margin. In our design it is about two hundred milliseconds, roughly four command periods, with a two-in-a-row rule.

译：命令周期由底盘响应和网络决定，默认 20 Hz。看门狗由停车距离推出：超时期间走过的距离加制动距离必须小于安全距离。我们的设计约 200 ms，约 4 个命令周期，并要求连续 2 次判定。

- **L2.** *Why four periods, not two or eight?*
> Two is too sensitive to a single late packet on Wi-Fi; eight lets the robot travel too far after the source dies. Four balances nuisance stops against stopping distance, and I re-check it against the distance formula whenever the speed tier or the command rate changes.

译：2 个周期对 Wi-Fi 上单个迟到的包太敏感；8 个周期会让来源失联后机器人走得太远。4 个周期在误停与停车距离之间折中，速度档位或命令速率变化时我会用距离公式重新核对。

**Q6. How did you configure DDS QoS and what happens with packet loss?**

> By data nature. High-rate state is best effort, volatile, keep last one, with a deadline of about twice the period. Capabilities are reliable and transient-local. Commands are reliable and volatile. With ten percent loss, three consecutive state losses are about a thousandth of the time, so a three-period staleness limit does not fire on isolated losses.

译：按数据性质配置。高频状态 BestEffort、Volatile、KeepLast(1)，Deadline 约 2 倍周期；能力记录 Reliable + TransientLocal；命令 Reliable + Volatile。10% 丢包时连续丢 3 条状态的概率约千分之一，所以 3 个周期的陈旧上限不会被孤立丢包触发。

- **L2.** *What goes wrong if state is configured reliable with keep-all?*
> Under a weak link the writer buffers and retransmits old samples for slow readers, queues grow and the freshest value waits behind stale ones. Reliability hurts timeliness for data where only the latest value matters.

译：弱网下发布端为慢读者缓存并重传旧样本，队列增长，最新值排在陈旧值后面。对只关心最新值的数据，可靠性反而损害及时性。

**Q7. How does task dispatch handle timeouts and retries?**

> There are staged receipts with a timeout per stage. If the first receipt does not arrive in about half a second, the dispatcher retries with backoff, at most three times, always with the same idempotency key. After that the task is marked unknown and escalated, rather than assumed lost or done.

译：回执分阶段，每阶段有超时。第一个回执约半秒未到，调度器带退避重试，最多 3 次，始终使用同一个幂等键。之后任务标为未知并升级，而不是假定丢失或已完成。

- **L2.** *Why can't you just guarantee exactly-once delivery?*
> Over an unreliable network a sender cannot distinguish a lost request from a lost reply. So I use at-least-once delivery with idempotent execution, which gives the effect of exactly once, provided the de-duplication window outlasts the retry window.

译：在不可靠网络上，发送方无法区分请求丢了还是回复丢了。所以我用至少一次投递加幂等执行，得到效果上的恰好一次，前提是去重窗口长于重试窗口。

**Q8. What is the latency budget of the safety chain?**

> In our design the command-to-actuator budget is under one hundred milliseconds. The nominal sum of the hops is far lower, around ten milliseconds, and the remainder is margin for retransmission and scheduling jitter. I would verify it with per-hop timestamps and the 99th percentile rather than quote it as measured.

译：我们的设计里命令到执行器的预算小于 100 毫秒。各跳名义合计远低于此，约十毫秒，其余是给重传和调度抖动的余量。我会用逐跳时间戳和第 99 分位验证，而不是把它说成实测。

- **L2.** *What was the biggest saving?*
> Moving the freshness check from a remote query on every request to a local state snapshot that the validator keeps up to date. That removed an inter-process round trip from the hot path, and a stale snapshot makes the validator reject by default.

译：把新鲜度检查从每次请求的远程查询，改为校验器本地维护的状态快照。这从热路径上去掉了一次跨进程往返，并且快照陈旧时校验器默认拒绝。

**Q9. Describe an optimisation you did, with how you checked it.**

> The phenomenon was occasional stale warnings during bench tests. I measured per-topic bandwidth and data age at subscribers, found the full-rate IMU stream was loading the Wi-Fi link, and changed to a twenty hertz aggregate with event-triggered updates and local reads for fast loops. Then I re-ran the staleness cases, the emergency-event latency case and a replay comparison to be sure nothing else moved.

译：现象是台架测试里偶发陈旧告警。我测了各 Topic 带宽和订阅端数据年龄，发现全速率 IMU 流占了 Wi-Fi，于是改为 20 Hz 聚合加事件触发更新，快回路改本地读取。然后重跑陈旧用例、急停事件延迟用例和回放对比，确保没有别处变化。

- **L2.** *How do you avoid optimising the wrong thing?*
> I always measure first and write down the hypothesis. If the change does not move the metric I expected, I revert it, because an optimisation that cannot be shown is just a risk.

译：我总是先测量并写下假设。如果改动没有让预期指标变化，就回退，因为无法证明的优化只是风险。

**Q10. Tell me about a bug that only appeared on the real robot.**

> In simulation the turn direction was right but on the robot it was reversed. The cause was a motor mounted the opposite way, so the sign convention differed. I moved per-motor direction and gear ratio into the device description, applied them once in the adapter, and added in-place-left-turn, forward and reverse cases to the contract tests for every base.

译：仿真里转向方向正确，实机却反了。原因是电机安装方向相反，符号约定不同。我把每个电机的方向和减速比放进设备描述，在适配器里统一应用一次，并给每种底盘的契约测试加入原地左转、前进、后退用例。

- **L2.** *Why wasn't this caught earlier?*
> Because simulation validated the interface shape, not the physical sign convention. The lesson is that every new hardware type needs direction cases on the first day.

译：因为仿真只验证了接口形状，没有验证物理符号约定。教训是每种新硬件第一天就要有方向用例。

**Q11. How do you run integration with several robots?**

> Incrementally: simulation, then a single robot with simulated peers, then a bench of three robots. At every step the same contract tests and the same recorded inputs run, and I inject delay, loss, process kills and clock jumps with written expected behaviour. I document each finding with an owner so nobody waits on someone else.

译：渐进式：仿真，再单机加模拟对端，再三台机器人台架。每一步跑同样的契约测试和同样的录制输入，并注入延迟、丢包、杀进程、时钟跳变，预期行为事先写好。每个发现都登记归属，避免互相等待。

- **L2.** *What do you do when you cannot reproduce a field failure?*
> I improve the evidence rather than guess: confirm the effective configuration hashes match, collect the correlated logs by proposal id, and try to reproduce with the recorded stream and the same fault injection. If I still cannot, I add the missing log field so the next occurrence is explainable.

译：我先改善证据而不是猜测：确认生效配置哈希一致，按 proposal id 收集关联日志，用录制数据流和同样的故障注入尝试复现。仍不能复现，就补上缺失的日志字段，使下次出现时可以解释。

**Q12. How do you work with other teams and resolve a disagreement?**

> I depend on the platform team for the base and middleware, and on driver colleagues for existing drivers. For interface changes I write the change down first with old and new fields, defaults and a migration path. When two requests conflict, I find the real need, quantify each option, propose a middle path and let my mentor decide, then record the outcome.

译：我依赖平台团队提供底座和中间件，依赖驱动同事提供既有驱动。接口变更我先写说明：新旧字段、默认值、迁移路径。两个请求冲突时，我找出真实需求，量化每个方案，提出折中，请导师决定，并记录结果。

- **L2.** *Give a concrete case.*
> A scheduler owner wanted a longer proposal validity because of flaky Wi-Fi. A longer window would also widen the replay and de-duplication windows, so I proposed validity by action type, short for motion and longer for navigation goals, plus bounded retries. We recorded the decision in the interface note.

译：一位调度器负责人因 Wi-Fi 不稳想延长提案有效期。更长的窗口也会扩大重放和去重窗口，所以我提出按动作类型设有效期：运动类短，导航目标类长，再加有上限的重试。我们把决定写进了接口说明。

## 15. 本章自测

1. 不看表，说出各层频率，并解释"状态为什么是 20 Hz 而 IMU 是 100 Hz"。
2. 手算：20 个设备、20 Hz、250 B 负载、60 B 开销的带宽；500 kbit/s 经典 CAN、800 帧/s 的总线占用。
3. 手算停车距离：$v=0.8$ m/s、看门狗 0.2 s、检测滞后 0.05 s、$a=1.0$ m/s²。
4. 说出超时、重试、去重三者的数量关系（去重窗口必须长于重试窗口）。
5. 任选一次优化，按"现象 → 度量 → 瓶颈 → 改动 → 对比 → 回归"六步讲完，并说明数字是设计取值。
6. 从十二个问题里挑三个，按"时间类/投递类/配置类"归类。
7. 用英文 90 秒回答 Q1 与 Q12。

**参考答案要点**：2 题：124 kB/s ≈ 0.99 Mbit/s；CAN 占用约 21%。3 题：$0.8\times0.25+0.32=0.52$ m。
