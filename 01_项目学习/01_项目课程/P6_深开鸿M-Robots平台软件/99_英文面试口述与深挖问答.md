## 0. 使用规则：三种句子的置信度

> **提示**：以下每个英文答案里的句子可分为三类。上场前，把答案里不符合你实际情况的地方改掉。

| 标记 | 含义 | 怎么说 |
|---|---|---|
| **[CV]** | CV / PS 明确写了的事实 | 可以直接用 "I built / I implemented / I standardised..." |
| **[设计]** | 这类系统的典型设计与原理，CV 没写具体实现 | 用 "typically", "in a design like this", "the way I think about it"。如果你确实就是这样实现的，可去掉限定词 |
| **[待补]** | 面试官可能追问的实机细节 | 用你自己的真实答案替换；没有就用第 2 节的诚实模板 |

CV 里的三条事实（你随时可以放心说）：

1. I built a unified capability model for sensors, actuators and controllers in C++ on OpenHarmony, and mapped ROS/ROS2 motion commands to low-level drivers, so motion-control code could be reused across hardware.
2. I standardised timestamps, coordinate frames and validity checks across multi-source perception and actuator feedback, so the motion-control and task layers get a consistent, trusted robot state.
3. I implemented device discovery, capability registration, state synchronisation and task dispatch over M-DDS, and gated task plans through an action-proposal, policy-check, execution and state-feedback chain.

## 1. 三个长度的口述稿

### 1.1 30 秒版（约 75 词）

> I'm a robotics platform intern at Kaihong, working on M-Robots, a multi-robot platform on OpenHarmony. I built a unified capability model in C++ so ROS and ROS2 motion commands can drive different hardware through one interface, I standardised timestamps, frames and validity so the control and task layers get a trusted robot state, and I implemented discovery, registration and task dispatch over M-DDS. The part I enjoy most is the chain that checks a task plan before any actuator moves.

译：我在深开鸿做机器人平台实习，平台是 OpenHarmony 上的 M-Robots。我做了 C++ 统一能力模型，使 ROS/ROS2 命令通过一个接口驱动不同硬件；统一了时间戳、坐标系和有效性，给控制和任务层可信状态；在 M-DDS 上实现了发现、注册和任务分发。最感兴趣的是在执行器动之前检查任务计划的那条链。

### 1.2 90 秒版（约 220 词）

> I'm currently an intern on the M-Robots platform at Kaihong. It's a multi-robot platform on OpenHarmony for heterogeneous robots — different chassis, sensors and actuators.
>
> My work has three parts. First, a unified motion interface. I built a capability model in C++ for sensors, actuators and controllers, and mapped ROS and ROS2 motion commands onto the low-level drivers. That means motion-control code doesn't have to be rewritten for each piece of hardware.
>
> Second, robot state management. Data comes from several sources with different clocks, frames and quality, so I standardised timestamps, coordinate frames and validity checks. The motion layer and the task layer then get one consistent state that they can trust.
>
> Third, coordination and safe execution. Over M-DDS I implemented device discovery, capability registration, state synchronisation and task dispatch. And a task plan never goes straight to a robot: it passes through an action-proposal, policy-check, execution and state-feedback chain, so high-level decisions are constrained before they reach the actuators.
>
> It's an ongoing internship, so I can talk about the design and my own modules, but not proprietary details.

译：三块工作：统一运动接口、状态管理、协同与安全执行；任务计划不直接到机器人，经过提案-校验-执行-回传链；在职实习，可讲设计和我的模块，不能讲专有细节。

### 1.3 3 分钟版（约 450 词，建议分段练）

> **Context (20 s).** M-Robots is a platform that lets heterogeneous robots work together. The problem is that every robot has different hardware, different buses, different clocks and frames. Without a platform, each new robot means rewriting the control code, the state handling and the safety logic.
>
> **Part 1: Unified motion interface (40 s).** I built a unified capability model in C++ on OpenHarmony. Instead of asking "what model are you", the upper layer asks "what can you do, and within what limits". Sensors, actuators and controllers all describe themselves this way. ROS and ROS2 motion commands are mapped onto this model and then to the low-level drivers through adapters. So the same motion-control code can run on different hardware, with the hardware differences pushed into the adapters and parameters.
>
> **Part 2: State management (40 s).** I noticed that reuse across hardware only works if the state is consistent. Timestamps, frames and validity differ between sensors and actuators. So I standardised them: one time base, a common frame convention, and validity checks such as range, staleness and finiteness. The point is not only a clean number but a number with known quality, so the layers above can decide whether to trust it.
>
> **Part 3: Coordination and safe execution (60 s).** Over M-DDS I implemented device discovery, capability registration, state synchronisation and task dispatch. On top of that is the chain I find most interesting. A task plan is turned into a structured action proposal. A policy check decides, using the current trusted state, whether to accept it, adjust it or reject it. Only approved commands reach execution, and execution results and robot state are fed back. This keeps task planning, which is slow and flexible, separate from real-time control, which has to be deterministic.
>
> **Why it matters (20 s).** It made me realise that for robots the hard part is often the software around the controller — consistency, interfaces and safety — and that when plans come from learned or AI-based planners, a gate like this is essential.
>
> **Boundary (10 s).** It's an ongoing internship, so I'll keep to design and my own modules.

译：背景 → 统一运动接口 → 状态管理（复用依赖状态一致）→ 协同与安全链（慢而灵活的规划与确定性实时控制分离）→ 意义（AI 规划更需要门）→ 保密边界。

> **练习建议**：先背段落标题（Context / Interface / State / Chain / Why / Boundary），再用自己的话说。每段不超过 4 个事实点。录音，对照 [技术口述方法](../../04_面试准备/01_面试总指南/08_技术口述方法_如何讲清一个项目.md)。

## 3. 问答库

> 格式：**Q**（英文）→ **A**（英文）→ 译/要点 → 追问方向。带 **[CV]** / **[设计]** / **[待补]** 标记。

### A. 平台与总览

**Q1. What is M-Robots, in one sentence? [CV]**

> It's a multi-robot collaboration platform on OpenHarmony for heterogeneous robots, and I work on its device abstraction and motion coordination.

译：OpenHarmony 上的异构多机器人协同平台，我做设备抽象和运动协调。
追问：异构指哪些方面？→ 硬件、总线协议、时钟与坐标、规模。

**Q2. What problem does a platform like this solve? [设计]**

> Without a platform, every robot is a custom integration: control code tied to specific motors, state handled differently per sensor, and ad hoc networking. A platform pushes the variable parts — hardware, protocols — below a stable interface, so motion code, state and tasks are reusable, and coordination and safety are done once.

**Q3. Describe the architecture. [设计]**

> Typically in five layers: the operating system and drivers at the bottom; a device-abstraction layer with the capability model and adapters; a motion-and-state layer; a coordination-and-safety layer over a distributed bus; and the task layer on top. Commands flow down through a policy check, and state flows up after being validated.

追问：哪层最难？→ 层间一致性（时间、坐标、有效性）和安全链。 `【按实际架构微调】`

**Q4. How does it relate to ROS2? [CV + 设计]**

> It works with ROS and ROS2 rather than replacing them. ROS and ROS2 motion commands are mapped through the capability model to the low-level drivers on OpenHarmony. ROS2 already gives a common language for commands and tools; the platform makes hardware under OpenHarmony available to it.
> `【待补：接入方式（桥接/原生/DDS层）可公开程度】`

**Q5. Why OpenHarmony rather than Linux with ROS2? [设计]**

> The platform targets OpenHarmony devices, which come with a driver framework, componentised builds, and distributed capabilities. My job was to make the ROS-style ecosystem usable on that system. I can't speak to the business reasons for the choice.

**Q6. What is your role? [CV]**

> Robotics platform intern. I independently developed and integrated device abstraction, state management, distributed coordination and the safe-execution chain.

**Q7. What was the most technically interesting part? [设计/个人]**

> The safe-execution chain, because that's where an AI or planner decision turns into a physical action. You have to think about time, state validity, identity, failure, and what happens when any layer is wrong.

**Q8. If you had one more month, what would you improve? [设计/个人]**

> I'd invest in replay and fault-injection testing for the policy and state layers, and in better observability — sequence numbers, latency histograms and an audit trail that links each proposal to its execution. `【按实际想法替换】`

### B. OpenHarmony 与 C++

**Q9. What is HDF? [通用]**

> OpenHarmony's driver framework. It separates configuration from code, loads drivers on demand, and exposes hardware through stable interfaces, so drivers are reusable across kernels and boards. Each driver typically has bind, init and release phases.

追问：Bind 和 Init 的区别？→ Bind 发布服务/让系统知道我；Init 真正准备硬件。

**Q10. How do processes communicate in OpenHarmony? [通用]**

> Typically through IPC with a proxy and stub model: the client holds a proxy, the service implements a stub, and arguments are serialised. Calls can block, so on any control path I'd use timeouts or asynchronous calls.

**Q11. How is C++ built on OpenHarmony? [通用]**

> With GN and Ninja. Code is organised in components, each with a bundle.json and BUILD.gn targets such as shared libraries, and dependencies on other components are declared explicitly. ArkTS applications are built separately with hvigor.
> `【待补：你实际使用的构建流程与版本】`

**Q12. Why did you choose C++ and not exceptions? [设计]**

> C++ because the platform needs performance, deterministic resource handling through RAII, and a rich type system for interfaces. For error handling in an embedded context, I'd prefer status codes or result types, because exceptions complicate real-time behaviour and are often restricted in such builds. `【如你实际使用异常，按实际】`

**Q13. How do you manage object lifetime across callbacks and threads? [设计]**

> With RAII and clear ownership: unique ownership by default, shared ownership only when really needed. For callbacks, I avoid capturing raw pointers to objects that might be destroyed, and I make shutdown stop callbacks before destroying state. Callbacks should enqueue work instead of calling back into the owner while locks are held.

追问：虚析构为什么重要？→ 通过基类指针删除派生对象，没有虚析构是未定义行为。

**Q14. What concurrency problems did you worry about? [设计]**

> Data races on shared state, deadlocks from holding a lock across a call-out, and jitter on periodic threads from blocking calls. The state store hands out immutable snapshots so readers never see a torn state. `【按实际实现替换】`

### C. 能力模型与命令映射

**Q15. What is a capability model? [CV]**

> A way for sensors, actuators and controllers to describe what they can do, with limits and units, instead of what model they are. For example, "planar velocity, max 0.5 metres per second, can't move sideways". Upper layers program against the capability contract, not the hardware.

**Q16. What fields does a capability description have? [设计 / 待补]**

> In a design like this: an identifier and version, data type, units and frame, limits such as maximum speed and acceleration, timing properties such as command rate and timeout, supported modes, and safety attributes. `【待补：你们实际字段，可公开程度】`

**Q17. How do you make the motion code reusable across hardware? [CV + 设计]**

> The control code depends on a capability interface. Each hardware type has an adapter that handles kinematics, units, signs, bus protocol and clamping. Because the differences live in adapters and configuration, the control logic doesn't change. Reuse doesn't mean zero changes — parameters and a few capability-dependent branches remain.

追问：怎么验证复用？→ 契约测试（对每个适配器运行同一测试集，含运动学往返一致性）+ 真机。 `【待补：实际验证过的硬件组合】`

**Q18. How would you map a Twist to a differential-drive base? [通用]**

> The left and right wheel speeds are the forward speed minus or plus half the track width times the yaw rate, divided by the wheel radius. With 0.3 metres per second and 0.5 radians per second on a 0.4-metre track and 5-centimetre wheels, that's 4 and 8 radians per second. (Textbook numbers.)

译：$\omega_{L,R}=(v\mp\omega L/2)/r$；示例 4 与 8 rad/s。

**Q19. And for a car-like base? [通用]**

> I compute a steering angle: arctan of wheelbase times yaw rate over speed. When speed approaches zero that demands a ninety-degree steering angle, which is infeasible, so the capability description should include the minimum turning radius and the mapper should clamp or reject.

**Q20. What does a Twist message lack? [通用]**

> It has no timestamp, no validity period, no source and no explicit frame. So the mapper adds a receive time, a timeout and a source tag; otherwise the command can't be audited or expired.

追问：为什么需要超时？→ 上层崩溃后机器人会保持最后速度。

**Q21. Where do you apply speed limits? [设计]**

> In several places on purpose: the policy layer checks against the capability description, the interface validates arguments, and the adapter clamps again because it knows the real hardware limits. If one layer has a bug or is bypassed, the next one still protects the robot.

**Q22. What did you do about different feedback quality between hardware? [设计]**

> I treat feedback quality as part of the state: each value carries validity and age. A base with only open-loop speed gets a different trust level from one with encoders. Controllers can then choose how to use the feedback instead of assuming it's perfect.

### D. 状态管理

**Q23. What does "consistent, trusted state" mean? [CV]**

> Consistent: values share a time base, a frame convention and units. Trusted: each value carries information about whether it can still be used — valid, stale, suspect or invalid — so consumers decide rather than silently trusting.

**Q24. How did you standardise timestamps? [CV + 设计]**

> One platform time base, typically a monotonic clock, applied on entry. I prefer the measurement time to the receive time, subtract a calibrated latency where only the receive time exists, and flag the source as weaker. I also check for backward, duplicated or future stamps. `【待补：实际时间基准与同步方式】`

**Q25. Why a monotonic clock? [通用]**

> Because intervals and timeouts must not jump. A wall clock can be corrected by NTP, producing negative or huge time differences. Cross-device comparison needs a synchronisation mechanism mapping clocks to a common timeline.

追问：NTP 精度极限？→ 往返延迟的一半，不对称延迟引起；PTP 靠硬件时间戳改善。

**Q26. How do you handle different sensor rates? [通用]**

> Align to a reference time with interpolation between samples, or hold the latest valid value with a known age. Extrapolation is only for very short windows and is marked as such.

**Q27. How did you unify coordinate frames? [CV + 设计]**

> Every sample declares its frame, static sensor extrinsics come from calibrated configuration applied centrally, and dynamic transforms are looked up at the sample's timestamp. The platform offers views in the base frame for motion control and in the map frame for the task layer. I used the same conventions as ROS — SI units, x forward, y left, z up.
> `【待补：你们的 frame 命名与外参来源】`

**Q28. What validity checks did you implement? [CV + 设计]**

> Finiteness, range, frame declaration, timestamp monotonicity, staleness, and rate-of-change. Others I'd consider are frozen-value and cross-source consistency. Each failure maps to a validity level, from valid through stale and suspect to invalid. `【待补：实际规则清单与阈值】`

**Q29. How do you choose a staleness threshold? [通用]**

> From the source period — a small multiple, say two to five periods depending on loss tolerance — and from the control loop's delay budget, whichever is tighter. It isn't one global number.

追问：陈旧之后怎么办？→ 保持（短时）→ 降级（限速）→ 安全动作（停车），并拒绝依赖它的提案。

**Q30. Is this sensor fusion? [CV 边界]**

> No. It's the data governance before fusion: time, frames and validity. Fusion filters assume aligned, valid inputs, so the platform ensures that. The fusion algorithms themselves are a separate concern. (In my navigation project I did the fusion with EKF/AMCL.)

### E. M-DDS 与分布式

**Q31. What is DDS? [通用]**

> A data-centric publish-subscribe standard. Publishers write to named, typed topics, subscribers read them, discovery is automatic, and quality of service is declared per endpoint — reliability, durability, history, deadline, liveliness and so on.

**Q32. What is M-DDS and how is it different from standard DDS? [待补]**

> `【待补：必须用你的真实信息回答。】` What I can say in general: I used M-DDS as the data layer for discovery, registration, state sync and task dispatch. For how it differs from standard DDS in implementation, I'd prefer not to guess or go into internals.

> **提示**：不要为了显得懂而编造 M-DDS 的内部。诚实 + 讲清标准 DDS 机制，比乱说更得分。

**Q33. How does device discovery work? [CV + 设计]**

> Typically two layers. The middleware discovers participants and matches endpoints. On top, an application-level announcement says what the device is. A liveliness lease detects when a device disappears, and a graceful shutdown disposes the instance. I also separate discovered, registered and active, because being seen on the network isn't the same as being ready to take tasks.
> `【待补：实际流程】`

**Q34. How does capability registration work? [CV + 设计]**

> After a device initialises and self-checks, it publishes a capability record, keyed by device ID. The record should be delivered reliably and be available to late joiners, so a scheduler that starts later still sees the latest one. Registration is validated for format, version and duplicate IDs, and ideally authenticated.

**Q35. Which QoS for state, and why? [设计]**

> For continuous state: best-effort, volatile, keep-last one, with a deadline. A stale state is worthless, so retransmission would only add delay; the deadline tells me when updates stop. For low-frequency critical state I might use reliable with transient-local.

**Q36. Which QoS for task dispatch? [设计]**

> Reliable delivery with a lifespan, plus application-level validity time, task IDs for idempotency and a receipt topic for stage reporting. Transient-local helps late-joining devices, but it also replays history, so it needs idempotency and expiry to avoid running old tasks.

**Q37. Reader reliable, writer best-effort. What happens? [通用]**

> They don't match — the offered reliability is weaker than requested — so the reader sees no data. In practice you look for an incompatible-QoS event. It's one of the first things I check when a topic is silent.

**Q38. Does DDS guarantee consistency across receivers? [通用]**

> No. It delivers samples according to QoS, but receivers see them at different times. Consistency comes from timestamps on a common time base and validity checks at the receiver.

**Q39. How does discovery scale? [通用]**

> With full-mesh discovery the cost grows roughly with the square of participants. In practice you partition domains or use partitions, use static peer lists or a discovery server, and avoid multicast on Wi-Fi.

**Q40. IPC or DDS — how do you choose? [设计]**

> IPC for request-response calls within a device where I need a result and permissions are easy to check. DDS for broadcasting facts like state or for loosely coupled many-to-many data and cross-device communication.

### F. 分层与实时

**Q41. Why separate task planning from real-time control? [CV + 设计]**

> Different time scales and failure modes. Planning may take hundreds of milliseconds and isn't deterministic; control must run on a fixed period. The upper layer passes setpoints with a validity time, and the lower layer runs on its own clock and stays safe if the upper layer goes silent.

**Q42. What is the interface between them? [设计]**

> A contract: a setpoint with timestamp, validity time, source and frame, going down; feedback with sequence acknowledgement, tracking error and saturation flags, going up. It's asynchronous: the control loop never waits for the planner. `【待补：实际接口】`

**Q43. What happens if the planner crashes mid-motion? [设计]**

> The setpoint expires and a watchdog fires. The control layer decelerates in a controlled manner and stops. On recovery, motion doesn't resume automatically; the planner must re-confirm.

**Q44. How does delay affect control? [通用]**

> A delay adds phase lag of crossover frequency times delay. At 20 rad/s, a 50 ms delay costs about 57 degrees (a textbook example), which can consume almost the whole margin. So unbounded delays — planners, networks, synchronous IPC — stay out of the control loop.

**Q45. How do you pick a watchdog timeout? [通用]**

> From stopping distance: distance travelled during the timeout plus braking distance must be less than the safety margin. The lower bound comes from network jitter. I don't guess it.

## 4. 重点：action-proposal / policy-check 链的多层追问

> 面试官最可能反复追问的话题。准备思路：先给"一句话 + 四阶段"，然后按追问层级逐层深入。每层都有标记，**未标 [CV] 的内容是典型设计，请核对后再用 "I" 陈述**。

### 4.0 开篇（任何形式都从这里开始）

**Q46. Tell me about the action-proposal / policy-check chain.**

> The idea is that a high-level task plan can never go straight to a robot. First it's expressed as a structured action proposal — which device, what action, with what parameters, from whom, valid until when. Second, a policy check decides from the proposal and the current trusted state whether to accept it, adjust it, or reject it with a reason. Third, only approved commands reach execution, which has its own limits and a watchdog. Fourth, results and robot state come back to the planner, so the loop is closed and every step is auditable. In short: planning proposes, a deterministic gate decides, control executes, and state tells everyone what really happened.

译：计划不能直接给机器人：先结构化提案；策略校验依据提案和可信状态裁决（接受/修改/拒绝+原因）；通过的命令才执行（执行层有自己的限幅和看门狗）；结果和状态回传，闭环可审计。 [CV 链 + 设计细节]

### Level 1：为什么

**Q47. Why do you need this chain at all? Why not trust the planner?**

> Because the planner works from a snapshot that may already be out of date, it can be wrong, it can be misused, and in the case of learned planners its output can't be exhaustively tested. And physical mistakes can't be undone. So I don't want safety to depend on the planner being right; I want a gate that holds even if it isn't.

**Q48. Isn't this just a speed limit?**

> A speed limit is one rule. The chain also checks identity and permission, whether the action is on a whitelist, whether the proposal is still valid, whether the robot is in a mode that allows it, whether the state it's based on is fresh, and spatial constraints. And it records the decision so it can be audited.

### Level 2：校验规则

**Q49. What kinds of rules does the policy check apply?**

> Typically: schema and finiteness; permission — who may do what to which device; an action whitelist; validity time; mode, such as manual or emergency stop; state freshness; ranges and speed or acceleration limits from the capability description; and spatial constraints like geofences. Others are conflict or ownership checks and rate limits. `【待补：你们的规则类别，可公开程度】`

**Q50. Walk me through one rule in detail — say, the geofence.**

> Given the current pose, the proposed speed after clamping and the duration, I predict the end point and check that it's inside the allowed region. In the simplest version it's a straight-line prediction — for example, from x equals 8 at 0.5 metres per second for 5 seconds you reach 10.5, outside a 0 to 10 area, so it's rejected or the duration is shortened. A real version checks the whole predicted path with the robot's footprint and braking distance.

追问：为什么用限幅后的速度？→ 否则检查的是一个永远不会被执行的命令。

**Q51. Where do the limits come from?**

> From the capability description of the device, not hard-coded in the rules. That means the same rule adapts to each device and registration data is the source of truth. That's also why registration has to be validated.

**Q52. In what order do you evaluate rules?**

> Cheap structural checks first — schema, identity, whitelist — then validity time, then state-dependent checks like mode and freshness, then limits, then spatial and conflict rules. Any rejection ends the evaluation: deny wins. The order matters, for instance the geofence must use the already clamped values.

### Level 3：裁决与降级

**Q53. What happens when a proposal violates a rule?**

> There are four outcomes: accept, modify, reject, or require confirmation. Safety-critical violations — wrong identity, expired proposal, stale state — are rejected. Non-critical limits can be clamped, but the caller is told exactly what was changed. High-risk or unfamiliar actions can require human confirmation. Every rejection carries a structured reason code.

**Q54. Why tell the planner what you changed?**

> Otherwise it plans on a false assumption — for example thinking the robot is going 0.8 when it's allowed 0.5. Transparency also helps an AI planner replan instead of blindly retrying.

**Q55. What does "degrade" mean in your design?**

> The system becomes more conservative when uncertainty increases: lower speed limits, smaller allowed area, extra confirmation. It's not loosening thresholds to let the proposal through. For instance, if the localisation is stale, I'd allow only slow, local motion or stop.

### Level 4：时间与竞态

**Q56. What if the state changes between the check and the execution?**

> That's the time-of-check to time-of-use problem. The typical remedies are: approval is short-lived — a ticket with a short expiry; the execution side re-checks cheap, critical conditions like mode, emergency-stop state and state freshness; and long actions are split into short segments that are renewed. `【待补：你们是否有凭据/复核机制】`

**Q57. How do you prevent a stale or replayed proposal?**

> Each proposal has an ID and a validity time. The checker rejects expired ones; the middleware's lifespan expires samples too; and the executing side de-duplicates by ID, so even if a proposal is delivered twice it's executed once.

### Level 5：失败与幂等

**Q58. What if the policy checker is down?**

> Default deny. Proposals are rejected rather than waved through, except stop-type actions which are always allowed. The execution side has its own limits and a watchdog, so one failing component doesn't become a physical hazard. Also, the emergency stop doesn't depend on this chain at all.

**Q59. What if the acknowledgment is lost and the planner retries?**

> You can't distinguish a lost command from a lost acknowledgement, so assume at-least-once delivery and make execution idempotent: the executing side keeps IDs of processed proposals and returns the previous result for duplicates. It's also why I prefer absolute goals over relative moves — "go to x equals 2" is safe to repeat, "move forward 0.5 metres" isn't.

**Q60. What does "completed" mean? How do you know the robot actually did it?**

> Sent isn't received, received isn't accepted, accepted isn't started and started isn't completed. Completed must be based on state feedback — the pose or joint state reaching the target — not on the bus write succeeding. That's why state feedback is the fourth stage.

**Q61. What does the watchdog do exactly?**

> The execution layer expects renewed commands or heartbeats. If they don't arrive within the timeout, it decelerates in a controlled way and stops, and reports an aborted receipt. The timeout comes from stopping distance and network jitter, and only valid new commands feed the watchdog.

### Level 6：安全架构

**Q62. Can someone bypass the check?**

> That's the central design concern: a gate is only as strong as its bypasses. The principle is a single path — the execution side only accepts commands with a valid approval from the checker, and the planner has no actuator handle, only a way to submit proposals. And I'd audit every execution against a proposal ID to detect any bypass. `【待补：实际权限/进程隔离方式】`

**Q63. Why is the checker a separate service rather than a library? [设计]**

> A library lives in the caller's process, so the caller can skip it. A separate service, with the execution side trusting only its approvals, makes bypassing require crossing a process boundary. The trade-off is an extra hop and a dependency, which is why the default for failure is to deny.

**Q64. Why isn't the emergency stop part of the chain?**

> The chain itself can fail, and an emergency stop has to work then. It should be independent, simple and close to the hardware, with the highest priority. The chain cooperates: in emergency stop mode the checker rejects all motion proposals until an authorised reset.

**Q65. What do you log for audit?**

> A linked record: the proposal with issuer and parameters; the decision with each rule's result, a summary of the state it used and the policy version; the approval; the execution events; and the final feedback. Because the decision logic is deterministic, recording its inputs lets me replay and explain any decision later.

**Q66. How do you test the chain?**

> Unit tests for every rule, including boundaries and rule order; properties such as "deny wins" and "stop is always allowed"; golden cases from past incidents; fault injection — down checker, lost acknowledgements, clock jumps, stale state; and replay of recorded inputs. On the robot, I'd trigger the watchdog and limits at low speed to prove they work.

**Q67. What are the limits of this approach?**

> It protects the physical envelope, not decision quality: it can't tell whether a task is wise, and it can't see hazards the sensors and rules don't know about. Rules can themselves be wrong or incomplete, so they need versioning, review, tests and shadow runs. So I treat it as a floor, alongside reactive safety and human confirmation.

**Q68. How would you roll out a rule change safely?**

> Version it, review it, replay recorded traffic through both old and new policies to see the differences, run the new one in shadow mode — logging only — and then enable it with a quick rollback path.

> **练习建议**：把 Q46–Q68 做成"追问阶梯"，请同伴随机从某一层开始追问，直到你答不出为止；答不出的点回到 08 章补。

## 5. AI 风险与研究方向

**Q69. Why is this chain especially relevant for AI or LLM planners?**

> Their outputs are probabilistic and can't be exhaustively tested, they can hallucinate parameters or confuse units, they can be influenced by untrusted text, and they plan from stale observations. If a planner is 99.9% right and makes a hundred proposals a day, I should expect mistakes. So the gate must not rely on the model behaving well.

**Q70. Can prompt injection make the robot do something unsafe?**

> It can make the planner propose something unsafe, but the proposal still has to pass identity, whitelist, limits and state checks, which are deterministic code outside the model. So the damage is bounded by what the planner's identity is allowed to request. Permissions shouldn't depend on the model's compliance.

**Q71. What did building this teach you about AI in robotics?**

> That the interface between a learned decision and a physical action is an engineering problem in itself: structured proposals, constrained action spaces, explicit rejection feedback, audit. And it showed me the limits of my own training: my machine-learning experience is mostly practical, and I want to understand failure modes and system-level safeguards on a firmer theoretical footing.

**Q72. What would you like to study to make the gate more principled?**

> Runtime assurance — a simple verified safety controller backing up a complex one — safe learning and shielding, formal ways to specify the safe set, uncertainty estimation to know when a model shouldn't be trusted, and how to verify a policy set for consistency. At the moment my rules are hand-written, and I want to learn when they're complete.

## 6. 测试、故障与行为面试（含 STAR）

**Q73. How did you test the platform? [待补]**

> `【用你实际做的测试替换。】` The approach I follow: keep logic deterministic with time passed in, unit-test boundaries, contract-test every adapter, then integration with fake drivers and clocks, fault injection, and finally hardware at low speed. Each stage introduces one real thing at a time.

**Q74. Tell me about a bug you found. (STAR) [待补；以下是安全的结构]**

> **Situation:** In a platform that feeds sensor data into motion control, inconsistent timing or frames can make the controller react to something untrue. **Task:** I needed to give the motion and task layers a state they can trust. **Action:** I traced the inconsistencies to their sources — different clocks, frame conventions and silent stale values — and standardised timestamps, frames and validity checks in one place, so consumers got values with known age and quality. **Result:** motion-control code could then be reused across hardware without per-device workarounds, and downstream code could tell a live value from an old one. **Learning:** the failure that worries me most is the one that looks normal.
> `【待补：把 Action 换成你真实遇到的一个具体问题（现象→定位→修复→验证）】`

**Q75. Tell me about a time you had to design an interface. (STAR)**

> **Situation:** Different hardware needed to be driven by the same motion code. **Task:** Design a model that hides differences without hiding limits. **Action:** I described devices by capabilities — what they can do and within which limits — put hardware differences in adapters, fixed units and frame conventions, and made errors explicit with status codes. **Result:** the same control code could drive different hardware through one interface, with ROS and ROS2 commands mapped on top. **Learning:** a good interface makes limits visible; a bad one hides them.

**Q76. How do you handle disagreement or ambiguity about requirements? (STAR) [待补]**

> `【用你的真实经历。】` A safe structure: I write down the assumption, check it with the person who owns the requirement or the hardware, and when unsure, I choose the more conservative behaviour — such as rejecting instead of guessing — and make it configurable.

**Q77. What's your biggest weakness in this project? [诚实]**

> My experience with formal methods and rigorous evaluation is limited. My rules are hand-written and tested, but I can't yet prove they're complete. That's a big reason I want postgraduate training: to learn the theory behind safe execution and learning-based planning, not only the practice.

**Q78. How do you work with a mentor or team as an intern? [待补]**

> I try to bring a design note and a small prototype to reviews, ask specific questions, and write tests with the code so changes are easy to verify. `【按实际】`

## 7. 陷阱题与反问

### 7.1 陷阱题

**T1. "So you replaced ROS2?"**

> No. The platform is compatible with ROS and ROS2; it maps their commands onto drivers under OpenHarmony.

**T2. "You designed the whole platform?"**

> No. The platform belongs to the team. I independently developed and integrated several modules on it — the device abstraction, state management, distributed coordination and the safe-execution chain — within the team's architecture.

**T3. "Does your system guarantee safety?"**

> No system can guarantee that in absolute terms. The chain bounds the physical envelope under the rules and assumptions we made, and layers fail-safes and watchdogs. Its guarantees are only as good as the rules, the state quality and the testing.

**T4. "How many robots does it support? What latency?" [待补]**

> I don't have a number I can quote with confidence. I'd rather say how I'd measure it than give you a figure I can't back up.

**T5. "Is an LLM controlling your robots?" [待补]**

> The chain is designed so that whatever produces the plan — a scheduler, an operator or a learned planner — takes the same path to the actuators. `【按事实说明提案的实际来源】`

**T6. "Isn't this over-engineering?"**

> The cost of a mistake is physical, and it can't be undone, so I think a gate is proportionate. But rules should be few, clear and testable, and the severity of response should match the risk: reject, clamp or ask.

**T7. "Why not do everything on the robot, without distribution?"**

> A single robot can. A platform with several robots needs shared discovery, state and tasks. I'd keep time-critical control local and use the distributed layer for information and coordination.
