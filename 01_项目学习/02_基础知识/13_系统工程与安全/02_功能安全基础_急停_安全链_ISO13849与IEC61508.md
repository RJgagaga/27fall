## 1. 要解决的问题

机器人的动力部件（电机、气缸、泵、发射机构）储存或产生能量。控制软件有 bug、传感器失灵、总线断线、操作员误触，任何一个都可能让能量以不期望的方式释放：轮子一直转、手臂撞向人、水泵一直开。**功能安全要做的是：把"出故障后会造成伤害"的概率压到可接受的水平，而且能用文档与计算说明这件事。**

关键点有三个：

1. 安全不是"不出故障"，而是"出故障时落到安全状态"。因为任何硬件和软件都会失效。
2. 安全要被**量化**与**论证**，不能只说"我们很小心"。工业界用"安全完整性等级"（SIL）或"性能等级"（PL）来表达论证的强度。
3. 能做安全功能的组件和方法是**被限定**的：越靠近安全，越倾向于简单、可验证、独立于复杂软件。

对学生项目来说，不要求取得认证，但面试官会问："你的系统怎么保证失败时不会失控？" 本章给出的是可以诚实、清晰回答这个问题的概念框架。

## 2. 符号与术语

| 术语/符号 | 含义 |
|---|---|
| 危险（hazard） | 可能造成伤害的潜在根源，如旋转的轮子、失控的手臂 |
| 风险（risk） | 伤害发生概率与严重程度的组合 |
| 安全功能（safety function） | 为降低某个风险而专门实现的功能，如"急停时切断驱动能量" |
| 安全状态（safe state） | 失败时系统应进入的、不再产生危险的状态，如失能、零力矩、刹车 |
| 失效（failure） | 组件不再完成要求的功能 |
| 危险失效（dangerous failure） | 使安全功能失灵的失效 |
| 安全失效（safe failure） | 使系统趋向安全状态的失效，如误触发停车 |
| $\lambda$ | 失效率（failure rate），单位 1/h |
| $\lambda_D$、$\lambda_S$ | 危险失效率、安全失效率 |
| $DC$ | 诊断覆盖率（diagnostic coverage），被诊断发现的危险失效占比 |
| $\lambda_{DU}$ | 未被检测到的危险失效率，$\lambda_{DU}=\lambda_D(1-DC)$ |
| $PFD$ | 要求时的危险失效概率（probability of failure on demand），低要求模式 |
| $PFH$ | 每小时危险失效概率（probability of dangerous failure per hour），高要求/连续模式 |
| $\beta$ | 共因失效因子（common-cause factor） |
| $T_1$ | 验证测试间隔（proof-test interval） |
| SIL | 安全完整性等级（safety integrity level），IEC 61508 体系，1～4 级（具体区间未核对） |
| PL | 性能等级（performance level），ISO 13849-1 体系，a～e 级（具体区间未核对） |
| E-stop | 急停（emergency stop） |

## 3. 安全的基本概念：危险、风险、安全功能、安全状态

### 3.1 三个常被混淆的词

- **安全（safety）**：系统不会伤害人和环境。关心的是**故障与误用**造成的后果。
- **可靠性（reliability）**：系统在规定时间内持续正常工作的概率。关心的是"能不能一直工作"。（见 [03 可靠性](./03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)）
- **信息安全（security）**：系统不被恶意攻击。关心的是**主动的恶意**。（见 [06 信息安全](./06_信息安全与权限_DDS-Security_OTA安全.md)）

三者相关但目标不同：一个系统可以非常可靠但不安全（一直稳定地朝人冲过去）；也可以很安全但不可靠（一有风吹草动就停车）。"误停车"对安全是**安全失效**，对可用性是损失，设计时要在两者间权衡。

### 3.2 风险评估的思路

风险评估常用三个因素（概念性描述，具体分级表未核对）：

1. 伤害**严重程度**（轻伤、重伤、致命）；
2. 人**暴露**在危险中的频率与时间；
3. 危险事件发生时**避免伤害的可能性**（人能不能躲开）。

三个因素的组合决定所需的 PL（ISO 13849 的风险图思路）或 SIL（IEC 61508 的风险降低思路）。直觉：严重、频繁暴露、难以躲避的场景，要求的安全功能更可靠。

### 3.3 安全功能与安全状态

安全功能由三部分串联而成：**传感（检测危险条件）→ 逻辑（判断）→ 执行（切断能量）**。例如急停：按钮（传感）→ 安全继电器（逻辑）→ 接触器切断电机电源（执行）。整个功能的失效概率是三部分的总和（串联）。

**安全状态**必须事先定义，而且要想清楚"安全"具体是什么：

| 系统 | 安全状态 | 注意点 |
|---|---|---|
| 轮式底盘 | 减速停车，电机失能 | 突然断电是否会让机体倾倒？平衡车类系统"断电"本身可能不安全 |
| 机械臂 | 失能抱闸，或保持位置 | 重力负载下"失能"可能使手臂掉落，需要抱闸 |
| 水泵 | 关闭继电器 | 继电器粘连时需要上一级保护 |
| 发射机构 | 摩擦轮停转，拨盘停止 | 弹仓中已有弹丸 |
| 平衡类机器人（P1/P7） | 保护性失能并缓降/倒地 | 失能即倒地，需限制倒地的冲击与周围人的距离 |

最后一行是个重要提醒：**对不稳定系统，"停"不等于"安全"**。P1 的跌倒恢复保护、使能互锁与实验时的人工扶持，正是为了应对"安全状态本身不稳定"的问题。

## 4. 两套标准的定位（概念，未核对）

> **注意**：本节只讲两套标准"是什么、面向谁"的常识性概念。标准的条款号、表格、具体数值区间、认证要求均**未核对**，不得当作条文引用。需要准确内容时请查标准原文。

| 项目 | IEC 61508 | ISO 13849-1 |
|---|---|---|
| 全称（未核对） | Functional safety of electrical/electronic/programmable electronic safety-related systems（版本年份常见为 2010，未核对） | Safety of machinery — Safety-related parts of control systems — Part 1: General principles for design（版本年份常见为 2015，未核对） |
| 领域 | 通用基础标准，电气/电子/可编程系统，很多行业标准由它派生 | 机械安全，工业机械的控制系统安全相关部分 |
| 度量 | SIL 1～4 | PL a～e |
| 关键量 | PFD / PFH、硬件故障容错、系统性失效（软件、流程）措施 | 类别（Category B、1、2、3、4）、MTTFd、DC、CCF |
| 思路 | 全生命周期（需求、设计、验证、运维） | 以"结构类别 + 可靠性 + 诊断 + 共因"估算 PL |

一些在两套体系里都出现的**概念**：

1. **结构**：单通道、双通道（冗余）、带诊断的双通道。结构越强，能达到的等级越高。
2. **诊断覆盖**：能检测多少危险失效，检测后能否进入安全状态。
3. **共因失效**：冗余的两路因同一原因同时失效（同一电源、同一环境、同一设计缺陷）。
4. **系统性失效**：不是随机硬件坏掉，而是设计/软件错误，只能靠流程、评审、测试来降低。
5. **验证（proof test）**：定期测试把潜伏的故障找出来。

对你的项目来说，这些标准的作用是"提供一套结构化的词汇与思路"，让你在面试里能说出"我们采用了 X 类措施，它们对应标准里 Y 概念的精神"，同时诚实声明"项目没有做认证"。

## 5. 失效模式与诊断覆盖

### 5.1 随机失效与系统性失效

- **随机硬件失效**：电容老化、继电器粘连、传感器漂移。可以用失效率统计，可以用冗余缓解。
- **系统性失效**：需求写错、软件 bug、参数配置错、接口单位错。不是"概率"，只要条件触发就必现。冗余相同的软件**不能**缓解（两份同样的 bug）。需要评审、测试、多样性（diversity）设计。

这条区分解释了很多工程实践：为什么要做代码评审、为什么关键参数要有范围检查、为什么要做故障注入、为什么要避免"复制粘贴一份当冗余"。

### 5.2 检测覆盖与"安全失效分数"

危险失效率 $\lambda_D$ 分为两部分：被诊断发现的（可转入安全状态）和未发现的：

$$\lambda_{DD}=DC\cdot\lambda_D,\qquad \lambda_{DU}=(1-DC)\,\lambda_D$$

诊断的意义就在于把 $\lambda_{DU}$ 压低。常见的诊断手段：

| 失效 | 诊断手段 |
|---|---|
| 传感器卡死 | 合理性检查（值是否在变化）、冗余传感器比对 |
| 数据陈旧 | 时间戳新鲜度检查，序号连续性 |
| 通信丢失 | 超时（看门狗）、心跳 |
| CPU 死循环 | 硬件看门狗 |
| 输出级故障 | 回读（read-back），电流/电压监测 |
| 存储损坏 | CRC、ECC |
| 参数错误 | 范围检查，启动自检 |

诊断自身也会失效，这就是为什么高等级要求诊断本身也要有结构（如两路交叉监视）。

### 5.3 去抖与误触发的权衡

诊断条件通常需要"持续若干个周期"才触发，以避免噪声引起误停。设单次采样越限概率为 $p$（噪声下），要求连续 $N$ 次越限才判故障，则误触发概率约 $p^N$（假设独立）；而对真实故障的检测延迟增加 $N\cdot T_s$。这是一个典型的**安全失效 vs 危险失效**权衡：$N$ 越大，误停越少，但危险条件下反应越慢。后面第 9 节有手算。

## 6. PFD、PFH 与冗余架构的推导

> 本节公式是教科书常见的**简化近似**，用于理解概念；标准中对具体架构有更完整的公式与适用条件，**未核对**。

### 6.1 单通道（1oo1）

"1oo1" 表示 1 取 1：唯一一个通道失效即失效。假设未检测的危险失效率为 $\lambda_{DU}$（常数，指数分布），每隔 $T_1$ 做一次完整的验证测试并修复。在 $[0,T_1]$ 内，通道在 $t$ 时刻已失效的概率为 $1-e^{-\lambda_{DU}t}\approx\lambda_{DU}t$（$\lambda t\ll1$）。平均不可用度：

$$PFD_{avg}=\frac{1}{T_1}\int_0^{T_1}\lambda_{DU}t\,dt=\frac{\lambda_{DU}T_1}{2}$$

直觉：失效在区间内均匀发生，平均要等半个区间才会被发现。

### 6.2 双通道（1oo2）

"1oo2" 表示 2 取 1：任一通道能执行安全动作就够，只有两个通道都失效才失效。独立时，在 $t$ 时刻同时失效的概率为 $(\lambda t)^2$：

$$PFD_{avg}\approx\frac{1}{T_1}\int_0^{T_1}(\lambda_{DU}t)^2dt=\frac{(\lambda_{DU}T_1)^2}{3}$$

### 6.3 共因失效

两通道并非完全独立：同一电源故障、同一软件 bug、同一温度过高会同时影响两者。用 $\beta$ 因子建模：一部分比例 $\beta$ 的失效是共因的，会同时让两个通道失效，其作用像一个串联在前的单通道：

$$PFD_{avg}\approx\frac{\left[(1-\beta)\lambda_{DU}T_1\right]^2}{3}+\frac{\beta\lambda_{DU}T_1}{2}$$

教科书里常忽略第一项的 $(1-\beta)^2$ 因子，写成 $\frac{(\lambda T_1)^2}{3}+\beta\frac{\lambda T_1}{2}$。两种写法差别很小，下面按后一种计算。关键洞察：**当 $\beta$ 不太小时，共因项会主导，冗余的收益被它吃掉**，所以冗余设计的重点是降低 $\beta$（电源分离、软件多样性、物理隔离）。

### 6.4 为什么不是越冗余越好

冗余提高了安全（危险失效少），但增加了**安全失效**（误停）的概率，也增加复杂度与成本。2oo3（三取二表决）可以同时兼顾两者，见 [03 可靠性](./03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)。

## 7. 急停与安全链

### 7.1 急停是什么

急停（emergency stop）是一个**独立的、人可随时触发的、使机器进入安全状态的功能**。它的设计要求（概念层面，具体条款未核对）包括：

1. 按钮醒目、常闭触点（断线即触发）、自锁（按下后需要手动复位，不会自己恢复）；
2. **不依赖复杂软件**：急停通常断开驱动的能量（硬件切断），而不是向软件发一条"请停车"的消息；
3. 复位不应导致机器自动重启，必须再次明确使能。

### 7.2 为什么急停不能只是一条软件命令

软件命令路径上有：应用程序、中间件、网络、操作系统调度、驱动。任何一环卡死，"停车"消息就到不了。急停的价值正在于它**绕开这些环节**。P6 的安全执行链设计里明确写了"急停为什么不走这条链"：策略检查链是为了拒绝不当的**运动**请求，而停止请求永远应该被放行并且最高优先级，如果急停必须先通过检查才能执行，那么检查本身的故障就可能让急停失效（见 [P6 安全执行链第 12 节](../../01_项目课程/P6_深开鸿M-Robots平台软件/08_安全执行链.md)）。

### 7.3 安全链（safety chain）

安全链是把多个"可能要求停机"的条件**串联**成一条回路：任何一个条件失效，回路断开，能量被切断。

```text
 24V ──[急停1 NC]──[急停2 NC]──[门联锁 NC]──[安全继电器]──┐
                                                          │
                              ┌── 接触器 K1 (主电源) ◄────┤
                              └── 接触器 K2 (抱闸/驱动使能)◄┘
 反馈: K1/K2 辅助触点回读 ──► 安全继电器 (监视是否粘连)
```

要点：

- 触点用**常闭（NC）**：断线、接触器掉电都等同于触发，故障方向天然是安全的（fail-safe）。
- 回路是**串联**的：任何一个断开就断电。
- 有**回读（feedback）**：监视接触器是否真的断开，发现粘连就不许复位。
- 软件可以**读取**安全链的状态（用于显示与日志），但不应能够**绕过**它。

学生项目里很少有完整的认证安全链，但原则可以对应到：硬件急停/电源开关（比赛机器人的总电源开关、遥控器的急停）、独立的驱动使能线、驱动器侧的超时保护。

### 7.4 软件停止与硬件急停的对比

| 维度 | 软件停止（零命令/失能） | 硬件急停 |
|---|---|---|
| 路径 | 应用 → 中间件 → 总线 → 驱动 | 按钮 → 安全继电器 → 接触器 |
| 依赖软件 | 是 | 否 |
| 典型响应 | 几毫秒到几十毫秒 | 几十毫秒（接触器机械动作） |
| 灵活性 | 可以斜坡、可以保持位置 | 一般是断能量 |
| 用途 | 正常停止、故障停车 | 危险情况的最后手段 |

两者互补：软件停止优雅、灵活；硬件急停可靠、粗暴。真实系统里两者都要有。

## 8. 软件层的安全措施

学生项目几乎不会涉及认证硬件，但软件层有一套成熟的**纵深防御**措施。每一个都是一道独立的防线。

### 8.1 限幅（limiting）

对输出做硬限幅：力矩、速度、电流、加速度、跳变（jerk）。限幅放在**最靠近执行器**的位置，而且不依赖上层给的限值。P1 对三轮命令整体 $L_2$ 范数设上限（设计取值约 8，轮端 rad/s 量级），P6 的七类规则里有速度、加速度、跳变限幅，网关端再做一次，因为"上一层检查过"不是"这一层不需要检查"的理由（纵深防御）。

限幅与控制的关系：限幅会造成积分饱和与相位变化，需要抗积分饱和（见 [前馈、增益调度、限幅与饱和](../05_控制理论/07_前馈_增益调度_限幅与饱和.md)）。

### 8.2 看门狗（watchdog）

看门狗监视"某个行为是否按时发生"，超时则触发保护。

- **命令看门狗**：一段时间没收到有效命令就停车。P1 驱动侧 100 ms；P6 约 200 ms 加连续 2 次判定。
- **心跳/存活看门狗**：监视对端进程是否活着。
- **硬件看门狗（独立 WDT）**：MCU 内部或外部芯片，软件必须周期性"喂狗"，否则复位。
- **窗口看门狗**：喂狗不能太早也不能太晚，防止死循环里恰好有个喂狗调用。

看门狗的设计公式：超时 = 若干个命令周期（避免网络抖动误触发）；之后核对停车距离 $d=vT_w+v^2/(2a)$。详见 [03 可靠性](./03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)。

### 8.3 使能状态机与故障锁定

把"允许输出"做成显式状态机，而不是隐式布尔量。P1 的四状态：

| 状态 | 输出 | 含义 |
|---|---|---|
| DISABLED | 零 | 默认状态，上电即在此 |
| INITIALIZING | 零 | 等数据、采偏置、清状态，最多 5 s |
| RUNNING | 控制器输出（限幅后） | 正常平衡 |
| FAULT | 零，锁定 | 检测到跌倒或数据失效，只能人工复位再使能 |

三个设计原则：**默认失能**（上电不动）；**失败要明显**（报警、日志、状态灯，不静默带病运行）；**故障后锁定**，需要人为确认才能再使能（避免故障条件抖动时机器反复"诈尸"）。这与安全标准里对"复位不得导致自动重启"的精神一致。

### 8.4 合理性检查与新鲜度

- 范围检查：值是否在物理可能范围内；
- 变化率检查：相邻两次是否跳变过大；
- 新鲜度：时间戳年龄是否超限（P1 取 IMU 50 ms、臂状态 200 ms）；
- 交叉校验：两个独立来源是否一致（编码器积分 vs IMU）。

### 8.5 策略校验（P6）

P6 的链是"动作提案 → 策略校验 → 执行 → 状态回传"。高层（含 LLM 计划）发出的只是**提案**，必须经过白名单、范围、速度加速度跳变、模式、新鲜度、权限、空间约束等规则；通过后签发短时执行凭据（HMAC 签名的票据，运动类约 2 s），网关验票后才下发。这条链解决的是"不当的运动请求变成物理动作"的问题；它**不替代**急停和驱动侧看门狗。

### 8.6 软件失效的特别说明

软件没有"磨损"，但有缺陷。对安全软件的工程措施包括：简化（安全相关代码尽量小且独立）、评审、静态分析、覆盖率测试、故障注入、禁止动态内存分配和不可预测的阻塞、对关键变量做双份存储比对。这些在项目中的对应是：独立的状态机模块、执行端简短的限幅/看门狗逻辑、联调时的故障注入矩阵。

## 9. 完整手算示例

### 9.1 PFD：单通道 vs 双通道 vs 共因（教学示例，非项目实测）

设某安全通道危险失效率 $\lambda_D=10^{-6}$ /h，诊断覆盖 $DC=0.9$，验证测试间隔 $T_1=8760$ h（一年）。

1. 未检测危险失效率：$\lambda_{DU}=10^{-6}\times(1-0.9)=10^{-7}$ /h。
2. 单通道：$PFD_{avg}=\lambda_{DU}T_1/2=10^{-7}\times8760/2=4.38\times10^{-4}$。
3. 双通道独立：$PFD_{avg}=(\lambda_{DU}T_1)^2/3=(8.76\times10^{-4})^2/3=2.56\times10^{-7}$。
4. 加共因 $\beta=0.05$：增加项 $\beta\lambda_{DU}T_1/2=0.05\times4.38\times10^{-4}=2.19\times10^{-5}$，总计约 $2.22\times10^{-5}$。

结论：双通道把 PFD 降低了约 20 倍（从 $4.38\times10^{-4}$ 到 $2.2\times10^{-5}$），但共因项占了几乎全部（独立项仅 $2.6\times10^{-7}$）；要想进一步改善，应当把 $\beta$ 降下去，而不是再加第三个通道。

**Python 复核：**

```python
lam_D, DC, T1, beta = 1e-6, 0.9, 8760, 0.05
lam_DU = lam_D * (1 - DC)
pfd1 = lam_DU * T1 / 2
pfd2 = (lam_DU * T1) ** 2 / 3
pfd2c = pfd2 + beta * lam_DU * T1 / 2
print(lam_DU, pfd1, pfd2, pfd2c)
# 1e-07  4.38e-04  2.558e-07  2.2156e-05
```

输出与手算一致（$2.2156\times10^{-5}$）。

> 这些数是**教学示例**，不是任何器件的数据；真实评估需要器件失效率数据，并按标准给出的公式与表格，**未核对**。

### 9.2 去抖次数与误触发（P1 跌倒检测的思路）

P1 的跌倒判定：倾角超过 0.5 rad（约 28.6°）且持续 $N_f=5$ 个控制周期（50 ms）。设噪声使单个采样虚假越限的概率为 $p=10^{-3}$，控制周期 10 ms（100 Hz），则一小时内虚假触发期望次数：

$$n_{\text{false}}=p^{N}\times 100\times3600$$

| $N$ | $p^N$ | 每小时虚假触发期望 |
|---|---|---|
| 1 | $10^{-3}$ | 360 次 |
| 3 | $10^{-9}$ | $3.6\times10^{-4}$ 次 |
| 5 | $10^{-15}$ | $3.6\times10^{-10}$ 次 |

（这里把各次采样视为独立，实际噪声有相关性，真实误触发会更高，所以 $p^N$ 是乐观估计。）

对真实跌倒的检测延迟：$N\times T_s=5\times10=50$ ms；再加上链路延迟（典型 15 ms，最坏 25 ms，来自 P1 延迟预算的设计取值），从倾角越限到零输出命令生效约 65～75 ms。这是"安全响应时间"：

$$t_{\text{safe}}=t_{\text{detect}}+t_{\text{react}}=50+(15\sim25)=65\sim75\ \text{ms}$$

**Python 复核：**

```python
for N in (1, 3, 5):
    print(N, (1e-3) ** N * 100 * 3600)   # 360.0, 0.00036, 3.6e-10
print(5 * 10 + 15, 5 * 10 + 25)          # 65 75
```

注意 $N=1$ 的误触发会让机器一小时停 360 次，根本不可用；而 $N$ 再增大，对真实跌倒的反应变慢，机体可能已倒下。这就是"安全失效 vs 危险失效"的工程权衡。

### 9.3 安全响应时间与停车距离

命令看门狗取 0.25 s，速度 0.8 m/s，减速度 1.0 m/s²（P6 工程化章节的设计取值）：

$$d=vT_w+\frac{v^2}{2a}=0.2+0.32=0.52\ \text{m}$$

若采用硬件急停（接触器动作设为 0.05 s 并加 0.1 s 的系统惯性，教学假设）：$d=0.8\times(0.05+0.1)+0.32=0.44$ m。**Python 复核** `0.8*(0.05+0.1)+0.8**2/2/1.0 = 0.44`。可见急停比看门狗路径短 0.08 m，但并不神奇：真正决定停车距离的是减速度，所以降速档位比"更快的传感"更有效。

## 11. 常见错误与故障现象

1. **把"检查过"当成"不用再限幅"。** 上层限幅失效（bug、配置错）时，没有第二道防线。
2. **看门狗只在软件里实现且与业务线程同一进程。** 业务线程死锁时看门狗线程也可能受牵连；关键的要有独立于业务逻辑的执行端检查。
3. **故障后自动恢复。** 故障条件抖动时机器反复使能，最危险。要锁定并人工确认。
4. **超时只警告不动作。** "警告后继续运行"等于没有保护。
5. **复位即重启。** 复位键之后机器立刻动作，违背安全设计。复位只应使系统回到失能，使能需另一个明确动作。
6. **把急停做成软件消息。** 链路故障时急停不工作。
7. **冗余使用同一份代码/同一电源。** 共因失效让冗余形同虚设。
8. **没有定义安全状态，或定义错误。** 平衡机器人或有重力负载的机械臂"断电"不等于安全。
9. **去抖次数拍脑袋。** 过小导致频繁误停，过大导致反应过慢；应用噪声统计与响应时间预算推导。
10. **数据陈旧时继续用旧值。** 通信断开后 `last value` 被当成当前值；必须检查时间戳。
11. **在文档里声称"符合 SIL/PL"。** 没有评估就不要声称，只说采用了哪些措施。

## 12. 面试怎么问、怎么答

**Q1. What is functional safety, and how is it different from reliability?**

> Functional safety is about making sure that when something fails, the system goes to a safe state instead of causing harm. Reliability is about how long it keeps working. A system can be very reliable but unsafe if it reliably keeps moving when a sensor lies. In my projects I focused on safe defaults: the robot starts disabled, outputs are limited at the execution layer, and a command watchdog stops it when commands stop arriving.

中文译文：功能安全关心的是出故障时系统进入安全状态而不是造成伤害；可靠性关心能持续工作多久。系统可以很可靠但不安全，比如传感器出错时它还稳定地继续运动。我在项目里重点做了安全默认值：上电默认失能，输出在执行层限幅，命令看门狗在命令中断时停车。

*Follow-up: Is your project certified? —* No. I used safety-by-design measures in the spirit of the standards, but I did not do a formal assessment.（追问：项目认证了吗？没有。我按标准的思想做了安全设计，但没有做正式评估。）

**Q2. What is the difference between an emergency stop and a software stop?**

> A software stop goes through the application, middleware and bus, so it depends on all of them working. An emergency stop is an independent hardware path that removes power or enables the safe state without needing the software. In my platform work the safe-execution chain deliberately lets stop requests through with the highest priority and does not require them to pass the motion checks, and there is also a watchdog on the actuator side.

中文译文：软件停止要经过应用、中间件和总线，依赖这些环节都正常。急停是独立的硬件路径，不需要软件就能切断能量或进入安全状态。在平台项目里，安全执行链让停止请求以最高优先级直接放行，不必通过运动检查，执行端还有看门狗。

*Follow-up: Why shouldn't E-stop go through the policy check? —* Because a fault in the checker could then block the stop request; a stop is always safe to execute.（追问：为什么急停不走策略检查？因为检查模块本身的故障会阻断停止；而"停止"总是可以安全执行的。）

**Q3. How would you make redundancy actually effective?**

> Redundancy only helps if the channels fail independently. I would use separate power and wiring, different implementations where possible, and diagnostics that compare the channels. Otherwise a common-cause failure, modelled by a beta factor, dominates. In a quick calculation with beta equal to five percent, the common-cause term was about a hundred times larger than the independent term.

中文译文：冗余只有在通道独立失效时才有效。要分开电源和走线，尽量用不同实现，并用诊断对比通道。否则共因失效（用 β 因子建模）会占主导。快速计算里 β 取 5% 时，共因项比独立项大约 80 倍。

*Follow-up: Does duplicating the same software give redundancy? —* No, a systematic bug appears in both copies; I would rely on review, testing and diversity.（追问：复制同一份软件算冗余吗？不算，系统性 bug 会同时出现在两份里，需要评审、测试和多样性。）

**Q4. How do you choose a fault-detection debounce time?**

> I trade false trips against reaction time. With a per-sample false probability p, requiring N consecutive samples gives about p to the N false trips, while the detection delay grows by N sampling periods. For a fall detector at 100 Hz I used five cycles, which is 50 ms of delay, and the total reaction was still well inside what the robot needs to avoid a hard fall.

中文译文：我在误触发和反应时间之间权衡。单次采样虚假概率为 p，要求连续 N 次，误触发约 p 的 N 次方，检测延迟增加 N 个采样周期。100 Hz 的跌倒检测我取五个周期，延迟 50 ms，总反应时间仍在机器人避免重摔所需的范围内。

*Follow-up: What if the noise is correlated? —* Then the independence assumption is optimistic, so I would validate with recorded data and test the threshold on real logs.（追问：噪声相关怎么办？独立假设是乐观的，要用真实日志验证阈值。）

## 13. 本章要点速记

1. 功能安全：出故障时落入安全状态；与可靠性（持续工作）和信息安全（抗恶意）不同。
2. 安全功能 = 传感 + 逻辑 + 执行，串联；先定义安全状态，注意平衡类系统"停"不等于安全。
3. IEC 61508（SIL）面向通用电气电子可编程系统，ISO 13849-1（PL）面向机械控制，条款与区间未核对，只讲概念。
4. 随机硬件失效可用冗余缓解，系统性失效（软件、需求）靠评审、测试、多样性。
5. $\lambda_{DU}=(1-DC)\lambda_D$；$PFD_{1oo1}=\lambda_{DU}T_1/2$；$PFD_{1oo2}\approx(\lambda_{DU}T_1)^2/3+\beta\lambda_{DU}T_1/2$。
6. 共因失效常主导冗余系统，降低 $\beta$ 比增加通道更有效。
7. 急停是独立于软件的硬件路径，常闭触点、自锁、复位不自动重启。
8. 软件层纵深防御：限幅、看门狗、使能状态机、故障锁定、新鲜度、策略校验。
9. 去抖：误触发约 $p^N$，检测延迟增加 $N T_s$；两者要权衡。
10. 不要声称项目通过了某一安全等级；诚实表述为"按其精神做了设计"。

## 14. 自测题
