## 1. 要解决的问题

机器人系统的测试比普通软件更难，原因有四：

1. **物理世界不可重复**：同一条地面、同一次推扰永远不完全相同；
2. **实机试验昂贵且有风险**：失误可能摔坏机器、烧电机、伤人；
3. **组合爆炸**：传感器 × 环境 × 故障 × 软件版本 × 参数；
4. **时序问题难复现**：偶发的丢帧、抖动、竞争条件，在台架上一周才出现一次。

因此测试策略的核心思想是：**把问题尽可能留在便宜、安全、可重复的层次去发现，把昂贵危险的实机试验留给无法在别处验证的少数项。** 同时，为了让测试结果有意义，必须能说清"测的是哪个版本的代码、哪一组参数、哪份数据"，这就是版本管理与配置管理的作用。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 单元测试（unit test） | 对最小单元（函数、类、算法）的测试 |
| 集成测试（integration test） | 测试多个模块经接口组合后的行为 |
| 系统测试（system test） | 对整个系统端到端地测试 |
| 验收测试（acceptance test） | 以需求为准判断是否交付 |
| 回归测试（regression test） | 修改后验证原有功能没有被破坏 |
| MIL | 模型在环（model-in-the-loop），控制模型与被控对象模型都在仿真工具里 |
| SIL | 软件在环（software-in-the-loop），真实控制软件代码接仿真被控对象 |
| PIL | 处理器在环（processor-in-the-loop），代码跑在目标处理器上，对象仍是仿真 |
| HIL | 硬件在环（hardware-in-the-loop），真实控制器硬件接实时仿真的被控对象 |
| 回放（replay） | 用录制的传感器数据重放给算法，以复现现象或比较版本 |
| 故障注入（fault injection） | 人为制造丢包、延迟、断线、噪声等来检验系统反应 |
| CI | 持续集成（continuous integration）：每次提交自动构建、测试 |
| CD | 持续交付/部署（continuous delivery/deployment） |
| 语义化版本 | MAJOR.MINOR.PATCH |
| 测试覆盖率 | 被测试执行到的代码比例 |
| 置信度 $C$、可靠度 $R$ | 零失败 $n$ 次试验后，以置信度 $C$ 断言可靠度不低于 $R$ |

## 3. 测试层次：金字塔

### 3.1 经典的测试金字塔

```text
              /\
             /  \   实机 / 验收测试 (少、慢、贵、危险)
            /----\
           /      \   系统 / HIL / 仿真场景测试
          /--------\
         /          \   集成测试 (接口、时序、消息)
        /------------\
       /              \   单元测试 (多、快、便宜、确定)
      /----------------\
```

越往下越多越快，越往上越少越慢。比例没有绝对标准，常见的口径是单元测试占大多数。关键思想是**每层捕获本层最擅长发现的缺陷**：

| 层次 | 擅长发现 | 机器人例子 |
|---|---|---|
| 单元 | 公式、边界、符号、单位错误 | 运动学正逆解互逆；限幅函数边界；PID 抗积分饱和 |
| 集成 | 接口不一致、时序、消息缺失 | 控制节点收到消息的单位；TF 坐标系对齐；CAN 打包与解包 |
| 系统/仿真 | 行为、闭环稳定性、场景覆盖 | 仿真里的推扰恢复；导航到目标 |
| HIL | 实时性、硬件接口、固件行为 | 控制周期抖动；CAN 总线负载；看门狗触发 |
| 实机 | 真实物理（摩擦、柔性、噪声、热） | 地面接触切换；电机温升；操作员体验 |

### 3.2 机器人单元测试的例子

好的单元测试的特点：**确定性**（不依赖真实时钟和随机）、**快**、**一个测试验证一个事实**。机器人里适合单元测试的对象：

- 运动学：给定关节角，正解再逆解应回到原值；
- 坐标变换：旋转矩阵的正交性 $R^TR=I$、行列式为 1；
- 限幅函数：输入超限时输出恰好等于界；边界值上不翻转符号；
- 数字 PID：阶跃输入下的响应与手算值一致；抗饱和后积分不继续增长；
- 状态机：给定事件序列，状态转移符合表格（尤其 FAULT 只能经复位退出）；
- 协议解析：CRC 错误的帧被丢弃；半帧、粘包处理正确；
- 时间处理：时钟回拨时年龄不为负、不触发误判。

```python
# 教学示例，非项目源码：限幅函数的单元测试
def clamp(x, lo, hi):
    return max(lo, min(hi, x))

def test_clamp():
    assert clamp(5, -1, 1) == 1
    assert clamp(-5, -1, 1) == -1
    assert clamp(0.3, -1, 1) == 0.3
    assert clamp(1, -1, 1) == 1       # 边界值保持
```

### 3.3 属性测试与对拍

对数值算法，除了固定输入输出，还可以用**属性（property）**：随机生成大量输入，检查性质恒成立，如"限幅后的值永远在 $[lo,hi]$ 内""逆运动学的解代回正运动学误差小于阈值"。也可以与**参考实现对拍**：新的 C++ 实现与旧的 Python 实现在同一批输入上输出差在容差内。

## 4. 仿真到实机：MIL / SIL / PIL / HIL

### 4.1 递进的路线

```text
MIL  → SIL  → PIL  → HIL  → 台架(受限实机) → 实机(完整场景)
模型     代码     目标CPU    真硬件+仿真对象    真对象+保护      真环境
```

每向右一步，**更真实，但更贵、更慢、更危险、更难重复**。每一步新增的缺陷类型不同：

| 阶段 | 新增暴露的问题 |
|---|---|
| MIL | 算法与模型层面的设计缺陷（稳定性、参数合理性） |
| SIL | 代码与模型的偏差、数值精度、状态机实现错误 |
| PIL | 目标处理器上的数值（浮点/定点）、栈与内存、执行时间 |
| HIL | 实时性、总线、驱动、中断、看门狗行为 |
| 台架 | 真实传感器噪声、执行器非线性、供电 |
| 实机 | 摩擦、柔性、热、环境、人 |

### 4.2 仿真的局限

仿真模型总是简化的（摩擦、接触、延迟、传感器噪声、电机饱和），因此"仿真通过"只是必要条件。所谓 sim-to-real gap 往往出在：接触模型（轮腿离地/着地切换，P7 的接触切换）、延迟（仿真里常是零延迟）、传感器噪声与偏置、电机的带宽与饱和。一个务实的做法是：**把已知的真实延迟、噪声和饱和显式加进仿真**（延迟用延迟线，噪声用实测方差，饱和用真实力矩上限），这样仿真对稳定性的预测才有参考价值。

### 4.3 HIL 做什么、不做什么

HIL 让真实控制器（STM32 板子）以真实的实时节拍和总线运行，对象由实时仿真器模拟（或用简化的电机/传感器模拟板代替）。它特别适合：

- 验证周期抖动、CPU 余量、最坏响应时间；
- 注入传感器故障、总线错误、掉线，而不用担心损坏机械；
- 验证看门狗、故障锁定、复位流程；
- 自动化长时间运行（过夜）。

学生项目里 HIL 不一定是昂贵设备，**"控制板 + 电机模拟/示波器/逻辑分析仪 + 脚本注入"**也是一种轻量 HIL。

## 5. 回放与回归测试

### 5.1 回放测试的价值

机器人上最宝贵的测试数据是真实运行记录（rosbag 等）。回放让你：

1. **复现现象**：把发生过故障那一刻的传感器数据重放给算法，确认能重现并调试；
2. **比较版本**：新旧两个版本的滤波器吃同一份数据，比较输出；
3. **做回归**：把录制数据与期望指标固化为基准，每次提交自动对比。

回放的限制是**开环**：回放时算法输出不再影响传感器数据（环境不会因新输出而改变）。因此回放适合验证**估计与感知**（定位、滤波、检测），不适合直接验证**闭环控制**（那要靠仿真或实机）。

### 5.2 回归判据怎么设

回归测试最怕"偶尔红"。判据应基于**指标**而不是"逐字节相等"，并带容差。典型指标：

| 模块 | 指标 | 判据（例） |
|---|---|---|
| 定位 | 位置 RMSE、最大跳变 | RMSE 不高于基准的 1.1 倍；最大单步跳变小于阈值 |
| 姿态 | 对静止数据的零偏估计与方差 | 稳定后漂移速率不高于基准 |
| 控制（仿真） | 超调、调节时间、控制量峰值 | 峰值不高于限幅，调节时间不高于基准的 1.2 倍 |
| 周期 | 抖动的第 99 百分位 | 不高于周期的 10% |
| 日志 | 拒绝率、陈旧事件数 | 不高于基准 |

容差来源：从基准运行的多次结果得到均值 $\mu$ 与标准差 $\sigma$，设阈值为 $\mu+3\sigma$（具体倍数视误报与漏报的权衡）。

### 5.3 基准的维护

基准不是一成不变。算法**有意**改进时要更新基准，但更新必须是**显式、评审过**的动作，并记录原因；不能因为测试红了就顺手把基准改掉。

### 5.4 随机性与确定性

仿真和算法里的随机数要**固定种子**，并把种子记入测试报告。ROS 回放要使用仿真时间（`use_sim_time`）和固定的回放速率，否则节点内的定时器与数据时间戳不一致，测试结果会漂。

## 6. 故障注入

### 6.1 为什么要故意制造故障

只在正常条件下测试，等于没有测试"安全机制"。看门狗、新鲜度检查、故障锁定这些代码，在没有故障时**永远不会执行**，一旦有 bug，只有真出故障那天才会暴露。故障注入就是把"那一天"提前到你可控的时候。

### 6.2 注入点与矩阵

| 注入 | 方法 | 参数（例） | 预期 |
|---|---|---|---|
| 通信延迟 | 延迟线、`tc netem` 类工具（未核对具体命令） | 50/100/200 ms | 命令链不误停；状态年龄上升但不越限；超限则拒绝 |
| 丢包 | 随机丢弃 | 5%/10%/30% | 偶发丢失不触发陈旧；高丢包进入降级 |
| 进程崩溃 | 杀进程 | 校验服务、状态管理器 | 默认拒绝；停止放行；看门狗停车 |
| 传感器卡死 | 固定输出 | IMU 恒值 | 卡死检测触发，故障锁定 |
| 传感器噪声 | 叠加噪声 | 若干倍标准差 | 不误触发；滤波后性能退化可接受 |
| 时钟跳变 | 前跳/回拨 | ±数秒 | 单调时钟不受影响，年龄不为负 |
| 重复/乱序消息 | 重放、重排 | 同一幂等键两次 | 只执行一次 |
| 电源跌落 | 降压 | 电池低压 | 欠压保护动作，状态保存 |
| 参数错误 | 载入越界配置 | 增益取负 | 启动自检拒绝加载 |

这张表的格式来自 P6 的"故障注入矩阵"（见 [P6 联调与工程化](../../01_项目课程/P6_深开鸿M-Robots平台软件/20_工程化实践_频率周期与问题解决.md)）。其意义不在列了多少项，而在于**每一项都有预期行为**：没有预期的注入只是"看看会怎样"，不是测试。

### 6.3 故障注入的安全

注入故障本身可能触发危险（比如把一个平衡机器人的 IMU 断掉）。故障注入应先在 SIL/HIL 做，实机上只做低风险的（拔掉上层通信看停车、模拟陈旧时间戳），并且保证有人手在急停上、机器吊起或有保护架。

## 7. 测试量够不够：零失败样本的统计含义

### 7.1 问题

"我连续跑了 50 次都没出问题"能说明什么？零失败不等于可靠度为 1。设每次试验独立，失败概率为 $q=1-R$。$n$ 次全部成功的概率为 $R^n$。如果真实可靠度低于 $R$，那么观察到 $n$ 次全成功的概率小于 $R^n$。要以置信度 $C$ 断言"可靠度至少为 $R$"，只需

$$R^n\le1-C\ \Rightarrow\ n\ge\frac{\ln(1-C)}{\ln R}$$

### 7.2 计算

- 想以 95% 置信度说明 $R\ge0.99$：$n\ge\ln0.05/\ln0.99=298.07$，取 **299** 次零失败；
- 想说明 $R\ge0.999$：$n\ge2995$；
- 想以 90% 置信度说明 $R\ge0.95$：$n\ge45$。

近似"三法则"（rule of three）：零失败 $n$ 次后，95% 置信上界的失败概率约为 $3/n$。如 299 次零失败，上界约 $3/299\approx1.0\%$，与上面精确值 $1-0.05^{1/299}=0.99\%$ 一致。

**Python 复核：**

```python
import math
for C, R in [(0.95, 0.99), (0.95, 0.999), (0.9, 0.95)]:
    print(C, R, math.ceil(math.log(1 - C) / math.log(R)))   # 299, 2995, 45
print(3 / 299, 1 - 0.05 ** (1 / 299))                        # 0.01003  0.00997
```

### 7.3 含义

要证明较高的可靠度需要**惊人数量**的试验（0.999 要近 3000 次），这是为什么高等级安全系统不靠"多测"而靠**设计与分析**（冗余、诊断、形式化论证）。对学生项目的启示是：不要说"测试了很多次所以很可靠"，而要说"在这些条件下重复了 N 次，没有观察到失败，覆盖了以下故障场景"。

### 7.4 偶发失败（flaky test）的复合概率

如果每个测试偶发误报的概率为 $p_f$，共 $m$ 个测试，则整个套件至少有一个误报的概率为 $1-(1-p_f)^m$。$p_f=0.5\%$、$m=200$ 时为 $63.3\%$，即这个套件**多半每次都红**，最终开发者会学会忽视红色。所以必须修复或隔离不稳定的测试，并记录它们。

```python
print(1 - 0.995 ** 200)   # 0.633
```

## 8. 实机试验的安全流程

### 8.1 原则

1. **渐进**：从小幅度、低速度、低增益开始，逐步提升；
2. **有保护**：急停可达、吊装或保护架、围栏、限幅与看门狗在位；
3. **有计划**：每次试验有目的、有通过判据、有中止条件；
4. **有记录**：版本、参数哈希、日志、结果、异常；
5. **有角色**：谁操作、谁负责急停、谁记录。

### 8.2 实机上线 checklist（可直接套用的一份）

**上电前**

- [ ] 软件版本已打标签，参数文件哈希已记录，与计划一致
- [ ] 急停按钮功能测试通过，位置伸手可及
- [ ] 电源、线缆、接头检查；电池电压正常
- [ ] 机械紧固检查，轮子/臂/腿悬空或有保护架
- [ ] 限幅（力矩、速度、角度）已加载，数值与文档一致
- [ ] 看门狗/超时已启用，数值已读回确认

**上电后（无负载）**

- [ ] 默认失能：上电后电机无输出
- [ ] 传感器数据新鲜、方向正确（人工转动机体，检查符号）
- [ ] 使能流程：等数据 → 采偏置（机体静止）→ 使能，各步判据通过
- [ ] 停止命令与看门狗：拔掉上层通信，输出在预期时间内归零
- [ ] 日志/录包已启动，磁盘空间足够

**首次运动**

- [ ] 小幅度、低速度、低增益，一次一个自由度
- [ ] 人手在急停上，观察电机温度、电流
- [ ] 逐步放开限幅，每一步记录
- [ ] 异常（异响、抖动、过热）立即停止并复盘，不要"再试一次"

**结束**

- [ ] 失能、断电、保存日志、记录现象与参数变更
- [ ] 更新问题清单与下一步

### 8.3 中止条件

事先约定：出现任何一项就停——超温、电流超过限值、状态陈旧告警、异常声音、人员进入危险区、测试目标已完成。事先约定的目的是避免临场"再试最后一次"。

## 9. 版本管理与配置管理

### 9.1 为什么要管

没有版本管理，测试结果不可追溯："昨天能跑今天不行"，却说不清昨天到底是哪份代码、哪份参数。机器人系统由**代码**、**参数/配置**、**模型/地图**、**固件**、**依赖**共同决定行为，缺一不可。

### 9.2 Git 的做法

- **分支策略**：主干（main）保持可用；功能在分支开发，合并前评审与测试。
- **提交信息**：说明做了什么、为什么。
- **标签（tag）**：每次实机试验或交付用标签固定版本，例如 `v1.4.0`。
- **不要提交**：编译产物、大二进制日志、密钥。大文件用专门的存储。
- **子模块**：外部依赖固定到具体提交，而不是跟随主干漂移。

### 9.3 语义化版本

MAJOR.MINOR.PATCH：接口不兼容的变更增加 MAJOR；向后兼容的新功能增加 MINOR；向后兼容的缺陷修复增加 PATCH。对机器人，"接口"包括消息格式、参数含义、通信协议。协议里带上版本号，两端不兼容时能明确报错而不是悄悄误解。

### 9.4 配置即代码与参数哈希

把参数放在文件（YAML/JSON）里并纳入版本控制，而不是改在运行时的某个界面上然后忘了。更进一步，把**规范化后的配置内容计算哈希**写进日志和每份录包的元数据：

```python
import json, hashlib
cfg = {"kp": 1.2, "ki": 0.0, "limit": 8.0}   # 教学示例，非项目参数
s = json.dumps(cfg, sort_keys=True, separators=(",", ":"))
print(s, hashlib.sha256(s.encode()).hexdigest()[:12])
# {"ki":0.0,"kp":1.2,"limit":8.0} 2a1a4022420a
```

规范化（排序键、固定分隔符）保证内容相同则哈希相同。事后看日志就能知道"这次用的是哪一组参数"；两次结果不同，先比对哈希。

### 9.5 配置的分层

| 层 | 例 | 变更频率 | 管理 |
|---|---|---|---|
| 常量（编译期） | 控制周期、协议字段 | 极少 | 代码，评审 |
| 平台配置 | 机器人型号、几何参数、电机限值 | 少 | 文件，版本控制 |
| 调参 | 增益、阈值 | 常 | 文件，带哈希，调参记录 |
| 运行时 | 模式、目标 | 持续 | 消息，有范围检查 |

调参最容易失控：现场改了十个参数，最后只记得最后一个。建议每次现场调参结束后把有效参数写回文件并提交，提交信息写明现象与依据。

### 9.6 启动自检

加载配置时检查：必需项齐全、数值在合理范围、单位一致、不同参数间一致（如下限小于上限）。不合法则拒绝启动并输出明确原因，而不是带着错配置运行。

## 10. CI/CD 流水线

### 10.1 CI 做什么

每次提交或合并请求，自动执行：

```text
提交 → 拉取依赖 → 编译(含警告当错误) → 静态检查/格式检查
     → 单元测试 → 集成测试(含 SIL 仿真场景) → 回放回归 → 生成报告/产物
```

CI 的价值是**快反馈**：错误在引入后几分钟内被发现，而不是几周后集成时。流水线时间要控制：单元测试秒级到分钟级，回放和仿真可以分到夜间任务。

### 10.2 CD 与机器人

CD 在机器人场景里不能像网站那样"自动部署到生产"。更稳妥的做法：

1. CI 通过 → 产出**带版本的制品**（二进制/镜像/固件）；
2. 在仿真和 HIL 上跑完整场景；
3. **人工批准**后部署到少数机器（灰度/金丝雀）；
4. 观察指标（拒绝率、周期抖动、故障事件）；
5. 无异常再推广；有异常**一键回滚**到上一个稳定版本。

固件更新（OTA）还涉及签名与回滚保护，见 [06 信息安全](./06_信息安全与权限_DDS-Security_OTA安全.md)。

### 10.3 可重复构建

构建环境要固定：容器镜像固定版本，依赖固定到具体版本，编译器版本固定。否则"在我电脑上能跑"。ROS2 Humble 项目通常用容器或固定的系统镜像来保证一致（部署细节见 [ROS2 实战](../12_机器人软件/08_ROS2_Humble实战_launch_参数_生命周期_组件.md)）。

### 10.4 代码评审与测试门禁

合并规则：必须通过 CI；至少一人评审；涉及安全相关代码（限幅、看门狗、状态机、策略规则）需要额外关注，并要求有对应的测试。没有测试的安全逻辑，视为不存在。

## 11. 完整手算示例

### 11.1 回放回归：RMSE 比较

教学示例（非项目实测）：对同一份回放数据，旧版本与新版本滤波器的位置误差序列（单位 m）为：

- 旧版本：0.10, 0.12, 0.09, 0.11, 0.30
- 新版本：0.10, 0.11, 0.09, 0.12, 0.14

旧版本 RMSE $=\sqrt{(0.01+0.0144+0.0081+0.0121+0.09)/5}=\sqrt{0.1346/5}=0.1641$，新版本 $=\sqrt{(0.01+0.0121+0.0081+0.0144+0.0196)/5}=\sqrt{0.0642/5}=0.1133$。最大误差由 0.30 降到 0.14。回归判据"RMSE 不高于基准的 1.1 倍且最大值不高于基准"，新版本通过。

**Python 复核：**

```python
import math
a = [0.10, 0.12, 0.09, 0.11, 0.30]
b = [0.10, 0.11, 0.09, 0.12, 0.14]
rms = lambda x: math.sqrt(sum(v * v for v in x) / len(x))
print(round(rms(a), 4), round(rms(b), 4), max(a), max(b))   # 0.1641 0.1133 0.3 0.14
```

### 11.2 阈值的统计设定

对基准版本重复 5 次运行，得到某指标：0.101, 0.099, 0.100, 0.102, 0.098。均值 $\mu=0.100$，样本标准差 $\sigma=0.00158$，阈值取 $\mu+3\sigma=0.1047$。新版本此指标为 0.103 则通过，0.106 则报红。**Python 复核**见：

```python
import math
base = [0.101, 0.099, 0.100, 0.102, 0.098]
m = sum(base) / 5
sd = math.sqrt(sum((x - m) ** 2 for x in base) / 4)
print(m, round(sd, 5), round(m + 3 * sd, 4))   # 0.1 0.00158 0.1047
```

5 个样本估计出的 $\sigma$ 本身很不准，因此阈值只是起点，应随积累的运行次数修正，并留出工程余量。

### 11.3 零失败试验次数

见第 7 节：95% 置信度、$R\ge0.99$ 需要 299 次零失败；若每次测试耗时 30 s，需要约 2.5 小时（$299\times30/3600=2.49$ h），可以自动化；而 $R\ge0.999$ 需要 2995 次、约 25 小时，只能放进夜间 HIL。

## 13. 常见错误与故障现象

1. **只测"正常路径"。** 看门狗、故障锁定等代码从未被执行过，真出故障时才发现有 bug。
2. **仿真里没有延迟与饱和。** 仿真很稳，实机振荡。
3. **回放当作闭环验证。** 回放是开环，控制效果不能靠回放证明。
4. **回归基准被顺手更新。** 测试红了就改基准，等于关掉警报。
5. **随机种子不固定，结果无法复现。**
6. **不稳定测试（flaky）长期存在**，团队学会忽视红灯。
7. **测试通过后参数又被现场改动，没有写回版本库。**
8. **没有记录测试对应的版本与参数哈希**，无法复盘。
9. **实机一上来就满幅度、满增益。**
10. **故障注入没有预期行为**，只是"看看"。
11. **将"没出过问题"当作"可靠"**，不理解零失败样本的统计含义。
12. **CI 里编译警告被忽略**，后来变成线上 bug。
13. **回滚方案缺失**：新版本有问题时无法回到上一个稳定版本。

## 14. 面试怎么问、怎么答

**Q1. How do you test a robot control system before running it on the real robot?**

> I go step by step. First unit tests for the pure pieces, such as kinematics, limiters and state machines. Then simulation with realistic delay, noise and torque limits to check closed-loop behaviour. Then bench tests with the real board and the motors lifted, checking signs, limits and the watchdog. Only then do I run on the real robot, starting with small amplitudes and low gains, with a hand on the emergency stop.

中文译文：分步骤做。先对纯逻辑部分做单元测试，如运动学、限幅、状态机；再在加入真实延迟、噪声和力矩限值的仿真里检查闭环行为；再用真实板子和悬空电机做台架测试，检查符号、限幅和看门狗；最后才上整机，从小幅度、低增益开始，手放在急停上。

*Follow-up: What is the main gap between simulation and the real robot? —* Contact, delay, sensor noise and actuator saturation; I add measured delay and limits to the simulation to narrow it.（追问：仿真与实机最大差距？接触、延迟、传感器噪声、执行器饱和；我把测得的延迟和限值加进仿真来缩小差距。）

**Q2. What is hardware-in-the-loop testing, and why is it useful?**

> HIL runs the real controller hardware against a simulated plant in real time. It checks things simulation alone cannot, like timing jitter, bus load, interrupts and watchdog behaviour, and it lets you inject faults safely, for example unplugging a sensor, without risking the mechanics. I have not built a full HIL rig, but on the bench I use a lightweight version: the real board with scripted inputs and a logic analyser.

中文译文：HIL 让真实控制器硬件与实时仿真对象一起运行。它能检查仅靠仿真看不到的东西，如时序抖动、总线负载、中断和看门狗行为，还能安全地注入故障，比如拔掉传感器，而不会损坏机械。我没有搭过完整的 HIL 台架，但在台架上用轻量版：真实板子加脚本输入和逻辑分析仪。

*Follow-up: What would a full HIL need? —* A real-time simulator with I/O that mimics the sensors and motor drives, plus automation to run fault scenarios.（追问：完整 HIL 需要什么？带 I/O 的实时仿真器模拟传感器和驱动，加自动化场景执行。）

**Q3. How do you avoid regressions when you change the algorithm?**

> I keep recorded data and metrics as a baseline. After each change I replay the same data and compare metrics like RMSE, maximum jump and rejection counts against thresholds derived from several baseline runs. Baseline updates are explicit and reviewed. Replay is open-loop, so for controllers I also keep a few closed-loop simulation scenarios.

中文译文：我保留录制数据和指标作为基准。每次改动后用同样的数据回放，把 RMSE、最大跳变、拒绝次数等指标与多次基准运行得到的阈值比较。基准的更新是显式并经评审的。回放是开环的，所以控制器还要保留几个闭环仿真场景。

*Follow-up: How do you set the threshold? —* Mean plus a few standard deviations of repeated baseline runs, then adjust with engineering margin.（追问：阈值怎么定？重复基准运行的均值加几倍标准差，再加工程余量。）

**Q4. How do you manage parameters and versions on a robot that you tune on site?**

> Parameters live in files under version control. Each log and bag stores the git tag and a hash of the normalised config, so any result can be traced to the exact setup. After on-site tuning I write the effective values back and commit them with the reason. I also validate the config at start-up and refuse to run if values are out of range or inconsistent.

中文译文：参数放在受版本控制的文件里。每份日志和录包都记录 git 标签和规范化配置的哈希，任何结果都可以追溯到确切的配置。现场调参后把有效值写回并提交，写明原因。启动时校验配置，数值越界或不一致就拒绝运行。

*Follow-up: What if a new version misbehaves in the field? —* Roll back to the last tagged stable version, which is why I keep each release as a versioned artifact.（追问：新版本现场出问题？回滚到上一个带标签的稳定版本，所以每个发布都保留成带版本的制品。）

## 15. 本章要点速记

1. 测试金字塔：单元（多、快）→ 集成 → 系统/HIL → 实机（少、慢、险）；每层抓本层擅长的缺陷。
2. MIL → SIL → PIL → HIL → 台架 → 实机，越右越真实也越贵越险；仿真需加入真实延迟、噪声、饱和。
3. 回放是开环，适合估计与感知，不适合直接验证闭环控制。
4. 回归判据用指标加容差，阈值可取 $\mu+3\sigma$；基准更新要评审。
5. 故障注入每项都要有预期行为；看门狗等机制必须被真正触发过。
6. 零失败 $n$ 次：$n\ge\ln(1-C)/\ln R$；95%、0.99 需要 299 次；三法则 $3/n$。
7. 不稳定测试复合概率 $1-(1-p_f)^m$ 会让套件常红，必须治理。
8. 实机清单：急停可达、默认失能、符号检查、看门狗读回、渐进放开、事先约定中止条件。
9. 版本管理：Git 标签、语义化版本、参数配置即代码、规范化哈希写入日志。
10. CD 在机器人上要有人工批准、灰度和一键回滚；安全相关代码必须有测试。

## 16. 自测题

1. 为什么回放测试不能证明闭环控制器是稳定的？*要点：开环，输出不影响数据。*
2. 以 99% 置信度证明 $R\ge0.98$ 需要多少次零失败？*答案：$\ln0.01/\ln0.98=227.9$，取 228 次（Python 复核）。*
3. 一个测试套件 100 个测试，每个误报率 1%，整套全绿的概率是多少？*答案：$0.99^{100}=0.366$。*
4. 列出三个"仿真里通常没有、但实机里会遇到"的因素，并说明如何在仿真中近似。*要点：延迟（延迟线）、传感器噪声/偏置（叠加实测噪声）、执行器饱和与带宽（限幅与一阶滞后）。*
5. 写出实机首次上电前应检查的五件事。*要点：版本与参数哈希、急停、限幅与看门狗加载、机械与悬空、默认失能与传感器符号。*
