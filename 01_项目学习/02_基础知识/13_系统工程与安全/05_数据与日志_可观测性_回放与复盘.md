# 数据与日志、可观测性、性能分析、回放与复盘

> **一句话定位**：机器人出问题时，往往没有人在现场、现象一闪而过、也无法重现。可观测性（observability）就是提前把"系统内部正在发生什么"变成可记录、可查询、可回放的数据，使你事后能回答"发生了什么、为什么、怎么修"。本章讲日志分级与结构化、指标（计数器/仪表/直方图）、百分位与抖动统计、录包（rosbag）策略与数据量估算、性能剖析与阿姆达尔定律，以及故障复盘模板。

**本章学完你能：**

- 设计日志分级、结构化字段与限速规则，保证关键事件不丢、日志不拖慢控制；
- 区分日志、指标、追踪三类可观测性数据，说出各自适合回答什么问题；
- 手算均值、百分位（最近秩法）、抖动标准差，并说明为什么看 p99 而不是平均；
- 估算录包的数据量与磁盘占用，设计"常驻环形缓冲 + 事件触发保存"策略；
- 用阿姆达尔定律估计优化收益，并描述性能剖析的步骤与工具思路（火焰图、追踪，具体命令标"未核对"）；
- 写出一份故障复盘（postmortem）：时间线、根因、五个为什么、纠正措施；
- 用英文回答 "how do you debug a failure you cannot reproduce / what do you log / how do you find a performance bottleneck"。

## 1. 要解决的问题

现场调试时的典型对话是："刚才抖了一下。""哪里抖？""不知道，现在又好了。"没有数据，就只能凭记忆和猜测。更糟的是，为了找原因而打开详细日志，反而使控制周期变慢，问题被"海森堡化"（观察改变了现象）。

可观测性要解决三个矛盾：

1. **要详细，但不能拖慢系统**：日志的开销必须可控；
2. **要全面，但磁盘和带宽有限**：不能录一切，要有取舍；
3. **要事后能分析**：数据要有统一时间、统一字段、能互相关联（同一个事件在日志、指标、录包里能对上）。

这套能力在项目中的价值是：定位一次异常从"半小时翻日志"缩短到"几分钟看一条时间线"（见 P6 的日志优化）；面试时，它是你讲"我如何排查问题"的骨架。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 日志（log） | 离散事件的文本/结构化记录，回答"发生了什么" |
| 指标（metric） | 随时间聚合的数值（计数、水位、分布），回答"有多少、多快" |
| 追踪（trace） | 一次请求/一个数据流经多个模块的时间线，回答"时间花在哪里" |
| 可观测性 | 仅凭外部输出就能推断内部状态的能力 |
| 计数器（counter） | 只增不减的计数，如拒绝次数 |
| 仪表（gauge） | 可上下变化的当前值，如队列长度、电池电压 |
| 直方图（histogram） | 数值分布，用于延迟、周期 |
| $p_q$ | 第 $q$ 百分位数 |
| 抖动（jitter） | 实际周期相对期望周期的偏差 |
| 环形缓冲（ring buffer） | 固定容量、写满后覆盖最旧数据的缓冲 |
| 单调时钟 | 只增不减的时钟，不受校时影响 |
| 墙上时钟 | 与日期对应的系统时钟，可被校时跳变 |
| 阿姆达尔定律 | 并行/优化部分的整体加速受不可优化部分限制 |
| 复盘（postmortem） | 事故后系统地总结原因与改进 |

## 3. 日志：分级、结构化、限速、异步

### 3.1 日志分级

| 级别 | 含义 | 例子 | 频率期望 |
|---|---|---|---|
| FATAL / CRITICAL | 系统无法继续，已进入安全停机 | 跌倒锁定、关键总线故障 | 极少，必须记 |
| ERROR | 某个功能失败，需要关注 | 校验服务超时、命令被拒绝 | 少 |
| WARN | 异常但已处理，可能前兆 | 数据陈旧一次、重试 | 中 |
| INFO | 关键状态转移与事件 | 状态机转移、使能、任务开始/结束 | 低频 |
| DEBUG | 调试细节 | 中间量、规则逐条结果 | 高，默认关 |
| TRACE | 逐周期数据 | 每周期的输入输出 | 极高，只在短窗口开 |

原则：**高频路径只用 DEBUG/TRACE，并且受开关与限速控制**；INFO 以上必须是"事件"而不是"每周期"。

### 3.2 结构化日志

自由文本难以检索。结构化日志每条记录固定字段，便于过滤、关联：

```text
t_mono=123456.789012 level=WARN module=gateway device=base_01
event=cmd_rejected proposal_id=p-0042 seq=881
rule=freshness age_ms=83 limit_ms=50 action=reject
```

推荐字段：**单调时间**、模块、设备/实体 ID、事件名、关联 ID（如提案 ID、会话 ID）、序号、关键量及其阈值、采取的动作。事件名使用固定词表，便于统计。P6 的日志优化正是统一了这类字段（见 [P6 工程化](../../01_项目课程/P6_深开鸿M-Robots平台软件/20_工程化实践_频率周期与问题解决.md)），把"按提案 ID 关联一次拒绝"的耗时由约半小时降到几分钟（设计级对比）。

### 3.3 单调时钟与墙上时钟

日志里应同时记两个时间：**单调时间**用于计算间隔、年龄（不受校时跳变影响），**墙上时间**用于对应现实日期、与其他设备对时。仅用墙上时间会在被校时的时候出现负间隔或"数据突然陈旧"，P6 的时钟回拨复盘就是这个问题：年龄计算改以本机接收时的单调时钟锚定，设备上报的墙上时间戳仅作参考。

### 3.4 限速与关键事件保护

高频告警不限速会"洪泛"，把真正重要的事件淹没、拖慢系统。做法：

- **按级别限速**：同一事件在时间窗内只记第一条，并带"重复了 N 次"的计数；
- **关键事件绝不丢**：FATAL/ERROR 及状态转移走保留通道，不被限速；
- **去重聚合**：同类事件合并为一条带计数。

### 3.5 异步与不阻塞控制线程

**铁律：控制线程不做阻塞 I/O。** 同步写盘可能偶发几毫秒到几十毫秒的阻塞（磁盘缓存回写、文件系统锁），足以让一个 10 ms 的控制周期失守。标准做法：

```text
控制线程 ──写入──► 无锁环形缓冲 ──► 日志线程(低优先级) ──批量──► 磁盘/网络
                     │
                     └─ 满时丢弃最低优先级，并计数 dropped
```

必须记录并暴露"丢弃计数"（dropped counter），否则你不知道日志是否完整。P6 的优化五中"日志洪泛下关键事件仍完整"就是对这套机制的回归验证。

#### 缓冲容量估算

缓冲需要吸收爆发。设爆发速率 $b$ 条/s，持续 $t$ s，日志线程的排空速率 $d$ 条/s，则所需最小容量

$$Q\ge(b-d)\,t$$

例（教学示例，非项目实测）：爆发 2000 条/s，持续 0.5 s，排空 500 条/s：$Q\ge(2000-500)\times0.5=750$ 条。实际取两倍余量，1500 条。

### 3.6 日志里不该有什么

不记录密钥、凭据、个人身份信息（见 [06 信息安全](./06_信息安全与权限_DDS-Security_OTA安全.md) 与 [07 人机共融](./07_人机共融_伦理与法规概览.md) 的隐私部分）；不在日志里放超大二进制（图像帧）；不用日志代替指标做高频统计。

## 4. 指标：计数器、仪表、直方图

日志适合"离散事件"，指标适合"随时间的数量与分布"。三种基本类型：

| 类型 | 例子 | 用途 |
|---|---|---|
| 计数器 | `cmd_rejected_total`、`stale_events_total`、`log_dropped_total` | 看速率与突增；只增不减，便于差分 |
| 仪表 | `battery_voltage`、`queue_depth`、`cpu_util` | 看当前水位 |
| 直方图 | `control_period_ms`、`e2e_latency_ms` | 看分布，计算百分位 |

### 4.1 该监控什么：一个最小清单

| 类别 | 指标 |
|---|---|
| 实时性 | 每周期实际周期、执行时间、超时次数 |
| 数据质量 | 各传感器年龄、丢帧计数、校验失败计数、序号间断 |
| 通信 | 总线负载、重发次数、掉线次数、QoS 不匹配 |
| 控制 | 输出饱和比例、误差 RMS、状态机状态 |
| 安全 | 看门狗触发次数、拒绝次数（按规则分类）、FAULT 次数 |
| 资源 | CPU、内存、温度、电池 |

### 4.2 指标与告警

告警基于指标：**阈值**（周期 p99 大于 1.5 倍期望）、**突变**（拒绝率比过去一小时高三倍）、**缺失**（心跳停止）。告警要少而准，每条告警应有明确的响应动作；否则就是噪声。

## 5. 统计：均值、百分位与抖动

### 5.1 为什么看百分位

延迟和周期的分布通常是右偏的：大多数很好，偶尔有尖峰。平均值会把尖峰抹平，而尖峰恰好决定控制是否出问题。

**最近秩法**求第 $q$ 百分位：把 $n$ 个样本升序排列，取第 $\lceil qn\rceil$ 个值。

### 5.2 手算

延迟样本（ms，教学示例，非项目实测）：8, 9, 9, 10, 10, 11, 12, 13, 15, 40。

- 均值 $=137/10=13.7$ ms；
- $p_{50}$：$\lceil0.5\times10\rceil=5$，第 5 个值为 10 ms（若用插值定义，中位数为 $(10+11)/2=10.5$）；
- $p_{90}$：$\lceil9\rceil=9$，第 9 个值为 15 ms；
- $p_{99}$：$\lceil9.9\rceil=10$，第 10 个值为 40 ms，等于最大值。

两点教训：（1）均值 13.7 ms 看起来不差，但 p99 是 40 ms，如果控制环路预算 25 ms，则偶发超限；（2）样本数 10 时 p99 没有统计意义，要得到可信的 p99，样本数至少数百到上千。

**Python 复核：**

```python
import math
d = [8, 9, 9, 10, 10, 11, 12, 13, 15, 40]
s = sorted(d); n = len(s)
p = lambda q: s[math.ceil(q * n) - 1]
print(sum(d) / n, p(0.5), p(0.9), p(0.99), max(d))   # 13.7 10 15 40 40
```

### 5.3 抖动的度量

周期序列（ms，教学示例）：10.0, 10.1, 9.9, 10.0, 17.0, 10.0, 9.8, 10.2。

- 均值 $=10.875$ ms；
- 样本标准差 $\approx2.48$ ms；
- 峰峰值 $=17.0-9.8=7.2$ ms；
- 超过 1.5 倍期望周期（15 ms）的有 1 个（17.0）。

均值偏离期望 10 ms 不多，标准差却被一个尖峰拉大。按 P6 的判定口径，"连续两个周期超过 1.5 倍"才上报降级，单个尖峰只计数。**Python 复核：**

```python
import math
per = [10.0, 10.1, 9.9, 10.0, 17.0, 10.0, 9.8, 10.2]
m = sum(per) / len(per)
sd = math.sqrt(sum((x - m) ** 2 for x in per) / (len(per) - 1))
print(m, round(sd, 3), round(max(per) - min(per), 1))   # 10.875 2.478 7.2
```

周期推进要用绝对时刻（`sleep_until(next)`）而不是 `sleep_for(period)`，后者会累计漂移；每周期记录 `actual_period` 与 `exec_time` 进直方图。

## 6. 录包策略与数据量估算

### 6.1 录什么

录包（如 ROS 的 rosbag）是回放与复盘的数据基础。原则是**录足够复现问题的最小集合**：

1. 所有进入算法的**原始输入**（IMU、编码器、激光、遥控命令）；
2. 算法**输出**（控制命令、规划结果）；
3. **状态与诊断**（状态机、健康事件）；
4. **坐标变换与参数**（TF、参数快照、版本与配置哈希）。

不录或低频录：原始高分辨率图像（带宽巨大）——改为录压缩流或触发式。

### 6.2 数据量估算

按每个话题 $\text{频率}\times\text{单条大小}$ 求和。以 P1 工程化章节的估算为例（项目文档的设计估算）：IMU 约 32 kB/s、轮状态约 16 kB/s、轮命令约 8 kB/s、两臂状态约 15 kB/s、质心等约 5 kB/s，合计约 $76$ kB/s，一小时约 $76\times3600=273.6$ MB，8 小时约 2.2 GB。项目文档里取整为约 80 kB/s、约 300 MB/h，量级一致。

结论：**这个量级对现代磁盘不是问题，真正的风险是写盘与同机 CPU 对控制周期抖动的影响**，不是容量。所以录包进程要放在低优先级、独立的核心，或写到独立的磁盘。

```python
rates = [32, 16, 8, 15, 5]     # kB/s，来自项目文档估算
tot = sum(rates)
print(tot, tot * 3600 / 1000, tot * 3600 * 8 / 1e6)   # 76 273.6 2.1888
```

### 6.3 常驻环形缓冲加事件触发保存

长期全量录会产生大量无用数据，只在出事后才想起录又太晚。折中：

1. **常驻内存环形缓冲**，持续保留最近 $W$ 秒（如 10～30 s）；
2. 发生**触发事件**（FAULT、看门狗触发、拒绝率突增、操作员按键标记）时，把缓冲区**事件前后**一段落盘；
3. 另外按需做低频全程"摘要"录制。

P1 的做法是"事件触发另存最后 1 s"（见 [P1 工程化 2.5](../../01_项目课程/P1_AIRS球形机器人平衡控制/20_工程化实践_频率周期与问题解决.md)）。这样既不拖慢系统，又保证关键时刻有数据。

### 6.4 录包的元数据

每份录包必须附：代码版本（git 标签或提交号）、配置哈希、机器人/型号、日期、操作员、测试目的、已知现象。没有元数据的录包过一周就没有人知道它是什么。命名建议：`日期_机器_场景_版本.bag`。

## 7. 性能分析与剖析

### 7.1 方法论：先度量，再优化

流程：**现象 → 度量 → 找瓶颈 → 改动 → 回归**。这是 P6 五次优化的统一结构。不要凭直觉优化。

### 7.2 阿姆达尔定律

若程序中比例 $f$ 的部分被加速 $s$ 倍，其余不变，则整体加速比

$$S=\frac{1}{(1-f)+f/s}$$

即使 $s\to\infty$，$S\le 1/(1-f)$。例：占总耗时 60% 的模块并行加速 4 倍：

$$S=\frac{1}{0.4+0.6/4}=\frac{1}{0.55}=1.818$$

加速 8 倍也只有 2.105，上限 $1/0.4=2.5$。启示：**先找占比最大的，且要看它是否真是瓶颈**；把占 5% 的东西优化到零，整体最多只快 5%。

```python
f = 0.6
for s in (2, 4, 8):
    print(s, round(1 / ((1 - f) + f / s), 3))   # 1.429 1.818 2.105
```

### 7.3 剖析工具的思路

- **采样剖析（sampling profiler）**：定期记录调用栈，统计热点函数，开销小；适合找 CPU 热点。
- **火焰图（flame graph）**：把采样得到的调用栈可视化，横向宽度表示时间占比；用来找"哪条调用路径最宽"。
- **追踪（tracing）**：在关键点打时间戳，重建一个数据在节点间的延迟（ROS2 有对应的追踪工具链，具体命令与版本接口未核对）。
- **逐跳时间戳**：最朴素也最有效——每个模块在处理前后记录时间并随消息传递，事后算每一跳耗时。
- **周期统计**：记录 `exec_time` 与 `actual_period` 直方图，看 p99 与最大值。
- **系统级**：CPU 利用率、上下文切换、缺页、总线负载、内存带宽。

### 7.4 机器人上常见的性能陷阱

| 症状 | 常见原因 | 验证与对策 |
|---|---|---|
| 周期偶发超时 | 阻塞 I/O、锁竞争、GC、缺页 | 对比开关日志；锁内存；异步化 |
| 延迟随时间增长 | 队列堆积、生产快于消费 | 看队列长度仪表，限深度、丢旧 |
| CPU 高但无进展 | 忙等、过度日志、序列化开销 | 采样剖析、减少拷贝 |
| 网络抖动大 | 事件风暴、发现流量 | 抑制/退避；P6 设备上电发现风暴优化 |
| 带宽打满 | 每帧发图 | 只发结构化结果；P4 估算整帧上传约 18 Mbit/s 会占满 2.4 GHz 信道 |

### 7.5 实时系统的剖析要看"最坏"

平均 CPU 利用率 20% 不代表安全。一个 10 ms 周期、WCET 约 2 ms 的线程利用率 20%，但如果日志同步写盘偶发阻塞 8 ms，最坏响应逼近整个周期。分析要看最坏情形和高百分位，参见 [01 章](./01_机器人系统架构设计_分层_接口_需求.md) 的响应时间分析。

## 8. 故障复盘

### 8.1 为什么要复盘

复盘的目的是**改进系统与流程**，而不是追责。没有复盘，同一个坑会被不同的人在不同时间重复踩。好的复盘产出：可验证的根因、纠正措施、回归用例。

### 8.2 复盘模板

```text
标题：[日期] [系统] [一句话现象]
影响：什么功能受影响，持续多久，有无伤害/损坏
检测：怎么发现的（告警/人工）；发现延迟多久（MTTD）
时间线（单调/墙上时间）：
  t0  触发条件出现
  t1  首个异常信号
  t2  保护动作
  t3  恢复
证据：日志片段、指标曲线、录包名与版本/配置哈希
根因（五个为什么）：
  1. 为什么出现现象？
  2. 为什么 1 会发生？ ...
  5. 最深层原因（设计/流程/监控缺口）
直接修复：
纠正与预防措施（负责人、期限、验证方式）：
  - 代码/参数
  - 检测与告警
  - 测试（新增回归/故障注入用例）
  - 文档与流程
经验：下次如何更早发现
```

### 8.3 示例：P6 时钟回拨（项目文档中的案例，摘要）

- 现象：某设备被校时后，墙上时钟回拨约 200 ms，其状态被判陈旧，调度器暂停向它派任务；
- 度量：对比该设备单调时钟间隔（正常）和墙上时间戳（出现负间隔）；
- 根因：状态管理器用设备上报的墙上时间戳计算年龄；
- 改动：年龄以本机接收时的单调时钟为锚，设备时间戳仅作参考；时间戳倒退标记 Suspect 并上报健康事件；
- 回归：时钟跳变（向前、向后各一次）加入故障注入用例。

从中可以看到完整闭环：**现象→度量→根因→改动→回归**。

### 8.4 无责文化与五个为什么

"五个为什么"追问到**系统原因**而不是人。"因为小明接错线"不是根因；"因为接头没有防呆设计、也没有上电前自检"才是。

## 9. 完整手算示例

### 9.1 查询一次拒绝（结构化日志的价值）

假设日志里有三条与提案 `p-0042` 相关的记录：

```text
t=100.000 INFO  module=proposal  event=proposal_received proposal_id=p-0042 src=planner
t=100.002 WARN  module=policy    event=rule_failed       proposal_id=p-0042 rule=freshness age_ms=83 limit_ms=50
t=100.003 ERROR module=gateway   event=cmd_rejected      proposal_id=p-0042 reason=policy_reject
```

按 `proposal_id` 过滤即得完整故事：提案到达、新鲜度规则失败（状态年龄 83 ms 大于 50 ms 的限值）、被网关拒绝，整个过程 3 ms。接下来问："为什么状态年龄会有 83 ms？" 去查状态发布频率与链路延迟指标；这与 [01 章](./01_机器人系统架构设计_分层_接口_需求.md) 的数据年龄公式衔接。（这是教学示例日志，非项目实际输出。）

### 9.2 日志开销预算

每周期（100 Hz）记录 TRACE，每条约 200 B，则 $100\times200=20$ kB/s，一小时 72 MB；若同时 10 个模块各记，每小时 720 MB，且每条格式化与拷贝要消耗 CPU。这是 TRACE 只在短窗口打开的原因：

```python
print(100 * 200 * 3600 / 1e6, 10 * 100 * 200 * 3600 / 1e6)   # 72.0 720.0
```

### 9.3 缓冲容量

见 3.5：$(2000-500)\times0.5=750$，**Python 复核** `(2000-500)*0.5 = 750.0`。

## 11. 常见错误与故障现象

1. **控制线程里同步写日志。** 周期抖动，打开详细日志问题更重（海森堡）。
2. **只记平均值。** 看不到尖峰。
3. **日志没有统一时间和字段。** 无法跨模块关联。
4. **使用墙上时钟计算年龄。** 校时跳变导致误判陈旧。
5. **日志洪泛。** 关键事件被淹没或被限速丢弃。
6. **丢弃日志却不计数。** 以为日志完整，其实丢了。
7. **录包无元数据。** 事后不知道对应哪个版本、哪组参数。
8. **全量录一切**，磁盘和写盘开销拖垮系统；或**只在出事后才想起录**。
9. **p99 用太少样本**，得出没有意义的结论。
10. **没有度量就优化**，花力气优化占比很小的模块。
11. **复盘追责，不追系统原因**，同类问题反复出现。
12. **告警太多**，无人响应，真正的告警被忽略。

## 12. 面试怎么问、怎么答

**Q1. How do you debug a failure you cannot reproduce?**

> I try to make it observable first. I keep a ring buffer of recent raw data and log events with monotonic timestamps, so when the fault happens I can dump the last seconds. Then I replay that data offline, compare against the code version and config hash, and form a hypothesis from the timeline. After I fix it, I add the scenario as a regression or fault-injection test.

中文译文：先让它可观测。保留最近原始数据的环形缓冲，并用单调时间戳记录事件，故障发生时能把最后几秒转存。然后离线回放，对照代码版本和配置哈希，从时间线形成假设。修复后把这个场景加入回归或故障注入测试。

*Follow-up: What if logging itself changes the behaviour? —* I make logging asynchronous with a lock-free buffer and low priority, and I check that period jitter does not change when logging is on.（追问：日志本身改变了现象怎么办？日志异步、无锁缓冲、低优先级，并检查开关日志时周期抖动不变。）

**Q2. What do you log in a real-time controller?**

> Events, not every cycle. State transitions, faults, rejections with the reason and the threshold, plus a few health metrics like period jitter and sensor age. High-rate data goes to a bag with a ring buffer. Every record has a monotonic timestamp and an identifier I can use to correlate across modules.

中文译文：记录事件而不是每周期数据：状态转移、故障、带原因与阈值的拒绝，以及周期抖动和传感器年龄等健康指标。高频数据进带环形缓冲的录包。每条记录都有单调时间戳和能跨模块关联的标识。

*Follow-up: How do you keep the critical events from being dropped? —* Critical levels use a reserved channel that bypasses rate limiting, and I count dropped messages so I know whether the log is complete.（追问：如何保证关键事件不丢？关键级别走不限速的保留通道，并统计丢弃数以知道日志是否完整。）

**Q3. Why do you look at the 99th percentile instead of the mean latency?**

> Because control quality is decided by the worst cycles, not the average. In a small example, the mean was 13.7 milliseconds, but the 99th percentile was 40, which would break a 25 millisecond budget. I also make sure there are enough samples, otherwise the percentile is meaningless.

中文译文：因为控制质量由最差的那些周期决定而不是平均值。在一个小例子里，均值是 13.7 ms，而 p99 是 40 ms，会打破 25 ms 的预算。我也会保证样本够多，否则百分位没有意义。

*Follow-up: How would you reduce tail latency? —* Remove blocking calls from the critical path, raise priority, pin the thread, lock memory, and avoid garbage collection or allocation in the loop.（追问：怎么降低尾延迟？去掉关键路径上的阻塞调用，提高优先级、绑核、锁内存，循环内避免分配与 GC。）

**Q4. How do you find a performance bottleneck?**

> Measure first. I record the symptom, then use per-hop timestamps and execution-time histograms to find where time goes, sometimes a sampling profiler and a flame graph. Then I change one thing and rerun the same measurement. I also use Amdahl's law to check whether optimising that part can even matter: speeding up a sixty-percent part by four times only gives about 1.8 times overall.

中文译文：先度量。记录现象，用逐跳时间戳和执行时间直方图找时间花在哪，有时用采样剖析和火焰图。然后只改一件事，重跑同样的度量。我还用阿姆达尔定律判断优化这一部分是否值得：把占 60% 的部分加速 4 倍，整体只快约 1.8 倍。

*Follow-up: Give an example from your work. —* In the platform project the status broadcast went from 100 Hz full messages to 20 Hz aggregated plus change-triggered, which cut network load without hurting consumers.（追问：举个你的例子。平台项目里把状态从 100 Hz 全量广播改为 20 Hz 聚合加变化触发，在不影响消费者的情况下降低了网络负载。）

## 13. 本章要点速记

1. 日志（事件）、指标（数量与分布）、追踪（时间线）各回答不同问题。
2. 日志分级；高频只用 DEBUG/TRACE 且受开关与限速控制；关键事件走保留通道。
3. 结构化字段：单调时间、模块、实体、事件、关联 ID、序号、量与阈值、动作。
4. 控制线程不做阻塞 I/O：无锁环形缓冲 + 低优先级日志线程；必须统计丢弃数。
5. 缓冲容量 $Q\ge(b-d)t$；留余量。
6. 看百分位不看均值；最近秩法；样本要足够多。
7. 周期推进用绝对时刻，记录 actual_period 与 exec_time。
8. 录包：原始输入、输出、状态、TF 与参数；环形缓冲 + 事件触发；带版本与配置哈希元数据。
9. 阿姆达尔：$S=1/((1-f)+f/s)$；先度量、再优化、再回归。
10. 复盘产出根因（五个为什么）、纠正措施、新回归用例；追系统不追人。

## 14. 自测题

1. 为什么年龄计算应使用单调时钟？*要点：墙上时钟可被校时跳变，导致负间隔或误判陈旧。*
2. 样本 5, 6, 6, 7, 20：求均值与 $p_{80}$（最近秩法）。*答案：均值 8.8；$\lceil0.8\times5\rceil=4$，第 4 个值为 7。*
3. 缓冲吸收爆发：1000 条/s 持续 2 s，排空 400 条/s，最小容量多少？*答案：$(1000-400)\times2=1200$ 条。*
4. 占比 30% 的模块加速 10 倍，整体加速比？*答案：$1/(0.7+0.03)=1.370$。*
5. 为什么"关闭日志后问题消失"并不说明日志无关？*要点：日志改变了时序（阻塞、CPU 竞争），可能掩盖或制造问题；需要异步日志并比较抖动。*
