# 信息安全与权限：威胁模型、认证加密、DDS-Security 与 OTA 安全

## 1. 要解决的问题

实验室里的机器人通常"信任一切"：同一个局域网里谁都能发 `cmd_vel`，谁都能订阅相机图像，U 盘里的固件想刷就刷。一旦机器人进入真实环境（工厂、商场、家庭、园区），问题就来了：

- 恶意或误入的设备向机器人发运动命令；
- 有人抓包后**重放**一条"开门"或"前进"的命令；
- 固件更新包被替换成带后门的版本；
- 摄像头数据被窃听，涉及隐私；
- 一个被攻陷的低权限模块（如大模型插件）借权限发起高危动作。

信息安全的核心不是"绝对安全"，而是**提高攻击成本，限制事故半径，并让事件可追溯**。对机器人而言，信息安全还有特殊性：被攻破的后果不是数据泄露，而是**物理世界的动作**。这就是为什么 P6 的安全执行链里同时有策略检查、短时凭据和审计，也是申请材料中"AI 决策如何变成物理动作"这条主线的现实意义。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 机密性（confidentiality） | 只有授权者能读 |
| 完整性（integrity） | 数据未被篡改 |

| 对称加密 | 加解密用同一密钥（如 AES） |

| STRIDE | 威胁分类：Spoofing、Tampering、Repudiation、Information disclosure、Denial of service、Elevation of privilege |
| 最小权限 | 每个主体只拥有完成任务所需的最少权限 |

## 3. 安全属性与威胁建模

### 3.1 CIA 与机器人的偏好

经典三属性：机密性（C）、完整性（I）、可用性（A）。对于数据中心，机密性通常最重要；对于机器人控制链，**完整性和可用性优先**：被篡改的命令比被窃听的命令危险得多；而"被拒绝服务"可能让机器人失去控制或停在危险位置。

### 3.2 STRIDE：六类威胁

| 威胁 | 含义 | 机器人例子 | 典型缓解 |
|---|---|---|---|
| Spoofing 冒充 | 假冒身份 | 陌生节点冒充规划器发 `cmd_vel` | 认证、证书、白名单 |
| Tampering 篡改 | 修改数据/代码 | 修改命令速度字段；替换固件 | MAC/签名、校验、安全启动 |
| Repudiation 抵赖 | 否认行为 | 操作员否认下过某个危险命令 | 审计日志、签名、时间戳 |
| Information disclosure 信息泄露 | 非授权读取 | 窃听相机视频、地图 | 加密、访问控制 |
| Denial of service 拒绝服务 | 使系统不可用 | 洪泛 DDS 发现流量，阻塞总线 | 限速、过滤、优先级、看门狗 |
| Elevation of privilege 提权 | 越权操作 | 低权限的 LLM 插件调用关节驱动 | 最小权限、策略校验、沙箱 |

### 3.3 威胁建模步骤

1. **画数据流图**：模块、信任边界（进程、网络、人机界面）、数据存储；
2. **识别资产**：命令通道、固件、地图/图像、参数、日志、密钥；
3. **对每个跨越信任边界的数据流套用 STRIDE**；
4. **评估风险**：可能性 × 影响（可用类似 FMEA 的评分，参见 [03 章](./03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)）；
5. **选缓解措施**：优先"消除入口"（关掉不用的端口）而不是"加密一切"；
6. **验证**：渗透测试、模糊测试（fuzzing）、配置审计。

### 3.4 示例：一个小机器人的信任边界

```text
 [手机App/遥控器] --Wi-Fi--> [网关/策略层] --内部总线--> [控制器] --CAN--> [电机驱动]
        ^信任边界1                 ^信任边界2                      ^信任边界3(物理)
 [云端/LLM服务] --Internet--> [网关]
        ^信任边界0(最弱)
```

越靠外越不可信：来自互联网/大模型的输出只能当作**提案**，必须穿过策略层并获得短时凭据才能影响控制器；物理总线通常被视为受信，但物理接触是另一种威胁（有人把设备接上 CAN 总线）。

## 4. 密码学基本构件

### 4.1 哈希

SHA-256 把任意输入映射为 256 位摘要，具有：**单向**（由摘要难以反推输入）、**抗碰撞**（难找到两个不同输入有相同摘要）、**雪崩**（输入改一位，摘要约一半位改变）。用途：校验固件完整性（对比摘要）、构造 MAC、签名的第一步（先哈希再签）。

示例（Python 复核）：

```python
import hashlib
print(hashlib.sha256(b"firmware-v1.2.0").hexdigest()[:16])   # 72cb4f60bb7f69c5
print(hashlib.sha256(b"firmware-v1.2.1").hexdigest()[:16])   # 8950801d177d5627
```

只改了版本号最后一个字符，摘要前 16 位十六进制完全不同，这就是雪崩效应。**哈希本身不提供认证**：攻击者可以同时篡改文件和摘要，所以摘要必须通过可信渠道提供，或被签名保护。

### 4.2 对称加密与 MAC

对称加密（如 AES）用同一把密钥加解密，速度快，适合加密大量数据，问题是**密钥分发**。MAC 在此基础上提供**完整性与来源认证**：发送方用共享密钥 $K$ 对消息 $m$ 计算标签 $t=\text{HMAC}(K,m)$，附在消息后发送；接收方重算并比较。没有 $K$ 的攻击者无法为改过的消息算出正确标签。

HMAC 的结构（概念）：

$$\text{HMAC}(K,m)=H\bigl((K'\oplus opad)\,\Vert\,H((K'\oplus ipad)\,\Vert\,m)\bigr)$$

其中 $K'$ 是调整到哈希块长度的密钥，$ipad,opad$ 是固定常数。实现时直接调用库函数，**不要自己拼**；比较标签时使用常数时间比较，避免通过响应时间泄露信息。

### 4.3 公钥密码与签名

公钥体系用一对密钥：私钥签名，公钥验证。优点：**验证方不需要持有秘密**，所以即使验证端被攻破，也不能伪造签名。这正是 OTA 固件签名的合适场景：厂商用私钥签固件，设备里只存公钥。缺点：计算更慢。典型混合用法：公钥体系做身份认证与密钥协商，建立后的会话用对称密钥保护（这是 TLS 的思路，细节未核对）。

| 机制 | 提供 | 需要共享秘密 | 速度 | 机器人用途 |
|---|---|---|---|---|
| 哈希 | 摘要 | 否 | 很快 | 配置/固件指纹 |
| HMAC | 完整性、来源 | 是 | 快 | 短时命令凭据、内部通信 |
| 对称加密 | 机密性 | 是 | 快 | 视频、地图加密 |
| 数字签名 | 完整性、来源、不可否认 | 否（验证端） | 较慢 | 固件、策略包、证书 |

### 4.4 密钥长度与暴力破解的量级

密钥长度 $k$ 位，穷举平均需要 $2^{k-1}$ 次尝试。设攻击者每秒尝试 $10^{12}$ 次，对 128 位密钥穷举全部空间约需

$$\frac{2^{128}}{10^{12}\times3600\times24\times365}\approx1.08\times10^{19}\ \text{年}$$

即暴力破解不可行，真正的风险在**密钥管理**：硬编码在固件里、提交进代码库、日志里打印、长期不轮换。对比：8 位字母数字口令空间 $62^8$，约 47.6 位，以每秒 $10^{10}$ 次尝试约 6 小时可穷举，口令强度远低于密钥。

```python
import math
print(2**128 / 1e12 / 3600 / 24 / 365)     # 1.079e+19
print(math.log2(62**8), 62**8 / 1e10 / 3600)   # 47.63  6.07
```

## 5. 认证、授权与权限设计

### 5.1 认证与授权要分开

认证回答"你是谁"，授权回答"你能做什么"。证明了身份，不意味着可以做任何事。很多事故是"认证做了，授权没做"：合法登录的用户或模块，调用了它不该调用的接口。

### 5.2 最小权限与能力白名单

给每个主体（节点、用户、插件）显式列出允许的**动作 × 对象 × 范围**：

| 主体 | 允许 | 范围 |
|---|---|---|
| 遥控器 | 发速度命令 | 速度不超过档位上限；仅 `base` |
| 任务规划器 | 发导航目标 | 仅地图内目标；不能直接调电机 |
| LLM 规划插件 | 只产生"提案" | 必须经策略层；无直接执行权 |
| 维护工程师 | 修改参数、升级固件 | 需双因素与审计；仅维护模式 |
| 日志服务 | 只读状态 | 不可发命令 |

P6 的策略校验里有"权限（Permission）"与"白名单（Whitelist）"规则，P4 的执行边界也采用白名单：高层只能请求设备允许的有限动作集合，且参数有范围（见 [P6 安全执行链](../../01_项目课程/P6_深开鸿M-Robots平台软件/08_安全执行链.md)、[P4 执行边界](../../01_项目课程/P4_OpenHarmony智能园艺系统/11_执行边界_白名单_幂等与设备反馈.md)）。

### 5.3 模式与手动优先

权限随**运行模式**变化：维护模式可以关节单独运动，自动模式不可；有人在旁（手动）时手动命令优先于自动。P4 的"手动优先"和 P1 的"默认失能"从信息安全角度看，就是**让本地、物理在场的人拥有最高权限**。

### 5.4 凭据与密钥的生命周期

生成（足够随机）→ 分发（安全信道）→ 存储（安全存储区，不进代码库）→ 使用（最小暴露）→ 轮换（定期、泄露后立即）→ 撤销（设备丢失、人员离职）→ 销毁。每一步都可能出错。

## 6. 命令凭据与重放防护

### 6.1 重放攻击

攻击者不必破解任何东西：他只需录下一条**合法的、已认证的**命令，稍后原样再发。如果系统只验证"标签正确"，重放的消息会被接受。例如录下"前进 0.5 m/s"，一小时后在机器人旁边再发一次。

### 6.2 防御要素

1. **时间戳 + TTL**：消息带签发时刻，接收方拒绝过期的。需要时钟大体同步，并允许一个小的时钟偏差容限。
2. **随机数/单调序号（nonce / sequence）**：每条消息唯一，接收方记录已见过的，拒绝重复。
3. **绑定上下文**：把设备 ID、动作类型、参数一起纳入 MAC 覆盖范围，防止把给设备 A 的凭据拿去用于设备 B 或另一动作。
4. **短时效**：运动类凭据只有约 2 s，导航目标类约 30 s（P6 的设计取值）。过期必须重新校验当前状态，这样同时缓解 **TOCTOU**（检查时状态合法，使用时已不合法）。

### 6.3 滑动窗口

只记"所有见过的序号"会无限增长。采用**滑动窗口**：保存当前最高序号 $hi$ 与窗口宽度 $w$ 内的已见集合。对新序号 $n$：

- $n>hi$：接受，窗口前移到 $hi\leftarrow n$；
- $n\le hi-w$：太旧，拒绝；
- $hi-w<n\le hi$：若已见则拒绝（重放），否则接受并记录（允许轻微乱序）。

### 6.4 手算：窗口 $w=8$

初始 $hi=100$，已见 $\{100,98\}$。依次到达序号 103, 99, 99, 90, 101, 95：

| 序号 | 判断 | 结果 |
|---|---|---|
| 103 | 大于 100，前移窗口，$hi=103$ | 接受 |
| 99 | $103-8=95<99\le103$，未见过 | 接受 |
| 99 | 已见过 | 拒绝（重放） |
| 90 | $90\le95$，太旧 | 拒绝 |
| 101 | 窗口内未见过 | 接受 |
| 95 | $95\le95$，太旧 | 拒绝 |

**Python 复核：**

```python
class ReplayWindow:
    def __init__(self, w=8):
        self.w, self.hi, self.seen = w, -1, set()
    def accept(self, n):
        if n > self.hi:
            self.hi = n
            self.seen = {x for x in self.seen if x > self.hi - self.w}
            self.seen.add(n)
            return True
        if n <= self.hi - self.w or n in self.seen:
            return False
        self.seen.add(n)
        return True

rw = ReplayWindow(8)
rw.hi, rw.seen = 100, {100, 98}
print([rw.accept(x) for x in (103, 99, 99, 90, 101, 95)])
# [True, True, False, False, True, False]
```

输出与手算一致。

## 7. DDS-Security 概念

> **注意**：DDS-Security 是 OMG 的规范，ROS2 通过 SROS2 工具链支持（具体规范版本号、文件格式、命令行参数均**未核对**）。以下只讲概念。

### 7.1 为什么需要

DDS 默认是**自动发现、开放加入**：同一域（domain）里谁都能发现并订阅/发布。这对开发便利，对生产环境是风险。DDS-Security 在 DDS 之上增加了可插拔的安全机制。

### 7.2 五类插件概念

| 插件 | 作用 | 直觉 |
|---|---|---|
| 认证（Authentication） | 参与者出示证书，彼此验证身份 | 进门要刷卡 |
| 访问控制（Access Control） | 按策略规定某身份能发布/订阅哪些主题 | 刷卡后只能进指定房间 |
| 加密（Cryptographic） | 对数据加密、签名 | 房间里说的话加密 |
| 日志（Logging） | 记录安全事件 | 门禁记录 |
| 数据标记（Data Tagging） | 给数据加敏感级别等标签 | 文件分级 |

在 ROS2 中，这对应：为每个节点生成身份证书与权限文件（"哪个节点能发布哪些话题"），由证书颁发机构签发。

### 7.3 代价

- **CPU 与延迟**：加密/签名增加每条消息的开销，对高频小消息影响明显，需要实测（影响数值未核对，不要想当然）；
- **配置复杂度**：证书分发、权限文件维护、证书过期；
- **调试困难**：抓包看不到明文；
- **与实时性的冲突**：控制环内的消息通常走同机共享内存或受信总线，不一定开加密；加密主要用在跨设备、跨信任域的边界。

### 7.4 工程取舍

一个务实的分层：**网络边界**上开认证与访问控制（防陌生设备）；**跨信任域**的数据加密；**设备内部的实时控制环**依赖隔离（独立总线、进程隔离）而不是对每条消息加密；所有层次都保留审计。P6 的设备发现、能力注册和状态同步是在 M-DDS 上进行的，这些就是需要考虑"谁有资格注册什么能力"的位置（具体安全配置不在 CV 描述之内，面试时讲思路，不声称做过）。

## 8. OTA 与固件安全

### 8.1 威胁

OTA（Over-The-Air）升级让固件可以远程更新，但同时开了一个高危入口：伪造的固件等于完全控制设备。

### 8.2 安全链

1. **签名**：厂商在离线、受保护的环境用**私钥**对固件的哈希签名；
2. **传输**：用 TLS 等传输加密（防窃听，非必须但推荐），但**不依赖传输层保证完整性**，固件本身要有签名；
3. **验证**：设备里只存**公钥**（放在只读/受保护的区域），下载后重算哈希、验签，失败即丢弃；
4. **防回滚（anti-rollback）**：固件元数据中有单调递增的版本号；设备记录已安装的最高版本（存在受保护的计数器里），拒绝低版本，防止攻击者把设备降级到有已知漏洞的旧版；
5. **安全启动（secure boot）链**：上电后从不可修改的启动代码开始，逐级验证下一级镜像的签名，形成信任链（具体实现依硬件，未核对）；
6. **A/B 分区**：新固件写入备用分区，验证并试运行；成功"确认"后才切换为主；若启动失败或健康检查不过，自动回退到旧分区；
7. **分阶段发布**：先升级少量设备，监控健康，再扩大。

### 8.3 与功能安全的结合

升级失败不能让机器人进入危险状态：

- 升级只在**安全状态**（失能、停放、充电）下进行；
- 升级过程中断电，设备仍能从旧分区启动（A/B 提供）；
- 升级后的**首次运动**走第一次上线流程（见 [04 测试策略](./04_测试策略_仿真在环_硬件在环_回归.md) 的实机清单），不要直接投入全负载；
- 版本、配置哈希、签名者写入审计日志。

### 8.4 手算：验证流程（教学示例）

假设固件字节串 `firmware-v1.2.0` 的 SHA-256 摘要前 16 位十六进制为 `72cb4f60bb7f69c5`，厂商把完整摘要用私钥签名并随包发布。设备流程：

1. 下载固件，计算摘要，若前 16 位不是 `72cb4f60bb7f69c5` → 文件被改过，丢弃；
2. 用内置公钥验证签名：摘要与签名一致 → 来源可信；
3. 读取版本号 1.2.0，对比本地记录的最高版本（例 1.1.5）：$1.2.0>1.1.5$ → 通过防回滚；
4. 写入备用分区 B，设启动标志"试运行，3 次未确认则回退"；
5. 重启进 B，自检通过后确认，A 变为备份。

若攻击者把固件改成 `firmware-v1.2.1`，摘要变为 `8950801d177d5627`，第 1 步即失败。注意：只比对摘要而摘要本身来自同一下载渠道是**不安全**的，必须靠签名保证摘要可信。

## 9. 信息安全与功能安全的交互

1. **安全依赖信息安全**：如果命令通道被冒充，所有功能安全措施（限幅、看门狗）仍在，但"合法命令"可能是恶意的；所以执行端的限幅和策略检查是最后防线，不能被网络层的信任关系绕开。
2. **信息安全措施可能损害功能安全**：加密增加延迟，可能使延迟预算超限；认证失败导致命令被拒绝，可能使机器人"该动时不动"；证书过期使整个机队停摆。设计时必须评估对安全响应时间的影响。
3. **急停不应依赖网络认证**：硬件急停与本地停止必须在任何网络/认证状态下可用；允许任意来源的"停止"请求被执行（风险：拒绝服务式的恶意停车，但这比无法停车安全得多）。P6 的设计中，停止请求不需要过运动策略链。
4. **故障安全同样适用于安全机制自身**：证书服务不可达时，应该"拒绝新的运动授权并保持/进入安全状态"，而不是"默认放行"（fail-closed）。
5. **审计**：每个提案、裁决、凭据签发、执行结果可追溯（见 [05 章](./05_数据与日志_可观测性_回放与复盘.md)），既服务排障，也服务事后责任认定。
6. **大模型/AI 规划**：模型输出不可信（可能被提示词注入、可能幻觉），任何由 AI 产生的动作请求都当作**不可信提案**，由确定性的策略层校验（见 [P6 第 9 章](../../01_项目课程/P6_深开鸿M-Robots平台软件/09_LLM_AI规划进入物理执行的风险.md)）。

## 10. 完整手算示例

### 10.1 命令凭据：HMAC 签发与篡改检测

场景（教学示例）：策略层对一条运动命令签发凭据。共享密钥（仅为演示，真实系统不得硬编码）`demo-key-0123456789`，消息 `vx=0.50;wz=0.00;t=1000;nonce=7`。计算 HMAC-SHA256，取前 16 位十六进制作为展示。

```python
import hmac, hashlib
key = b"demo-key-0123456789"          # 演示用，勿用于真实系统
def mac(m):
    return hmac.new(key, m, hashlib.sha256).hexdigest()

msg = b"vx=0.50;wz=0.00;t=1000;nonce=7"
print(mac(msg)[:16])                                          # c340ef56618f3e73
print(mac(b"vx=0.90;wz=0.00;t=1000;nonce=7")[:16])            # 680de1a47baa0387
print(hmac.compare_digest(mac(msg), mac(msg)))                # True
```

只把速度由 0.50 改为 0.90，标签前 16 位由 `c340ef56618f3e73` 变为 `680de1a47baa0387`。没有密钥的攻击者无法计算新标签，所以网关重算后发现不一致，拒绝命令。

猜对一个截断到 64 位的标签的概率为 $2^{-64}\approx5.4\times10^{-20}$；若允许每秒尝试 $10^9$ 次伪造，穷举需要约 $2^{64}/10^9/(3600\cdot24\cdot365)\approx585$ 年。实际系统应使用完整长度标签。

### 10.2 凭据时效与时钟偏差

凭据于 $t_0=100.0$ s 签发，TTL $=2$ s，允许时钟偏差容限 $\delta=0.1$ s。网关接收时钟读数 $t_r$：

- $t_r=101.5$：年龄 1.5 s，小于 2 s，有效；
- $t_r=102.05$：年龄 2.05 s，处于容限内（$\le2.1$），有效但接近边缘；
- $t_r=102.3$：年龄 2.3 s，过期，拒绝并要求重新校验。

时效越短，攻击者能利用被截获凭据的窗口越小，但也要求签发端到网关的延迟（见 [01 章](./01_机器人系统架构设计_分层_接口_需求.md) 的延迟预算，约 8～31 ms）远小于 TTL。由此得到设计检查：$\text{TTL}\gg$ 最坏链路延迟（2 s 对 31 ms，约 60 倍余量），同时 $\text{TTL}$ 远小于"环境可能发生实质变化的时间"。

## 12. 常见错误与故障现象

1. **把功能安全措施当成信息安全。** 限幅、看门狗挡不住"合法的恶意命令"。
2. **只加密，不认证。** 加密不等于防篡改，没有完整性保护的密文也可能被改。
3. **只比对摘要，不验签。** 摘要和文件一起被替换。
4. **密钥硬编码在固件或代码库里**，所有设备共用一把，泄露一次全部失守。
5. **没有重放防护**：只验证标签，被录制的合法命令可无限重发。
6. **凭据永不过期**或时效过长，TOCTOU 无法缓解。
7. **MAC 不覆盖关键字段**（设备 ID、动作类型），凭据可被挪用。
8. **自实现密码算法**或用不安全的比较函数。
9. **证书过期导致机队停摆**，没有监控与续期流程。
10. **OTA 无防回滚**，攻击者降级到有漏洞的旧版。
11. **升级过程中断电变砖**，没有 A/B 分区与回退。
12. **认证失败时默认放行（fail-open）。**
13. **日志里打印密钥、令牌或人脸图像。**
14. **LLM 输出未经校验直达执行器。**

## 13. 面试怎么问、怎么答

**Q1. How would you secure the command channel of a robot?**

> I would authenticate the sender, keep authorisation separate from authentication, and make the commands short-lived and tamper-evident. In my platform work, a proposal goes through a policy check, and if it passes it gets a signed ticket with a short validity, so a replayed or stale command is rejected. On the execution side I still limit and watchdog everything, because security of the network should not be the only line of defence.

中文译文：我会认证发送方，把授权和认证分开，让命令短时有效并且可检测篡改。在平台项目里，提案先过策略检查，通过后得到带签名的短时凭据，所以重放或陈旧的命令会被拒绝。执行端仍然做限幅和看门狗，因为网络安全不应是唯一防线。

*Follow-up: What is a replay attack and how do you stop it? —* An attacker records a valid message and sends it again; I use timestamps with a short TTL, sequence numbers with a sliding window, and bind the device and action into the MAC.（追问：什么是重放攻击，怎么防？攻击者录下合法消息再发；用带短 TTL 的时间戳、带滑动窗口的序号，并把设备和动作绑定进 MAC。）

**Q2. What is the difference between safety and security?**

> Safety protects people and the environment from the system's accidental failures. Security protects the system from deliberate attacks. They interact: a security breach can cause unsafe motion, and a security feature, such as authentication, can add latency or block a needed stop. So I keep emergency stop independent of network authentication and make security mechanisms fail closed for motion but never block stopping.

中文译文：安全（safety）保护人和环境不受系统意外故障伤害；信息安全（security）保护系统不受故意攻击。二者相互作用：安全漏洞可能导致危险运动，而认证之类的安全功能可能增加延迟或阻断必要的停止。所以急停独立于网络认证，安全机制对"运动"是 fail-closed，但绝不阻止"停止"。

*Follow-up: Give an example of a conflict. —* Strict certificate checking might refuse commands when the certificate server is unreachable; for motion that is the right default, for stop it is not.（追问：举冲突的例子？证书服务不可达时严格校验会拒绝命令；对运动这是对的，对停止则不对。）

**Q3. How do you make OTA updates safe?**

> The firmware is signed offline with a private key, and the device only holds the public key, so it can verify but not forge. The device also checks a monotonic version counter to prevent rollback, installs into a spare partition, and only confirms after a health check, otherwise it falls back automatically. I would update in a safe state and roll out to a few units first.

中文译文：固件用私钥离线签名，设备只存公钥，因此只能验证不能伪造。设备还检查单调递增的版本计数器防回滚，写入备用分区，健康检查通过后才确认，否则自动回退。我会在安全状态下升级，并先对少量设备灰度。

*Follow-up: Why not just compare a hash? —* The hash and the file can be swapped together, so the hash must be protected by a signature or delivered over a trusted channel.（追问：为什么不只比对哈希？哈希和文件可以一起被替换，哈希必须由签名保护或通过可信渠道提供。）

**Q4. What is the security risk of connecting an LLM to a robot?**

> The model output is untrusted. It can hallucinate, or be manipulated by prompt injection, and the cost is a physical action. So I treat it as a proposal only, validate it with deterministic rules, such as whitelist, range, freshness and permission, and give it no direct path to the actuators. The model can suggest, but the policy layer and the execution layer decide.

中文译文：模型输出是不可信的，可能幻觉，也可能被提示词注入操纵，后果是物理动作。所以我只把它当作提案，用确定性的规则（白名单、范围、新鲜度、权限）校验，并且不给它直达执行器的路径。模型可以建议，决定权在策略层和执行层。

*Follow-up: How do you audit this? —* Every proposal, rule result, ticket and execution outcome is logged with a shared identifier so a decision can be reconstructed afterwards.（追问：怎么审计？每个提案、规则结果、凭据和执行结果用同一标识记录，可事后重建决策。）

## 14. 本章要点速记

1. 信息安全防故意攻击，功能安全防意外故障；机器人被攻破的后果是物理动作，所以完整性和可用性常比机密性更重要。
2. STRIDE：冒充、篡改、抵赖、泄露、拒绝服务、提权；对跨信任边界的数据流逐项检查。
3. 哈希不提供认证；MAC 需共享密钥；签名只需公钥验证，适合固件。
4. 128 位密钥不可暴力破解，风险在密钥管理（硬编码、泄露、不轮换）。
5. 认证与授权分开；最小权限、能力白名单、模式与手动优先。
6. 重放防护：短 TTL、nonce/序号、滑动窗口、MAC 绑定上下文；同时缓解 TOCTOU。
7. DDS-Security 五类插件：认证、访问控制、加密、日志、数据标记；有 CPU、复杂度与调试代价（数值未核对）。
8. OTA：签名、验签、防回滚、安全启动链、A/B 分区、回退、灰度、安全状态下升级。
9. 安全机制对"运动"fail-closed，对"停止"绝不阻断；急停不依赖网络认证。
10. LLM 输出是不可信提案，必须经确定性策略层。

## 15. 自测题

1. 为什么只发送"固件加它的 SHA-256"不能防止恶意替换？*要点：攻击者可以同时替换两者；需要签名或可信渠道。*
2. 窗口 $w=4$，$hi=50$，已见 $\{50,48\}$，序号 51、47、48、46 的结果各是什么？*答案：51 接受（hi=51，窗口下界 47）；47 满足 $47\le51-4$，太旧，拒绝；48 已见，拒绝；46 太旧，拒绝。*
3. 凭据 TTL 2 s，最坏链路延迟 31 ms，TTL 对延迟的余量倍数？*答案：$2/0.031\approx64.5$ 倍。*
4. 为什么 HMAC 标签要覆盖设备 ID 与动作类型？*要点：防止把给 A 的凭据用于 B 或另一动作。*
5. 解释 fail-closed 与 fail-open，并分别说明在"运动授权"和"停止"上应取哪种。*要点：运动授权 fail-closed；停止请求应总被放行。*
