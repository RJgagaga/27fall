## 1. 要解决什么问题

假设一台只有一个 CPU 核的机器同时运行三个程序：控制算法、日志记录、网络通信。没有操作系统时会遇到五个麻烦：

1. **CPU 怎么分**：谁先跑、跑多久？一个程序死循环能不能拖死整台机器？——**调度**与**抢占**。
2. **内存怎么分**：三个程序都以为地址 0x1000 是自己的，怎么避免互相覆盖？一个程序写越界怎么不让它搞坏别人？——**虚拟内存**与**保护**。
3. **怎么共享数据**：两个程序同时改一个计数器会怎样？——**同步**。
4. **设备怎么用**：串口、网卡、磁盘速度差几个数量级，CPU 不能傻等。——**IO 模型**、中断、DMA。
5. **出了错怎么办**：互相等待对方释放资源怎么办？——**死锁**。

对机器人工程师，这些不是抽象概念：P3/P7 固件里 FreeRTOS 任务的优先级决定控制环能否按时执行；P2、P5、P6 的 ROS2 节点跑在 Linux 上，进程间用共享内存或 socket 通信；一个回调里加了互斥锁而另一个线程反向加锁，就会出现"程序卡住没有报错"的死锁现象。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 进程（process） | 资源分配的单位：独立的虚拟地址空间、文件描述符表、权限 |
| 线程（thread） | CPU 调度的单位：同一进程内共享地址空间，各自有栈、寄存器、程序计数器（PC） |
| PCB / TCB | 进程 / 线程控制块，内核保存其状态的数据结构 |
| 上下文切换 | 保存当前执行流的 CPU 状态，恢复另一个的状态 |
| 内核态 / 用户态 | CPU 的特权级；系统调用从用户态陷入内核态 |
| 虚拟地址 VA / 物理地址 PA | 程序看到的地址 / 内存条上的真实地址 |
| 页（page）/ 页框（frame） | 虚拟内存 / 物理内存按固定大小（常见 4 KiB）划分的块 |
| 页表（page table） | VA 页号到 PA 页框号的映射 |
| TLB | 页表项的高速缓存（Translation Lookaside Buffer） |
| 缺页（page fault） | 访问的页不在内存（或权限不符），由内核处理 |
| 周转时间 TAT | 完成时刻 − 到达时刻 |
| 等待时间 WT | TAT − 运行时间（CPU burst） |
| 抢占（preemption） | 内核强行收回正在运行任务的 CPU |
| 临界区 | 访问共享资源、同一时刻只允许一个执行流进入的代码段 |
| 死锁 | 一组执行流互相等待对方持有的资源，永远无法前进 |

## 3. 进程、线程与上下文切换

### 3.1 进程与线程的本质区别

**进程**是"资源的容器"：它拥有一个独立的虚拟地址空间（代码段、数据段、堆、栈、内存映射区）、打开的文件、信号处理、用户身份。**线程**是"执行的流"：同一个进程内的多个线程共享地址空间和文件描述符，只有各自私有的栈、寄存器集合、线程局部存储。

推论：

- 线程间通信简单（直接读写共享变量），但正因共享，需要同步；
- 一个线程越界写内存可能破坏整个进程；进程之间有硬件隔离（MMU），一个进程崩溃一般不影响其他进程；
- 创建与切换线程比进程便宜：不必切换页表。

在 Linux 里，进程与线程在内核中都是 `task_struct`，线程只是"和别的 task 共享地址空间"的 task（`clone` 系统调用的标志位决定共享什么）。这一点是"常见实现"，细节依内核版本，未逐版本核对。

**协程（coroutine）**：用户态的轻量执行流，由程序自己在 `await`/`yield` 处主动让出，不经过内核调度。P4 服务端的 asyncio 就是协程（见 [P4 服务端 DataStore 与 asyncio](../../01_项目课程/P4_OpenHarmony智能园艺系统/09_服务端_DataStore_WebSocket_asyncio.md)）：单线程里靠事件循环在 IO 等待时切换任务，适合 IO 密集；CPU 密集的计算会阻塞整个事件循环。

### 3.2 进程的状态

```text
        创建            调度器选中
 new ---------> ready ------------> running
                  ^  ^                | |
     IO/事件完成   |  | 时间片用完     | | 等待 IO/锁
                  |  +----------------+ |
               blocked <----------------+
                                running --退出--> terminated
```

三个核心状态：就绪（等 CPU）、运行（占 CPU）、阻塞（等 IO 或锁）。FreeRTOS 的任务状态是同一模型：Running / Ready / Blocked / Suspended。

### 3.3 上下文切换保存什么、代价多大

必须保存：通用寄存器、程序计数器、栈指针、状态寄存器（以及浮点/向量寄存器，若用过）。进程切换还要切换**页表基址寄存器**，导致 TLB 失效（除非带 ASID 标签），之后一段时间内缓存和 TLB 都是"冷"的，间接代价往往比直接保存寄存器大得多。

量级（教学估计，非实测）：直接切换通常在微秒量级，间接的缓存/TLB 重新预热可能再加几微秒到几十微秒。Cortex-M 上 FreeRTOS 的任务切换由 PendSV 异常完成，保存/恢复一组寄存器，代价在数百个时钟周期的量级（取决于是否使用 FPU 懒保存，未逐芯片核对）。

时间片开销比例：设时间片 $q$、切换代价 $c$，则切换开销占比为 $c/(q+c)$。示例（非项目实测）：$q=10\,\text{ms}$，$c=0.05\,\text{ms}$ 时约 0.4975%（Python 复核）；$q$ 过小则开销显著。

### 3.4 系统调用与中断

用户程序要读文件、发网络包，必须通过**系统调用**陷入内核（用特殊指令切到内核态，经系统调用表分派）。**中断**是硬件异步通知（定时器、网卡、串口），CPU 暂停当前执行流转去运行中断服务程序。时钟中断是抢占式调度的基础：每隔一个 tick 内核有机会检查是否该换任务。

## 4. 虚拟内存与分页

### 4.1 为什么要虚拟内存

直接使用物理地址有三个问题：不同程序地址冲突；程序能访问到别人的内存；物理内存不够就装不下。虚拟内存给每个进程一个**独立的、连续的地址空间**，由 MMU（内存管理单元）在硬件上把 VA 翻译成 PA，翻译规则由内核维护的页表决定。收益：隔离、保护、可以"超卖"内存（把暂时不用的页放到磁盘）、共享（多个进程映射同一个物理页，如共享库）。

### 4.2 分页与地址翻译

页大小 $P$ 为 $2^k$（4 KiB 时 $k=12$）。虚拟地址 $\text{VA}$ 分成两部分：

$$\text{页号 VPN}=\lfloor \text{VA}/P\rfloor,\qquad \text{页内偏移 }d=\text{VA}\bmod P$$

页表把 VPN 映射到物理页框号 PFN，物理地址：

$$\text{PA}=\text{PFN}\times P+d$$

**手算**：页大小 4096 B，页表 $\{0\!\to\!5,\ 1\!\to\!9,\ 2\!\to\!3\}$（页号→页框号）。虚拟地址 $\text{VA}=\text{0x2A5C}=10844$。

- VPN $=\lfloor10844/4096\rfloor=2$，偏移 $d=10844-8192=2652=\text{0xA5C}$；
- 页表查得 PFN $=3$；
- $\text{PA}=3\times4096+2652=14940=\text{0x3A5C}$。

Python 复核：`divmod(0x2A5C, 4096)` 得 `(2, 2652)`，`hex(3*4096+2652)` 为 `0x3a5c`。注意偏移位不变，只替换高位页号——所以偏移取低 12 位、页号取高位。

页表项（PTE）除了 PFN，还有标志位：有效位（V）、读/写/执行权限、用户/内核位、访问位（A）、脏位（D）。访问无效页或违反权限触发缺页异常，由内核处理：合法的缺页（页被换出，或首次访问延迟分配）则调入页并重试；非法访问则向进程发 `SIGSEGV`（段错误）。

### 4.3 多级页表

32 位地址、4 KiB 页，单级页表有 $2^{20}$ 项，每项 4 B，共 4 MiB，且每个进程都要一份。多数进程只用地址空间的一小部分，大量项是空的。**二级页表**把 20 位页号再分成 10 位 + 10 位：一级目录（1024 项）每项指向一张二级表（1024 项），未使用的区域不分配二级表。

**手算**：$\text{VA}=\text{0x08049F10}$，二级页表（10+10+12）：

- 一级索引 $=\text{VA}\gg22\,\&\,\text{0x3FF}=32$；
- 二级索引 $=\text{VA}\gg12\,\&\,\text{0x3FF}=73$；
- 偏移 $=\text{VA}\,\&\,\text{0xFFF}=3856$。

（Python 复核：`32 73 3856`。）64 位系统用 4 级甚至 5 级页表（x86-64 常见 48 位虚拟地址、4 级，每级 9 位，该配置属于"常见实现"，其他架构不同）。代价是每次翻译需要多次内存访问，所以必须有 TLB。

### 4.4 TLB 与有效访问时间

TLB 缓存最近用过的 VPN→PFN。命中则一次内存访问（取数据）即可；未命中要先查页表（单级需多一次内存访问）。设 TLB 命中率 $h$，TLB 查找时间 $t$，内存访问时间 $m$，单级页表：

$$\text{EAT}=h\,(t+m)+(1-h)\,(t+2m)$$

**手算**（示例，非实测）：$h=0.98$，$t=1\,\text{ns}$，$m=100\,\text{ns}$：

$\text{EAT}=0.98\times101+0.02\times201=98.98+4.02=103\,\text{ns}$（Python 复核 103.0）。

即命中率从 100% 降到 98%，平均访问时间只多了约 2%，说明 TLB 局部性很重要；如果是 4 级页表，未命中的代价是 $t+5m$，对"随机访问大数组"的程序影响会明显更大。这就是**大页（huge page）**减少 TLB 压力的原因，缓存与局部性在 [体系结构一章](./04_计算机体系结构_缓存_流水线_SIMD_GPU.md) 中继续展开。

### 4.5 进程地址空间布局

```text
高地址  +----------------------+
        |  内核空间            |
        +----------------------+
        |  栈 (向下增长)       |  局部变量、返回地址
        |          |           |
        |          v           |
        |  ......              |
        |          ^           |
        |          |           |
        |  内存映射区 (mmap)   |  共享库、文件映射
        |  堆 (向上增长)       |  malloc / new
        +----------------------+
        |  .bss  (未初始化全局)|
        |  .data (已初始化全局)|
        |  .text (代码，只读)  |
低地址  +----------------------+
```

MCU（如 STM32）没有 MMU（Cortex-M 常带可选的 MPU，只做区域保护，不做地址翻译），所以没有虚拟内存，所有任务共用一个物理地址空间，一个任务的栈溢出可能直接踩坏别的任务——这是 FreeRTOS 项目必须检查栈水位的原因（见 [FreeRTOS 实时系统](../11_嵌入式与通信/02_FreeRTOS实时系统.md)）。

## 5. 页面置换

物理页框不够时，缺页处理需要选一个"牺牲页"换出。设页框数 $n$，引用串依次访问页号。

- **FIFO**：换出最早进入内存的页。实现简单，但可能换出常用页，并有 **Belady 异常**：增加页框数反而缺页更多。
- **LRU**（最近最少使用）：换出最久未被访问的页，利用时间局部性，近似最优；精确实现需要记录访问时间（链表 + 哈希，$O(1)$），硬件上常用近似算法（CLOCK/二次机会：用访问位）。
- **OPT**（最优）：换出"未来最久不会被访问"的页。需要预知未来，不可实现，只作基准。

**手算**：引用串 `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1`，3 个页框，起始为空。三种算法的缺页数：FIFO = 15，LRU = 12，OPT = 9（Python 复核）。

为了便于核对，给出 LRU 前几步的页框状态（页框中按"最近使用在右"排列）：

| 访问 | 7 | 0 | 1 | 2 | 0 | 3 | 0 | 4 |
|---|---|---|---|---|---|---|---|---|
| 页框 | 7 | 7 0 | 7 0 1 | 0 1 2 | 1 2 0 | 2 0 3 | 2 3 0 | 3 0 4 |
| 缺页 | 是 | 是 | 是 | 是（换 7） | 否 | 是（换 1） | 否 | 是（换 2） |

**Belady 异常**：引用串 `1 2 3 4 1 2 5 1 2 3 4 5`，FIFO 在 3 个页框时缺页 9 次，4 个页框时缺页 10 次（Python 复核），页框更多缺页更多。LRU 与 OPT 属于"栈算法"，没有这个异常。

**抖动（thrashing）**：进程的活跃工作集（working set）大于分配的页框，几乎每次访问都缺页，CPU 大部分时间花在换页，利用率骤降。对策：降低并发度、增加内存、按工作集分配。

## 6. CPU 调度

### 6.1 目标与指标

指标：CPU 利用率、吞吐量、周转时间、等待时间、**响应时间**（第一次得到 CPU 的时间）、公平性。批处理关心吞吐与周转，交互式关心响应时间，**实时系统关心"是否满足截止期"**，其理论见 [实时调度理论](../11_嵌入式与通信/11_实时调度理论_RMS_EDF_优先级反转.md)。

### 6.2 基本算法

- **FCFS**（先来先服务）：按到达顺序，非抢占。简单，但有**护航效应**：长作业在前，短作业都得等。
- **SJF**（最短作业优先）：先运行预计时间最短的。平均等待时间最优（可证明，用交换论证：把长作业放在短作业前面，只会增加总等待时间）；缺点是需要预知运行时间、长作业可能饥饿。抢占式版本是 SRTF。
- **时间片轮转（RR）**：每个进程最多连续运行一个时间片 $q$，用完回就绪队列尾。响应好，周转时间通常比 SJF 差。$q$ 过大退化为 FCFS，过小则切换开销大（见 3.3）。
- **优先级调度**：按优先级选择；低优先级可能饥饿，用"老化"（等待越久优先级越高）缓解。
- **多级反馈队列（MLFQ）**：多个优先级队列，新进程进最高队列，用完时间片则降级，IO 密集型（常主动让出）留在高优先级。无需预知运行时间就能近似 SJF 并保证交互响应。

### 6.3 完整手算：四个进程三种算法

进程（到达时间 $a$，运行时间 $b$）：P1(0, 6)，P2(1, 8)，P3(2, 7)，P4(3, 3)。

**FCFS**：P1 0–6，P2 6–14，P3 14–21，P4 21–24。完成时刻 6/14/21/24；周转时间 6/13/19/21，平均 14.75；等待时间 0/5/12/18，平均 8.75。

**SJF（非抢占）**：t=0 只有 P1，运行到 6；此时 P2(8)、P3(7)、P4(3) 都已到达，选 P4 运行 6–9；再选 P3（7）9–16；最后 P2 16–24。完成时刻 P1=6，P4=9，P3=16，P2=24。周转时间 P1=6，P2=23，P3=14，P4=6，平均 12.25；等待时间平均 6.25。

**RR（$q=4$）**：运行序列 P1 0–4，P2 4–8，P3 8–12，P4 12–15（P4 只需 3，提前结束），P1 15–17，P2 17–21，P3 21–24。完成时刻 P4=15，P1=17，P2=21，P3=24。周转时间 P1=17，P2=20，P3=22，P4=12，平均 17.75；等待时间平均 11.75。

| 算法 | 平均周转 | 平均等待 | 观察 |
|---|---|---|---|
| FCFS | 14.75 | 8.75 | 简单，护航效应 |
| SJF | 12.25 | 6.25 | 平均等待最优 |
| RR($q=4$) | 17.75 | 11.75 | 平均更差，但没有进程等很久才第一次运行 |

（上表全部由 Python 模拟复核。）RR 的优势是第一次运行时间：P4 在 t=12 首次运行，而 FCFS 要到 t=21；若进程数更多，交互式用户的感受差异会更明显。

### 6.4 Linux 与 FreeRTOS 的调度对比

| 方面 | 通用 Linux（CFS 等） | FreeRTOS |
|---|---|---|
| 目标 | 公平、吞吐、交互 | 确定性、按优先级响应 |
| 策略 | 按虚拟运行时间（vruntime）近似公平分享 CPU | 固定优先级抢占；同优先级可选时间片轮转 |
| 实时扩展 | `SCHED_FIFO`、`SCHED_RR`，PREEMPT_RT 补丁 | 本身就是固定优先级调度 |
| 内存 | 虚拟内存，进程隔离 | 单一地址空间，可选 MPU |

通用 Linux 内核默认调度器的细节随版本变化（近年有从 CFS 向 EEVDF 的演进），这里未逐版本核对，面试说"公平调度、按权重分配 CPU 时间"即可。实时需求的 Linux 方案见 [嵌入式 Linux 与 RT-Preempt](../11_嵌入式与通信/12_嵌入式Linux_设备树_驱动_RT-Preempt.md)。

## 7. 同步原语与死锁

### 7.1 竞争条件

两个线程各执行 `counter++`。这一句在机器层是三步：读、加、写。若交织为 A 读 0、B 读 0、A 写 1、B 写 1，结果为 1 而不是 2。**竞争条件（race condition）**指结果依赖于线程执行的交织顺序。解决：把读-改-写做成不可分割的整体——用互斥锁，或硬件原子指令（见 [并发与内存模型](./05_并发与内存模型_锁_原子_无锁.md)）。

### 7.2 互斥锁、信号量、条件变量

- **互斥锁（mutex）**：同一时刻只有一个持有者；谁加锁谁解锁；用于保护临界区。
- **信号量（semaphore）**：计数器 + 等待队列，$P$（wait）减 1，若不足则阻塞；$V$（signal）加 1 并唤醒。二值信号量用于事件通知（可由中断释放，用于"通知任务"），计数信号量用于资源池。**互斥量与二值信号量的关键区别**：互斥量有所有权，且（在 FreeRTOS 里）带优先级继承；二值信号量没有。
- **条件变量**：与互斥锁配合，"在某条件成立前睡眠"。必须用 `while` 而不是 `if` 检查条件，因为可能被**虚假唤醒**，或者被唤醒时条件已被别的线程改变。
- **自旋锁**：忙等，不让出 CPU，适合临界区极短、不能睡眠的场景（如中断上下文）；单核上自旋无意义。
- **读写锁**：允许多读单写。

经典**生产者—消费者**：用一个有界缓冲区，一个互斥量保护缓冲区，两个信号量 `empty`（空槽数）、`full`（已用槽数）。生产者 `P(empty); lock; put; unlock; V(full)`，消费者对称。**顺序不能颠倒**：若先 `lock` 再 `P(empty)`，缓冲区满时生产者持锁睡眠，消费者拿不到锁，死锁。

### 7.3 死锁的四个必要条件

1. **互斥**：资源一次只能被一个执行流占用；
2. **持有并等待**：持有部分资源的同时请求其他资源；
3. **不可剥夺**：已获得的资源不能被强行收回；
4. **循环等待**：存在一个环，每个执行流等待环中下一个持有的资源。

四个条件**同时**满足才可能死锁，破坏任一个即可防止：
- 破坏持有并等待：一次性申请所有资源；
- 破坏不可剥夺：`try_lock` 失败则释放已持有的锁（回退重试）；
- 破坏循环等待：**给所有锁规定全局加锁顺序**，所有线程按序加锁——工程中最常用。

最小的死锁：线程 A 先锁 `m1` 再锁 `m2`，线程 B 先锁 `m2` 再锁 `m1`；交织到 A 持有 `m1`、B 持有 `m2`，互相等待。C++17 的 `std::scoped_lock(m1, m2)` 使用避免死锁的算法一次性锁多个互斥量（实现细节依标准库，未核对）。

### 7.4 银行家算法：死锁避免

系统有若干类资源，状态用四个量描述：`Available`（当前可用）、`Max`（各进程最大需求）、`Allocation`（已分配）、`Need = Max − Allocation`。**安全状态**：存在一个进程执行序列，每个进程都能拿到其剩余需求并运行完毕，释放的资源再供后续进程使用。银行家算法在每次分配前"试分配"，若试分配后仍是安全状态才真正批准。

**安全性检查**：令 `Work = Available`，`Finish = 假`；重复找一个未完成且 `Need ≤ Work` 的进程，令 `Work += Allocation`，标记完成；若所有进程都能完成则安全。

**手算**（经典数据，3 类资源 A、B、C，5 个进程）：

| 进程 | Allocation | Max | Need = Max − Alloc |
|---|---|---|---|
| P0 | (0,1,0) | (7,5,3) | (7,4,3) |
| P1 | (2,0,0) | (3,2,2) | (1,2,2) |
| P2 | (3,0,2) | (9,0,2) | (6,0,0) |
| P3 | (2,1,1) | (2,2,2) | (0,1,1) |
| P4 | (0,0,2) | (4,3,3) | (4,3,1) |

`Available = (3,3,2)`。逐步：

1. P1：Need (1,2,2) ≤ (3,3,2)，运行完，Work = (3,3,2)+(2,0,0) = (5,3,2)；
2. P3：Need (0,1,1) ≤ (5,3,2)，Work = (5,3,2)+(2,1,1) = (7,4,3)；
3. P4：Need (4,3,1) ≤ (7,4,3)，Work = (7,4,3)+(0,0,2) = (7,4,5)；
4. P0：Need (7,4,3) ≤ (7,4,5)，Work = (7,4,5)+(0,1,0) = (7,5,5)；
5. P2：Need (6,0,0) ≤ (7,5,5)，Work = (7,5,5)+(3,0,2) = (10,5,7)。

安全序列 $\langle P1,P3,P4,P0,P2\rangle$（Python 复核，Work 序列与上述一致）。银行家算法需要事先知道每个进程的最大需求，且复杂度为 $O(m n^2)$，所以通用 OS 很少实际使用，更多是理解"避免"与"预防"的区别。

### 7.5 优先级反转（预告）

低优先级任务持有互斥量，被中优先级任务抢占，高优先级任务因等锁而间接被中优先级任务压住。解决：优先级继承或天花板协议。详见 [实时调度理论](../11_嵌入式与通信/11_实时调度理论_RMS_EDF_优先级反转.md)。

## 8. IO 模型与 epoll

### 8.1 阻塞与非阻塞，同步与异步

读一个网络套接字时，数据可能还没到。五种常见模型（Unix 网络编程的分类）：

1. **阻塞 IO**：`read` 一直阻塞到数据到达并复制完成；一个线程服务一个连接；
2. **非阻塞 IO**：数据没到立即返回 `EAGAIN`，调用者轮询（忙等，浪费 CPU）；
3. **IO 多路复用**：用 `select/poll/epoll` 同时监视大量描述符，哪个就绪再去读；
4. **信号驱动 IO**：数据就绪时内核发信号；
5. **异步 IO**：发起请求后立即返回，内核完成"等待数据 + 复制到用户缓冲区"两个阶段后通知（如 Linux `io_uring`、Windows IOCP）。

关键区分：前四种在**数据从内核复制到用户空间**这一步都会阻塞调用者，所以严格来说是同步 IO；只有第五种整个过程都不阻塞，才是 POSIX 意义上的异步 IO。日常说"异步"常指"事件驱动 + 回调/协程"，要看上下文。

### 8.2 select / poll / epoll

| 机制 | 数据结构 | 每次调用代价 | 描述符上限 | 通知方式 |
|---|---|---|---|---|
| select | 位图 fd_set | 每次把全集复制到内核并线性扫描，$O(n)$ | 通常 1024（`FD_SETSIZE`） | 水平触发 |
| poll | 数组 pollfd | 线性扫描 $O(n)$ | 无硬上限 | 水平触发 |
| epoll | 内核红黑树 + 就绪链表 | 只返回就绪的，与活跃数相关 | 受内存限制 | 水平 / 边缘触发 |

**水平触发（LT）**：只要缓冲区有数据就一直通知；**边缘触发（ET）**：状态变化时通知一次，必须配合非阻塞 IO，一次读到 `EAGAIN`，否则会丢事件。epoll 适合"连接多、同一时刻活跃的少"；连接少且大多活跃时优势不明显。

### 8.3 中断、轮询与 DMA

设备通知 CPU 的三种方式：**轮询**（CPU 反复查询，简单、延迟确定，但浪费 CPU）、**中断**（设备就绪时打断 CPU）、**DMA**（设备与内存之间直接搬运数据，完成后才中断一次）。STM32 上 UART 接收大量数据用 DMA + 空闲中断是典型做法，详见 [STM32 时钟、GPIO、中断与 DMA](../11_嵌入式与通信/01_STM32_时钟_GPIO_中断_DMA.md)。

## 9. 完整手算（Python 复核）

本章的所有数值例子均已用 Python 3.12 运行复核，核心代码如下（教学示例，非项目源码）：

```python
def lru(ref, n):
    frames, faults = [], 0
    for r in ref:
        if r in frames:
            frames.remove(r); frames.append(r)      # 刷新为最近使用
        else:
            faults += 1
            if len(frames) == n:
                frames.pop(0)                       # 弹出最久未使用
            frames.append(r)
    return faults

ref = [7,0,1,2,0,3,0,4,2,3,0,3,2,1,2,0,1,7,0,1]
print(lru(ref, 3))   # 12

# 地址翻译
vpn, off = divmod(0x2A5C, 4096)
page_table = {0: 5, 1: 9, 2: 3}
print(vpn, off, hex(page_table[vpn] * 4096 + off))   # 2 2652 0x3a5c
```

## 11. 常见错误

1. **把线程当"便宜的进程"乱开**：线程多了切换与同步开销上升；CPU 密集任务线程数一般不应大幅超过核数。
2. **条件变量用 `if` 而非 `while`**：虚假唤醒后读到不满足的条件。
3. **加锁顺序不一致**：典型死锁来源；在代码评审里检查"所有路径的加锁顺序"。
4. **持锁做耗时操作**：持锁时调用阻塞 IO、日志、动态分配，使其他线程长时间等待；在实时线程里更危险。
5. **在中断服务程序里调用会阻塞的 API**：FreeRTOS 要用带 `FromISR` 后缀的接口。
6. **以为 `volatile` 能解决线程同步**：它只阻止编译器优化，不提供原子性或内存序（见 [并发与内存模型](./05_并发与内存模型_锁_原子_无锁.md)）。
7. **栈太小**：嵌入式大数组放局部变量，导致栈溢出；应放静态区或堆，并启用栈溢出检测钩子。
8. **在 epoll 的 ET 模式下只读一次**：丢失后续数据。
9. **把"阻塞"与"同步"混为一谈**：阻塞描述调用者是否等待；同步/异步描述通知机制。
10. **忽略 TLB/缓存的间接代价**：只看到"切换几微秒"而忽略切换后的冷启动。

## 12. 英文面试问答

### Q1. What is the difference between a process and a thread?

"A process is the unit of resource ownership: it has its own virtual address space, file descriptors and permissions. A thread is the unit of scheduling inside a process. Threads in the same process share the address space and the heap, but each has its own stack and registers. That makes thread creation and context switching cheaper, and communication easier, but it also means a bug in one thread can corrupt the whole process, and shared data needs synchronization."

中文要点：进程是资源单位（独立地址空间），线程是调度单位（共享地址空间，私有栈与寄存器）；线程更便宜、通信更容易，但需要同步，且一个线程出错可能拖垮整个进程。

**追问**：

- *"What exactly is saved in a context switch?"* — "The program counter, stack pointer, general registers and status flags, plus floating point state if it was used. For a process switch the kernel also switches the page table, which flushes or tags the TLB, so the hidden cost is the cold caches afterwards."
- *"On your robot, what plays the role of a process?"* — "On the STM32 there is no MMU, so FreeRTOS only has tasks, which are like threads in one address space. On the Linux side, each ROS2 node is typically its own process."（诚实回答：MCU 上只有任务，没有进程。）

### Q2. Explain virtual memory and what happens on a page fault.

"Virtual memory gives each process its own address space. The MMU translates virtual addresses to physical ones using page tables, and a TLB caches recent translations. If the page is not present, or the access violates permissions, the CPU raises a page fault. If the access is legal, for example the page was swapped out or is allocated lazily, the kernel loads or allocates the page, updates the page table, and restarts the instruction. If it is illegal, the process gets a segmentation fault."

中文要点：每个进程独立地址空间；MMU + 页表翻译，TLB 缓存；缺页时合法则调入并重试，非法则段错误。

**追问**：*"How can page faults hurt a real-time control loop?"* — "A fault that needs disk or even just a kernel allocation can add unpredictable delay, so on Linux for real-time work people lock memory with mlockall and pre-allocate buffers. On an MCU without virtual memory this problem does not exist, which is one reason we use bare-metal or an RTOS for the inner loops."

### Q3. What are the four conditions for deadlock, and how do you prevent it in practice?

"Mutual exclusion, hold and wait, no preemption, and circular wait. All four must hold. In practice the cheapest fix is to break circular wait by defining a global lock order and always acquiring locks in that order. Other options are acquiring all locks at once, using try-lock with back-off, or avoiding nested locks by redesigning around message passing."

中文要点：互斥、持有并等待、不可剥夺、循环等待；实践中规定全局加锁顺序；也可一次性申请、try_lock 回退、改成消息传递。

**追问**：*"What is the difference between deadlock avoidance and prevention?"* — "Prevention structurally removes one of the four conditions. Avoidance, like the banker's algorithm, allows all four but checks at runtime that a request keeps the system in a safe state, which needs advance knowledge of maximum demands."

### Q4. How does FreeRTOS scheduling differ from Linux scheduling?

"FreeRTOS uses fixed-priority preemptive scheduling: the highest-priority ready task always runs, and equal priorities can share time slices. That gives bounded, analyzable response times, which is what a control loop needs. A general-purpose Linux scheduler aims at fairness and throughput, and without real-time patches it cannot give hard guarantees. In my robot firmware I used FreeRTOS tasks with different priorities for the control loop, communication and so on, so that the control task always preempts the lower-priority work."

中文要点：FreeRTOS 固定优先级抢占，响应可分析；Linux 通用调度追求公平与吞吐，无实时补丁给不了硬保证。最后一句须与自己在 P3/P7 的实际任务划分一致，细节参见项目章节。

## 13. 要点速记、自测题、相关链接

### 要点速记

1. 进程是资源单位，线程是调度单位；线程共享地址空间，私有栈与寄存器。
2. 上下文切换的直接代价是保存恢复寄存器，间接代价是缓存与 TLB 变冷。
3. $\text{PA}=\text{PFN}\times P+d$，偏移位不变；多级页表节省空间，TLB 节省时间。
4. $\text{EAT}=h(t+m)+(1-h)(t+2m)$（单级页表）。
5. FIFO 有 Belady 异常；LRU、OPT 是栈算法；抖动源于工作集大于页框。
6. SJF 平均等待最优；RR 响应好但周转差；MLFQ 无需预知时间。
7. 条件变量必须用 `while` 检查条件；互斥量有所有权，二值信号量没有。
8. 死锁四条件：互斥、持有并等待、不可剥夺、循环等待；统一加锁顺序最实用。
9. 银行家算法检查"是否存在安全序列"，需要预知最大需求。
10. 前四种 IO 模型在复制阶段都阻塞；epoll 适合连接多、活跃少；ET 必须读到 `EAGAIN`。

### 自测题

1. 页大小 4 KiB，页表 $\{0\to5,1\to9,2\to3\}$，求 VA = 0x1ABC 的物理地址。
   *要点*：VPN=1，偏移=0xABC；PFN=9；PA=9×4096+0xABC=0x9ABC。
2. TLB 命中率 95%，TLB 查找 2 ns，内存 80 ns，单级页表，求 EAT。
   *要点*：$0.95\times82+0.05\times162=77.9+8.1=86$ ns。
3. 为什么生产者—消费者里"先锁互斥量再等信号量"会死锁？
   *要点*：缓冲区满时生产者持锁睡眠，消费者无法获取锁取走数据。
4. 说明 SJF 为什么使平均等待时间最小。
   *要点*：交换论证：若长作业在短作业前，交换后短作业少等了长作业的时间而长作业多等短作业的时间，总和减少。
5. ET 模式下的 epoll 为什么必须配合非阻塞 IO？
   *要点*：ET 只通知一次，必须循环读到 `EAGAIN` 才能确保读空；阻塞 socket 在最后一次读会卡住线程。
