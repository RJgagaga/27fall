## 1. 要解决什么问题

先看三段"看起来没问题"的代码。

```cpp
// 例 1：两个线程各执行 100 万次
counter++;

// 例 2：线程 A 写，线程 B 读
data = 42;        // A
ready = true;     // A
while (!ready) {} // B
use(data);        // B，能保证读到 42 吗？

// 例 3：两个线程
// A: x = 1; r1 = y;      B: y = 1; r2 = x;
// 能否出现 r1 == 0 且 r2 == 0？
```

答案分别是：例 1 会丢更新（结果小于预期）；例 2 在没有同步时**不能保证**（编译器可能把 `ready` 读取提到循环外导致死循环，CPU 可能让 `ready` 先于 `data` 可见）；例 3 在宽松内存序下**可能**出现 `r1=r2=0`，本章会实际跑出来。要回答它们，需要三个概念：

1. **原子性（atomicity）**：一个操作要么完全发生要么完全没发生，别人看不到中间态。`counter++` 不是原子的。
2. **可见性（visibility）**：一个线程写入的值，什么时候对其他线程可见。受缓存、写缓冲、编译器寄存器分配影响。
3. **有序性（ordering）**：多条读写在别的线程看来是什么顺序。编译器和 CPU 都会重排。

锁、原子操作、内存序，都是为了对这三者提供**可控的保证**。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 数据竞争（data race） | 两个线程并发访问同一内存位置，至少一个是写，且没有同步（C++11 起：对非原子变量，这是未定义行为） |
| 竞争条件（race condition） | 结果依赖于调度交织的更一般的逻辑错误；可以没有数据竞争（例如全程加锁但检查与使用分在两次加锁里） |
| 临界区 | 同一时刻只允许一个线程进入的代码段 |
| happens-before | 一种偏序：若 A happens-before B，则 A 的效果对 B 可见 |
| synchronizes-with | release 写与读到该值的 acquire 读之间建立的同步关系 |
| CAS | 比较并交换（compare-and-swap）：原子地"若当前值等于期望值则写入新值" |
| ABA 问题 | 值从 A 变成 B 又变回 A，CAS 误以为"没变过" |
| 无锁 / 无等待 | lock-free：系统整体总有线程能前进；wait-free：每个线程都在有限步内完成 |
| 内存序 | 约束某次原子操作周围的读写如何被其他线程观察到的顺序 |
| 虚假唤醒 | 条件变量在条件未成立时被唤醒 |
| 缓存行 | 64 B 左右的缓存一致性单位，伪共享的根源 |

## 3. 数据竞争与 `counter++`

### 3.1 一句语句，三步机器操作

`counter++` 在机器层是：

1. LOAD：把 `counter` 读入寄存器；
2. ADD：寄存器加 1；
3. STORE：写回 `counter`。

**手算丢更新**：初始 `counter=0`，线程 A、B 各执行一次 `counter++`。一种合法交织：

| 步 | 线程 A | 线程 B | `counter`（内存） |
|---|---|---|---|
| 1 | LOAD → rA=0 | | 0 |
| 2 | | LOAD → rB=0 | 0 |
| 3 | ADD → rA=1 | | 0 |
| 4 | | ADD → rB=1 | 0 |
| 5 | STORE ← 1 | | 1 |
| 6 | | STORE ← 1 | 1 |

两次自增只增加了 1。$N$ 个线程各自增 $K$ 次，丢更新使最终值落在 $[K, NK]$ 之间的某处（每个线程至少自己那一次不会被"覆盖"；严格下界取决于细节，此处只强调"小于预期"）。

### 3.2 实验：真的会丢

下面程序（C++17，MinGW GCC 8.1，`-O1`，4 个线程各自增 $10^6$ 次，预期 4000000）：

```cpp
#include <thread>
#include <atomic>
#include <mutex>
#include <vector>
#include <cstdio>
int plain = 0; std::atomic<int> at{0}; int mtxc = 0; std::mutex m;
int main() {
  const int K = 1000000; std::vector<std::thread> v;
  for (int t = 0; t < 4; t++) v.emplace_back([&]{ for (int i = 0; i < K; i++) plain++; });
  for (auto& x : v) x.join(); v.clear();
  for (int t = 0; t < 4; t++) v.emplace_back([&]{ for (int i = 0; i < K; i++) at.fetch_add(1, std::memory_order_relaxed); });
  for (auto& x : v) x.join(); v.clear();
  for (int t = 0; t < 4; t++) v.emplace_back([&]{ for (int i = 0; i < K; i++) { std::lock_guard<std::mutex> g(m); mtxc++; } });
  for (auto& x : v) x.join();
  std::printf("plain %d atomic %d mutex %d\n", plain, at.load(), mtxc);
}
```

本机两次运行的结果：普通变量分别为 **1000000** 和 **2000000**（预期 4000000，丢失了大半，且两次不同）；原子变量与加锁版本均为 **4000000**。耗时（本机，4 线程 × $10^6$ 次）：原子约 27–34 ms，互斥锁约 78–90 ms。结论：

- 数据竞争的结果**不可预测**，且依赖编译选项与机器；这里普通版的结果甚至是整数倍的 $10^6$，很可能是因为编译器把循环优化成了"在寄存器里累加，最后一次写回"，于是只有最后写回的那几个线程的结果留了下来（未反汇编核对）——这恰好说明**数据竞争是未定义行为，编译器可以做任何事**；
- 原子版本和锁版本都正确，原子版本更快（原子读-改-写指令比"加锁-操作-解锁"便宜）。耗时数值是单机一次观察，只说明量级。

### 3.3 为什么 `volatile` 不能修

`volatile` 告诉编译器"每次都真的去内存读写、不要缓存到寄存器"，常用于内存映射的硬件寄存器。它**不提供原子性**（`counter++` 依然三步），**不提供线程间的内存序**，也不阻止 CPU 重排。在 C++ 里线程同步应使用 `std::atomic` 与锁；`volatile` 的合法用途是 MMIO 寄存器、信号处理中的 `sig_atomic_t`（嵌入式里中断与主循环共享的标志位常用 `volatile` 加单字节/单字原子读写，仍要小心，见第 9 节）。

## 4. 互斥锁与条件变量

### 4.1 互斥锁的保证

加锁与解锁之间是临界区。互斥锁**同时**提供：互斥（原子性）、可见性（解锁的 release 与随后加锁的 acquire 建立 happens-before，所以前一个持有者在临界区内的所有写入对下一个持有者可见）、有序性（临界区内的操作不会被移到锁边界之外）。

RAII 用法：`std::lock_guard` / `std::scoped_lock` / `std::unique_lock`，离开作用域自动解锁，**异常安全**，不会忘记解锁。

锁的粒度：粗粒度（一把大锁）简单但串行化严重；细粒度（每个对象一把锁）并发好但容易死锁。折中：保护**不变量**，而不是保护"变量"。如果两个变量之间有关系（如链表节点与计数），它们应由同一把锁保护。

### 4.2 条件变量的正确用法

需求：消费者等"队列非空"。

```cpp
std::mutex m; std::condition_variable cv; std::queue<int> q;

// 生产者
{ std::lock_guard<std::mutex> g(m); q.push(x); }   // 先改状态（持锁）
cv.notify_one();                                   // 再通知

// 消费者
std::unique_lock<std::mutex> lk(m);
cv.wait(lk, []{ return !q.empty(); });             // 谓词版本 = while (!pred) wait
int v = q.front(); q.pop();
```

要点：

1. `wait` 内部原子地"释放锁并睡眠"，唤醒后重新加锁再返回，所以谓词检查是在持锁下做的；
2. **用谓词（循环）而不是 `if`**：虚假唤醒、多个消费者被同时唤醒但只有一个能拿到数据；
3. 共享状态必须在锁内修改，哪怕是为了通知。否则可能出现"消费者检查谓词为假、准备睡眠之前，生产者改状态并通知，通知丢失，消费者永久睡眠"（**丢失唤醒**）；
4. `notify` 可以在锁外调用（可减少唤醒后立即阻塞），但状态修改必须在锁内。

### 4.3 死锁与锁序

见 [操作系统 7.3](./02_操作系统_进程线程_内存_调度_同步.md)。补充：**回调中调用外部代码**（用户回调、日志函数）时持锁，是隐蔽的死锁来源——回调里又要拿同一把锁。经验：持锁时不调用未知代码。

## 5. 原子操作与 CAS

### 5.1 `std::atomic` 提供什么

对 `std::atomic<T>` 的读、写、读-改-写（`fetch_add`、`exchange`、`compare_exchange_*`）是**不可分割**的，不构成数据竞争。是否真正"无锁"取决于类型大小和平台：`is_lock_free()` 可查询；在 32 位 Cortex-M 上，32 位及以下的原子读写通常是单条指令，64 位原子往往需要锁或不可用（编译器和库实现相关，未核对）。

### 5.2 CAS 与重试循环

```cpp
// 教学示例：用 CAS 实现"取最大值"
void update_max(std::atomic<int>& maxv, int v) {
  int cur = maxv.load(std::memory_order_relaxed);
  while (cur < v && !maxv.compare_exchange_weak(cur, v)) {
    // 失败时 cur 被更新为最新值，循环重新比较
  }
}
```

`compare_exchange_weak` 可能"虚假失败"，必须放在循环里，但在循环里比 `strong` 版本更快。CAS 循环是无锁算法的基本形状：读旧值→算新值→尝试提交→失败则重来。**无锁不等于更快**：竞争激烈时 CAS 反复失败，所有核都在空转。

### 5.3 ABA 问题

无锁栈：`head` 指向栈顶节点。线程 1 想弹出：读到 `head=A`，`A->next=B`，准备 CAS(`head`: A→B)。此时线程 2 把 A、B 都弹出，又重新压入 A（此时 `A->next` 已是 C）。线程 1 的 CAS 发现 `head` 仍是 A，成功——把 `head` 设成了已经被释放的 B，破坏了栈。

对策：带**版本号**的指针（把计数器与指针打包一起 CAS，双倍宽度 CAS）、危险指针（hazard pointer）、基于纪元的回收（RCU 思想）。本章只要求能讲清楚现象与思路；具体回收算法的实现细节超出范围。

## 6. 内存序：为什么需要内存模型

### 6.1 重排的三个来源

1. **编译器**：为优化重排或消除内存访问（例 2 的 `ready` 读取被提出循环）；
2. **CPU 乱序**与**写缓冲（store buffer）**：写入先进私有写缓冲，不立即对其他核可见；之后的读可以越过写缓冲里未提交的写；
3. **缓存层次**：不同核看到不同的更新到达顺序。

C++11 引入的内存模型把这些统一抽象：只要程序**没有数据竞争**，且用原子变量/锁建立了正确的同步，它的行为就等价于某种"顺序一致"的交织，编译器和 CPU 在此之下可以随意优化。

### 6.2 `happens-before` 与 acquire/release

- 同一线程内，按程序顺序，前面的操作 sequenced-before 后面的；
- 线程 A 对原子变量 `x` 做 **release 写**，线程 B 对 `x` 做 **acquire 读**且读到了该值，则 A 中 release 写**之前**的所有写，对 B 中 acquire 读**之后**的读可见（synchronizes-with）。

消息传递模式的正确写法：

```cpp
int data = 0;
std::atomic<bool> ready{false};

// 线程 A
data = 42;                                      // 普通写
ready.store(true, std::memory_order_release);   // 发布

// 线程 B
while (!ready.load(std::memory_order_acquire)) {}
assert(data == 42);                             // 一定成立
```

release 保证"之前的写不会被重排到它之后"，acquire 保证"之后的读不会被重排到它之前"，二者配对才起效，缺任何一边都不行。

### 6.3 五种内存序

| 内存序 | 保证 | 典型用途 |
|---|---|---|
| `relaxed` | 只保证该操作自身原子，不对周围操作排序 | 计数器、统计量 |
| `acquire` | 读之后的访问不会提前到它之前 | 读取"数据已就绪"标志 |
| `release` | 写之前的访问不会推后到它之后 | 发布"数据已就绪"标志 |
| `acq_rel` | 读-改-写操作同时具备二者 | 自旋锁的 exchange |
| `seq_cst` | 在 acq_rel 基础上，所有 `seq_cst` 操作存在一个全局唯一的总顺序 | 默认；需要全局一致观感时 |

**默认是 `seq_cst`**。不确定就别用更弱的。弱内存序的收益在 x86 上很小（x86 的 TSO 模型本来就较强，acquire/release 读写不需要额外屏障指令，只有 `seq_cst` 写需要），在 ARM 上更明显。

### 6.4 Store Buffer 与 `r1 = r2 = 0`

例 3 的经典测试（Store Buffering）：

```text
初值 a = b = 0
线程 1:  a = 1;  r1 = b;
线程 2:  b = 1;  r2 = a;
问：能否 r1 == 0 && r2 == 0 ?
```

在**顺序一致**下不可能：假设 `r1=0`，则线程 1 的读 `b` 在线程 2 的写 `b` 之前；程序序下线程 2 的读 `a` 在其写 `b` 之后，所以在线程 1 的写 `a` 之后，应读到 1，矛盾。

但是真实硬件有**写缓冲**：线程 1 的 `a=1` 先放入自己的写缓冲，还没对线程 2 可见，就去读 `b`（得 0）；线程 2 同理。于是两者都读到 0。这在 x86 上也会发生（x86 唯一允许的重排就是"读越过较早的写到不同地址"）。

**实验**（C++ 实际运行，`-O2`，各 200000 轮，双方用自旋同步每轮同时开跑）：

- `relaxed` 版本：出现 $r_1=r_2=0$ **149** 次；
- `seq_cst` 版本：**0** 次。

数值是本机单次观察（概率与机器、负载有关），重点是：宽松序下确实观察到了"不可能"的结果，而 `seq_cst`（在 x86 上编译器会为 store 插入 `mfence` 或使用 `xchg`）消除了它。

### 6.5 单例的双重检查锁（DCLP）

```cpp
// 错误的写法（旧）：指针不是原子的，可能看到"指针已赋值但对象未构造完"
if (!inst) { std::lock_guard<std::mutex> g(m); if (!inst) inst = new T; }
```

正确做法：C++11 的函数内静态变量初始化是线程安全的（`static T inst;` 在函数里），或使用 `std::call_once`，或把指针换成 `std::atomic<T*>` 并用 acquire/release。Python 的模块级对象在导入时初始化，由导入锁保护。

## 7. 无锁队列：SPSC 环形缓冲

### 7.1 设计

单生产者单消费者（SPSC）环形队列是机器人软件中最常用的"线程间/中断到任务"通信结构：只有一个线程写 `tail`，只有一个线程写 `head`，因此**不需要 CAS**，只需要 acquire/release 保证数据先于索引可见。

```cpp
// 教学示例，非项目源码：SPSC 无锁环形队列，N 必须是 2 的幂
#include <atomic>
#include <cstddef>
template <typename T, size_t N>
class SpscQueue {
  T buf_[N];
  std::atomic<size_t> head_{0};   // 仅消费者写
  std::atomic<size_t> tail_{0};   // 仅生产者写
public:
  bool push(const T& v) {                                        // 生产者调用
    size_t t = tail_.load(std::memory_order_relaxed);
    if (t - head_.load(std::memory_order_acquire) == N) return false;   // 满
    buf_[t & (N - 1)] = v;                                       // 先写数据
    tail_.store(t + 1, std::memory_order_release);               // 再发布索引
    return true;
  }
  bool pop(T& out) {                                             // 消费者调用
    size_t h = head_.load(std::memory_order_relaxed);
    if (h == tail_.load(std::memory_order_acquire)) return false;       // 空
    out = buf_[h & (N - 1)];                                     // 先读数据
    head_.store(h + 1, std::memory_order_release);               // 再释放槽位
    return true;
  }
};
```

### 7.2 正确性论证

- **索引不取模，单调递增**，下标用 `& (N-1)`：避免"满/空"歧义，满是 `tail - head == N`，空是 `tail == head`；无符号整数回绕时差值仍正确。
- 生产者：写数据 → release 存 `tail`；消费者：acquire 读 `tail` → 读数据。release/acquire 配对使消费者看到新 `tail` 时必然能看到对应的数据。
- 消费者读完数据 → release 存 `head`；生产者 acquire 读 `head` 后才覆盖该槽，保证消费者已读完。
- 自己的索引用 `relaxed` 读即可，因为只有自己写。

### 7.3 实验验证

两个线程，生产者按序推入 $0,1,\dots,M-1$（$M=5\times10^6$），消费者按序弹出并校验顺序与总和（`-O2`）：结果顺序全部正确，总和 $12499997500000=M(M-1)/2$，与预期相等。说明在 SPSC 前提下该实现无丢失、无重复、无乱序。

> **注意**：如果有两个生产者或两个消费者，该结构**不再正确**（两个写 `tail` 的线程会冲突），需要 MPSC/MPMC 队列，通常用 CAS 或锁。

### 7.4 伪共享

`head_` 与 `tail_` 若落在同一缓存行，一个线程写 `tail_` 会使另一个线程的 `head_` 缓存失效。实验（本机，两线程各对一个原子计数器做 $2\times10^7$ 次 `fetch_add`）：计数器相邻（同一缓存行）约 303–340 ms；各自对齐到 64 B（`alignas(64)`）约 71 ms，快 4–5 倍。工程做法：把 `head_`、`tail_` 用 `alignas(64)` 隔开（数值为本机观察，缓存行大小以目标平台为准）。

## 8. 完整手算与实验（C++ 实际运行）

本章的结论都有实验支撑，汇总：

| 实验 | 设置 | 结果（本机观察） |
|---|---|---|
| 数据竞争 | 4 线程 × $10^6$ 次 `++` | 普通变量 1000000 / 2000000；原子、互斥均 4000000 |
| 原子 vs 互斥 | 同上 | 原子约 27–34 ms，互斥约 78–90 ms |
| SB 测试 relaxed | 200000 轮 | $r_1=r_2=0$ 出现 149 次 |
| SB 测试 seq_cst | 200000 轮 | 0 次 |
| 伪共享 | 2 线程 × $2\times10^7$ 次 | 同行约 303–340 ms，分行约 71 ms |
| SPSC 队列 | $M=5\times10^6$ | 全部有序，和 $=12499997500000$ |

另外手算一道：队列容量 $N=4$，依次 push 5 次不 pop，第 5 次返回什么？`tail=4,head=0`，`tail-head=4=N`，返回 false；pop 一次后 `head=1`，再 push：`tail-head=3<4`，写入槽 `4&3=0`（覆盖已被读取的第 0 槽），`tail=5`。

## 9. 在七个项目里怎么用

| 项目 | 对应概念 | 性质 |
|---|---|---|
| P3/P7（FreeRTOS） | 中断与任务通信：ISR（如 CAN/UART 接收中断）把数据放入队列（`xQueueSendFromISR`）或通知任务，任务在临界区外处理；任务间共享状态用互斥量，注意优先级反转（互斥量带优先级继承）。这是"SPSC 队列 + 同步"在 MCU 上的现成版本。见 [FreeRTOS 任务设计与时序](../../01_项目课程/P3_RoboMaster英雄机器人嵌入式控制/03_FreeRTOS任务设计与时序.md) | 项目内 |
| P3/P7 | ISR 与主循环共享的标志位：单字节/32 位对齐读写在 Cortex-M 上本身是单指令，常用 `volatile`；多字段数据（如一个带时间戳的 IMU 样本）不是原子的，需要临界区（关中断或队列拷贝）才能保证一致，否则出现"时间戳是新的、数据是旧的"的撕裂读 | 项目内（概念，具体写法依项目代码） |
| P1/P2/P5（ROS2） | 执行器与回调组：默认的互斥回调组保证同组回调不并发；可重入组允许并发，此时回调内共享数据需要自己加锁。订阅回调更新、定时器回调读取同一份状态是最常见的数据竞争。见 [ROS2 Humble 核心概念](../12_机器人软件/04_ROS2_Humble核心概念与ROS1对比.md) | 项目内（概念） |
| P4 | Python asyncio 是单线程协作式并发，在 `await` 点之间天然不存在数据竞争（同一线程内），但一旦用到线程池（`run_in_executor`）或多线程，共享字典要加锁；CPython 的 GIL 保证字节码级的互斥，但不保证复合操作（`d[k] += 1`）原子。见 [服务端 DataStore 与 asyncio](../../01_项目课程/P4_OpenHarmony智能园艺系统/09_服务端_DataStore_WebSocket_asyncio.md) | 项目内 |
| P6 | 多源状态汇聚（感知、反馈）时的时间戳与有效性检查，本质是对"并发写入的数据如何得到一致快照"的工程处理；发布订阅里的最新值缓存可以用 SPSC/seqlock 一类结构（延伸知识，非 CV 逐项内容） | 延伸 |

> **面试要点**：谈到并发时，最稳妥的项目锚点是"中断到任务的数据传递"与"ROS2 回调之间的共享状态"。能说出"我们用队列把数据从中断拷贝到任务，避免在中断里做耗时处理，也避免任务读到半更新的结构体"，既真实又展示了原理。

## 10. 常见错误

1. **用 `volatile` 做线程同步**：没有原子性与内存序。
2. **条件变量用 `if`**、改共享状态不加锁、先通知后改状态。
3. **只读不加锁**：读写者之间同样构成数据竞争；"只是读一下"也需要同步。
4. **锁住了错误的东西**：两个相关变量用两把锁；检查与使用分两次加锁（TOCTOU）。
5. **持锁调用回调/日志/阻塞函数**。
6. **滥用 `relaxed`**：没有彻底理解就用弱内存序，bug 在 x86 上可能永远复现不了，换到 ARM 才暴露。
7. **以为 `std::atomic` 的复合表达式是整体原子**：`a = a + 1` 是 load 与 store 两次原子操作，不是原子自增；要用 `fetch_add`。
8. **无锁迷信**：无锁不一定更快，调试和证明难度大；先用锁，测量后再优化。
9. **忽略 ABA 与内存回收**：自己写无锁栈/队列的节点回收。
10. **伪共享**：多线程各自更新相邻的计数器/统计量。
11. **中断里用会阻塞的 API**，或在中断与任务共享的结构上不做保护。
12. **多生产者误用 SPSC 队列**。

## 11. 英文面试问答

### Q1. What is a data race, and how do you avoid it?

"A data race happens when two threads access the same memory location at the same time, at least one access is a write, and there is no synchronization between them. In C and C++ it is undefined behavior, so the compiler is allowed to assume it never happens. I avoid it by protecting shared data with a mutex, or by using atomic variables, or by not sharing at all, for example passing messages through a queue. A classic example is two threads doing counter plus plus, which is really a load, an add and a store, so updates get lost."

中文要点：并发访问同一位置、至少一个写、无同步；C/C++ 中是未定义行为；用互斥锁、原子变量或消息传递避免；`counter++` 是 load/add/store 三步所以会丢更新。

**追问**：

- *"Did you actually see it happen?"* — "Yes. In a small test with four threads incrementing a plain integer a million times each, I got results like one million or two million instead of four million, and the numbers changed between runs, while atomic and mutex versions gave exactly four million."（真实实验，可直接说。）
- *"Is volatile enough?"* — "No. It prevents the compiler from caching a value in a register, but it provides neither atomicity nor ordering between threads."

### Q2. Explain acquire and release memory ordering.

"They let one thread publish data to another. The writer stores data normally and then does a release store to a flag. The reader does an acquire load on that flag. If the reader sees the flag set, it is guaranteed to also see all writes the writer did before the release. Release prevents earlier writes from moving after the store, and acquire prevents later reads from moving before the load. Sequential consistency is stronger and also gives one global order of all such operations, and it is the default, so I only weaken it when I understand why."

中文要点：release 写发布、acquire 读订阅，看到标志就能看到之前的写；seq_cst 更强、是默认；不确定就不要用弱序。

**追问**：*"Can you give an example where relaxed gives a surprising result?"* — "Store buffering: two threads each write their own variable and then read the other's. With relaxed or even on x86 hardware, both can read zero. In my test with relaxed ordering I saw that outcome 149 times in 200,000 rounds, and never with sequential consistency."

### Q3. How does a condition variable work, and why use a while loop?

"A condition variable lets a thread sleep until some condition on shared state becomes true. The wait function atomically releases the mutex and sleeps; when woken, it re-acquires the mutex. I check the predicate in a loop because of spurious wakeups, and because another consumer might have taken the item before I got the lock. The producer must change the shared state while holding the mutex, otherwise a notification can be lost."

中文要点：等待条件，wait 原子地释放锁并睡眠，醒后重新加锁；用循环检查谓词（虚假唤醒、被他人抢先）；修改状态须在锁内，否则丢失唤醒。

### Q4. How would you pass data from an interrupt handler to a task safely?

"I keep the interrupt handler short. It copies the data into a lock-free single-producer single-consumer buffer, or on FreeRTOS uses a queue from ISR function, and then wakes a task. The task processes the data with normal code. This avoids long work in the interrupt, avoids blocking calls there, and avoids the task seeing a half-updated struct, because the data is copied as a unit."

中文要点：中断里只做短拷贝（SPSC 缓冲或 FromISR 队列）并唤醒任务；耗时处理在任务中；整体拷贝避免读到半更新结构体。须和 P3/P7 实际通信方式（队列/通知）保持一致，细节见项目章节。

## 12. 要点速记、自测题、相关链接

### 要点速记

1. 并发三问题：原子性、可见性、有序性；锁三者兼顾，原子操作给原子性并按内存序给可见/有序。
2. 数据竞争 = 并发访问 + 至少一写 + 无同步，C/C++ 里是未定义行为；实验里 $4\times10^6$ 的预期结果可能变成 $10^6$。
3. `volatile` 不是同步工具。
4. 条件变量：`while` 谓词、状态修改在锁内、防虚假唤醒与丢失唤醒。
5. CAS 循环是无锁基本形态；无锁不等于更快；注意 ABA。
6. release 写 + acquire 读配对建立 happens-before；默认 `seq_cst`；`relaxed` 只保原子。
7. Store Buffer 导致 SB 测试 $r_1=r_2=0$，`seq_cst` 禁止；本机 relaxed 观察到 149/200000。
8. SPSC 环形队列：单调索引 + `&(N-1)`，数据写完再 release 发布索引，无需 CAS。
9. 伪共享用 `alignas(64)` 隔开，本机观察到 4–5 倍差异。
10. MCU 上用"ISR 拷贝入队 + 任务处理"；ROS2 回调共享状态要看回调组。

### 自测题

1. 写出两个线程各 `counter++` 一次得到结果 1 的交织。
   *要点*：两线程都先 LOAD 到 0，再各自 ADD、STORE 1（见 3.1 表）。
2. 为什么 `while(!ready){}` 在没有 `atomic` 时可能死循环？
   *要点*：编译器可把对非原子 `ready` 的读提到循环外；数据竞争是未定义行为。
3. 在 SPSC 队列里，为什么消费者读 `head_` 可以用 `relaxed` 而读 `tail_` 必须 `acquire`？
   *要点*：`head_` 只有消费者自己写；`tail_` 是生产者发布数据的信号，需要 acquire 才能看到对应的数据。
4. 说明 ABA 问题及一种对策。
   *要点*：值 A→B→A 使 CAS 误判未变；用带版本号的指针或 hazard pointer。
5. `std::atomic<int> a; a = a + 1;` 为什么不是原子自增？
   *要点*：`a + 1` 先 load（原子），再 store（原子），两步之间可被其他线程插入；应使用 `a.fetch_add(1)`。
