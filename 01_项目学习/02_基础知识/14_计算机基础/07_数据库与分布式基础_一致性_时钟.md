## 1. 要解决什么问题

数据库与分布式系统回答同一组问题的不同版本：

1. **数据不能丢**：断电、崩溃之后已确认的写入仍在——**持久性**。
2. **多个人同时改不能乱**：两个客户端同时扣款，余额不能算错——**并发控制**。
3. **一次操作要么全做要么全不做**：转账不能只扣不加——**原子性**。
4. **查询要快**：在 $10^8$ 行里找一行，不能全表扫描——**索引**。
5. **一台机器放不下或不够可靠**：数据复制到多台，但复制品之间怎么保持一致？网络断了怎么办？——**一致性与可用性的取舍**。
6. **多台机器的时钟不一样**：哪个事件先发生？——**逻辑时钟与时间同步**。

机器人系统中的对应：一台机器人内部有多个进程共享"最新状态"（P4 的 DataStore）；多台机器人之间要同步状态、分发任务（P6 的 M-DDS）；传感器时间戳要对齐才能融合（P5/P6）。这些都是缩小版的分布式系统问题。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 事务（transaction） | 一组被视为整体的读写操作，`BEGIN ... COMMIT/ROLLBACK` |
| ACID | 原子性 Atomicity、一致性 Consistency、隔离性 Isolation、持久性 Durability |
| WAL | 预写日志（Write-Ahead Log）：先写日志再改数据页，崩溃后重放或回滚 |
| MVCC | 多版本并发控制：每次写产生新版本，读者读旧版本而不阻塞 |
| 主键 / 索引 | 唯一标识行的列 / 加速查找的辅助数据结构 |
| 扇出（fanout） | B+ 树每个内部节点的子节点数 |
| 分区（partition） | 网络分裂为互不连通的几部分（CAP 里的 P） |
| 线性一致性 | 操作看起来按某个全局顺序瞬间完成，且该顺序尊重真实时间先后 |
| 最终一致性 | 若不再有更新，所有副本最终收敛到同一值 |
| 法定人数 / 多数派（quorum） | 参与决策的副本数量下限，如 $\lfloor N/2\rfloor+1$ |
| 共识（consensus） | 多个节点就某个值达成一致，如 Raft、Paxos |
| NTP / PTP | 网络时间协议 / 精确时间协议 |
| $\theta$ | 时钟偏移（offset）：对方时钟减本地时钟 |
| $\delta$ | 往返网络延迟 |
| Lamport 时钟 | 单个计数器，保证因果前者的时间戳更小 |
| 向量时钟 | 每个进程一个分量的计数器向量，可以判断并发 |
| $\rightarrow$ | 先发生关系（happened-before） |

## 3. 事务与 ACID

### 3.1 银行转账的例子

从账户 1 转 70 到账户 2。有两条 SQL：

```sql
UPDATE acct SET bal = bal - 70 WHERE id = 1;
UPDATE acct SET bal = bal + 70 WHERE id = 2;
```

如果第一条成功、第二条之前系统崩溃，钱凭空消失。**事务**把两条语句捆成一个整体。

### 3.2 ACID

- **原子性**：事务中的操作要么全部生效，要么全部不生效。靠**回滚日志（undo log）**实现：出错时撤销已做的修改。
- **一致性**：事务把数据库从一个满足约束的状态带到另一个满足约束的状态（主键唯一、外键、`CHECK` 约束、业务不变量如"总额不变"）。注意这里的"一致"是**应用语义**上的，由应用与约束共同保证，与分布式里的"一致性"不是同一个词。
- **隔离性**：并发事务互不干扰，效果等价于某个串行顺序（取决于隔离级别，见第 4 节）。
- **持久性**：提交后即使崩溃也不丢。靠**预写日志（WAL）**实现：提交前，先把日志顺序写入磁盘并刷盘（`fsync`）；数据页可以稍后异步写回，崩溃重启时重放日志（redo）恢复。顺序写日志比随机写数据页快得多，这也是 WAL 的性能来源。

### 3.3 实机验证：约束触发回滚

下面在 SQLite 3.45.3（Python 内置 `sqlite3`）里实际运行：表 `acct(id, bal CHECK(bal>=0))`，初值账户 1 为 100、账户 2 为 50。执行一个事务：先扣 70，再扣 70（余额变 −40，违反约束），再给账户 2 加 140。

```python
import sqlite3
c = sqlite3.connect(":memory:")
c.execute("create table acct(id integer primary key, bal integer check(bal>=0))")
c.executemany("insert into acct values(?,?)", [(1, 100), (2, 50)]); c.commit()
try:
    with c:      # with 连接对象 = 一个事务：成功提交，异常则回滚
        c.execute("update acct set bal=bal-70 where id=1")
        c.execute("update acct set bal=bal-70 where id=1")   # 违反 CHECK
        c.execute("update acct set bal=bal+140 where id=2")
except Exception as e:
    print("rollback:", type(e).__name__, e)
print(c.execute("select * from acct").fetchall())
```

实际输出：`rollback: IntegrityError CHECK constraint failed: bal>=0`，随后 `[(1, 100), (2, 50)]`——**第一条已执行的扣款也被撤销**，表恢复到初始状态，这就是原子性。再执行正确的转账事务（扣 70 / 加 70）后得到 `[(1, 30), (2, 120)]`，总额 150 不变。

## 4. 并发控制与隔离级别

### 4.1 四种并发异常

设两个并发事务 T1、T2：

| 异常 | 现象 | 例子 |
|---|---|---|
| 脏读（dirty read） | 读到别的事务**未提交**的修改，那个事务之后回滚 | T1 把余额改成 0 未提交，T2 读到 0，T1 回滚 |
| 不可重复读（non-repeatable read） | 同一事务内两次读**同一行**得到不同值 | T1 读余额 100，T2 改成 50 并提交，T1 再读得 50 |
| 幻读（phantom） | 同一事务内两次**范围查询**，行数不同 | T1 查 `bal>0` 有 2 行，T2 插入一行并提交，T1 再查得 3 行 |
| 丢失更新（lost update） | 两个事务读-改-写同一行，后一个覆盖前一个 | 与 `counter++` 的丢更新同构（见 [并发与内存模型](./05_并发与内存模型_锁_原子_无锁.md)） |

### 4.2 SQL 标准的四个隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（READ UNCOMMITTED） | 可能 | 可能 | 可能 |
| 读已提交（READ COMMITTED） | 不会 | 可能 | 可能 |
| 可重复读（REPEATABLE READ） | 不会 | 不会 | 标准上可能（实现可能更强，如 MySQL InnoDB 靠间隙锁/MVCC 大幅减少幻读） |
| 可串行化（SERIALIZABLE） | 不会 | 不会 | 不会 |

隔离越强，并发度越低、冲突越多。**各数据库的默认级别和实现细节不同**（例如 PostgreSQL 默认读已提交，MySQL InnoDB 默认可重复读，SQLite 对写事务本质上是串行的），具体行为以使用的数据库版本文档为准，此处未逐一核对。

### 4.3 两种实现思路

1. **悲观：加锁**。读加共享锁（S），写加排他锁（X）；**两阶段锁（2PL）**：事务先只加锁（增长阶段），提交时才释放（收缩阶段），能保证可串行化，但会产生死锁（数据库检测死锁并回滚其中一个事务）和等待。
2. **乐观：MVCC**。每次写产生新版本并带版本号/时间戳；读事务按开始时的快照读取符合可见性规则的旧版本，**读不阻塞写，写不阻塞读**。写-写冲突仍需解决（先提交者胜或加锁）。快照隔离（Snapshot Isolation）能避免上述前三种异常，但有"写偏斜（write skew）"等更微妙的异常，不等价于可串行化。

另有**乐观并发控制（OCC）**：读写都不加锁，提交时验证期间有无冲突，冲突则重试——与无锁数据结构的 CAS 重试思路相同，适合冲突少的场景。机器人状态更新里常用"版本号 + 比较后写入"的方式实现，同样的想法。

## 5. 索引与 B+ 树

### 5.1 为什么需要索引

没有索引，`SELECT ... WHERE dev='d42'` 只能全表扫描，复杂度 $O(n)$。索引是额外维护的、按键有序的数据结构，使查找变成 $O(\log n)$ 级。代价：占用空间；**每次写入都要同步维护索引**，写变慢。

**实机验证**（SQLite 3.45.3，表 `log(id, dev, ts, v)` 共 200000 行，`dev` 取 1000 个值之一）：

- 无索引：`EXPLAIN QUERY PLAN` 显示 `SCAN log`（全表扫描），查询 `where dev='d42'` 的平均耗时约 **8.4 ms**；
- 建立 `CREATE INDEX idx_dev ON log(dev)` 后，计划变为 `SEARCH log USING COVERING INDEX idx_dev (dev=?)`，平均耗时约 **0.008 ms**，约 1000 倍。

两个结果均为 204 行匹配。耗时是本机内存数据库、20 次平均的观测值，量级可信，具体数字随机器变化。

### 5.2 B+ 树

数据库索引通常用 **B+ 树**，一种多路平衡搜索树：

- 每个节点对应一个磁盘页（常见 4 KB–16 KB），内部节点只存键和子指针，**叶子节点**存键（和数据或数据位置）并用链表串联；
- 扇出很大（几百），所以树很矮；
- 所有叶子在同一深度，查找代价稳定；叶子链表使**范围查询**（`BETWEEN`、排序）高效：找到起点后沿链表顺序扫描。

**手算高度**：设页 4096 B，键 8 B + 子指针 8 B = 16 B/项，每页约容纳 $4096/16=256$ 项（忽略页头开销，示例，非实际数据库）。取扇出 $f=100$（保守）：

- $10^6$ 行：高度 $\lceil\log_{100}10^6\rceil=3$；
- $10^9$ 行：$\lceil\log_{100}10^9\rceil=5$（扇出 500 时为 4）（Python 复核）。

也就是说十亿行的表，一次索引查找只需约 4–5 次页访问；而且根节点和上层几乎总在缓存里，真正的磁盘读取往往只有 1–2 次。对比二叉树 $\log_2 10^9\approx30$ 层，扇出大使树矮，页访问少——这正是"用磁盘页作节点大小"的设计原因（与 [体系结构一章](./04_计算机体系结构_缓存_流水线_SIMD_GPU.md) 中"以缓存行为单位"的思想一致）。

### 5.3 索引设计要点

1. **联合索引的最左前缀原则**：索引 `(dev, ts)` 先按 `dev` 排序，`dev` 相同再按 `ts` 排序。因此它能加速 `where dev=? `、`where dev=? and ts between ...`，但**不能**加速只按 `ts` 查询。实机验证：`where dev='d1' and ts between 10 and 5000` 的计划是 `SEARCH ... USING INDEX idx_dev_ts (dev=? AND ts>? AND ts<?)`；`where ts=5` 则是 `SCAN log`（全表扫描）。
2. **覆盖索引**：查询需要的列全部在索引里，不必回表。上面 `count(*)` 用了 `COVERING INDEX`。
3. **选择性**：区分度低的列（如性别）建索引收益小。
4. **索引失效**：对索引列做函数运算、隐式类型转换、以 `%` 开头的模糊匹配，常会使优化器放弃索引。
5. 用 `EXPLAIN` 看执行计划，而不是凭感觉。
6. **写多读少**的场景（如高频遥测日志）少建索引，或考虑追加写的存储（LSM 树：先写内存表再顺序落盘合并，写吞吐高，读需要多层查找）。

### 5.4 关系型 vs 键值 / 文档 / 时序

关系型适合结构化、需要事务与复杂查询的数据；键值型（如 Redis）适合缓存与简单查找；文档型适合灵活结构；时序数据库适合带时间戳的遥测，按时间分区与降采样。机器人系统里遥测日志常落成文件（如 ROS bag）而不是数据库，原因是追加写简单、回放方便（见 [ROS2 测试与 CI：rosbag 回放](../12_机器人软件/09_ROS2测试与CI_launch_testing_gtest_rosbag回放.md)）。

## 6. 分布式系统：CAP 与一致性模型

### 6.1 为什么难

单机里调用函数要么返回要么崩溃；分布式里，请求发出后没有回应，你不知道是**请求没到、对方没处理、处理了但回应丢了、还是对方慢**。这种"不确定性"加上**没有共享内存**、**没有全局时钟**、**部分失败**（一部分节点挂了，别的还活着），使问题的性质变化。

### 6.2 CAP 定理

在一个分布式数据存储里，三个性质：

- **C（一致性，这里指线性一致性）**：读总是返回最新的写；
- **A（可用性）**：每个发给未故障节点的请求都得到（非错误的）响应；
- **P（分区容错）**：网络分区（节点间消息丢失）时系统仍继续工作。

CAP 定理（Gilbert 与 Lynch 对 Brewer 猜想的形式化证明，细节未核对原文）说：**当发生网络分区时，只能在 C 和 A 之间二选一**。直观证明：两个副本 $R_1$、$R_2$ 被分区隔开。客户端向 $R_1$ 写入新值 $v$。此时若 $R_2$ 收到读请求：(a) 要保证一致就必须拒绝响应或等待（牺牲 A）；(b) 要保证可用就只能返回旧值（牺牲 C）。

> **注意**：现实中分区无法避免，所以真实的选择是"分区发生时选 CP 还是 AP"；没有分区时可以同时有 C 和 A。更完整的框架是 **PACELC**：如果有分区（P），在 A 与 C 间选；否则（E, Else），在延迟（L）与一致性（C）间选——强一致需要同步副本，增加延迟。

典型取向：协调服务和强一致数据库（如基于 Raft 的 etcd）偏 CP；按"最终一致"设计的副本系统偏 AP。具体产品的默认配置因版本而异，面试时以原理回答为主。

### 6.3 一致性模型（从强到弱）

1. **线性一致性（linearizability）**：每个操作看起来在其开始和结束之间的某一瞬间原子地发生，且所有客户端看到同一个全局顺序，且顺序符合真实时间。最强，代价最高（需要协调）。
2. **顺序一致性**：所有操作存在一个全局顺序，且每个进程内部的顺序保持，但不要求符合真实时间。
3. **因果一致性（causal consistency）**：有因果关系的操作所有节点看到相同顺序，没有因果关系（并发）的操作可以不同。这是**无需全局协调所能达到的最强一致性**之一（常见结论，细节未核对）。
4. **最终一致性（eventual consistency）**：停止更新后所有副本最终收敛。需要冲突解决策略（最后写入者胜 LWW、向量时钟检测冲突、CRDT 无冲突合并）。

还有"读己之写""单调读"等会话保证。一个常见的坑：把多份状态副本做成"最终一致"，却在上面做需要线性一致才能正确的操作（如"检查后再扣减"），产生丢失更新。

## 7. 复制、多数派与共识

### 7.1 复制

- **主从复制**：一个主节点处理写，同步/异步复制到从节点。同步复制不丢数据但写延迟大；异步复制快，主挂了可能丢最近的写。
- **多主 / 无主**：多个节点可写，需要冲突解决。

### 7.2 多数派条件

设数据存 $N$ 个副本，写操作需要 $W$ 个副本确认，读操作需要查询 $R$ 个副本并取最新版本。若

$$R+W>N$$

则任一读集合与任一写集合**至少有一个共同副本**（鸽巢原理），读一定能看到最近一次已提交的写。若同时 $2W>N$，则任意两个写集合也相交，写-写冲突可被发现。

**手算**（Python 复核）：

| $(N,W,R)$ | $R+W>N$ | $2W>N$ | 说明 |
|---|---|---|---|
| (3,2,2) | 是 | 是 | 多数派读写，可容忍 1 个节点故障 |
| (3,1,1) | 否 | 否 | 快，但读可能读到旧值 |
| (5,3,3) | 是 | 是 | 可容忍 2 个故障 |
| (5,2,4) | 是 | 否 | 读都看得到最新，但两个写可以互不相交 |

### 7.3 共识与 Raft 的直觉

共识要解决的是：多个节点就一个值（如"谁是主""日志第 $k$ 条是什么"）达成一致，即使有节点崩溃。Raft 将问题分解为**领导者选举**、**日志复制**、**安全性**：

- 时间划分为**任期（term）**；节点在随机超时后发起选举，**获得多数票**者成为领导者；
- 客户端的写只交给领导者；领导者把日志条目复制到多数派后才算**提交**；
- 因为选举与提交都需要多数派，两个多数派必相交，所以不会出现两个领导者同时提交冲突的日志。
- 容错：$N$ 个节点可容忍 $\lfloor (N-1)/2\rfloor$ 个故障：$N=3$ 容忍 1，$N=5$ 容忍 2，$N=7$ 容忍 3（Python 复核）。

这里只讲直觉，不涉及 Raft 论文中的全部细则（任期规则、日志匹配性质、成员变更等），具体条文未逐条核对。机器人系统一般不自己实现共识，而是依赖成熟组件，或者设计成不需要共识（每个状态有唯一的数据所有者）。

## 8. 时钟与事件顺序

### 8.1 物理时钟的问题

- **漂移**：晶振频率有误差，典型廉价晶振约几十 ppm（百万分之一）。50 ppm 意味着每小时偏差 $50\times10^{-6}\times3600\ \text{s}=0.18\ \text{s}=180\ \text{ms}$（Python 复核；示例数字，实际精度依器件，未核对）。
- **墙上时钟 vs 单调时钟**：墙上时钟（`time.time()`、系统时间）会被 NTP 调整、闰秒、手动改时间而**跳变甚至倒退**；单调时钟（`time.monotonic()`、`CLOCK_MONOTONIC`）只增不减，适合测量时间间隔，但不同机器之间不可比。
- 经验：**测间隔用单调时钟，跨机器对齐用同步后的墙上时钟，因果顺序用逻辑时钟**。

### 8.2 NTP 式偏移与延迟估计

客户端向服务器发请求，记录四个时间戳：

- $t_1$：客户端发送（客户端时钟）；
- $t_2$：服务器接收（服务器时钟）；
- $t_3$：服务器发送回复（服务器时钟）；
- $t_4$：客户端接收（客户端时钟）。

往返网络延迟（扣除服务器处理时间）与时钟偏移的估计：

$$\delta=(t_4-t_1)-(t_3-t_2),\qquad \theta=\frac{(t_2-t_1)+(t_3-t_4)}{2}$$

**推导**：设服务器时钟比客户端快 $\theta$，去程延迟 $d_1$，回程延迟 $d_2$（真实时间）。则 $t_2=t_1+d_1+\theta$，$t_4=t_3-\theta+d_2$。于是 $t_2-t_1=d_1+\theta$，$t_3-t_4=\theta-d_2$，相加除以 2：

$$\frac{(t_2-t_1)+(t_3-t_4)}{2}=\theta+\frac{d_1-d_2}{2}$$

所以估计 $\hat\theta=\theta+\frac{d_1-d_2}{2}$。**当去程与回程延迟对称（$d_1=d_2$）时估计无偏；不对称时误差等于两方向延迟差的一半**，且误差的绝对值不超过 $\delta/2$。

**手算 1（对称）**：$t_1=100.000$，$t_2=100.060$，$t_3=100.062$，$t_4=100.020$（秒，示例，非实测）。$\delta=(0.020)-(0.002)=0.018\ \text{s}$，$\theta=\frac{0.060+0.042}{2}=0.051\ \text{s}$，即服务器时钟约比本地快 51 ms（Python 复核）。

**手算 2（不对称）**：真实偏移 $\theta=50\ \text{ms}$，去程 5 ms，回程 15 ms，服务器处理 1 ms。取 $t_1=0$，则 $t_2=0+5+50=55$ ms，$t_3=56$ ms，客户端真实到达时刻为 $0+5+1+15=21$ ms，故 $t_4=21$ ms。$\delta=21-1=20\ \text{ms}$；$\hat\theta=\frac{(55-0)+(56-21)}{2}=\frac{55+35}{2}=45\ \text{ms}$，误差 $=-5\ \text{ms}=\frac{d_1-d_2}{2}=\frac{5-15}{2}$，与推导一致，且 $|{-5}|\le\delta/2=10$（Python 复核）。

实用启示：偏移估计的精度受路径不对称限制；采样多次取往返延迟最小的样本（其排队影响最小）；无线网络的不对称较大，精度较差。更高精度的同步（亚微秒）需要硬件时间戳的 PTP（IEEE 1588，具体精度依硬件，未核对）。P6 的"标准化时间戳"章节讲了这个公式在机器人状态管理里的使用，见 [机器人状态管理](../../01_项目课程/P6_深开鸿M-Robots平台软件/05_机器人状态管理.md)。

### 8.3 先发生关系与 Lamport 时钟

Lamport 提出：不依赖物理时钟，用**因果关系**定义顺序。事件 $a\rightarrow b$（$a$ 先于 $b$）当且仅当：(1) 同一进程内 $a$ 在 $b$ 之前；或 (2) $a$ 是发送、$b$ 是对应的接收；或 (3) 传递性。没有因果关系的两个事件是**并发**的，记为 $a\parallel b$。

**Lamport 逻辑时钟**：每个进程一个计数器 $L$：

1. 本地事件：$L\leftarrow L+1$；
2. 发送消息：$L\leftarrow L+1$，把 $L$ 附在消息上；
3. 接收消息（带时间戳 $L_m$）：$L\leftarrow\max(L,L_m)+1$。

性质：若 $a\rightarrow b$，则 $L(a)<L(b)$。**逆命题不成立**：$L(a)<L(b)$ 不能推出 $a\rightarrow b$（也可能是并发）。因此 Lamport 时钟可用来给事件定一个与因果一致的全序（时间戳相同则用进程号打破平局），但**不能判断并发**。

### 8.4 向量时钟

$N$ 个进程，每个进程维护 $N$ 维向量 $V$，$V[i]$ 表示"我所知道的进程 $i$ 的事件数"：

1. 进程 $i$ 本地事件或发送：$V[i]\leftarrow V[i]+1$（发送时把 $V$ 附在消息上）；
2. 接收消息（向量 $V_m$）：先对每个分量取 $\max$，再 $V[i]\leftarrow V[i]+1$。

比较：$V_a\le V_b$ 当且仅当所有分量 $V_a[k]\le V_b[k]$。则 $a\rightarrow b\iff V_a<V_b$（$\le$ 且不相等）；若两者互不 $\le$，则 $a\parallel b$。向量时钟**精确刻画因果关系**，代价是向量长度随进程数增长。

**手算**（3 个进程 P1、P2、P3，Python 复核）：

1. P1 发生事件 $a$ 并发送消息 $m$ 给 P2：$V_a=(1,0,0)$；
2. P2 接收 $m$：先 $\max((0,0,0),(1,0,0))=(1,0,0)$，再 P2 分量加 1，事件 $b$：$V_b=(1,1,0)$；
3. P3 独立发生事件 $c$：$V_c=(0,0,1)$；
4. P2 之后本地事件 $d$：$V_d=(1,2,0)$。

比较：$V_a<V_b$（$(1,0,0)\le(1,1,0)$，且不等），所以 $a\rightarrow b$；$V_a$ 与 $V_c$ 互不小于，所以 $a\parallel c$；$V_b<V_d$，所以 $b\rightarrow d$。

应用：多副本数据冲突检测——两个写的向量时钟若是并发的，就不能简单覆盖，需要合并或交给应用处理（Amazon Dynamo 一类系统的做法，细节未核对）。机器人里：多机共同维护一份地图/任务表时，需要判断两个更新是否有因果关系。

### 8.5 幂等与重复

分布式里的消息可能**至少一次**（重试，可能重复）、**至多一次**（不重试，可能丢）、**恰好一次**（理论上需要代价高的协议，实践中常用"至少一次 + 幂等处理"近似）。**幂等**操作执行多次与一次效果相同：把"开泵"设计成"设置泵状态为开"而不是"切换泵"，重复投递也安全；给每条指令加序号/唯一 ID 并在接收端去重。P4 的执行边界与 P6 的安全执行链都用到这一思想，见 [P4 执行边界：白名单、幂等与设备反馈](../../01_项目课程/P4_OpenHarmony智能园艺系统/11_执行边界_白名单_幂等与设备反馈.md)。

## 9. 完整手算与实机运行（Python 复核）

综合小题：**两台机器人共享任务表**。

> 机器人 R1 与 R2 各持有任务表副本。网络分区期间，R1 把任务 7 标为"完成"（版本向量 R1: (1,0)），R2 把任务 7 标为"取消"（R2: (0,1)）。分区恢复后同步，如何处理？

1. 比较向量 $(1,0)$ 与 $(0,1)$：互不 $\le$，二者**并发**，不能简单取"后写入者"（物理时间戳在漂移下不可靠）；
2. 策略选择：应用层规定优先级（"取消"覆盖"完成"？还是人工确认？），或为任务设计**单一所有者**（只有被分配的机器人能修改该任务），从根本上消除并发写；
3. 无论怎样，冲突**被检测到**是前提——这就是向量时钟的用途；
4. 若改用 Lamport 时钟 + 进程号打破平局，会得到确定的顺序，但这个顺序对"并发"事件是任意的，可能让"完成"悄悄覆盖"取消"，需要明确这是否可接受。

另可手算：$N=3$ 副本（$W=2,R=2$）。写 $x=5$ 成功地写入了副本 A、B；副本 C 因分区未收到。随后读取 B、C，得到 B 的新值 5（版本较新）和 C 的旧值，客户端取版本最大者 → 5。若读取 $R=1$ 恰好只读 C，则会读到旧值——这就是 $R+W>N$ 的必要性。

## 11. 常见错误

1. **把 ACID 的 C 与 CAP 的 C 混为一谈**：前者是约束/不变量，后者是线性一致性。
2. **在 `READ COMMITTED` 下做"先读余额再更新"的业务逻辑**：产生丢失更新；应使用原子更新语句（`UPDATE ... SET bal = bal - x WHERE bal >= x`）、行锁或更高隔离级别。
3. **索引设计不看查询**：建了索引但最左前缀不匹配，或对索引列用函数。
4. **索引越多越好**：写放大，占空间。
5. **用墙上时钟测间隔**：被 NTP 调整后出现负的耗时。
6. **用物理时间戳在多机间判断先后**：时钟漂移与不对称延迟使其不可靠；需要因果顺序时用逻辑时钟。
7. **以为"最终一致"等于"很快一致"**：它只承诺收敛，没有时间上限，需要业务容忍中间状态。
8. **重试非幂等操作**：重复扣款、重复下发动作指令。
9. **忽略部分失败**：把远程调用当本地调用，没有超时、重试、熔断。
10. **自己实现共识协议**：极易出错，优先用成熟库。
11. **没有区分"超时"与"失败"**：超时只代表未知，操作可能已经执行。

## 12. 英文面试问答

### Q1. Explain the CAP theorem.

"CAP says that in a distributed data store you can't have consistency, availability and partition tolerance all at once. Since network partitions will happen, the real choice is what to give up during a partition. If I keep consistency, some requests must fail or wait, so availability suffers. If I keep availability, nodes answer from their local state, so a read might return stale data. A better description is PACELC: even when there is no partition, you trade off latency against consistency."

中文要点：分区不可避免，真正的选择是分区时在一致性与可用性间取舍；保一致则部分请求失败/等待，保可用则可能读到旧值；PACELC：无分区时是延迟与一致性的权衡。

**追问**：

- *"Give an example of each choice."* — "A coordination service that stores leader election state should favor consistency. A sensor dashboard that shows the last known value can favor availability and tolerate stale data."
- *"Does your robot system face this?"* — "On a small scale. When a robot loses its network link, it still has to keep a safe local behavior, so the local control must not depend on remote state; the remote task state can lag and be reconciled later."（与 P6 的分层安全执行一致，是通用回答。）

### Q2. What are the ACID properties and what isolation anomalies can occur?

"Atomicity means all or nothing, implemented with an undo log. Consistency means the transaction preserves constraints. Isolation means concurrent transactions don't see each other's partial work, up to the chosen level. Durability means committed data survives crashes, implemented with a write-ahead log flushed to disk. Without enough isolation you can get dirty reads, non-repeatable reads, phantoms and lost updates. I tested a transaction with a check constraint in SQLite: when the second update violated the constraint, the first update was rolled back too."

中文要点：A 靠回滚日志；C 保持约束；I 隔离级别；D 靠 WAL；异常有脏读、不可重复读、幻读、丢失更新；SQLite 实验里约束失败使整个事务回滚。

### Q3. How do you order events across machines when clocks aren't synchronized?

"Physical clocks drift and network delay is asymmetric, so I wouldn't trust them for causal order. With Lamport clocks each process has a counter, increments on events, and on receiving a message sets it to the max of its own and the message's, plus one. This guarantees that if A happened before B, A has a smaller timestamp. If I also need to detect concurrency, I use vector clocks, where each process keeps a vector of counters; two events are concurrent if neither vector is less than or equal to the other. For real-time alignment of sensors, I estimate clock offset with the NTP formula and keep the best sample, the one with the shortest round trip."

中文要点：物理时钟漂移且延迟不对称；Lamport 时钟保证因果前者时间戳更小；向量时钟可判并发；传感器对齐用 NTP 公式估偏移并选往返最短的样本。

**追问**：*"What is the error in NTP-style estimation?"* — "Half the difference between forward and backward delay, bounded by half the round-trip time. In my example with 5 and 15 milliseconds the estimate was off by 5 milliseconds."

### Q4. Why does a database index make queries fast, and when can it hurt?

"An index like a B-plus tree keeps keys sorted with a very high fan-out, so a lookup touches only a few pages, for a billion rows about four or five, instead of scanning the whole table. In a quick SQLite test on 200 thousand rows, an equality lookup went from about 8 milliseconds with a full scan to under 0.01 milliseconds with an index. The cost is extra space and slower writes, since every insert or update must maintain the index, and a composite index only helps when the query matches its leftmost prefix."

中文要点：B+ 树扇出大，十亿行只需约 4–5 次页访问；SQLite 20 万行测试从约 8 ms 降到不足 0.01 ms；代价是空间与写变慢，联合索引需匹配最左前缀。

## 13. 要点速记、自测题、相关链接

### 要点速记

1. ACID：原子性靠回滚日志，持久性靠 WAL；这里的 C 是约束一致，与 CAP 的 C 不同。
2. 隔离异常：脏读、不可重复读、幻读、丢失更新；级别越高并发越低；MVCC 让读不阻塞写。
3. B+ 树扇出大、层数少（十亿行约 4–5 层），叶子链表支持范围查询；索引加速读、拖慢写。
4. 联合索引遵循最左前缀；用 `EXPLAIN` 验证；本机 20 万行例子 8.4 ms → 0.008 ms。
5. CAP：分区时在 C 与 A 间选；PACELC 补充无分区时的延迟与一致性权衡。
6. 一致性从强到弱：线性一致、顺序一致、因果一致、最终一致。
7. 多数派：$R+W>N$ 保证读看到最新写；$2W>N$ 保证写写相交；$N$ 节点容忍 $\lfloor(N-1)/2\rfloor$ 个故障。
8. NTP：$\delta=(t_4-t_1)-(t_3-t_2)$，$\theta=\frac{(t_2-t_1)+(t_3-t_4)}{2}$，路径不对称带来 $\frac{d_1-d_2}{2}$ 的误差。
9. Lamport 时钟保证 $a\rightarrow b\Rightarrow L(a)<L(b)$；向量时钟精确判断先后与并发。
10. 测间隔用单调时钟；重试配幂等；超时不等于失败。

### 自测题

1. 说明为什么 WAL 能保证持久性且比直接写数据页快。
   *要点*：提交前顺序写日志并刷盘，崩溃后重放；顺序写比随机写数据页快。
2. $N=5$，要求读写都至少能容忍 2 个节点故障并且读到最新写，$W$、$R$ 最小各取多少？
   *要点*：$W=R=3$：$R+W=6>5$；容忍 2 个故障时 3 个节点仍可组成多数派。
3. 向量时钟：P1 发送事件 $(2,0,0)$ 给 P2，P2 当前为 $(0,3,1)$，接收后向量是多少？
   *要点*：分量取 max 得 $(2,3,1)$，P2 分量加 1：$(2,4,1)$。
4. 已知 $t_1=10.000$，$t_2=10.130$，$t_3=10.134$，$t_4=10.020$，求 $\delta$ 与 $\theta$，并说明 $\theta$ 的符号含义。
   *要点*：$\delta=0.020-0.004=0.016$ s；$\theta=\frac{0.130+0.114}{2}=0.122$ s；服务器比本地快约 122 ms。
5. 为什么联合索引 `(a,b)` 不能加速 `where b=?`？
   *要点*：索引先按 `a` 排序，`b` 只在同一 `a` 内有序，全局不是有序的，无法二分定位。
