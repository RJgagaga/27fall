## 1. 要解决什么问题

小程序的复杂度来自算法，大程序的复杂度来自**变化**：需求变、硬件换、人员换。软件工程要解决的是：

1. **改一处不要崩十处**：模块之间耦合低，修改被局限。——设计原则与模式。
2. **改完要有信心**：怎么知道没改坏？——自动化测试、持续集成。
3. **别人（和三个月后的自己）能读懂**：——命名、结构、文档、评审。
4. **短期的捷径不要变成长期的负担**：——技术债管理。

机器人软件尤其需要：硬件会换（电机型号变了）、仿真与实机并存、控制回路不允许"改完再看看"。P6 的核心贡献之一——"统一能力模型使运动控制代码在不同硬件间复用"，本质就是**依赖倒置与抽象**（见第 3 节）。

## 2. 符号与术语

| 术语 | 含义 |
|---|---|
| 耦合（coupling） | 模块间依赖的强度，越低越好 |
| 内聚（cohesion） | 模块内部元素相关的紧密度，越高越好 |
| 抽象 / 接口 | 隐藏实现细节、只暴露契约 |
| 重构（refactoring） | 不改变外部行为地改善内部结构 |
| 回归（regression） | 以前正常的功能被新改动破坏 |
| 单元测试 | 测试最小可测单元（函数、类），隔离依赖，快 |
| 集成测试 | 测试多个组件配合 |
| 测试替身 | 用来代替真实依赖的对象：stub（返回预设值）、fake（可运行的简化实现）、mock（可验证调用的对象） |
| CI / CD | 持续集成 / 持续交付：每次提交自动构建并测试 |
| 技术债（technical debt） | 为了快而采用的次优方案，带来的未来额外成本 |
| 代码坏味道（code smell） | 暗示设计可能有问题的表象，如过长函数、重复代码 |
| 圈复杂度 | 独立路径数，约等于判定节点数 + 1 |

## 3. 设计原则：SOLID 及其他

### 3.1 单一职责原则（SRP）

**一个模块只应有一个引起它变化的原因。**

违反的样子：一个 `Robot` 类里既做电机 PID 计算，又解析 CAN 报文，又写日志，又提供 HTTP 接口。CAN 协议改了要动它，日志格式改了也要动它，PID 参数调整还要动它。

改法：拆成 `CanCodec`（编解码）、`PidController`（算法）、`Logger`、`Api`，`Robot` 只负责组合。判断标准不是"类的大小"，而是"会因为哪些不同原因而修改"。

### 3.2 开闭原则（OCP）

**对扩展开放，对修改关闭**：增加新行为时，应该是新增代码，而不是改动已验证过的旧代码。

违反的样子：

```python
def filter_step(kind, x, state):
    if kind == "lowpass": ...
    elif kind == "moving": ...      # 每加一种滤波器都要改这个函数
```

改法：定义统一接口，每种滤波器是一个新类（策略模式，见 4.1）。新增只需添加类并注册。

### 3.3 里氏替换原则（LSP）

**子类对象应能替换父类对象而不破坏程序正确性。** 违反的样子：`Rectangle.set_width()` 与 `Square` 继承——正方形改宽度要同时改高度，使依赖"宽高独立"的代码出错。教训：继承表达的是"行为上的 is-a"，不是"分类学上的 is-a"；优先**组合**而不是继承。机器人中的例子：子类 `SafeMotor` 在父类 `Motor.set_torque()` 的契约（接受任意范围的力矩）上偷偷增加限幅，调用者的假设被打破——应该把限幅写进契约，或用组合装饰。

### 3.4 接口隔离原则（ISP）

**不要强迫使用者依赖它们不用的方法。** 一个同时包含 `read_imu()`、`set_pwm()`、`flash_firmware()` 的巨大接口，会让只需要读 IMU 的仿真替身也不得不实现 `flash_firmware()`。拆成 `ImuSource`、`MotorSink` 等小接口。

### 3.5 依赖倒置原则（DIP）

**高层模块不应依赖低层模块，二者都应依赖抽象。** 控制算法（高层）不要直接 `#include "stm32_can.h"`（低层），而是依赖一个 `MotorInterface` 抽象；实机实现、仿真实现分别提供。这样：

1. 算法可以在 PC 上用仿真替身单元测试；
2. 换电机/总线只改实现，不动算法；
3. 对应 P6 "统一能力模型 + 设备抽象"，以及 ros2_control 的硬件接口思想。

**依赖注入（DI）**是实现 DIP 的手法：依赖不在类内部 `new`，而是由外部传入（构造函数参数）。

### 3.6 其他常用准则

- **DRY**（Don't Repeat Yourself）：知识只有一个权威表示；注意"偶然的重复"不一定要合并，过早抽象比重复更糟。
- **KISS / YAGNI**：保持简单；不要实现"可能将来需要"的功能。
- **最小惊讶原则**：函数名与行为一致；不要让 `get_x()` 修改状态。
- **组合优于继承**；**迪米特法则**（只和直接朋友说话，避免 `a.b().c().d()` 的长链）。
- **契约式设计**：明确前置条件、后置条件、不变量，用断言/类型表达。

> **注意**：原则是权衡的指南，不是教条。为只有一种实现的东西造接口，就违反了 YAGNI；先写出能工作的最简版本，出现第二种变化时再抽象（"三次法则"：重复三次再重构）。

## 4. 常用设计模式

模式是针对反复出现的问题的命名好的解决套路。面试重点是：**它解决什么变化？有什么代价？**

### 4.1 策略（Strategy）

把一族可互换的算法封装成统一接口，运行时选择。

```python
# 教学示例，非项目源码
from abc import ABC, abstractmethod

class Filter(ABC):
    @abstractmethod
    def step(self, x): ...

class Lowpass(Filter):
    def __init__(self, a): self.a, self.y = a, None
    def step(self, x):
        self.y = x if self.y is None else self.y + self.a * (x - self.y)
        return self.y

class Moving(Filter):
    def __init__(self, n): self.n, self.buf = n, []
    def step(self, x):
        self.buf.append(x); self.buf = self.buf[-self.n:]
        return sum(self.buf) / len(self.buf)
```

输入序列 `[0, 10, 10, 10]`，Python 复核：`Lowpass(0.5)` 输出 `[0, 5.0, 7.5, 8.75]`（$y\leftarrow y+0.5(x-y)$ 逐步手算：$0\to5\to7.5\to8.75$）；`Moving(3)` 输出 `[0.0, 5.0, 6.667, 10.0]`（第 3 个窗口为 $(0+10+10)/3=6.667$，第 4 个窗口 $(10+10+10)/3=10$）。使用方只依赖 `Filter` 接口，增加新滤波器不改使用方——这同时是 OCP 的体现。在机器人中，控制律可替换（PID / LQR / 滑模）、规划器可替换（见 [P3 从 PID 到变增益 PID 再到滑模](../../01_项目课程/P3_RoboMaster英雄机器人嵌入式控制/08_从PID到变增益PID再到滑模控制.md) 的演进过程）都适用该思想。

### 4.2 观察者 / 发布—订阅（Observer / Pub-Sub）

一个对象状态变化时通知多个依赖者，发布者不需要知道订阅者是谁。

```python
class Bus:
    def __init__(self): self.subs = {}
    def sub(self, topic, fn): self.subs.setdefault(topic, []).append(fn)
    def pub(self, topic, msg):
        for f in self.subs.get(topic, []): f(msg)

b = Bus(); got = []
b.sub("state", lambda m: got.append(("A", m)))
b.sub("state", lambda m: got.append(("B", m)))
b.pub("state", 1)
print(got)    # [('A', 1), ('B', 1)]
```

ROS2 的话题、DDS 的发布订阅就是这个模式的分布式版本，解耦了数据的产生者和消费者；代价是**调用关系隐含**，调试时较难追踪"谁在响应这条消息"，以及回调执行线程和顺序的问题（见 [并发与内存模型](./05_并发与内存模型_锁_原子_无锁.md)）。

### 4.3 状态机（State）

对象的行为取决于当前状态，状态转换由事件触发。比一堆嵌套的 `if` 清晰，易测试。P4 的水泵控制就是一个迟滞状态机（见第 6 节完整示例）；复杂任务可以用层次状态机或行为树（见 [行为树与任务规划](../08_规划与导航/08_行为树与任务规划_PDDL_有限状态机.md)）。

### 4.4 工厂（Factory）

把"创建哪个具体对象"的决定集中到一处，使用者只依赖接口。例如根据配置创建 `SimMotor` 或 `CanMotor`。ROS2 的组件加载、插件机制（pluginlib）是工厂思想的产物。

### 4.5 适配器（Adapter）

把一个接口转换成另一个期望的接口。例：把第三方电机驱动的 `set_current(amps)` 包装成统一的 `set_torque(nm)`。P6 把 ROS/ROS2 运动指令映射到底层驱动，是**适配器**的典型应用，见 [ROS/ROS2 命令映射与跨硬件复用](../../01_项目课程/P6_深开鸿M-Robots平台软件/04_ROS_ROS2命令映射与跨硬件复用.md)。

### 4.6 单例、装饰器、模板方法

- **单例**：全局唯一实例。被过度使用，等于隐藏的全局变量，妨碍测试；如要使用，建议由外部注入。
- **装饰器**：不改原对象，动态叠加功能（限幅、日志、重试）。比继承灵活。
- **模板方法**：父类定义算法骨架，子类实现步骤。ROS2 生命周期节点的 `on_configure/on_activate` 回调类似该思想。

### 4.7 何时不要用模式

模式是为"已知会变化的点"准备的。没有变化压力时引入，只增加间接层。判断：你能否说出**下一次具体要变的是什么**？说不出，就先写直白代码。

## 5. 测试：金字塔、替身与可测试性

### 5.1 测试金字塔

```text
          /\
         /  \     系统 / 端到端测试：少而慢，覆盖关键场景（真机、完整仿真）
        /----\
       /      \   集成测试：中等数量，验证组件配合（节点间通信、驱动+总线）
      /--------\
     /          \ 单元测试：多、快、稳定，验证函数/类逻辑
    /------------\
```

比例原则：底层多、顶层少。因为越往上越慢、越脆弱、越难定位。机器人系统的特殊难点：**硬件在环**测试昂贵且不可重复，所以要把尽可能多的逻辑做成可在 PC 上跑的纯函数/纯类，并用仿真和回放（rosbag）补集成层。

### 5.2 好测试的特征（FIRST）

Fast（快）、Independent（独立，不依赖执行顺序）、Repeatable（可重复，不依赖外部环境、随机数和时间）、Self-validating（自动判断通过与否）、Timely（及时写）。

### 5.3 测试替身与时间

测硬件相关代码的关键是**把硬件和时间都当作可注入的依赖**：

- 把 `read_adc()` 抽象成接口，测试里注入返回预设值的 stub；
- 把 `time.now()` 抽象成时钟对象，测试里用 `FakeClock`，`advance(dt)` 直接拨动时间，从而测试"超时 500 ms 后进入保护状态"而无需真等 500 ms；
- 用 mock 验证"安全链被调用了一次"这类交互。

```python
class FakeClock:
    def __init__(self): self.t = 0.0
    def now(self): return self.t
    def advance(self, dt): self.t += dt
```

### 5.4 覆盖率及其局限

行覆盖率 = 被执行的行数 / 总行数。例：200 行里执行了 170 行，覆盖率 $170/200=85\%$。更强的有**分支覆盖**（`if` 的真假分支都走到）和**条件覆盖**；`if a and b or c` 这类含 3 个布尔量的条件，输入组合有 $2^3=8$ 种。**覆盖率高不等于测试好**：没有断言的测试可以 100% 覆盖；它只能告诉你"哪些代码肯定没测过"。突变测试（故意引入 bug 看测试能否发现）可更直接评估测试质量。

### 5.5 其他测试类型

属性测试（对大量随机输入检查性质，如"排序结果有序且是输入的排列"）、回归测试（每个修复过的 bug 配一个测试）、仿真测试、回放测试、故障注入、模糊测试（fuzzing）、性能/延迟测试。机器人里特别重要：**边界/故障输入**（NaN、超范围、通信断开、时间戳倒退）——这些是真实世界里最常把系统打垮的输入。

## 6. 测试驱动开发（TDD）完整示例

### 6.1 红—绿—重构

1. **红**：先写一个会失败的测试，描述想要的行为；
2. **绿**：写最少的代码让它通过；
3. **重构**：在测试保护下整理代码；然后重复。

好处：强迫先想清楚接口和行为；产出的代码天然可测；得到一套回归保护网。

### 6.2 示例：迟滞开关（水泵控制）

需求（与 P4 同构的设计，教学示例，非项目源码）：土壤湿度低于下阈值开泵、高于上阈值关泵，中间保持原状态（避免在阈值附近反复开关，即迟滞）；手动指令优先于自动。

**第一轮 红**：写测试描述行为。

```python
import unittest

class T(unittest.TestCase):
    def test_hysteresis(self):
        p = PumpController()                       # 默认 on_th=30, off_th=45
        seq = [50, 40, 29, 35, 44, 46, 40]
        out = [p.update(m) for m in seq]
        self.assertEqual(out, [False, False, True, True, True, False, False])
```

此时 `PumpController` 不存在，测试失败（红）。

**绿**：最少实现：

```python
class PumpController:
    def __init__(self, on_th=30.0, off_th=45.0):
        self.on_th, self.off_th, self.on = on_th, off_th, False
    def update(self, moisture, manual=None):
        if moisture < self.on_th: self.on = True
        elif moisture > self.off_th: self.on = False
        return self.on
```

**手算检查**序列 `[50, 40, 29, 35, 44, 46, 40]`：50 在中间区间之上（>45）→ 关（False）；40 在 [30,45] 之间 → 保持 False；29 < 30 → 开（True）；35 保持 True；44 保持 True；46 > 45 → 关（False）；40 保持 False。与期望一致。

**第二轮 红**：增加"手动优先"与"阈值非法"与"边界"测试：

```python
    def test_manual(self):
        p = PumpController()
        self.assertTrue(p.update(100, manual=True))     # 即使湿度很高，手动开优先
        self.assertFalse(p.update(0, manual=False))     # 即使很干，手动关优先
    def test_bad_thresholds(self):
        with self.assertRaises(AssertionError): PumpController(50, 40)
    def test_boundaries(self):
        p = PumpController()
        self.assertFalse(p.update(30.0))                # 等于阈值不触发
        self.assertTrue(p.update(29.999))
```

**绿**：加上 `manual` 分支与构造时的 `assert on_th < off_th`。

```python
    def __init__(self, on_th=30.0, off_th=45.0):
        assert on_th < off_th
        ...
    def update(self, moisture, manual=None):
        if manual is not None:
            self.on = bool(manual); return self.on
        ...
```

运行 `unittest`：**4 个测试全部通过**（Python 复核：`Ran 4 tests ... OK`）。

**重构**：此时可以把阈值校验换成抛出明确异常的校验、把 `manual` 的语义写进文档字符串，每次修改后重跑测试保证行为不变。

### 6.3 TDD 的局限

对探索性强（不知道想要什么输出）、强依赖硬件或需要大量设计试验的代码，纯 TDD 不一定高效。实用做法：对**逻辑密集、边界多**的部分（状态机、协议解析、限幅、坐标变换、滤波）用 TDD 或至少补单元测试；对硬件交互用接口隔离后在集成/回放层验证。

## 7. 代码评审

### 7.1 目的

发现缺陷、保持一致性、传播知识、提高可维护性。**不是**挑错比赛或评判人。

### 7.2 评审清单（可直接使用）

**正确性**
- 逻辑是否符合需求？边界条件（空、零、最大、负、NaN）是否处理？
- 错误路径是否处理？失败时系统是否进入安全状态？
- 并发：共享数据有无保护？加锁顺序？回调线程？
- 资源：内存、文件、锁、句柄是否释放？有无泄漏？

**设计**
- 职责是否单一？有无不必要的耦合/全局状态？
- 是否有更简单的方案？有无过度设计？
- 接口是否清晰、难以误用？

**可读性**
- 命名是否表达意图？函数是否过长（经验上超过一屏就值得考虑拆分）？
- 魔法数字是否有名字和单位（`timeout_ms`、`gain_nm_per_rad`）？
- 注释解释"为什么"而不是复述"做什么"。

**测试与工程**
- 新逻辑有测试吗？覆盖了失败路径吗？
- 日志是否足以事后诊断，是否过多刷屏？
- 有无破坏向后兼容（接口、消息格式、参数名）？

**机器人专项**
- 单位和坐标系是否标注（rad 还是 deg，机体系还是世界系）？
- 控制回路里有无动态分配、阻塞调用、不确定耗时操作？
- 对输入的新鲜度、范围、NaN 是否检查？输出有无限幅？
- 通信中断/传感器失效时的降级行为是什么？

### 7.3 怎么提意见、怎么接受

- 针对**代码**而不是人；用提问和建议语气（"这里如果输入为空会怎样？"）；区分必须改（阻塞合并）与可选改进（nit）。
- 一次评审的改动尽量小（经验上几百行以内），大改动先对设计达成共识。
- 作者：自测并自审后再提交；提交说明解释"为什么"；对意见先理解后回应，不同意时给出依据。
- 自动化能做的交给工具：格式化、静态分析（lint）、编译警告、单元测试，评审者专注设计与逻辑。

## 8. 技术债、重构与版本管理

### 8.1 技术债的利息

技术债的比喻：为快速交付而选择次优方案，相当于借款；以后每做相关修改都要多付"利息"（理解和绕开坏设计的额外成本），直到偿还（重构）。设每次相关修改的基础成本为 1 单位，每个遗留捷径使后续成本按比例 $d$ 复合增长，则第 $k$ 次修改成本为 $(1+d)^k$。

**示例（假设性模型，非测量）**（Python 复核）：

| 增长率 $d$ | $k=0$ | $k=5$ | $k=10$ |
|---|---|---|---|
| 0 | 1.00 | 1.00 | 1.00 |
| 0.1 | 1.00 | 1.61 | 2.59 |
| 0.2 | 1.00 | 2.49 | 6.19 |

即使每次只增加 10% 的成本，十次修改后同类工作的成本就是 2.6 倍；增长率 20% 则超过 6 倍。这个模型是示意性的，它想说明的是"债是复利"。所以**不是不能欠债**（原型、比赛前夕可以刻意欠），而是要**有意识地记录并有计划地偿还**，比如在 TODO 里写明原因与偿还条件，每个迭代预留固定比例时间。

### 8.2 重构的安全做法

1. 先有测试保护（没有就先补特征测试，记录当前行为）；
2. 小步修改，每步都跑测试；
3. 重构与功能修改分开提交；
4. 常见手法：提取函数、重命名、消除重复、引入参数对象、以多态取代条件分支。

### 8.3 版本控制与持续集成

- Git 分支策略：主干保持可发布，功能分支短寿命，合并前跑 CI。提交粒度：一个提交一个逻辑改动，提交说明解释原因。（更多命令见 [Linux、Git、编译构建八股](../../03_八股知识/01_计算机基础/08_Linux_Git_编译构建八股.md)。）
- CI：每次提交自动编译、跑测试和静态检查；机器人项目可以在 CI 里跑仿真回归和 rosbag 回放（见 [ROS2 测试与 CI](../12_机器人软件/09_ROS2测试与CI_launch_testing_gtest_rosbag回放.md)）。
- 语义化版本（MAJOR.MINOR.PATCH）：不兼容改动升 MAJOR；接口变化是否兼容涉及 ABI（见 [编译链接加载与 ABI](./06_编译链接加载_C_C++_ABI.md)）。
- 配置与代码分离、参数有默认值与范围校验；可复现构建（锁定依赖版本）。

## 9. 完整手算与可运行示例（Python 复核）

### 9.1 圈复杂度手算

函数：

```python
def classify(v, manual):
    if manual is not None:          # 判定 1
        return manual
    if v < 30:                      # 判定 2
        return True
    elif v > 45:                    # 判定 3
        return False
    return None
```

圈复杂度 $=$ 判定节点数 $+1=3+1=4$，即需要至少 4 个测试用例才能覆盖每条独立路径：`manual` 非空；`v<30`；`v>45`；`30≤v≤45`。这与 6.2 节的测试用例相呼应。

### 9.2 把迟滞控制器与可注入时钟结合（设计说明，不是运行结果）

需求：湿度连续低于下阈值超过 `hold_s` 秒才开泵（防止传感器偶发抖动）。用 `FakeClock` 在测试里拨时间，不需要真的等待。设计要点是把"时间"作为依赖注入：`Debounce(clock, hold_s)` 内部只调用 `clock.now()`。测试用例：在 `t=0` 喂入"低"，`advance(hold_s-0.1)` 后仍为未触发，再 `advance(0.2)` 后触发；再喂入"高"重置计时。这类时间相关逻辑在真实时间下测试既慢又不稳定，用假时钟则是毫秒级确定性测试。

### 9.3 实际运行输出

第 6 节的 4 个单元测试在 Python 3.12 下全部通过；第 4 节策略模式输出 `Lowpass [0, 5.0, 7.5, 8.75]`、`Moving [0.0, 5.0, 6.667, 10.0]`；观察者输出 `[('A', 1), ('B', 1)]`。

## 11. 常见错误

1. **为了用模式而用模式**：过度设计，间接层过多。
2. **继承滥用**：深层继承树，子类违反父类契约；优先组合。
3. **全局状态和单例泛滥**：隐式依赖使测试困难。
4. **测试依赖真实时间、随机数、网络**：时而通过时而失败（flaky）。
5. **没有断言的测试**，或只测"快乐路径"。
6. **追求覆盖率数字**，忽略断言质量与边界用例。
7. **提交巨大的评审**：评审者无法认真看。
8. **评审只看风格不看逻辑**：风格应交给自动格式化工具。
9. **重构与功能混在一个提交**，出问题难以回滚。
10. **魔法数字和缺失单位**：`gain = 0.37` 不知道含义和单位。
11. **吞掉异常/错误码**，系统带着坏状态继续运行；在机器人里应进入明确的安全状态。
12. **没有记录的技术债**：捷径变成"永久方案"。
13. **相信"我测过了"**而没有自动化：下一次修改就失去保护。

## 12. 英文面试问答

### Q1. Tell me about a design decision you made and the trade-offs.

"In the robot platform project, motion-control code could not be reused across hardware because every device exposed its own interface. I built a unified capability model for sensors, actuators and controllers, and mapped ROS and ROS2 motion commands to the low-level drivers. The benefit was that the control code depends on an abstraction, so it can be reused on different hardware. The cost was an extra layer, and some hardware-specific features don't fit neatly, so I had to decide what to expose in the common interface and what to keep behind device-specific extensions."

中文要点：问题（接口异构导致无法复用）→ 方案（统一能力模型 + ROS/ROS2 命令映射）→ 收益（依赖抽象，可复用）→ 代价（间接层；特有功能难统一，需要取舍）。内容与 CV 的 P6 描述一致，细节参见 P6 章节。

**追问**：

- *"What principle is behind that?"* — "Dependency inversion: the high-level control code and the low-level drivers both depend on an abstraction, instead of the control code depending on a specific driver."
- *"How did you verify it worked?"* — 按真实情况回答，可结合 P6 测试章节，"I checked that the same control code ran against different device implementations and compared the behavior"。没有具体数据就不要编。

### Q2. How do you test code that talks to hardware?

"I separate the logic from the hardware. State machines, limiting, protocol parsing and filters are written as plain code with the hardware access behind a thin interface, so I can unit test them on a PC with fake inputs and a fake clock. Then I use simulation or replayed recordings for integration tests, and a small number of on-robot tests for the final checks. I specifically test bad inputs: out-of-range values, NaN, stale timestamps and lost communication, because those cause most real failures."

中文要点：逻辑与硬件分离（薄接口 + 假输入 + 假时钟）；仿真/回放做集成；少量实机测试；重点测坏输入（超范围、NaN、陈旧时间戳、通信中断）。

### Q3. What is the difference between a mock, a stub and a fake?

"A stub returns canned answers so the code under test can run. A fake is a working but simplified implementation, like an in-memory database or a simulated motor. A mock is used to verify interactions, for example that a function was called once with certain arguments. I prefer fakes and stubs when I can test by state, and use mocks sparingly, because tests that check exact calls break whenever the implementation changes."

中文要点：stub 返回预设值；fake 是简化但可工作的实现；mock 验证交互；能按状态断言就优先 stub/fake，少用 mock，避免测试与实现绑得太紧。

### Q4. What do you look for in a code review?

"First correctness, including edge cases and error paths. Then design: is each piece doing one job, are there hidden dependencies. Then readability and tests. For robotics code I also check units and frames, input validity such as NaN and stale data, output limits, and what happens when communication is lost. I try to keep comments about the code, phrase them as questions or suggestions, and let formatters and linters handle style."

中文要点：正确性（边界、错误路径）→ 设计（单一职责、隐含依赖）→ 可读性与测试；机器人专项：单位与坐标系、输入有效性、输出限幅、通信中断；对事不对人，风格交给工具。

## 13. 要点速记、自测题、相关链接

### 要点速记

1. SOLID：单一职责、开闭、里氏替换、接口隔离、依赖倒置；依赖倒置 + 依赖注入使算法可在仿真中测试。
2. 优先组合而非继承；继承要满足行为上的可替换。
3. 策略 = 可替换算法；观察者 = 发布订阅解耦；状态机 = 用状态与事件取代嵌套 `if`；适配器 = 接口转换。
4. 模式为"已知的变化点"服务，说不出下一次要变什么就不要用。
5. 测试金字塔：单元多而快，系统少而慢；机器人要尽量把逻辑做成可在 PC 上测试的纯代码。
6. 时间和硬件当作可注入依赖；用假时钟测试超时逻辑。
7. TDD：红（先写失败测试）→ 绿（最少实现）→ 重构；边界与异常用例必写。
8. 覆盖率只告诉你哪些没测过；高覆盖率不等于好测试。
9. 代码评审先看正确性与设计，风格交给工具；机器人加查单位、坐标系、有效性与降级。
10. 技术债是复利（示例 $d=0.1$ 时十次后 2.59 倍）；有意识地记录与偿还。

### 自测题

1. 指出下面设计违反了哪条 SOLID 原则并给出改法：一个 `Controller` 类内部直接创建 `Stm32CanDriver` 并调用它。
   *要点*：违反依赖倒置；改成依赖 `MotorInterface` 抽象，驱动通过构造函数注入，测试里注入 fake。
2. 对 `PumpController(on_th=30, off_th=45)`，输入序列 `[28, 35, 46, 44, 29]`，输出序列是什么？
   *要点*：28<30 开(True)；35 保持(True)；46>45 关(False)；44 保持(False)；29<30 开(True)。
3. 为什么直接用 `time.sleep(0.5)` 测试 500 ms 超时逻辑不是好做法？怎么改？
   *要点*：慢且不稳定（flaky）；引入可注入时钟，用 `FakeClock.advance` 拨动时间。
4. 一个函数有 4 个独立 `if`（互不嵌套），圈复杂度和最少测试数是多少？
   *要点*：圈复杂度 $4+1=5$，至少 5 个用例覆盖独立路径。
5. 技术债增长率 $d=0.15$，第 8 次相关修改的相对成本是多少？
   *要点*：$(1.15)^8\approx3.06$。
