````text
# P3 第 1 章：硬件反馈与 FreeRTOS 任务

先把整章压成一句话：

> **电机和传感器不断把“现在发生了什么”告诉控制板；控制程序根据这些反馈计算“接下来该怎么做”；控制板再把命令发回电机。FreeRTOS 负责安排这些程序什么时候使用 CPU。**

下面从实际的机器人信号怎么走开始，再解释任务、优先级、周期和反馈数据。

## 1. 先看一条完整的闭环

把电机想成一个会不断汇报状态的执行器：

```text
控制板发命令
    ↓
电机转动，机器人发生运动
    ↓
电机编码器和传感器测到新的状态
    ↓
状态反馈回控制板
    ↓
控制程序比较“想要的”和“实际的”
    ↓
生成下一条命令
    └──────────循环
```

比如云台要保持某个角度：

```text
目标角度
  ↓
控制器读取当前角度和转动速度
  ↓
计算需要给电机多大的驱动命令
  ↓
命令通过 CAN 发给电机
  ↓
电机带动云台转动
  ↓
编码器和陀螺仪测到新的状态
  └──反馈给控制器
```

这里有两个容易混淆的词：

- **反馈**：电机或传感器告诉控制板“我现在怎样”。例如测得转速 `speed_rpm`。
- **命令**：控制板告诉电机“你接下来怎样做”。例如控制器算出的 `give_current`。

反馈是“实际发生了什么”，命令是“希望接下来发生什么”。二者方向相反。

## 2. 在这个项目里，电机反馈怎么进入控制板？

### 2.1 CAN 报文先到达接收中断

CAN 可以先理解为控制板和电机之间的一条通信线路。电机按自己的通信协议发送状态报文，控制板收到报文后，硬件会触发 CAN 接收中断。

这个源码快照里的 `can_receive.c` 在中断里调用 `HAL_CAN_GetRxMessage` 取出报文，然后根据报文 ID 把数据交给云台或底盘对应的处理函数。可以看 [can_receive.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Communication/can_receive.c:9>)。

要注意：**电机 CAN 反馈不是先进入一个叫 `Decode_task` 的任务再解码。**在这里，电机报文是在 CAN 接收中断里直接分发和解码的。项目里的 `Decode_task` 主要处理 USB 通信协议；它不是电机 CAN 解码任务。相关代码分别在 [decode.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/communication/decode.c:34>) 和 [DJI_Motor.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/Motor/DJI_Motor.c:20>)。

这是很重要的区分：**“任务”不是所有程序工作的统称。中断也能处理数据，但中断和任务是不同的运行机制。**

### 2.2 报文里的字节怎样变成电机状态？

这份代码按电机协议把一条报文中的字节拆成状态字段，大致包括：

| 字段 | 白话意思 | 常见单位或格式 |
|---|---|---|
| `ecd` | 转子当前在一圈中的哪个角度位置 | 编码器计数 |
| `speed_rpm` | 转子现在转多快 | 转/分钟 |
| `given_current` | 电机反馈的电流相关值 | 协议整数 |
| `temperate` | 电机温度 | 协议数值 |

代码把报文中的字节组合成这些字段。比如 `data[2]` 和 `data[3]` 组合成 `speed_rpm`，`data[4]` 和 `data[5]` 组合成 `given_current`。源码在 [DJI_Motor.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/Motor/DJI_Motor.c:20>)。

**`given_current` 这个名字容易误导。**在反馈结构里，它是电机报回来的电流相关反馈值，不是此刻控制板正在发出的命令。控制程序算出的 `give_current` 才是要发送给电机的控制量。两个名字相似，但一个是反馈，一个是命令。

它们都是协议里的整数值。没有查清电机型号、协议换算和标定前，不能直接把数值说成安培或牛米。

### 2.3 编码器为什么需要处理“转了一整圈”？

电机编码器通常只报告当前这一圈里的位置。可以把它想成时钟：指针从 12 点转到 1 点，读数增加；从 11 点继续转过 12 点，读数会从一圈末尾回到开头。

如果直接相减，就会把“只多转了一点”误认为“倒退了很远”。

例如编码器计数从 `8180` 变成 `10`。如果一圈有 8192 个计数，直接相减得到：

\[
10-8180=-8170
\]

但电机实际上是正方向越过了一圈边界，只前进了：

\[
(8192-8180)+10=22\text{ 个计数}
\]

源码用前后两次编码器值判断这种回绕，并累计圈数，得到连续的总计数。相关逻辑叫 `DJI_Round_Count`，见 [DJI_Motor.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/Motor/DJI_Motor.c:36>)。

### 2.4 RPM 怎样换成角速度？

RPM 是每分钟转多少圈。要变成每秒转多少圈，先除以 60；一圈等于 \(2\pi\) 弧度，所以：

\[
\omega
=
\text{RPM}\times\frac{2\pi}{60}
\]

假设电机转速是 600 RPM：

\[
600\div60=10\text{ 圈/秒}
\]

\[
10\times2\pi=20\pi\approx62.83\text{ rad/s}
\]

也就是说，600 RPM 对应约 \(62.83\text{ rad/s}\)。

如果电机和输出轴之间有 10:1 减速，且 600 RPM 是电机转子的转速，那么输出轴转速约为电机转速的十分之一。但**不能看到齿轮比就盲目除**：如果控制器的目标和反馈本来都使用电机转子 RPM，就应该先在同一单位下比较。

## 3. CAN 之外，IMU 是怎样把姿态送给程序的？

电机反馈和 IMU 反馈走的路径不完全一样。

在这份代码中，IMU 通过 SPI 和 DMA 读取。可以先把 DMA 理解成一个“数据搬运工”：传感器数据搬到内存后，程序收到通知，再读取和处理数据。

大致过程是：

```text
IMU 产生新数据
  ↓
SPI / DMA 读取数据
  ↓
中断或通知提醒 INS 任务：“数据好了”
  ↓
INS 任务处理数据
  ↓
校正安装方向和零漂、滤波加速度、计算姿态
  ↓
云台控制读取姿态结果
```

源码里的 `INS_task` 会等待任务通知；收到通知后读取数据、处理陀螺仪和加速度计数据，并更新姿态结果。也就是说，这个任务不是简单地每隔固定时间醒来，而是会等待 IMU 数据处理的通知。见 [Atti.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Communication/Atti.c:215>)。

这个程序还对加速度计数据做了滤波，再交给姿态解算。滤波的直观作用是压低快速抖动，但它可能让数据反应稍慢。**滤波不是免费去噪：更平滑通常伴随更多延迟。**云台控制中的陀螺仪输入也使用了滤波；滤波发生在哪个量上，要沿代码路径逐项确认，不能假设所有传感器数据都经过相同处理。

## 4. `Chassis_task` 和 `Gimbal_task` 是什么？

它们是 FreeRTOS 中两个反复运行的工作程序，可以分别理解为：

- `Gimbal_task`：读取云台相关目标和反馈，计算云台与发射机构的控制量，再发送电机命令。
- `Chassis_task`：读取底盘目标和反馈，计算四个麦克纳姆轮的目标与控制量，再发送电机命令。

底盘任务的主要步骤在 [Chassis.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Chassis/Chassis.c:64>)。云台任务的主要步骤在 [Gimbal.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:69>)。

以云台为例，可以把控制链想成：

```text
希望的云台角度
        ↓
读取编码器角度、IMU 姿态和转动速度
        ↓
外层角度控制：角度差还剩多少？
        ↓
生成希望达到的转动速度
        ↓
内层速度控制：实际转速和希望转速差多少？
        ↓
生成电机电流命令 give_current
        ↓
打包为 CAN 报文发给电机
```

所以云台控制程序最终发给电机的不是“云台角度”，而是控制器根据角度和速度误差计算出的电流相关命令。电机收到命令后转动，新的编码器和 IMU 数据再返回，闭环就形成了。

底盘也是类似的闭环，只是从“车体要怎么走”开始，先通过麦克纳姆轮运动学得到各轮目标速度，再比较各轮目标速度和 `speed_rpm`，最后生成各轮的 `give_current` 命令。

## 5. FreeRTOS 的“任务”怎么理解？

FreeRTOS 是运行在控制板上的实时操作系统。它帮助程序安排多个工作：云台控制、底盘控制、IMU 处理、通信解析等。

如果控制板只有一个 CPU 核心，那么通常不是云台任务和底盘任务真的同时在这个核心上运行。更准确地说：

> CPU 很快地在不同任务之间切换，让它们看起来像同时工作。

有些硬件外设可以和 CPU 并行做事。例如 DMA 正在搬运 IMU 数据时，CPU 可以执行其他代码。数据搬完后，中断再通知 CPU。

任务可以粗略分成三种状态：

- **运行中**：CPU 现在正在执行它；
- **就绪**：它有工作，但 CPU 暂时在忙；
- **等待中**：它在等时间、数据或某个事件。

例如 `INS_task` 等 IMU 通知时处于等待状态；通知到来后它变成就绪任务，再由 FreeRTOS 安排它运行。`Gimbal_task` 调用 `vTaskDelay` 时也会主动等待，让出 CPU。

## 6. 优先级到底是什么？它不等于频率

优先级解决的是：

> **多个任务都准备运行时，CPU 先运行谁？**

这份源码快照中，FreeRTOS 初始化文件把云台、USB、`Decode_task` 等设置为较高优先级，把底盘设置为较低优先级，把 IMU 任务设置为 idle 优先级。任务创建配置见 [freertos.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/Core/Src/freertos.c:128>)。

优先级**不等于运行频率**：

- 优先级高，不表示它每秒运行次数一定更多；
- 优先级低，不表示它一定运行得慢；
- 优先级主要影响任务已经就绪时，谁先拿到 CPU。

举个例子：

1. 云台任务优先级高，且目前就绪；
2. 底盘任务优先级低，也已经就绪；
3. CPU 会优先让云台任务运行；
4. 如果云台任务随后进入等待，底盘任务就有机会运行。

所以优先级高的任务不一定一直霸占 CPU。关键还要看它什么时候有工作、什么时候等待、每次工作多久。

另一个需要记住的区别是：**硬件中断和 FreeRTOS 任务不是同一层。**CAN 或 DMA 中断可以打断正在运行的任务。FreeRTOS 的任务优先级不能直接说明硬件中断的优先级。

## 7. 为什么 `vTaskDelay(1)` 不一定代表“一毫秒后准时运行”？

这份源码的 FreeRTOS 配置设置了每秒 1000 个系统节拍：

\[
\text{tick 频率}=1000\text{ 次/秒}
\]

因此，一个 tick 名义上约为：

\[
1/1000\text{ 秒}=1\text{ ms}
\]

但 `vTaskDelay(1)` 的意思是“至少等待一个系统节拍再进入可运行状态”，不是“从这一行开始精确等待 1.000 ms，然后立刻执行”。

调用时刚好处于哪一个 tick 的位置、任务被唤醒后还要等多久才拿到 CPU，都会影响真实等待时间。任务自身的计算也需要时间。

粗略来说：

\[
\text{两次循环开始之间的时间}
=
\text{计算时间}
+
\text{等待时间}
+
\text{被其他工作推迟的时间}
\]

因此，`vTaskDelay(1)` 不能单独证明循环频率是 1 kHz。

## 8. 这份源码里还有一个重要的“实际细节”

章节里的“计算 0.4 ms，再等待 1 ms，所以约 1.4 ms”是帮助理解的**教学算例**，不是这份项目的实测频率。

我对照这份 P3 源码快照时发现，云台和底盘控制循环里不止一处 `vTaskDelay(1)`：

- 云台循环最后有一次延时；
- 云台的 `Send_Gimbal_Data` 里面还有两次延时；
- 底盘循环最后也有一次延时；
- 底盘的 `Send_Chassis_Data` 里面还有两次延时。

云台的延时常量 `GIMBAL_PERIOD` 是 1，定义在 [Gimbal.h](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.h:25>)；底盘的 `CHASSIS_PERIOD` 也是 1，定义在 [Chassis.h](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Chassis/Chassis.h:25>)。

## 9. 周期、频率、执行时间、抖动分别是什么？

假设一个任务每次开始的时刻是：

```text
第 1 次：0.0 ms
第 2 次：2.8 ms
第 3 次：5.7 ms
第 4 次：8.5 ms
```

相邻开始时刻的间隔就是这个任务的实际周期。例如平均周期约 2.83 ms，对应平均频率约：

\[
f=\frac{1}{T}
=\frac{1}{0.00283}
\approx353\text{ Hz}
\]

这些数字只是演示怎么算，不是这份机器人源码的测量结果。

几个词可以这样记：

- **周期**：相邻两次循环开始之间的时间。
- **频率**：一秒钟运行多少次；周期越短，频率越高。
- **执行时间**：任务这一轮实际占用 CPU 多久。
- **抖动**：周期忽长忽短的程度。
- **延迟**：从某个事件发生，到相应处理或命令真正发生，经过了多久。

控制器不只需要“够快”，也需要“间隔稳定”。例如目标是每 2 ms 控制一次，结果有时 2 ms、有时 12 ms，使用固定的控制参数时，实际效果会变化。

## 10. 数据共享有什么风险？

电机报文到来时，中断会更新反馈结构；控制任务之后读取这个结构。它们使用的是共享数据。

由于在单核 CPU 上，任务和中断不会真正同时执行，所以不是两段代码在同一瞬间抢 CPU。但仍可能出现这种顺序：

```text
控制任务读到某电机的新角度
    ↓
CAN 中断插进来，更新了转速和电流
    ↓
控制任务继续读到新的转速和电流
```

这样一次控制计算可能混用了两个报文时刻的数据。对某些算法这可能可以接受；若状态必须对应同一时刻，就要有一致的数据快照、序号或简短的保护机制。

此外，即使字段是“最近一次收到的值”，它也未必足够新。如果 CAN 断了，结构里的数字可能仍保留着上一次的值。控制器需要关注：

- 最近一次反馈是什么时候收到的；
- 反馈是否超过允许的数据年龄；
- 电机或传感器是否掉线；
- 超时后应该采取什么安全动作。

源码里有离线检测相关调用，但**是否构成完整、可靠的超时保护，要继续检查具体阈值和最终停机路径**，不能只看到“有检测函数”就下结论。

## 11. 如何实际判断任务跑得够不够快？

不能只看任务名称、优先级或 `PERIOD` 常量。需要测量：

1. 每次任务开始时的时间；
2. 每次任务结束时的时间；
3. 相邻开始时刻的间隔；
4. 最大执行时间；
5. 最大周期和周期抖动；
6. 反馈数据的年龄；
7. 从收到反馈到发出电机命令的延迟；
8. CAN 是否丢帧或报错。

一种简单方法是在任务开头和结尾翻转 GPIO，再用逻辑分析仪或示波器观察脉冲宽度和间隔。也可以用高精度计时器记录并在任务之外输出结果。

不要在高频控制任务里大量打印日志来测时间：打印本身可能很慢，会改变原本想测的周期。这叫“测量动作影响被测对象”，所以记录方式也要尽量轻量。
````

````text
# 先纠正一句话

前面我把 `vTaskDelay(1)` 说成“至少等待一个完整 tick”，这不准确。**它等待的是 FreeRTOS 的 tick 计数增加一次，不保证从调用这一刻开始，经过完整的 1 ms 才恢复运行。**

这正是理解周期时最容易卡住的地方。我们先只看一条时间线。

## 1. tick 是什么？

FreeRTOS 用一个定时中断反复“敲钟”。每敲一次，系统 tick 计数就增加一次。

这份项目源码的配置是：

\[
\texttt{configTICK\_RATE\_HZ}=1000
\]

意思是每秒敲 1000 次。两个 tick 之间名义上是：

\[
\frac{1}{1000}\text{ 秒}=1\text{ ms}
\]

可以把 tick 想成每 1 ms 出现一次的时间刻度：

```text
时间：  0 ms       1 ms       2 ms       3 ms
tick：   |----------|----------|----------|
```

tick 是系统用来管理任务等待时间的时间刻度。它不是“控制器每 1 ms 自动算一次”的意思。

## 2. `vTaskDelay(1)` 实际上做什么？

`vTaskDelay(1)` 的参数单位是 **tick**。它大意是：

> 当前任务先停下来，等系统 tick 计数增加一次，再进入可以运行的状态。

关键是：它看的是“增加一次”，而不是从调用这一刻开始用秒表计满 1 ms。

看两个情况：

```text
情况 A：任务在 0.1 ms 调用 vTaskDelay(1)
tick： 0 ms |----------------------| 1 ms
任务：        调用 delay ---------↑恢复
```

离 1 ms 的刻度还有约 0.9 ms，所以它大约等 0.9 ms 才变回就绪状态。

```text
情况 B：任务在 0.99 ms 调用 vTaskDelay(1)
tick： 0 ms |----------------------| 1 ms
任务：                             调用 delay ↑恢复
```

下一个 tick 很快就到了，它可能只等约 0.01 ms 就变回就绪状态。

因此，对于 1 ms 的 tick：

> `vTaskDelay(1)` 通常表示等到下一个 tick；从调用时刻算，等待时间可能接近 0 ms，也可能接近 1 ms。

任务变成“就绪”也不保证它在 tick 到来的那一瞬间马上运行。如果有更高优先级的任务正在运行，它还要等 CPU 有机会安排它。

FreeRTOS 自己的 `task.h` 也说明，`vTaskDelay` 是相对调用时刻进行等待的接口，任务代码执行时间和其他任务、中断会影响周期；它还提供了适合固定周期调度的 `vTaskDelayUntil`。可查看项目中的 [task.h](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/Middlewares/Third_Party/FreeRTOS/Source/include/task.h:714>)。

## 3. 那 `osDelay(1)` 又是什么？

它是另一层接口，来自 CMSIS-RTOS。可以先这样区分：

| 函数 | 参数通常表示 | 在本项目里的作用 |
|---|---|---|
| `vTaskDelay(n)` | 等待 `n` 个 FreeRTOS tick | 直接使用 FreeRTOS 的 tick 数 |
| `osDelay(n)` | 请求等待 `n` 毫秒 | CMSIS 接口再把毫秒换成 tick |

本项目使用的 `osDelay` 实现，会把传入的毫秒数除以每个 tick 的毫秒数，再调用 `vTaskDelay`。如果换算结果不到一个 tick，至少等待一个 tick。实现见 [cmsis_os.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/Middlewares/Third_Party/FreeRTOS/Source/CMSIS_RTOS/cmsis_os.c:322>)。

当前配置下：

- 每个 tick 名义上是 1 ms；
- 所以 `osDelay(1)` 会换成约 1 个 tick；
- 在这份项目配置中，`osDelay(1)` 和 `vTaskDelay(1)` 最终效果接近。

但要注意，它们的**接口单位不一样**。假设另一个系统每 10 ms 才有一个 tick，那么 `osDelay(1)` 请求的 1 ms 无法用完整 tick 表示，按这类实现至少会等 1 个 tick，也就是约 10 ms。不能看到 `osDelay(1)` 就脱离系统配置地断言“正好 1 ms”。

## 4. 控制周期到底是什么？

先规定我们在量什么。这里把一次控制周期定义为：

> **控制任务连续两次开始计算之间的时间。**

如果第 \(k\) 次开始时刻是 \(t_k\)，下一次是 \(t_{k+1}\)，那么：

\[
T_k=t_{k+1}-t_k
\]

频率是每秒执行多少次：

\[
f_k=\frac{1}{T_k}
\]

例如实测两次循环开始相差 0.003 秒：

\[
T=0.003\text{ s}=3\text{ ms}
\]

\[
f=\frac{1}{0.003}\approx333\text{ Hz}
\]

这说的是这个控制任务大约每秒计算 333 次。

**周期不是由 `vTaskDelay(1)` 单独决定的。**周期还受计算时间、代码中其他等待、任务被推迟运行等因素影响。

## 5. 为什么不能简单算“计算 0.4 ms + 等待 1 ms = 周期 1.4 ms”？

因为 `vTaskDelay(1)` 不是从调用那一刻开始完整睡眠 1 ms。

假设：

- 系统 tick 在 `0 ms` 和 `1 ms` 发生；
- 任务刚好在 `0 ms` 的 tick 后开始运行；
- 它做完控制计算花了 `0.4 ms`；
- 它在 `0.4 ms` 调用 `vTaskDelay(1)`。

这时当前 tick 计数还是 `0 ms` 对应的那一格。任务等到下一个 tick，也就是 `1 ms`，就可以重新进入就绪状态。

```text
时间： 0 ms       0.4 ms               1 ms
tick：  |------------------------------|
任务：  开始计算----计算完、delay 等待---恢复运行
```

从 `0 ms` 开始到 `1 ms` 恢复，间隔约 1 ms，而不是 \(0.4+1=1.4\) ms。

如果任务是在 `0.99 ms` 才调用 `vTaskDelay(1)`，它到 `1 ms` 就可能恢复，等待时间约 0.01 ms。这就是为什么必须把 tick 的位置考虑进去。

更准确的关系是：

\[
\text{周期}
=
\text{这一轮执行所用时间}
+
\text{实际等到 tick 的时间}
+
\text{恢复后等待 CPU 的时间}
\]

其中“实际等到 tick 的时间”会受调用时刻影响，“恢复后等待 CPU 的时间”会受优先级和其他任务影响。

## 7. FreeRTOS 和控制周期是什么关系？

FreeRTOS 提供任务运行和等待的机制，但它不会自动替控制器选好周期。

一轮控制任务通常像这样：

```text
任务开始
  ↓
读反馈
  ↓
计算控制量
  ↓
发送电机命令
  ↓
等待、被抢占，或等待某个事件
  ↓
下一轮任务开始
```

FreeRTOS 影响了“等待多久”和“什么时候重新获得 CPU”。控制算法决定“醒来后计算什么”。电机和传感器则有自己的通信和数据更新节奏。

所以至少要区分四个时间：

| 时间 | 它回答什么问题 |
|---|---|
| 控制任务周期 | 控制程序多久重新计算一次？ |
| 传感器更新周期 | 新反馈多久产生或到达一次？ |
| 命令发送周期 | 控制命令多久发一次？ |
| 反馈到命令的延迟 | 从收到一份反馈到新命令发出，经过多久？ |

它们不一定相等。比如控制任务每 3 ms 运行一次，但电机反馈可能在任务两次运行之间到达；也可能任务运行时读到的仍是上一帧数据。

## 8. `vTaskDelay` 和固定周期等待有什么差别？

### `vTaskDelay`

它是相对等待：**执行到这一行后，等待指定 tick 数对应的唤醒时刻。**

如果每轮工作时间有变化，下一轮开始时刻也会跟着变化。它适合“做完后稍微等一下”，但不适合单靠它保证稳定的固定频率。

### `vTaskDelayUntil`

它按一个绝对的计划时间表唤醒。可以把它想成先定好：

```text
计划开始时间：0 ms、3 ms、6 ms、9 ms……
```

每轮结束后，它等待下一个计划时刻，而不是再额外等一个相对时间。这样通常能减少“工作时间逐轮累加进周期”的漂移。

不过，如果任务计算太久，错过了计划时刻，`vTaskDelayUntil` 也不能让它回到过去补算；它只能按 FreeRTOS 的规则处理已经错过的唤醒时刻。因此依然要测执行时间和是否超期。

## 9. 实际周期应该怎么测？

真正要回答“它实际每几毫秒控制一次”，需要记录任务运行时间。

最简单的测法是：在控制计算的固定入口处，记下每次开始的高精度时间 \(t_k\)，然后计算：

\[
T_k=t_{k+1}-t_k
\]

还要记下单轮计算完成时刻 \(t_{\text{end},k}\)，计算执行时间：

\[
C_k=t_{\text{end},k}-t_k
\]

之后至少看：

- 平均周期；
- 最短和最长周期；
- 周期抖动，也就是周期忽长忽短的程度；
- 单轮最长执行时间；
- 从反馈接收时刻到新命令发出时刻的延迟；
- 是否出现某轮计算超时。

可以使用 MCU 的高精度计时器，或短暂翻转一个 GPIO，再用逻辑分析仪观察脉冲时间。不要在高频任务里不断 `printf` 测量，因为打印本身可能拖慢任务、改变被测周期。

## 最后把概念连起来

- `configTICK_RATE_HZ=1000`：系统每秒产生 1000 个 tick，名义上每 tick 1 ms。
- `vTaskDelay(1)`：等待 tick 计数增加一次；不等于从当前时刻起精确睡眠 1 ms。
- `osDelay(1)`：请求等待 1 ms，再由本项目的 CMSIS 封装换算成 tick；本项目配置下通常对应 1 tick。
- 控制周期：两次控制计算开始之间的实际时间。
- 项目代码中云台和底盘各有三处一 tick 延时；约 3 ms 是有条件的粗略估算，**实际周期必须测量**。
- FreeRTOS 影响任务何时等待、何时运行；传感器更新和电机命令也各有自己的节奏。不能把它们统称为一个“1 ms 控制周期”。
````

````text
# `vTaskDelayUntil` 和任务控制频率

先抓住一个最关键的区别：

> **控制频率是“控制程序实际多久计算一次”；FreeRTOS 的延时函数只是帮助任务安排下一次运行时间。**

FreeRTOS 能安排任务何时变成“可以运行”，但不保证它变成就绪后立刻拿到 CPU。因此要分清：

1. **计划周期**：代码希望任务每隔多久运行；
2. **实际周期**：任务真实两次开始计算之间隔了多久；
3. **运行频率**：根据实际周期算出的每秒计算次数。

## 1. `vTaskDelayUntil` 是按时刻表运行

假设控制任务希望每 3 ms 运行一次。理想的开始时刻是：

```text
0 ms、3 ms、6 ms、9 ms、12 ms……
```

这相当于预先列了一张时刻表。上一轮计划的开始时刻是 3 ms，下一轮就计划在：

\[
3+3=6\text{ ms}
\]

运行。

`vTaskDelayUntil` 的核心是：

> 下一次计划唤醒时间 = 上一次计划唤醒时间 + 周期

而 `vTaskDelay` 的核心是：

> 从现在开始，按相对时间等待一段时间。

这使 `vTaskDelayUntil` 更适合“我希望每 3 ms 做一轮控制”这种任务。

### 一个常见写法

```c
void GimbalTask(void *argument)
{
    TickType_t last_wake = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(3);

    for (;;)
    {
        ReadFeedback();
        CalculateControl();
        SendMotorCommand();

        vTaskDelayUntil(&last_wake, period);
    }
}
```

这段代码的意思是：

- `last_wake`：记录上一轮计划唤醒时刻；
- `period`：周期是多少个 tick；
- 每轮结束时，FreeRTOS 把下一次计划时刻往后推一个 `period`；
- 如果离计划时刻还早，任务等待到那个时刻；
- 到计划时刻后，任务变成就绪状态，等待 CPU 调度。

在本项目中，每秒有 1000 个 tick，所以每 tick 名义上是 1 ms。3 ms 就是 3 个 tick，因此：

```c
pdMS_TO_TICKS(3)
```

在这份配置下对应 3 个 tick。

`vTaskDelayUntil` 使用的计划时刻和行为，可以在项目 FreeRTOS 的 [task.h](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/Middlewares/Third_Party/FreeRTOS/Source/include/task.h:780>) 和 [tasks.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/Middlewares/Third_Party/FreeRTOS/Source/tasks.c:1257>) 里看到。

## 2. 为什么 `last_wake` 要一直保存？

它是时刻表的“上一次计划时间”。

比如周期是 3 ms：

```text
last_wake = 0 ms
下一次计划 = 0 + 3 = 3 ms
再下一次计划 = 3 + 3 = 6 ms
再下一次计划 = 6 + 3 = 9 ms
```

所以 `last_wake` 要在循环外初始化一次，之后交给 `vTaskDelayUntil` 持续更新。

如果每一轮都重新执行：

```c
last_wake = xTaskGetTickCount();
```

就会把时刻表每轮重置到“现在”，失去稳定的周期基准。这样做会更像每轮按当前时间重新安排，失去 `vTaskDelayUntil` 防止周期逐轮漂移的主要好处。

## 3. 用数字比较两种延时

假设任务计划每 3 ms 开始一次，执行控制计算花 0.8 ms。

### 使用 `vTaskDelay`

```c
for (;;)
{
    DoControl();       // 花约 0.8 ms
    vTaskDelay(3);     // 从这里开始按相对方式等 3 个 tick
}
```

这里是“工作完成后，再等 3 个 tick”。周期会包含工作时间和等待时间，粗略可能是：

\[
0.8\text{ ms}+约3\text{ ms}
\]

也就是约 3.8 ms，具体还受 tick 相位和调度影响。每轮工作时间稍有变化，下一轮开始时刻也会跟着变化。

### 使用 `vTaskDelayUntil`

```c
for (;;)
{
    DoControl();                        // 花约 0.8 ms
    vTaskDelayUntil(&last_wake, period); // 等到原时刻表上的下一次计划时刻
}
```

如果上一轮计划在 0 ms 开始，下一轮计划在 3 ms 开始，那么程序只需要等到 3 ms；它不会在 0.8 ms 工作结束后再额外等完整 3 ms。

```text
计划开始：0 ms                         3 ms
任务工作：|----约0.8 ms----|
任务等待：                  |--约2.2 ms--|
下一轮：                                  ↑
```

这就是它能避免“工作时间再加上完整等待时间”的原因。

## 4. 如果任务计算超过周期，会怎样？

周期设成 3 ms，计划在 3 ms 开始下一轮。但上一轮控制计算花了 3.4 ms：

```text
计划开始：0 ms             下一轮计划：3 ms
实际工作：|--------------------3.4 ms--------------------|
```

到 3 ms 时任务还没完成。FreeRTOS 不可能让它回到过去准时开始。它完成后再调用 `vTaskDelayUntil`，发现计划的 3 ms 已经过了，就不会再等待一个负时间；下一轮会晚开始。

这叫**超期**：任务没能在预定周期内完成本轮工作。

`vTaskDelayUntil` 可以减少正常情况下的周期漂移，但不能：

- 缩短控制计算本身；
- 抢走其他任务正在使用的 CPU；
- 让超期任务准时完成；
- 保证唤醒时任务立刻运行。

如果任务经常超期，就要减少它每轮的工作量、降低计划频率、优化中断和任务安排，或重新分配处理工作。

## 5. FreeRTOS 的 tick 会限制时间精度

`vTaskDelayUntil` 的时间表按 tick 计数，所以它的时间刻度不能比 tick 更细。

本项目的配置是 1000 tick/s，因此：

\[
1\text{ tick}\approx1\text{ ms}
\]

可以安排 1 ms、2 ms、3 ms 这样的 tick 周期。它不能仅凭这个 tick 机制可靠地安排“每 0.2 ms 精确运行一次”。

提高 tick 频率可以缩小调度刻度，但 tick 越频繁，系统处理中断和调度的开销也越大。高频控制也可能使用硬件定时器或数据就绪中断来唤醒任务。那是另一种唤醒来源，不能把它和 `vTaskDelayUntil` 的 tick 周期混成一回事。

## 6. 控制频率应该依据什么选择？

控制频率不是由 FreeRTOS 替你决定的。通常要同时看四件事。

### 6.1 机器人动作变化有多快？

如果云台运动很快，控制器就需要及时看到角度和速度的变化，并及时改变电机命令。控制周期太长，控制器看到的会是较旧状态，纠正动作也来得较晚。

一个直观判断方法是看动作变化的时间尺度。假设系统一次重要的变化大约要 30 ms：

- 每 10 ms 控制一次，约有 3 次更新；
- 每 3 ms 控制一次，约有 10 次更新。

后者能更细地观察和纠正运动，但 CPU 每秒要计算更多次。这个比较只是帮助理解“周期长短的影响”，不是说 3 ms 必定适合任何云台。

工程上会先根据系统最快的动态变化或控制带宽确定候选周期，再用仿真和实验检查效果；不存在所有机器人都适用的唯一频率。

### 6.2 新反馈多久到一次？

如果控制任务 1 ms 算一次，但电机新反馈 5 ms 才到一次，任务中间几次可能读到相同的旧反馈。

这并非绝对不能这样设计，但更高的计算频率不会自动带来新的传感器信息。要分清：

- 电机实际多久发一帧反馈；
- CAN 中断多久收到一帧；
- 控制任务多久读取和计算一次；
- 命令多久发送一次。

传感器更新、控制计算和命令发送的频率可能不同。

### 6.3 电机和通信能不能跟上？

控制板即使很快算出命令，电机驱动器和 CAN 通信也需要时间。如果控制计算频率远高于命令接口能够接受的速度，可能只是反复覆盖命令，或者增加通信负担。

所以要看电机驱动器的控制接口、CAN 总线负载、命令更新方式和反馈频率。

### 6.4 CPU 能不能按时做完所有任务？

任务频率越高，一秒内要做的计算就越多。可以先做一个 CPU 时间预算：

\[
\text{某任务 CPU 占用比例}
\approx
\frac{\text{每轮执行时间}}{\text{任务周期}}
\]

例如，一个任务每轮最坏要花 0.6 ms，计划周期是 3 ms，那么它大约使用：

\[
0.6/3=0.2=20\%
\]

的 CPU 时间。多个任务的占用还要加起来，并给中断、任务切换和偶发工作留空间。

这只是第一步估算。总占用低于 100% 也不能单独证明系统一定准时，因为任务优先级、临界区、阻塞和中断也会影响响应时间。做实时设计时，应该测**最长执行时间**和**最坏情况下能否赶上截止时间**，不能只用平均时间。

## 7. 不同任务为什么会用不同频率？

因为每个任务做的事不同、数据来源不同、变化速度也不同。

| 任务类型 | 频率主要看什么 |
|---|---|
| IMU 姿态处理 | IMU 的数据产生速度、数据就绪通知和处理时间 |
| 云台闭环 | 云台运动速度、反馈速度、电机命令接口和 CPU 预算 |
| 底盘闭环 | 轮速反馈、底盘响应速度、CAN 命令和 CPU 预算 |
| USB/通信解析 | 数据到达速度、通信延迟要求、缓冲区大小 |
| UI、指示灯等 | 显示变化速度，通常不必和快速控制环一样快 |

同一套控制器里也可能有多个控制环，但**不要只凭“外环、内环”这两个名字就假定它们运行在不同频率**。只有代码把它们拆到不同任务、不同定时器，或明确按不同周期调用时，频率才不同。

在 P3 这份源码里，云台控制函数在 `Gimbal_task` 中运行；若角度和速度控制都由这个循环调用，它们就随同一个任务循环一起计算。是否有别的独立驱动器内环，需要看电机驱动器内部实现，不能从 FreeRTOS 的云台任务优先级推断。

## 8. P3 这份代码能给出什么频率结论？

从本地源码快照可以确认：

- 系统 tick 配置为 1000 tick/s；
- 云台 `GIMBAL_PERIOD` 是 1；
- 底盘 `CHASSIS_PERIOD` 是 1；
- 两个任务用的是 `vTaskDelay`，不是 `vTaskDelayUntil`；
- 每个循环还会在数据发送函数中遇到两次延时，循环末尾另有一次延时；
- `INS_task` 等待 IMU 相关通知，属于事件唤醒路径，不能简单按 `vTaskDelay(1)` 推算它的周期。

所以，不能把 `GIMBAL_PERIOD=1` 直接解释成“云台实际控制频率是 1 kHz”。根据代码中的三个一 tick 等待，可以做一个**有条件的粗略估算**：如果各段工作都能在一个 tick 内完成，而且没有额外调度延迟，云台和底盘循环的间隔量级可能接近 3 ms，即约 333 Hz。但这不是实测值，也不是 FreeRTOS 保证值。

## 9. 怎样得到真实的任务控制频率？

在控制任务每轮**同一个位置**记录开始时刻：

\[
T_k=t_{k+1}-t_k
\]

例如采到的开始时刻差是：

```text
3.02 ms、3.01 ms、5.07 ms、3.03 ms
```

前三次接近 3 ms，但其中有一次明显拖长。若只报平均值，会掩盖这种延迟，所以至少要统计：

- 平均周期；
- 最短周期和最长周期；
- 周期变化幅度；
- 控制计算的最长执行时间；
- 反馈数据到电机命令的最长延迟；
- 超过计划周期的次数。

可以用高精度定时器或硬件计时器记录这些时间；把数据暂存起来，再由低优先级任务输出。不要在高频控制任务中大量打印，因为打印会占用 CPU，改变本来要测的周期。

## 最后用一句话记忆

- `vTaskDelay(n)`：**从现在起等待若干 tick**，适合相对等待。
- `vTaskDelayUntil(&last, period)`：**按上一次计划时刻加周期，等待下一次计划时刻**，适合周期任务。
- 两者都受 tick 精度和调度影响。
- 控制频率先依据机器人变化速度、反馈更新、执行器接口和 CPU 时间预算来设计，再用时间戳测量实际频率。
````

````text
# P3 第二章：云台角度环、速度环和视觉目标

第二章讲云台怎样“转到一个方向并稳住”，以及遥控器和视觉系统都能给目标时，程序怎样选目标。

先记一条主线：

> **先选“看哪里”，再看“实际指向哪里”；角度环把角度差变成转速要求，速度环再把转速差变成电机命令。**

```text
遥控器目标 ─┐
            ├─ 按当前模式选一个目标角度
视觉目标 ───┘
                         ↓
当前角度 ─────────→ 角度环：还差多少角度？
                         ↓
                  希望云台以多快速度转
                         ↓
IMU 测得的转速 ──→ 速度环：实际转速和希望值差多少？
                         ↓
                   电机电流命令
                         ↓
                云台转动、反馈再回来
```

这里的“外层”和“内层”不是两个不同的云台。它们是同一台云台上的两步控制计算。

## 1. 为什么云台需要两层控制？

假设要让云台转到 \(30^\circ\)。

如果只看角度，控制器知道当前还差多少，却不知道云台此刻转得有多快。比如云台已经快到 \(30^\circ\)，但它仍然高速向前转。如果控制器只盯着“角度还没到”，继续往前推，就容易冲过目标。

因此控制器要分两步：

1. **角度环**：比较目标角度和当前角度，算出希望的转动速度。
2. **速度环**：比较希望的转速和实际转速，算出电机命令。

角度环输出的是“希望以多快速度转”，不是电机电流，也不是力矩。速度环输出的才是送给电机的控制命令。

## 2. 用一个数字例子看两层怎样接力

为了先看清原理，暂时只用比例控制，忽略积分、微分和限幅。下面的增益是**教学数字，不是项目实测参数**。

假设：

- 目标角度：\(30^\circ\)
- 当前角度：\(20^\circ\)
- 角度环增益：\(4\ \text{s}^{-1}\)

角度还差：

\[
30^\circ-20^\circ=10^\circ
\]

角度环根据这 \(10^\circ\) 的误差给出希望转速：

\[
\omega^*=4\times10^\circ=40^\circ/\text{s}
\]

意思是：**现在角度差比较大，希望云台转快一些。**

接着假设 IMU 测到云台已经以 \(25^\circ/\text{s}\) 向目标方向转动，速度环希望让它达到 \(40^\circ/\text{s}\)。速度误差是：

\[
40-25=15^\circ/\text{s}
\]

如果教学用的速度环增益是 \(0.8\)，那么电机命令可以简化写成：

\[
u=0.8\times15=12
\]

这个 \(u=12\) 是教学例子中的控制输出。实际项目里的 `give_current` 是电机协议命令值，不能仅凭这个例子就把 12 说成 12 安培或某个力矩。

现在云台已经接近目标：

- 目标仍是 \(30^\circ\)
- 当前到了 \(29^\circ\)
- 角度环仍用 \(4\ \text{s}^{-1}\)

角度环给出的希望转速变成：

\[
\omega^*=4\times(30-29)=4^\circ/\text{s}
\]

但假设云台此刻还在以 \(20^\circ/\text{s}\) 向前转。速度误差是：

\[
4-20=-16^\circ/\text{s}
\]

速度环就会给出反方向的控制动作，减慢云台。**这时云台还没到目标角度，速度环已经开始制动了。**

所以两层各自回答的问题不同：

- 角度环：“离目标还差多少？现在希望转多快？”
- 速度环：“实际转得比希望快还是慢？电机该怎样出力？”

## 3. 目标角度从哪里来？

云台目标可以由不同输入来源产生，例如遥控器或视觉系统。关键是程序要根据当前模式决定使用哪个来源。

### 遥控模式：摇杆在逐步改变目标角度

这个项目的遥控逻辑不是简单地说“摇杆位置就是云台最终角度”。它会把摇杆和鼠标的输入变成目标角度的变化量，然后更新目标。

可以把它想成：

```text
摇杆保持向右
  ↓
每个控制周期都把 yaw 目标往一个方向推一点
  ↓
目标方向持续改变
  ↓
云台追着这个目标转
```

所以摇杆更像是在控制“目标角度往哪个方向移动”。代码还对鼠标输入做了滤波，并限制 pitch 目标范围；yaw 目标则会在角度边界处绕回。相关实现可看 [Gimbal_Active_Handle](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:403>)。

这一点也和上一章讲的任务周期有关：如果每轮都按固定量更新目标角度，却不乘实际经过的时间，那么目标每秒移动多少会受循环运行次数影响。源码里的换算常量需要结合它原先假定的任务周期理解；任务周期变化时，遥控手感也可能变化。

### 自动模式：视觉给目标角度

自动模式下，云台读取视觉相关数据中的 `robot_ctrl.pitch` 和 `robot_ctrl.yaw`，把它们作为自动瞄准的目标角度，再交给同一套角度环和速度环处理。

这意味着视觉系统提供的是“希望云台看向哪里”的目标；它不会直接替代云台的电机控制。云台仍然需要读取自己的角度和转速，再算电机命令。

### 模式仲裁：同一时刻用哪个目标？

遥控器和视觉都可能有目标，但不能不加规则地把两个目标混在一起。源码通过云台模式决定执行哪条路径：

- `GIMBAL_RELAX`：云台失能处理；
- `GIMBAL_ACTIVE`：采用遥控输入更新目标；
- `GIMBAL_AUTO`：采用视觉目标更新目标。

自动模式需要满足代码中的视觉状态条件。如果视觉检测被判为离线或目标状态不满足条件，代码会退回 `GIMBAL_ACTIVE`。具体条件见 [Gimbal_Mode_Set 和 Gimbal_Control](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:312>)。

所以“仲裁”可以先理解成：

> **当前由谁决定目标角度：遥控器，还是视觉系统？**

它不是两个人同时把云台往不同方向推。

## 4. yaw 为什么要把角度绕回 \([-180^\circ,180^\circ]\)？

角度是绕一圈会回到原处的量。\(180^\circ\) 和 \(-180^\circ\) 指向同一个方向附近。

假设当前角度是 \(-179^\circ\)，目标是 \(+179^\circ\)。直接相减：

\[
179-(-179)=358^\circ
\]

看上去像要转 \(358^\circ\)，但沿着更短的方向只要转 \(-2^\circ\)：从 \(-179^\circ\) 往负方向转 \(2^\circ\)，就到达与 \(+179^\circ\) 等价的方向。

代码里的 `pid_loop_calc` 会考虑角度范围的绕回，让角度环选择较短的误差方向。普通的“目标减当前”在角度边界附近会给出错误的大误差。

## 5. 为什么视觉 yaw 先滤波 `sin` 和 `cos`，再还原角度？

直接对角度数字做平均，在边界处会出错。

例如两个相邻方向：

\[
179^\circ,\qquad -179^\circ
\]

它们实际上都指向接近“正后方”。直接平均会得到：

\[
\frac{179+(-179)}{2}=0^\circ
\]

但 \(0^\circ\) 是另一个方向，平均结果错了。

解决办法是先把角度变成单位圆上的坐标：

\[
(\sin\theta,\cos\theta)
\]

对这两个数分别滤波，再用 `atan2` 还原角度。

对 \(179^\circ\)：

\[
\sin179^\circ\approx0.017,\qquad \cos179^\circ\approx-1
\]

对 \(-179^\circ\)：

\[
\sin(-179^\circ)\approx-0.017,\qquad \cos(-179^\circ)\approx-1
\]

两组数的平均大约是：

\[
\sin\approx0,\qquad \cos\approx-1
\]

这个点仍然在单位圆左侧，代表约 \(180^\circ\)，而不是 \(0^\circ\)。所以代码把视觉 yaw 拆成正弦和余弦分别滤波，再通过：

\[
\theta=\operatorname{atan2}(\sin\theta,\cos\theta)
\]

还原角度。这里的 `atan2` 是根据正弦、余弦对应的圆上位置找回角度，不是任意对角度做平均。实现可看 [Gimbal_Auto_Handle](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:495>)。

## 6. 当前角度和当前角速度从哪里来？

角度环需要“当前角度”，速度环需要“当前转速”。它们可以来自不同传感器。

### 当前角度

源码中的 `Gimbal_Angle_Update` 使用 IMU 姿态计算 yaw 和 pitch 角度，并把弧度换算为角度显示。电机编码器角度也会计算，但控制所用的角度量要看具体是哪一个轴、哪一个变量。

代码中尤其要留意 pitch：

\[
\texttt{pitch.relative\_up\_down\_get}
=
\texttt{pitch.absolute\_angle\_get}
+
\texttt{pitch.absolute\_angle\_get\_down}
\]

第二项来自底盘板通过板间 CAN 发送的 pitch 数据。因此这个 pitch 反馈是代码组合出来的量，不能简单把变量名里的 `relative` 直接理解成“只由 pitch 电机编码器得到的相对角”。源码计算可看 [Gimbal_Angle_Update](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:186>)。

理解绝对角和相对角时可以想象：底盘转了，但云台还想继续指向房间里的同一个方向。相对底盘的角度可能变化，指向房间的绝对方向则可能保持不变。程序必须让目标角和当前角用同一种参考方式，否则就会拿两种不同含义的角度相减。

### 当前角速度

当前角速度来自 IMU 陀螺仪。源码根据轴的安装和符号约定，从 `INS_gyro` 取 yaw、pitch 对应分量，并进行滤波，再交给速度环。代码可看 [Gimbal_Ctrl_Loop_Cal](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:460>)。

代码还把角速度从弧度相关单位换成角度相关单位，所以看数值时要检查：

- 当前角度是度还是弧度；
- 当前角速度是度/秒还是弧度/秒；
- 目标角度和反馈角度是否使用同一种单位；
- 陀螺仪轴方向是否与云台电机正方向一致。

如果一边是度，另一边是弧度，数值就不能直接相减或比较。

## 7. 从误差到电机命令，代码里每步是什么？

源码的 PID 计算函数使用：

\[
\text{误差}=\text{目标值}-\text{当前值}
\]

因此云台控制链可以读成：

### yaw 轴

1. 角度环比较 yaw 目标角和当前绝对 yaw 角；
2. `pid_loop_calc` 处理 \(\pm180^\circ\) 的边界，算出 `gyro_set`；
3. `gyro_set` 是期望 yaw 角速度；
4. yaw 陀螺仪角速度经过滤波；
5. 速度环比较期望角速度和滤波后的实测角速度；
6. 速度环输出 yaw 的 `give_current`。

### pitch 轴

1. 角度环比较 pitch 目标和 `relative_up_down_get`；
2. 角度环给出 pitch 的期望角速度 `gyro_set`；
3. pitch 陀螺仪角速度经过滤波；
4. 速度环比较期望角速度和实测角速度；
5. 速度环输出 pitch 电机命令；
6. 代码对 pitch 的输出额外取负号，以匹配该轴的方向约定。

源码中的 PID 函数把比例、积分、微分项相加，再限制积分量和总输出。其离散实现没有显式把积分乘控制周期、也没有把微分除以控制周期；这表示参数和运行周期有联系，不能改了任务周期后仍默认控制效果不变。参见 [PID.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/controller/PID.c:69>)。

最后，`give_current` 被打包进 CAN 电机命令。电机实际运动后，新编码器、IMU 角度和陀螺角速度再进入下一轮反馈。这里速度环的输出是电机协议命令值，不应不经协议换算就称为物理力矩或安培。

```text
遥控输入或视觉目标
        ↓
模式判断：当前信遥控还是信视觉？
        ↓
得到 yaw、pitch 目标角
        ↓
读取 IMU 角度和陀螺角速度
        ↓
角度环：角度误差 → 期望角速度 gyro_set
        ↓
滤波后的角速度环：角速度误差 → give_current
        ↓
CAN 发送给电机
        ↓

```

1. **角度环的输出 `gyro_set` 是期望角速度，不是电机命令。**
2. **速度环使用陀螺仪测得的角速度来调速，输出才是 `give_current`。**
3. **遥控和视觉是两种目标来源，程序按模式选择；yaw 还要处理 \(+180^\circ/-180^\circ\) 的绕回问题。**
````

````text
# 先回答最关键的问题：SPI + DMA 读到的是四元数吗？

**不是。**

这个项目使用的 BMI088 IMU 提供的是陀螺仪和加速度计的测量值：

- **陀螺仪**：测 IMU 此刻绕三个轴转得多快；
- **加速度计**：测 IMU 此刻沿三个轴受到的加速度，其中通常也包含重力影响。

它们最初是传感器寄存器里的数字读数。驱动程序把读数换算成有物理单位的数据后，程序再用姿态解算计算四元数和角度。

```text
BMI088 传感器
  ├─ 陀螺仪原始读数 ─→ 角速度
  └─ 加速度计原始读数 ─→ 加速度
                              ↓
                 校正安装方向、滤波
                              ↓
                      姿态解算 AHRS
                        ├─ 四元数 INS_quat
                        └─ 欧拉角 INS_angle
```

所以：

> **SPI + DMA 负责把传感器的数据搬进控制板；它不负责把这些数据变成四元数。四元数是后续姿态解算算出来的。**

## 1. IMU 原始数据是什么？

可以把 IMU 想成一个“测转动的小设备”和一个“测受力的小设备”装在一起。

### 1.1 陀螺仪测转动速度

陀螺仪测的是角速度，比如：

\[
\omega=0.2\text{ rad/s}
\]

意思是 IMU 当前大约每秒转 \(0.2\) 弧度。它测的是“现在转多快”，不是“现在角度是多少”。

把角速度乘经过的时间，可以近似得到这一小段时间转过的角度：

\[
\Delta\theta\approx\omega\Delta t
\]

例如，角速度为 \(0.2\text{ rad/s}\)，经过 \(0.01\text{ s}\)：

\[
\Delta\theta\approx0.2\times0.01=0.002\text{ rad}
\]

陀螺仪对快速转动很敏感，但如果它有一点零点偏差，长时间累加就会逐渐漂移。

### 1.2 加速度计测受力

加速度计测三个方向上的加速度或比力。机器人静止时，它仍然会感受到重力，因此读数不一定是零。

姿态解算可以利用“重力大致朝下”这一事实，帮助判断 IMU 是否倾斜。机器人快速加速、刹车或受到冲击时，加速度计读数还会包含运动造成的加速度，这时它就不能单独当成可靠的倾角。

因此程序会把陀螺仪和加速度计的信息结合起来，估计当前姿态。

## 2. SPI 和 DMA 分别在做什么？

### 2.1 SPI：控制板和 IMU 之间的通信方式

SPI 是控制板读取 BMI088 内部寄存器的一种通信方式。控制板发出读取请求，IMU 把寄存器中的数字读数按字节传回来。

传回来的内容仍是传感器测量值，例如陀螺仪和加速度计的各轴读数。**这一步还没有得到云台的 yaw、pitch 或四元数。**

### 2.2 DMA：帮 CPU 搬运数据

如果没有 DMA，CPU 可能需要自己逐个处理传输中的字节。使用 DMA 后，可以先让 DMA 按设置搬运 SPI 数据；搬运完成后，再通过中断或通知告诉任务：“数据准备好了。”

可以把它想成：

```text
SPI：数据通过哪条通信线路进来
DMA：谁负责把数据搬到内存
CPU 中的 INS 任务：拿到数据后做校正和姿态计算
```

这个项目的 `INS_task` 会等待任务通知；得到通知后处理传感器数据。它把陀螺仪、加速度计数据放进姿态解算流程，并更新姿态结果。见 [Atti.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Communication/Atti.c:215>)。

## 3. 原始读数怎样变成角速度、姿态和四元数？

按源码中的处理步骤，可以这样理解：

### 第一步：从 BMI088 读传感器数据

驱动程序从 BMI088 读出陀螺仪和加速度计读数，转换成程序使用的数据数组。

### 第二步：校正传感器安装方向和偏差

IMU 不一定正好按机器人定义的前、左、上方向安装。源码用安装方向矩阵重排、改变部分轴的符号，并处理传感器偏差。这样得到的 `INS_gyro`、`INS_accel` 才是程序后续使用的各轴数据。

不过，“矩阵做了轴变换”不等于我们已经仅凭代码知道了机械上的每个正方向。还需要结合 IMU 实际安装方向、轴标记和运动时的测量结果确认。

### 第三步：滤波加速度数据

源码对加速度计数据做低通滤波，再送入姿态解算。滤波可以压低快速抖动，但会让数据稍微滞后。

### 第四步：姿态解算

姿态解算程序把陀螺仪、加速度计等信息结合起来，更新姿态四元数 `INS_quat`。

四元数是**程序算出来的整体朝向表示**，不是 BMI088 通过 SPI 直接吐出的原始数据。

### 第五步：把四元数转成角度

源码调用 `get_angle`，从四元数计算 yaw、pitch、roll，放到 `INS_angle`。姿态角的单位是弧度。`get_angle` 的计算在 [AHRS.c](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/algorithm/AHRS.c:200>)。

这几个变量可以先这样区分：

| 变量 | 表示什么 | 单位或形式 |
|---|---|---|
| `INS_gyro` | IMU 当前各轴角速度 | rad/s |
| `INS_accel` | IMU 当前各轴加速度数据 | m/s² |
| `INS_quat` | 解算得到的整体姿态 | 四元数，4 个数 |
| `INS_angle` | 从姿态换算出的 yaw、pitch、roll | rad |

四元数和角度描述的是姿态；陀螺仪数据描述的是转动速度。它们不是同一种量。

## 4. 角度环中用的“当前角度”是什么？

角度环要比较目标角度和当前角度：

\[
\text{角度误差}=\text{目标角度}-\text{当前角度}
\]

但“当前角度”可以有不同来源，也可能相对不同的东西描述。

### 4.1 电机编码器角度：电机或云台关节相对转了多少

编码器测电机转子现在在什么位置。扣除校准偏移后，可以得到它相对某个机械零点转了多少角度。

这更像是：

> 云台的机械关节相对底座转了多少？

它不是自动等于云台相对房间的朝向。底座如果转了，云台相对底座的角度和云台相对房间的角度可能不同。

### 4.2 IMU 姿态角：IMU 所在组件当前是什么朝向

姿态解算得到的角度描述 IMU 的姿态。它不是电机转子编码器读数。

“绝对角度”在这里应理解为“不是直接用电机相对零位表示的角度”。它不自动代表已经校准到地理真北，也不保证永远没有漂移；实际参考方向取决于姿态解算的初始化、传感器校准和磁力计使用情况。

### 4.3 底座转动的例子

假设底座朝房间方向转了 \(40^\circ\)，云台关节相对底座转了 \(10^\circ\)。在符号方向一致的简化情况下，云台相对房间的方向约为：

\[
40^\circ+10^\circ=50^\circ
\]

如果目标是让云台继续指向房间里的 \(50^\circ\)，底座再转 \(10^\circ\) 后，云台相对底座的关节角就需要减到约 \(0^\circ\)。因此“云台相对底座转了多少”和“云台相对房间指向哪里”是不同的问题。

## 7. 当前角速度为什么用陀螺仪，而不只用电机编码器？

电机编码器可以用相邻位置变化估计电机转速；陀螺仪则直接测它所在组件的角速度。两者回答的问题不同：

- **编码器**：电机转子相对电机自身转了多少、转多快；
- **陀螺仪**：IMU 所在组件绕各轴实际转得多快。

当机器人底座也在转动时，IMU 感受到的组件转动可能包含底座运动。编码器只知道电机相对自身机械结构的转动，不会单独知道整个组件相对房间的运动。

这份云台控制代码把 `INS_gyro` 转成角度/秒、滤波后交给速度环；某些位置还留有使用电机 `speed_rpm` 的注释，但目前控制表达式使用的是陀螺仪角速度。可看 [Gimbal_Ctrl_Loop_Cal](<F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/Gimbal.c:460>)。

## 8. 从目标角度到电机命令：一步一步看

以 yaw 轴为例。假设：

- 当前 yaw 角：\(20^\circ\)；
- 目标 yaw 角：\(30^\circ\)。

### 第一步：角度环计算“还差多少”

\[
30^\circ-20^\circ=10^\circ
\]

yaw 还差 \(10^\circ\)。

如果角度误差是在 \(+180^\circ/-180^\circ\) 附近，还要先换成最短方向的误差。例如从 \(-179^\circ\) 到 \(+179^\circ\)，最短误差是 \(-2^\circ\)，不是 \(+358^\circ\)。

### 第二步：角度环把角度差变成希望转多快

假设只是为了教学，角度环使用比例增益 \(4\ \text{s}^{-1}\)，那么：

\[
\omega^*=4\times10^\circ=40^\circ/\text{s}
\]

这里的 \(\omega^*\) 就是代码中 `gyro_set` 这类变量所表示的目标角速度。**它不是角度，也不是电流。**

### 第三步：速度环读取 IMU 实际转速

假设滤波后的陀螺仪反馈为：

\[
\omega=25^\circ/\text{s}
\]

云台希望达到 \(40^\circ/\text{s}\)，实际只有 \(25^\circ/\text{s}\)，因此速度环会倾向于增加驱动。

反过来，如果云台快到目标时：

\[
\omega^*=4^\circ/\text{s},\qquad \omega=20^\circ/\text{s}
\]

那么速度误差为：

\[
4-20=-16^\circ/\text{s}
\]

速度环就会给出反向控制动作，减慢云台。此时角度还没到目标，它已经在制动。

### 第四步：速度环输出电机控制量

源码的 `pid_calc` 按“目标减当前”算误差，再计算 PID 输出。速度环最终得到 `give_current`。

这个值随后作为 CAN 电机命令发送。它是电机协议中的控制值；没有额外的电机协议换算和标定信息时，不能直接说它是多少安培或牛米。

pitch 输出额外取负号，是该实现的轴向或电机正方向约定。它说明程序在映射控制方向时做了反号，但单凭负号本身无法推断机器人实际向哪边动；还要结合安装方向与电机接线。

## 9. 滤波在这条链里位于哪里？

这里至少要分清两类滤波：

```text
BMI088 原始角速度
  ↓ 校正安装方向、零偏
INS_gyro
  ↓ 转成云台控制使用的单位
gyro_yaw / gyro_pitch
  ↓ 云台角速度低通滤波
速度环读取滤波后的角速度
```

滤波的作用是减少测量抖动。速度环如果对每个瞬间的小噪声都强烈反应，电机命令也会跟着抖。

滤波太强则会让数据滞后。例如真实角速度已经开始下降，但滤波值还在慢慢下降，控制器就会晚一点才知道。因而速度环使用的不是“原始数据必然最好”，而是在噪声和延迟之间折中。

> BMI088 通过 SPI 把陀螺仪和加速度计读数交给控制板；DMA 帮忙搬数据；INS 处理传感器轴向和偏差、滤波并做姿态解算，得到角速度、四元数和姿态角；云台角度环用目标角和当前角生成 `gyro_set`；速度环用 `gyro_set` 与滤波后的 IMU 角速度生成 `give_current`；电机收到 CAN 命令后运动，新的 IMU 和编码器反馈再进入下一轮。
````

````text
## 第一步：先明确这些数据沿着哪些轴表示

传感器芯片有自己的轴。芯片装到电路板上后，芯片的 `x/y/z` 轴未必和板子、机器人规定的轴一致。因此程序先对原始数据做轴变换和偏置修正。

本项目的 BMI088 安装矩阵把陀螺仪和加速度计分量改写为：

```text
处理后 x = 传感器原始 y
处理后 y = -传感器原始 x
处理后 z = 传感器原始 z
```

因此，后面 AHRS 使用的 `INS_gyro` 和 `INS_accel`，已经不是直接照搬芯片的原始三个数，而是经过轴方向调整和偏置处理的数。源码中的变换在 [Atti.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Communication/Atti.c:81) 和 [imu_cali_slove](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Communication/Atti.c:351)。

可以先把它们理解成：

- `INS_gyro`：按程序规定的板上轴方向表示，机身每秒绕三个轴转多快，单位应是 rad/s。
- `INS_accel`：按相同的轴方向表示，加速度计测到的比力，通常单位是 m/s²。
- `INS_quat`：AHRS 根据这些读数估计出的机身姿态。

这里的“机身姿态”具体是相对于 AHRS 所采用的参考轴来表达。**轴变换矩阵负责把传感器轴摆正；它本身不告诉我们房间里的绝对方向。**

## 第二步：AHRS 怎样一步步算四元数？

### 1. 陀螺仪提供“这一小段时间转了多少”

陀螺仪给出的是角速度。比如：

```text
绕 z 轴角速度 = 90°/s
```

意思是：如果速度保持不变，1 秒会转过 90°。控制器并不是等它转完 1 秒才更新，而是每个小周期估算这段时间转了多少：

\[
\text{这一步的转角}\approx\text{角速度}\times\text{这一步的时间}
\]

例如周期是 1 ms：

\[
90^\circ/\text{s}\times0.001\text{s}=0.09^\circ
\]

所以每次更新，陀螺仪只告诉程序：“这一个很短的周期里，大约转了 0.09°。”AHRS 把这一小步旋转接到上一次姿态上，形成新的四元数。许多很小的更新累积起来，就得到持续变化的姿态。

四元数写成：

\[
q=[w,x,y,z]
\]

它不是四个角，而是**一个整体姿态的四个数字编码**。表示绕单位轴 \(\mathbf n\) 转角 \(\theta\) 的四元数形式为：

\[
q=\left[\cos\frac{\theta}{2},\ \mathbf n\sin\frac{\theta}{2}\right]
\]

例如，绕 z 轴转 90°：

\[
q=[\cos45^\circ,0,0,\sin45^\circ]
 \approx[0.707,0,0,0.707]
\]

这是“绕 z 轴转了 90°”的一种编码。程序更新四元数时，不是把陀螺仪三个数直接塞进四元数，而是把角速度换成每周期的小旋转，再按四元数更新公式累积。

### 2. 加速度计帮助校正“上下倾斜”

只靠陀螺仪不断累积，会有一个问题：陀螺仪的小误差也会不断累积，最后角度可能越来越偏，这叫**漂移**。

加速度计在机器人没有明显平移加速时，主要能告诉程序重力从哪个方向作用。比如，机器人倾斜后，重力在传感器三个轴上的分量会改变。AHRS 将这个测出的重力方向与当前四元数预测的重力方向比较，再用差值修正姿态。

通俗地说：

```text
陀螺仪：刚才转了多少，反应快，但累积会漂
加速度计：重力大致朝哪边，能校正倾斜，但运动加速时会受干扰
AHRS：主要靠陀螺仪跟踪变化，再用重力方向纠正倾斜误差
```

加速度计并不能单独告诉程序“朝着房间哪个方向”。重力只提供上下方向；绕重力方向转一圈，重力方向本身并不改变。

### 3. 磁力计能帮助判断航向，但本代码片段没有正常使用它

磁力计如果提供有效的地磁方向，AHRS 可以再用它校正航向角，也就是 yaw。当前源码中 `INS_mag` 初始化为零，`ist8310_read_mag` 的读取调用被注释；AHRS 在磁力计三轴全为零时会转而调用只使用陀螺仪和加速度计的更新函数。

因此，对这份源码快照更稳妥的理解是：

- 加速度计可帮助校正与重力有关的倾斜方向；
- 陀螺仪负责跟踪角速度变化；
- **没有有效磁力计校正时，yaw 没有地磁北方向的绝对参考，会从启动时的约定值开始积分，也可能逐渐漂移。**

AHRS 的四元数更新、重力方向误差修正、无磁力计分支和归一化代码见 [AHRS.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/algorithm/AHRS.c:20)。

### 4. 本项目如何控制每次更新的时间？

这份代码的 AHRS 头文件把 `sampleFreq` 设为 1000 Hz，所以算法内部使用的步长是：

\[
\Delta t=\frac{1}{1000}=0.001\text{s}
\]

虽然 `AHRS_update` 接收了一个 `timing_time` 参数，但所检查到的更新公式使用的是 `sampleFreq`，不是这个参数。这意味着算法**按配置的 1 ms 假设**积分；如果实际任务周期与这个假设相差很多，角度积分就可能不准确。这里的 1000 Hz 是源码设置，不代表已经实测任务每 1 ms 准时运行。定义在 [AHRS.h](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/algorithm/AHRS.h:13)。

### 5. 为什么更新完还要归一化四元数？

理想情况下，单位四元数长度始终为 1：

\[
w^2+x^2+y^2+z^2=1
\]

计算机用有限精度反复加很小的数，长度可能逐渐偏离 1。源码每次更新后会把四个分量重新缩放到长度为 1。可以把它理解成：**防止姿态编码因计算误差慢慢变形。**

## 第三步：`get_angle` 怎样从四元数得到三个角？

`get_angle` 不再重新估计姿态。它只把刚才算出的四元数转换成比较容易阅读的三个角：

```text
yaw   偏航角：通常理解为绕 z 轴的转角
pitch 俯仰角：通常理解为绕 y 轴的转角
roll  横滚角：通常理解为绕 x 轴的转角
```

这里“通常”很重要：最后显示成哪个轴的正负角，取决于传感器轴变换、坐标约定和欧拉角旋转顺序。源码函数用的四元数顺序是 `[w,x,y,z]`，输出参数顺序是 `yaw, pitch, roll`：

\[
\begin{aligned}
\text{yaw}
&=\operatorname{atan2}\left(
2(wx+yz),\ 2(w^2+x^2)-1
\right)\\[2mm]
\text{pitch}
&=\arcsin\left(-2(xz-wy)\right)\\[2mm]
\text{roll}
&=\operatorname{atan2}\left(
2(wx+yz),\ 2(w^2+z^2)-1
\right)
\end{aligned}
\]

这些式子看起来复杂，是因为它们在从“四个数构成的整体旋转”中提取三个有顺序的角。学习时不需要先背公式，可以用两个简单例子理解。

### 例子一：四元数是初始单位姿态

若：

\[
q=[1,0,0,0]
\]

代入后：

\[
\text{yaw}=0,\qquad \text{pitch}=0,\qquad \text{roll}=0
\]

也就是 AHRS 的当前姿态被表示为零角。

### 例子二：只绕 z 轴转 90°

若：

\[
q=[0.707,0,0,0.707]
\]

代入 `get_angle` 的 yaw 公式：

\[
\text{yaw}
=\operatorname{atan2}(1,0)
=90^\circ
\]

pitch 和 roll 是 0°。所以同一个姿态可以写成四元数 `[0.707,0,0,0.707]`，也可以读成 yaw 90°、pitch 0°、roll 0°。这两个结果不是两个不同姿态，只是两种写法。

`atan2` 用来根据两个数确定角度所在方向；函数返回的角是**弧度**。例如 90° 等于约 1.571 rad。`get_angle` 的实现见 [AHRS.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/algorithm/AHRS.c:200)。

## 这组姿态相对什么“初始状态”？

这是最容易误会的地方。先区分“程序给了什么初始值”和“真实机器人当时到底是什么姿态”。

源码的 `AHRS_init` 实际上直接设定：

\[
\texttt{INS\_quat}=[1,0,0,0]
\]

尽管函数注释说会根据加速度计和磁力计初始化，函数体实际没有使用这两个输入来求初始姿态。也就是说，**程序一开始把四元数设为单位姿态，并没有在这个函数里先测出机器人真实的初始倾斜和绝对航向。**

因此：

- 如果机器人启动时恰好处于程序约定的水平、正向状态，零角可以符合直觉；
- 如果启动时已经倾斜，四元数仍先被设为单位姿态，之后加速度计校正可能逐渐把倾斜估计拉回来；
- 如果没有有效磁力计，启动时的 yaw 零点是程序约定的参考，不能直接说它就是房间的正北或地图的绝对方向；
- 这一段没有显示“记录启动姿态，再把之后姿态减去启动姿态”的处理。`get_angle` 只做四元数到角度的转换，不负责重设零点。

所以，“相对初始状态”更准确地说是：**相对于 AHRS 初始化时采用的参考约定，并由之后的传感器数据持续更新。它不是自动知道的全球绝对姿态。**

## 轴和变量名还有一个源码对应问题

`Atti.c` 的调用是：

```c
get_angle(INS_quat, &INS_angle[0], &INS_angle[1], &INS_angle[2]);
```

函数形参顺序是 yaw、pitch、roll，所以按这个调用：

```text
INS_angle[0] = yaw
INS_angle[1] = pitch
INS_angle[2] = roll
```

但当前 `Gimbal.c` 中把 `INS_angle[2]` 用作 pitch 角反馈，并把 `INS_angle[1]` 放进名为 `vision_data.roll` 的字段。这里的数组索引与常见 yaw/pitch/roll 名称对不上。它可能涉及项目轴定义、使用处命名或代码问题，需要结合整条轴映射确认；**不能只凭 `INS_angle[2]` 的变量位置，就断言它在物理上一定代表机身 pitch。**

你现在可以先记住这条主线：

```text
BMI088 原始轴数据
→ 轴向调整与偏置处理
→ 陀螺仪小步积分姿态
→ 加速度计校正重力方向
→ 得到并归一化四元数 INS_quat
→ get_angle 提取 yaw / pitch / roll
```

其中，四元数和角度都描述姿态；四元数是估计器内部持续更新的整体表示，角度是从它转换出来的读数。启动零点、磁力计是否有效、轴映射和欧拉角顺序，决定了这些角能否直接对应你熟悉的“机身向左、向前、朝哪个方向”。
````

````text
## 用“只绕 z 轴转”算一遍

假设：

- 初始四元数是 \(q_0=[1,0,0,0]\)，表示程序当前记为零角；
- 陀螺仪持续读到绕 \(+z\) 轴以 \(90^\circ/\text{s}\) 转动；
- 算法按每 \(1\text{ ms}\) 更新一次。

源码配置的 `sampleFreq` 是 1000 Hz，因此算法按 \(0.001\text{ s}\) 作为一次更新的时间间隔。

### 第 1 次更新：只转了 \(0.09^\circ\)

\[
90^\circ/\text{s}\times0.001\text{s}=0.09^\circ
\]

这 \(0.09^\circ\) 是**这一小步转过的角度**，不是总角度。对应的小步四元数约为：

\[
\Delta q=
\left[
\cos(0.045^\circ),\ 0,\ 0,\ \sin(0.045^\circ)
\right]
\approx[0.99999969,0,0,0.0007854]
\]

把这小步接到初始姿态上，得到新的姿态：

\[
q_1\approx[0.99999969,0,0,0.0007854]
\]

### 第 2 次更新：在上一步基础上再转 \(0.09^\circ\)

程序拿的是刚才的 \(q_1\)，不是重新拿初始的 \(q_0\)。再叠加一个 \(0.09^\circ\) 的小转动后，总转角约为 \(0.18^\circ\)：

\[
q_2\approx
\left[
\cos(0.09^\circ),0,0,\sin(0.09^\circ)
\right]
\]

接下来每个周期都这样更新。转了 0.1 秒，总角度约 \(9^\circ\)，四元数约为：

\[
q\approx[\cos(4.5^\circ),0,0,\sin(4.5^\circ)]
\approx[0.996917,0,0,0.078459]
\]

转了 1 秒，总角度约 \(90^\circ\)，四元数约为：

\[
q\approx[\cos(45^\circ),0,0,\sin(45^\circ)]
\approx[0.707107,0,0,0.707107]
\]

所以 `[0.707,0,0,0.707]` 可以表示“从参考零角累计转到约 \(90^\circ\)”。期间程序经历了许多小步，并不是某一周期突然从零跳到 \(90^\circ\)。

## 程序每一步实际更新哪些东西？

源码里先把陀螺仪读数乘上每次更新的时间，再根据当前四元数算出四个分量各自该改变多少。省略加速度修正时，可以用下面的关系理解：

\[
\begin{aligned}
\dot q_0&=-\frac12(q_1\omega_x+q_2\omega_y+q_3\omega_z)\\
\dot q_1&=\frac12(q_0\omega_x+q_2\omega_z-q_3\omega_y)\\
\dot q_2&=\frac12(q_0\omega_y-q_1\omega_z+q_3\omega_x)\\
\dot q_3&=\frac12(q_0\omega_z+q_1\omega_y-q_2\omega_x)
\end{aligned}
\]

这些式子的意思是：**四元数怎样变化，取决于当前四元数和三个轴的角速度。**实际程序用每秒 1000 次的配置，把这次变化乘以约 \(0.001\) 秒，加到旧四元数上，最后把它重新归一化。

实际 AHRS 还会用加速度计给陀螺仪积分做姿态校正；若有有效磁力计数据，也可以用它校正航向。本源码片段中的磁力计数据是零时，会走陀螺仪加加速度计的分支。

## 每次更新后，角度怎样算出来？

更新得到新四元数后，`get_angle` 立刻把它转换成三个角。对刚才“只有 z 轴转动”的情况，四元数是：

\[
q=[\cos(\theta/2),0,0,\sin(\theta/2)]
\]

把它代入 yaw 公式，公式里的两个数分别会变成：

\[
2q_0q_3=\sin\theta,\qquad
2q_0^2-1=\cos\theta
\]

因此：

\[
\text{yaw}=\operatorname{atan2}(\sin\theta,\cos\theta)=\theta
\]

而 pitch 和 roll 为零。也就是说，若累计转到了 \(9^\circ\)，这一周期得到的四元数约为 `[0.996917, 0, 0, 0.078459]`，`get_angle` 就会从它算出 yaw 约 \(9^\circ\)、pitch \(0^\circ\)、roll \(0^\circ\)。

这里的 `atan2` 是根据两个数判断角度的函数。程序返回的单位是弧度，所以 \(9^\circ\) 会以约 \(0.157\text{ rad}\) 的数值保存。

## 如果停止转动呢？

如果之后陀螺仪读数变为零，而且加速度计没有需要进行的姿态修正，四元数会保持在当前姿态。例如停在约 \(90^\circ\)，四元数就保持约 `[0.707, 0, 0, 0.707]`，角度仍约为 yaw \(90^\circ\)。它不会因为停止转动就自动回到零。

## 多个方向一起转时呢？

如果三个轴同时转，程序会把三个陀螺仪分量都放进四元数更新公式，再从更新后的四元数提取 yaw、pitch、roll。此时不能简单地分别计算：

```text
新的 yaw = 旧 yaw + z 轴角速度 × 时间
新的 pitch = 旧 pitch + y 轴角速度 × 时间
新的 roll = 旧 roll + x 轴角速度 × 时间
```

因为机器人正在转动时，三个轴的相对方向也会变化；而且先绕一个轴转、再绕另一个轴转，通常和反过来转的结果不同。四元数更新会整体处理这三个轴的转动，再由 `get_angle` 将最终姿态换成三个角。

还有一个读数特点：四元数可以持续表示连续转动，但 yaw 角通常只显示在 \([-180^\circ,180^\circ]\) 范围内。因此实际姿态从 \(179^\circ\) 继续转到 \(181^\circ\) 时，显示值可能从 \(179^\circ\) 变成 \(-179^\circ\)。这是角度表示绕回了，不代表机器人反向跳转。
````

````text
从零姿态开始，第一次绕 \(z\) 轴转 \(90^\circ\)：

\[
q_z=[0.707,0,0,0.707]
\]

接着，假设陀螺仪测到机身绕**此刻 IMU 自己的 \(x\) 轴**又转了 \(90^\circ\)：

\[
q_x=[0.707,0.707,0,0]

在这份 AHRS 的更新方式里，可以把它理解为：

q_{\text{新}}=q_z\otimes q_x

算出来是：

\[
q_{\text{新}}=[0.5,0.5,0.5,0.5]
\]

重点是：结果不是把 yaw 写成 \(90^\circ\)、roll 写成 \(90^\circ\) 就结束了。第二次转动的 \(x\) 轴属于已经转过的 IMU，因此它的方向已经跟第一次转动前不同。程序用四元数乘法把这个先后关系一起算进去。

如果先绕 \(x\) 轴转 \(90^\circ\)，再绕 \(z\) 轴转 \(90^\circ\)，结果是：

\[
q_x\otimes q_z=[0.5,0.5,-0.5,0.5]
\]

它和先 \(z\) 后 \(x\) 的结果

\[
[0.5,0.5,0.5,0.5]
\]

不同。这说明三维里“先转哪根轴、再转哪根轴”会影响最终姿态。

## 实际每个周期都只转一小步

假设第一个周期绕 \(z\) 轴转了 \(0.09^\circ\)，第二个周期绕 IMU 自己的 \(x\) 轴转了 \(0.09^\circ\)。程序会：

1. 保留第一个周期得到的四元数；
2. 根据第二个周期的陀螺仪读数，算出绕 \(x\) 轴的小转动四元数；
3. 用四元数乘法把小转动合进去；
4. 把结果归一化；
5. 再从这个新四元数计算 yaw、pitch、roll。

数值很小，没必要手动逐周期算；重要的是：**每次用上一步的完整姿态加上这一步的三轴转动，得到新的完整姿态。**

这里的“绕 \(x\) 轴”要看坐标系。如果陀螺仪报的是 IMU 自己的 \(x\) 轴，轴会随 IMU 一起转；如果说的是房间里固定不动的 \(x\) 轴，计算顺序会不同。这个项目会先将 BMI088 轴向调整到程序采用的轴约定，再把陀螺仪三轴读数交给 AHRS。
````

### 助手最终答复

````text
先说明一个容易混淆的地方：\(q_z\otimes q_x\) 里的 \(q_x\) 必须说明是绕**哪一个坐标系的 x 轴**。结合刚才的陀螺仪例子，我们把它解释成“陀螺仪测到的、绕当前 IMU 自己的 \(x\) 轴的小转动”。这和绕房间里固定的 \(x\) 轴转不是同一回事。

## 一、\(q_z\otimes q_x\) 是怎么乘的？

四元数按这个顺序写：

\[
q=[w,x,y,z]
\]

这里 \(w\) 是第一个分量，后面三个分量分别对应 \(x,y,z\)。四元数乘法不是把相同位置的数字相乘，而是按固定公式把分量交叉组合：

\[
\begin{aligned}
q_A\otimes q_B
=&[
w_Aw_B-x_Ax_B-y_Ay_B-z_Az_B,\\
& w_Ax_B+x_Aw_B+y_Az_B-z_Ay_B,\\
& w_Ay_B-x_Az_B+y_Aw_B+z_Ax_B,\\
& w_Az_B+x_Ay_B-y_Ax_B+z_Aw_B
]
\end{aligned}
\]

这个公式的作用是：**把两个转动合成为一个最终姿态**。

### 1. 写出两个 90° 转动的四元数

绕 \(z\) 轴转 \(90^\circ\)：

\[
q_z=
[\cos45^\circ,0,0,\sin45^\circ]
\approx[0.707,0,0,0.707]
\]

绕 \(x\) 轴转 \(90^\circ\)：

\[
q_x=
[\cos45^\circ,\sin45^\circ,0,0]
\approx[0.707,0.707,0,0]
\]

### 2. 代入乘法公式

为了看清每个数从哪来，先用 \(0.707\) 近似：

\[
q_z=[0.707,0,0,0.707],\qquad
q_x=[0.707,0.707,0,0]
\]

依次算出新四元数的四个分量：

\[
\begin{aligned}
w_{\text{新}}
&=0.707(0.707)-0-0-0=0.5\\
x_{\text{新}}
&=0.707(0.707)+0+0-0=0.5\\
y_{\text{新}}
&=0-0+0+0.707(0.707)=0.5\\
z_{\text{新}}
&=0+0-0+0.707(0.707)=0.5
\end{aligned}
\]

所以：

\[
\boxed{q_z\otimes q_x=[0.5,0.5,0.5,0.5]}
\]

注意：虽然单独的 \(q_z\) 和 \(q_x\) 的 \(y\) 分量都是零，合成后 \(y\) 分量却是 \(0.5\)。这是因为两个三维转动合成时会互相影响；乘法公式里的交叉项把这种影响算进去了。

### 3. 乘法左右顺序代表什么？

在刚才的 IMU 例子里，第二个小转动是按**当前 IMU 自己的轴**描述的。源码的四元数更新公式相当于把这个小转动接到当前姿态右边：

\[
q_{\text{新}}=q_{\text{旧}}\otimes\Delta q_{\text{IMU}}
\]

所以 \(q_z\otimes q_x\) 这个例子中，\(q_x\) 表示当前 IMU 轴下的 x 轴增量。

如果说的是绕房间里固定不动的 x 轴转，表达方法会不同，不能不说明坐标系就只看乘号顺序。对你目前的问题，先记住：**IMU 每次报告的是当前传感器轴方向上的转动，程序把这一步合进上次的完整姿态。**

## 二、四元数怎样变成 yaw、pitch、roll？

可以分成两步：

```text
四元数的四个数
→ 换成等价的旋转矩阵
→ 从旋转矩阵中提取 yaw、pitch、roll
```

四元数是姿态的一种紧凑写法。旋转矩阵则是另一种写法，可以看成一张记录三个轴如何指向的表。`get_angle` 的公式，本质上就是从这张表里取几个数字来算角度。

### 1. 先把公式里的四个量认出来

源码按这个顺序读四元数：

\[
q=[w,x,y,z]
\]

也就是 `quat[0]` 对应 \(w\)，`quat[1]` 对应 \(x\)，`quat[2]` 对应 \(y\)，`quat[3]` 对应 \(z\)。

源码的三个角公式是：

\[
\begin{aligned}
\text{yaw}
&=\operatorname{atan2}\big(2(wz+xy),\ 2(w^2+x^2)-1\big)\\
\text{pitch}
&=\arcsin\big(-2(xz-wy)\big)\\
\text{roll}
&=\operatorname{atan2}\big(2(wx+yz),\ 2(w^2+z^2)-1\big)
\end{aligned}
\]

先不用背它们。下面把我们刚算出的四元数代进去：

\[
q_{\text{新}}=[0.5,0.5,0.5,0.5]
\]

### 2. 算 yaw

公式中的第一个数：

\[
2(wz+xy)
=2(0.5\times0.5+0.5\times0.5)
=1
\]

第二个数：

\[
2(w^2+x^2)-1
=2(0.25+0.25)-1
=0
\]

所以：

\[
\text{yaw}=\operatorname{atan2}(1,0)=90^\circ
\]

`atan2(1,0)` 可以先理解成：水平方向分量是 0，垂直方向分量是正的，因此指向 \(90^\circ\)。

### 3. 算 pitch

先算反正弦括号里的数：

\[
-2(xz-wy)
=-2(0.5\times0.5-0.5\times0.5)
=0
\]

所以：

\[
\text{pitch}=\arcsin(0)=0^\circ
\]

### 4. 算 roll

公式里的第一个数：

\[
2(wx+yz)
=2(0.5\times0.5+0.5\times0.5)
=1
\]

第二个数：

\[
2(w^2+z^2)-1
=2(0.25+0.25)-1
=0
\]

所以：

\[
\text{roll}=\operatorname{atan2}(1,0)=90^\circ
\]

因此这个四元数用项目的 `get_angle` 转成角度后是：

\[
\boxed{
\text{yaw}=90^\circ,\qquad
\text{pitch}=0^\circ,\qquad
\text{roll}=90^\circ
}
\]

这些角是按源码采用的欧拉角约定，从**最终整体姿态**中提取的。它们不等于把两次转动的角度分别随手填进 yaw 和 roll；它们是对合成后姿态的一种读取方式。

### `atan2` 和 `asin` 在这里做什么？

- \(\operatorname{atan2}(a,b)\)：根据两个数 \(a,b\) 判断角度。比如 `atan2(1,0)` 是 \(90^\circ\)。
- \(\arcsin(a)\)：找一个角，使这个角的正弦等于 \(a\)。比如 \(\arcsin(0)=0^\circ\)。

`get_angle` 返回的是弧度。上面的角度换成弧度分别约为：

\[
[1.571,\ 0,\ 1.571]\text{ rad}
\]

所以每个控制周期的实际过程可以记成：

```text
保留 q旧
→ 用陀螺仪三轴读数算这一小步转动
→ q新 = q旧 ⊗ 这一小步转动（IMU轴约定下）
→ 归一化 q新
→ get_angle(q新)，得到当前 yaw、pitch、roll
```

`q_z\otimes q_x\) 只是用两个大转动演示四元数乘法。真实系统每周期的转动很小，程序会反复更新；`get_angle` 每次读的都是**更新后的当前姿态**。
````

````text
# 第三章：摩擦轮和拨弹机构怎样闭环工作

本章要先分清两个机构：

## 1. 先想象机械动作

可以把发射机构想成两步：

```text
摩擦轮高速旋转
      ↓
弹丸进入轮子接触区域，被轮面摩擦加速
      ↓
拨盘把下一颗弹丸送到发射位置
```

源码里三个摩擦轮的变量叫 `fire_l`、`fire_r`、`fire_on`。左右轮和另一个轮子的转动方向、安装位置可能不同，所以它们的目标速度正负号也可能不同。**速度是负数不一定表示转得慢，而可能表示转动方向与程序定义的正方向相反。**

拨盘在代码中叫 `trigger`。它不是为了持续高速旋转，而是按一次发射推进到下一个弹丸位置。

## 2. 摩擦轮为什么需要速度反馈？

假设控制器要求一个摩擦轮保持在某个转速。电机转起来以后，电机反馈会报告当前转速。控制器每周期比较：

\[
e=\text{目标转速}-\text{当前转速}
\]

例如：

```text
目标转速：6000 RPM
当前转速：5900 RPM
误差：+100 RPM
```

正误差表示实际转速还低于目标。控制器就要输出一个电机命令，让摩擦轮继续加速。

弹丸进入轮子之间时会从轮面吸收能量，摩擦轮通常会短暂降速。速度反馈发现降速后，控制器再增加电机驱动力，让轮速恢复。因此闭环不是“算一次电机命令就结束”，而是反复进行：

```text
设置目标速度
→ 读取当前转速
→ 算误差
→ 计算电机命令
→ 电机带动摩擦轮
→ 再读新转速
```

电机转矩和轮速变化可用简化关系理解：

\[
J\dot\omega=\tau_{\text{motor}}-\tau_{\text{load}}-\tau_{\text{friction}}
\]

- \(J\)：轮子和转子转起来的惯性；
- \(\dot\omega\)：角速度变化快慢；
- \(\tau_{\text{motor}}\)：电机产生的转矩；
- \(\tau_{\text{load}}\)：弹丸接触等带来的负载；
- \(\tau_{\text{friction}}\)：机械摩擦等阻力。

电机命令影响电机输出转矩，转矩改变轮子的角速度，速度反馈再告诉控制器效果如何。源码中的 `give_current` 是给驱动器的电流命令尺度值；没有驱动器协议和电机参数换算，不能直接把它说成多少安培或多少牛米。

## 3. 轮子转速和弹丸速度不是一回事

轮子表面的线速度可以由半径和角速度计算：

\[
v_{\text{轮面}}=r\omega
\]

例如轮半径 \(r=0.03\text{ m}\)，角速度 \(\omega=300\text{ rad/s}\)：

\[
v_{\text{轮面}}=0.03\times300=9\text{ m/s}
\]

这表示轮面在接触处的理论线速度是 \(9\text{ m/s}\)。**它不保证弹丸也恰好以 \(9\text{ m/s}\) 飞出。**

原因是弹丸和轮面之间可能打滑；弹丸可能受挤压变形；实际接触时间、材料、弹簧压力和轮面磨损也会影响弹丸速度。因此，不能只根据轮速就断言弹丸速度是多少。

这份源码还读取裁判系统的弹速数据，并据此对摩擦轮目标作分档调整。它的作用可以理解为：如果测到的弹速偏离要求，就逐步调整轮速目标。不过这是目标速度的额外调整；底下的摩擦轮闭环仍然要根据电机反馈努力跟踪新的目标。

## 4. 源码里摩擦轮的滑模控制具体在算什么？

源码每次会先形成摩擦轮的误差：

\[
e_k=\text{目标 RPM}-\text{测得 RPM}
\]

例如当前目标是 \(6000\text{ RPM}\)，测到 \(5900\text{ RPM}\)：

\[
e_k=6000-5900=100\text{ RPM}
\]

程序还保存上一次误差，比较误差这一次变化了多少：

\[
\dot e_k\approx \frac{e_k-e_{k-1}}{\Delta t}
\]

这里的 \(\dot e\) 可以读作“误差变化速度”。假设上一周期的误差是 \(98\text{ RPM}\)，两次调用相隔 \(0.001\text{ s}\)：

\[
\dot e_k=\frac{100-98}{0.001}=2000\text{ RPM/s}
\]

这不是摩擦轮转速，而是**转速误差每秒变化多少**。

然后源码把误差和误差变化速度合成一个量：

\[
\sigma=\dot e+c e
\]

这个 \(\sigma\) 有点像控制器的“综合判断分数”：

- \(e\) 大，说明离目标还远；
- \(\dot e\) 大，说明误差正在明显变化；
- \(c\) 调节当前误差在这个综合分数中的影响。

滑模控制的常见直觉是：设计一个希望误差遵循的变化关系。若理想情况下：

\[
\sigma=\dot e+c e=0
\]

那么：

\[
\dot e=-ce
\]

意思是误差应该逐步往零衰减。这里 \(c\) 越大，理想衰减越快。**这帮助理解 \(\sigma\) 的设计意图，但不能单凭这条关系就证明源码中的整个控制器稳定。**

源码之后对 \(\sigma\) 使用饱和函数：

\[
\operatorname{sat}(\sigma)=
\begin{cases}
\sigma/\epsilon,&|\sigma|\leq\epsilon\\
1,&\sigma>\epsilon\\
-1,&\sigma<-\epsilon
\end{cases}
\]

可以先这样理解：

- \(\sigma\) 离零很远时，输出固定为 \(+1\) 或 \(-1\)，控制器作较明确的纠正；
- \(\sigma\) 接近零时，输出随它平缓变化，不在零附近突然从 \(-1\) 跳到 \(+1\)。

这种平缓过渡可以减少控制命令快速抖动。参数 \(\epsilon\) 决定这个平缓区域的宽度。

源码的控制计算是：

\[
u_{\text{内部}}=-c e-\rho\,\operatorname{sat}(\sigma)
\]

最终还受 `max_i` 限幅。摩擦轮调用处又取了一次负号：

```cpp
launcher.fire_l.give_current = -smc_controller(...);
```

因此要区分两个值：

1. `smc_controller` 返回的内部结果；
2. 经过调用处负号后，写入 `give_current` 的结果。

这个负号和各轮目标的正负方向一起决定电机方向，不能只看到公式里的负号就断定它一定是在制动。

### 按源码数字手算一遍

取：

```text
当前目标误差 e       = 100 RPM
上一次目标误差       = 98 RPM
dt                   = 0.001 s
c                    = 5
rho                  = 2
epsilon              = 1
max_i                = 10000
```

先算误差变化速度：

\[
\dot e=\frac{100-98}{0.001}=2000\text{ RPM/s}
\]

再算综合量：

\[
\sigma=2000+5\times100=2500
\]

因为 \(2500>1\)，饱和函数结果是 \(1\)。于是：

\[
u_{\text{内部}}=-5\times100-2\times1=-502
\]

它没有超过限幅。调用处再取负号：

\[
\texttt{give\_current}=-(-502)=+502
\]

这里的 \(+502\) 是源码里送给电机驱动接口的命令尺度值，**不是 \(502\text{ A}\)、不是 \(502\text{ N·m}\)，也不是转速变成了 \(502\text{ RPM}\)**。它只是控制器算出的一个命令数值，实际效果要看电机驱动、协议和反馈。

还有个重要限制：源码把 \(\dot e\) 和 \(ce\) 放在同一计算里，但当前讲义没有证据说明 \(c,\rho\) 对这些量做了完整的物理单位换算。因此上面的数值演示的是**代码按当前参数怎样计算**，不是经过物理单位验证的控制设计证明。

## 5. PID 在哪里？为什么不能说摩擦轮也在用 PID？

本项目发射机构里有多种控制代码，不代表它们都在同时运行：

- **摩擦轮：**三个 VSP PID 调用被注释，当前活动路径调用 `update_system` 和 `smc_controller`。
- **拨盘：**角度 PID 和速度 PID 仍在活动控制路径中。
- **VSP PID：**代码初始化了相关参数，但初始化参数不等于控制器每周期真的被调用。

判断某个控制算法有没有运行，要看**活动的调用语句**，不能只看项目里是否存在这个函数或参数。

## 6. 拨盘为什么使用“角度环加速度环”的 PID？

摩擦轮要维持持续旋转；拨盘则要把弹丸送到指定位置。拨盘因此有两个连续的问题：

1. **还差多少角度？**
2. **现在转得是否太快或太慢？**

源码的结构可以画成：

```text
拨盘目标编码角 − 当前累计编码角
                ↓
             角度 PID
                ↓
       拨盘目标速度 trigger.speed
                ↓
当前拨盘转速 → 速度 PID ← 目标速度
                ↓
      拨盘电机 give_current
```

### 外层：角度 PID 产生速度要求

目标角度和当前角度相差很大时，角度环会要求拨盘转快一些；接近目标角度时，它会把速度要求逐渐减小。

所以角度 PID 输出的 `trigger.speed` 是一个**速度参考**，不是最终电机电流，也不是新的角度。

### 内层：速度 PID 产生电机命令

速度环比较：

```text
角度环给出的目标速度
和
电机反馈报告的当前速度
```

再根据速度差计算 `give_current`。这条内环让拨盘按外环要求的速度运动。

源码调用形式是先用 `angle_p` 计算 `trigger.speed`，再用 `speed_p` 计算 `trigger.give_current`，见 [launcher.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/launcher.c:259)。

“角度环给速度、速度环给电机命令”就是级联控制：一个环的输出成为下一个环的目标。

## 7. 一次拨弹动作怎样开始、完成和判断卡弹？

拨盘使用电机编码器累计角度。代码会记录一个目标累计编码值。单发开始时，目标角度会按一次发射对应的编码增量改变；角度环再让拨盘朝目标位置移动。

编码器的“累计编码值”可以理解成电机转过多少个计数单位。它不是直接的度数；齿轮比、编码器分辨率和机构比例决定多少个计数对应拨盘转多少角度。因此源码里的 `DEGREE_60_TO_ENCODER` 这类宏负责把机构角度换成编码器单位。

拨盘还用累计编码变化量和经过时间判断动作是否完成或堵转。当前代码中，若一次动作在规定时间里没有达到相应的编码变化，会进入堵转处理；堵转后会尝试反转，再判断是否失败。这是**看拨盘是否真的移动**，不能简单说成“检测到电流很大，所以堵转”。

## 8. Fire_OFF 和 RELAX 有什么区别？

这两个状态很容易被误认为一样。

- **Fire_OFF：**把摩擦轮的目标速度设为零。随后摩擦轮控制器仍会运行，可能输出电机命令，让高速旋转的轮子减速。因此“目标转速为零”不等于“电机命令立刻为零”。
- **RELAX：**调用 `Launcher_Relax_Handle`，明确把摩擦轮和拨盘的 `give_current` 设为零，并重置拨盘目标参考。

可以类比汽车：

```text
Fire_OFF：踩着制动把车减速到零
RELAX：把驱动命令撤掉
```

只是这个类比用于区分控制意图，不能据此推断电机断电后的实际滑行或制动行为。

## 9. 把一个完整周期串起来

以摩擦轮为例：

```text
遥控/模式决定是否开启发射机构
→ 程序设定三个摩擦轮的目标 RPM
→ 电机反馈提供三个轮子的实际 RPM
→ 分别计算目标与实际的误差
→ 根据误差变化算滑模控制输出
→ 限幅并按电机方向写入 give_current
→ CAN 把命令交给电机驱动
→ 摩擦轮改变实际转速
→ 新 RPM 再进入下一周期
```

以拨盘为例：

```text
单发命令和拨弹状态决定拨盘目标编码角
→ 编码器反馈提供当前累计角和转速
→ 角度 PID 算出目标速度
→ 速度 PID 算出 give_current
→ CAN 把命令交给电机驱动
→ 拨盘实际转动
→ 新编码器数据进入下一周期
→ 根据移动量和时间判断完成、堵转或失败
```

注意：源码中的 SMC 使用 `dt=0.001` 计算误差变化率，这相当于算法假设两次调用间隔为 1 ms。若实际调用周期与它差得较多，\(\dot e\) 的数值会被算偏。源码配置值不等于实测频率；要确认真实周期，需要测相邻调用的时间戳。

2. 当前源码的摩擦轮活动调用是滑模控制；拨盘是角度 PID 给速度目标、速度 PID 给电机命令。

5. 是否真正使用某个控制器，要看活动调用；函数存在或参数初始化本身不能证明它正在运行。
````

````text
# 一、变比例 PID 是什么？

## 1. 先回忆普通 PID 里的比例项

目标转速减去实际转速，得到误差：

\[
e=\text{目标转速}-\text{实际转速}
\]

例如：

```text
目标转速：6000 RPM
实际转速：5900 RPM
误差：+100 RPM
```

普通 PID 的比例部分是：

\[
P=K_p e
\]

\(K_p\) 是比例增益。它决定：**转速差 1 个单位时，控制输出要改变多少。**

普通 PID 的 \(K_p\) 是固定的。误差是 1 RPM 或 1000 RPM，都使用同一个 \(K_p\)。

变比例 PID 的想法是：**误差变化时，\(K_p\) 也跟着变化。**

- 误差大时，可以提高 \(K_p\)，让控制器更有力地追赶目标；
- 误差小时，可以降低 \(K_p\)，减少靠近目标时过猛的反应。

注意：变的是 \(K_p\)，不是说 PID 三项都自动按同一种方式变化。

## 2. 这份代码怎样改变 \(K_p\)？

源码里的 VSP PID 按下面的公式算比例增益：

\[
K_p=k_0\log_{10}(k_1|e|)+k_2
\]

本项目这组参数是：

\[
k_0=1,\qquad k_1=8,\qquad k_2=5
\]

所以，在使用这些参数的教学手算中：

\[
K_p=\log_{10}(8|e|)+5
\]

然后源码用新的 \(K_p\) 计算比例输出：

\[
P=K_p e
\]

并把这个 \(K_p\) 限制为不低于 `minimum_kp`。当前设定的最小值是 0。实现见 [Feedforward_PID.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/controller/Feedforward_PID.c:34)。

## 3. 用三个误差数看它怎样变化

先按公式做教学计算：

| 误差大小 \(|e|\) | 计算出的 \(K_p\) | 比例输出 \(P=K_pe\) |
|---:|---:|---:|
| 1 | \(\log_{10}(8)+5\approx5.903\) | 约 5.903 |
| 10 | \(\log_{10}(80)+5\approx6.903\) | 约 69.03 |
| 100 | \(\log_{10}(800)+5\approx7.903\) | 约 790.3 |

误差从 10 增加到 100，增大了 10 倍；\(K_p\) 只增加约 1，但比例输出因为误差本身也变大，所以从约 69 增加到约 790。

可以这样理解：

> 对数公式让比例增益随着误差变大而慢慢增大。它不会像“误差翻十倍，\(K_p\) 也翻十倍”那样快速增长。

VSP PID 的积分、微分项仍然会计算，但它们使用各自的 \(K_i\)、\(K_d\)，并不会因为这条公式而自动变成另一个动态增益。

## 4. 这份 VSP PID 的 P、I、D 在代码里怎样算？

它的计算形式是：

\[
\begin{aligned}
e_k &= \text{reference}-\text{feedback}\\
P_k &= K_{p,k}e_k\\
I_k &= I_{k-1}+K_i(e_{k-1}+e_k)\\
D_k &= K_d(e_k-e_{k-1})\\
u_k &= P_k+I_k+D_k
\end{aligned}
\]

之后，积分项和总输出分别进行限幅。

这里有个关键细节：**这个 VSP PID 的积分和微分计算里没有显式乘或除控制周期 \(\Delta t\)**。所以它不是把所有教材公式原样搬进代码。控制周期变化时，积分累积和微分输出也可能随之改变，需要重新核对参数。

### 教学手算

假设：

```text
当前误差       e = 100 RPM
上次误差       e_prev = 98 RPM
Ki = 0
Kd = 1
```

刚才算得 \(K_p\approx7.903\)，因此：

\[
P\approx7.903\times100=790.3
\]

积分项因为 \(K_i=0\)，所以为 0：

\[
I=0
\]

微分项：

\[
D=1\times(100-98)=2
\]

于是总输出约为：

\[
u=790.3+0+2=792.3
\]

这个 792.3 是控制器输出尺度，不是 RPM、安培或牛米。即使 VSP PID 调用，最终还要看驱动协议怎样解释这个数。

## 5. VSP PID 在当前源码里实际有没有控制摩擦轮？

**没有看到它在当前摩擦轮控制路径里被调用。**

`Launcher_Init` 中确实初始化了三个摩擦轮的 VSP PID；但 `Launcher_Control` 中用 `VSP_PID_Calc` 产生三个摩擦轮电流的语句被注释掉了。实际执行的是：

```text
update_system(...)
→ smc_controller(...)
→ 写入 give_current
```

因此要分开说：

- VSP PID：源码里存在并初始化了，能解释它的设计；
- 当前摩擦轮活动控制：走 SMC；
- 拨盘 PID：仍在当前控制路径里使用。

源码里的名字 `feedforward_speed_p` 容易让人以为这里一定加了独立的前馈项。但 `VSP_PID_Calc` 展示的公式实际是变比例 PID 计算，没有另外看到一个单独的“前馈输出”加项。

还有一处代码细节值得检查：误差是浮点数，但源码写的是 `abs(error)`，而 C 里的 `abs` 通常用于整数；浮点绝对值一般使用 `fabsf`。如果传入小数误差，整数转换可能改变它的值。这是静态代码审阅发现的潜在问题，不能据此直接说它已经造成了实际故障；而且这个 VSP 调用在当前摩擦轮路径里被注释掉了。

# 二、滑模控制是什么？

## 1. 先不用“滑模”这个名字理解

摩擦轮控制器要知道两件事：

1. 现在离目标转速差多少；
2. 这个误差是在变大还是变小。

源码先算误差：

\[
e_k=\text{目标 RPM}-\text{当前 RPM}
\]

再用相邻两次误差的变化估算误差变化速度：

\[
\dot e_k\approx\frac{e_k-e_{k-1}}{\Delta t}
\]

例如：

```text
上次误差 98 RPM
本次误差 100 RPM
两次间隔 0.001 秒
```

那么：

\[
\dot e_k=\frac{100-98}{0.001}=2000\text{ RPM/s}
\]

误差是 100 RPM，正在以约 2000 RPM/s 的速度增大。符号很重要：正数表示按这份误差定义，误差在增大；负数表示误差在减小。

## 2. \(\sigma\) 是什么？

源码接着计算：

\[
\sigma=\dot e+ce
\]

\(\sigma\) 是误差和误差变化速度的组合量。可以把它理解为控制器对“当前偏差和偏差走势”的综合判断值：

- \(e\)：现在差多少；
- \(\dot e\)：差距变化有多快；
- \(c\)：调节这两部分相对影响的系数。

在滑模控制的常见思路中，会把 \(\sigma=0\) 设为希望误差遵循的关系：

\[
\dot e+ce=0
\quad\Longrightarrow\quad
\dot e=-ce
\]

当 \(c>0\) 时，这代表误差应该朝零逐渐减小。

“滑模面”不是机械上的表面。它是数学上定义的一种目标关系：控制器希望误差状态逐渐回到并沿着这条关系收敛。

## 3. 为什么还要 `sat` 饱和函数？

如果直接用正负号函数，\(\sigma\) 只要刚好从正变负，输出就可能从 \(+1\) 突然跳到 \(-1\)。数字上快速来回跳会使电机命令抖动，这通常叫“抖振”。

源码用 `sat` 函数，在零附近做平缓过渡：

\[
\operatorname{sat}(\sigma)=
\begin{cases}
\sigma/\epsilon,&|\sigma|\leq\epsilon\\
1,&\sigma>\epsilon\\
-1,&\sigma<-\epsilon
\end{cases}
\]

当前源码中的 \(\epsilon=1\)。

例如：

- \(\sigma=0.5\)，则 \(\operatorname{sat}(\sigma)=0.5\)；
- \(\sigma=1\)，结果为 1；
- \(\sigma=10\)，结果仍为 1；
- \(\sigma=-10\)，结果为 -1。

超出边界层后，它不再随 \(\sigma\) 的大小继续增长，只保留正负方向；靠近零时则平滑变化。

## 4. 源码怎样由 \(\sigma\) 算出电机命令？

SMC 函数里的实际公式是：

\[
u_{\text{内部}}=-ce-\rho\,\operatorname{sat}(\sigma)
\]

参数是：

```text
c = 5
rho = 2
epsilon = 1
max_i = 10000
```

先算 \(u_{\text{内部}}\)，再把它限制在 \([-10000,10000]\)。

调用位置还会再取一次负号：

```cpp
give_current = -smc_controller(...);
```

所以要分清：

```text
SMC 函数内部的输出
→ 调用处取负号
→ 存入 give_current
```

正负号和电机安装方向、编码器方向、驱动命令约定有关。看到正数，不能脱离硬件约定直接断定轮子一定“朝前转”。

## 5. 用源码参数完整算一遍

假设：

```text
目标转速         6000 RPM
当前转速         5900 RPM
上次误差         98 RPM
本次误差         100 RPM
dt               0.001 秒
```

第一步，误差：

\[
e=6000-5900=100\text{ RPM}
\]

第二步，误差变化速度：

\[
\dot e=\frac{100-98}{0.001}=2000\text{ RPM/s}
\]

第三步，综合量：

\[
\sigma=2000+5\times100=2500
\]

第四步，饱和函数：

\[
|\sigma|=2500>1
\quad\Longrightarrow\quad
\operatorname{sat}(\sigma)=1
\]

第五步，SMC 内部输出：

\[
u_{\text{内部}}
=-5\times100-2\times1
=-502
\]

第六步，摩擦轮调用处取负号：

\[
\texttt{give\_current}=-(-502)=+502
\]

这只是按源码运算得到的协议尺度数值。它**不证明**电机必然增加多少转速，也不等于 502 A 或 502 N·m；真实影响由驱动器、电机、负载和符号约定共同决定。

源码的误差变化率使用 \(\Delta t=0.001\) 秒。如果反馈 RPM 变化 1 个数值单位，差分就是：

\[
\frac{1\text{ RPM}}{0.001\text{s}}=1000\text{ RPM/s}
\]

因此，差分项对量化跳动和周期设置比较敏感。实际设计需要检查测速噪声、调用周期、限幅和输出抖动。当前代码中写了 `dt=0.001`，但这只是配置假设，不能代替实测任务周期。

这份代码叫 SMC，包含了滑模面的形式和饱和切换项；不过只凭它有 \(\sigma\) 和 `sat`，不能证明整个控制器在真实摩擦轮系统上一定稳定。完整稳定性分析还需要弄清电机输入怎样影响轮速、参数的量纲、采样周期、饱和和扰动范围。

# 三、发射请求怎样变成拨盘动作？

这里有两个不同状态：

- `fire_mode`：摩擦轮是开启还是关闭；
- `shoot_cmd`：拨盘这一次送弹进行到哪一步。

**摩擦轮开启并不代表每一周期都在拨弹。**通常摩擦轮先进入目标转速，拨盘等到发射请求和限制允许后再移动。

## 1. 手动触发和自动触发

手动路径大致是：

```text
操作者打开 Fire_ON
→ 摩擦轮建立目标转速
→ 拨弹开关边沿或鼠标点击产生单发请求
→ shoot_cmd 从 SHOOT_OVER 变为 SHOOT_READLY
→ Launcher_Control 设置一次拨盘目标
```

`SHOOT_READLY` 在源码里就是这个拼法，意思是“收到单发请求，准备执行”。

自动路径大致是：

```text
robot_ctrl.fire_command == 1
且云台模式为 GIMBAL_AUTO
且42 mm发射机构热量低于代码阈值
且距上次自动发射超过500 ms
→ 设置拨盘目标
→ 进入 SHOOT_SINGLE
```

源码使用的阈值是 `shooter_42mm_barrel_heat < 100`，发射间隔检查是大于 500 ms。它是这份代码的具体条件，不能直接推广成所有 RoboMaster 发射机构的规则。

## 2. 摩擦轮目标怎样设置？

Fire_ON 时，代码给三个轮子写入目标速度，左右轮与第三只轮使用对应的正负号。头文件中当前可见的标称值包括：

```text
FIRE_SPEED_L = 4910
FIRE_SPEED_R = FIRE_SPEED_L
FIRE_SPEED_ON = 4960
```

这些是源码配置值，不是测得的实际速度。

代码还根据裁判系统传来的弹速 `bullet_speed` 调整 `fire_speed`，每次调整以 50 为步长。直觉上，这是拿“弹丸实际测得的速度”慢慢改变“摩擦轮目标速度”。弹速读数不是直接给电机的命令，它改变目标后，摩擦轮控制器再追踪新目标。

静态检查时还要注意：源码中对 `bullet_speed > 15.7` 和 `bullet_speed > 16` 使用了两个独立的 `if`，而不是互斥的 `else if`。所以在某些变化条件下，`fire_speed` 可能一次加两个 50。至于这是故意设置的分段加速策略还是需要修正，必须结合参数意图和实际记录判断；只看这段代码不能下结论。

## 3. 单发时拨盘目标怎样变化？

拨盘编码器有一个累计计数。源码中一次发射使用 `DEGREE_60_TO_ENCODER` 作为单步位置增量，当前值是 26225 个编码计数；堵转反转时使用 `DEGREE_120_TO_ENCODER`，当前值是 52450 个计数。

当单发开始时，代码把目标设置成：

\[
\text{目标累计编码}
=
\text{当前累计编码}-26225
\]

这里的减号表示按源码当前编码器正方向约定，目标向负方向移动。若编码器安装方向不同，物理上的“前进”或“后退”要以设备方向校准为准。

拨盘角度控制分两层：

```text
目标累计编码 − 当前累计编码
                ↓
角度 PID 产生目标速度 trigger.speed
                ↓
目标速度 − 电机实测 RPM
                ↓
速度 PID 产生 trigger.give_current
```

第一层决定拨盘“还差多少位置”，第二层决定电机“怎样产生运动去完成它”。

当前 PID 函数采用 `set-get` 作为误差，积分量和微分量按相邻周期误差更新，并对积分、总输出限幅；公式实现没有显式乘或除 \(\Delta t\)。因此，教材上的连续 PID 公式可帮助理解功能，但不能不加说明地当成代码逐字实现。见 [PID.c](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/controller/PID.c:69)。

# 四、堵转怎样判断？

## 1. 它看“目标还差多少、等了多久”

堵转判断不只是看电流，也不只是看“电机没转”。当前 `Trigger_Finish_Judge` 主要比较：

\[
\text{剩余位置误差}
=
|\text{目标累计编码}-\text{当前累计编码}|
\]

代码阈值：

```text
TRI_MINECD = 5000 个编码计数
TRI_MAXTIME = 1000 ms
```

它的判断直觉是：

- 剩余编码误差仍大于 5000，说明拨盘还离目标较远；
- 如果 1 秒内还在这个范围外，先继续等待；
- 如果超过 1 秒仍离目标较远，就判为堵转；
- 如果剩余误差小于 5000，就认为这次位置动作完成。

注意：5000 是编码计数，不是 5000 度。和一次目标步进 26225 个计数相比，它约为五分之一；这是代码的完成容差大小。

## 2. 用数字理解判断条件

假设目标与当前累计编码相差 18000：

### 情况 A：开始后 500 ms，误差仍为 18000

```text
误差 18000 > 5000
时间 500 ms < 1000 ms
```

仍处于等待时间内，状态保持为 `SHOOT_SINGLE`。代码不会因为拨盘刚开始时还没到位，就立刻判断堵转。

### 情况 B：过了 1000 ms，误差仍为 18000

```text
误差 18000 > 5000
时间 > 1000 ms
```

控制器把状态改成 `SHOOT_BLOCK`，准备执行反转恢复。

### 情况 C：误差降到 3000

```text
误差 3000 < 5000
```

控制器认为拨盘已经足够接近目标，状态改成 `SHOOT_OVER`，允许后续发射请求。

源码使用严格的大于和小于比较。若误差恰好等于 5000，或计时恰好等于 1000 ms，这一周期不会命中对应的 `>` 或 `<` 分支；状态要等下一次检查才可能变化。

## 3. 堵转后怎样恢复？

检测到 `SHOOT_BLOCK` 后，控制路径会：

1. 重新记录开始时间；
2. 把拨盘目标再加上 `DEGREE_120_TO_ENCODER`，即 52450 个编码计数；
3. 把状态改为 `SHOOT_BLOCK_BACK`；
4. 继续由拨盘角度 PID 和速度 PID 追踪这个新目标；
5. 再用位置误差和时间判断反向动作是否完成。

如果反转后误差降到 5000 以下，代码将状态设为 `SHOOT_OVER`，表示这次动作完成；如果反转超过 1 秒后剩余误差仍大于 5000，则进入 `SHOOT_FAIL`。

这个“加 120°”是否对应物理上的反方向，要结合编码器计数正方向和拨盘电机接线方向验证。源码注释把它称为反转，但实际物理方向最终由这些符号约定决定。

## 4. `SHOOT_FAIL` 是否自动停电？

在当前检查到的 `Launcher_Control` 路径里，`SHOOT_FAIL` 是一个状态标记；**这个状态名本身不能证明拨盘电流已经归零**。Fire_ON 时，角度 PID 和速度 PID 仍会计算拨盘命令，除非其他路径另行处理。

Fire_OFF 会把拨盘电流命令设为零；进入 `GIMBAL_RELAX` 时，`Launcher_Relax_Handle` 会把四路命令归零。若要确认堵转失败后的真实停机保护，还需要继续检查上层模式、CAN 驱动和电机侧行为。

另外，源码注释提到反转失败可能再次反转，但在当前看到的状态分支里，`SHOOT_BLOCK_BACK` 超时后直接转为 `SHOOT_FAIL`；没有看到明确的第二次反转状态流程。**应按实际分支说明，不要只照抄注释。**
````

### 用户消息 01

````text
\[ K_p=k_0\log_{10}(k_1|e|)+k_2 \]  为什么公式是这样 三个k分别有什么作用
````

### 助手最终答复

````text
这个公式不是从 PID 的基本定律里“必然推导出来”的。它是设计者选的一条**调参曲线**：误差大时让比例增益 \(K_p\) 大一些，误差小时让 \(K_p\) 小一些。为什么选对数曲线？因为对数增长比较慢，误差扩大很多倍时，\(K_p\) 不会跟着成倍暴涨。

公式是：

\[
K_p=k_0\log_{10}(k_1|e|)+k_2
\]

可以从里面往外看：

```text
误差 e
→ 取大小 |e|：只看差距有多大，不看方向
→ 乘 k1：调整误差的刻度
→ 取 log10：把很大的范围压缩
→ 乘 k0：调整增益变化幅度
→ 加 k2：整体抬高或压低增益
```

## 三个 \(k\) 分别做什么？

### \(k_0\)：控制增益随误差变化得有多快

它乘在对数结果前面，所以控制整条曲线的变化幅度。

当误差扩大 10 倍时：

\[
\log_{10}(10k_1|e|)
=\log_{10}(k_1|e|)+1
\]

所以 \(K_p\) 会增加 \(k_0\)。

- \(k_0=1\)：误差每扩大 10 倍，\(K_p\) 增加 1；
- \(k_0=2\)：误差每扩大 10 倍，\(K_p\) 增加 2；
- \(k_0\) 越大，大误差和小误差对应的增益差得越多。

### \(k_1\)：调整误差进入对数前的刻度

它决定同一个误差数值会落在曲线的什么位置。

在对数运算里，把 \(k_1\) 放大 10 倍，会让 \(K_p\) 增加 \(k_0\)。因此它会整体抬高或压低这条曲线。

### \(k_2\)：给增益加一个固定底数

它对每种误差都加同一个数：

- \(k_2\) 增加 1，所有情况下的 \(K_p\) 都增加 1；
- \(k_2\) 减少 1，所有情况下的 \(K_p\) 都减少 1。

可以把它想成“整条曲线上下平移”。

## 用源码参数算一遍

这份代码设置：

\[
k_0=1,\qquad k_1=8,\qquad k_2=5
\]

暂时按 \(e\) 的正数大小计算：

| \(|e|\) | 代入公式 | \(K_p\) |
|---:|---|---:|
| 1 | \(\log_{10}(8)+5\) | 约 5.903 |
| 10 | \(\log_{10}(80)+5\) | 约 6.903 |
| 100 | \(\log_{10}(800)+5\) | 约 7.903 |

误差从 1 增加到 10，\(K_p\) 增加 1；从 10 增加到 100，\(K_p\) 又增加 1。也就是误差每扩大十倍，比例增益只增加一点。

接下来比例输出是：

\[
P=K_p e
\]

假设误差 \(e=100\)，那么比例输出约为：

\[
P=7.903\times100=790.3
\]

这里的 \(|e|\) 只用于计算增益，所以误差 \(+100\) 和 \(-100\) 算出的 \(K_p\) 一样；但最后乘的是带正负号的 \(e\)，因此 \(P\) 的方向相反。

## 为什么不能把这公式当成通用定律？

因为它是人为选择的曲线。设计者需要用仿真或台架测试来决定 \(k_0,k_1,k_2\)，并观察响应是否太慢、过冲、振荡或输出饱和。

它还依赖误差的单位。若原来 \(e\) 用 RPM，后来改用 rad/s，同一个物理误差会变成不同数字，计算出的 \(K_p\) 也会变化。所以 \(k_1\) 必须和误差单位、数值范围一起选，不能脱离系统单独解释。

最后，\(e=0\) 时 \(\log_{10}(k_1|e|)=\log_{10}(0)\) 没有有限数值；源码还设置了最小 \(K_p\) 限制，但实际实现仍应妥善处理零误差输入。该 VSP 函数在当前摩擦轮路径中没有被调用，因此这些是对这段**备用控制代码**的解释。
````

````text
## 先说结论

这三个 \(k\) **没有唯一的理论答案**。它们用来决定“误差大小不同的时候，比例增益 \(K_p\) 怎样变化”，通常要根据目标响应和测试结果来选。

这份源码里，摩擦轮的 VSP PID 调用目前被注释了，所以直接改这三个参数**不会改变当前活动的摩擦轮控制**。下面讲的是：如果在隔离的仿真或测试版本中启用它，应怎样调。源码可见 [VSP_PID_Calc](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/component/controller/Feedforward_PID.c:34) 和 [摩擦轮调用处](F:/27fall/申请材料/03_源码实验/02_原始项目源码/resume/项目源码/RoboMaster英雄机器人电控系统/2025_Hero/application/Gimbal/launcher.c:276)。

公式是：

\[
K_p=k_0\log_{10}(k_1|e|)+k_2
\]

最直观的调参原则是：

- **\(k_0\)**：控制误差放大十倍时，\(K_p\) 增加多少；
- **\(k_1\)**：选择“哪一个误差大小作为参考点”；
- **\(k_2\)**：参考点上的 \(K_p\) 是多少。

## 用两个期望点算出三个参数

先不要盲猜 \(k\)。先问自己：

> 误差比较小时，我希望 \(K_p\) 是多少？误差很大时，我希望 \(K_p\) 是多少？

例如，假设用 RPM 表示误差，并通过仿真试出或确定：

- 误差为 \(10\text{ RPM}\) 时，希望 \(K_p=6\)；
- 误差为 \(1000\text{ RPM}\) 时，希望 \(K_p=10\)。

从 \(10\) 到 \(1000\) 是扩大 100 倍，也就是两个十倍。因此每扩大十倍，\(K_p\) 要增加：

\[
k_0=\frac{10-6}{\log_{10}(1000/10)}
=\frac{4}{2}=2
\]

接着把 \(10\text{ RPM}\) 选作参考误差。为了让误差等于 10 时对数部分为 0，取：

\[
k_1=\frac{1}{10}=0.1\ \text{RPM}^{-1}
\]

这样当 \(e=10\) 时，\(k_1|e|=1\)，而 \(\log_{10}(1)=0\)。于是 \(k_2\) 就直接设为参考点的增益：

\[
k_2=6
\]

得到：

\[
\boxed{
K_p=2\log_{10}(0.1|e|)+6
}
\]

检查一下：

| 误差 \(|e|\) | 算出来的 \(K_p\) |
|---:|---:|
| \(10\text{ RPM}\) | \(2\log_{10}(1)+6=6\) |
| \(100\text{ RPM}\) | \(2\log_{10}(10)+6=8\) |
| \(1000\text{ RPM}\) | \(2\log_{10}(100)+6=10\) |

这就是一种有依据的选法：先定低误差和大误差时想要的增益，再用公式算参数。

## 单独改一个参数，会发生什么？

### 改 \(k_0\)：改变曲线斜率

误差扩大十倍时，\(K_p\) 增加 \(k_0\)。

- 大误差追得不够有力、小误差表现正常：可以考虑增加 \(k_0\)；
- 大误差时过冲、振荡或频繁打到输出限幅：可以考虑减小 \(k_0\)。

但改 \(k_0\) 也会改变参考误差处的增益，所以之后通常还要重新校准 \(k_2\)。

### 改 \(k_2\)：整体提高或降低增益

\(k_2\) 对所有误差都加同一个固定量。

- 增大 \(k_2\)：大误差和小误差的 \(K_p\) 都提高；
- 减小 \(k_2\)：两者都降低。

因此，如果整条曲线都太高或太低，通常先调 \(k_2\)。

### 改 \(k_1\)：移动参考位置

\(k_1\) 会改变什么误差对应对数里的 1。它也会让整条曲线整体移动，效果和改变 \(k_2\) 有重叠。

所以 \(k_1\) 和 \(k_2\) **不是完全独立、各管一件事**。比较清楚的做法是先选一个参考误差 \(e_{\text{ref}}\)，设：

\[
k_1=\frac{1}{e_{\text{ref}}}
\]

然后让：

\[
k_2=K_p(e_{\text{ref}})
\]

这样参考点的含义明确，之后主要用 \(k_0\) 决定曲线斜率。

## 实际调参顺序

1. **先固定误差单位和循环周期。**例如一直用 RPM，不能调到一半又改成 rad/s；代码的差分和积分也受控制周期影响。
2. **先用普通固定 \(K_p\) 找到可用范围。**测试时暂时让 \(K_i,K_d\) 不干扰观察，先确认比例控制大致多强合适。
3. **选一个小误差和一个大误差。**例如 10 RPM 和 1000 RPM；这两个值应来自系统实际工作范围。
4. **分别定下这两个位置希望的 \(K_p\)。**再用前面的公式计算 \(k_0,k_1,k_2\)。
5. **逐步测试误差大小。**记录转速误差、过冲、稳定时间、输出峰值和限幅时间。不要只看“转得快不快”。
6. **最后再一起核对积分、微分和限幅。**VSP 公式只改变 \(K_p\)，不代表其它 PID 项可以忽略。

源码当前设置 \(k_0=1,k_1=8,k_2=5\)，但这组数字本身不能证明它是最佳参数；还需要测试记录支持。

## 实际使用前要处理的边界

当 \(e=0\) 时：

\[
\log_{10}(k_1|e|)=\log_{10}(0)
\]

没有有限结果。实际实现应先给误差大小设置一个下限，例如用：

\[
e_{\text{safe}}=\max(|e|,e_{\min})
\]

还应给 \(K_p\) 同时设最小值和最大值。当前源码对 \(K_p\) 做了最小值限制，但没有看到最大 \(K_p\) 限制；总输出限幅不能代替增益本身的上限。

另外，这份实现写的是 `abs(error)`，而 `error` 是浮点数。正式调参前应确认它使用的是浮点绝对值（通常是 `fabsf`），否则小数误差可能被当整数处理。

**一句话记住：先选两个误差大小以及希望的 \(K_p\)，再算三个 \(k\)；不要先随意改 \(k\)，再猜效果为什么变了。**
````

````text
# 一、滑模控制：控制摩擦轮转速

## 1. 控制器每次拿到什么？

每个控制周期，程序拿到两种转速：

- **目标转速**：摩擦轮应该达到的速度；
- **当前转速**：电机反馈回来的实际速度。

假设：

```text
目标：6000 RPM
实际：5900 RPM
```

误差定义为：

\[
e=\text{目标转速}-\text{实际转速}
\]

所以：

\[
e=6000-5900=100\text{ RPM}
\]

这表示：摩擦轮比目标慢 100 RPM。控制器要根据这个差距给电机一个命令，实际转速变化后，再重新读取并计算。

```text
目标 RPM 和当前 RPM
        ↓
算误差
        ↓
算电机命令
        ↓
摩擦轮转速改变
        ↓
读取新的 RPM，再算一遍
```

## 2. 为什么还要看“误差正在怎样变化”？

假设这一周期误差是 100 RPM，上个周期误差是 98 RPM。说明误差从 98 增加到了 100，目标与实际之间的差距正在扩大。

源码用下面的式子估计误差变化速度：

\[
\dot e\approx\frac{\text{本次误差}-\text{上次误差}}{\text{两次间隔}}
\]

若两次间隔是 \(0.001\) 秒：

\[
\dot e=\frac{100-98}{0.001}
=2000\text{ RPM/s}
\]

这里的 2000 不是电机速度，而是“转速误差每秒变化多少”。

## 3. \(\sigma\) 是什么？

代码再把误差和误差变化速度合在一起：

\[
\sigma=\dot e+ce
\]

你可以先把 \(\sigma\) 当成一个**综合判断值**：

- \(e\)：现在离目标差多少；
- \(\dot e\)：这个差距正在变大还是变小；
- \(c\)：调节“差距大小”在综合判断中占多少。

\(\sigma=0\) 对应一个希望误差遵循的变化关系：

\[
\dot e=-ce
\]

通俗地说：误差不但要存在，而且应该正在朝零缩小。滑模控制会根据偏离这种关系的程度来改变控制输出。

“滑模面”不是机器人里的实体表面；它是控制器用来描述“误差和误差变化应该满足什么关系”的数学说法。

## 4. 把这个项目的数代进去

这个源码中：

```text
c = 5
rho = 2
epsilon = 1
max_i = 10000
dt = 0.001 s
```

沿用上面的数字：

\[
e=100,\qquad \dot e=2000
\]

先算综合判断值：

\[
\sigma=2000+5\times100=2500
\]

这时 \(\sigma\) 大于边界 \(\epsilon=1\)，所以代码的饱和函数给出：

\[
\operatorname{sat}(\sigma)=1
\]

源码接着算：

\[
u_{\text{内部}}=-ce-\rho\operatorname{sat}(\sigma)
\]

\[
u_{\text{内部}}=-5\times100-2\times1=-502
\]

摩擦轮调用处又取了一次负号：

\[
\texttt{give\_current}=-u_{\text{内部}}=+502
\]

完整过程是：

```text
误差100 RPM、误差正在增加
→ sigma = 2500
→ sat(sigma) = 1
→ SMC内部输出 -502
→ 调用处再取负号
→ give_current = +502
```

这个 \(+502\) 是送给电机驱动接口的数字。它不是 502 RPM、502 安培或 502 牛米。具体让电机怎样转，还要看电机方向、驱动协议和电机本身。

## 5. 为什么用了 `sat`？

如果控制器只看 \(\sigma\) 的正负，并在正负之间突然切换，电机命令可能在零附近快速来回跳。`sat` 在 \(\sigma\) 接近零时让结果逐渐变化：

\[
\operatorname{sat}(\sigma)=
\begin{cases}
\sigma/\epsilon,&|\sigma|\leq\epsilon\\
1,&\sigma>\epsilon\\
-1,&\sigma<-\epsilon
\end{cases}
\]

例如 \(\epsilon=1\)：

- \(\sigma=0.5\)，结果是 0.5；
- \(\sigma=1\)，结果是 1；
- \(\sigma=10\)，结果仍是 1；
- \(\sigma=-10\)，结果是 -1。

它的作用是减少控制器在零附近突然切换的情况。注意，它**减少**抖动风险，不代表实际输出一定完全平滑。

## 6. 这份源码里的重要限制

当前源码中的误差单位是 RPM，差分结果是 RPM/s。代码把它们按参数 `c` 组合。要判断参数有没有清楚的物理单位，必须进一步查设计和标定记录；单看这几行只能准确描述程序怎样计算，不能证明整套控制器已经有完整的稳定性保证。

另外，`dt` 写成了 `0.001` 秒。如果实际调用间隔并不是 1 ms，误差变化率就可能算偏。RPM 若每次跳 1 个单位，除以 0.001 秒后就变成 \(1000\text{ RPM/s}\)，所以这个差分对测量跳动和控制周期比较敏感。

# 二、发射逻辑：开轮和送弹是两回事

发射机构有两个状态变量，含义不同：

- `fire_mode`：摩擦轮开还是关；
- `shoot_cmd`：拨盘这一发进行到哪一步。

所以，打开摩擦轮，不代表拨盘马上送弹。通常先让摩擦轮达到发射转速，然后才根据手动或自动命令让拨盘推进弹丸。

## 1. 手动单发的完整步骤

手动操作大致是：

```text
操作者打开摩擦轮
→ 三个摩擦轮开始追踪目标 RPM
→ 操作者触发单发
→ 程序登记“准备送一发”
→ 拨盘得到一个目标位置
→ 拨盘转到目标位置
→ 程序判断是否完成或堵转
```

源码中的状态可这样读：

| 状态 | 白话含义 |
|---|---|
| `SHOOT_CLOSE` | 单发流程关闭 |
| `SHOOT_READLY` | 收到单发请求，准备执行 |
| `SHOOT_SINGLE` | 正在执行这一发 |
| `SHOOT_OVER` | 这一发完成 |
| `SHOOT_BLOCK` | 发现拨盘可能卡住 |
| `SHOOT_BLOCK_BACK` | 正在尝试反方向恢复 |
| `SHOOT_FAIL` | 反向恢复仍未成功 |

代码里的 `READLY` 拼法如此，意思是 ready。

手动模式中，发射开关或鼠标点击会提出单发请求；如果上一发已经是 `SHOOT_OVER`，状态才进入 `SHOOT_READLY`。随后控制函数把状态改成 `SHOOT_SINGLE`，同时设置拨盘目标。

## 2. 自动发射的大致条件

源码的自动路径会检查：

- 有发射命令；
- 云台处于 `GIMBAL_AUTO`；
- 42 mm 发射机构热量小于代码阈值 100；
- 距上次自动发射超过 500 ms。

满足条件后，程序设置拨盘目标并开始单发。这些是**当前源码里的条件和参数**，不代表所有项目都采用同样的阈值。

## 3. 拨盘怎么知道该转多远？

拨盘电机编码器会累计计数。可以把累计编码值想成电机转过的“计数尺”。

源码中单发目标使用：

```text
DEGREE_60_TO_ENCODER = 26225 个编码计数
```

当前单发目标的计算是：

\[
\text{目标累计编码}
=
\text{当前累计编码}-26225
\]

也就是说，目标相对当前位置差 26225 个编码计数。这个数是程序按机构比例配置的，不应直接理解为电机轴上的“26225 度”。

编码器的方向约定决定了正负号代表哪边转。这里目标减小，表示沿这份程序定义的负方向转；真实机械方向需结合电机和编码器方向确认。

拨盘不是直接拿位置误差给电机，而是有两层控制：

```text
目标编码位置 − 当前编码位置
                  ↓
角度 PID：决定拨盘应该转多快
                  ↓
速度 PID：决定电机要收到多大的驱动命令
                  ↓
拨盘电机转动
```

如果目标位置差得很多，角度环通常给出较大的速度目标；快到目标时，位置差变小，速度目标也会减下来。速度环再根据“目标速度和当前 RPM 的差”算电机命令。

# 三、堵转判断：目标还有多远，等了多久？

把它想成拨盘要走到一条地面标记：

- 目标编码值：标记在哪里；
- 当前累计编码值：拨盘现在在哪；
- 两者差值：离标记还剩多远；
- 计时器：已经走了多久。

代码每次检查：

\[
\text{剩余误差}
=
|\text{目标累计编码}-\text{当前累计编码}|
\]

阈值是：

```text
剩余误差阈值：5000 个编码计数
时间阈值：1000 ms
```

代码没有直接说“电流大就是堵转”，而是看拨盘是否在规定时间内接近目标。

## 1. 数字例子：正常完成

假设当前累计编码是 100000，单发目标是：

\[
100000-26225=73775
\]

拨盘转动过程中，当前累计编码逐渐接近 73775。

例如当前到达 78000：

\[
|73775-78000|=4225
\]

4225 小于 5000，代码就认为拨盘已经足够接近目标，将状态改成 `SHOOT_OVER`。

## 2. 数字例子：暂时还没到，不急着判堵

假设发射开始 500 ms 后，当前位置是 85000：

\[
|73775-85000|=11225
\]

11225 大于 5000，但只过去 500 ms，小于 1000 ms。代码让拨盘继续执行，状态仍为 `SHOOT_SINGLE`。

这个等待时间很重要：刚开始走时，拨盘肯定还离目标较远，不能一开始就判堵。

## 3. 数字例子：超过时间还离目标很远

假设超过 1000 ms，当前位置仍然是 95000：

\[
|73775-95000|=21225
\]

21225 大于 5000，而且已经超过时间阈值，于是程序认为这一步可能堵住了，状态改成 `SHOOT_BLOCK`。

可以把判断概括成：

```text
还没走到目标附近
+ 已经等超过1秒
→ 判为拨盘堵转
```

# 四、判堵后怎样尝试恢复？

当状态为 `SHOOT_BLOCK`，程序会给拨盘一个新的目标：

```text
原目标 + 52450 个编码计数
```

52450 是源码中的 `DEGREE_120_TO_ENCODER`，约为单发 60° 增量的两倍。它的设计意图是让拨盘往反方向转一段，试着退出卡住位置。程序同时重新计时，并把状态改成 `SHOOT_BLOCK_BACK`。

继续用前面的例子：

```text
起点编码：100000
单发目标：73775
堵转时位置：95000
```

反向目标变为：

\[
73775+52450=126225
\]

从当前的 95000 到新目标 126225，数值方向与第一次目标相反。随后仍由角度 PID 和速度 PID 控制拨盘移动。

如果反向移动后剩余误差小于 5000，程序认为动作完成，进入 `SHOOT_OVER`；如果超过 1000 ms 后仍离目标大于 5000，则进入 `SHOOT_FAIL`。

“加 52450”是否在实际机械上确实让拨盘反转，要看编码器正方向约定；数值正负必须和实物运动方向核对。

## `SHOOT_FAIL` 就一定会停电吗？

不能仅凭这个状态名这么认为。当前检查到的控制路径里，`SHOOT_FAIL` 表示恢复失败，但没有在这个状态分支里明确把拨盘电流设为零。拨盘是否停止，还要看别处有没有处理这个状态。

这份源码能明确看到：

- Fire_OFF 路径会把拨盘电流命令设为零；
- `GIMBAL_RELAX` 路径会调用 `Launcher_Relax_Handle`，将各路命令归零；
- `SHOOT_FAIL` 状态本身不等于上述两个动作。

所以阅读保护逻辑时，要查“失败状态有没有真正改变电机输出”，不能只看状态名称。
````

````text
## 一、滑模控制是什么

滑模控制（Sliding Mode Control, SMC）是一种鲁棒控制方法。它的核心思想是：

> 先定义一条“理想轨道”（滑模面），然后用控制力把系统状态逼到这条轨道上，一旦上了轨道，就让它沿轨道滑向目标。

“滑模”名字的来源：

- **滑模面**：定义的一条理想关系。
- **滑模控制**：用控制力把系统状态逼到这条面上，再让它沿面滑动到目标。

### 1.1 为什么需要滑模控制

PID 的局限：

- 系统参数变化大时，效果变差。
- 有外部扰动时，恢复慢。
- 模型不准时，增益需要重新调整。

滑模控制的优势：

- 对参数变化和外部扰动鲁棒。
- 只要控制力足够大，就能把状态逼到滑模面上。
- 设计相对简单。

代价：

- 控制输出可能高频切换，产生抖振。
- 需要误差变化率，对噪声敏感。
- 控制力可能较大。
- 用饱和函数减少抖振后，会留下边界层残差。

---

## 二、滑模面

### 2.1 定义

P3 源码里的滑模面：

\[
s = \dot e + c \cdot e
\]

其中：

- \(e = \text{target\_rpm} - \text{measured\_rpm}\)：转速误差。
- \(\dot e = \frac{e - e_{\text{previous}}}{dt}\)：误差变化率。
- \(c\)：正系数，决定误差收敛速度。

### 2.2 滑模面代表什么

\(s = 0\) 就是滑模面。它定义了一个理想关系：

\[
\dot e = -c \cdot e
\]

这是一个一阶微分方程。解为：

\[
e(t) = e(0) \cdot e^{-ct}
\]

意思是：如果系统一直在滑模面上，误差会以指数速度衰减到零。

**重要**：滑模面不是“误差为零”，而是“误差以指定速度收敛到零”。

### 2.3 相平面可视化

把误差 \(e\) 画在横轴，误差变化率 \(\dot e\) 画在纵轴，得到相平面。滑模面 \(s = 0\) 是一条过原点的直线，斜率为 \(-c\)。

```text
ė
 ↑
 |\
 | \   ← 滑模面 s = 0
 |  \
 |   \
 |    \
 |     \________→ e
```

系统当前状态是平面上的一个点。目标是到达原点 (0, 0)。

---

## 三、微分方程 \(e(t) = e(0) \cdot e^{-ct}\) 的推导

### 3.1 从滑模面得到微分方程

滑模面 \(s = 0\) 意味着：

\[
\dot e + c \cdot e = 0
\]

即：

\[
\frac{de}{dt} = -c \cdot e
\]

翻译：e 越大，减得越快；e 越小，减得越慢。

### 3.2 解微分方程

分离变量：

\[
\frac{1}{e} \, de = -c \, dt
\]

两边积分：

\[
\ln e = -c t + C
\]

取指数：

\[
e = e^{-ct + C} = e^{-ct} \cdot e^C
\]

当 \(t = 0\) 时，\(e(0) = e^C\)，所以：

\[
e(t) = e(0) \cdot e^{-ct}
\]

### 3.3 数字验证

取 \(c = 5\)，\(e(0) = 100\)：

| t | e(t) = 100 × e^{-5t} |
|---|---|
| 0 | 100 |
| 0.1 | 60.65 |
| 0.2 | 36.79 |
| 0.4 | 13.53 |
| 0.6 | 4.98 |

每过 0.2 秒，误差缩小到约 37%。

### 3.4 在滑模控制中的意义

- 只要系统在滑模面上，误差就会按此公式自动衰减。
- \(c\) 越大，衰减越快，但控制力可能越大。
- 代码中不需要真的计算 \(e(0)e^{-ct}\)，控制器每个周期重新计算，自动实现这个行为。

---

## 四、控制律

### 4.1 控制律公式

源码中的控制律：

\[
u_{\text{internal}} = -c \cdot e - \rho \cdot \text{sat}\left(\frac{s}{\epsilon}\right)
\]

拆成两部分：

| 部分 | 名称 | 作用 |
|---|---|---|
| \(-c \cdot e\) | 等效控制 | 维持系统在滑模面上，驱动误差按指数衰减 |
| \(-\rho \cdot \text{sat}(s/\epsilon)\) | 趋近控制 | 把系统从任意位置推到滑模面上 |

### 4.2 等效控制 \(-c \cdot e\) 的来源

假设系统已经在滑模面上，\(s = 0\)，则 \(\dot e = -c e\)。

考虑一阶系统 \(\dot v = u + d\)，误差 \(e = \text{target} - v\)，则 \(\dot e = -u - d\)。

代入 \(\dot e = -c e\)，得 \(u = c e - d\)。忽略扰动 \(d\)，得 \(u \approx c e\)。

源码中符号可能相反，取决于误差定义和电机正方向。关键是：等效控制来自“假设系统在滑模面上，反推所需控制力”。

### 4.3 趋近控制 \(-\rho \cdot \text{sat}(s/\epsilon)\) 的来源

如果系统不在滑模面上，\(s \neq 0\)，需要额外的力把系统推回滑模面。

- 若 \(s > 0\)，需要往负方向推。
- 若 \(s < 0\)，需要往正方向推。

理想情况用 \(\text{sign}(s)\)，但会在 \(s=0\) 附近高频切换，产生抖振。因此用饱和函数 \(\text{sat}(s/\epsilon)\) 替代。

- \(\rho\)：趋近增益，越大推得越快，但可能抖振。
- \(\epsilon\)：边界层宽度，越大越平滑，但残差越大。

### 4.4 饱和函数

\[
\text{sat}(s/\epsilon) =
\begin{cases}
s/\epsilon, & |s| \leq \epsilon \\
+1, & s > \epsilon \\
-1, & s < -\epsilon
\end{cases}
\]

作用：在 \(s=0\) 附近平滑过渡，减少抖振。代价：边界层内不再严格保证 \(s \to 0\)，会留下小残差。

---

## 五、系统如何到达并沿滑模面运动

### 5.1 到达滑模面

如果系统不在滑模面上，趋近控制 \(-\rho \cdot \text{sat}(s/\epsilon)\) 主导，把系统状态推向滑模面。

相平面示意：

```text
ė
 ↑
 |\
 | \   A ●
 |  \ /
 |   ●  ← 到达滑模面
 |  /
 | /
 |/________________→ e
```

### 5.2 沿滑模面滑动

一旦系统到达滑模面，\(s \approx 0\)，趋近控制近似为零，等效控制 \(-c \cdot e\) 主导。

在滑模面上，\(\dot e = -c e\)，误差按 \(e(t) = e(0)e^{-ct}\) 衰减。系统沿滑模面向原点移动。

**关键**：沿滑模面滑动不是自然发生的，而是等效控制 \(-c \cdot e\) 持续作用的结果。它不断抵消扰动，驱动误差衰减。

## 六、源码实现

### 6.1 代码流程

```c
// 1. 计算误差
e = target_rpm - measured_rpm;

// 2. 计算误差变化率
e_dot = (e - previous_error) / dt;

// 3. 计算滑模面
s = e_dot + c * e;

// 4. 饱和函数
if (fabs(s) <= epsilon) {
    sat = s / epsilon;
} else {
    sat = (s > 0) ? 1.0 : -1.0;
}

// 5. 控制律
u_internal = -c * e - rho * sat;

// 6. 限幅
if (u_internal > max_i) u_internal = max_i;
if (u_internal < -max_i) u_internal = -max_i;

// 7. 保存误差
previous_error = e;

// 8. 外部负号
give_current = -u_internal;
```

### 6.2 参数与手算

源码参数：

| 符号 | 值 | 含义 |
|---|---|---|
| \(c\) | 5 | 滑模面系数 |
| \(\rho\) | 2 | 趋近增益 |
| \(\epsilon\) | 1 | 边界层宽度 |
| \(dt\) | 0.001 s | 差分时间步 |
| \(max\_i\) | 10000 | 输出限幅 |

手算例子：

- 目标 RPM = 6000
- 测得 RPM = 5900
- 上次误差 = 98

计算：

\[
e = 100
\]

\[
\dot e = \frac{100 - 98}{0.001} = 2000
\]

\[
s = 2000 + 5 \times 100 = 2500
\]

\(|s| > \epsilon\)，所以 \(\text{sat} = +1\)。

内部输出：

\[
u_{\text{internal}} = -5 \times 100 - 2 \times 1 = -502
\]

外部负号：

\[
give\_current = +502
\]

注意：502 是协议电流尺度，不是安培，也不是实测转速。

## 七、外部负号的作用

### 7.1 为什么有外部负号

源码中：

- `SMC.c` 内部：\(u_{\text{internal}} = -c e - \rho \cdot \text{sat}\)
- `launcher.c` 调用：\(give\_current = -u_{\text{internal}}\)

外部负号是为了**修正电机安装方向**。控制器假设正输出使电机正转，但实际电机可能相反。若不加负号，系统会发散。

### 7.2 为什么不在控制器内部改

控制器是通用模块，不同电机方向可能不同。将方向修正放在调用处，使算法与硬件解耦。

### 7.3 数字例子

内部 \(-502\)，外部加负号后 \(+502\)。最终命令方向符合实际电机。

### 7.4 读源码原则

内部符号和外部符号必须一起看，不能只看一半。文档强调：“应从误差、函数输出、调用处符号一路算到最后的电流字段。”
````

````text
# 第一部分：发射逻辑

## 一、发射机构的两个部件

发射机构不是单一执行器，它由两部分组成：

| 部件 | 作用 | 控制目标 | 反馈 |
|---|---|---|---|
| 摩擦轮 | 高速旋转，靠表面摩擦把弹丸带出去 | 保持目标转速 RPM | 电机 RPM、电流 |
| 拨盘 | 转动弹仓，把弹丸送到发射位置 | 转到目标角度、完成送弹 | 累计编码器角、速度、电流 |

这两个部件**控制问题不同**：

- 摩擦轮：主要控制**转速**，弹丸撞击后会掉速，需要恢复。
- 拨盘：主要控制**位置和送弹状态**，要转到确定角度，还要判断是否堵住。

不能把它们当成同一个控制器。

## 二、发射状态机

### 2.1 状态枚举

| 状态 | 含义 | 动作 |
|---|---|---|
| READY | 准备发射 | 摩擦轮达到目标转速，等待发射指令 |
| SINGLE | 单发 | 拨盘转一个角度，送出一颗弹 |
| BLOCK | 堵转 | 拨盘卡住，需要处理 |
| BACK | 退弹 | 反向转，退出卡住的弹 |
| FAIL | 失败 | 多次尝试仍失败，停止 |
| RELAX | 放松 | 所有电流归零，重置累计角参考 |

### 2.2 状态转移表

| 当前状态 | 事件 | 下一状态 | 动作 |
|---|---|---|---|
| RELAX | 收到使能 | READY | 摩擦轮加速 |
| READY | Fire_ON | SINGLE | 设置拨盘目标角 |
| SINGLE | 到达目标角 | READY | 完成送弹 |
| SINGLE | 角差>阈值且超时 | BLOCK | 拨盘停止 |
| BLOCK | 自动处理 | BACK | 反向退弹 |
| BACK | 到达退弹角 | READY | 退弹成功 |

| 任意 | 多次失败 | FAIL | 停止，等待人工 |

## 三、Fire_ON 和 Fire_OFF

### 3.1 Fire_ON

```text
Fire_ON:
  设置三个摩擦轮正负目标 RPM
  用裁判弹速变化调整 fire_speed
  拨盘状态从 READY 进入 SINGLE
```

- 三个摩擦轮：左、右、上。
- 目标转速根据需要的弹速计算。
- `fire_speed` 可能根据裁判反馈的弹速变化调整。

### 3.2 Fire_OFF

```text
Fire_OFF:
  非 RELAX 时：把速度参考设为 0
  但 SMC 仍可能产生制动电流
  不能说 Fire_OFF 必然所有摩擦轮电流为 0
```

关键区别：

- Fire_OFF 把目标轮速设为 0。

## 五、堵转逻辑

### 5.1 为什么需要堵转判断

拨盘送弹时，如果弹丸卡住：

- 电机继续转，但拨盘转不动。
- 电流持续增大。
- 可能烧电机或损坏机构。

所以需要检测堵转，并及时处理。

### 5.2 常见错误做法

> 电流大就是堵转。

这是不对的。因为：

- 启动瞬间电流也大。
- 加速时电流也大。
- 负载变化时电流也大。

只看电流会误判。

### 5.3 源码做法

文档说：

> 堵转判断用目标与累计编码差、HAL 时间和状态，不是简单“电流大即堵转”。

翻译：

- **目标与累计编码差**：拨盘应该转到的角度，和实际转到的角度，差多少。
- **HAL 时间**：从开始送弹到现在，过了多久。
- **状态**：当前在 SINGLE、BLOCK 还是其他状态。

判断逻辑：

```text
如果：
  拨盘在 SINGLE 状态
  目标角度和实际角度差 > TRI_MINECD
  持续时间 > MAXTIME
则：
  判定为堵转
  进入 BLOCK 状态
```

### 5.4 阈值

文档提到：

- `TRI_MINECD = 5000`
- `MAXTIME = 1000`

解释：

- `TRI_MINECD`：编码器差值阈值。
- `MAXTIME`：时间阈值。

注意：

- 5000 个编码器计数对应多少角度？要看编码器一圈多少计数。
- 1000 是什么单位？tick 还是 ms？要看 HAL 时间定义。
- 等于阈值的分支还要注意严格 `<` 和 `>`。

### 5.5 堵转处理

```text
进入 BLOCK:
  停止拨盘电机
  feeder_target_speed = 0
  feeder_give_current = 0（或制动电流）
  摩擦轮：保持当前目标转速，不停
  jam_counter += 1
```

### 5.6 退弹

```text
进入 BACK:
  feeder_target_angle = feeder_current_angle - 退弹角度
  示例：feeder_current_angle = 10050
       退弹角度 = 2048
       feeder_target_angle = 8002
  feeder_target_speed = 负值（反向转）
  feeder_give_current = 负值
  trigger_timer = 0（重置计时）
```

退弹逻辑：

- 反向转，把卡住的弹退出来。
- 退弹角度通常比送弹角度小。
- 退弹速度可能比送弹慢，避免二次卡住。

### 5.7 退弹成功或失败

```text
退弹成功:
  状态：BACK → READY
  feeder_current_angle ≈ feeder_target_angle
  angle_error ≈ 0
  弹已退出，机构恢复正常

退弹失败:
  状态：BACK
  feeder_current_angle 几乎不变
  angle_error 仍然大
  trigger_timer 递增
  超过 MAXTIME 后再次判定堵转
  jam_counter += 1
  如果 jam_counter < 最大尝试次数：再次进入 BACK 或 BLOCK
  如果 jam_counter >= 最大尝试次数：进入 FAIL
```

### 5.8 FAIL

```text
状态：FAIL
feeder_target_speed = 0
feeder_give_current = 0
摩擦轮：可能继续转，也可能停止，取决于设计
等待人工处理或重新初始化
```

## 六、摩擦轮滑模控制（SMC）

### 6.1 滑模面

\[
s = \dot e + c \cdot e
\]

其中：

- \(e = \text{target\_rpm} - \text{measured\_rpm}\)：转速误差。
- \(\dot e = (e - e_{\text{previous}}) / dt\)：误差变化率。
- \(c\)：正系数。

### 6.2 滑模面意义

\(s = 0\) 定义了一个理想关系：

\[
\dot e = -c \cdot e
\]

解为：

\[
e(t) = e(0) \cdot e^{-ct}
\]

误差按指数速度衰减到零。

### 6.3 控制律

\[
u_{\text{internal}} = -c \cdot e - \rho \cdot \text{sat}\left(\frac{s}{\epsilon}\right)
\]

拆成两部分：

| 部分 | 名称 | 作用 |
|---|---|---|
| \(-c \cdot e\) | 等效控制 | 维持系统在滑模面上 |
| \(-\rho \cdot \text{sat}(s/\epsilon)\) | 趋近控制 | 把系统推到滑模面上 |

### 6.4 饱和函数

\[
\text{sat}(s/\epsilon) =
\begin{cases}
s/\epsilon, & |s| \leq \epsilon \\
+1, & s > \epsilon \\
-1, & s < -\epsilon
\end{cases}
\]

作用：在 \(s=0\) 附近平滑过渡，减少抖振。代价：边界层内留下小残差。

### 6.5 源码参数与手算

| 符号 | 值 | 含义 |
|---|---|---|
| \(c\) | 5 | 滑模面系数 |
| \(\rho\) | 2 | 趋近增益 |
| \(\epsilon\) | 1 | 边界层宽度 |
| \(dt\) | 0.001 s | 差分时间步 |
| \(max\_i\) | 10000 | 输出限幅 |

手算：

- 目标 RPM = 6000
- 测得 RPM = 5900
- 上次误差 = 98

\[
e = 100
\]

\[
\dot e = \frac{100 - 98}{0.001} = 2000
\]

\[
s = 2000 + 5 \times 100 = 2500
\]

\[
\text{sat} = +1
\]

\[
u_{\text{internal}} = -5 \times 100 - 2 \times 1 = -502
\]

外部负号：

\[
give\_current = +502
\]

注意：502 是协议电流尺度，不是安培。

### 6.6 外部负号

- 内部：\(u_{\text{internal}} = -c e - \rho \cdot \text{sat}\)
- 外部：\(give\_current = -u_{\text{internal}}\)

外部负号是为了**修正电机安装方向**。控制器假设正输出使电机正转，但实际电机可能相反。

### 6.7 版本说明

- `launcher.c` 定义了普通 PID 和 VSP 参数并初始化。
- 当前三个 `VSP_PID_Calc` 调用**被注释**。
- 实际活动代码是 `update_system → -smc_controller`。
- 不能说 PID、VSP、SMC 同时并行使用。

## 七、教学代码 launcher_control.py

### 7.1 被控对象

```python
speed += dt * (u - speed - load) / TIME_CONSTANT
```

- `TIME_CONSTANT = 0.15` s
- 模型：`0.15 * v_dot = u - v - load`
- 目标 = 1（归一化速度）
- 负载在 t ∈ [1, 1.2) 时为 0.6，其余为 0

### 7.2 PI 控制器

```python
candidate = np.clip(integral + error * dt, -1, 1)
raw = 4 * error + 3 * candidate
if abs(raw) < 5 or raw * error < 0:
    integral = candidate
u = np.clip(4 * error + 3 * integral, -5, 5)
```

- P = 4，I = 3
- 有抗积分饱和
- 输出限幅 ±5

### 7.3 边界滑模控制器

```python
def sliding_speed_control(error, rate, gain, boundary):
    return float(rate + TIME_CONSTANT * gain * np.clip(error / boundary, -1, 1))
```

- `rate` 参数实际是**测得轮速 v**，不是误差导数。
- 滑模面：`s = error = 1 - v`。
- 控制律：`u = v + T * k * sat(e/φ)`。

### 7.4 手算

v = 0.9，e = 0.1，k = 5，φ = 0.2：

- `sat = 0.1 / 0.2 = 0.5`
- `u = 0.9 + 0.15 × 5 × 0.5 = 1.275`
- 无负载：`v_dot = (1.275 - 0.9) / 0.15 = 2.5`
- `e_dot = -2.5`

### 7.5 教学 vs 源码

| | 源码 | 教学 |
|---|---|---|
| 滑模面 | `s = e_dot + c e` | `s = e = 1 - v` |
| 控制律 | `u = -c e - ρ sat(s/ε)` | `u = v + T k sat(e/φ)` |
| 外部负号 | 有 | 无 |
| 拨盘逻辑 | 有 | 无 |
| 堵转判断 | 有 | 无 |

教学脚本只覆盖摩擦轮转速控制，不覆盖完整发射逻辑。

# 第二部分：麦轮运动学与轮速反馈

## 一、麦轮结构

### 1.1 普通轮子 vs 麦轮

普通轮子：

- 只能沿一个方向滚动。
- 想横移，必须整辆车转方向。

麦轮：

- 轮子外圈有一圈斜着的小滚子。
- 滚子允许轮子在某个方向自由滑动。
- 同时轮子的驱动方向仍能推地。

### 1.2 X 型布局

```text
FL ↘        ↙ FR
     \      /
      \    /
      /    \
     /      \
RL ↗        ↖ RR
```

- FL：左前
- FR：右前
- RL：左后
- RR：右后

---

## 二、为什么每只轮子不只管一个方向

车体要：

- 前进 \(v_x\)
- 横移 \(v_y\)
- 旋转 \(\omega\)

四只轮子都会同时感受到这三种运动的影响。

每只轮子的目标转速：

\[
\omega_w = \frac{1}{r} \cdot (\text{前进分量} + \text{横移分量} + \text{旋转分量})
\]

---

## 三、麦轮矩阵推导

### 3.1 轮子处的速度

轮子不只在车体中心，它在四个角上。

车体既有平移，又有旋转。

轮子处的总速度：

\[
\vec{v}_{\text{wheel}} = \vec{v}_{\text{body}} + \vec{\omega} \times \vec{r}
\]

二维叉积：

\[
\omega \times (r_x, r_y) = (-\omega \cdot r_y, \omega \cdot r_x)
\]

所以：

\[
\vec{v}_{\text{wheel}} = (v_x - \omega r_y, \quad v_y + \omega r_x)
\]

### 3.2 为什么 \(\omega \times (r_x, r_y) = (-\omega r_y, \omega r_x)\)

三维叉积：

\[
(a_1, a_2, a_3) \times (b_1, b_2, b_3) = (a_2 b_3 - a_3 b_2, \quad a_3 b_1 - a_1 b_3, \quad a_1 b_2 - a_2 b_1)
\]

代入 \(\vec{\omega} = (0, 0, \omega)\)，\(\vec{r} = (r_x, r_y, 0)\)：

- 第一分量：\(0 \cdot 0 - \omega \cdot r_y = -\omega r_y\)
- 第二分量：\(\omega \cdot r_x - 0 \cdot 0 = \omega r_x\)
- 第三分量：\(0 \cdot r_y - 0 \cdot r_x = 0\)

结果：

\[
\vec{\omega} \times \vec{r} = (-\omega r_y, \omega r_x, 0)
\]

### 3.3 投影到驱动方向

麦轮有两个方向：

| 方向 | 含义 | 能否传递力 |
|---|---|---|
| 驱动方向 | 轮子转动时推地的方向 | 能 |
| 自由方向 | 滚子允许滑动的方向 | 不能 |

只有驱动方向分量驱动轮子。

投影 = 点乘。

### 3.4 逐轮推导

| 轮子 | 位置 | 驱动方向 | 投影公式 |
|---|---|---|---|
| FL | \((a, b)\) | \((1, -1)\) | \((v_x - \omega b) - (v_y + \omega a)\) |
| FR | \((a, -b)\) | \((1, 1)\) | \((v_x + \omega b) + (v_y + \omega a)\) |
| RL | \((-a, b)\) | \((1, 1)\) | \((v_x - \omega b) + (v_y - \omega a)\) |
| RR | \((-a, -b)\) | \((1, -1)\) | \((v_x + \omega b) - (v_y - \omega a)\) |

### 3.5 矩阵形式

\[
\omega_w = \frac{1}{r}
\begin{bmatrix}
1 & -1 & -d \\
1 & 1 & d \\
1 & 1 & -d \\
1 & -1 & d
\end{bmatrix}
\begin{bmatrix}
v_x \\ v_y \\ \omega
\end{bmatrix}
\]

其中 \(d = a + b\)。

### 3.6 每列含义

| 列 | 含义 |
|---|---|
| 第一列 | 前进，四轮都加 |
| 第二列 | 横移，对角正负 |
| 第三列 | 旋转，左负右正 |

## 五、源码轮序和教学不同

### 5.1 源码公式

```text
wheel0 = (vy - vx + vw * rotate_ratio_f)   // RF
wheel1 = (vy + vx + ...)                    // LF
wheel2 = (-vy - vx + vw * rotate_ratio_b)  // RB
wheel3 = (-vy + vx + ...)                   // LB
```

源码轮序：RF/LF/RB/LB。

教学轮序：FL/FR/RL/RR。

### 5.2 不能直接换

| 项目 | 教学 | 源码 |
|---|---|---|
| 轮序 | FL/FR/RL/RR | RF/LF/RB/LB |
| 前进方向 | +x 前 | 源码自己的约定 |
| 横移方向 | +y 左 | 源码自己的约定 |
| 旋转比例 | d = a + b | rotate_ratio_f、rotate_ratio_b 可能不同 |
| 电机正方向 | 教学定义 | 实际电机安装 |

必须显式对齐。

## 六、统一缩放

### 6.1 为什么需要缩放

四轮目标 RPM 可能超过电机上限。

### 6.2 独立截断的问题

```text
[100, 200, -100, -200] → [100, 150, -100, -150]
```

比例变了，车会往别的方向走。

### 6.3 统一缩放

```text
max = 200
scale = 150 / 200 = 0.75
[100, 200, -100, -200] × 0.75 = [75, 150, -75, -150]
```

比例保持，整体变慢。

### 6.4 源码实现

```text
先算 int16_t wheel_rpm
再求 max
如果 max > M3508_MAX_RPM
  统一乘 scale = M3508_MAX_RPM / max
```

整数化会有小量化误差。

## 八、矩阵的逆

### 8.1 为什么需要逆

已知四轮速度，反推车体运动：

\[
\text{body} = A^+ \cdot \omega_w
\]

用途：里程计、打滑检测、状态估计。

### 8.2 相容性

\(A\) 是 4×3，满列秩。

任意四轮速度不一定满足无滑动的刚体运动。

只有落在 \(A\) 的列空间里的四轮速度，才对应真实刚体运动。

### 8.3 打滑影响

单轮打滑时，理想矩阵不再准确，里程计会漂。

# 第三部分：功率缓冲与输出缩放

## 一、为什么需要功率限制

### 1.1 现实场景

英雄机器人同时要做很多事：

- 云台跟踪目标。
- 摩擦轮高速旋转。
- 拨盘准备送弹。
- 底盘快速移动。

这些都需要电。但电池和裁判系统有功率上限。

如果不管功率：

- 可能触发裁判罚则。
- 可能拉低电压，影响其他子系统。
- 可能烧保险丝。

### 1.2 谁来提供功率预算

裁判系统会给出：

| 信息 | 含义 |
|---|---|
| `chassis_power_limit` | 底盘允许的功率上限 |
| `power_management_chassis_output` | 是否允许底盘输出 |
| 缓冲能量信息 | 超级电容还剩多少能量 |

源码里：

```text
限制来源 = Referee.GameRobotStat.chassis_power_limit - 5
```

减 5 留余量。

## 二、基础物理：功率、能量、电流

### 2.1 功率 W

功率是**每秒使用多少能量**。

\[
P = \frac{dE}{dt}
\]

单位：瓦特，W = J/s。

机械功率：

\[
P = \tau \cdot \omega
\]

电功率：

\[
P \approx U \cdot I
\]

铜耗：

\[
P_{\text{铜}} = I^2 R
\]

### 2.2 能量 J

能量是**存量**。

\[
E = \int P \, dt
\]

单位：焦耳，J。

缓冲能量：

\[
E_{\text{next}} \approx E + (P_{\text{allow}} - P_{\text{used}}) \cdot dt
\]

### 2.3 功率和能量的区别

| | 功率 | 能量 |
|---|---|---|
| 单位 | W = J/s | J |
| 含义 | 每秒用多少 | 总共还剩多少 |
| 类比 | 水龙头流量 | 水箱里有多少水 |

### 2.4 缓冲能量公式解释

想象一个水箱：

- 进水口：允许功率 \(P_{\text{allow}}\)，单位 W。
- 出水口：实际功率 \(P_{\text{used}}\)，单位 W。
- 水箱里的水：缓冲能量 \(E\)，单位 J。

净功率：

\[
P_{\text{allow}} - P_{\text{used}}
\]

- 正：缓冲充电。
- 负：缓冲放电。

乘以 \(dt\)：

\[
(P_{\text{allow}} - P_{\text{used}}) \times dt
\]

单位：W × s = J。

加到 \(E\) 上：

\[
E_{\text{next}} = E + (P_{\text{allow}} - P_{\text{used}}) \times dt
\]

### 2.5 超级电容

超级电容就像一个水桶：

- 电机需要大功率时，水桶帮忙放水。
- 电机功率需求低时，水桶存水。

裁判看的是电池输出是否超过上限，电容充放电是内部的事。

---

## 三、功率模型 \(P(k) = a k^2 + b k + c\)

### 3.1 一个电机的功率组成

机械功率：

\[
P_{\text{mech}} = \tau \cdot \omega
\]

铜耗：

\[
P_{\text{copper}} = I^2 \cdot R
\]

总功率：

\[
P = P_{\text{mech}} + P_{\text{copper}} + P_{\text{other}}
\]

### 3.2 缩放系数 k

源码把四个轮子的**目标速度**都乘一个系数 k：

\[
\omega_{\text{target}}' = k \cdot \omega_{\text{target}}
\]

### 3.3 缩放后电流怎么变

稳态下电流和力矩成正比：

\[
\tau = K_t \cdot I
\]

目标速度降低后，所需力矩也变小：

\[
I' \propto \tau' \propto k \cdot I
\]

### 3.4 机械功率怎么变

- 如果负载是粘性摩擦：力矩和速度都乘 k，机械功率乘 k²。
- 如果负载是恒定摩擦：力矩不变，机械功率乘 k。
- 真实负载介于两者之间。

所以机械功率是两部分之和：

\[
P_{\text{mech}}' = a_1 \cdot k^2 + b_1 \cdot k
\]

### 3.5 铜耗怎么变

\[
P_{\text{copper}}' = (k \cdot I)^2 \cdot R = k^2 \cdot I^2 R = k^2 \cdot P_{\text{copper}}
\]

铜耗乘 k²。

### 3.6 静态损耗

驱动器、传感器、控制器本身也耗电，基本不随 k 变，是常数：

\[
P_{\text{static}} = c
\]

### 3.7 合起来

\[
P(k) = \underbrace{a k^2}_{\text{铜耗 + 部分机械}} + \underbrace{b k}_{\text{另一部分机械}} + \underbrace{c}_{\text{静态}}
\]

| 系数 | 来源 | 物理含义 |
|---|---|---|
| \(a\) | \(I^2 R\) + 部分机械功率 | 与 k² 成正比 |
| \(b\) | 部分机械功率 | 与 k 成正比 |
| \(c\) | 常数项 | 静态损耗 |

---

## 四、a、b、c 怎么算

### 4.1 核心思路

a、b、c 不是直接给的，而是**用轮 PID 参数和测得 RPM 算出来的**。

### 4.2 单个轮子的电流

轮 PID 输出：

\[
I = K_p \cdot e + K_i \cdot \int e
\]

误差：

\[
e = \text{target\_rpm} - \text{measured\_rpm}
\]

缩放后：

\[
e(k) = k \cdot \text{target\_rpm} - \text{measured\_rpm}
\]

代入：

\[
I(k) = K_p \cdot (k \cdot \text{target\_rpm} - \text{measured\_rpm}) + K_i \cdot \int e
\]

整理：

\[
I(k) = A \cdot k + B
\]

其中：

\[
A = K_p \cdot \text{target\_rpm}
\]

\[
B = -K_p \cdot \text{measured\_rpm} + K_i \cdot \int e
\]

### 4.3 单个轮子的功率

\[
P(k) = (A k + B)^2 R + K_t (A k + B) \cdot k \cdot \omega_{\text{target}}
\]

展开合并：

\[
P(k) = \underbrace{(R A^2 + K_t A \omega_{\text{target}})}_{a_i} k^2 + \underbrace{(2RAB + K_t B \omega_{\text{target}})}_{b_i} k + \underbrace{RB^2}_{c_i}
\]

### 4.4 四个轮子加起来

\[
a = \sum_{i=1}^{4} a_i
\]

\[
b = \sum_{i=1}^{4} b_i
\]

\[
c = \sum_{i=1}^{4} c_i
\]

### 4.5 简化理解

| 系数 | 来源 | 物理含义 |
|---|---|---|
| \(a\) | 铜耗和部分机械功率 | 与 k² 成正比 |
| \(b\) | 部分机械功率 | 与 k 成正比 |
| \(c\) | 静态损耗 | 常数 |

a、b、c 都是从 PID 参数和 RPM 算出来的，不是手动设的。

---

## 五、判断是否超出功率限制

### 5.1 方法

先用 k=1 代入，算当前功率：

\[
P(1) = a \cdot 1^2 + b \cdot 1 + c = a + b + c
\]

- 如果 \(P(1) \leq P_{\text{limit}}\)：不超限，k=1，不缩放。
- 如果 \(P(1) > P_{\text{limit}}\)：超限，需要解方程找 k < 1。

### 5.2 举例

假设：

- \(a = 0.5\)
- \(b = 2.0\)
- \(c = 1.0\)
- \(P_{\text{limit}} = 25\) W

\[
P(1) = 0.5 + 2.0 + 1.0 = 3.5 \text{ W}
\]

\[
3.5 < 25
\]

不超限。

再假设：

- \(a = 10\)
- \(b = 20\)
- \(c = 5\)

\[
P(1) = 10 + 20 + 5 = 35 \text{ W}
\]

\[
35 > 25
\]

超限，需要缩放。

---

## 六、解二次式求 k

### 6.1 目标

要满足：

\[
a k^2 + b k + c \leq P_{\text{limit}}
\]

即：

\[
a k^2 + b k + (c - P_{\text{limit}}) = 0
\]

### 6.2 求根

\[
k = \frac{-b \pm \sqrt{b^2 - 4a(c - P_{\text{limit}})}}{2a}
\]

取合理根，限制在 [0, 1]。

### 6.3 限制 k

- \(k < 0\)：取 0。
- \(k > 1\)：取 1。
- \(0 \leq k \leq 1\)：正常。

### 6.4 边界情况

| 情况 | 处理 |
|---|---|
| \(a \approx 0\) | 退化为一次方程 |
| 判别式 < 0 | 无实数解 |
| \(c > P_{\text{limit}}\) | 即使 k=0 也超 |
| 所有系数为 0 | 无功率信息 |

### 6.5 完整例子

假设：

- \(a = 10\)
- \(b = 20\)
- \(c = 5\)
- \(P_{\text{limit}} = 25\)

\[
10 k^2 + 20 k + 5 = 25
\]

\[
10 k^2 + 20 k - 20 = 0
\]

\[
k^2 + 2k - 2 = 0
\]

\[
k = \frac{-2 + \sqrt{4 + 8}}{2} = \frac{-2 + 3.464}{2} = 0.732
\]

## 七、恢复平滑

### 7.1 公式

\[
k_c \leftarrow k_c + (1 - k_c) \cdot k
\]

- \(k_c\)：当前实际用的缩放系数。
- \(k\)：恢复速度参数，比如 0.1。
- \(1 - k_c\)：距离 1 还有多远。

翻译：

> 每周期让 \(k_c\) 向 1 靠近一点点。

### 7.2 数字走一遍

假设 \(k_c = 0.5\)，恢复速度 \(k = 0.1\)：

| 周期 | k_c |
|---|---|
| 0 | 0.500 |
| 1 | 0.550 |
| 2 | 0.595 |
| 3 | 0.636 |
| 4 | 0.672 |
| 5 | 0.705 |
| ... | ... |
| 很多周期后 | 接近 1 |

### 7.3 为什么要这样

如果直接从 0.5 跳到 1：

- 底盘动作突然变强。
- 可能让车抖动。
- 可能让功率瞬间超限。

平滑恢复让动作逐渐变强，更稳定。

### 7.4 和功率限制的关系

```text
1. 解二次式，得到目标缩放 k_solve
2. 如果 k_solve < k_c：
     直接取 k_c = k_solve（限制介入，立即缩小）
3. 如果 k_solve >= k_c：
     k_c += (1 - k_c) * k（慢慢恢复）
4. rpm_set *= k_c
```

### 7.5 注意

文档说：

> 恢复平滑后不再严格满足原阈值。

翻译：

- 平滑恢复后，实际功率可能重新超过限制。
- 不能把它当成绝对硬保证。

## 八、统一缩放

### 8.1 四轮同乘

\[
\omega_{\text{new}} = k_c \cdot \omega_{\text{old}}
\]

- 保持比例。
- 保持方向。
- 整体变慢。

### 8.2 为什么不用逐轮缩放

逐轮缩放会改变方向比例，车会往别的方向走。

## 九、源码已知问题

文档提到：

> calc_power_limit 里 sum_err 约束两个边界都为负 MAX 的调用值得核对，不能把其解释成正常对称积分限幅。

翻译：

- 代码里有个 `sum_err` 约束。
- 两个边界都是负的 MAX。
- 正常积分限幅应该是 \([-MAX, +MAX]\)。
- 两个都是负 MAX，意味着积分只能在负区间变化。
- 这可能是 bug，也可能有特殊原因，需要核对。

## 十、教学 vs 源码

| | 教学 | 源码 |
|---|---|---|
| 功率模型 | \(P = 0.2\|\omega\|^2\) | \(a k^2 + b k + c\) |
| 缩放 | \(k = \sqrt{P_{\text{limit}}/P}\) | 解二次式求 k |
| 缓冲能量 | 不考虑 | 缓冲低时增加危险项 |
| 裁判 | 不考虑 | `chassis_power_limit - 5` |
| 恢复平滑 | 无 | \(k_c += (1-k_c)k\) |
| 数据来源 | 合成 | 轮 PID、测得 RPM、裁判信息 |

教学模型只有平方项，源码有三项。教学不考虑缓冲和裁判，源码考虑。

## 十一、失败条件

| 现象 | 可能原因 |
|---|---|
| 预测没超实际超 | 模型系数未标定、消息延迟 |
| 动作突然变慢 | 功率限制介入 |
| 缓冲耗尽 | 持续大功率 |
| 裁判罚则 | 功率限制未生效 |
| 负判别式 | 二次式无实数解 |
| \(a \approx 0\) | 退化为一次 |
| 恢复平滑后超限 | 恢复项太激进 |

| 裁判消息旧 | 用了过期数据 |

```text

2. 建立电流估计
3. 建立二次功率模型 a k² + b k + c

Jam detection uses the difference between commanded and measured angle over time, not current alone. Fire_OFF sets the speed reference to zero, while RELAX explicitly clears the current commands.

## 麦轮运动学

**中文**：

**英文**：

**中文**：

# 第六部分：最直白的总结

## 发射逻辑

1. **两个部件**：摩擦轮管转速，拨盘管送弹位置。
2. **六个状态**：READY、SINGLE、BLOCK、BACK、FAIL、RELAX。
3. **正常流程**：READY → SINGLE → 到达目标角 → READY。
4. **堵转判断**：角差 > TRI_MINECD 且时间 > MAXTIME。
5. **堵转处理**：SINGLE → BLOCK → BACK → READY 或 FAIL。
6. **退弹**：反向转，角度小于送弹角，速度可能更慢。
7. **重试限制**：超过最大次数进入 FAIL。
8. **Fire_OFF vs RELAX**：前者设速度参考 0，后者所有电流归零。
9. **摩擦轮独立**：堵转不影响摩擦轮。
10. **边界**：阈值要按编码器齿比和时间单位解释，注意 `<` 和 `<=`。

## 麦轮运动学

1. **麦轮特殊**：外圈有斜滚子，允许一个方向自由滑动。
2. **驱动方向**：轮子能推地的方向，与车体轴成 45°。
3. **轮子位置**：四个角，旋转时每个轮子额外获得速度。
4. **关键公式**：轮子处速度 = 车体平移 + 旋转贡献。
5. **逐轮投影**：把轮子处速度投影到驱动方向，得到轮速。
6. **矩阵结果**：4×3，输入 [vx, vy, ω]，输出四轮角速度。
7. **每列含义**：前进全正，横移对角正负，旋转左负右正。
8. **手算**：[1, 0.5, 1] → [1, 19, 11, 9] rad/s。
9. **源码轮序不同**：RF/LF/RB/LB，不能直接换。
10. **统一缩放**：超过上限时四轮同乘 scale，保持方向比例。

## 功率限制

1. **总功率三部分**：铜耗、机械功率、静态损耗。
2. **铜耗**：I²R，电流乘 k，铜耗乘 k²。
3. **机械功率**：一部分乘 k²，一部分乘 k。
4. **静态损耗**：常数 c。
5. **合起来**：P = a k² + b k + c。
6. **a**：平方项系数，主要来自铜耗。
7. **b**：线性项系数，主要来自恒定摩擦。
8. **c**：常数项，静态损耗。
9. **判断超限**：算 P(1) = a + b + c，和 P_limit 比较。
10. **解二次式**：求满足功率限制的 k。
11. **限制 k**：在 [0, 1]。
12. **恢复平滑**：k_c += (1-k_c)k，慢慢向 1 恢复。
13. **统一缩放**：四轮同乘 k，保持方向。
14. **超级电容**：存能量，短时透支。
15. **功率 vs 能量**：W 和 J 不同，不能直接加减。
16. **低速大电流**：也可能高功率，不能只看速度。
17. **源码风险**：sum_err 两个负 MAX，需核对。
````
