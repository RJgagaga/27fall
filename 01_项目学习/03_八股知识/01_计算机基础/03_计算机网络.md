## 一、分层模型

### Q1 OSI 七层与 TCP/IP 四层模型？（OSI vs TCP/IP）
**优先级：★★★**

| OSI | TCP/IP | 典型协议 | 数据单位 |
|---|---|---|---|
| 应用/表示/会话 | 应用层 | HTTP, DNS, MQTT, DDS-RTPS | 报文 |
| 传输层 | 传输层 | TCP, UDP | 段/数据报 |
| 网络层 | 网络层 | IP, ICMP | 包 |
| 数据链路/物理 | 网络接口层 | Ethernet, Wi-Fi, CAN | 帧/比特 |

**答案要点**：分层的好处是各层独立演进，下层为上层提供服务。数据发送时逐层封装（加头），接收时逐层解封装。路由器工作在网络层，交换机在链路层。CAN 总线属于链路层/物理层范畴，与 IP 栈无关。

**English short answer**
The OSI model has seven layers, but in practice we use the four-layer TCP/IP model: application, transport, network and link. Each layer adds its own header when sending, and removes it when receiving. For example HTTP runs over TCP, TCP over IP, and IP over Ethernet or Wi-Fi.

**追问方向**：一次浏览器访问网页经过哪些协议；交换机与路由器的区别。

### Q2 输入一个 URL 回车后发生了什么？（What happens when you type a URL）
**优先级：★★★**

**答案要点**：①解析 URL；②DNS 解析（本地缓存→递归解析器→根/顶级/权威）得到 IP；③TCP 三次握手（HTTPS 再加 TLS 握手）；④发送 HTTP 请求；⑤服务器处理并返回响应；⑥浏览器解析 HTML、加载资源、渲染；⑦连接复用（keep-alive）或关闭。可延伸到 ARP（同网段）、NAT、路由。

**English short answer**
The browser first resolves the domain name to an IP address with DNS, then opens a TCP connection with a three-way handshake, and for HTTPS performs a TLS handshake. It sends an HTTP request, the server returns a response, and the browser parses and renders the page, loading further resources over the same or new connections.

**追问方向**：ARP 的作用；HTTP/2 多路复用。

### Q3 MAC 地址、IP 地址、端口的区别？（MAC, IP, port）
**优先级：★★**

**答案要点**：MAC 标识网卡，链路层局域网内寻址；IP 标识主机/接口，网络层跨网路由；端口（16 位，0–65535）标识主机上的应用进程。一条 TCP 连接由四元组（源 IP、源端口、目的 IP、目的端口）唯一标识。ARP 把 IP 解析成 MAC。

**English short answer**
A MAC address identifies a network interface on the local link, an IP address identifies a host on the network for routing, and a port identifies the application on that host. A TCP connection is uniquely defined by the source and destination IP and port.

**追问方向**：NAT 如何工作；知名端口。

### Q4 IPv4 地址、子网掩码、CIDR？（Subnetting）
**优先级：★★**

**答案要点**：IPv4 32 位。CIDR 写法 `192.168.1.0/24` 表示前 24 位为网络号，主机位 8 位，可用主机 $2^8-2=254$（去掉网络地址和广播地址）。判断两台机器是否同网段：各自与掩码按位与后比较。私有地址：10/8、172.16/12、192.168/16。机器人局域网（如机器人与上位机）通常配同网段静态 IP。

**English short answer**
An IPv4 address has 32 bits, and the subnet mask or CIDR prefix tells which bits are the network part. For a slash 24 network there are 254 usable host addresses. Two hosts are on the same subnet if their addresses ANDed with the mask are equal. Private ranges include 192.168.0.0/16.

**追问方向**：路由表最长前缀匹配；IPv6。

## 二、TCP

### Q5 TCP 与 UDP 的区别？（TCP vs UDP）
**优先级：★★★**

| 项 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 确认、重传、排序、去重 | 不保证 |
| 传输单位 | 字节流（无边界） | 数据报（有边界） |
| 流控/拥塞控制 | 有 | 无 |
| 头部 | 20B 起 | 8B |
| 场景 | 文件、HTTP、控制命令需可靠 | 视频、语音、高频遥测、DNS、DDS |

**English short answer**
TCP is connection-oriented and reliable: it orders data, retransmits lost segments and controls flow and congestion, but delivers a byte stream with no message boundaries. UDP is connectionless and light, preserves message boundaries but offers no reliability. I would use UDP for real-time streams where fresh data matters more than old lost data, and TCP when every byte must arrive.

**追问方向**：为什么实时控制不愿用 TCP（重传带来延迟、队头阻塞）。

### Q6 TCP 三次握手的过程与为什么是三次？（Three-way handshake）
**优先级：★★★**

```text
Client                          Server
  | --- SYN, seq=x ----------->  |   (SYN_SENT)
  | <-- SYN+ACK, seq=y, ack=x+1 -|   (SYN_RCVD)
  | --- ACK, ack=y+1 --------->  |   (ESTABLISHED)
```

**答案要点**
- 目的：双方确认彼此的收发能力，同步初始序号 ISN。
- 为什么不是两次：①两次只能让服务端确认客户端发送正常，服务端无法确认客户端收到了自己的 SYN；②防止**历史（延迟的）重复 SYN** 建立无用连接：第三次握手时客户端可对旧连接发 RST。③需要双方都同步 ISN。
- 为什么不是四次：第二步服务端的 SYN 和 ACK 可合并。
- SYN 洪泛攻击：伪造大量 SYN 使半连接队列满，防御：SYN cookies。

**English short answer**
The client sends SYN, the server replies SYN plus ACK, and the client sends ACK. This confirms that both sides can send and receive and synchronizes the initial sequence numbers. Two steps would not let the server know the client received its SYN, and it could not reject stale duplicate SYNs. Two messages from the server are merged into one, so four is unnecessary.

**追问方向**：半连接队列和全连接队列；SYN flood 与 SYN cookies；ISN 为何随机。

### Q7 TCP 四次挥手与 TIME_WAIT？（Four-way close, TIME_WAIT）
**优先级：★★★**

```text
Client                          Server
  | --- FIN ----------------->   |  (FIN_WAIT_1)
  | <-- ACK ------------------   |  (CLOSE_WAIT / FIN_WAIT_2)
  | <-- FIN ------------------   |  (LAST_ACK)
  | --- ACK ----------------->   |  (TIME_WAIT 2MSL -> CLOSED)
```

**答案要点**
- 为何四次：TCP 全双工，每个方向独立关闭；收到 FIN 只表示对方不再发送，己方可能还有数据要发，所以 ACK 和 FIN 往往分开。
- TIME_WAIT 持续 $2\,\text{MSL}$（Linux 固定 60s）：①保证最后一个 ACK 丢失时能重发（对方重传 FIN）；②让旧连接的延迟报文在网络中消失，避免污染新连接。
- 大量 TIME_WAIT：短连接频繁主动关闭方堆积；解决：长连接/连接池、`SO_REUSEADDR`、让服务端不主动关闭。
- 大量 CLOSE_WAIT：说明应用忘记 `close()`，是代码 bug。

**English short answer**
Closing takes four steps because each direction of the full-duplex connection is closed separately: FIN, ACK, then the other side's FIN and ACK. The side that closes first stays in TIME_WAIT for twice the maximum segment lifetime so the last ACK can be retransmitted and old packets expire. Many CLOSE_WAIT sockets usually mean the application forgot to close.

**追问方向**：RST 与 FIN 区别；同时关闭；SO_LINGER。

### Q8 TCP 如何保证可靠传输？（TCP reliability）
**优先级：★★★**

**答案要点**：①序号 + 确认号（ACK）；②超时重传（RTO 由 RTT 估计动态计算）；③快速重传（收到 3 个重复 ACK 即重传）；④校验和；⑤滑动窗口（流量控制）；⑥拥塞控制；⑦乱序重排与去重。累积确认；SACK 选择确认可提高重传效率。

**English short answer**
TCP numbers every byte, and the receiver acknowledges what it got. If an ACK does not arrive before a timeout, or three duplicate ACKs arrive, the sender retransmits. Checksums detect corruption, the receiver reorders segments, and flow and congestion control keep the sender from overloading the receiver or the network.

**追问方向**：RTO 计算（SRTT）；SACK；Nagle 与延迟确认。

### Q9 滑动窗口与流量控制？（Sliding window and flow control）
**优先级：★★★**

**答案要点**
- 接收方在 ACK 中通告接收窗口 rwnd（剩余缓冲区），发送方未确认的数据量不得超过 $\min(rwnd, cwnd)$。
- 窗口为 0 时发送方停止，并周期性发送**窗口探测**，防止窗口更新报文丢失导致死锁。
- 糊涂窗口综合征（silly window）：接收方每次只腾出很小空间，发送方发很小的段，效率低；解决：接收方等空间够大再通告，发送方 Nagle 合并。
- 吞吐上限 $\approx \text{window}/\text{RTT}$（教学估算：窗口 64KB、RTT 100ms，约 5.2 Mbit/s）。窗口缩放选项（window scale）扩大 16 位限制。

**English short answer**
The receiver advertises how much buffer space it has, called the receive window, and the sender must not have more unacknowledged data in flight than that. If the window drops to zero the sender pauses and sends probes. This is flow control; it protects the receiver, while congestion control protects the network.

**追问方向**：流控和拥塞控制区别；带宽时延积 BDP。

### Q10 TCP 拥塞控制算法？（Congestion control）
**优先级：★★★**

**答案要点**
- 发送窗口 $=\min(rwnd, cwnd)$。
- 慢启动（slow start）：cwnd 从 1 MSS 起，每个 RTT 翻倍（指数增长）直到 ssthresh。
- 拥塞避免：cwnd 每 RTT 加 1 MSS（线性，AIMD 的加性增）。
- 丢包：超时 → ssthresh = cwnd/2，cwnd 回到 1，重新慢启动；3 个重复 ACK → 快速重传 + 快速恢复，cwnd 减半（乘性减）。
- 现代：CUBIC（Linux 默认）、BBR（基于带宽和 RTT 估计而不是丢包）。无线链路丢包不一定是拥塞，传统算法会误判。

**English short answer**
TCP starts in slow start, doubling the congestion window each round trip until a threshold, then grows linearly in congestion avoidance. On a timeout it cuts the window drastically and restarts; on three duplicate ACKs it halves the window and does fast recovery. This additive increase, multiplicative decrease behaviour shares bandwidth fairly. Modern variants include CUBIC and BBR.

**追问方向**：为什么 AIMD 能收敛到公平；Wi-Fi 下丢包误判。

### Q11 什么是 TCP 粘包/拆包？怎么解决？（Sticky packets / message framing）
**优先级：★★★**

**答案要点**
- 本质：TCP 是**字节流**，没有消息边界。一次 `send` 的数据可能被拆成多个段，多次 `send` 也可能被合并成一次 `recv`。因此严格说不是 TCP 的 bug，而是应用层没有分帧。
- 原因：Nagle 算法合并、MSS 分段、接收缓冲区读取时机。
- 解决（应用层协议设计）：①定长消息；②分隔符（如 `\n`，需转义）；③**长度前缀**（最常用）：头部 4 字节长度 + 负载，读时先读满头，再读满负载；④带帧头魔数 + 长度 + CRC 的二进制帧（串口、CAN 自定义协议同理）。
- UDP 没有粘包，但有丢失、乱序、重复。

```python
# 教学示例：长度前缀收包
import struct
def recv_exact(sock, n):
    buf = b""
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk: raise ConnectionError
        buf += chunk
    return buf
def recv_msg(sock):
    (length,) = struct.unpack("!I", recv_exact(sock, 4))  # network byte order
    return recv_exact(sock, length)
```

**English short answer**
TCP is a byte stream with no message boundaries, so several sends can arrive merged, or one send can arrive in pieces. It is the application's job to frame messages. The most common solution is a length prefix: read a fixed-size header giving the payload length, then read exactly that many bytes. Delimiters or fixed-length messages also work. The same idea applies to serial or CAN custom protocols.

**追问方向**：Nagle 与 TCP_NODELAY；recv 返回值含义；半包处理状态机。

### Q12 Nagle 算法与延迟确认，为什么会让小包延迟增大？（Nagle and delayed ACK）
**优先级：★★**

**答案要点**：Nagle：有未确认数据时，小数据先缓存，攒到 MSS 或收到 ACK 再发，减少小包。延迟确认：接收方等待最多约 40ms 以便捎带 ACK。两者叠加可能造成 40ms 左右的停顿，影响交互式/低延迟控制命令。设置 `TCP_NODELAY` 关闭 Nagle。

**English short answer**
Nagle's algorithm holds back small segments until the previous data is acknowledged, and delayed ACK makes the receiver wait to piggyback acknowledgements. Together they can add tens of milliseconds of latency to small messages. For low-latency control or interactive traffic I enable TCP_NODELAY.

**追问方向**：corking；写合并。

### Q13 TCP 的 keepalive 与心跳？（Keepalive and heartbeat）
**优先级：★★**

**答案要点**：TCP 连接在两端静默时，不会感知对方断电/网线拔掉（半开连接）。`SO_KEEPALIVE` 默认两小时才探测，太慢。应用层心跳：定期发小消息，超时未收到则判断断线并重连，同时可携带时间戳测延迟。机器人/设备状态上报常用心跳 + 重连 + 状态重新同步。

**English short answer**
If a peer disappears without closing, for example a power loss, TCP does not notice for a long time. TCP keepalive is too slow by default, so I implement an application-level heartbeat with a timeout. When the heartbeat is missing, I close the connection, reconnect and resynchronize state.

**追问方向**：半开连接；重连退避（exponential backoff）。

### Q14 TCP 与 UDP 的头部，校验和及 MTU/分片？（Header, MTU, fragmentation）
**优先级：★**

**答案要点**：TCP 头 20B 起，含源/目的端口、序号、确认号、标志位（SYN/ACK/FIN/RST/PSH）、窗口、校验和。UDP 头 8B：源/目的端口、长度、校验和。以太网 MTU 1500B，TCP MSS 通常 1460。UDP 大于 MTU 会 IP 分片，一个分片丢失整包丢失，故应控制报文 ≤ MTU。

**English short answer**
The TCP header is at least 20 bytes with ports, sequence and ack numbers, flags, window and checksum. UDP's is just 8 bytes. Ethernet MTU is 1500 bytes, so I keep UDP datagrams below that to avoid IP fragmentation, where losing one fragment loses the whole datagram.

**追问方向**：路径 MTU 发现；巨帧。

## 三、UDP 与可靠性取舍

### Q15 UDP 为什么快？怎么在 UDP 上做可靠传输？（Reliable UDP）
**优先级：★★**

**答案要点**：UDP 无握手、无拥塞控制、头小，延迟低。需要可靠时在应用层自己加序号、确认、重传、超时（如 QUIC、KCP、DDS 的 RELIABLE QoS）。不一定要全部可靠：高频状态（里程计）丢一帧无所谓，下一帧会覆盖；关键命令（急停、模式切换）需要确认。

**English short answer**
UDP is fast because it has no handshake, no retransmission and no congestion control. When I need reliability I add sequence numbers, acknowledgements and retransmission at the application layer, as protocols like QUIC and DDS reliable mode do. For high-rate sensor data I often prefer best effort, because old data is useless.

**追问方向**：DDS QoS（RELIABLE vs BEST_EFFORT）；见 [DDS与分布式通信](../../02_基础知识/09_机器人软件/05_DDS与分布式通信.md)。

### Q16 广播与多播？（Broadcast and multicast）
**优先级：★**

**答案要点**：广播发给子网内所有主机；多播发给加入某组（D 类地址 224.0.0.0/4）的主机，用 IGMP 加入组。DDS 的发现机制常用多播；跨网段/Wi-Fi 下多播可能被路由器过滤，导致"节点互相看不见"，这是 ROS2 多机常见问题。

**English short answer**
Broadcast reaches every host on the subnet, while multicast reaches only hosts that joined a group. Robot middleware uses multicast for discovery, and when multicast is blocked on a Wi-Fi network, nodes on different machines cannot see each other.

**追问方向**：ROS2 多机通信排障（ROS_DOMAIN_ID、防火墙）。

## 四、应用层协议

### Q17 HTTP 请求方法和状态码？（HTTP methods and status codes）
**优先级：★★★**

**答案要点**
- 方法：GET（读，幂等）、POST（创建，非幂等）、PUT（整体替换，幂等）、PATCH、DELETE、HEAD、OPTIONS。
- 状态码：200 OK、201 Created、204 No Content、301/302 重定向、304 Not Modified、400 Bad Request、401 未认证、403 禁止、404、409 冲突、429 限流、500 服务器错误、502/503/504 网关/不可用/超时。
- 幂等性：同一请求重复执行效果相同，对重试设计重要（设备命令应设计成幂等，如"设置目标值"而不是"加 1"）。

**English short answer**
GET reads data and is idempotent, POST creates something, PUT replaces a resource, and DELETE removes it. Status codes starting with 2 mean success, 3 redirection, 4 client error such as 404, and 5 server error. Idempotency matters for retries, so I design device commands as set-to-value rather than increment.

**追问方向**：GET 与 POST 区别；REST 风格。

### Q18 HTTP/1.1、HTTP/2、HTTP/3 的区别？（HTTP versions）
**优先级：★★**

**答案要点**：HTTP/1.1：文本协议，keep-alive 复用连接，但有应用层队头阻塞（请求按序），浏览器开多连接缓解。HTTP/2：二进制分帧、多路复用（一条 TCP 内多个流）、头部压缩（HPACK）、服务器推送；但 TCP 层队头阻塞仍在。HTTP/3：基于 QUIC（UDP），每流独立丢包恢复，连接建立更快，支持连接迁移。

**English short answer**
HTTP/1.1 is a text protocol with persistent connections but suffers head-of-line blocking at the request level. HTTP/2 uses binary framing and multiplexes many streams over one TCP connection with header compression. HTTP/3 moves to QUIC over UDP, so a lost packet only blocks one stream.

**追问方向**：QUIC 的 0-RTT；多路复用与队头阻塞。

### Q19 HTTPS 的握手过程？TLS 如何保证安全？（HTTPS and TLS）
**优先级：★★★**

**答案要点**
- 目标：机密性（加密）、完整性（MAC/AEAD）、身份认证（证书）。
- 简化流程（TLS 1.2）：客户端 ClientHello（支持的套件、随机数）→ 服务端 ServerHello + 证书 + 随机数 → 客户端校验证书链（CA 签名、域名、有效期）→ 密钥交换（ECDHE 提供前向保密）→ 双方推导会话密钥 → 之后用**对称加密**通信。
- 为什么混合：非对称慢，只用来安全地协商对称密钥；对称（AES-GCM）快，用于数据。
- TLS 1.3：只需 1-RTT，去掉不安全套件，支持 0-RTT。
- 中间人攻击靠证书链防御；自签名证书需自行信任。

**English short answer**
HTTPS is HTTP over TLS. During the handshake the server proves its identity with a certificate signed by a trusted authority, the two sides agree on keys using a key exchange like ECDHE, and then they encrypt the data with a fast symmetric cipher. Asymmetric cryptography is used only for setup because it is slow. TLS provides confidentiality, integrity and authentication.

**追问方向**：前向保密；证书验证细节；对称与非对称区别。

### Q20 WebSocket 是什么？和 HTTP 轮询、SSE 比怎么样？（WebSocket）
**优先级：★★★**

**答案要点**
- WebSocket：先用 HTTP `Upgrade: websocket` 握手（状态码 101），之后在同一 TCP 连接上全双工、低开销的帧通信；服务端可主动推送。
- 对比：短轮询浪费、延迟高；长轮询占连接；SSE 单向（服务端→客户端），文本，自动重连；WebSocket 双向，二进制/文本。
- 适合：实时仪表盘、机器人遥测可视化、聊天。需要处理心跳（ping/pong）、断线重连、背压（慢客户端）。
- 对话式 Agent 系统中，服务端把决策结果、设备状态流式推给网页前端也适合 WebSocket 或 SSE。我们在 P4 的做法是：服务端用 asyncio 事件循环运行 WebSocket 服务，状态变化事件驱动地广播给网页；网页断线重连后先拉一次全量快照，再接增量。

```javascript
// 教学示例（浏览器端）
const ws = new WebSocket("ws://host:8080/telemetry");
ws.onmessage = (e) => console.log(JSON.parse(e.data));
```

**English short answer**
WebSocket starts as an HTTP request that is upgraded, and then keeps one TCP connection open for full-duplex messaging, so the server can push data any time with small overhead. Compared with polling it is more efficient and has lower latency, and compared with server-sent events it is bidirectional. It is a good fit for live robot telemetry dashboards, and I add heartbeats and reconnect logic.

**追问方向**：握手细节（Sec-WebSocket-Key）；与 MQTT 对比；背压。

### Q21 Cookie、Session、Token（JWT）的区别？（Cookie, session, token）
**优先级：★★**

**答案要点**：HTTP 无状态。Cookie：存在浏览器，随请求自动携带。Session：服务端保存状态，Cookie 里只放 session id。Token（如 JWT）：服务端签发的自包含令牌，无需服务端存储，但难以主动失效；需注意 XSS（窃取）、CSRF（跨站请求）。设备控制 API 必须鉴权，机器人不能被任意人遥控。

**English short answer**
HTTP is stateless, so we need a way to remember users. A cookie is stored in the browser, a session keeps state on the server and the cookie only holds an id, and a token such as a JWT is a signed, self-contained credential. Any API that can command a physical robot must be authenticated.

**追问方向**：XSS/CSRF；OAuth。

### Q22 MQTT 是什么，和 HTTP 比？（MQTT）
**优先级：★★**

**答案要点**：基于 TCP 的发布/订阅协议，经 broker 转发；主题（topic）分层，QoS 0/1/2（至多一次/至少一次/恰好一次）；遗嘱消息（LWT）用于设备离线通知；头部极小，适合 IoT 设备（如 Hi3861 这类低功耗设备）。HTTP 是请求/响应，需主动拉取。

**English short answer**
MQTT is a lightweight publish-subscribe protocol over TCP with a central broker. It has three quality-of-service levels and a last-will message for detecting offline devices, so it is popular for IoT devices with limited resources, unlike HTTP's request-response style.

**追问方向**：QoS 选择；与 ROS topic 的类比。

### Q23 REST 与 RPC（gRPC）？（REST vs RPC）
**优先级：★**

**答案要点**：REST 以资源为中心，URL + 方法，JSON，易调试；gRPC 基于 HTTP/2 + Protobuf，强类型、二进制、流式，性能高，适合服务间调用。机器人领域 ROS service/action 是 RPC 思想。

**English short answer**
REST models resources with URLs and HTTP verbs and usually carries JSON, which is easy to debug. gRPC uses HTTP/2 and Protobuf for typed, efficient and streaming calls, and fits service-to-service communication.

**追问方向**：Protobuf 编码；ROS service vs topic。

## 五、DNS 与 IP

### Q24 DNS 解析过程与记录类型？（DNS）
**优先级：★★★**

**答案要点**：浏览器/系统缓存 → hosts → 本地递归解析器（ISP/8.8.8.8）→ 根服务器 → 顶级域（.com）→ 权威服务器，返回 IP；递归解析器缓存结果，受 TTL 控制。常见记录：A（IPv4）、AAAA（IPv6）、CNAME（别名）、MX（邮件）、NS、TXT。通常 UDP 53，响应过大或区域传送时用 TCP。

**English short answer**
The resolver checks its caches first, then queries a recursive resolver, which walks from the root servers to the top-level domain servers and finally to the authoritative server for the name. The answer is cached according to its TTL. DNS mostly uses UDP on port 53 and falls back to TCP for large responses.

**追问方向**：DNS 污染；CDN 如何用 DNS 调度。

### Q25 ARP 和 ICMP（ping）是什么？（ARP, ICMP）
**优先级：★★**

**答案要点**：ARP：同网段内广播"谁是 192.168.1.5？"，目标回自己的 MAC，缓存 ARP 表。ICMP 属于网络层，ping 用 Echo Request/Reply 测连通与往返时间；traceroute 利用 TTL 递减触发 Time Exceeded。排障时：ping 通说明 IP 层通，端口不通要看防火墙/服务监听。

**English short answer**
ARP maps an IP address to a MAC address on the local network by broadcasting a request. ICMP carries control messages, and ping uses its echo request to test reachability and measure round-trip time. I use ping first when diagnosing a network problem between a robot and my laptop.

**追问方向**：traceroute 原理；`ss -tlnp` 查端口。

### Q26 NAT 是什么？（NAT）
**优先级：★★**

**答案要点**：网络地址转换，路由器把内网私有 IP:端口映射为公网 IP:端口，缓解 IPv4 地址不足。副作用：外部无法主动连接内网设备，需要端口映射、内网穿透、或设备主动连出到云端（长连接）。IoT 设备常主动连云服务器正因如此。

**English short answer**
NAT lets many devices share one public IP by rewriting addresses and ports at the router. A side effect is that outside machines cannot start connections into the private network, so IoT devices usually connect out to a cloud server and keep the connection open.

**追问方向**：NAT 穿透 STUN/TURN；端口转发。

## 六、socket 编程

### Q27 TCP 服务端/客户端 socket 调用流程？（TCP socket API）
**优先级：★★★**

```text
服务端: socket() -> bind() -> listen() -> accept() -> recv()/send() -> close()
客户端: socket() ------------------------> connect() -> send()/recv() -> close()
```

```python
# 教学示例：回显服务端（单连接）
import socket
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 9000)); srv.listen(5)
conn, addr = srv.accept()
while (data := conn.recv(1024)):
    conn.sendall(data)
conn.close(); srv.close()
```

**答案要点**：`listen` 的 backlog 影响全连接队列；`accept` 返回新的连接 socket；`recv` 返回 0 表示对方关闭；`send` 可能只发出部分数据，要循环或用 `sendall`；`SO_REUSEADDR` 允许重启服务时立即重新绑定仍在 TIME_WAIT 的端口。

**English short answer**
On the server I call socket, bind, listen and accept, which returns a new socket for each client; the client calls socket and connect. Then both sides use send and recv. A recv returning zero means the peer closed. Because send may write only part of the buffer, I loop or use sendall, and I set SO_REUSEADDR so the server can restart quickly.

**追问方向**：bind 失败原因；非阻塞 connect。

### Q28 如何实现高并发服务器？（Concurrency models for servers）
**优先级：★★★**

**答案要点**：①每连接一个进程/线程（简单，规模受限）；②线程池 + 阻塞 IO；③单线程 Reactor + epoll 事件循环（Nginx、Redis、asyncio）；④多 Reactor / 主从 Reactor（主线程 accept，工作线程处理 IO）；⑤Proactor（io_uring）。C10K 问题推动了 epoll。注意：CPU 密集的处理要丢到线程池，否则会阻塞事件循环。见 [Python八股](./06_Python八股.md) 的 asyncio。

**English short answer**
A simple server uses one thread per connection, which doesn't scale. Higher-performance servers use an event loop with epoll, where one thread handles many connections with non-blocking IO, optionally with several worker threads. CPU-heavy work should be pushed to a thread pool so it does not block the loop.

**追问方向**：Reactor vs Proactor；惊群；asyncio。

### Q29 字节序（大小端）与网络字节序？（Byte order）
**优先级：★★★**

**答案要点**：小端（little-endian）低字节在低地址（x86、ARM 常用）；大端（big-endian）高字节在低地址。网络字节序规定为**大端**。例（教学示例）：`0x12345678` 在小端内存里依次是 `78 56 34 12`。转换：`htons/htonl/ntohs/ntohl`。跨设备二进制协议（STM32 ↔ 上位机）必须明确字节序，并注意结构体对齐/填充，最好显式序列化（逐字节拼装）而非直接 `memcpy` 结构体。见 [C语言与嵌入式八股](./04_C语言与嵌入式八股.md)。

```python
import struct
struct.pack("<f", 1.5)   # little-endian float32
struct.pack("!H", 8080)  # network order uint16
```

**English short answer**
Little-endian stores the least significant byte at the lowest address, which is what x86 and most ARM systems use. Network byte order is big-endian, so I convert with htons and htonl. In binary protocols between a microcontroller and a PC I define the byte order explicitly and serialize field by field rather than copying a struct, to avoid padding and endianness problems.

**追问方向**：如何判断本机字节序；浮点数传输。

### Q30 常见 socket 选项与错误处理？（socket options and errors）
**优先级：★★**

**答案要点**：`SO_REUSEADDR`/`SO_REUSEPORT`、`TCP_NODELAY`、`SO_KEEPALIVE`、`SO_RCVBUF/SO_SNDBUF`、`SO_RCVTIMEO`。错误：`EAGAIN`（非阻塞无数据）、`EINTR`（被信号打断，重试）、`ECONNRESET`（对方 RST）、`EPIPE`/SIGPIPE（对已关闭连接写，需忽略信号并检查返回值）。

**English short answer**
Common options are SO_REUSEADDR for quick restarts, TCP_NODELAY for low latency, keepalive for dead peer detection, and buffer sizes. I always handle EINTR by retrying, EAGAIN in non-blocking mode, and ignore SIGPIPE so writing to a closed connection returns an error instead of killing the process.

**追问方向**：连接超时的设置；半关闭 `shutdown`。

### Q31 select/epoll 做事件循环的基本结构？（Event loop with epoll）
**优先级：★★**

**答案要点**：创建 epoll 实例，把监听 socket 与连接 socket 注册为非阻塞；循环 `epoll_wait`；监听 fd 可读则 `accept` 并注册新连接；连接 fd 可读则 `recv`，边缘触发时读到 `EAGAIN`；可写事件处理发送缓冲。每个连接维护读缓冲和协议状态机（解决半包）。

```python
# 教学示例：selectors 事件循环骨架
import selectors, socket
sel = selectors.DefaultSelector()
def on_accept(s):
    c, _ = s.accept(); c.setblocking(False); sel.register(c, selectors.EVENT_READ, on_read)
def on_read(c):
    d = c.recv(4096)
    if d: c.sendall(d)
    else: sel.unregister(c); c.close()
srv = socket.socket(); srv.bind(("", 9000)); srv.listen(); srv.setblocking(False)
sel.register(srv, selectors.EVENT_READ, on_accept)
while True:
    for key, _ in sel.select():
        key.data(key.fileobj)
```

**English short answer**
I register the listening socket and all client sockets as non-blocking with epoll, then loop on epoll_wait. If the listening socket is readable I accept and register the new connection; if a client socket is readable I read into that connection's buffer and parse complete messages. This lets one thread serve many clients.

**追问方向**：写事件何时关注；背压处理。

## 七、机器人通信选型

### Q32 机器人系统里，通信方式如何选型？（Choosing communication for robots）
**优先级：★★★**

**答案要点**
| 场景 | 常用做法（典型） | 原因 |
|---|---|---|
| MCU ↔ 电机驱动 | CAN / FDCAN | 抗干扰、多节点、仲裁，短帧确定性好 |
| MCU ↔ 上位机 | UART / USB / CAN / 以太网 | 看带宽与距离 |
| 节点间传感器流 | ROS2/DDS，UDP，best effort | 新数据优先，丢帧可接受 |
| 命令/配置 | 可靠通信（service/TCP） | 不能丢 |
| 远程监控网页 | WebSocket / HTTP | 浏览器兼容 |
| 低功耗 IoT | MQTT | broker、QoS、遗嘱 |

关键考量：延迟、抖动、带宽、可靠性、断线恢复、时间戳同步、安全。控制环**闭环发生在本地 MCU**，网络链路只传设定值和状态，避免把闭环放在不可靠的网络上。P6 做的设备发现、能力注册、状态同步、任务分发基于 M-DDS（CV 原文），其底层思想与 DDS 相同，见 [DDS与分布式通信](../../02_基础知识/09_机器人软件/05_DDS与分布式通信.md)；实现细节上，本项目通常的取法（典型/教学示例，以实机为准）是：高频状态流用 best-effort + keep-last 小深度（新数据优先）；设备能力注册这类"晚加入者也要看到"的数据用 reliable + transient-local；任务分发命令用 reliable 并带 action_id 保证幂等。消息类型按"设备能力描述、机器人状态（带时间戳、坐标系、有效性标志）、任务提案/反馈"三类划分。English: "For fast state streams I use best-effort with a shallow history; for capability registration I use reliable and transient-local so late joiners still see it; commands are reliable and idempotent."（高频状态流用 best-effort 加浅历史；能力注册用 reliable + transient-local，让晚加入者也能收到；命令用 reliable 且幂等。）

**English short answer**
I match the protocol to the requirement. For motor communication I use CAN because it is robust and deterministic. For sensor streams between nodes I use publish-subscribe over UDP with best-effort delivery, since fresh data matters more than retransmission. Commands and configuration need reliable delivery, and browser dashboards use WebSocket. I keep fast control loops local to the microcontroller and send only setpoints and states over the network.

**追问方向**：延迟怎么测；时间同步；为什么不通过 Wi-Fi 做闭环。

### Q33 如何设计一个简单的设备—服务端二进制协议？（Designing a binary protocol）
**优先级：★★**

**答案要点**：帧结构：`[帧头魔数 2B][版本 1B][类型 1B][序号 2B][长度 2B][负载 N][CRC16 2B]`。要点：定义字节序；长度前缀解决粘包；CRC 检测误码；序号用于丢包/重复检测；版本便于升级；心跳帧；ACK/NACK 机制；超时重传；接收端状态机逐字节解析并在失步时按魔数重新同步。适用于串口、无线数传、TCP。

```c
// 教学示例：帧结构（显式字段，序列化时逐字节写，避免依赖结构体填充）
typedef struct {
    uint16_t magic;    // 0xA55A
    uint8_t  version;
    uint8_t  type;
    uint16_t seq;
    uint16_t len;
    uint8_t  payload[]; // len bytes, followed by crc16
} frame_t;
```

**English short answer**
I would define a frame with a magic header, version, message type, sequence number, payload length, payload and a CRC. The length field solves message boundaries, the CRC detects corruption, and the sequence number detects loss or duplication. On the receiving side I use a byte-by-byte state machine that can resynchronize on the magic number after errors.

**追问方向**：CRC 与校验和；转义；ACK 超时重传。

### Q34 如何测量与排查网络延迟？（Debugging network latency）
**优先级：★★**

**答案要点**：`ping` 测 RTT；`iperf3` 测吞吐；`tcpdump`/Wireshark 抓包看握手、重传、窗口；`ss -ti` 查看 TCP 内部状态（cwnd、rtt、重传）；`netstat/ss` 看 TIME_WAIT/CLOSE_WAIT 数；应用层给每条消息打时间戳算单程延迟（需要时钟同步 NTP/PTP）。常见根因：Wi-Fi 干扰、缓冲区膨胀（bufferbloat）、Nagle、日志阻塞线程、DNS 慢。

**English short answer**
I use ping for round-trip time, iperf for throughput, and Wireshark or tcpdump to see retransmissions and window behaviour. For one-way latency I timestamp messages in the application, which requires synchronized clocks. Typical causes are wireless interference, buffer bloat, Nagle's algorithm, or the application blocking on logging.

**追问方向**：PTP/NTP 精度；抓包过滤语法。

### Q35 什么是长连接与短连接，连接池有什么用？（Persistent vs short connections）
**优先级：★★**

**答案要点**：短连接每次请求都握手挥手，开销大，TIME_WAIT 多。长连接复用，需要心跳保活、超时关闭空闲连接。连接池预先创建并复用连接，限制最大并发，避免服务端被压垮。HTTP/1.1 默认 keep-alive。

**English short answer**
A short connection is opened and closed for every request, which costs handshakes and creates many TIME_WAIT sockets. A persistent connection is reused, with heartbeats to keep it alive, and a connection pool manages a bounded set of such connections.

**追问方向**：空闲超时；连接泄漏。

### Q36 拥塞控制与流量控制、可靠性相关的 "Wi-Fi 下机器人网络变差" 怎么应对？（Unreliable wireless links）
**优先级：★★**

**答案要点**：应用层要容错：超时、重连与指数退避、命令带序号和幂等、状态快照 + 增量、**失联保护**（超过一定时间收不到上位机命令，机器人自动停车/进入安全状态，类似 watchdog）；关键控制在本地；数据降采样、压缩；选择 5GHz、固定信道。这与 P6 的 policy-check 与安全执行链思想一致：网络命令不能直接驱动执行器，需要经过本地检查（见 CV 描述）。

**English short answer**
I design for failure: commands are idempotent and carry sequence numbers, connections reconnect with exponential backoff, and the robot enters a safe state, for example stopping, if no command arrives within a timeout. Critical loops run locally, so a bad link degrades performance but not safety.

**追问方向**：failsafe；心跳超时设置。

### Q37 CLOSE_WAIT 大量堆积和 SYN Flood 分别是什么问题？（CLOSE_WAIT and SYN flood）
**优先级：★★**

**答案要点**
- CLOSE_WAIT：对端已发 FIN，本端内核已回 ACK，但**本端应用没有调用 close()**。几乎总是代码 bug（忘记关 fd、读到 0 字节后不处理、连接泄漏），不是网络问题。排查：`ss -tan state close-wait` 找进程，检查 `recv` 返回 0 的分支是否关闭了 socket。
- TIME_WAIT：主动关闭方的正常状态，持续 2MSL；大量出现多见于短连接，可改长连接、连接池，或在客户端侧复用（`SO_REUSEADDR`）。
- SYN Flood：攻击者只发 SYN 不完成第三次握手，占满半连接队列。缓解：SYN Cookie（不保存状态，把信息编码进 ISN）、调大 backlog、限速。
- 记忆：CLOSE_WAIT 找自己的代码，TIME_WAIT 是协议正常现象。

**English short answer**
Many CLOSE_WAIT sockets mean the peer closed the connection but my application never called close, so it is usually a resource leak in my code. TIME_WAIT is different: it is a normal state on the side that closed first. A SYN flood fills the half-open queue with connections that never complete the handshake, and SYN cookies are the standard defence.
（大量 CLOSE_WAIT 表示对端已关闭而应用没调 close，通常是自己代码的资源泄漏；TIME_WAIT 是主动关闭方的正常状态；SYN Flood 用半连接占满队列，标准防御是 SYN Cookie。）

**追问方向**：半连接队列与全连接队列；`tcp_tw_reuse`。

### Q38 UDP socket 编程与 TCP 有什么不同？（UDP socket programming）
**优先级：★★**

**答案要点**
- 流程：`socket(AF_INET, SOCK_DGRAM)` → 服务端 `bind` → `recvfrom`/`sendto`；无 `listen/accept`，无连接状态。
- 一次 `sendto` 对应一个数据报，`recvfrom` 一次取一个完整数据报，**天然有消息边界**，不存在粘包；但缓冲区小于数据报时多余部分被丢弃。
- 数据报可能丢失、重复、乱序；需要应用层序号与时间戳，旧数据直接丢弃。
- 数据报大小应小于路径 MTU 减去头部（以太网典型负载约 1472 字节），避免 IP 分片（任一分片丢失则整个数据报丢失）。
- 可对 UDP socket 调 `connect` 固定对端，之后可用 `send/recv`，并能收到 ICMP 错误。
- 机器人中的典型用法：高频遥测、传感器流、多播发现。

```c
// 教学示例：UDP 接收一个数据报
int fd = socket(AF_INET, SOCK_DGRAM, 0);
struct sockaddr_in addr = {.sin_family = AF_INET,
                           .sin_port = htons(9000),
                           .sin_addr.s_addr = htonl(INADDR_ANY)};
bind(fd, (struct sockaddr*)&addr, sizeof addr);
char buf[1500];
struct sockaddr_in peer; socklen_t plen = sizeof peer;
ssize_t n = recvfrom(fd, buf, sizeof buf, 0, (struct sockaddr*)&peer, &plen);
```

**English short answer**
With UDP there is no listen or accept: I create a datagram socket, bind it, and call recvfrom and sendto. Each call carries exactly one datagram, so message boundaries are preserved and there is no sticky-packet problem. But datagrams can be lost, duplicated or reordered, so I add sequence numbers and keep each datagram below the MTU to avoid fragmentation.
（UDP 没有 listen/accept，创建数据报 socket、bind 后用 recvfrom/sendto；每次调用对应一个数据报，保留消息边界、无粘包；但可能丢失、重复、乱序，所以加序号并让数据报小于 MTU 以避免分片。）

**追问方向**：为什么 UDP 数据报不宜过大；多播加入组（`IP_ADD_MEMBERSHIP`）。

### Q39 机器人多设备之间如何做时间同步？NTP 与 PTP 的区别？（Time synchronisation）
**优先级：★★**

**答案要点**
- 问题：多设备的时间戳要能比较，否则传感器融合、延迟测量、状态有效性判断都会出错（CV 中 P5、P6 都强调时间戳一致与对齐）。
- NTP：基于 UDP 123 端口，通过四个时间戳估计往返延迟与时钟偏差：$\delta=\frac{(t_2-t_1)+(t_3-t_4)}{2}$ 为偏移估计（$t_1$ 客户端发、$t_2$ 服务端收、$t_3$ 服务端发、$t_4$ 客户端收），假设上下行对称；局域网典型精度毫秒级。
- PTP（IEEE 1588）：利用网卡或交换机的**硬件时间戳**，局域网可到亚微秒～微秒级，适合高精度同步。
- 实用做法：同一台机器内用单调时钟（`CLOCK_MONOTONIC`）算间隔，用 UTC/系统时钟做跨设备对齐；每条消息带采集时刻（不是发送时刻）；接收端检查时间戳新鲜度，超过阈值标记为无效。
- 手算示例（教学数值）：$t_1=0,\ t_2=12,\ t_3=13,\ t_4=5$（ms，客户端与服务端时钟不同）。往返延迟 $=(t_4-t_1)-(t_3-t_2)=5-1=4$ ms；偏移 $=\frac{(12-0)+(13-5)}{2}=10$ ms，即服务端时钟比客户端快约 10 ms。

**English short answer**
Time synchronisation matters because sensor fusion and latency measurement need comparable timestamps. NTP estimates clock offset from four timestamps and is usually accurate to milliseconds on a local network. PTP uses hardware timestamping and can reach microseconds. In practice I stamp each message at acquisition time, use a monotonic clock for intervals, and mark data invalid when its timestamp is too old.
（时间同步的意义在于传感器融合和延迟测量需要可比较的时间戳。NTP 用四个时间戳估计偏移，局域网约毫秒级；PTP 用硬件时间戳可达微秒级。实践中在采集时刻打戳，用单调时钟算间隔，时间戳过旧则标记无效。）

**追问方向**：为什么 NTP 假设路径对称；`chrony` 配置；ROS2 的 `use_sim_time`。

### Q40 ROS2/DDS 的节点发现是如何工作的？为什么 QoS 不兼容会"静默失败"？（DDS discovery and QoS）
**优先级：★★**

**答案要点**
- 发现：DDS（RTPS 协议）典型用 **UDP 多播**周期广播参与者（participant）信息，再交换各端点（endpoint）的 Topic 名、类型、QoS；多播不可用时可配置单播 peer 列表或 discovery server。
- 匹配条件：Topic 名相同、类型兼容、QoS 兼容（遵循"请求/提供"规则：订阅方请求的可靠性不能高于发布方提供的）。
- 典型例子：发布方 best-effort、订阅方请求 reliable，则**不匹配**，话题存在、数据在发，但订阅方收不到；通常只在日志或 QoS 事件回调里出现 incompatible-QoS。排查：`ros2 topic info -v` 看两端 QoS。
- 另一类问题：不同网络/域（`ROS_DOMAIN_ID`）隔离、防火墙拦多播、Wi-Fi 对多播不友好导致发现慢。
- 与本章关系：这是 UDP 多播（Q16）与可靠性取舍（Q15）的实际应用；P6 的设备发现与能力注册基于 M-DDS（CV 原文），思想相同，细节见 [DDS与分布式通信](../../02_基础知识/09_机器人软件/05_DDS与分布式通信.md)。

**English short answer**
DDS discovery typically uses UDP multicast to announce participants, and then peers exchange the topic name, type and QoS of each endpoint. A writer and a reader only connect if the topic, type and QoS are compatible. For example, a reliable subscriber cannot match a best-effort publisher, so the topic exists but no data arrives, and often the only clue is an incompatible-QoS event. I check both sides with ros2 topic info in verbose mode.
（DDS 发现典型用 UDP 多播广播参与者，再交换每个端点的话题名、类型与 QoS；三者兼容才会匹配。例如 reliable 订阅方无法匹配 best-effort 发布方，话题存在但收不到数据，线索往往只有 incompatible-QoS 事件。我用 verbose 模式的 ros2 topic info 检查两端。）

**追问方向**：多播被禁用时怎么办；`ROS_DOMAIN_ID` 的作用。

## 本章要点速记
1. 分层：应用、传输、网络、链路；封装与解封装。
2. TCP 面向连接可靠字节流，UDP 无连接数据报；实时数据流常选 UDP/best effort。
3. 三次握手：确认双方收发 + 同步 ISN + 防历史 SYN；四次挥手：全双工两个方向分别关闭；TIME_WAIT = 2MSL。
4. 流量控制保护接收方（rwnd），拥塞控制保护网络（cwnd：慢启动、拥塞避免、快速重传/恢复）。
5. 粘包是字节流没有边界：长度前缀最常用。
6. HTTP 方法与状态码；HTTPS = HTTP + TLS（证书、密钥交换、对称加密）。
7. WebSocket：HTTP 升级后的全双工长连接，适合实时遥测。
8. socket：socket-bind-listen-accept / connect；send 可能部分发送；epoll 做高并发。
9. 网络字节序是大端；二进制协议要显式序列化。
