## 一、存储层次与缓存

### Q1 存储层次是怎样的？为什么要分层？（Memory hierarchy）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 从上到下：寄存器 → L1/L2/L3 缓存（SRAM）→ 主存（DRAM）→ 固态/磁盘。越靠上越快越小越贵。
- 典型量级（教学示例）：寄存器 <1 ns；L1 约 1 ns（几十 KB）；L2 几 ns；L3 十余 ns；DRAM 约 60–100 ns；SSD 约 10–100 µs；机械盘毫秒级。
- 分层有效的前提是**局部性**：时间局部性（刚用过的会再用）与空间局部性（附近的数据也会用）。
- 程序性能常被"访存"而不是"算术"限制；优化的核心是让工作集适合缓存、访问尽量顺序。
- MCU（如 Cortex-M4）通常无数据缓存，SRAM 访问是确定的；Cortex-M7 有 I/D-Cache，需要关注 DMA 一致性。

**English short answer**
Memory is organized in levels from registers and small fast caches down to large slow DRAM and storage. It works because programs show temporal and spatial locality, so most accesses hit in the fast levels. In practice many programs are limited by memory access rather than arithmetic, so I keep the working set small and access data sequentially.

（译：存储分层从寄存器、缓存到 DRAM 和外存，靠时间与空间局部性使多数访问命中高速层；很多程序受限于访存，因此要让工作集小、访问顺序化。）

**追问方向**：MCU 与应用处理器的缓存差异；工作集的概念。

### Q2 缓存行、命中率与三种缺失？（Cache line and the 3 Cs）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 缓存以**缓存行（cache line）**为单位搬运，常见 64 字节；读一个字节会把整行带入。
- 缺失三类（3C）：**强制缺失**（首次访问）、**容量缺失**（工作集大于缓存）、**冲突缺失**（映射到同一组被挤出）。
- 平均访存时间 AMAT = 命中时间 + 缺失率 × 缺失代价。
- 优化：顺序访问、结构体按访问频率分组、数组结构（SoA）替代结构数组（AoS）以便向量化、分块（tiling）矩阵乘法使子块驻留缓存。
- 例：按行遍历 C 的二维数组比按列遍历快很多，因为行内元素在内存连续。

**English short answer**
Caches move data in lines, typically 64 bytes, so touching one byte brings in its neighbors. Misses are compulsory, capacity or conflict misses. Average memory access time is hit time plus miss rate times miss penalty. I improve it by accessing memory sequentially, using structure-of-arrays layouts, and blocking loops so tiles fit in cache.

（译：缓存以行（常 64 字节）为单位；缺失分强制、容量、冲突三类；AMAT = 命中时间 + 缺失率×缺失代价；通过顺序访问、SoA、分块来优化。）

**追问方向**：矩阵乘法分块的原理；为什么链表遍历慢。

### Q3 缓存的映射方式与替换策略？（Cache mapping and replacement）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 直接映射：每个地址只能放一个固定行，硬件简单但冲突多。全相联：任意位置，冲突少但比较电路复杂。**组相联（N-way）**：折中，地址分为 tag / index / offset，index 选组，组内 N 路并行比较 tag。
- 替换：LRU（最近最少使用）、伪 LRU、随机、FIFO；实际硬件多用近似 LRU。
- 步长为 2 的幂的访问（如列遍历大矩阵）容易让大量地址映射到同一组，造成冲突缺失，可通过填充（padding）缓解。
- 写策略：写直达（write-through）与写回（write-back）；写分配与否。

**English short answer**
A set-associative cache splits an address into tag, index and offset: the index selects a set and the tag is compared across the ways in that set. Direct-mapped is simple but conflicts a lot, fully associative is flexible but expensive. Replacement is usually an approximation of LRU. Power-of-two strides can thrash one set, which padding fixes.

（译：组相联缓存把地址分为 tag/index/offset，index 选组、组内比较 tag；直接映射冲突多、全相联成本高；替换近似 LRU；2 的幂步长易抖动，可用填充缓解。）

**追问方向**：写回与写直达的取舍；如何计算缓存的组数。

### Q4 伪共享（false sharing）是什么？怎么避免？（False sharing）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 多个线程各自修改**不同变量**，但这些变量落在**同一缓存行**，每次写入都会使其他核心的该行失效（一致性协议），导致缓存行来回弹跳，性能大幅下降，且代码"逻辑上没有共享"。
- 避免：给热点变量填充/对齐到缓存行（C++11 `alignas(64)`，或 `std::hardware_destructive_interference_size`）；把每线程的计数器分开放置；线程局部累加后再合并。
- 诊断：`perf c2c`、观察多线程扩展性差、缓存缺失/一致性流量高。
- 对立概念：真共享（true sharing）是多个线程确实访问同一变量，需要同步。
- SPSC 队列的 `head/tail` 应分别对齐到不同缓存行。

**English short answer**
False sharing happens when threads write different variables that live on the same cache line, so the coherence protocol keeps invalidating the line between cores and performance collapses even though nothing is logically shared. I fix it by padding or aligning hot variables to the cache line size, or by accumulating per thread and merging later.

（译：不同线程写同一缓存行内的不同变量，一致性协议使该行反复失效，性能骤降；用对齐/填充到缓存行或线程局部累加后合并来解决。）

**追问方向**：如何用 perf 发现；原子计数器在多核下的开销。

### Q5 缓存一致性协议（MESI）的基本思想？（Cache coherence, MESI）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 多核各有私有缓存，需要保证对同一地址的读写看起来一致。
- MESI 四种状态：**M**odified（独占且已改）、**E**xclusive（独占未改）、**S**hared（多核共享只读）、**I**nvalid。写共享行时，该核发出失效消息使其他副本变 I，自己变 M。
- 一致性解决"同一地址"的可见性，**内存序（memory ordering）**解决"不同地址之间"的顺序，二者不同。
- 嗅探（snooping）适合核数少，目录式（directory）适合核数多。
- 对软件的意义：频繁写共享变量代价高；原子操作和锁依赖该协议。

**English short answer**
Coherence protocols such as MESI make sure all cores see a consistent value for each address. A line can be Modified, Exclusive, Shared or Invalid, and a write to a shared line invalidates the other copies. Coherence is about one address, whereas memory ordering is about the order of operations on different addresses, which is a separate issue.

（译：MESI 保证各核对同一地址看到一致的值，状态有 M/E/S/I，写共享行会使其他副本失效；一致性针对单地址，内存序针对不同地址间的顺序，两者不同。）

**追问方向**：为什么写频繁的全局变量会让多线程变慢；总线嗅探与目录协议。

### Q6 DMA 与缓存一致性问题怎么处理？（DMA and cache coherence）
**优先级：★★★** · 对应基础知识：[STM32_时钟_GPIO_中断_DMA](../../02_基础知识/11_嵌入式与通信/01_STM32_时钟_GPIO_中断_DMA.md)

**答案要点**
- DMA 控制器直接读写主存，不经过 CPU 的缓存。若 CPU 缓存里有该区域的脏行，DMA 读到旧数据；若 DMA 写入后 CPU 缓存里还有旧副本，CPU 读到旧数据。
- 做法：①把 DMA 缓冲区放在**不可缓存**区域（MPU 配置为 non-cacheable）；②发送前对缓冲区做 **clean**（写回），接收后做 **invalidate**（作废）；③缓冲区按缓存行大小对齐（如 32 字节），避免相邻变量被连带作废。
- 典型出现在 Cortex-M7（STM32H7 有 D-Cache）；M3/M4 无数据缓存则无此问题。
- 症状：偶发数据错误，关闭缓存后恢复正常。

**English short answer**
DMA reads and writes main memory directly and bypasses the CPU cache. So before a DMA transmit I clean the cache to write dirty lines back, and after a DMA receive I invalidate the cache so the CPU sees the new data. I also align buffers to cache lines, or place them in a non-cacheable region. This matters on Cortex-M7 parts such as STM32H7.

（译：DMA 绕过 CPU 缓存；发送前 clean 写回，接收后 invalidate 作废，缓冲区按缓存行对齐或放入不可缓存区；Cortex-M7（如 STM32H7）上尤为重要。）

**追问方向**：为什么缓冲区必须按缓存行对齐；如何在 H7 上配置 MPU。

### Q7 虚拟内存、页表与 TLB 如何协同？（Virtual memory, page table, TLB）
**优先级：★★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- 每个进程有独立虚拟地址空间，MMU 通过**页表**把虚拟页映射到物理页；页大小常见 4 KB。
- 页表在内存里，一次访存需多次查表；**TLB** 是缓存最近地址翻译的小型硬件缓存，命中则一次翻译几乎零成本。
- 多级页表（如 x86-64 四级）节省稀疏地址空间的页表内存。
- 缺页（page fault）：页不在内存或权限不符；操作系统调入页或终止进程。
- 巨页（huge page，2 MB）减少 TLB 缺失，适合大模型推理、数据库；代价是内部碎片。
- MCU 通常无 MMU，只有 MPU（内存保护单元），做权限保护但不做地址翻译。

**English short answer**
Each process has its own virtual address space, and the MMU translates virtual pages to physical pages through page tables. Because walking the tables is slow, the TLB caches recent translations. A missing or protected page triggers a page fault handled by the OS. Huge pages reduce TLB misses. Microcontrollers usually have only an MPU, which protects regions but does not translate addresses.

（译：MMU 用页表把虚拟页映射到物理页，TLB 缓存最近的翻译；缺页由操作系统处理；巨页减少 TLB 缺失；MCU 通常只有 MPU，做保护不做翻译。）

**追问方向**：多级页表如何省内存；上下文切换对 TLB 的影响（ASID/PCID）。

## 二、流水线、并行与指令集

### Q8 CPU 流水线与冒险是什么？（Pipelining and hazards）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 流水线把指令执行拆为取指、译码、执行、访存、写回等级，不同指令在不同级重叠，提高吞吐（不降低单条指令延迟）。
- 三类冒险：**结构冒险**（资源冲突）、**数据冒险**（后一条依赖前一条结果，用旁路/转发、停顿解决）、**控制冒险**（分支未决，用分支预测）。
- 分支预测失败要清空流水线，代价十几个周期。
- 对软件的启示：避免不可预测分支（数据相关的 if）、用无分支写法（条件移动）、循环展开减少分支。

**English short answer**
Pipelining overlaps the stages of consecutive instructions to raise throughput. Structural, data and control hazards can stall it; forwarding handles many data hazards and branch prediction handles control hazards. A mispredicted branch flushes the pipeline and costs a dozen or so cycles, so unpredictable branches in hot loops are expensive.

（译：流水线让指令各级重叠以提高吞吐；结构/数据/控制三类冒险，数据冒险用转发、控制冒险用分支预测；预测失败需清空流水线，热点循环中不可预测分支代价高。）

**追问方向**：为什么排序后的数组循环更快（分支预测）；Cortex-M 的流水线深度。

### Q9 乱序执行、超标量与指令级并行？（Out-of-order and superscalar）
**优先级：★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 超标量：每周期发射多条指令；乱序：硬件在保持程序语义的前提下，根据数据依赖重排执行顺序，隐藏访存延迟，最后按序提交。
- 限制：指令间的真依赖（RAW）决定可并行度；长依赖链（如链表指针追逐）无法并行。
- 对软件：打破依赖链（累加时用多个累加器）能提速；但浮点累加顺序改变会影响结果的舍入。
- 乱序与推测执行也是 Spectre 类侧信道漏洞的根源（原理层面了解即可）。
- 嵌入式 MCU（M0/M3/M4）一般顺序执行，延迟更可预测，利于实时分析。

**English short answer**
Superscalar cores issue several instructions per cycle, and out-of-order cores reorder them by data dependencies to hide memory latency while committing in program order. Long dependency chains, like pointer chasing, limit parallelism. Many small microcontrollers are in-order, which makes timing more predictable for real-time work.

（译：超标量每周期发射多条指令，乱序按依赖重排以隐藏延迟、按序提交；依赖链（如指针追逐）限制并行；MCU 多为顺序执行，时序更可预测。）

**追问方向**：多累加器展开为什么改变浮点结果；实时系统为何偏好简单核。

### Q10 SIMD 是什么？在机器人里怎么用？（SIMD）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- SIMD（单指令多数据）：一条指令同时处理多个数据元素，如 x86 的 SSE/AVX、ARM 的 NEON，宽度 128/256/512 位。
- 使用方式：①依赖编译器自动向量化（`-O3`，循环无依赖、无别名）；②内建函数（intrinsics）；③使用已向量化的库（Eigen、OpenCV、BLAS）。
- 条件：数据连续、对齐、类型一致；SoA 布局更友好。
- 机器人：点云变换、图像预处理、矩阵运算、神经网络推理的底层核。ARM 平台（RK3588、Jetson）NEON 常用。
- 注意：对齐加载、剩余尾部元素处理、浮点结合律导致的数值差异。

**English short answer**
SIMD lets one instruction operate on several data elements at once, such as AVX on x86 or NEON on ARM. I usually rely on compiler auto-vectorization with contiguous, non-aliasing data, or on libraries like Eigen and OpenCV that already use intrinsics. In robotics it speeds up point cloud transforms, image preprocessing and matrix math.

（译：SIMD 一条指令处理多个数据（AVX、NEON）；依赖编译器自动向量化或 Eigen/OpenCV 等库；用于点云变换、图像预处理、矩阵运算。）

**追问方向**：自动向量化失败的常见原因；`restrict` 的作用。

### Q11 GPU 与 CPU 的架构差异？（GPU vs CPU）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- CPU：少量强核，大缓存、复杂控制逻辑，擅长**低延迟**与串行/分支多的任务。GPU：成千上万个简单核，擅长**高吞吐**的数据并行。
- NVIDIA 模型：线程组织为线程块（block）→ 网格（grid）；硬件按 32 个线程一组（warp）以 SIMT 方式执行；同一 warp 内分支分歧（divergence）会串行化。
- 内存层级：寄存器、共享内存（片上，块内共享）、L2、全局显存（HBM/GDDR）；访问**合并（coalescing）**是性能关键。
- 适合：矩阵乘、卷积、点云批处理；不适合：小数据量、频繁 CPU–GPU 拷贝、强分支逻辑。
- 嵌入式 GPU（Jetson）与 CPU 共享内存，可减少拷贝；NPU（如 RK3588 的 NPU）则面向低精度推理。

**English short answer**
A CPU has a few powerful cores optimized for low latency and branching, while a GPU has thousands of simple cores optimized for throughput on data-parallel work. Threads run in warps of 32 in SIMT fashion, so divergent branches slow them down, and coalesced global memory access matters a lot. GPUs lose when the data is small or the host-device transfers dominate.

（译：CPU 少量强核、低延迟；GPU 大量简单核、高吞吐；线程以 32 个一组（warp）执行，分支分歧会降速，显存合并访问关键；数据小或拷贝占主导时 GPU 不占优。）

**追问方向**：共享内存的 bank 冲突；为什么推理要批处理。

### Q12 屋顶线模型（Roofline）是什么？（Roofline model）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 用**算术强度**（FLOPs / 访存字节）判断程序受限于算力还是带宽：可达性能 = min(峰值算力, 带宽 × 算术强度)。
- 强度低（如向量加、逐元素运算、注意力中的某些步骤）→ 带宽受限（memory-bound）；强度高（大矩阵乘）→ 算力受限（compute-bound）。
- 用途：判断优化方向——带宽受限就减少访存（融合算子、量化、分块），算力受限才去提升并行度和指令效率。
- LLM 推理的解码阶段通常是带宽受限（每生成一个 token 要读全部权重），所以量化和批处理能显著提高吞吐。

**English short answer**
The roofline model plots attainable performance against arithmetic intensity, which is operations per byte moved. Low-intensity kernels are limited by memory bandwidth and high-intensity ones by compute. It tells me where to optimize: fuse operators or quantize when memory-bound, and improve parallelism when compute-bound. LLM decoding is typically memory-bound.

（译：屋顶线模型按算术强度（运算/字节）判断受限于带宽还是算力；带宽受限时融合算子、量化，算力受限时提升并行；LLM 解码通常带宽受限。）

**追问方向**：如何测一个算子的算术强度；为什么批处理提高解码吞吐。

### Q13 字节序（大端/小端）及其在通信中的影响？（Endianness）
**优先级：★★★** · 对应基础知识：[计算机网络_TCP_UDP_以太网_时延](../../02_基础知识/14_计算机基础/03_计算机网络_TCP_UDP_以太网_时延.md)

**答案要点**
- 小端（little-endian）：低字节放低地址（x86、大多数 ARM 配置）；大端：高字节放低地址（网络字节序为大端）。
- 影响：跨设备通信（CAN 帧、串口协议、网络包）、文件格式、共用体/类型双关解析。
- 做法：用 `htons/htonl/ntohs/ntohl` 或手动移位组包；不要直接把结构体 `memcpy` 到线路上（还有对齐/填充、字节序问题）。
- 判断：`uint16_t x=1; *(uint8_t*)&x==1` 为小端（C 中通过 char 指针访问合法）。
- 电机驱动协议常自定义字节序，需严格按手册；位域（bitfield）的排列也是实现定义的，不适合协议解析。

**English short answer**
Little-endian stores the least significant byte at the lowest address, which is what x86 and most ARM systems use; network byte order is big-endian. When I define protocols for CAN or serial I pack fields with explicit shifts rather than copying structs, to avoid endianness, padding and bitfield-layout issues.

（译：小端低字节在低地址（x86、多数 ARM），网络字节序为大端；协议用显式移位组包而不是直接拷贝结构体，避免字节序、填充和位域布局问题。）

**追问方向**：IEEE 754 浮点数在不同端上的传输；`memcpy` 与类型双关的合法性。

### Q14 内存对齐与结构体填充？（Alignment and struct padding）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 对齐：某类型的地址是其对齐值（常为自身大小）的整数倍。编译器在成员间插入填充以满足对齐，结构体总大小是最大成员对齐的整数倍。
- 例：`struct {char a; int b; char c;}` 通常占 12 字节；重排为 `int b; char a; char c;` 占 8 字节。
- 不对齐访问：x86 允许但慢；ARM Cortex-M0 不允许（HardFault），Cortex-M3/M4 多数允许但有代价，且 DMA、多字加载指令仍可能要求对齐。
- `#pragma pack(1)` / `__attribute__((packed))` 取消填充，用于协议帧，但访问成员可能不对齐，需要 `memcpy` 取值。
- `alignas`、`aligned_alloc` 指定对齐（SIMD 要求 16/32 字节，缓存行 64 字节）。

**English short answer**
Types are aligned to multiples of their size, and the compiler inserts padding between struct members so each is aligned; the whole struct is padded to its largest alignment. Reordering members from large to small reduces waste. Misaligned access is slow on x86 and can fault on some ARM cores, so I avoid packed structs for hot data and copy fields with memcpy when parsing frames.

（译：成员按自身大小对齐，编译器插入填充；按大到小排列成员可省空间；不对齐访问在 x86 慢、部分 ARM 核会 fault，协议解析用 memcpy 取值而不直接访问 packed 成员。）

**追问方向**：为什么 packed 结构体取地址有风险；位域的可移植性。

### Q15 浮点数 IEEE 754 的关键性质与陷阱？（Floating-point pitfalls）
**优先级：★★★** · 对应基础知识：[数值方法与离散化](../../02_基础知识/01_数学基础/05_数值方法与离散化.md)

**答案要点**
- 单精度 float 32 位（1 符号 + 8 指数 + 23 尾数，约 7 位十进制有效数字）；双精度 double 64 位（约 15–16 位）。
- 陷阱：`0.1+0.2!=0.3`（二进制无法精确表示）；比较用容差 `fabs(a-b)<eps`；大数加小数会"吃掉"小数（浮点累加顺序影响结果，可用 Kahan 求和）；相近数相减造成灾难性抵消。
- 特殊值：`inf`、`NaN`（`NaN != NaN`）、次正规数（denormal）可能使运算变慢。
- 单位与时间戳：用 float 存大数值（如 Unix 时间）会丢精度，应用 double 或整数纳秒。
- MCU 若无 FPU，浮点运算由软件模拟，慢几十倍；Cortex-M4F 单精度 FPU，`double` 仍是软件实现，常用 `float` 并加 `f` 后缀（`1.0f`）。

**English short answer**
Floats have limited precision, about seven digits for single and fifteen for double, so I compare with a tolerance, watch out for catastrophic cancellation, and use compensated summation when the order matters. I also store timestamps in double or integer nanoseconds. On a Cortex-M4F the FPU is single-precision only, so I use float and avoid accidental double arithmetic.

（译：float 约 7 位、double 约 15 位有效数字；比较用容差，警惕相近数相减，累加可用补偿求和；时间戳用 double 或整数纳秒；Cortex-M4F 的 FPU 仅单精度，避免意外的 double 运算。）

**追问方向**：Kahan 求和原理；次正规数为何慢；定点数的 Q 格式。

### Q16 定点数与浮点数如何取舍？（Fixed point vs floating point）
**优先级：★★** · 对应基础知识：[STM32_时钟_GPIO_中断_DMA](../../02_基础知识/11_嵌入式与通信/01_STM32_时钟_GPIO_中断_DMA.md)

**答案要点**
- 定点（Qm.n）：用整数表示小数，缩放因子 $2^{-n}$；乘法后需右移 n 位，注意中间结果用更宽整数防溢出。
- 优点：无 FPU 的 MCU 上快、结果可复现、确定性强；缺点：范围/精度需手工权衡，溢出需饱和处理。
- 浮点：范围大、开发简单；有 FPU 的 MCU 控制算法一般直接用 float。
- 神经网络 INT8 量化本质也是定点：`real = scale × (q - zero_point)`。
- FOC 电机控制中的 Clarke/Park 变换、查表 sin/cos 常用 Q15/Q31 定点（如 CMSIS-DSP 的 `q15_t`）。

**English short answer**
Fixed-point stores fractions as scaled integers, so it is fast and deterministic on microcontrollers without an FPU, but I must manage range, scaling and overflow myself. Floating point is easier and has a huge dynamic range, so on parts with an FPU I use float. INT8 quantization of neural networks is essentially the same fixed-point idea.

（译：定点用缩放整数表示小数，在无 FPU 的 MCU 上快且确定，但需自行管理范围与溢出；有 FPU 时直接用 float；INT8 量化本质也是定点。）

**追问方向**：Q15 乘法的写法；饱和运算指令。

## 三、内存序与并发硬件基础

### Q17 什么是内存序？为什么单线程看不出来？（Memory ordering）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 编译器和 CPU 为了性能会重排**不相关地址**的读写，只保证单线程内的可见语义。多线程下，另一个线程看到的写入顺序可能与程序顺序不同。
- 经典例子：线程 A 先写数据再置 `ready=true`；线程 B 看到 `ready` 为真却读到旧数据——需要 release/acquire 或锁建立"先行发生"关系。
- 硬件模型：x86 是 TSO（较强，主要允许 store→load 重排）；ARM 是弱序（允许更多重排），所以 x86 上"能跑"的无锁代码在 ARM 上可能出错。
- `volatile` 在 C/C++ 中**不提供**线程间同步或原子性；只防止编译器优化掉访问（对硬件寄存器有用）。

**English short answer**
Compilers and CPUs reorder memory operations to different addresses, preserving only single-thread semantics. Another thread may therefore see writes in a different order, so I need acquire and release semantics or a lock to publish data safely. x86 is fairly strong while ARM is weakly ordered, so lock-free code that works on x86 can break on ARM. Volatile does not give inter-thread ordering.

（译：编译器与 CPU 会重排不同地址的访存，多线程下对方可能看到不同顺序，需 release/acquire 或锁发布数据；x86 较强、ARM 弱序，x86 上能跑的无锁代码在 ARM 上可能出错；volatile 不提供线程间有序性。）

**追问方向**：C++ 六种 memory_order；双重检查锁定为什么需要原子。

### Q18 内存屏障（memory barrier）和原子操作的关系？（Barriers and atomics）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 屏障：阻止其两侧的内存操作被重排，分编译器屏障（`asm volatile("":::"memory")`）与硬件屏障（ARM 的 `DMB/DSB/ISB`）。
- 原子操作：读-改-写在多核下不可分割（x86 的 `lock` 前缀、ARM 的 LL/SC 或 LSE 原子指令），并带有指定的内存序。
- C++ `std::atomic` 自带需要的屏障；优先使用高层原语而不是手写屏障。
- Cortex-M：`DSB` 保证写完成（如配置完 NVIC 或外设后）、`ISB` 刷新流水线（修改向量表/MPU 后）。
- CAS（比较并交换）是无锁数据结构的基础，需注意 ABA 问题。

**English short answer**
A barrier prevents operations on either side from being reordered, either by the compiler or by the hardware, such as DMB on ARM. Atomic operations make read-modify-write indivisible and carry an ordering. In C++ I use std::atomic with the weakest correct order rather than hand-written barriers. On Cortex-M I use DSB and ISB after configuring system registers.

（译：屏障阻止两侧访存被重排（编译器或硬件）；原子操作使读-改-写不可分割并带内存序；C++ 用 std::atomic 选取足够的内存序；Cortex-M 配置系统寄存器后用 DSB/ISB。）

**追问方向**：ABA 问题与解决（带版本号）；为什么 seq_cst 更慢。

### Q19 什么是 NUMA？对多线程程序有什么影响？（NUMA）
**优先级：★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- NUMA（非统一内存访问）：多路服务器中，每个 CPU 插槽有本地内存，访问远端内存延迟更高、带宽更低。
- 影响：线程与其数据最好在同一节点；操作系统通常"首次触碰"策略分配页（first-touch）。
- 优化：绑核（`taskset`/亲和性）、按节点分配内存（`numactl`）、让线程初始化自己要用的数据。
- 机器人板载计算（Jetson、RK3588）通常是单插槽统一内存，NUMA 主要出现在训练/仿真服务器；但 big.LITTLE 异构核心同样需要绑核策略。

**English short answer**
In NUMA systems each CPU socket has local memory and remote access is slower. I keep threads and their data on the same node using CPU affinity and first-touch allocation. Onboard robot computers are usually single-socket, but big.LITTLE cores still make thread pinning worthwhile, and training servers do have NUMA effects.

（译：NUMA 中访问远端内存更慢，需用亲和性与首次触碰分配让线程和数据同节点；机器人板载计算多为单插槽，但 big.LITTLE 同样值得绑核；训练服务器有 NUMA 影响。）

**追问方向**：CPU 亲和性在实时控制线程中的用法；`isolcpus`。

## 四、编译、链接与装载

### Q20 从源码到可执行文件经历哪些阶段？（Build pipeline）
**优先级：★★★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- ①预处理：展开 `#include`/`#define`/条件编译，产生 `.i`；②编译：词法 → 语法 → 语义 → 中间表示 → 优化 → 汇编 `.s`；③汇编：生成目标文件 `.o`（机器码 + 符号表 + 重定位信息）；④链接：合并目标文件和库，解析符号、重定位，产生可执行文件。
- 查看：`gcc -E`、`gcc -S`、`gcc -c`、`objdump -d`、`nm`、`readelf`。
- 每个 `.cpp` 单独编译，所以头文件里放声明，实现放源文件，否则违反单一定义规则（ODR）。
- 嵌入式还要生成 `.bin/.hex`（`objcopy`）并烧录；链接脚本决定各段放入 Flash 还是 RAM。

**English short answer**
The preprocessor expands includes and macros, the compiler translates each source file to assembly, the assembler produces object files with symbol tables and relocations, and the linker merges objects and libraries, resolves symbols and assigns addresses. Each translation unit is compiled separately, which is why declarations go in headers and definitions in source files.

（译：预处理展开头文件与宏；编译生成汇编；汇编产生含符号表与重定位信息的目标文件；链接合并并解析符号、分配地址；每个编译单元独立编译，所以头文件放声明、源文件放定义。）

**追问方向**：编译优化等级 `-O0/-O2/-Os` 的区别；为什么模板定义放头文件。

### Q21 静态链接与动态链接的区别？（Static vs dynamic linking）
**优先级：★★★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- 静态库（`.a`）：链接时把用到的目标文件拷贝进可执行文件；程序自包含、启动快、部署简单，但体积大、库更新要重新链接。
- 动态库（`.so`）：运行时由动态链接器（`ld.so`）加载，多进程共享同一份代码页，节省内存；可独立升级，但有"依赖地狱"、版本兼容（ABI）问题。
- 动态库用 PIC（位置无关代码）+ GOT/PLT 实现延迟绑定，首次调用时解析符号。
- 查依赖：`ldd`；搜索路径：`RPATH/RUNPATH`、`LD_LIBRARY_PATH`、`/etc/ld.so.conf`。
- 嵌入式通常静态链接（无动态加载器）；ROS 2 的各包共享库通过 `LD_LIBRARY_PATH` 与 ament 前缀机制定位。

**English short answer**
Static linking copies the needed code into the executable, so it is self-contained but larger and must be relinked to update. Dynamic linking resolves libraries at load time, lets processes share one copy in memory and allows independent updates, at the cost of version compatibility problems. Embedded firmware is almost always statically linked.

（译：静态链接把代码拷进可执行文件，自包含但体积大；动态链接在加载时解析，多进程共享、可独立升级，但有版本兼容问题；嵌入式固件基本静态链接。）

**追问方向**：延迟绑定 GOT/PLT 的流程；"找不到 .so" 的排查顺序。

### Q22 常见链接错误及排查？（Undefined reference and multiple definition）
**优先级：★★★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- `undefined reference to ...`：声明了但没有定义/没链接到含定义的库。检查：源文件是否加入构建、库是否列在链接命令里、**库的顺序**（静态库须在依赖它的目标之后）、C++ 符号名修饰（`extern "C"`）是否一致、函数签名是否匹配。
- `multiple definition`：同一符号在多个翻译单元定义，常因把函数/全局变量定义写在头文件里。修复：声明放头文件、定义放 `.cpp`；或函数加 `inline`、变量用 `inline`（C++17）/`static`。
- 工具：`nm -C libx.a | grep symbol`、`c++filt` 还原名字、`ldd`、`readelf -d`。
- 版本不匹配的 ABI 问题（如 `_GLIBCXX_USE_CXX11_ABI`）会在链接或运行时出现奇怪错误。

**English short answer**
An undefined reference means a symbol was declared but no object or library providing it was linked, so I check that the source is in the build, the library is listed and ordered after its users, and name mangling matches via extern C. A multiple definition usually comes from defining a function or variable in a header. I use nm and c++filt to inspect symbols.

（译：undefined reference 表示符号只声明未链接到定义，检查源文件、库及其顺序、extern "C"；multiple definition 多因头文件里写了定义；用 nm、c++filt 查看符号。）

**追问方向**：ODR 与 `inline` 变量；循环依赖的静态库怎么办。

### Q23 ELF 文件有哪些段？`.data`、`.bss`、`.text` 的区别？（ELF sections）
**优先级：★★★** · 对应基础知识：[Cortex-M体系_启动_链接脚本_内存映射](../../02_基础知识/11_嵌入式与通信/07_Cortex-M体系_启动_链接脚本_内存映射.md)

**答案要点**
- `.text`：代码（只读可执行）；`.rodata`：只读常量（字符串字面量、`const` 全局）；`.data`：已初始化的全局/静态变量（占文件空间，运行时在 RAM）；`.bss`：未初始化或零初始化的全局/静态变量（不占文件空间，启动时清零）。
- 栈与堆不在文件里，是运行时区域。
- 嵌入式启动代码（startup）要做的事：把 `.data` 的初始值从 Flash 拷贝到 RAM，把 `.bss` 清零，设置栈指针，再调用 `main`；忘记这一步，全局变量初值会错。
- 工具：`size a.out` 看各段大小，`readelf -S`，`objdump -h`；链接脚本中定义 `_sdata/_edata/_sbss/_ebss` 等符号。
- Flash 占用 = `.text + .rodata + .data`（初始值）；RAM 占用 = `.data + .bss + 堆 + 栈`。

**English short answer**
Text holds code, rodata holds constants, data holds initialized globals and takes space in the file, and bss holds zero-initialized globals and takes no file space. On a microcontroller the startup code copies data from flash to RAM and clears bss before calling main. Flash usage is text plus rodata plus the initial data image, and RAM usage is data plus bss plus heap and stack.

（译：.text 代码、.rodata 常量、.data 已初始化全局变量（占文件）、.bss 零初始化全局变量（不占文件）；MCU 启动代码把 .data 从 Flash 拷到 RAM 并清零 .bss；Flash = text+rodata+data 初值，RAM = data+bss+堆+栈。）

**追问方向**：为什么局部静态变量也在 .data/.bss；链接脚本如何分配内存区域。

### Q24 符号、弱符号与符号可见性？（Symbols, weak symbols, visibility）
**优先级：★★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- 符号是函数/变量的名字，链接器按名字匹配。`static`（文件作用域）使符号为本地，不参与跨文件解析，避免命名冲突。
- 强/弱符号：强符号（已初始化的全局、函数）冲突报错；弱符号（`__attribute__((weak))`）可被强符号覆盖。嵌入式 HAL 常把中断回调、`SystemInit` 定义为弱函数，用户在自己的文件里重写即可覆盖。
- C++ 名字修饰（name mangling）使重载可区分；`extern "C"` 关闭修饰以便 C 调用。
- 可见性：`-fvisibility=hidden` 隐藏库内部符号，只导出标记的接口，减小体积、加快加载、避免符号冲突。
- 符号插桩：`LD_PRELOAD` 可在运行时用自己的函数替换库函数（调试、性能分析用）。

**English short answer**
Symbols are the names the linker resolves. Static functions have internal linkage and cannot clash across files. Weak symbols can be overridden by strong ones, which is how HAL libraries provide default callbacks that users replace. C++ mangles names to support overloading, and extern C turns that off. Hiding symbols with visibility flags keeps a library's internals private.

（译：链接器按符号名解析；static 使符号局部；弱符号可被强符号覆盖（HAL 默认回调）；C++ 名字修饰支持重载，extern "C" 关闭修饰；可见性设置隐藏库内部符号。）

**追问方向**：HAL 的 `__weak` 回调怎么重写；`LD_PRELOAD` 的原理。

### Q25 函数调用约定与栈帧结构？（Calling convention and stack frame）
**优先级：★★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- 调用约定规定参数如何传递（寄存器/栈）、返回值放哪、谁清理栈、哪些寄存器由调用者/被调用者保存。例：ARM AAPCS 用 r0–r3 传前四个参数，r0 返回；x86-64 System V 用 rdi, rsi, rdx, rcx, r8, r9。
- 栈帧：返回地址、保存的寄存器、局部变量、（可能有）对齐填充；栈向低地址增长（常见）。
- 栈溢出：深递归、大局部数组、栈缓冲区越界覆盖返回地址（经典安全漏洞）。
- 嵌入式：每个任务有独立栈，大小需估算并启用栈水位检测（FreeRTOS `uxTaskGetStackHighWaterMark`）；中断使用主栈或进程栈。
- 防护：栈保护（canary）、不可执行栈、ASLR。

**English short answer**
A calling convention defines how arguments and return values are passed in registers or on the stack and which registers each side must preserve. Each call pushes a stack frame with the return address, saved registers and locals. Deep recursion or large local arrays can overflow the stack, and buffer overruns can overwrite return addresses. On an RTOS I size each task stack and monitor the high-water mark.

（译：调用约定规定参数/返回值如何经寄存器或栈传递及寄存器保存责任；每次调用压入含返回地址、保存寄存器与局部变量的栈帧；深递归/大数组会栈溢出；RTOS 需为每个任务估算栈并监测水位。）

**追问方向**：尾调用优化；变参函数如何取参数。

### Q26 ABI 与 API 的区别？为什么 C++ 库升级会出问题？（ABI vs API）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- API 是源码层面的接口约定；ABI 是二进制层面的约定：类型布局、符号名修饰、调用约定、虚表布局、标准库实现。
- 修改类的成员（增删字段、改虚函数顺序）会改变布局和虚表，已编译的使用方未重编译就会崩溃或行为异常——ABI 不兼容，即使 API 看似未变。
- 缓解：稳定的 C 接口 + 不透明指针（pimpl）；版本化符号；语义版本号；发布时同时发布 ABI 检查（`abi-compliance-checker`）。
- ROS 2 中同一发行版内的包要求 ABI 稳定，跨发行版需重编译。标准库 ABI 变化（如 GCC 5 的 `std::string`）曾导致大面积链接错误。

**English short answer**
An API is the source-level contract, while an ABI is the binary-level contract covering type layout, name mangling, calling conventions and vtable layout. Changing a class's members or virtual function order can break already compiled clients even if the source API looks the same. A stable C interface with an opaque pointer, or the pimpl idiom, helps keep ABI stable.

（译：API 是源码约定，ABI 是二进制约定（布局、修饰、调用约定、虚表）；改类成员或虚函数顺序会使已编译的使用方出错；用稳定 C 接口 + 不透明指针/pimpl 保持 ABI 稳定。）

**追问方向**：pimpl 的性能代价；ROS 2 发行版之间的兼容策略。

### Q27 位置无关代码（PIC）与 GOT/PLT？（PIC, GOT, PLT）
**优先级：★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- 共享库加载到的虚拟地址不固定（且 ASLR 会随机化），所以代码必须与加载地址无关：用相对寻址访问数据，对外部符号通过 **GOT**（全局偏移表）间接访问。
- 函数调用经 **PLT**（过程链接表）：首次调用跳转到动态链接器解析真实地址并写入 GOT，之后直接跳转（延迟绑定，lazy binding）。
- 编译选项：`-fPIC`；可执行文件可为 PIE（`-fPIE -pie`）。
- 安全：`-z now`（立即绑定）+ RELRO 使 GOT 只读，防止 GOT 覆盖攻击。
- 代价：PIC 略增寄存器压力和间接寻址，现代 CPU 上差异很小。

**English short answer**
Shared libraries can be loaded at arbitrary addresses, so their code is position-independent and reaches external symbols through the global offset table. Calls go through the procedure linkage table, which resolves the real address on first use. This lazy binding can be turned off with immediate binding plus RELRO, which hardens against GOT overwrites.

（译：共享库加载地址不固定，代码须位置无关，经 GOT 访问外部符号；函数调用经 PLT 延迟绑定；立即绑定 + RELRO 可防 GOT 覆盖。）

**追问方向**：PIE 与 ASLR；为什么静态库链进 .so 需要 -fPIC。

### Q28 编译优化等级与它带来的"诡异现象"？（Optimization surprises）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- `-O0` 不优化便于调试；`-O2` 常用发布；`-O3` 更激进（向量化、展开）；`-Os` 优化体积（嵌入式常用）；`-Ofast` 放宽浮点语义（可能改变结果）。
- 现象：循环中读取的外设寄存器或 ISR 修改的标志被缓存到寄存器 → 死循环（需 `volatile`）；优化后变量被"优化掉"在调试器里看不到；未定义行为（UB）被优化器利用，导致 Debug 正常、Release 出错。
- 典型 UB：有符号整数溢出、空指针解引用、越界访问、未初始化读取、违反严格别名规则、数据竞争。
- 排查：对比 `-O0/-O2` 行为、开启 `-fsanitize=undefined,address`、加 `-Wall -Wextra`、检查是否缺少 `volatile`/原子。

**English short answer**
Higher optimization levels reorder, inline, vectorize and remove code, which exposes bugs that are hidden at O0. If a flag modified by an interrupt is not volatile the compiler may cache it in a register and the loop never exits. Undefined behavior such as signed overflow or out-of-bounds access can be exploited by the optimizer, so I use warnings and sanitizers when Debug and Release differ.

（译：高优化等级会重排、内联、向量化、删除代码，暴露 O0 下被隐藏的 bug；中断修改的标志未加 volatile 会被缓存导致死循环；未定义行为会被优化器利用，Debug/Release 不一致时用警告与 sanitizer 排查。）

**追问方向**：严格别名规则；为什么有符号溢出是 UB 而无符号不是。

### Q29 未定义行为（UB）是什么？举几个例子。（Undefined behavior）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- UB 指标准不规定结果的操作，编译器可假设它不会发生并据此优化；后果从"正常"到崩溃、错误结果甚至安全漏洞，且可能随编译器版本或优化等级变化。
- 例子：有符号整数溢出；越界读写；解引用空/悬空指针；使用未初始化变量（C++ 中部分情形）；除以零；移位量过大或为负；违反严格别名；修改字符串字面量；数据竞争；释放后使用。
- 实现定义（implementation-defined，如有符号右移）与未指定（unspecified，如函数参数求值顺序）不同于 UB。
- 防护：编译警告、静态分析（clang-tidy、cppcheck）、UBSan/ASan、代码评审、使用 `std::span`/`at()` 等更安全的接口。

**English short answer**
Undefined behavior means the standard imposes no requirements, so the compiler may assume it never happens and optimize accordingly. Examples are signed overflow, out-of-bounds access, use after free, uninitialized reads and data races. Results may look fine in debug builds and fail in release. I catch it with warnings, static analysis and sanitizers.

（译：UB 指标准不规定结果，编译器可假设其不发生并据此优化；例子有有符号溢出、越界、释放后使用、未初始化读、数据竞争；用警告、静态分析、sanitizer 排查。）

**追问方向**：UB 与实现定义行为的区别；一个"优化掉空指针检查"的例子。

### Q30 严格别名规则（strict aliasing）是什么？（Strict aliasing）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 规则：通过不兼容类型的指针访问同一对象是 UB（`char*`/`unsigned char*`/`std::byte*` 例外）。编译器据此假设 `int*` 与 `float*` 不指向同一地址，可重排或缓存访问。
- 常见违例：`*(uint32_t*)&f` 读取 float 的位模式。
- 合法做法：`memcpy` 到目标类型变量（编译器通常优化为单条指令）；C++20 `std::bit_cast`；union 双关在 C 中合法、C++ 中不保证。
- 协议解析：从字节缓冲区读多字节整数，用移位组合或 `memcpy`，不要强转指针（同时避免对齐问题）。
- 关闭：`-fno-strict-aliasing`（Linux 内核使用），但不是推荐做法。

**English short answer**
Strict aliasing says that accessing an object through a pointer of an incompatible type is undefined, except through char types, so the compiler may assume different pointer types do not alias. To read the bits of a float I use memcpy or std::bit_cast instead of casting the pointer. When parsing byte buffers I combine bytes with shifts, which also avoids alignment trouble.

（译：通过不兼容类型指针访问同一对象是 UB（char 类型例外），编译器据此假设不别名；读取 float 位模式用 memcpy 或 std::bit_cast；解析字节缓冲区用移位组合，也避免对齐问题。）

**追问方向**：`restrict` 与别名；union 双关在 C/C++ 的区别。

### Q31 内联（inline）、宏与 `constexpr` 的取舍？（inline vs macro vs constexpr）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 宏：文本替换，无类型、无作用域，参数多次求值（`#define SQR(x) x*x` 的经典坑），调试困难；仅用于条件编译、头文件保护、需要字符串化/拼接的场景。
- `inline` 函数：有类型检查，可被编译器内联（只是建议），同时放宽 ODR 允许在头文件定义；过度内联增大代码体积，影响指令缓存。
- `constexpr`：编译期求值，可替代常量宏与部分模板元编程；`const` 仅表示只读，不保证编译期常量。
- `static inline` 在 C 里常用于头文件中的小函数；MCU 中小而热的函数（读寄存器、限幅）常内联。
- 现代做法：`constexpr` 常量 + `inline`/模板函数 + `enum class`，少用宏。

**English short answer**
Macros are plain text substitution without types or scope and evaluate arguments multiple times, so I avoid them except for conditional compilation. Inline functions are type-checked and the compiler can expand them, while constexpr evaluates at compile time. In modern C++ I use constexpr constants, inline or template functions and enum class instead of macros.

（译：宏是无类型、无作用域的文本替换且参数会多次求值，仅用于条件编译等；inline 函数有类型检查且可被内联；constexpr 编译期求值；现代 C++ 用 constexpr、inline/模板、enum class 取代宏。）

**追问方向**：`#define MAX(a,b)` 的副作用问题；链接时优化 LTO。

### Q32 链接时优化（LTO）与链接脚本？（LTO and linker scripts）
**优先级：★★** · 对应基础知识：[Cortex-M体系_启动_链接脚本_内存映射](../../02_基础知识/11_嵌入式与通信/07_Cortex-M体系_启动_链接脚本_内存映射.md)

**答案要点**
- LTO（`-flto`）：在链接阶段保留中间表示，跨翻译单元内联与死代码消除，可缩小体积、提升速度；代价是链接时间长、调试信息受影响。
- 链接脚本（`.ld`）：描述存储器区域（FLASH、RAM、CCM）、各段放置位置、栈/堆大小、向量表地址。MCU 里自定义段（如把某函数放 RAM 执行、把 DMA 缓冲区放特定 RAM、把参数放一块 Flash 扇区）依赖它。
- `-ffunction-sections -fdata-sections` + `-Wl,--gc-sections`：丢弃未使用的函数与数据，减小固件。
- 查看结果：`.map` 文件列出每个符号地址与大小，定位 Flash/RAM 占用大户。

**English short answer**
Link-time optimization keeps the intermediate form until link time so the compiler can inline across files and remove dead code. A linker script describes memory regions and where each section goes, which I use to place the vector table, stack, DMA buffers or time-critical functions in RAM. Section garbage collection and the map file help me shrink firmware.

（译：LTO 在链接时跨文件内联与删死码；链接脚本描述存储区域与段放置，可放向量表、栈、DMA 缓冲区或把关键函数放 RAM；section GC 与 map 文件帮助瘦身固件。）

**追问方向**：把函数放 RAM 执行的做法；map 文件怎么看。

## 五、内存管理与内存错误

### Q33 栈和堆的区别？（Stack vs heap）
**优先级：★★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- 栈：函数调用的局部变量与返回地址，自动分配释放（改栈指针），极快，大小有限（Linux 线程默认约 8 MB，MCU 任务栈常几百字节到几 KB），LIFO。
- 堆：动态分配（`malloc/new`），生命周期由程序员控制，大小受内存限制，分配有开销且可能碎片化、耗时不确定。
- 常见错误：返回局部变量地址（悬空指针）、栈上放超大数组导致溢出、堆泄漏。
- 实时系统倾向：避免运行时动态分配，启动时预分配（静态数组、内存池）；或使用确定性分配器。
- 数据放置：小的、短生命周期的放栈；大的、跨函数/线程共享的放堆（或静态区）。

**English short answer**
The stack holds local variables and return addresses, is allocated automatically and very fast, but is small. The heap is for dynamic allocation with manually controlled lifetime; it is slower, can fragment, and its timing is not deterministic. In real-time code I avoid allocating on the heap in the control loop and preallocate buffers or pools at startup.

（译：栈存局部变量与返回地址，自动分配、很快但很小；堆用于动态分配、生命周期手动控制，较慢、会碎片化、耗时不确定；实时控制环路避免堆分配，启动时预分配。）

**追问方向**：栈大小如何估算；为什么不能返回局部数组的指针。

### Q34 `malloc` 的大致实现与碎片问题？（malloc internals and fragmentation）
**优先级：★★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- 基本做法：向 OS 申请大块（`brk`/`mmap`），自己管理空闲块链表/按大小分级的 bins；分配时找合适块（首次适应/最佳适应），可分割；释放时合并相邻空闲块。
- 小对象走线程本地缓存（glibc 的 tcache、tcmalloc/jemalloc 的 thread cache）减少锁竞争；大对象直接 `mmap`。
- **外部碎片**：空闲总量够但不连续；**内部碎片**：块比请求大造成浪费。
- 实时/嵌入式：用固定大小块的内存池（O(1) 分配释放，无外部碎片）、FreeRTOS 的 heap_4（合并空闲块）、静态分配。
- 长期运行的机器人进程要警惕碎片化导致的内存缓慢增长（看似泄漏），可换 jemalloc/tcmalloc 或调参。

**English short answer**
An allocator obtains large regions from the OS and manages free blocks in size-class bins, splitting on allocation and coalescing neighbors on free. Small objects use per-thread caches to avoid locking. Fragmentation can be external, where free memory is not contiguous, or internal, where blocks are larger than requested. For deterministic timing I use fixed-size memory pools.

（译：分配器向 OS 要大块，按尺寸分级管理空闲块，分配时分割、释放时合并；小对象用线程缓存；碎片有外部与内部两种；确定性要求下用固定块内存池。）

**追问方向**：tcmalloc/jemalloc 的区别；长时间运行内存增长的诊断。

### Q35 内存池（Memory pool）怎么设计？（Memory pool design）
**优先级：★★★** · 对应基础知识：[Cortex-M体系_启动_链接脚本_内存映射](../../02_基础知识/11_嵌入式与通信/07_Cortex-M体系_启动_链接脚本_内存映射.md)

**答案要点**
- 固定块大小池：预先分配一大块内存，切成等大小块串成空闲链表；分配 = 取链表头 $O(1)$，释放 = 插回链表头 $O(1)$，无外部碎片，时间确定。
- 变体：多个池覆盖不同大小类；arena/bump 分配器（只前进指针，整体重置，适合每帧临时数据）。
- 线程安全：每线程一个池（无锁），或用原子操作/锁；ISR 中分配需用无锁或临界区。
- 防护：块头/尾加哨兵检测越界；释放时检查指针是否属于池且对齐；统计水位。
- C++：自定义 `operator new` 或 `std::pmr::monotonic_buffer_resource`/`pool_resource`。

```c
typedef struct node { struct node* next; } node_t;
static uint8_t pool[N][BLK] __attribute__((aligned(8)));
static node_t* free_list;
void pool_init(void){ for (int i=0;i<N;i++){ ((node_t*)pool[i])->next = free_list; free_list=(node_t*)pool[i]; } }
void* pool_alloc(void){ node_t* n=free_list; if(n) free_list=n->next; return n; }
void  pool_free(void* p){ node_t* n=p; n->next=free_list; free_list=n; }
```

**English short answer**
A fixed-block pool carves one preallocated region into equal blocks linked in a free list. Allocation pops the head and free pushes it back, both in constant time with no external fragmentation, which suits real-time code. I add per-thread pools or locks for thread safety and sentinel checks for debugging. C++ offers std::pmr resources for the same idea.

（译：固定块池把预分配内存切成等大块串成空闲链表，分配/释放 $O(1)$、无外部碎片，适合实时代码；线程安全用每线程池或锁；调试加哨兵；C++ 有 pmr 资源。）

**追问方向**：ISR 中使用池的注意点；arena 分配器适用场景。

### Q36 常见内存错误有哪些？分别怎么检测？（Memory bugs and tools）
**优先级：★★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- 错误类型：缓冲区溢出/越界；释放后使用（use-after-free）；重复释放（double free）；内存泄漏；未初始化读取；栈使用后返回（use-after-return）；数据竞争。
- 工具：**AddressSanitizer**（`-fsanitize=address`，编译插桩，捕获越界/释放后使用/泄漏，约 2 倍开销）；**Valgrind memcheck**（无需重编，慢 10–50 倍）；**UBSan**、**ThreadSanitizer**（数据竞争）、**MSan**（未初始化，需 clang）。
- 静态分析：clang-tidy、cppcheck、编译器警告。
- 防御编码：RAII/智能指针、`std::vector`/`std::array`/`std::span`、边界检查 `at()`、释放后置空、避免裸 `new/delete`。
- 嵌入式：栈水位检测、堆使用统计、MPU 保护栈底（栈溢出直接触发 fault）。

**English short answer**
Typical bugs are out-of-bounds access, use after free, double free, leaks and uninitialized reads. AddressSanitizer catches most memory errors at about twice the runtime cost, Valgrind works without recompiling, UBSan finds undefined behavior and ThreadSanitizer finds data races. In code I prefer RAII, vectors and spans over raw pointers, and on MCUs I use stack watermarks and MPU guard regions.

（译：常见错误有越界、释放后使用、重复释放、泄漏、未初始化读；ASan 捕获多数内存错误，Valgrind 无需重编译，UBSan 查未定义行为，TSan 查数据竞争；代码上多用 RAII/vector/span，MCU 用栈水位与 MPU 保护区。）

**追问方向**：ASan 的影子内存原理；如何在 ROS 2 节点上跑 ASan/TSan。

### Q37 内存泄漏如何定位？（Finding a memory leak）
**优先级：★★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- 现象：进程 RSS 随时间单调增长；OOM 被杀；系统变慢。先区分"真泄漏"、缓存/队列无限增长、堆碎片、已释放但分配器未归还 OS。
- 工具：ASan/LeakSanitizer（程序退出时报告未释放块与分配栈）；`valgrind --leak-check=full`；`heaptrack`、`massif`（堆随时间剖析）；tcmalloc/jemalloc 的堆剖析；Python 用 `tracemalloc`、`objgraph`。
- 方法：二分复现（最小化场景）、对比两个时间点的堆快照、查看长生命周期容器（map、队列、缓存、订阅回调）、检查循环引用（`shared_ptr` 环）。
- ROS 2 常见：订阅积压（QoS depth 大 + 处理慢）、`rosbag` 缓冲、未清理的定时器/回调组。
- 预防：RAII、`weak_ptr` 打破环、对缓存设上限与淘汰策略。

**English short answer**
I first confirm that memory really grows over time, then use LeakSanitizer or Valgrind for definite leaks and heaptrack or massif to see allocation sites over time. Many apparent leaks are unbounded queues or caches or shared_ptr cycles rather than missing frees. I bound caches and queues, and break cycles with weak_ptr.

（译：先确认内存随时间增长，再用 LeakSanitizer/Valgrind 找明确泄漏，用 heaptrack/massif 看分配点随时间的变化；很多"泄漏"其实是无界队列/缓存或 shared_ptr 环；给缓存和队列设上限，用 weak_ptr 破环。）

**追问方向**：RSS、VSZ、PSS 的区别；Python 的引用环与 GC。

### Q38 `mmap`、写时复制（COW）和内存映射文件？（mmap and copy-on-write）
**优先级：★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- `mmap` 把文件或匿名内存映射到进程虚拟地址空间；访问时按需缺页调入（懒加载）。用途：大文件随机读、进程间共享内存（`MAP_SHARED`）、动态库加载、`malloc` 大块分配。
- 写时复制：`fork()` 后父子进程共享物理页并标为只读，任一方写入时触发缺页，内核复制该页再允许写。这使 `fork` 很快，也是 Redis 持久化快照的基础。
- 共享内存是最快的 IPC（零拷贝），但需要自己做同步（信号量/锁）。ROS 2 的零拷贝传输（如 iceoryx）基于共享内存。
- 风险：映射文件被截断后访问会触发 `SIGBUS`；大量脏页回写的抖动。

**English short answer**
mmap maps a file or anonymous memory into the address space and pages it in on demand. With MAP_SHARED it gives processes shared memory, the fastest IPC, though I must synchronize access. Copy-on-write lets fork share pages between parent and child until one writes, at which point the kernel copies just that page.

（译：mmap 把文件/匿名内存映射到地址空间并按需缺页调入；MAP_SHARED 提供最快的共享内存 IPC，但需自行同步；写时复制让 fork 先共享页、写入时才复制该页。）

**追问方向**：共享内存的同步方式；`SIGBUS` 的成因。

### Q39 内存序列化与零拷贝为什么重要？（Zero-copy）
**优先级：★★** · 对应基础知识：[DDS与分布式通信](../../02_基础知识/12_机器人软件/05_DDS与分布式通信.md)

**答案要点**
- 大数据（图像、点云）在进程间传递时，序列化 + 拷贝会消耗 CPU 和带宽并增加延迟。
- 零拷贝思路：共享内存传递指针/句柄；`sendfile`；DMA 直接写入应用可见缓冲区；GPU 与 CPU 共享（统一内存）；ROS 2 的进程内通信（同一进程内组件传 `unique_ptr` 消息）与基于共享内存的传输。
- 约束：发布后发布者不能再修改消息；生命周期管理；需要固定大小/平凡可复制类型才能用共享内存传输。
- 对比：一般 DDS 传输需要序列化（CDR）+ 拷贝，适合小消息。

**English short answer**
Serializing and copying large messages such as images or point clouds wastes CPU and adds latency. Zero-copy passes ownership or a handle through shared memory instead, as in ROS 2 intra-process communication with unique pointers or shared-memory transports. The publisher must not modify a message after publishing, and the message type often has to be plain data.

（译：大消息的序列化与拷贝浪费 CPU 并增加延迟；零拷贝通过共享内存传递所有权/句柄（如 ROS 2 进程内通信或共享内存传输）；发布后发布者不得再改消息，类型常需为平凡数据。）

**追问方向**：进程内通信的限制；DDS 共享内存传输的条件。

### Q40 大小端、对齐、填充在跨平台序列化中的坑？（Serialization pitfalls）
**优先级：★★** · 对应基础知识：[DDS与分布式通信](../../02_基础知识/12_机器人软件/05_DDS与分布式通信.md)

**答案要点**
- 直接 `fwrite(&struct)` 或 `memcpy` 结构体到网络，会带上编译器填充、字节序、类型宽度（`long` 在 Windows 为 4 字节、Linux 64 位为 8 字节）、指针值等不可移植内容。
- 做法：用固定宽度类型（`uint32_t`）；显式定义字节序；逐字段编码；或使用 protobuf、FlatBuffers、CDR、msgpack 等带 schema 的序列化。
- 版本演进：新增字段用可选字段/默认值、保留字段编号，支持前后向兼容。
- 校验：长度、CRC、魔数（magic number）与版本号，防止粘包与错位。
- 机器人：MCU–上位机串口协议常用 `帧头 + 长度 + 负载 + CRC`，上位机用 `struct.unpack` 或 C 移位解析。

**English short answer**
Writing a raw struct to disk or the wire bakes in padding, endianness, type widths and pointers, so it is not portable. I use fixed-width types and encode fields explicitly, or use a schema-based format such as protobuf or FlatBuffers that supports versioning. A frame header, length, payload and CRC protect against misaligned or corrupted frames.

（译：直接写结构体会带入填充、字节序、类型宽度、指针等不可移植因素；用固定宽度类型、逐字段编码或带 schema 的序列化（protobuf/FlatBuffers）；帧头+长度+负载+CRC 防止错位和损坏。）

**追问方向**：protobuf 的向后兼容规则；CRC 与校验和的区别。

### Q41 多级缓存对多线程计数器性能的影响？（Atomic counter contention）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 多线程频繁 `fetch_add` 同一原子变量，缓存行在核间来回转移，吞吐随线程数增长反而下降（争用）。
- 优化：每线程局部计数（thread-local / 分片），定期汇总；放宽内存序（`relaxed` 足够计数）；分条带（striped counter）。
- 相关：自旋锁在持有时间很短时有效，但在争用下浪费 CPU；争用大时用带退避（backoff）的锁或 futex。
- 度量方法：压测不同线程数下的吞吐曲线，看扩展性。

**English short answer**
When many threads increment one atomic, the cache line bounces between cores and throughput can drop as threads increase. I use per-thread counters that are merged periodically, relaxed ordering for pure counting, or striped counters. I verify with a benchmark that varies thread count.

（译：多线程频繁原子递增同一变量会让缓存行在核间弹跳、吞吐反降；用线程局部计数周期合并、relaxed 内存序或分条带计数；用不同线程数的基准测试验证。）

**追问方向**：自旋锁与互斥锁的取舍；futex 的原理。

### Q42 什么是内存映射 I/O（MMIO）？与 `volatile` 的关系？（Memory-mapped I/O）
**优先级：★★★** · 对应基础知识：[STM32_时钟_GPIO_中断_DMA](../../02_基础知识/11_嵌入式与通信/01_STM32_时钟_GPIO_中断_DMA.md)

**答案要点**
- 外设寄存器被映射到地址空间，读写这些地址就是控制外设，如 `*(volatile uint32_t*)0x40020014 = value`。
- 必须 `volatile`：告诉编译器每次访问都要真正执行、不能合并/缓存/重排掉（读状态寄存器可能有副作用，如读清标志）。
- `volatile` 只管编译器，不管 CPU 乱序与缓存；Cortex-M 的外设区通常是 Device 内存类型，访问保持顺序且不缓存；必要时用 `DSB`。
- 读-改-写（`reg |= bit`）对"写 1 清零"类寄存器是危险的，会误清其他标志；很多外设提供 BSRR 这类原子置位/复位寄存器。
- 位带（bit-banding，M3/M4）提供原子位操作（M7 无）。

**English short answer**
With memory-mapped I/O, peripheral registers appear at fixed addresses, and reading or writing them controls the hardware. I access them through volatile pointers so the compiler performs every access in order. Volatile does not affect the CPU or caches, so I rely on device memory attributes and barriers where needed. Read-modify-write on write-one-to-clear registers is dangerous, so I use dedicated set and reset registers.

（译：MMIO 把外设寄存器映射到固定地址，经 volatile 指针访问以保证每次访问都执行；volatile 不管 CPU 和缓存，需依赖设备内存属性与屏障；对写 1 清零寄存器不要读-改-写，使用专用置位/复位寄存器。）

**追问方向**：GPIO 的 BSRR 寄存器；为什么读状态寄存器可能有副作用。

### Q43 中断与异常的硬件流程（以 Cortex-M 为例）？（Interrupt entry on Cortex-M）
**优先级：★★★** · 对应基础知识：[Cortex-M体系_启动_链接脚本_内存映射](../../02_基础知识/11_嵌入式与通信/07_Cortex-M体系_启动_链接脚本_内存映射.md)

**答案要点**
- 中断发生：NVIC 根据优先级仲裁；硬件自动压栈（xPSR、PC、LR、R12、R3–R0，共 8 个字），取向量表项跳转 ISR；返回时执行特殊 `EXC_RETURN` 值出栈。
- 优先级：数值越小优先级越高；抢占优先级与子优先级分组；FreeRTOS 要求调用 `FromISR` API 的中断优先级不高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`（数值上不小于它）。
- 中断延迟：从事件到 ISR 第一条指令，M3/M4 约十几个周期（未核对具体值），受更高优先级中断、临界区关中断时间影响。
- 规则：ISR 要短；不阻塞、不调用不可重入函数；与任务共享的变量需 `volatile` + 原子/临界区。
- 尾链（tail-chaining）与晚到（late arrival）优化减少连续中断的开销。

**English short answer**
On a Cortex-M the NVIC picks the highest-priority pending interrupt, the hardware automatically pushes eight registers, and the core fetches the handler address from the vector table. A lower number means higher priority. With FreeRTOS, interrupts that call FromISR APIs must have a priority at or below the configured syscall limit. ISRs should be short and never block.

（译：NVIC 选最高优先级的挂起中断，硬件自动压入 8 个寄存器并从向量表取 ISR 地址；数值越小优先级越高；FreeRTOS 中调用 FromISR 的中断优先级不能高于配置上限；ISR 要短且不阻塞。）

**追问方向**：优先级分组配置；中断里为什么不能用互斥锁。

### Q44 栈溢出在 MCU 上如何发生和排查？（Stack overflow on MCUs）
**优先级：★★★** · 对应基础知识：[FreeRTOS实时系统](../../02_基础知识/11_嵌入式与通信/02_FreeRTOS实时系统.md)

**答案要点**
- 原因：任务栈过小；大局部数组；深递归；`printf` 系列和浮点格式化占用栈很多；ISR 嵌套使用主栈。
- 症状：随机 HardFault、变量被莫名改写（栈向下溢出覆盖相邻任务栈或全局变量）、行为随调用路径变化。
- 排查：FreeRTOS `configCHECK_FOR_STACK_OVERFLOW`（方法 1 检查栈指针，方法 2 检查栈底填充模式）+ 钩子函数；`uxTaskGetStackHighWaterMark` 查看历史最小剩余；启动时用 0xA5 填充栈再看被破坏范围；MPU 设置栈底保护区。
- 估算：静态分析（`-fstack-usage`、`.su` 文件）+ 实测水位并留 25–50% 余量。
- 修复：大数组改静态或池分配，减少 printf，加大栈。

**English short answer**
Stack overflows come from small task stacks, large local arrays, deep recursion or heavy printf calls, and show up as random hard faults or corrupted variables. In FreeRTOS I enable stack overflow checking with a hook, read the high-water mark to see the minimum free stack, and size stacks from static stack usage analysis plus margin. An MPU guard region can trap overflows immediately.

（译：栈溢出源于任务栈小、大局部数组、深递归、重量级 printf，表现为随机 HardFault 或变量被改；FreeRTOS 启用溢出检测钩子、查看水位、结合静态栈用量分析并留余量；MPU 保护区可立即捕获。）

**追问方向**：`-fstack-usage` 的使用；HardFault 现场如何定位。

### Q45 编译器屏障、`volatile` 与原子在 ISR–任务共享变量中的使用？（Sharing data between ISR and task）
**优先级：★★★** · 对应基础知识：[FreeRTOS实时系统](../../02_基础知识/11_嵌入式与通信/02_FreeRTOS实时系统.md)

**答案要点**
- 单个对齐的 32 位变量在 Cortex-M 上读写本身是原子的，但仍需 `volatile` 防编译器缓存；`++` 这类读-改-写**不是**原子，被 ISR 打断会丢失更新。
- 多字节结构（如位姿 + 时间戳）可能读到"半新半旧"：用临界区（`taskENTER_CRITICAL`/关中断）、双缓冲 + 序号（seqlock）、或 SPSC 环形队列。
- 单生产者单消费者且只一方写：用带 release/acquire 的标志位即可。
- 避免在 ISR 中做重活，只置标志或把数据放入队列（`xQueueSendFromISR`），由任务处理。
- 测试：压力测试 + 随机打断（提高中断频率）才能暴露竞态。

**English short answer**
A naturally aligned 32-bit variable is read and written atomically on Cortex-M, but I still declare it volatile, and increments are not atomic so an interrupt can cause lost updates. For multi-field data I use a critical section, a double buffer with a sequence counter, or a queue from the ISR. The ISR sets a flag or enqueues data and a task does the heavy work.

（译：Cortex-M 上对齐的 32 位变量读写原子，但仍需 volatile，自增不是原子会丢更新；多字段数据用临界区、带序号的双缓冲或队列；ISR 只置标志/入队，重活交给任务。）

**追问方向**：seqlock 的读写流程；临界区关中断的最长允许时间。

### Q46 阿姆达尔定律（Amdahl's law）说明了什么？（Amdahl's law）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 若程序中比例 $p$ 的部分可并行加速 $s$ 倍，整体加速比 $S=\dfrac{1}{(1-p)+p/s}$。当 $s\to\infty$ 时上限为 $1/(1-p)$。
- 例（教学示例）：95% 可并行，核数无限也最多加速 20 倍；若只有 50% 可并行，上限仅 2 倍。
- 启示：先测量热点（profile），优化占比最大的部分；串行部分（锁、IO、通信同步）是扩展性瓶颈。
- 补充：Gustafson 定律认为问题规模可随核数增大，因此大问题的并行收益更高。
- 机器人：感知流水线并行化后，端到端延迟常被最慢的串行阶段（如数据传输、后处理 NMS）决定。

**English short answer**
Amdahl's law says the speedup is limited by the serial fraction: with a parallel fraction p sped up by s, the total speedup is one over one minus p plus p over s. If ninety-five percent is parallel, the limit is twenty times. So I profile first and attack the biggest serial bottleneck, such as synchronization or transfer time.

（译：加速比受串行部分限制：$S=1/((1-p)+p/s)$；95% 并行时上限 20 倍；所以先剖析、再优化最大的串行瓶颈（同步或传输）。）

**追问方向**：Gustafson 定律；流水线并行与数据并行的区别。

### Q47 RISC 与 CISC、ARM 与 x86 有什么区别？（RISC vs CISC）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- RISC：指令定长、数量少、加载/存储架构（只有 load/store 访问内存），流水线友好，功耗低（ARM、RISC-V）；CISC：指令变长、功能复杂，可直接对内存操作数运算（x86），现代 x86 在内部把指令译码为类 RISC 微操作。
- 实际差异主要在生态与功耗：ARM 主导移动/嵌入式，x86 主导桌面/服务器；RISC-V 是开放指令集，可扩展。
- 机器人：MCU 为 ARM Cortex-M（STM32）；板载计算为 ARM64（Jetson、RK3588）或 x86 工控机；跨架构部署要关注交叉编译与库的可用性（如 CUDA 仅限 NVIDIA）。

**English short answer**
RISC uses simple fixed-length instructions with a load-store model, which is friendly to pipelining and power, as in ARM and RISC-V. CISC such as x86 has complex variable-length instructions that modern chips decode into micro-operations. In robotics, microcontrollers are ARM Cortex-M and onboard computers are ARM64 or x86, so I need cross-compilation and attention to library support.

（译：RISC 指令简单定长、load-store 模型，利于流水线与功耗（ARM、RISC-V）；x86 是 CISC，内部译为微操作；机器人上 MCU 为 Cortex-M、板载计算为 ARM64 或 x86，需交叉编译与库兼容。）

**追问方向**：RISC-V 的优势；跨架构部署的常见坑。

### Q48 Cortex-M 与 Cortex-A 的区别？（Cortex-M vs Cortex-A）
**优先级：★★★** · 对应基础知识：[Cortex-M体系_启动_链接脚本_内存映射](../../02_基础知识/11_嵌入式与通信/07_Cortex-M体系_启动_链接脚本_内存映射.md)

**答案要点**
- Cortex-M：面向微控制器，无 MMU（可选 MPU），中断响应快且确定，单周期 SRAM，低功耗，通常裸机/RTOS；主频几十到几百 MHz。典型：M0/M3/M4/M7（STM32F1/F4/H7）。
- Cortex-A：应用处理器，有 MMU 和多级缓存，跑 Linux/Android，吞吐高但时序抖动大；主频 GHz 级、多核。典型：RK3588 的 A76/A55。
- Cortex-R：实时、功能安全场景。
- 选择：硬实时电机控制 → M；视觉/规划/大模型推理 → A；常见架构是"A 核跑高层 + M 核跑底层，用 CAN/串口/以太网通信"。

**English short answer**
Cortex-M cores target microcontrollers: no MMU, fast deterministic interrupts, low power, and usually bare metal or an RTOS. Cortex-A cores are application processors with an MMU and caches that run Linux and offer high throughput but less deterministic timing. Robots commonly pair an A-class computer for perception and planning with M-class controllers for motor loops.

（译：Cortex-M 面向 MCU，无 MMU、中断确定、低功耗，跑裸机/RTOS；Cortex-A 为应用处理器，有 MMU 与缓存，跑 Linux、吞吐高但时序抖动；机器人常用 A 核做感知规划、M 核做电机环。）

**追问方向**：M7 与 M4 的差别；A/M 异构通信方式。

### Q49 Linux 进程的虚拟地址空间布局？（Process address space layout）
**优先级：★★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- 从低到高：代码段 `.text` → 只读数据 → `.data` → `.bss` → 堆（向高地址增长）→ 内存映射区（共享库、`mmap`）→ 栈（向低地址增长）→ 内核空间。
- 堆与栈相向增长，中间是大片未映射区域；`mmap` 区放共享库和大块分配。
- 查看：`/proc/<pid>/maps`、`pmap`、`readelf -l`。
- 内核空间对用户态不可访问（访问会段错误）；ASLR 随机化栈、堆、库的基址。
- 每个线程有独立栈（`mmap` 出来的区域），共享堆与全局数据。

**English short answer**
A process address space has code, read-only data, initialized and zero data, the heap growing upward, a memory-mapping area for shared libraries and mmap, and the stack growing downward, with kernel space on top. Threads share everything but their stacks. I inspect it with /proc/pid/maps, and ASLR randomizes the base addresses.

（译：地址空间自低到高为代码、只读数据、.data、.bss、堆（向上）、映射区（共享库、mmap）、栈（向下）、内核空间；线程除栈外共享；用 /proc/pid/maps 查看，ASLR 随机化基址。）

**追问方向**：段错误的几种成因；线程栈如何分配。

### Q50 可执行文件是怎样被加载并运行的？（How a program is loaded）
**优先级：★★** · 对应基础知识：[操作系统_进程线程_内存_调度_同步](../../02_基础知识/14_计算机基础/02_操作系统_进程线程_内存_调度_同步.md)

**答案要点**
- `execve` 系统调用：内核读取 ELF 头，建立新的地址空间，按程序头（program headers）把各段映射为内存（`mmap`），设置栈（放入 `argv/envp/auxv`）。
- 若程序是动态链接，ELF 的 `PT_INTERP` 指定动态链接器 `ld.so`，内核先把控制权交给它；它加载依赖的 `.so`，做重定位，初始化（构造函数 `.init_array`）后跳转到 `_start`。
- `_start` 调用 C 运行时初始化（`__libc_start_main`）→ 全局对象构造 → `main`；`main` 返回后调用 `exit`，执行析构与 `atexit` 回调。
- 嵌入式对应：复位向量 → `Reset_Handler` → 拷贝 `.data`、清 `.bss`、`SystemInit`、`__libc_init_array` → `main`。

**English short answer**
The kernel's execve maps the ELF segments into a fresh address space and sets up the stack. For dynamic executables it first runs the dynamic linker, which loads shared libraries and relocates them, then jumps to the entry point. The C runtime then initializes globals and calls main. On a microcontroller the reset handler plays the same role by copying data, clearing bss and calling constructors.

（译：execve 把 ELF 段映射到新地址空间并建栈；动态可执行文件先由动态链接器加载并重定位共享库，再进入入口，C 运行时初始化全局对象后调用 main；MCU 上由复位处理函数完成同样工作。）

**追问方向**：全局对象构造顺序（static initialization order fiasco）；`LD_DEBUG` 的用法。

### Q51 栈保护、ASLR、NX 等基本防护是什么？（Basic exploit mitigations）
**优先级：★**

**答案要点**
- 栈金丝雀（stack canary）：函数返回前检查栈上哨兵值是否被改写，发现缓冲区溢出即终止（`-fstack-protector`）。
- NX/DEP：数据页不可执行，阻止注入代码执行。
- ASLR：随机化加载基址，增加攻击者猜地址的难度；PIE 使可执行文件本身也随机化。
- RELRO：重定位表只读。CFI（控制流完整性）限制间接跳转目标。
- 对嵌入式：许多 MCU 无 MMU/ASLR，主要靠安全编码、MPU 隔离、固件签名与安全启动（见 信息安全（见基础知识 13_系统工程与安全））。

**English short answer**
A stack canary detects overwritten return addresses before a function returns, NX marks data pages non-executable, and ASLR randomizes load addresses so exploits cannot rely on fixed locations. RELRO and control-flow integrity harden further. Microcontrollers often lack these, so firmware relies on safe coding, MPU isolation and signed secure boot.

（译：栈金丝雀检测返回地址被改写，NX 使数据页不可执行，ASLR 随机化加载地址；RELRO、CFI 进一步加固；MCU 常缺这些，靠安全编码、MPU 隔离与签名安全启动。）

**追问方向**：为何 ROP 能绕过 NX；安全启动的信任链。

### Q52 core dump 与 gdb 如何定位崩溃？（Debugging a crash with core dump）
**优先级：★★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- 开启：`ulimit -c unlimited`，配置 `core_pattern`；编译保留符号 `-g`（可用 `-O0` 或 `-Og` 便于看变量）。
- 分析：`gdb ./prog core` → `bt`（回溯）、`frame N`、`info locals`、`p var`、`info registers`；多线程用 `thread apply all bt`。
- 无调试符号的发布版：保存带符号的副本，用 `addr2line -e prog addr` 把地址转源码行。
- 实时现场：`gdb -p <pid>` 附加；`gdbserver` 远程调试嵌入式 Linux；MCU 用 OpenOCD + GDB 或 IDE 的 SWD 调试。
- 常见崩溃原因：空指针、越界、野指针、栈溢出、双重释放；配合 ASan 可更快发现。

**English short answer**
I enable core dumps, build with debug symbols, then open the core in gdb and run bt to see the call stack, inspecting frames and locals. For release builds I keep the symbol file and map addresses with addr2line. In multithreaded programs I print backtraces of all threads, and AddressSanitizer often pinpoints the root cause faster.

（译：开启 core dump 并带调试符号，用 gdb 看 bt、栈帧与局部变量；发布版保留符号文件并用 addr2line 映射；多线程打印所有线程栈；ASan 往往能更快找到根因。）

**追问方向**：`-O2` 下变量被优化掉怎么办；MCU HardFault 的现场寄存器分析。

### Q53 交叉编译的基本概念与常见问题？（Cross compilation）
**优先级：★★★** · 对应基础知识：[Docker与部署_交叉编译_systemd](../../02_基础知识/12_机器人软件/12_Docker与部署_交叉编译_systemd.md)

**答案要点**
- 在宿主机（x86）上编译在目标机（ARM）运行的程序，需要目标架构的**工具链**（如 `aarch64-linux-gnu-g++`、`arm-none-eabi-gcc`）和目标的 **sysroot**（头文件与库）。
- 工具链三元组：`arch-vendor-os-abi`，如 `aarch64-linux-gnu`；裸机用 `arm-none-eabi`。
- CMake：`-DCMAKE_TOOLCHAIN_FILE=...`，设置 `CMAKE_SYSTEM_NAME`、编译器、`CMAKE_FIND_ROOT_PATH`；ROS 2 可用 colcon + 工具链文件，或用 Docker + QEMU（`buildx` 多架构）。
- 常见坑：库架构不匹配（`file lib.so` 检查）、glibc 版本过新导致目标机无法运行、浮点 ABI（`hard`/`softfp`）不一致、依赖库未放入 sysroot。
- 对比：原生在目标机上编译简单但慢。

**English short answer**
Cross compilation builds on a host for a different target architecture, using a target toolchain and a sysroot with the target's headers and libraries. With CMake I pass a toolchain file. Typical problems are libraries of the wrong architecture, a glibc newer than the target provides, and mismatched floating-point ABIs. Docker with QEMU is a convenient alternative for ARM images.

（译：在宿主机上用目标工具链与 sysroot 编译目标架构程序，CMake 用工具链文件；常见问题是库架构不符、glibc 版本过新、浮点 ABI 不一致；Docker+QEMU 是便利替代。）

**追问方向**：sysroot 如何构建；`file` 与 `readelf -A` 的用法。

### Q54 如何缩短 C++ 大项目的编译时间？（Reducing build time）
**优先级：★★** · 对应基础知识：[CMake_ament_构建系统与依赖管理](../../02_基础知识/12_机器人软件/11_CMake_ament_构建系统与依赖管理.md)

**答案要点**
- 依赖层面：头文件只包含必要内容，用前置声明代替 `#include`，pimpl 隔离实现，避免在头文件放重型模板/大库。

**English short answer**
I cut down header dependencies with forward declarations and pimpl, and use incremental builds with Ninja, ccache and precompiled headers. A faster linker such as lld or mold helps a lot at link time. In ROS 2 I build only the packages I changed with colcon options like packages-select and use symlink install.

（译：用前置声明与 pimpl 减少头文件依赖；用增量构建、Ninja、ccache、预编译头；lld/mold 加速链接；ROS 2 只构建改动的包并使用 symlink install。）

**追问方向**：unity build 的副作用；ccache 失效的常见原因。

### Q55 数据布局：AoS 与 SoA 如何选择？（AoS vs SoA）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- AoS（结构数组）：`struct Point{float x,y,z;} pts[N]`，同一对象的字段相邻，适合一次处理一个对象的所有字段。
- SoA（数组结构）：`float x[N], y[N], z[N]`，同一字段连续，适合 SIMD 与只访问部分字段的批量运算，缓存利用率高。
- 点云处理、粒子滤波（大量粒子的 x,y,θ,w）、物理仿真常用 SoA；GPU 合并访问也偏向 SoA。
- 折中：AoSoA（小块 SoA），Eigen 的 `Matrix<float,3,Dynamic>` 列主序存储点云。
- 选择依据：访问模式——按对象访问用 AoS，按字段批量运算用 SoA；用基准测试验证。

**English short answer**
Array of structures keeps all fields of one element together, while structure of arrays keeps each field contiguous. SoA is better for vectorized or field-wise batch operations and for GPU coalescing, so I use it for large particle sets and point clouds. AoS is natural when I handle one object at a time. I measure to confirm.

（译：AoS 把一个元素的字段放一起，SoA 把同一字段连续存放；批量按字段运算、SIMD、GPU 合并访问时 SoA 更优，点云/粒子常用；按对象访问用 AoS；用基准验证。）

**追问方向**：Eigen 点云的存储布局；AoSoA 的意义。

### Q56 软件预取与缓存友好编程技巧？（Prefetching and cache-friendly code）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 硬件预取器能识别顺序/定步长访问并提前取数；不规则访问（链表、哈希、树）难以预取，缓存缺失多。
- 软件预取：`__builtin_prefetch(addr)` 在使用前提前发出请求；只在访问模式可预测但硬件看不出时有效，用错反而污染缓存。
- 技巧：连续存储（`vector` 替代 `list`）、紧凑数据类型（`float` 替代 `double`、`int8` 量化）、热冷字段分离、循环分块、避免大步长访问、按访问顺序排列数据（如对点云按空间排序）。
- 度量：`perf stat -e cache-misses,cache-references`，`perf record` 找热点。

**English short answer**
Hardware prefetchers handle sequential and strided access well but not pointer chasing. I make data contiguous, use compact types, separate hot and cold fields and tile loops. Explicit prefetch can help when the pattern is predictable to me but not to the hardware, and I check the effect with perf counters rather than assuming.

（译：硬件预取擅长顺序/定步长，不擅长指针追逐；用连续存储、紧凑类型、冷热分离、循环分块；访问模式可预测但硬件看不出时可显式预取，并用 perf 计数器验证。）

**追问方向**：为什么 `std::vector` 通常比 `std::list` 快；perf 常用事件。

### Q57 实时 Linux 程序为何要 `mlockall`、预触碰栈与堆？（mlockall and prefaulting）
**优先级：★★** · 对应基础知识：[嵌入式Linux_设备树_驱动_RT-Preempt](../../02_基础知识/11_嵌入式与通信/12_嵌入式Linux_设备树_驱动_RT-Preempt.md)

**答案要点**
- 缺页（page fault）可能触发磁盘 IO 或内存回收，延迟从微秒变成毫秒，破坏硬实时周期。
- 对策：`mlockall(MCL_CURRENT|MCL_FUTURE)` 锁定所有页不被换出；启动阶段**预触碰**（prefault）栈和堆：分配并写入一遍，使页在进入实时循环前已映射；关闭 swap 或限制；使用预分配内存池避免运行时 `malloc`。
- 同时配合：实时调度策略（`SCHED_FIFO`）、CPU 隔离（`isolcpus`）、PREEMPT_RT 内核、避免在实时线程中做文件/网络 IO 或日志阻塞写。
- 验证：`cyclictest` 测调度延迟分布，关注最大值而不是平均值。

**English short answer**
A page fault can turn a microsecond access into a millisecond stall, which breaks a real-time deadline. So I lock memory with mlockall, prefault the stack and heap before entering the real-time loop, preallocate buffers, and combine this with FIFO scheduling, an isolated core and a PREEMPT_RT kernel. I validate with cyclictest and look at the worst-case latency.

（译：缺页会把微秒级访问变成毫秒级停顿；用 mlockall 锁页、进入实时循环前预触碰栈堆、预分配缓冲，并配合 FIFO 调度、核隔离、PREEMPT_RT；用 cyclictest 看最坏延迟。）

**追问方向**：为什么要看最大延迟；日志写入如何避免阻塞实时线程。

### Q58 Linux OOM Killer 是什么？机器人上如何避免被杀？（OOM killer）
**优先级：★★** · 对应基础知识：[Docker与部署_交叉编译_systemd](../../02_基础知识/12_机器人软件/12_Docker与部署_交叉编译_systemd.md)

**答案要点**
- 当系统内存与交换空间耗尽，内核的 OOM killer 按 `oom_score`（占用内存、`oom_score_adj` 等）选进程杀掉，日志在 `dmesg` 中可见。
- 原因：真实泄漏、无限增长的队列/缓存、一次性加载过大的模型或点云、多进程同时峰值。
- 预防：设置容器/cgroup 内存上限（Docker `--memory`）以便早失败可预期；给关键进程调低 `oom_score_adj`；监控 RSS 与 `MemAvailable`；限制消息队列深度；预估峰值内存并留余量。
- 嵌入式板子常无 swap，内存耗尽立即被杀或卡死，需要看门狗重启兜底。

**English short answer**
When memory runs out, the kernel's OOM killer picks a process by score and terminates it, which shows in dmesg. To avoid losing critical nodes I bound queues and caches, set cgroup limits so failures are predictable, lower the OOM score adjustment of key processes, and monitor available memory. A watchdog provides a final safety net on boards without swap.

（译：内存耗尽时 OOM killer 按评分杀进程，dmesg 可见；通过限制队列/缓存、设置 cgroup 上限、调低关键进程 oom_score_adj、监控可用内存来避免；无 swap 的板子用看门狗兜底。）

**追问方向**：`oom_score_adj` 的取值含义；cgroup v2 内存限制。

### Q59 动态频率调节与热降频如何影响性能测试？（DVFS and thermal throttling）
**优先级：★★** · 对应基础知识：[日志_诊断_性能剖析_perf_tracing](../../02_基础知识/12_机器人软件/13_日志_诊断_性能剖析_perf_tracing.md)

**答案要点**
- DVFS：系统按负载调整 CPU/GPU 频率与电压以省电（Linux governor：`performance`、`powersave`、`schedutil`）；NVIDIA Jetson 有 `nvpmodel` 功耗模式与 `jetson_clocks` 锁频。
- 热降频：温度超限后硬件降频保护，运行一段时间后性能下降，导致基准测试结果前高后低、延迟抖动。
- 性能测试方法：固定 governor/锁频、等待温度稳定后再测、记录温度与频率、多次重复取分布而非单次。
- 机器人：电池供电时功耗模式影响续航；长时间运行（如巡检）必须在热稳态下验证帧率与延迟。

**English short answer**
Dynamic voltage and frequency scaling changes clocks with load, and thermal throttling lowers them when the chip is hot, so a benchmark can look fast at first and slow later. For reliable measurements I fix the governor or lock clocks, wait for thermal steady state, log temperature and frequency, and repeat the run. On robots I validate frame rate and latency at steady-state temperature.

（译：DVFS 随负载调频，芯片过热会降频，基准测试可能前快后慢；测试时固定 governor/锁频、等热稳态、记录温度频率、重复多次；机器人需在热稳态下验证帧率与延迟。）

**追问方向**：`jetson_clocks` 的作用；功耗与续航的权衡。

### Q60 GPU 编程中的锁页内存与异步拷贝是什么？（Pinned memory and streams）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 普通主机内存是可分页的，GPU DMA 需要先拷贝到临时锁页缓冲；**锁页（pinned）内存**不会被换出，可被 GPU 直接 DMA，带宽更高并支持异步拷贝。
- **流（stream）**：同一流内操作顺序执行，不同流可并行；把"拷贝 H2D → 计算 → 拷贝 D2H"分块放入多个流，可让拷贝与计算重叠（流水线），隐藏传输延迟。
- 注意：锁页内存过多会降低系统可用内存；小数据频繁拷贝开销大，宜批处理；统一内存（Jetson 上 CPU/GPU 共享物理内存）可减少拷贝。
- 推理部署：预处理放 GPU（resize/归一化），减少 CPU↔GPU 往返。

**English short answer**
Pinned host memory cannot be paged out, so the GPU can DMA from it directly, giving higher bandwidth and enabling asynchronous copies. Using several streams lets me overlap host-to-device copies, kernels and device-to-host copies in a pipeline. I batch small transfers and, on Jetson, take advantage of the shared physical memory.

（译：锁页内存不会被换出，GPU 可直接 DMA，带宽高并支持异步拷贝；多个流让拷贝与计算重叠形成流水线；小传输要批处理，Jetson 上可利用 CPU/GPU 共享内存。）

**追问方向**：如何用 nsys 查看重叠情况；CUDA 统一内存的缺页迁移。

### Q61 解释执行、JIT 与 AOT 编译的区别？（Interpreter, JIT, AOT）
**优先级：★★** · 对应基础知识：[Python工程与科学计算](../../02_基础知识/12_机器人软件/03_Python工程与科学计算.md)

**答案要点**
- 解释执行：逐条读取并执行字节码/源码（CPython），启动快、灵活但慢。
- AOT（提前编译）：运行前编译成机器码（C/C++/Rust），运行快、启动快，但失去运行时信息。
- JIT：运行时把热点代码编译为机器码（Java HotSpot、PyPy、PyTorch 的 `torch.compile` 与 TorchScript 概念、Numba），可用运行时类型信息优化，代价是预热时间和内存。
- 机器人：Python 做胶水与原型，计算密集部分用 C++/NumPy/Numba/CUDA；实时回路用 AOT 语言，避免 JIT 预热与 GC 的不确定停顿。
- 垃圾回收（GC）：引用计数（CPython，加循环检测）与追踪式 GC（Java，分代）；追踪式 GC 的停顿对实时有影响。

**English short answer**
An interpreter executes code step by step, which is flexible but slow. AOT compilation produces machine code ahead of time, which is fast with predictable startup. A JIT compiles hot code at run time using type feedback, trading warm-up time for speed. For real-time loops I prefer AOT languages, because JIT warm-up and garbage-collection pauses are unpredictable.

（译：解释执行灵活但慢；AOT 提前生成机器码，快且启动可预期；JIT 运行时按类型反馈编译热点，用预热换速度；实时回路选 AOT，避免 JIT 预热与 GC 停顿的不确定性。）

**追问方向**：引用计数与追踪 GC 的对比；Numba 的适用范围。

## 本章要点速记
1. 缓存以行为单位，局部性决定性能；伪共享与 DMA 一致性是两大典型陷阱。
2. 内存序不同于缓存一致性；x86 强、ARM 弱；`volatile` 不是线程同步。
3. 对齐、字节序、填充决定协议与结构体能否跨平台；用移位或 memcpy 解析。
4. 编译→汇编→链接→装载；`.data` 初值拷贝与 `.bss` 清零是 MCU 启动的关键。
5. undefined reference 查符号与库顺序；multiple definition 查头文件里的定义。
6. UB 会被优化器利用，Debug 正常 Release 出错时先用 sanitizer。
7. 实时代码避免运行时 `malloc`，用内存池；用 ASan/Valgrind 查内存错误。
