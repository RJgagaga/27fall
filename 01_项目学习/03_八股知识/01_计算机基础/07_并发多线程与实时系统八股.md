## 一、线程安全基础

### Q1 什么是线程安全？怎么保证？（Thread safety）
**优先级：★★★**

**答案要点**
- 线程安全：多线程并发调用时，行为正确，不出现数据竞争（data race）、不变量被破坏。
- 数据竞争：两个线程并发访问同一内存，至少一个是写，且无同步。在 C/C++ 中是**未定义行为**。
- 保证方式（由易到难）：
  1. **不共享**：每线程私有数据、线程局部存储、消息传递（队列）；
  2. **不可变**：共享的只读数据（`const`）；
  3. **互斥**：锁保护临界区；
  4. **原子操作**：单个变量；
  5. **无锁结构**：最难，慎用。
- 原则：共享可变状态最少化，"通过通信来共享内存，而不是通过共享内存来通信"。

**English short answer**
Thread safe code stays correct under concurrent calls, with no data races. A data race is two threads touching the same memory without synchronization with at least one writing, which is undefined behaviour in C and C++. I minimize shared mutable state first by giving each thread its own data or passing messages through queues, and then protect what remains with locks or atomics.

**追问方向**：可重入与线程安全的区别；`thread_local`。

### Q2 竞态条件的经典例子与修复？（Race condition example）
**优先级：★★★**

**答案要点**：`counter++` 编译为 load、add、store，两个线程交错会丢失更新。检查再行动（check-then-act）如"if 队列不空再 pop"也有竞态。

```cpp
// 教学示例：丢失更新
int counter = 0;
void work(){ for (int i = 0; i < 100000; ++i) ++counter; }  // 数据竞争, UB
// 修复1: std::atomic<int> counter;  ++counter;
// 修复2: 用 std::mutex 保护
```

**English short answer**
Incrementing a shared integer is really a load, an add and a store, so two threads can read the same old value and one update is lost. I fix it with an atomic integer or a mutex. The same applies to check-then-act sequences such as testing that a queue is non-empty and then popping.

**追问方向**：TOCTOU；如何用 TSan 发现。

### Q3 `mutex`、`lock_guard`、`unique_lock`、`scoped_lock` 怎么选？（C++ locking utilities）
**优先级：★★★**

**答案要点**：`lock_guard`：最简单 RAII，作用域内持锁。`unique_lock`：可延迟加锁、提前解锁、配合条件变量 `wait`、可转移。`scoped_lock`（C++17）：同时锁多个互斥量，内部用死锁避免算法。锁粒度：尽量缩短临界区，不在持锁时做 IO、回调或调用未知代码。

```cpp
std::mutex m;
std::vector<int> v;
void add(int x){ std::lock_guard<std::mutex> g(m); v.push_back(x); }
void transfer(Account& a, Account& b){
    std::scoped_lock lk(a.m, b.m);   // 同时锁，避免死锁
    // ...
}
```

**English short answer**
lock_guard is the simplest scoped lock. unique_lock is more flexible: it can be unlocked early, deferred, moved, and it is required for condition variables. scoped_lock locks several mutexes at once without deadlocking. I keep critical sections short and never call unknown code while holding a lock.

**追问方向**：`try_lock`；`timed_mutex`；递归锁的坏味道。

### Q4 有哪些锁类型？各自适用场景？（Lock types）
**优先级：★★★**

| 锁 | 特点 | 场景 |
|---|---|---|
| 互斥锁 mutex | 阻塞休眠 | 通用 |
| 自旋锁 spinlock | 忙等，不切换 | 临界区极短、多核、内核/中断 |
| 递归锁 recursive_mutex | 同线程可重入 | 少用，通常表示设计问题 |
| 读写锁 shared_mutex | 多读单写 | 读多写少 |
| 乐观锁（CAS/版本号） | 冲突才重试 | 低冲突 |
| 悲观锁 | 先锁再访问 | 高冲突 |
| 信号量 | 计数 | 资源池、同步 |
| 屏障 barrier | 等待所有线程到达 | 分阶段并行 |

**答案要点**：单核 MCU 上自旋无意义（持锁线程被抢占时，等待者空转到时间片耗尽）；中断与任务共享数据通常"关中断临界区"或 FreeRTOS `taskENTER_CRITICAL`。

**English short answer**
A mutex puts waiters to sleep, a spinlock busy-waits and suits only very short critical sections on multi-core hardware, a read-write lock allows many readers, and a semaphore counts resources. Recursive locks usually hint at a design problem. On a single-core microcontroller I protect data shared with an interrupt by briefly disabling interrupts.

**追问方向**：自旋锁实现（test-and-set）；公平性。

### Q5 条件变量怎么用？为什么必须用循环检查谓词？（Condition variables）
**优先级：★★★**

**答案要点**：条件变量让线程等待"某个条件成立"，避免忙等。`wait(lock, pred)` 内部：解锁并睡眠 → 被唤醒 → 重新加锁 → 检查谓词。必须用谓词循环，原因：①**虚假唤醒**（spurious wakeup）；②多个等待者时被别人抢先消费；③通知先于等待发生（丢失唤醒）则靠谓词状态弥补。

```cpp
std::mutex m; std::condition_variable cv; std::queue<int> q;
void consumer(){
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, []{ return !q.empty(); });
    int x = q.front(); q.pop();
}
void producer(int x){
    { std::lock_guard<std::mutex> g(m); q.push(x); }
    cv.notify_one();
}
```

**English short answer**
A condition variable lets a thread sleep until some condition holds. I always wait with a predicate in a loop, because wakeups can be spurious, another consumer may have taken the item first, and a notification sent before the wait must not be lost. The shared state is protected by the same mutex.

**追问方向**：`notify_one` vs `notify_all`；先通知后等待。

## 二、原子操作、内存序、无锁

### Q6 什么是原子操作？`std::atomic` 提供什么？（Atomic operations）
**优先级：★★★**

**答案要点**：原子操作不可分割，其他线程只能看到操作前或操作后，不会看到中间状态。`std::atomic<T>`：`load/store/exchange/fetch_add/compare_exchange`。`is_lock_free()` 检查是否由硬件指令实现（Cortex-M 上 32 位原子通过 LDREX/STREX 实现，Cortex-M0 没有这些指令，需关中断实现）。原子只保证**单个变量**的原子性与可见性顺序，不保证多个变量间的不变量。

```cpp
std::atomic<int> hits{0};
hits.fetch_add(1, std::memory_order_relaxed);
```

**English short answer**
An atomic operation cannot be observed half done by other threads. std::atomic provides load, store, exchange, fetch-and-add and compare-exchange. It guarantees atomicity of a single variable, not consistency across several variables, so multi-variable invariants still need a lock.

**追问方向**：LL/SC 与 CAS；is_lock_free。

### Q7 CAS 是什么？ABA 问题？（Compare-and-swap and ABA）
**优先级：★★★**

**答案要点**：CAS(addr, expected, desired)：若 `*addr == expected` 则写入 `desired` 并返回成功，否则把当前值回写 `expected` 并失败，整个过程原子。用循环重试实现无锁更新：

```cpp
std::atomic<int> v{0};
int old = v.load();
while (!v.compare_exchange_weak(old, old * 2)) { /* old 已更新, 重试 */ }
```

ABA：线程 1 读到 A，被切走；线程 2 把 A 改成 B 再改回 A；线程 1 的 CAS 成功，但中间状态已变（无锁栈中节点被释放重用时会出严重错误）。解决：带版本号的指针（tagged pointer）、危险指针（hazard pointer）、epoch 回收。`compare_exchange_weak` 可能伪失败，适合循环；`strong` 不会伪失败。

**English short answer**
Compare-and-swap atomically writes a new value only if the current value still equals the expected one, so I can build lock-free updates with a retry loop. The ABA problem is when the value changes from A to B and back to A, so the CAS succeeds even though the state changed in between; it is solved with version counters or safe memory reclamation techniques.

**追问方向**：无锁栈实现；weak 与 strong 区别。

### Q8 内存序（memory order）到底在解决什么问题？（Memory ordering）
**优先级：★★★**

**答案要点**
- 编译器和 CPU 为了性能会**重排**无依赖的读写；单线程看不出，多线程会看到"意外"的顺序。
- C++ 的 `memory_order`：
  - `relaxed`：只保证该操作原子，不保证与其他操作的顺序（计数器、统计）。
  - `release`（写）+ `acquire`（读）：配对形成**同步关系**，release 之前的所有写，在读到该值的 acquire 之后可见。
  - `seq_cst`：默认，全局统一顺序，最强也最慢。
- 经典：消息传递模式。

```cpp
int data = 0; std::atomic<bool> ready{false};
// 线程 A
data = 42;
ready.store(true, std::memory_order_release);
// 线程 B
if (ready.load(std::memory_order_acquire)) { assert(data == 42); }
```
- 硬件差异：x86 是强序（TSO），acquire/release 几乎免费；ARM 是弱序，需要 `dmb` 屏障指令；所以"在 x86 上正常"的无锁代码移到 ARM 可能出 bug。
- 不确定时用默认 `seq_cst` 或直接用锁。

**English short answer**
Compilers and CPUs reorder independent memory operations for speed, which is invisible in one thread but visible across threads. Release and acquire operations are paired: everything written before a release store is visible to a thread that reads that value with an acquire load. Relaxed gives only atomicity, and seq_cst gives a single global order. x86 is strongly ordered, but ARM is weakly ordered, so code that works on a PC may break on an ARM board.

**追问方向**：什么是 happens-before；双检锁为何需要原子；内存屏障指令。

### Q9 `volatile` 与 `atomic` 的区别？（volatile vs atomic）
**优先级：★★★**

**答案要点**：`volatile`（C/C++）只阻止编译器优化掉/合并对该变量的访问，**不保证原子性，不保证 CPU 层面的顺序和可见性**。`atomic` 保证原子性并带内存序语义。例外：单核 MCU 里，ISR 与主循环间共享的对齐 32 位标志，用 `volatile` 往往够用，因为没有其他核心和 cache 重排问题，且对齐的 32 位读写在 Cortex-M 上是单指令；但读-改-写（`++`）仍需保护。Java 的 `volatile` 语义与 C++ 不同（带可见性和有序性）——面试时注意区分语言。

**English short answer**
In C and C++, volatile only stops the compiler from optimizing accesses away. It gives no atomicity and no ordering between cores. std::atomic gives both atomicity and memory ordering. On a single-core microcontroller a volatile aligned flag shared with an interrupt is usually fine, but an increment still needs protection.

**追问方向**：Java volatile；`sig_atomic_t`。

### Q10 什么是无锁（lock-free）与无等待（wait-free）？优缺点？（Lock-free）
**优先级：★★**

**答案要点**：无锁：系统整体总有线程能前进（个别线程可能饥饿）；无等待：每个线程都在有限步内完成。优点：无死锁、无优先级反转、适合中断上下文与实时路径；缺点：实现困难（ABA、内存回收、内存序）、调试困难，不一定比锁快（高竞争时 CAS 自旋浪费）。实践：优先使用成熟实现——SPSC 环形队列（单生产者单消费者）是最实用、最简单的无锁结构。

**English short answer**
Lock-free means that at least one thread always makes progress, and wait-free means every thread finishes in a bounded number of steps. They avoid deadlock and priority inversion and suit interrupt contexts, but they are very hard to get right, so I use well-tested structures such as a single-producer single-consumer ring buffer.

**追问方向**：SPSC 队列实现；MPMC。

### Q11 单生产者单消费者无锁环形队列怎么写？（SPSC ring buffer）
**优先级：★★★**

**答案要点**：关键是**只有生产者写 head，只有消费者写 tail**，各自读对方的索引；容量取 2 的幂，用掩码代替取模；写数据先于更新 head（release），读 head 用 acquire。适用于 ISR → 任务（UART 接收）、采样线程 → 处理线程。

```cpp
template <class T, size_t N>   // N 为 2 的幂, 教学示例
class Spsc {
    T buf_[N]; std::atomic<size_t> head_{0}, tail_{0};
public:
    bool push(const T& v){
        size_t h = head_.load(std::memory_order_relaxed);
        if (h - tail_.load(std::memory_order_acquire) == N) return false; // 满
        buf_[h & (N-1)] = v;
        head_.store(h + 1, std::memory_order_release);
        return true;
    }
    bool pop(T& out){
        size_t t = tail_.load(std::memory_order_relaxed);
        if (t == head_.load(std::memory_order_acquire)) return false;     // 空
        out = buf_[t & (N-1)];
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }
};
```

**English short answer**
In a single-producer single-consumer ring buffer only the producer writes the head index and only the consumer writes the tail index. The producer writes the element first and then publishes the new head with a release store; the consumer reads the head with an acquire load. Using a power-of-two capacity lets me wrap indices with a mask. It needs no lock, which makes it ideal between an interrupt and a task.

**追问方向**：为什么不用取模；false sharing 与缓存行对齐；多生产者怎么办。

### Q12 伪共享（false sharing）是什么？（False sharing）
**优先级：★★**

**答案要点**：不同线程频繁写**同一缓存行**（典型 64 字节）里的不同变量，使该缓存行在核心间来回失效，性能骤降，尽管逻辑上互不相关。解决：把热点变量按缓存行对齐/填充（`alignas(64)`），或让每个线程使用独立的数据结构。SPSC 队列的 head 与 tail 常故意分在不同缓存行。

**English short answer**
False sharing happens when two threads write different variables that live on the same cache line, so the line bounces between cores and performance collapses. The fix is to align or pad hot variables to separate cache lines.

**追问方向**：`std::hardware_destructive_interference_size`。

## 三、线程池与并发模式

### Q13 线程池的原理与实现？（Thread pool）
**优先级：★★★**

**答案要点**：预先创建固定数量的工作线程，任务放入共享**任务队列**，工作线程循环取任务执行。好处：避免频繁创建销毁线程，限制并发度，防止线程爆炸。要点：队列加锁 + 条件变量；停止标志；任务异常处理；线程数选择——CPU 密集约等于核数，IO 密集可更多（经验：$N_{cpu}(1+W/C)$，$W/C$ 为等待/计算时间比）。

```cpp
class ThreadPool {
    std::vector<std::thread> ws_;
    std::queue<std::function<void()>> q_;
    std::mutex m_; std::condition_variable cv_; bool stop_ = false;
public:
    explicit ThreadPool(size_t n){
        for (size_t i = 0; i < n; ++i) ws_.emplace_back([this]{
            for(;;){
                std::function<void()> job;
                { std::unique_lock<std::mutex> lk(m_);
                  cv_.wait(lk, [this]{ return stop_ || !q_.empty(); });
                  if (stop_ && q_.empty()) return;
                  job = std::move(q_.front()); q_.pop(); }
                job();
            }});
    }
    void submit(std::function<void()> f){
        { std::lock_guard<std::mutex> g(m_); q_.push(std::move(f)); }
        cv_.notify_one();
    }
    ~ThreadPool(){
        { std::lock_guard<std::mutex> g(m_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : ws_) t.join();
    }
};
```

**English short answer**
A thread pool creates a fixed set of worker threads that take jobs from a shared queue. This avoids the cost of creating threads per task and limits concurrency. The queue is protected by a mutex and a condition variable, and on shutdown I set a stop flag, notify all workers and join them. For CPU-bound work I size the pool near the number of cores.

**追问方向**：任务窃取（work stealing）；返回 future；队列有界还是无界。

### Q14 生产者—消费者模型，有界阻塞队列怎么写？（Producer-consumer, bounded blocking queue）
**优先级：★★★**

**答案要点**：解耦生产与消费速率，缓冲突发。**有界**队列提供背压（队满时生产者阻塞或丢弃），防止内存无限增长；无界队列在消费者慢时会耗尽内存。机器人里：传感器线程 → 处理线程；日志线程。队满策略：阻塞、丢最旧（实时数据常保留最新）、丢最新。

```python
# 教学示例：Python 有界队列，满时丢最旧（保留最新数据）
import queue
def put_latest(q: queue.Queue, item):
    try:
        q.put_nowait(item)
    except queue.Full:
        try: q.get_nowait()
        except queue.Empty: pass
        q.put_nowait(item)
```

**English short answer**
A producer-consumer queue decouples the rate of producing and consuming data and absorbs bursts. A bounded queue also gives backpressure, because when it is full the producer blocks or drops data, instead of memory growing without limit. For real-time sensor data I often drop the oldest item so the consumer always works on the freshest sample.

**追问方向**：多生产者多消费者；用信号量实现；背压策略。

### Q15 死锁、活锁、饥饿怎么区分？怎么排查？（Deadlock, livelock, starvation）
**优先级：★★★**

**答案要点**：死锁：互相等待对方持有的资源，永久阻塞。活锁：线程不断响应对方而不前进（两人走廊互让）。饥饿：某线程长期得不到资源（低优先级、不公平锁）。排查死锁：`gdb` 的 `thread apply all bt` 查看各线程在等哪把锁；日志加锁顺序；Helgrind/TSan 的锁序检测。预防见 [操作系统](./02_操作系统.md) 的死锁四条件：统一加锁顺序最实用。

**English short answer**
In a deadlock, threads wait for each other forever. In a livelock they keep reacting to each other but make no progress. In starvation one thread never gets a resource. To debug a deadlock I dump the stacks of all threads to see which locks they wait on, and I prevent it with a global lock ordering.

**追问方向**：哲学家就餐；锁序检测工具。

### Q16 如何设计线程模型：控制线程、通信线程、日志线程？（Designing threads for a robot node）
**优先级：★★★**

**答案要点**：典型做法：①**控制线程**：固定周期、高优先级、绝不阻塞在不确定的 IO/锁上，不分配内存，不打日志（写入无锁队列交给日志线程）；②**通信线程**：接收命令/传感器，写入"最新值"缓冲（latest-value buffer）或 SPSC 队列；③**日志/诊断线程**：低优先级，批量写盘；④**规划线程**：中等优先级，输出目标给控制线程。控制线程读取命令时取"最新一份快照"（双缓冲/seqlock），而非加长时间锁。这与"高层规划、低层闭环、两者通过有界数据交换"的分层结构一致（P5 导航栈、P7 控制环都是该思想的实例）。

```text
 [通信线程]--SPSC-->[规划线程]--最新目标(双缓冲)-->[控制线程 高优先级 固定周期]-->执行器
                                   ^                      |
                                   +-------状态快照--------+
 [日志线程 低优先级] <--SPSC-- (控制/通信 线程只推入日志条目)
```

**English short answer**
I give the control loop its own high-priority thread with a fixed period, and it never blocks on unbounded operations, never allocates memory and does not print. Communication threads feed it through a latest-value buffer or a lock-free queue, and a low-priority logging thread writes data out. The control thread takes a snapshot of its inputs, so it never waits on a long lock.

**追问方向**：双缓冲实现；如何测控制线程抖动；ROS2 executor。

### Q17 `std::async`、`future/promise`、协程之间的关系？（async, future, promise）
**优先级：★★**

**答案要点**：`std::promise` 写入结果，`std::future` 读取；`std::async` 一键启动异步任务并返回 future，`launch::async` 强制新线程，默认策略可能延迟执行。`future::get` 阻塞并传播异常。C++20 协程是语言级的可暂停函数。Python 的 `concurrent.futures.Future` 与 asyncio 的 `Future` 类似但不同。

**English short answer**
A promise is where a result is written, and the matching future is where it is read, blocking until ready and rethrowing any exception. std::async starts a task and returns a future. C++20 coroutines are a language-level way to suspend and resume functions.

**追问方向**：`shared_future`；析构阻塞的陷阱。

### Q18 线程局部存储与线程数据？（Thread-local storage）
**优先级：★★**

**答案要点**：`thread_local`（C++11）、`threading.local`（Python）、pthread key。每个线程独立副本，避免共享。用途：`errno`、随机数引擎、每线程缓存。注意生命周期与线程池里线程复用时的残留状态。

**English short answer**
Thread-local storage gives each thread its own copy of a variable, which removes sharing and the need for locks. It is used for things like errno, random generators and per-thread caches.

**追问方向**：线程池复用的陷阱。

## 四、实时系统与调度

### Q19 硬实时、软实时、固实时的区别？（Hard vs soft real-time）
**优先级：★★★**

**答案要点**：硬实时：错过截止期即系统失败，后果严重（电机控制环、平衡机器人、刹车）；软实时：偶尔超期降低质量但可接受（视频、UI）；固实时（firm）：结果过期无价值但系统不失败。"实时"≠"快"，而是**可预测**（在已知上界内完成）。平衡类机器人（如 P1 球形机器人、P7 轮腿）的内环属于硬实时需求：控制周期若丢失会导致失稳（一般性判断，具体容忍度要实测）。

**English short answer**
In a hard real-time system a missed deadline is a failure, as in a motor control loop on a balancing robot. In a soft real-time system occasional misses just degrade quality. Real time means predictable and bounded latency, not simply fast.

**追问方向**：为什么 Linux 不是硬实时；截止期 miss 的处理。

### Q20 FreeRTOS 的任务划分与优先级分配原则？（Task design in an RTOS）
**优先级：★★★**

**答案要点**
- 原则：周期短、截止期紧的任务优先级高（接近 RM）；阻塞等待事件的任务大多数时间不占 CPU；高优先级任务必须**短**并尽快回到阻塞状态，否则饿死低优先级任务。
- 典型划分（教学示例）：IMU 采样与姿态解算（高）→ 控制环（高）→ CAN 收发（中高，往往靠中断 + 队列）→ 遥控/视觉数据解析（中）→ 调试日志（低）→ 空闲任务。
- 任务间通信：队列（数据）、任务通知（轻量信号，比信号量快）、事件组、互斥量（带优先级继承）。
- 避免：在高优先级任务里忙等；两个同优先级任务都不阻塞（时间片轮转导致抖动）；在 ISR 里做重活。
- 周期任务用 `vTaskDelayUntil`；让硬件定时器中断通知控制任务的方式抖动更低。

```c
// 教学示例：定时器中断通知控制任务（任务通知）
void TIM_IRQHandler(void){
    BaseType_t w = pdFALSE;
    vTaskNotifyGiveFromISR(ctrl_task_handle, &w);
    portYIELD_FROM_ISR(w);
}
void ctrl_task(void *p){
    for(;;){
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);   // 等待周期节拍
        read_sensors(); control_step(); write_outputs();
    }
}
```

**English short answer**
I assign higher priority to tasks with shorter periods and tighter deadlines, as in rate-monotonic scheduling. High-priority tasks must be short and block again quickly, otherwise they starve everything below. Interrupts handle the time-critical hardware part and signal tasks through notifications or queues. For a precise control period I can trigger the control task from a hardware timer interrupt instead of relying only on the tick delay.

**追问方向**：任务通知与信号量的区别；两个同优先级任务；栈大小估算。

### Q21 优先级反转与优先级继承（再讲一遍并对比天花板）（Priority inversion in depth）
**优先级：★★★**

**答案要点**
- 场景：L 持有锁 → H 请求该锁被阻塞 → M（不需要锁）抢占 L，H 被 M 间接压住，延迟不可界定。
- 优先级继承（PIP）：持锁的 L 暂时提升到等待者 H 的优先级，使其尽快跑完并释放锁，之后恢复。FreeRTOS `xSemaphoreCreateMutex` 具备；二值信号量**没有**。
- 优先级天花板（PCP）：每把锁有天花板优先级 = 所有可能使用它的任务中最高者，持锁任务立即提升到天花板；可同时避免死锁和链式阻塞。
- 设计层面最好：避免高低优先级任务共享锁，改用消息队列或无锁结构；在 ISR 里不能用互斥量。
- 症状：高优先级任务偶发超时，且与某低优先级任务的运行相关。

**English short answer**
Priority inversion occurs when a low-priority task holds a lock needed by a high-priority task and a medium-priority task keeps preempting the low one, so the high-priority task waits for an unbounded time. Priority inheritance temporarily raises the lock holder to the waiter's priority, and a priority ceiling protocol raises it to the lock's maximum priority immediately. In FreeRTOS I use a mutex rather than a binary semaphore for this reason, and better still, I avoid sharing locks between very different priorities.

**追问方向**：中断与优先级反转；继承链；如何复现。

### Q22 速率单调与可调度性分析（再给一个手算例子）（RM schedulability, worked example）
**优先级：★★**

**答案要点**：RM 利用率上界 $U\le n(2^{1/n}-1)$：$n=1$ 为 1，$n=2$ 为 0.828，$n=3$ 为 0.780，$n\to\infty$ 为 $\ln 2\approx0.693$。这是**充分不必要**条件。精确分析：响应时间法 $R_i = C_i + \sum_{j\in hp(i)} \lceil R_i/T_j \rceil C_j$，迭代至收敛，$R_i \le D_i$ 则可调度。

教学示例（非项目数据）：任务 A：$C=0.2\,\text{ms}$，$T=1\,\text{ms}$（高）；任务 B：$C=1.0\,\text{ms}$，$T=5\,\text{ms}$（低）。
- $U = 0.2/1 + 1/5 = 0.4 < 0.828$ 可调度。
- B 的响应时间：$R^{(0)}=1.0$；$R^{(1)}=1.0+\lceil 1.0/1\rceil\cdot0.2=1.2$；$R^{(2)}=1.0+\lceil1.2/1\rceil\cdot0.2=1.4$；$R^{(3)}=1.0+\lceil 1.4/1\rceil\cdot 0.2=1.4$，收敛，$R_B=1.4\,\text{ms}\le 5\,\text{ms}$。

**English short answer**
For rate-monotonic scheduling, a task set is guaranteed schedulable if the total utilization is below n times two to the one over n minus one, which tends to about 69 percent. That is sufficient but not necessary, so for exact analysis I iterate the response time equation for each task and compare it with its deadline. Both require good estimates of the worst-case execution time.

**追问方向**：阻塞时间项；EDF；多核。

### Q23 实时性指标：延迟、抖动、截止期错过率？怎么测？（Latency, jitter, deadline misses）
**优先级：★★★**

**答案要点**
- **中断延迟**：事件发生到 ISR 第一条指令的时间；**调度延迟**：任务就绪到真正运行；**执行时间**；**响应时间** = 以上之和；**周期抖动**：连续两次执行起点间隔的偏差，常用最大/标准差/直方图描述；**截止期错过率**。
- 测量：①GPIO 翻转 + 示波器/逻辑分析仪（最可信，几乎无侵入）；②DWT 周期计数器（Cortex-M3+）打时间戳；③在运行期对每个周期记录 `now - last` 到环形缓冲，离线统计 min/max/avg/P99；④Linux 用 `cyclictest`。
- 注意：测量本身不能影响被测系统（不要在里面 printf）；要在系统满负载下测最坏值，而不是空载。
- 降低抖动：提高优先级；缩短关中断区；避免 cache miss 抖动（把关键代码放 ITCM/锁定 cache）；DMA；固定频率硬件定时触发；Linux 上 PREEMPT_RT、CPU 隔离 `isolcpus`、`mlockall`、关闭动态调频。
- 我们的做法：控制周期典型取 1～2 ms（P3 云台/底盘）和约 1～2 ms 量级（P7 控制任务，以实机为准）；抖动的测量方法是每周期记录 DWT 周期计数器时间戳，离线统计最大/标准差/P99，并用 GPIO 翻转配合示波器交叉验证。典型目标是抖动不超过周期的 10%（教学示例，非项目实测数据）。

**English short answer**
The key metrics are interrupt latency, scheduling latency, execution time and period jitter, which is how much the actual start times vary around the nominal period. I measure with a GPIO toggle and a scope or logic analyzer, or with the cycle counter, and log timestamps into a ring buffer for offline statistics, always under full system load. To reduce jitter I raise task priority, shorten interrupt-disabled sections, use DMA and hardware timers, and on Linux use the real-time kernel features.

**追问方向**：最坏情况与平均情况；cyclictest；时钟源精度。

### Q24 Linux 上做实时控制应该注意什么？（Real-time on Linux）
**优先级：★★**

**答案要点**：①`SCHED_FIFO` + 合理优先级（`chrt`、`pthread_setschedparam`），需权限；②`mlockall(MCL_CURRENT|MCL_FUTURE)` 防止缺页；③预分配内存与预热；④避免在实时线程里 malloc、IO、锁竞争；⑤绑核 `taskset`/`isolcpus`；⑥PREEMPT_RT 补丁；⑦时钟用 `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME)` 绝对时间睡眠避免漂移；⑧关闭省电；⑨ROS2 中使用 `rclcpp` 的实时友好写法（预分配消息、专用 executor）。

```c
// 教学示例：绝对时间周期循环
struct timespec next; clock_gettime(CLOCK_MONOTONIC, &next);
for(;;){
    next.tv_nsec += 2000000;                       // 教学示例: 2 ms
    if (next.tv_nsec >= 1000000000L){ next.tv_nsec -= 1000000000L; next.tv_sec++; }
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
    control_step();
}
```

**English short answer**
For real-time control on Linux I use the SCHED_FIFO policy, lock memory with mlockall, preallocate everything, avoid blocking calls in the loop, pin the thread to an isolated core, and ideally run a PREEMPT_RT kernel. I sleep until absolute times so the period does not drift.

**追问方向**：为什么相对睡眠会漂移；Linux 与 MCU 分工。

### Q25 看门狗、超时与故障安全如何与并发设计结合？（Watchdog and fail-safe with concurrency）
**优先级：★★**

**答案要点**：多任务系统中看门狗应由一个监督任务统一喂：各关键任务周期性设置"心跳位"（事件组位），监督任务检查全部到齐才喂狗；任何任务卡死（死锁、无限等待）都会触发复位。每个阻塞调用使用**超时**而非永远等待。通信超时 → 进入安全状态（停止输出、保持姿态或平稳降速）。与 P1 的"状态初始化、输出限幅、倒地恢复"（CV）同属安全设计思路。

**English short answer**
In a multitask system I let a supervisor task feed the watchdog only when every critical task has reported its heartbeat, so a deadlock in any task triggers a reset. I use timeouts on all blocking calls, and when communication times out the robot goes into a safe state.

**追问方向**：事件组实现心跳；复位后的状态恢复。

## 五、综合与场景题

### Q26 设计一个线程安全的"最新传感器数据"缓冲，供高频控制线程读取？（Latest-value buffer design）
**优先级：★★★**

**答案要点**：目标：写者（通信线程）更新，读者（控制线程）永远不阻塞，读到的是一致的完整结构体。方案：
1. **双缓冲 + 原子索引**：写者写非活动缓冲，写完用 `store(release)` 切换索引；读者 `load(acquire)` 读当前缓冲。注意读者拷贝时写者可能已在翻回——若写频率高于读，需三缓冲。
2. **seqlock**：写者 `seq++`（奇数表示写中）→ 写数据 → `seq++`（偶数）；读者读前后比较 `seq`，不一致或奇数则重试。读者无锁，写者很少。
3. 关中断极短拷贝（MCU）。

```cpp
// 教学示例: seqlock 读者
Data read_data(){
    Data d; uint32_t s1, s2;
    do {
        s1 = seq.load(std::memory_order_acquire);
        d = shared;                                  // 实际需保证拷贝期间的数据竞争语义, 示意
        std::atomic_thread_fence(std::memory_order_acquire);
        s2 = seq.load(std::memory_order_relaxed);
    } while ((s1 & 1) || s1 != s2);
    return d;
}
```
> **注意**：严格的 C++ 内存模型下 seqlock 的数据拷贝需要用原子/relaxed 逐字段读取才无 UB，上面为简化示意。

**English short answer**
I want the control thread to read a consistent snapshot without ever blocking. One way is a double or triple buffer, where the writer fills a spare buffer and then atomically publishes its index. Another is a seqlock, where the writer increments a sequence number before and after writing and the reader retries if the number changed or was odd. Both avoid long locks and priority inversion.

**追问方向**：为什么不直接用 mutex（优先级反转、阻塞）；三缓冲。

### Q27 多线程程序性能没提升甚至变慢，可能的原因？（Why multi-threading is slower）
**优先级：★★**

**答案要点**：锁竞争严重；临界区太大；伪共享；线程数大于核数导致频繁切换；任务粒度太细（调度开销 > 计算）；内存带宽受限；GIL（Python）；串行部分占比大（阿姆达尔定律：加速比 $S=1/((1-p)+p/n)$，$p=0.9, n=8$ 时 $S\approx4.7$）。排查：profile、`perf`、查看锁等待时间。

**English short answer**
Typical reasons are heavy lock contention, false sharing, too many threads for the cores, tasks that are too small, a memory bandwidth limit, the GIL in Python, or a large serial fraction as described by Amdahl's law. I profile to see where threads are waiting.

**追问方向**：Amdahl 与 Gustafson；`perf`、`htop` 查看。

### Q28 ROS 里的回调线程模型与线程安全？（Callbacks in ROS）
**优先级：★★**

**答案要点**：ROS1 `spin()` 单线程按序执行回调，`AsyncSpinner` 多线程；ROS2 的 executor：`SingleThreadedExecutor`、`MultiThreadedExecutor`，回调组（`MutuallyExclusive` / `Reentrant`）控制是否并行。同一节点多个回调共享成员变量时需要锁或回调组互斥。避免在回调里做耗时计算或阻塞（会拖慢整个 executor）。见 [ROS1_ROS2核心概念](../../02_基础知识/09_机器人软件/04_ROS1_ROS2核心概念.md)。

**English short answer**
In ROS2 an executor runs callbacks, either on one thread or on a pool. Callback groups define whether callbacks may run in parallel, so I use mutually exclusive groups or locks when callbacks share state. I keep callbacks short, and move heavy computation to a separate thread.

**追问方向**：回调饥饿；定时器与订阅回调的顺序。

### Q29 如何调试并发 bug？（Debugging concurrency bugs）
**优先级：★★★**

**答案要点**：并发 bug 难复现。手段：①ThreadSanitizer（`-fsanitize=thread`）检测数据竞争；Helgrind 检测锁序；②压力测试（多次循环、提高线程数、加随机延时 `sleep` 扩大时间窗口）；③日志带线程 id 与时间戳（低侵入）；④`gdb` 看全部线程栈；⑤嵌入式：HardFault 分析、栈水位、事件追踪（Percepio Tracealyzer / SEGGER SystemView 可视化任务调度）；⑥代码评审：关注共享变量、锁顺序、`volatile` 误用。

**English short answer**
I use ThreadSanitizer to find data races, stress tests with random delays to widen race windows, and logs with thread ids and timestamps. For stuck programs I dump all thread stacks with gdb. On an RTOS I use a trace tool to visualize task scheduling.

**追问方向**：TSan 局限；Heisenbug。

### Q30 描述一次你遇到的并发/实时问题的排查过程（行为面试模板）（Behavioral: a concurrency bug story）
**优先级：★★**

**答案要点**：此题考真实经历，**不要编造**。CV 里可用的相关线索：P7 "traced balance anomalies to state inconsistency, torque limits and ground-contact transitions"（把平衡异常追溯到状态不一致、力矩限制、触地切换）；P1 "ROS state processing with CAN motor execution"；P5 "drift and pose jumps from inconsistent timing, frames and motion direction"（时间戳、坐标系不一致造成漂移与位姿跳变）。可围绕"时间一致性/状态不一致"讲，用 STAR 结构。下面是一条与 CV 一致、不含具体数值的排查路线（P7 场景）：**现象**——机器人在触地切换（腾空到落地）附近平衡变差，力矩输出出现突变；**定位**——给每路反馈（IMU、轮速、关节）打上时间戳并记录控制周期内的取样时刻，发现腿长估计与轮速取自不同周期（状态不一致），同时力矩在触地瞬间触及限幅；**修复**——每个周期开头取一次整块快照，所有计算只用这一份快照，并对触地状态加入滞回，输出限幅后再下发；**验证**——在同一工况下对比修复前后的姿态角波形与力矩是否触顶，并反复测试触地切换。

**English short answer**
In my wheel-legged robot project, I traced a balance anomaly to inconsistent state data. The robot became unstable around ground-contact transitions, and the torque sometimes hit its limit. I timestamped every feedback source and found that the leg state and the wheel speed used by one control step came from different cycles. I fixed it by taking one snapshot at the start of each cycle and computing everything from it, added hysteresis to the contact detection, and limited the output. I verified it by running the same test before and after and comparing the pitch response and the torque.
（中文：轮腿项目中，平衡异常出现在触地切换附近且力矩触顶；给各路反馈打时间戳，发现同一控制步用了不同周期的腿状态和轮速；改为每周期取一次快照、触地检测加滞回、输出限幅；在同一工况下对比修复前后的俯仰响应和力矩来验证。）

**追问方向**：你怎么证明修好了；有没有回归测试。

## 六、补充题：RTOS 机制、中断与工程细节

### Q31 读写锁（读多写少）怎么用？有什么坑？（Reader-writer lock）
**优先级：★★**

**答案要点**
- 读写锁允许**多个读者并发**、**写者独占**：C++17 `std::shared_mutex`（读用 `std::shared_lock`，写用 `std::unique_lock`）。适合读远多于写、读临界区较长的数据（如地图、配置表）。
- 坑：①读临界区很短时，读写锁自身开销（原子操作、缓存行争用）可能比普通 `mutex` 还大；②写者饥饿或读者饥饿，取决于实现的公平性；③读锁不能升级为写锁（会死锁），要先释放再重新获取；④在控制线程里依然可能因写者持锁而被阻塞，实时路径上更倾向快照或无锁。
- 控制线程读"最新传感器值"这类场景，用双缓冲/seqlock（见 Q26）比读写锁更合适。

**English short answer**
A reader-writer lock lets many readers hold the lock together while a writer gets exclusive access. It helps when reads dominate and the read section is long, such as a shared map or configuration. It does not help for tiny critical sections, you cannot upgrade a read lock to a write lock, and a control thread can still be blocked by a writer, so for hard timing I prefer snapshots.
（中文：读写锁允许多读者并发、写者独占；适合读多写少且读临界区较长；临界区很短时无收益，读锁不能升级，写者仍可能阻塞控制线程，所以强实时更倾向快照。）

**追问方向**：写者饥饿；`shared_timed_mutex`；RCU 思想。

### Q32 信号量、互斥量、二值信号量有什么区别？（Semaphore vs mutex）
**优先级：★★★**

**答案要点**
- **互斥量（mutex）**：保护共享资源，有**所有权**——谁加锁谁解锁；FreeRTOS 的互斥量带**优先级继承**，不能在 ISR 中使用。
- **计数信号量**：计数资源个数（如缓冲区空槽数），无所有权，任何任务/ISR 都可 give。
- **二值信号量**：计数上限为 1，常用于**同步/通知**（ISR give，任务 take 唤醒），无优先级继承——所以不应拿它做资源互斥，否则会出现无界的优先级反转。
- 经典用法：生产者-消费者用两个计数信号量（空槽、满槽）加一个互斥量；在 FreeRTOS 中，ISR 通知任务优先用**任务通知**（比二值信号量更快、更省 RAM）。

**English short answer**
A mutex protects a shared resource and has an owner, so the same task must release it, and in FreeRTOS it supports priority inheritance. A counting semaphore tracks a number of available resources, and a binary semaphore is mostly used for signalling, for example from an interrupt to a task. Because a binary semaphore has no inheritance, I do not use it for mutual exclusion.
（中文：互斥量保护资源、有所有权、FreeRTOS 中有优先级继承；计数信号量统计可用资源数；二值信号量主要用于同步通知（如中断唤醒任务），没有继承，所以不用于互斥。）

**追问方向**：递归互斥量；ISR 里能否用互斥量；任务通知。

### Q33 FreeRTOS 里队列、任务通知、事件组、流缓冲怎么选？（IPC in FreeRTOS）
**优先级：★★★**

**答案要点**

| 机制 | 特点 | 典型用途 |
|---|---|---|
| 队列（queue） | 按值拷贝，多发多收，可阻塞等待 | 命令传递、多源消息 |
| 任务通知（task notification） | 每任务内置，最快最省 RAM，只能一对一 | ISR 唤醒任务（如 IMU 数据就绪、DMA 完成） |
| 事件组（event group） | 位标志，多个任务可等多个条件（与/或） | 看门狗心跳、启动同步 |
| 流/消息缓冲 | 字节流，单写单读 | 串口字节流 |
| 互斥量/信号量 | 资源保护/同步 | 共享数据、资源计数 |

- 本项目通常取：传感器反馈用"带时间戳的整块快照"（最新值语义，不用队列排队）；指令用队列（长度小，满时丢旧或报错）；ISR 到任务用任务通知；监督任务用事件组收集各任务心跳。
- 队列传大对象时传**指针/索引**而非整体拷贝，同时明确内存所有权。

**English short answer**
I use a queue to pass messages by copy between tasks, a task notification for the fastest and lightest wake-up from an interrupt to one task, and an event group when a task must wait for several conditions, such as heartbeats from all tasks. For sensor data where only the newest value matters, I use a timestamped snapshot instead of a queue.
（中文：任务间拷贝传消息用队列；从中断唤醒单个任务用最快最省的任务通知；等多个条件（如各任务心跳）用事件组；只关心最新值的传感器数据用带时间戳的快照而非队列。）

**追问方向**：队列满时策略；ISR 版 API；通知的局限（只能一个接收者）。

### Q34 在中断服务程序（ISR）里写并发代码有什么规则？（ISR rules）
**优先级：★★★**

**答案要点**
- ISR 要**短**：只做取数据、清标志、给通知/入队，重活交给任务（"上半部/下半部"思想）。
- 不能阻塞：不能 `take` 互斥量、不能用带延时的 API；FreeRTOS 中只能调 `...FromISR` 版本，并通过 `BaseType_t *pxHigherPriorityTaskWoken` + `portYIELD_FROM_ISR` 在退出时切换到被唤醒的高优先级任务。
- ISR 与任务共享数据：①`volatile` 只能保证编译器不优化，**不保证原子性**；②多字节变量要用原子操作、临界区（关中断极短）或快照 + 序号；③单写单读环形缓冲（SPSC）是 UART/CAN 接收的常用做法（见 Q11）。
- 不要在 ISR 里 `malloc`、`printf`、做长时间浮点运算。
- Cortex-M：中断优先级数值**越小优先级越高**；调用 FreeRTOS API 的中断，其优先级不能高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`（见 Q35）。

**English short answer**
An interrupt handler must be short and never block. I only read the data, clear the flag, and hand the work to a task through a notification or a queue using the FromISR API variants, then yield on exit if a higher-priority task was woken. Shared data needs atomic access or a short critical section, because volatile alone does not make multi-word updates atomic.
（中文：ISR 要短且不阻塞；只取数据、清标志，用 FromISR 版本的通知/队列把工作交给任务，必要时退出时让出；共享数据要原子访问或短临界区，因为 volatile 不保证多字更新的原子性。）

**追问方向**：上半部/下半部；DMA 完成中断；FPU 上下文。

### Q35 Cortex-M 中断优先级与 FreeRTOS 的配合？为什么会"莫名 HardFault"？（NVIC priorities and FreeRTOS）
**优先级：★★**

**答案要点**
- Cortex-M 的 NVIC 优先级寄存器只实现高几位（如 STM32 为 4 位，共 16 级），数值越小越高；分组为"抢占优先级 + 子优先级"，FreeRTOS 要求**全部为抢占优先级**（`NVIC_PriorityGroup_4`）。
- `configMAX_SYSCALL_INTERRUPT_PRIORITY`（BASEPRI 阈值）：优先级**数值大于等于**它的中断可调用 `FromISR` API，临界区通过写 BASEPRI 屏蔽它们；更高优先级（数值更小）的中断不被 FreeRTOS 屏蔽，延迟极低，但**不能调用任何 FreeRTOS API**。
- 典型故障：中断优先级设得比阈值更高却调用了 `FromISR` API，触发断言或随机崩溃；忘了设分组；SysTick/PendSV 必须配置为最低优先级以保证不打断其他 ISR。
- 取法（典型）：电机 CAN/DMA 等需要调用 FreeRTOS API 的中断放在阈值之下，仅做极短硬实时处理的中断可放在阈值之上。

**English short answer**
On Cortex-M a lower number means a higher priority, and FreeRTOS wants all priority bits used for preemption. Interrupts at or below the configured maximum syscall priority may call the FromISR functions, while more urgent interrupts are never masked by the kernel but must not call any FreeRTOS API. A common bug is giving an interrupt a too-urgent priority and then calling a FreeRTOS function from it.
（中文：Cortex-M 数值越小优先级越高，FreeRTOS 要求全部位用作抢占优先级；不高于阈值的中断可调用 FromISR 接口，更高优先级的中断不被内核屏蔽但不能调用 FreeRTOS API；常见错误是中断优先级设得过高却调用了 FreeRTOS 函数。）

**追问方向**：BASEPRI 与 PRIMASK；PendSV；断言捕获。

### Q36 任务栈溢出怎么发现和预防？（Stack overflow in RTOS tasks）
**优先级：★★**

**答案要点**
- 每个任务有独立栈，栈溢出会悄悄覆盖相邻内存，表现为随机 HardFault、变量被改。
- 检测：①`configCHECK_FOR_STACK_OVERFLOW`（方式 1 检查栈指针，方式 2 检查栈尾哨兵字节）+ `vApplicationStackOverflowHook`；②`uxTaskGetStackHighWaterMark()` 读取历史最小剩余栈（单位：字），在压力测试后查看；③MPU 保护栈边界（可选）。
- 预防：避免大局部数组与深递归，大缓冲用静态/全局；`printf`/`sprintf` 会吃很多栈，浮点格式化尤甚；预留 20%～30% 余量；开发阶段栈给大一点，实测高水位后再收紧。
- 栈大小典型取 512～2048 字（教学示例，以实测高水位为准）。

**English short answer**
Stack overflow silently corrupts neighbouring memory, so it shows up as random crashes. I enable FreeRTOS stack overflow checking with a hook, read the stack high-water mark of every task after a stress test, avoid large local arrays and heavy printf use in tasks, and leave a safety margin when sizing the stacks.
（中文：栈溢出会悄悄破坏相邻内存、表现为随机崩溃；开启 FreeRTOS 栈溢出检查与钩子，压力测试后读各任务栈高水位，避免大局部数组和任务内重 printf，并留出余量。）

**追问方向**：MPU；静态任务创建 `xTaskCreateStatic`；HardFault 分析。

### Q37 如何让多线程程序优雅退出？（Graceful shutdown）
**优先级：★★**

**答案要点**
- 不要强杀线程（资源泄漏、锁未释放）。用**停止标志**：`std::atomic<bool>` 或 C++20 `std::stop_token`/`std::jthread`；循环中检查标志，阻塞等待要有**超时**或可被唤醒（条件变量 `notify_all`、往队列放"毒丸"哨兵）。
- 退出顺序：先停生产者，再停消费者；`join` 所有线程；最后释放共享资源。析构里要 `join`，否则 `std::thread` 析构时仍 joinable 会导致 `std::terminate`。
- 机器人特例：收到 `SIGINT/SIGTERM` 时，信号处理函数只置标志，主循环发现后先**使电机失能/输出归零**再退出；Python 里用 `threading.Event`、`asyncio` 的 task 取消。

```cpp
// 教学示例: C++20 jthread
std::jthread t([](std::stop_token st){
    while (!st.stop_requested()) { step(); std::this_thread::sleep_for(std::chrono::milliseconds(2)); }
});  // 析构自动 request_stop + join
```

**English short answer**
I never kill threads. Each loop checks a stop flag, such as an atomic boolean or a stop token, and blocking waits use timeouts or are woken by a notification or a sentinel message. I stop producers first, then consumers, join every thread, and on a robot the signal handler only sets the flag so the main loop can disable the motors before exiting.
（中文：不强杀线程；循环检查停止标志，阻塞等待带超时或可被唤醒；先停生产者再停消费者并 join；机器人上信号处理函数只置标志，主循环先使电机失能再退出。）

**追问方向**：毒丸模式；`pthread_cancel` 的问题；信号安全函数。

### Q38 线程-每连接、线程池、epoll 反应堆（Reactor）怎么选？（Concurrency models for servers）
**优先级：★★**

**答案要点**
- **线程/进程每连接**：编程简单，连接数大时线程栈与切换开销大。
- **线程池 + 阻塞 IO**：限制线程数；一个慢连接占住一个线程。
- **事件驱动（Reactor）**：`epoll`（Linux）单线程监听大量 fd，就绪后回调处理；高并发连接、IO 密集下高效；回调里不能阻塞，计算密集要丢给线程池（"Reactor + 线程池"，每核一个事件循环是常见做法）。
- 协程（asyncio、C++20 coroutine）是在 Reactor 之上的更易写的抽象。
- 本项目的类比：P4 服务端用阻塞 TCP 接收线程 + asyncio 处理 WebSocket；P6 的 M-DDS 设备发现与状态同步属于事件/消息驱动。

**English short answer**
Thread-per-connection is simple but does not scale to many connections. A thread pool bounds resource use, but a slow client can hold a thread. An event-driven reactor built on epoll handles many mostly idle connections on a few threads, as long as callbacks never block and heavy work goes to a worker pool. Coroutines such as asyncio give a more readable form of the same idea.
（中文：每连接一线程简单但扩展差；线程池限制资源但慢连接会占线程；基于 epoll 的 Reactor 用少量线程处理大量空闲连接，前提是回调不阻塞、重活交给工作线程池；协程是更易读的同类抽象。）

**追问方向**：epoll 的水平/边沿触发；惊群；`select/poll` 对比。

### Q39 实时系统里为什么要避免动态内存分配？怎么替代？（Dynamic allocation in real-time code）
**优先级：★★★**

**答案要点**
- 原因：①`malloc/new` 耗时不确定（碎片整理、锁竞争），破坏可预测性；②碎片化导致长期运行后分配失败；③多线程下堆锁可引起优先级反转；④嵌入式 RAM 小，失败难处理。
- 替代：启动期**一次性预分配**（静态数组、`std::array`、`reserve`）；**内存池/对象池**（固定大小块，$O(1)$ 分配释放）；FreeRTOS 用静态创建 API（`xTaskCreateStatic`、`xQueueCreateStatic`）或 `heap_4` 的合并策略（仍应只在初始化阶段分配）。
- C++：避免在控制循环里使用 `std::vector::push_back`（可能重分配）、`std::string` 拼接、`std::function` 捕获大对象；ROS2 里可用预分配消息与 loaned messages（视中间件支持）。
- 控制线程规则（与本章要点一致）：不 malloc、不 printf、不阻塞等待、读快照。

**English short answer**
Allocation time is not deterministic and the heap can fragment, so in a real-time loop I allocate everything up front. I use static buffers, preallocated containers and fixed-size memory pools with constant-time allocation, and on FreeRTOS I create tasks and queues statically. The control loop itself never calls malloc or printf.
（中文：分配耗时不确定且堆会碎片化，所以实时循环里所有内存提前分配；使用静态缓冲、预分配容器和定长内存池，FreeRTOS 里静态创建任务和队列；控制循环内不 malloc、不 printf。）

**追问方向**：placement new；`std::pmr`；碎片率监控。

### Q40 控制周期超时（overrun）时怎么处理？（Handling deadline overruns）
**优先级：★★★**

**答案要点**
- 现象：本周期计算尚未结束，下一个周期的触发点已过。检测：用 `xTaskDelayUntil`/`vTaskDelayUntil` 是否实际延时（新版 API 返回值）、或比较当前 tick 与应唤醒 tick；记录周期耗时最大值和超时次数。
- 策略（按实时等级选）：①**跳过**错过的周期并计数（控制环常见，避免"追赶"造成突发负载）；②**不追赶**：从当前时间重新对齐下一周期；③连续 N 次超时 → 进入安全状态（降速、输出归零、报警）；④软实时可容忍偶发。
- 实现上：用实测 `dt`（而非名义值）做积分/微分，避免周期抖动引入误差；输出限幅与斜率限制；记录超时事件供复盘。
- 根因排查：高优先级任务占用过多、关中断过长、CAN 发送阻塞、日志打印、cache miss；用 GPIO 翻转或 Tracealyzer 看谁抢占了控制任务。

**English short answer**
When a control step overruns, I detect it by comparing the actual wake-up time with the expected one, count it, and do not try to catch up with a burst of extra cycles. I use the measured time step in the controller, and if overruns repeat I move the robot into a safe state. Then I find the cause with a GPIO toggle or a trace tool, usually a long interrupt-disabled section or a blocking call.
（中文：检测实际唤醒时间与预期的偏差并计数，不用突发的多余周期去追赶；控制器使用实测时间步长；连续超时则进入安全状态；再用 GPIO 翻转或追踪工具找原因，通常是关中断过长或阻塞调用。）

**追问方向**：`vTaskDelayUntil` 与 `vTaskDelay`；看门狗联动；用实测 dt 的利弊。

## 本章要点速记
1. 线程安全三招：不共享、不可变、同步；数据竞争在 C/C++ 是 UB。
2. 条件变量必须配谓词循环（虚假唤醒）。
3. 原子只保证单变量；多变量不变量需要锁；CAS 有 ABA。
4. acquire/release 配对形成 happens-before；ARM 弱序，x86 强序。
5. `volatile` ≠ `atomic`。
6. SPSC 环形队列：谁写 head，谁写 tail，写数据先于发布索引。
7. 线程池 = 固定工人 + 任务队列；有界队列提供背压。
8. 优先级反转：用优先级继承的互斥量，更好是避免共享锁。
9. 实时 = 可预测；用 GPIO+示波器或周期计数器测抖动，在满载下测。
10. 控制线程：高优先级、固定周期、不 malloc、不 printf、读快照。
