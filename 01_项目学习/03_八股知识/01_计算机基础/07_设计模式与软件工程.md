## 一、设计原则

### Q1 SOLID 五原则分别是什么？（SOLID principles）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- **S 单一职责**：一个类只有一个变化的理由（电机驱动类不应同时负责日志格式化）。
- **O 开闭**：对扩展开放、对修改关闭——新增一种传感器应通过新增类而不是改旧代码里的 if-else。
- **L 里氏替换**：子类对象必须能替换父类对象而不破坏正确性（子类不得收紧前置条件或放宽后置条件）。
- **I 接口隔离**：不要强迫使用者依赖不需要的方法，拆成小接口。
- **D 依赖倒置**：高层模块依赖抽象而不是具体实现；具体实现通过构造函数/注入提供。
- 落地信号：改一个需求要动很多文件→违反 S/O；子类里抛 `not implemented`→违反 L。

**English short answer**
Single responsibility means one reason to change per class. Open-closed means I extend behavior by adding code rather than editing old code. Liskov substitution says subclasses must be usable wherever the base class is. Interface segregation prefers small focused interfaces, and dependency inversion makes high-level code depend on abstractions. Together they keep code easy to test and extend.

（译：单一职责：一个类只有一个变化原因；开闭：靠新增扩展而非修改；里氏替换：子类可替换父类；接口隔离：小而专的接口；依赖倒置：高层依赖抽象；整体使代码易测易扩展。）

**追问方向**：举一个违反里氏替换的例子（正方形继承矩形）；SOLID 的过度使用有什么风险。

### Q2 什么是依赖注入？为什么有利于测试？（Dependency injection）
**优先级：★★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 对象不自己创建依赖，而是由外部通过构造函数（推荐）、setter 或工厂传入。
- 好处：用接口替换实现——单元测试里注入假的（mock/fake）电机或传感器，无需真实硬件；降低耦合；便于配置不同实现（仿真/真机）。
- 机器人例：控制器依赖 `IMotor` 接口，真机注入 `CanMotor`，仿真注入 `SimMotor`，测试注入 `FakeMotor` 记录收到的命令。
- 反面：在构造函数里直接 `new CanMotor()` 或使用全局单例，导致测试必须有硬件。
- 轻量做法：不需要 DI 框架，手动在 `main` 里组装对象图（composition root）即可。

```cpp
struct IMotor { virtual void setTorque(double) = 0; virtual ~IMotor() = default; };
class Controller {
    IMotor& motor_;
public:
    explicit Controller(IMotor& m) : motor_(m) {}
    void step(double err){ motor_.setTorque(kp * err); }
    double kp = 1.0;
};
```

**English short answer**
Dependency injection means an object receives its collaborators from outside instead of creating them. It lets me replace a real motor with a simulated or fake one in tests, reduces coupling, and makes switching between simulation and hardware a matter of wiring. I usually do it manually through constructors in the main function.

（译：对象从外部接收依赖而不是自己创建；可在测试中用假电机替换真实电机，降低耦合，仿真/真机切换只需改装配；通常在 main 里通过构造函数手动装配。）

**追问方向**：构造注入与 setter 注入取舍；全局单例的问题。

### Q3 组合优于继承是什么意思？（Composition over inheritance）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 继承表达"is-a"，耦合强（子类依赖父类实现细节）、层次易膨胀；组合表达"has-a"，通过持有对象并委托获得功能，可在运行时替换，耦合弱。
- 例：机器人有 `Arm`、`Gripper`，用组合构成 `Manipulator`，而不是 `ArmWithGripper` 继承链。
- 继承的合理场景：真正的多态接口（抽象基类）、框架扩展点；避免用继承只为复用代码。
- 策略模式、装饰器、适配器本质都是用组合替代继承。
- 陷阱：深继承树、菱形继承、基类脆弱问题（fragile base class）。

**English short answer**
Inheritance models is-a and couples a subclass to its parent's details, while composition models has-a and delegates to held objects that can be swapped at run time. I use inheritance mainly for abstract interfaces and use composition for reuse. Strategy, decorator and adapter all rely on composition.

（译：继承是 is-a 且耦合强，组合是 has-a 并通过委托获得功能、可运行时替换；继承主要用于抽象接口，复用靠组合；策略、装饰器、适配器都基于组合。）

**追问方向**：菱形继承与虚继承；基类脆弱问题。

### Q4 高内聚低耦合如何衡量和实现？（Cohesion and coupling）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 内聚：模块内部各部分是否为同一目的服务；耦合：模块间依赖的强度（数据耦合 < 控制耦合 < 公共耦合 < 内容耦合）。
- 指标：一个模块被改动时波及的其他模块数量；循环依赖；包间依赖方向是否一致。
- 实现：明确接口、隐藏实现细节（信息隐藏）、依赖抽象、避免全局状态、按变化频率划分模块（经常变的与稳定的分开）。
- 机器人：感知、规划、控制各为独立节点/模块，通过明确的消息接口通信，而不是互相直接调用内部函数。
- 循环依赖的解决：抽取公共接口到第三个模块，或引入事件/回调反转依赖。

**English short answer**
High cohesion means a module's parts serve one purpose, and low coupling means modules depend on each other through small stable interfaces. I achieve that by hiding implementation details, depending on abstractions, avoiding global state and breaking dependency cycles. In a robot stack, perception, planning and control communicate only through well-defined messages.

（译：高内聚是模块内部目的单一，低耦合是模块间通过小而稳定的接口依赖；做法有信息隐藏、依赖抽象、避免全局状态、打破循环依赖；机器人栈中感知/规划/控制只通过明确消息通信。）

**追问方向**：如何用依赖图发现坏味道；ROS 2 中话题耦合与服务耦合的差别。

### Q5 KISS、DRY、YAGNI 分别指什么？（KISS, DRY, YAGNI）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- KISS：保持简单，能用简单方案就不用复杂方案。
- DRY：不要重复自己——同一知识只在一处表达；但"偶然相似"的代码强行合并会造成错误抽象，需判断是否是同一变化原因。
- YAGNI：你不会需要它——不为想象中的未来需求提前设计；先实现当前需求，需要时再重构。
- 三者冲突时的权衡：过早抽象比重复更昂贵（"三次法则"：第三次重复时再抽象）。
- 机器人原型阶段：先让闭环跑通，再整理参数与接口，而不是一开始搭一个通用框架。

**English short answer**
KISS says keep solutions simple, DRY says express each piece of knowledge once, and YAGNI says do not build features for needs you do not have yet. They can conflict, so I avoid premature abstraction and usually wait for the third repetition before extracting a shared piece.

（译：KISS 保持简单，DRY 同一知识只表达一次，YAGNI 不为未来需求预先设计；三者会冲突，我避免过早抽象，通常第三次重复才抽取。）

**追问方向**：错误的抽象为什么比重复更糟；如何安全地重构重复代码。

### Q6 什么是接口与实现分离？C++ 里怎么做？（Interface/implementation separation）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 头文件暴露稳定的接口，实现细节放源文件；使用方只依赖接口，改实现无需重新编译使用方。
- 手段：抽象基类（纯虚函数）+ 工厂；pimpl（指针指向实现）隐藏私有成员与依赖，稳定 ABI、减少编译依赖；模板/概念在编译期约束接口（零开销，但耦合编译）。
- 代价：虚调用有间接开销，pimpl 多一次堆分配和间接访问；在热路径上可用 CRTP 或模板静态多态。
- P6 口径：传感器/执行器/控制器的抽象基类 + 适配器，让上层只依赖接口。

**English short answer**
I expose a stable interface in the header, such as an abstract base class or a pimpl wrapper, and keep implementation in source files, so clients depend only on the interface and are not rebuilt when internals change. Virtual calls and pimpl add indirection, so on hot paths I may use templates or CRTP for static polymorphism instead.

（译：头文件暴露抽象基类或 pimpl 等稳定接口，实现放源文件，使用方只依赖接口且实现改动无需重编；虚调用与 pimpl 有间接开销，热路径可用模板/CRTP 静态多态。）

**追问方向**：CRTP 的原理；虚函数调用开销大小。

## 二、创建型模式

### Q7 单例模式怎么实现？有什么问题？（Singleton）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 意图：保证一个类只有一个实例并提供全局访问点（日志器、配置管理）。
- C++11 推荐 Meyers 单例：函数内局部静态变量，初始化线程安全（编译器保证），无需手写双重检查锁。
- 问题：全局状态让测试困难、隐藏依赖、多线程共享需额外同步、初始化/销毁顺序问题；多个动态库各有一份可能出现"多个单例"。
- 改进：用依赖注入传入对象，仅在 `main` 里创建一份；真需要全局访问时限制为日志等无状态服务。

```cpp
class Logger {
public:
    static Logger& instance() { static Logger inst; return inst; }
    Logger(const Logger&) = delete; Logger& operator=(const Logger&) = delete;
private:
    Logger() = default;
};
```

**English short answer**
A singleton ensures one instance with a global access point. In C++11 the simplest safe version is a function-local static, whose initialization is thread-safe. The downsides are hidden dependencies, hard testing and shared mutable state, so I prefer to create one object in main and inject it.

（译：单例保证唯一实例并提供全局入口；C++11 用函数内局部静态即可线程安全；缺点是隐藏依赖、难测试、共享可变状态，更推荐在 main 创建一份并注入。）

**追问方向**：双重检查锁定为何曾经出错；Python 里单例怎么写（模块级对象）。

### Q8 工厂方法与抽象工厂的区别？（Factory method vs abstract factory）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 简单工厂/工厂方法：根据参数或子类创建一种产品，把"创建哪个类"的决定集中。例：根据配置字符串 `"can"`/`"sim"` 创建对应的 `IMotor`。
- 抽象工厂：创建**一族**相关产品（传感器、执行器、通信）而不指定具体类。例：`HardwareFactory` 有真机与仿真两个实现，各自产出一套配套对象。
- 好处：调用方不依赖具体类，新增产品只需新增类+注册；坏处：类数量增加。
- 现代 C++ 常用注册表：`map<string, function<unique_ptr<Base>()>>` 实现可扩展工厂；ROS 2 的 `pluginlib` 就是插件工厂。

**English short answer**
A factory method creates one kind of product and hides which concrete class is chosen, for example creating a motor from a config string. An abstract factory creates a whole family of related products, such as a matching set of sensors and actuators for hardware or simulation. In C++ I often keep a registry of creator functions so that new types can be added without editing the factory.

（译：工厂方法创建一种产品并隐藏具体类选择；抽象工厂创建一族相关产品（如真机或仿真的整套传感器执行器）；C++ 常用创建函数注册表，新增类型无需改工厂。）

**追问方向**：pluginlib 的工作方式；静态注册的初始化顺序问题。

### Q9 建造者模式与流式接口适合什么场景？（Builder）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 意图：逐步构造参数很多、可选项很多的复杂对象，避免超长构造函数和"伸缩构造器"。
- 做法：`Builder` 提供链式 setter，最后 `build()` 校验并返回对象；不可变对象尤其适合。
- 例：规划器配置（分辨率、速度上限、代价权重、膨胀半径）、HTTP 请求构造、`CMake` 目标属性。
- 替代：C++20 指定初始化（designated initializers）、Python 关键字参数 + dataclass 已能解决一部分问题。
- 注意在 `build()` 里统一做参数合法性校验，使对象一旦创建即有效。

**English short answer**
A builder constructs a complex object step by step through chained setters and validates everything in a final build call, which avoids constructors with many parameters. I use it for planner or request configurations with many optional fields. Designated initializers in C++20 and keyword arguments in Python cover simple cases.

（译：建造者用链式 setter 逐步构造复杂对象并在 build 中统一校验，避免长参数构造；适合规划器/请求等多可选项配置；C++20 指定初始化与 Python 关键字参数可覆盖简单情形。）

**追问方向**：不可变对象的好处；参数校验放在哪一层。

### Q10 原型模式与对象池分别解决什么？（Prototype and object pool）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 原型：通过**克隆**已有对象创建新对象（`clone()`），适合创建成本高或类型在运行时才知道的场景；注意深拷贝与浅拷贝。
- 对象池：预先创建一批可复用对象，用完归还，避免频繁分配/销毁（线程池、连接池、消息缓冲池）。
- 机器人：高频消息（点云、图像）用池化缓冲避免 `malloc` 抖动；ROS 2 的 loaned messages 本质上是借用预分配消息。
- 池化需防止：忘记归还导致耗尽、归还后继续使用（悬空）、归还时未重置状态。
- 与内存池的区别：对象池复用的是**已构造的对象**。

**English short answer**
The prototype pattern creates new objects by cloning an existing one, which helps when construction is expensive or the type is only known at run time. An object pool preallocates reusable objects to avoid repeated allocation, which I use for image or point cloud buffers. A pool needs discipline to return objects and to reset their state.

（译：原型通过克隆创建对象；对象池预分配可复用对象避免频繁分配，用于图像/点云缓冲；池化要保证归还并重置状态。）

**追问方向**：RAII 句柄如何自动归还；loaned message 的约束。

## 三、结构型模式

### Q11 适配器模式的意图与机器人中的应用？（Adapter）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 意图：把一个类的接口转换成客户期望的另一个接口，让不兼容的类协同工作。
- 结构：客户依赖目标接口 `Target`；`Adapter` 实现 `Target` 并持有被适配对象 `Adaptee`，把调用转发并转换参数/单位/数据格式。
- 机器人：不同厂商的电机驱动协议各异，写一个 `IMotor` 接口 + 每种电机一个适配器；这正是 P6 统一能力模型"抽象接口 + 适配器"的做法，运动控制代码因此可跨硬件复用。
- 对象适配器（组合）优于类适配器（多重继承）。
- 与外观模式区别：适配器改接口以匹配期望；外观简化一组接口。

**English short answer**
An adapter converts one interface into the one a client expects. The adapter implements the target interface and wraps the incompatible class, translating calls and units. In my P6 platform work, each hardware type gets an adapter behind a common interface, so the control code stays hardware-independent. It differs from a facade, which simplifies a subsystem rather than matching an interface.

（译：适配器把一个接口转换成客户期望的接口，实现目标接口并包装不兼容类；P6 中每种硬件一个适配器挂在统一接口后，控制代码与硬件无关；与外观模式不同，外观是简化而非匹配接口。）

**追问方向**：单位换算与坐标系约定放在适配器还是上层；适配器的测试方法。

### Q12 外观（Facade）、代理（Proxy）、装饰器（Decorator）如何区分？（Facade vs Proxy vs Decorator）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 外观：为复杂子系统提供**简化的统一入口**（`Robot::pickAndPlace()` 内部协调感知、规划、控制）。
- 代理：持有同接口的**替身**控制对Real对象的访问——远程代理（RPC 存根）、虚代理（延迟加载）、保护代理（权限检查）、缓存代理。
- 装饰器：在不改类的前提下**动态叠加行为**，同接口，可层层包裹（给电机加限幅、加日志、加重试）。
- 区分关键：外观改变接口粒度；代理控制访问；装饰器增加职责。
- C++/Python：Python 装饰器语法、C++ 包装类；中间件中的拦截器（interceptor）类似装饰器。

**English short answer**
A facade offers one simplified entry point to a complex subsystem. A proxy stands in for an object with the same interface to control access, for example lazy loading, remote calls or permission checks. A decorator wraps an object to add behavior dynamically, like adding saturation or logging to a motor interface. The difference is simplify, control access, and add responsibility.

（译：外观为复杂子系统提供简化入口；代理以同接口替身控制访问（延迟加载、远程调用、权限）；装饰器动态叠加行为（如给电机接口加限幅/日志）；区别在于简化、控访问、加职责。）

**追问方向**：用装饰器给控制器加安全限幅的例子；RPC 存根属于哪种。

### Q13 组合模式（Composite）有什么用？（Composite）
**优先级：★★** · 对应基础知识：[行为树与任务规划_PDDL_有限状态机](../../02_基础知识/08_规划与导航/08_行为树与任务规划_PDDL_有限状态机.md)

**答案要点**
- 把对象组织成树形结构，使客户对**单个对象和组合对象一视同仁**（统一接口 `tick()` / `execute()`）。
- 机器人典型：**行为树**（节点分叶子动作与组合节点 Sequence/Selector）、场景图/URDF 链接树、UI 控件树、文件系统。
- 结构：`Component` 接口，`Leaf` 实现，`Composite` 持有子 `Component` 列表并转发。
- 注意：对叶子调用 `add/remove` 的语义；循环引用；遍历顺序与副作用。

**English short answer**
The composite pattern arranges objects in a tree where leaves and groups share one interface, so clients treat them uniformly. Behavior trees are a good example: sequence and selector nodes contain children, and action nodes are leaves, all with the same tick interface. URDF link trees and scene graphs follow the same idea.

（译：组合模式用树结构让叶子与组合对象共享同一接口；行为树（Sequence/Selector 含子节点、动作为叶子）是典型例子，URDF 链接树与场景图同理。）

**追问方向**：行为树 tick 的返回值语义（成功/失败/运行中）；如何避免树遍历中的副作用。

### Q14 桥接与策略模式的区别？（Bridge vs Strategy）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 策略：把一族可互换的**算法**封装为独立类，运行时选择（局部规划器的代价函数、不同滤波器、PID 与 LQR 切换）。关注"做事的方法"。
- 桥接：把**抽象与实现两个独立变化的维度**解耦（形状 × 渲染 API；机器人行为 × 硬件平台），两者各自继承扩展，组合时用桥相连。
- 结构上相似（都是持有接口指针），目的不同：策略解决算法选择，桥接解决避免类爆炸。
- C++ 里策略可用模板参数（编译期，零开销）或 `std::function`（运行期）。

**English short answer**
Strategy encapsulates interchangeable algorithms behind an interface so one can be chosen at run time, like swapping a PID controller for an LQR one. Bridge separates two independent dimensions of variation, an abstraction and its implementation, so they can evolve separately and avoid a class explosion. The structures look alike but the intents differ.

（译：策略封装可互换算法、运行时选择（如 PID↔LQR）；桥接把抽象与实现两个独立变化维度解耦以避免类爆炸；结构相似但意图不同。）

**追问方向**：模板策略与虚函数策略的取舍；策略切换的无扰动问题。

### Q15 享元（Flyweight）与缓存的共同点？（Flyweight）
**优先级：★**

**答案要点**
- 享元：共享大量相同的细粒度对象的**不变内部状态**（intrinsic），把变化部分（extrinsic）由外部传入，节省内存。
- 例：字符字形、地图中重复的瓦片纹理、点云中共享的相机内参对象、字符串驻留（string interning）。
- 与缓存的区别：享元强调对象共享以省内存；缓存强调避免重复计算以省时间。
- 实现：工厂 + 哈希表按键返回共享实例；注意线程安全与不可变性（共享对象必须不可变）。

**English short answer**
Flyweight shares the immutable intrinsic part of many similar objects and passes the varying part from outside, which saves memory. String interning is a familiar example. It differs from a cache, which saves recomputation. Shared objects must be immutable and the lookup must be thread-safe.

（译：享元共享大量相似对象的不变部分、外部传入可变部分以省内存，字符串驻留是例子；与缓存不同（缓存省重复计算）；共享对象须不可变且查找线程安全。）

**追问方向**：享元与单例的关系；不可变对象的线程安全。

## 四、行为型模式

### Q16 观察者模式与发布订阅的区别？（Observer vs Pub/Sub）
**优先级：★★★** · 对应基础知识：[ROS2_Humble核心概念与ROS1对比](../../02_基础知识/12_机器人软件/04_ROS2_Humble核心概念与ROS1对比.md)

**答案要点**
- 观察者：主题（Subject）直接持有观察者列表，状态变化时逐个回调；两者在同进程、彼此知道对方接口，耦合较直接。
- 发布订阅：通过**消息代理/总线**中转，发布者与订阅者互不认识，按主题（topic）路由，可跨进程跨机器，可异步解耦。ROS 2 的话题、DDS、MQTT 都是发布订阅。
- 共同注意：回调中抛异常、回调里取消订阅造成迭代器失效、悬空回调（对象已销毁，可用 `weak_ptr`）、回调耗时阻塞发布者、线程安全。
- 选择：进程内简单事件用观察者/信号槽；系统级解耦用发布订阅，并设计 QoS（可靠性、历史深度）。

**English short answer**
In the observer pattern a subject calls registered observers directly, usually in one process. In publish-subscribe a broker or middleware routes messages by topic, so publishers and subscribers do not know each other and can be in different processes. ROS 2 topics are publish-subscribe. In both I watch for dangling callbacks, slow callbacks and thread safety.

（译：观察者由主题直接回调注册的观察者，通常同进程；发布订阅经中间件按主题路由，双方互不相识并可跨进程（ROS 2 话题）；两者都要注意悬空回调、慢回调和线程安全。）

**追问方向**：回调中取消订阅怎么处理；QoS 对订阅的影响。

### Q17 状态模式与有限状态机怎么实现？（State pattern and FSM）
**优先级：★★★** · 对应基础知识：[行为树与任务规划_PDDL_有限状态机](../../02_基础知识/08_规划与导航/08_行为树与任务规划_PDDL_有限状态机.md)

**答案要点**
- 有限状态机：状态 + 事件 + 转移 + 动作；用于机器人模式管理（待机/使能/运行/故障）。
- 实现一：`enum` + `switch`（简单、显式，状态多时变长）；实现二：状态模式（每个状态一个类，实现 `handle(event)`，转移时切换对象）；实现三：转移表（表驱动，数据化、易校验、易生成图）。
- 要点：明确**非法事件**的处理、入口/出口动作、故障状态的优先级（急停事件可从任意状态触发）、转移的原子性。
- 层次状态机（HSM）、状态图（statechart）解决状态爆炸；行为树在复杂决策上更模块化。
- 测试：对转移表做全覆盖，检查不可达状态与死状态。

**English short answer**
A finite state machine has states, events, transitions and actions. I implement it with an enum and switch for small cases, a table-driven design for easy verification, or the state pattern with one class per state. I define what happens on illegal events, make fault or emergency-stop transitions available from every state, and test transitions systematically.

（译：FSM 由状态、事件、转移、动作构成，可用 enum+switch、表驱动或状态模式实现；需定义非法事件处理，故障/急停可从任意状态触发，并系统测试转移。）

**追问方向**：层次状态机；FSM 与行为树的取舍。

### Q18 命令模式与撤销/重做、任务队列？（Command）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 把请求封装成对象（`Command`，含 `execute()`，可选 `undo()`），可排队、记录、延迟执行、撤销。
- 机器人：遥操作指令队列、动作序列回放、宏命令（一连串关节目标）、事件溯源式日志、ROS 2 的 Action 目标本质上是可取消的命令。
- 好处：调用者与执行者解耦；便于审计与重放（飞行记录仪）。
- 与安全：命令要带过期时间与序号，执行前校验，过期/重复命令丢弃，防止延迟后的动作造成危险。

**English short answer**
The command pattern turns a request into an object that can be queued, logged, delayed, canceled or undone. In robotics it appears as teleoperation command queues, action sequences and ROS 2 actions. Because queued commands can be stale, I attach timestamps and sequence numbers and discard expired ones before execution.

（译：命令模式把请求封装成对象，可排队、记录、延迟、取消或撤销；机器人中体现为遥操作指令队列、动作序列、ROS 2 Action；排队命令可能过期，故加时间戳与序号并丢弃过期命令。）

**追问方向**：如何设计可撤销的机械臂动作；命令的幂等性。

### Q19 责任链与中间件拦截器模式？（Chain of responsibility）
**优先级：★★**

**答案要点**
- 把处理者串成链，请求沿链传递，每个处理者决定处理、修改或转发。典型：HTTP 中间件（鉴权→限流→日志→业务）、异常处理链、过滤器链。
- 机器人：指令安全过滤链——速度限幅→加速度限幅→碰撞检查→急停检查→下发；一环否决则整条拒绝。P6 的"安全执行链"可按此思路理解（具体口径以 CV 与项目文档为准）。
- 好处：新增检查只需插入一环，顺序可配置；坏处：调试链路较长，需要每环记录原因。
- 实现要点：链上每环返回"通过/修改/拒绝+原因"，便于日志与回放。

**English short answer**
A chain of responsibility passes a request through a sequence of handlers, each of which can handle, modify or forward it. Web middleware works this way, and so does a command safety filter chain in a robot: limit speed, limit acceleration, check collisions, check the emergency stop, then send. A rejection should record its reason for debugging.

（译：责任链让请求沿处理者链传递，每环可处理、修改或转发；Web 中间件和机器人指令安全过滤链（限速、限加速度、碰撞检查、急停检查、下发）都是此模式；拒绝时记录原因便于调试。）

**追问方向**：链的顺序如何影响结果；某一环超时怎么办。

### Q20 模板方法与钩子函数？（Template method and hooks）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 基类定义算法**骨架**（固定步骤顺序），把可变步骤留给子类重写（虚函数）；可选步骤做成钩子（默认空实现）。
- 例：控制器基类 `update()` 固定为"读传感器→计算→限幅→写执行器"，子类只实现"计算"；ROS 2 生命周期节点的 `on_configure/on_activate` 钩子。
- 非虚接口（NVI）习惯：公共接口非虚，内部调用私有虚函数，便于在基类统一做前后检查。
- 与策略的区别：模板方法用继承在编译期定骨架，策略用组合在运行期换算法。

**English short answer**
The template method defines the skeleton of an algorithm in a base class and lets subclasses override specific steps through virtual functions or hooks. A controller base class can fix the loop of read, compute, saturate and write while subclasses implement only compute. Lifecycle node callbacks in ROS 2 are the same idea. Unlike strategy, it uses inheritance rather than composition.

（译：模板方法在基类定义算法骨架，子类通过虚函数/钩子重写特定步骤；控制器基类固定"读→算→限幅→写"，子类只实现"算"；ROS 2 生命周期回调同理；与策略不同，它用继承而非组合。）

**追问方向**：NVI 习惯的优点；在构造函数里调用虚函数的陷阱。

### Q21 访问者与迭代器模式的用途？（Visitor and iterator）
**优先级：★**

**答案要点**
- 迭代器：提供不暴露内部结构的顺序访问方式（STL 迭代器、Python 的 `__iter__`/生成器）。
- 访问者：在不修改元素类的前提下，为一个**稳定的类层次**添加新操作（双分派）。适合编译器 AST、场景图、URDF 遍历做导出/碰撞检查/统计。
- 访问者的代价：新增元素类型需改所有访问者；现代 C++ 可用 `std::variant` + `std::visit` 更简洁地实现。
- 迭代器失效规则是 STL 高频考点（`vector` 扩容后全部失效）。

**English short answer**
An iterator gives sequential access to a collection without exposing its structure, as in STL iterators or Python generators. A visitor adds new operations to a stable class hierarchy without modifying the classes, using double dispatch. In modern C++ I often use std::variant with std::visit instead of a classic visitor.

（译：迭代器不暴露内部结构地顺序访问集合；访问者用双分派给稳定类层次添加新操作；现代 C++ 常用 std::variant 与 std::visit 取代传统访问者。）

**追问方向**：`variant` 与继承多态对比；迭代器失效的几种情形。

### Q22 中介者与事件总线有什么区别？（Mediator vs event bus）
**优先级：★**

**答案要点**
- 中介者：让多个对象不直接互相引用，而是通过一个中介对象通信，把网状依赖变成星形；中介者知道所有参与者，可能膨胀成"上帝类"。
- 事件总线：参与者只发布/订阅事件，不知道对方；更松耦合，但控制流不显式，调试困难。
- 机器人：高层任务管理器协调感知/规划/控制属于中介者；ROS 话题是事件总线。
- 选择：协作逻辑复杂、需集中控制→中介者；松耦合、扩展性优先→事件总线；必须保证事件顺序与可追溯性（日志）。

**English short answer**
A mediator centralizes communication between components so they do not reference each other, turning a web of dependencies into a star, but it can grow into a god class. An event bus decouples further because participants only publish and subscribe, at the price of a less explicit control flow. A task manager coordinating modules is a mediator, while ROS topics form an event bus.

（译：中介者集中通信使组件互不引用，但可能变成上帝类；事件总线靠发布/订阅进一步解耦，控制流不显式；任务管理器是中介者，ROS 话题是事件总线。）

**追问方向**：如何避免上帝类；事件风暴与回放问题。

### Q23 空对象、备忘录等其他常见模式？（Null object and memento）
**优先级：★**

**答案要点**
- 空对象：提供一个什么都不做的默认实现代替 `nullptr` 检查（`NullLogger`、`NoopController`），减少分支；仿真中的假硬件就是其变体。
- 备忘录：保存对象内部状态的快照以便恢复（不暴露细节）。机器人：参数快照/回滚、状态机检查点、仿真重置到某状态。
- 其他：对象池（见上）、依赖注入（原则）、RAII（C++ 惯用法，资源管理的"模式"）。
- 提示：面试不要罗列 23 个模式，选与自己项目有关的 5–6 个讲透。

**English short answer**
A null object is a do-nothing implementation used instead of a null pointer, so callers need no checks. A memento stores a snapshot of an object's state so it can be restored later, which I use for parameter rollback and simulation resets. In interviews I focus on the few patterns that match my projects and explain them well.

（译：空对象是不做事的默认实现，省去空指针检查；备忘录保存状态快照以便恢复，用于参数回滚与仿真重置；面试时挑与项目相关的几个模式讲透。）

**追问方向**：参数热更新失败时的回滚设计；仿真状态快照的粒度。

## 五、架构与并发模式

### Q24 分层架构的优缺点？机器人软件怎么分层？（Layered architecture）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 典型分层：硬件驱动层（HAL）→ 设备抽象层 → 控制/算法层 → 任务/决策层 → 应用/接口层。上层只依赖下层，下层不知道上层。
- 优点：职责清晰、可替换下层（仿真代替硬件）、便于独立测试；缺点：层层传递带来延迟与样板代码，跨层优化困难。
- 实时约束：控制环路层要有确定性，决策层可非实时；两者之间用有界队列/最新值缓冲隔离，避免慢层拖慢快层。
- 常见反模式：层间跳跃调用、下层回调上层造成循环依赖、"万能工具类"。

**English short answer**
A layered design stacks hardware drivers, device abstractions, control algorithms, task logic and application interfaces, with each layer depending only on the one below. It makes parts replaceable and testable, for example swapping hardware for a simulator, but adds overhead and can make cross-layer optimization harder. Between real-time and non-real-time layers I use bounded queues so slow layers cannot block fast ones.

（译：分层从驱动、设备抽象、控制算法、任务逻辑到应用接口，上层只依赖下层；便于替换（仿真代替硬件）与测试，但有开销；实时与非实时层间用有界队列隔离。）

**追问方向**：如何处理需要跨层的紧耦合优化；层与节点的对应关系。

### Q25 事件驱动、轮询与回调的取舍？（Event-driven vs polling）
**优先级：★★★** · 对应基础知识：[FreeRTOS实时系统](../../02_基础知识/11_嵌入式与通信/02_FreeRTOS实时系统.md)

**答案要点**
- 轮询：循环检查状态，简单、延迟由轮询周期决定，浪费 CPU 和功耗。
- 中断/事件驱动：事件发生才处理，响应快、省电，但处理上下文受限（ISR 要短），竞态更多。
- 回调：事件到达时调用注册函数，需注意回调线程、重入与生命周期。
- 混合：ISR 只置标志或入队，主循环/任务轮询队列（"下半部"思想）；周期性控制环用定时器触发。
- 判断标准：事件稀疏且要求低延迟→中断；事件频繁且有固定周期→定时轮询。

**English short answer**
Polling repeatedly checks a condition, which is simple but wastes CPU and has latency up to the polling period. Interrupts or events react only when something happens, which is faster and more power-efficient but harder to get right. A common hybrid has the ISR record the event in a queue and a task process it, keeping interrupt handlers short.

（译：轮询简单但耗 CPU，延迟取决于周期；中断/事件驱动响应快省电但更难写对；常用混合：ISR 入队、任务处理，保持中断短。）

**追问方向**：回调在哪个线程执行；定时器触发与轮询的抖动差异。

### Q26 Reactor 与 Proactor 模型？（Reactor vs Proactor）
**优先级：★★** · 对应基础知识：[计算机网络_TCP_UDP_以太网_时延](../../02_基础知识/14_计算机基础/03_计算机网络_TCP_UDP_以太网_时延.md)

**答案要点**
- Reactor：事件循环等待**就绪**事件（`epoll`），就绪后由应用自己做读写；同步非阻塞 IO。Nginx、Redis、Node.js 属此类，ROS 2 executor 也类似"等待就绪回调"的思想。
- Proactor：应用发起**异步操作**，由系统完成后通知完成事件（Windows IOCP、Linux io_uring 更接近）。
- 单线程事件循环适合 IO 密集；CPU 密集需交给线程池，避免阻塞循环。
- 实现要点：非阻塞 socket、边缘触发/水平触发的处理（ET 必须读到 EAGAIN）、缓冲区管理。

**English short answer**
In the Reactor model the event loop waits for readiness events, such as from epoll, and then the application performs the non-blocking read or write. In the Proactor model the application starts an asynchronous operation and is notified on completion, as with IOCP or io_uring. Single-threaded event loops suit IO-bound work, and CPU-heavy tasks go to a thread pool.

（译：Reactor 等待就绪事件后由应用自己读写；Proactor 发起异步操作、完成后通知；单线程事件循环适合 IO 密集，CPU 密集交线程池。）

**追问方向**：epoll 的 ET 与 LT；ROS 2 executor 的调度。

### Q27 生产者–消费者与背压（backpressure）怎么设计？（Producer-consumer and backpressure）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 用有界队列解耦速度不同的两端；队满时的策略必须明确：阻塞生产者、丢弃最新、丢弃最旧、合并（只保留最新值）。
- 传感器流（相机、激光）通常"丢旧保新"，因为过时数据没价值；命令流不能随便丢，需要确认与重传。
- 无界队列会让内存无限增长、延迟越来越大（"延迟雪崩"）。
- 监控：队列长度、丢弃计数、端到端延迟，作为健康指标。
- ROS 2 的 QoS：`history=KEEP_LAST` + `depth`、`reliability`、`durability` 对应这些策略。

**English short answer**
A bounded queue decouples a fast producer from a slow consumer, and I must decide what happens when it is full: block, drop the newest, drop the oldest, or keep only the latest value. For sensor streams I drop the oldest because stale data is useless; commands must not be dropped silently. Unbounded queues cause growing latency and memory, so I monitor queue depth and drops.

（译：有界队列解耦快慢两端，需明确队满策略：阻塞、丢最新、丢最旧或只保留最新；传感器流丢旧保新，命令不能静默丢失；无界队列导致延迟与内存增长，要监控队列深度与丢弃数。）

**追问方向**：ROS 2 QoS 如何映射这些策略；延迟雪崩的排查。

### Q28 微服务与单体架构对比？机器人系统怎么选？（Monolith vs microservices）
**优先级：★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 单体：一个进程内模块通过函数调用交互，延迟低、部署简单、调试方便；但耦合高、局部更新困难、一处崩溃全部挂。
- 微服务/多进程：独立部署、故障隔离、可用不同语言；代价是通信开销、分布式一致性、运维复杂。
- 机器人通常是"多进程节点 + 中间件"：ROS 2 节点天然是进程级小服务；实时控制回路常放在同一进程或同一 MCU 内以保证确定性，高层功能分成节点。
- 取舍指标：延迟预算、故障隔离需求、团队规模、更新频率。
- 进程内组件化（composable nodes）可在隔离与零拷贝之间折中。

**English short answer**
A monolith keeps modules in one process with fast calls and simple deployment, but a bug can take everything down. Multiple processes or services give isolation and independent updates at the cost of communication overhead and operational complexity. Robot stacks usually run nodes as separate processes while keeping tight control loops in a single deterministic context, and composable nodes offer a middle ground.

（译：单体延迟低、部署简单但耦合高；多进程/服务隔离好、可独立更新，但有通信与运维成本；机器人通常用多进程节点，紧耦合控制环放在同一确定性上下文，composable nodes 是折中。）

**追问方向**：延迟预算如何分配；故障隔离粒度的选择。

### Q29 插件化架构如何实现？（Plugin architecture）
**优先级：★★** · 对应基础知识：[ROS2_Humble实战_launch_参数_生命周期_组件](../../02_基础知识/12_机器人软件/08_ROS2_Humble实战_launch_参数_生命周期_组件.md)

**答案要点**
- 核心定义稳定接口，插件实现接口并在运行时通过配置加载（动态库 `dlopen` 或脚本模块）。
- ROS 2：`pluginlib` + `plugin description xml`，Nav2 的规划器、控制器、行为树节点都是插件；改配置即可切换算法，不用重编核心。
- 要点：接口稳定与版本化、ABI 兼容、插件异常隔离、生命周期（加载/初始化/卸载）、依赖声明。
- 风险：插件崩溃拖垮宿主→考虑进程外插件；安全→只加载可信签名的插件。

**English short answer**
A plugin architecture defines a stable interface in the core and loads implementations at run time from shared libraries chosen in configuration. Nav2 does this with pluginlib for planners, controllers and behavior tree nodes. I need stable, versioned interfaces and ABI compatibility, and for safety I consider loading only trusted plugins and isolating crashes.

（译：核心定义稳定接口，运行时按配置从动态库加载实现；Nav2 用 pluginlib 加载规划器/控制器/行为树节点；需稳定版本化接口与 ABI 兼容，安全上只加载可信插件并隔离崩溃。）

**追问方向**：`dlopen` 加载失败如何处理；Nav2 切换控制器的流程。

### Q30 配置管理：硬编码、配置文件与参数服务器？（Configuration management）
**优先级：★★★** · 对应基础知识：[ROS2_Humble实战_launch_参数_生命周期_组件](../../02_基础知识/12_机器人软件/08_ROS2_Humble实战_launch_参数_生命周期_组件.md)

**答案要点**
- 避免魔法数字；参数分类：编译期常量、启动参数（YAML）、运行时可调参数（动态参数）、标定数据（版本化）。
- ROS 2 参数：节点声明参数（带类型、范围、描述）、YAML 加载、`ros2 param set` 运行时修改、参数回调校验。
- 原则：配置有默认值与合法性校验；启动时打印生效配置；配置与代码版本一同记录（可复现）；敏感信息不入仓库。
- 热更新风险：控制增益突变导致冲击，需无扰动切换或限幅斜坡；多参数的原子性更新。
- 分环境配置：仿真/真机 launch 与参数文件分离。

**English short answer**
I keep tunable values out of the code: constants at compile time, startup parameters in YAML, and runtime-adjustable parameters with declared types and ranges. I validate values, log the effective configuration at startup and version it with the code. For live changes such as control gains I ramp or switch bumplessly to avoid sudden jumps.

（译：可调值不写死在代码里：编译期常量、YAML 启动参数、带类型范围的运行时参数；做校验、启动时打印生效配置并与代码一同版本化；在线改增益要斜坡或无扰动切换。）

**追问方向**：参数回调里怎么拒绝非法值；标定参数如何版本管理。

### Q31 幂等性与重试：为什么对机器人命令重要？（Idempotency and retries）
**优先级：★★** · 对应基础知识：[可靠性与故障诊断_FMEA_看门狗_降级策略](../../02_基础知识/13_系统工程与安全/03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)

**答案要点**
- 幂等：同一操作执行多次与执行一次效果相同（设置目标位置幂等，"前进 1 米"不幂等）。
- 网络不可靠会导致重传或重复投递；非幂等命令重复执行会造成危险（重复上料、多次开火）。
- 做法：命令带唯一 ID/序号，接收方去重；使用绝对量代替增量；确认机制（ack）+ 超时重试（指数退避）；状态机校验"此时是否允许该命令"。
- 重试要有上限，失败后进入安全状态，而不是无限重试。

**English short answer**
An idempotent operation has the same effect when applied once or many times; setting a target position is idempotent, while move forward one meter is not. Because networks duplicate or retry messages, I give commands unique IDs for de-duplication, prefer absolute targets over increments, and use acknowledgements with bounded retries and backoff, falling back to a safe state on failure.

（译：幂等指执行多次与一次效果相同；网络会重传，故命令带唯一 ID 去重、优先使用绝对量、使用确认+有限次退避重试，失败后进入安全状态。）

**追问方向**：指数退避的参数；分布式场景下的"恰好一次"。

## 六、重构与代码质量

### Q32 什么是代码坏味道？如何重构？（Code smells and refactoring）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 常见坏味道：过长函数/过大类、重复代码、过长参数列表、霸占数据、霰弹式修改（改一处需改多处）、依恋情结（方法过度使用别的类的数据）、魔法数字、注释掩盖糟糕代码。
- 重构：在**不改变外部行为**的前提下改善内部结构。常用手法：提取函数、内联、引入参数对象、以多态取代条件表达式、搬移方法。
- 安全重构的前提：有自动化测试保护；小步提交；每步运行测试。
- 没有测试时先补特征测试（characterization test），固定现有行为再重构。
- 控制类代码重构要特别小心：数值行为不能变，用回放数据比对重构前后输出。

**English short answer**
Code smells are structural signs of trouble, like long functions, duplication, long parameter lists and magic numbers. Refactoring improves the structure without changing behavior, using small steps such as extract function or replace conditional with polymorphism, protected by automated tests. With legacy control code I first record outputs on replay data and compare them after each change.

（译：坏味道是结构问题的信号（过长函数、重复、长参数、魔法数字）；重构在不改变行为下改善结构，小步进行并由自动化测试保护；遗留控制代码先录制回放输出，改动后比对。）

**追问方向**：特征测试如何写；重构与性能优化的关系。

### Q33 如何做有效的代码评审（Code review）？（Code review）
**优先级：★★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 目的：发现缺陷、统一风格、传播知识、保证可维护性；不是找茬。
- 评审者看：正确性与边界、并发与资源释放、错误处理、命名与可读性、测试是否覆盖、接口变更是否兼容、性能热点、安全问题。
- 提交者：小而聚焦的变更（建议几百行以内）、清晰的描述（为什么改）、附测试与运行结果、先自查。
- 流程：CI 先通过（编译、格式、静态检查、测试）再人工评审；用 checklist；对有分歧的点以数据/文档裁决。
- 软技能：对事不对人，用提问代替命令（"这里如果为空会怎样？"）。

**English short answer**
Code review catches defects, keeps a consistent style and spreads knowledge. Authors submit small focused changes with a clear description and tests, and CI runs first so reviewers can concentrate on correctness, concurrency, error handling, readability and interface compatibility. I give feedback on the code, not the person, and phrase concerns as questions.

（译：评审发现缺陷、统一风格、传播知识；作者提交小而聚焦、描述清晰且带测试的变更，CI 先过，评审者关注正确性、并发、错误处理、可读性与接口兼容；对事不对人，用提问表达疑虑。）

**追问方向**：你评审时最先看什么；如何处理评审意见分歧。

### Q34 技术债务是什么？如何管理？（Technical debt）
**优先级：★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 为了短期交付而采用次优方案，未来需要付出"利息"（修改更慢、bug 更多）。比赛/项目赶进度时常见。
- 类型：有意的（先上线后重构）与无意的（经验不足）；代码债、架构债、测试债、文档债。
- 管理：显式记录（TODO 带编号/issue）、定期偿还（每个迭代预留重构时间）、在改动某区域时顺手改善（童子军规则）、用指标（复杂度、测试覆盖率、缺陷率）作为依据。
- 沟通：向非技术方说明风险，用"不还的代价"而不是抽象的"代码不优雅"。

**English short answer**
Technical debt is the cost of choosing a quick, suboptimal solution now, which slows later changes like interest. I manage it by recording it explicitly in the tracker, paying it down regularly, improving the code I touch, and using metrics such as test coverage and defect rate to argue for the time. Under deadline pressure, taking on debt consciously is fine as long as it is tracked.

（译：技术债务是为短期交付选择次优方案、之后需付"利息"；显式记录、定期偿还、顺手改善所改代码、用覆盖率/缺陷率等指标争取时间；赶进度时有意识地借债可以，但要登记。）

**追问方向**：比赛项目的典型债务；如何判断何时必须偿还。

### Q35 命名、注释与文档的最佳实践？（Naming, comments, documentation）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 命名：表达意图、带单位和坐标系（`speed_mps`、`yaw_rad`、`pose_in_map`），避免缩写歧义；布尔值用 `is_/has_`；一致的风格（Google/ROS 风格指南）。
- 注释：解释"为什么"（设计决策、物理含义、公式出处）而非"做什么"；过期注释比没有注释更糟；复杂算法在头部写推导链接。
- 文档：README（构建/运行/依赖）、接口文档（Doxygen/Sphinx）、架构图、变更日志、故障排查手册；与代码一起版本管理。
- 单位混淆是机器人常见 bug（度/弧度、毫米/米、rpm/rad/s），类型系统（强类型单位库）或命名可以预防。

**English short answer**
I name things by intent and include units and frames, like speed in meters per second or a pose in the map frame, because unit confusion is a classic robotics bug. Comments explain why rather than what, and documentation includes a README, interface docs and troubleshooting notes versioned with the code.

（译：命名表达意图并带单位与坐标系，因为单位混淆是机器人经典 bug；注释解释"为什么"；文档含 README、接口文档、排障说明，与代码一同版本管理。）

**追问方向**：强类型单位库（如 `units`）的利弊；一次因单位错误引发的故障案例。

### Q36 静态分析与代码规范工具有哪些？（Static analysis and linters）
**优先级：★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- C/C++：编译器警告（`-Wall -Wextra -Werror`）、`clang-tidy`、`cppcheck`、`clang-format`；Python：`ruff/flake8`、`black`、`mypy`；ROS 2 提供 `ament_lint`（cpplint、uncrustify、flake8 等）。
- 作用：在运行前发现未初始化变量、可疑转换、资源泄漏、风格违规；统一格式减少评审噪声。
- 嵌入式安全标准：MISRA C 规则集（汽车/功能安全常用，具体条款以官方文档为准，未核对）。
- 接入 CI 作为门禁；对误报用注释抑制并写明理由。

**English short answer**
Static analysis finds problems before running the code. For C++ I use strict compiler warnings, clang-tidy, cppcheck and clang-format; for Python I use a linter, a formatter and type checking with mypy. ROS 2 packages can run ament lint checks. I wire them into CI as gates and document any suppressions.

（译：静态分析在运行前发现问题；C++ 用严格警告、clang-tidy、cppcheck、clang-format，Python 用 linter、formatter 和 mypy；ROS 2 有 ament lint；接入 CI 做门禁并为抑制项写明理由。）

**追问方向**：MISRA 的作用；误报的处理流程。

### Q37 圈复杂度是什么？为什么要控制？（Cyclomatic complexity）
**优先级：★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 圈复杂度 = 判定节点数 + 1（等价于独立路径数）；衡量需要多少测试用例才能覆盖所有分支。
- 经验阈值：单个函数 10 左右以下较易维护（具体阈值依团队规范，未核对）。
- 过高意味着难读、难测、易出错；降低手段：提前返回（守卫子句）、拆分函数、用表驱动替代 if-else 链、多态替代分支。
- 对状态机/协议解析类代码，表驱动能显著降复杂度。

**English short answer**
Cyclomatic complexity counts independent paths through a function, roughly the number of decision points plus one, and tells how many tests are needed to cover all branches. High values mean code that is hard to read and test. I reduce it with early returns, smaller functions, table-driven logic and polymorphism.

（译：圈复杂度是函数中独立路径数（判定点数+1），反映覆盖所有分支所需测试数；过高则难读难测；用提前返回、拆函数、表驱动、多态来降低。）

**追问方向**：圈复杂度与测试覆盖率的关系；认知复杂度的区别。

### Q38 持续集成（CI）与持续交付（CD）包含什么？（CI/CD）
**优先级：★★★** · 对应基础知识：[ROS2测试与CI_launch_testing_gtest_rosbag回放](../../02_基础知识/12_机器人软件/09_ROS2测试与CI_launch_testing_gtest_rosbag回放.md)

**答案要点**
- CI：每次提交自动构建、跑静态检查与测试，尽快发现集成问题。CD：自动把通过测试的构建打包/发布到测试或生产环境（持续交付需人工批准，持续部署全自动）。
- 机器人流水线：编译（x86 + ARM 交叉）→ 单元测试 → 仿真集成测试（headless Gazebo/MuJoCo）→ 回放测试（rosbag）→ 打包镜像/固件 → 在目标硬件上冒烟测试（HIL）。
- 质量门禁：测试通过、覆盖率不下降、静态分析零新增告警。
- 缓存依赖、构建矩阵（多 ROS 版本/架构）、保持流水线快（几分钟到十几分钟）。
- 固件发布：版本号写入固件，产物带校验和与符号文件，支持回滚。

**English short answer**
Continuous integration builds and tests every commit automatically to catch integration problems early, and continuous delivery packages passing builds for release. A robotics pipeline builds for x86 and ARM, runs unit tests, headless simulation and recorded-data replay tests, then packages images or firmware and smoke-tests on target hardware. Quality gates block merges that fail tests or add warnings.

（译：CI 每次提交自动构建测试以尽早发现集成问题，CD 把通过的构建打包发布；机器人流水线含 x86/ARM 构建、单元测试、无头仿真与回放测试、打包镜像/固件、目标硬件冒烟测试；质量门禁阻止不合格合并。）

**追问方向**：硬件在环如何接入 CI；构建缓存策略。

### Q39 语义化版本（SemVer）与发布管理？（Semantic versioning）
**优先级：★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- 格式 `MAJOR.MINOR.PATCH`：不兼容的 API 变更升主版本；向后兼容的功能新增升次版本；向后兼容的修复升补丁版本。预发布标签如 `1.2.0-rc.1`。
- 发布流程：从稳定分支或打 tag；变更日志（changelog）；发布说明包含已知问题与升级步骤；制品带版本与校验和。
- 依赖声明用范围（如 `^1.2`），锁文件固定可复现构建。
- 机器人：固件、上位机软件、协议版本三者要有兼容矩阵；协议握手时交换版本号并拒绝不兼容组合。
- 硬件改版与软件版本关联到序列号/批次。

**English short answer**
Semantic versioning uses major, minor and patch numbers: major for breaking changes, minor for compatible features and patch for fixes. I tag releases, keep a changelog, ship artifacts with checksums, and pin dependencies with lock files for reproducibility. For robots I also keep a compatibility matrix between firmware, host software and protocol versions and check versions in the handshake.

（译：SemVer 主版本表示不兼容变更、次版本表示兼容新增、补丁表示修复；发布打 tag、写 changelog、产物带校验和，用锁文件固定依赖；机器人还需固件/上位机/协议的兼容矩阵并在握手时检查版本。）

**追问方向**：协议向后兼容的设计；回滚策略。

### Q40 敏捷、Scrum 与看板的基本概念？（Agile, Scrum, Kanban）
**优先级：★★**

**答案要点**
- 敏捷：迭代增量交付，拥抱变化，快速反馈。Scrum：固定长度迭代（sprint，1–4 周）、角色（产品负责人、Scrum Master、团队）、仪式（计划、每日站会、评审、回顾）、工件（产品待办列表、迭代待办、增量）。
- 看板：可视化工作流、限制在制品数量（WIP），持续流动，适合运维/支持类任务。
- 科研/比赛团队的适配：短周期里程碑（周）、可演示的增量（先跑通闭环再优化）、定期回顾。
- 常见误区：把敏捷当成"不写文档/不做设计"。

**English short answer**
Agile delivers in small increments with fast feedback. Scrum organizes work into fixed sprints with planning, daily stand-ups, review and retrospective, while Kanban visualizes the workflow and limits work in progress. In a robotics team I use short milestones and demonstrable increments, such as getting the closed loop running first and then refining it.

（译：敏捷以小增量与快速反馈交付；Scrum 用固定迭代及计划/站会/评审/回顾；看板可视化工作流并限制在制品；机器人团队用短里程碑和可演示的增量。）

**追问方向**：你在团队中如何分工与同步；回顾会改进过什么。

### Q41 技术文档与设计文档（design doc）应包含什么？（Design documents）
**优先级：★★**

**答案要点**
- 结构：背景与目标/非目标、需求与约束、方案概述（架构图、接口）、备选方案与取舍、风险与缓解、测试与验证计划、发布与回滚、里程碑。
- 好处：在写代码前暴露分歧，沉淀决策原因（ADR：Architecture Decision Record 记录"为什么这样选"）。
- 写作原则：先结论后细节，图优先，量化指标（延迟预算、带宽、成功标准），明确假设。
- 面试中描述项目时按同样结构讲：问题→约束→方案→取舍→验证→结果。

**English short answer**
A design document states the goals and non-goals, requirements and constraints, the proposed architecture and interfaces, alternatives with trade-offs, risks, the test plan and the rollout and rollback plan. Recording decisions in short architecture decision records keeps the reasons for future readers. I also describe my projects in this order in interviews.

（译：设计文档包括目标与非目标、需求约束、架构与接口、备选方案与取舍、风险、测试计划、发布与回滚；用 ADR 记录决策原因；面试讲项目也按这个顺序。）

**追问方向**：ADR 的模板；如何量化成功标准。

### Q42 如何做需求分析和估算？（Requirements and estimation）
**优先级：★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 需求要可验证：功能需求（做什么）与非功能需求（延迟、精度、可靠性、安全、功耗、成本）；用"可测试的验收标准"写，例如"控制周期抖动 < X（本项目取值依平台）"。
- 估算：拆分工作包（WBS）、三点估算（乐观/最可能/悲观，期望 $(O+4M+P)/6$）、参考历史数据、留缓冲、先做风险最大的部分（spike）。
- 常见偏差：低估集成与调试时间（硬件项目尤其）；需求蔓延。
- 沟通：把不确定性显式化（区间而非单点），随进度更新估算。

**English short answer**
I write requirements as testable acceptance criteria, covering both functions and non-functional needs such as latency, accuracy and safety. For estimates I break work into packages, use three-point estimates, add buffer and tackle the riskiest parts early with a spike. Hardware projects usually underestimate integration and debugging time.

（译：需求写成可测试的验收标准，涵盖功能与延迟/精度/安全等非功能需求；估算拆工作包、三点估算、留缓冲、先做风险最大部分；硬件项目常低估集成与调试时间。）

**追问方向**：三点估算的期望公式；如何应对需求变更。

### Q43 Git 工作流（分支策略）怎么选？（Git branching strategies）
**优先级：★★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- 主干开发（trunk-based）：短分支频繁合入主干，配合特性开关与强 CI，适合迭代快的团队。
- Git Flow：`main`/`develop`/`feature`/`release`/`hotfix`，适合有明确版本发布的产品，流程较重。
- GitHub Flow：`main` 始终可部署，功能分支 + Pull Request + 评审后合并，简单通用。
- 选择：团队小、发布频繁→GitHub Flow/主干；有多版本维护→Git Flow。
- 合并策略：merge commit 保留历史；squash 保持主干整洁；rebase 线性历史（不要对已共享分支 rebase）。
- 机器人项目有子模块/多仓库时，用 `vcstool`/`repos` 文件或 submodule 固定依赖版本。

**English short answer**
Trunk-based development merges short-lived branches into the main branch often, backed by strong CI. Git Flow uses long-lived develop and release branches for versioned products. GitHub Flow keeps main always deployable with feature branches and pull requests. I choose by team size and release cadence, and I never rebase a branch others have already pulled.

（译：主干开发频繁合并短分支并依赖强 CI；Git Flow 用长期 develop/release 分支适合版本化产品；GitHub Flow 保持 main 可部署，功能分支+PR；按团队规模与发布节奏选择，不对他人已拉取的分支做 rebase。）

**追问方向**：squash 与 merge 的取舍；子模块的维护痛点。

### Q44 机器人软件为什么更难测试？有哪些策略？（Testing robot software）
**优先级：★★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 难点：依赖硬件与物理世界、时序与并发、非确定性（传感器噪声）、长时间运行问题。
- 策略金字塔：大量纯函数/算法的单元测试（可重复、不依赖 ROS）→ 节点级集成测试（launch_testing）→ 仿真测试（SIL）→ 回放真实数据（rosbag）→ 硬件在环（HIL）→ 少量实机验收。
- 设计可测试：把算法与 IO 分离（算法层纯 C++，ROS 层只做胶水）；注入时钟（可控时间）；固定随机种子。
- 回归：把线上发现的问题录成 bag，作为永久回归用例。

**English short answer**
Robot software depends on hardware, timing and noisy sensors, so I separate algorithms from I/O, test the pure algorithms with fast unit tests, then use node integration tests, simulation, recorded-data replay and finally hardware-in-the-loop. I inject a controllable clock and fixed random seeds, and I turn every field bug into a replayable regression case.

（译：机器人软件依赖硬件、时序和噪声传感器，故将算法与 IO 分离，纯算法用快速单测，再做节点集成、仿真、回放、硬件在环；注入可控时钟与固定随机种子，把现场 bug 录成可回放的回归用例。）

**追问方向**：如何测试时间相关逻辑；仿真与现实的差距。

### Q45 代码与硬件迭代的协同：如何降低联调风险？（Hardware-software integration risk）
**优先级：★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 先做接口契约（协议、单位、坐标系、时序），双方各自用模拟器/假数据开发。
- 分层验证：单设备自检 → 总线通信 → 单关节 → 多关节 → 整机；每层通过再叠加下一层。
- 安全先行：上电默认失能，限幅、急停、看门狗在联调第一天就启用；限制初次运行的速度/力矩。
- 记录一切：版本、参数、日志、示波器/逻辑分析仪截图，便于复现。
- 复盘：每次故障记录现象、根因、修复、预防措施。

**English short answer**
I agree on interface contracts first, covering protocol, units, frames and timing, and develop each side against simulators. Then I verify bottom up: single device, bus, single joint, multiple joints, full robot. Safety features like default-disabled actuators, limits and the e-stop are enabled from day one, and I log versions and parameters so failures can be reproduced.

（译：先约定接口契约（协议、单位、坐标系、时序），各自用模拟器开发；自底向上验证（单设备→总线→单关节→多关节→整机）；联调第一天就启用默认失能、限幅、急停，并记录版本与参数以复现。）

**追问方向**：初次上电的检查清单；故障复盘模板。

### Q46 如何管理机器人上的日志与数据？（Logging and data management）
**优先级：★★★** · 对应基础知识：[数据与日志_可观测性_回放与复盘](../../02_基础知识/13_系统工程与安全/05_数据与日志_可观测性_回放与复盘.md)

**答案要点**
- 日志分级（DEBUG/INFO/WARN/ERROR/FATAL）；结构化字段（时间戳、模块、事件码）便于检索；限频与去重避免刷屏；关键事件必记（模式切换、故障、参数变更）。
- 数据记录：rosbag2（话题）、定期快照、故障前后窗口（环形缓冲，触发时保存前 N 秒）；记录版本、参数、时钟同步信息。
- 存储：磁盘配额与轮转、压缩、断电安全（定期 flush）；敏感数据脱敏。
- 实时线程不要直接写文件：通过无锁队列交给低优先级线程。
- 回放与复盘：同一份 bag 能离线重放算法，复现现场问题。

**English short answer**
I use leveled, structured logs with timestamps, module names and event codes, rate-limit repetitive messages, and always log mode changes, faults and parameter changes. Data goes into rosbag with a ring buffer that saves the window around a fault. Real-time threads hand log messages to a low-priority writer through a lock-free queue, and I rotate files and limit disk use.

（译：日志分级结构化，带时间戳/模块/事件码，限频并必记模式切换、故障、参数变更；数据用 rosbag 加环形缓冲保存故障前后窗口；实时线程经无锁队列交给低优先级写入线程；做轮转与配额。）

**追问方向**：环形缓冲触发保存的实现；日志导致的实时抖动案例。

### Q47 说说你理解的"可维护的机器人软件"标准。（What makes robot software maintainable）
**优先级：★★★** · 对应基础知识：[机器人系统架构设计_分层_接口_需求](../../02_基础知识/13_系统工程与安全/01_机器人系统架构设计_分层_接口_需求.md)

**答案要点**
- 模块边界清晰，接口稳定并有文档；参数外置且有默认值与校验；日志与诊断完备，出问题能自证。
- 可替换：硬件/算法通过接口与插件替换；仿真与真机同一套代码路径。
- 可测试：有分层测试和回放用例；CI 守门。
- 可观测：关键量（延迟、丢包、队列、温度、电压）可监控；有健康状态与降级策略。
- 可复现：版本固定、环境容器化、构建脚本化。
- 可交接：README、架构图、故障手册；新成员能在一天内跑通。

**English short answer**
Maintainable robot software has clear module boundaries with stable documented interfaces, externalized and validated parameters, and good logging and diagnostics so it can explain failures. Hardware and algorithms are replaceable through interfaces, tests and CI protect changes, builds are reproducible in containers, and a new teammate can run it in a day from the README.

（译：可维护的机器人软件有清晰模块边界与稳定文档化接口、外置且校验的参数、完备日志诊断；硬件/算法经接口可替换，有测试与 CI，构建可复现，新成员按 README 一天内能跑通。）

**追问方向**：你的项目里哪一点最体现这些；如何衡量可维护性。

### Q48 面向对象 vs 数据导向设计（DOD）在机器人里如何取舍？（OOP vs data-oriented design）
**优先级：★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- OOP：用对象封装状态与行为，适合建模抽象接口（硬件、能力、状态机）。
- 数据导向：围绕数据布局和批量处理组织代码（SoA、连续内存、无虚调用），适合高吞吐计算（点云、粒子、仿真）。
- 结合：外层用接口/OOP 组织系统，内层热点循环用 DOD；避免在每个点上调用虚函数。
- ECS（实体–组件–系统）是游戏与仿真引擎采用的 DOD 架构，MuJoCo/Drake 内部也偏数据导向。
- 度量先行：用 profile 判断是否值得改布局。

**English short answer**
Object-oriented design is good for abstractions such as hardware interfaces and state machines, while data-oriented design arranges memory for bulk processing in hot loops, as in point clouds or particle filters. I combine them: interfaces at the system level and contiguous, virtual-call-free data inside the hot paths, guided by profiling.

（译：OOP 适合硬件接口、状态机等抽象；数据导向围绕内存布局做批处理，适合点云/粒子滤波热点；结合使用——系统层用接口，热路径用连续数据、无虚调用，并以 profile 为依据。）

**追问方向**：ECS 的核心概念；虚函数调用阻碍内联的影响。

### Q49 Python 与 C++ 混合工程（pybind11）的设计要点？（Mixing Python and C++）
**优先级：★★** · 对应基础知识：[Python工程与科学计算](../../02_基础知识/12_机器人软件/03_Python工程与科学计算.md)

**答案要点**
- 动机：算法与实时部分用 C++，原型、胶水、可视化、训练用 Python；用 pybind11 / Cython / ctypes / nanobind 暴露 C++ 接口。
- 注意：GIL（长时间 C++ 计算时释放 GIL）；对象生命周期与引用（返回内部指针的风险）；NumPy 与 Eigen 之间的零拷贝（缓冲协议）；异常转换。
- 构建：CMake + pybind11，使用 `setuptools`/`scikit-build` 打包，ABI 与 Python 版本匹配。
- 替代：ROS 2 的 `rclpy`/`rclcpp` 通过消息跨语言交互，隔离更好但有序列化开销。

**English short answer**
I write performance-critical code in C++ and expose it to Python with pybind11 or similar tools, so Python handles prototyping, glue and visualization. Key points are releasing the GIL during long computations, zero-copy sharing of NumPy arrays through the buffer protocol, careful object lifetimes, and building wheels that match the Python version. Alternatively nodes can talk over ROS 2 messages for stronger isolation.

（译：性能关键部分用 C++，经 pybind11 暴露给 Python 做原型/胶水/可视化；要点是长计算时释放 GIL、用缓冲协议零拷贝共享 NumPy 数组、注意对象生命周期、构建匹配 Python 版本的包；也可用 ROS 2 消息进程间通信获得更好隔离。）

**追问方向**：返回 NumPy 视图的生命周期问题；rclpy 回调与 GIL。

### Q50 如何选择合适的序列化格式（protobuf、JSON、CDR、msgpack）？（Serialization format choice）
**优先级：★★** · 对应基础知识：[DDS与分布式通信](../../02_基础知识/12_机器人软件/05_DDS与分布式通信.md)

**答案要点**
- JSON：可读、通用，体积大、解析慢，适合配置与 Web 接口；protobuf/FlatBuffers：带 schema、紧凑、跨语言、支持演进，FlatBuffers 零拷贝读取；msgpack：类 JSON 的二进制；CDR：DDS/ROS 2 的标准序列化。
- 选择维度：性能与体积、可读性与调试、schema 演进能力、语言支持、是否需要随机访问/零拷贝。
- 实践：Web 前端用 JSON/WebSocket；MCU 与上位机用自定义紧凑帧 + CRC；跨语言服务用 protobuf。
- 版本演进：字段只增不删、保留编号、给默认值。

**English short answer**
JSON is readable and universal but bulky and slow, so I use it for configuration and web APIs. Protobuf and FlatBuffers are compact, schema-based and support evolution, and FlatBuffers allows zero-copy reads. CDR is the standard on the ROS 2 and DDS side. I choose by performance, debuggability, schema evolution and language support.

（译：JSON 可读通用但体积大且慢，用于配置和 Web；protobuf/FlatBuffers 紧凑、带 schema、可演进，FlatBuffers 可零拷贝读取；CDR 是 ROS 2/DDS 标准；按性能、可调试性、演进能力、语言支持选择。）

**追问方向**：protobuf 的 varint 编码；schema 演进破坏兼容的情形。

### Q51 如何做性能优化？流程是什么？（Performance optimization workflow）
**优先级：★★★** · 对应基础知识：[日志_诊断_性能剖析_perf_tracing](../../02_基础知识/12_机器人软件/13_日志_诊断_性能剖析_perf_tracing.md)

**答案要点**
- 流程：①定义目标（延迟/吞吐/功耗）与基线测量；②profile 找热点（`perf`、火焰图、`gprof`、Tracy）；③提出假设并修改一处；④再测并对比；⑤回归测试保证正确性；⑥记录。
- 原则：先测量再优化；优化占比最大的部分（阿姆达尔）；算法与数据结构优先于微优化；避免过早优化。
- 常见手段：减少分配与拷贝、缓存友好布局、批处理、并行化、向量化、降低精度（FP16/INT8）、异步流水线、预计算与查表。
- 注意：测量噪声（预热、频率、其它进程），用多次运行的中位数与分位数；性能回归加入 CI。

**English short answer**
I set a target and measure a baseline, profile to find the real hotspots with tools like perf or flame graphs, change one thing, measure again, and verify correctness. I start with algorithms and data structures before micro-optimizations, and I watch measurement noise such as warm-up and clock scaling by reporting medians and percentiles over multiple runs.

（译：先定目标并测基线，用 perf/火焰图找热点，一次只改一处再测并验证正确性；先改算法与数据结构再做微优化；注意预热与频率缩放造成的噪声，报告多次运行的中位数与分位数。）

**追问方向**：火焰图怎么看；如何防止性能回归。

### Q52 错误处理：异常、错误码与 `Result` 类型怎么选？（Error handling strategies）
**优先级：★★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 错误码/返回状态：显式、开销可预测、适合 C、嵌入式与实时代码（不启用异常）；缺点是容易被忽略、传播繁琐。
- 异常：把错误处理与正常路径分离，自动栈展开配合 RAII；缺点是控制流不可见、实时代码中抛出路径耗时不确定，很多嵌入式/实时项目禁用（`-fno-exceptions`）。
- `Result<T,E>`/`std::expected`（C++23）/`std::optional`：把错误放进返回类型，强制调用者处理，兼具显式与类型安全。
- 原则：异常用于"真正的异常"（不可恢复或罕见）；预期内的失败（解析失败、超时）用返回值；在模块边界统一翻译错误类型；日志里记录上下文。
- 控制回路里：检测到非法输入应进入安全状态，而不是抛出异常后让线程退出。

**English short answer**
Error codes are explicit and predictable, so they suit embedded and real-time code. Exceptions separate error handling from the normal path but have unpredictable cost and are often disabled in firmware. Result or expected types put the error in the return type and force the caller to handle it. I use return values for expected failures and keep exceptions for rare, unrecoverable situations.

（译：错误码显式且开销可预测，适合嵌入式/实时；异常把错误处理与正常路径分离但耗时不确定，固件常禁用；Result/expected 把错误放进返回类型强制处理；预期内失败用返回值，异常留给罕见不可恢复情形。）

**追问方向**：`noexcept` 的作用；控制环中检测到错误该怎么办。

### Q53 断言、前置条件与防御式编程？（Assertions and defensive programming）
**优先级：★★★** · 对应基础知识：[可靠性与故障诊断_FMEA_看门狗_降级策略](../../02_基础知识/13_系统工程与安全/03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)

**答案要点**
- 断言（`assert`）检查**不应发生**的内部不变量/程序员错误，发布版可能被关闭；对外部输入（传感器、网络、用户）不能靠断言，必须做运行时校验。
- 契约式设计：函数文档化前置条件、后置条件、不变量；在边界检查输入的范围（NaN、无穷、量纲、时间戳单调）。
- 防御式编程的度：边界处防御，内部信任；过度防御会掩盖 bug、增加复杂度。
- 嵌入式：断言失败的处理策略要安全（进入失能、保存现场、复位），而不是死循环卡住电机在使能状态。
- 与日志配合：断言失败打印文件行号和关键变量。

**English short answer**
Assertions check internal invariants that should never be violated and may be compiled out in release builds, so they are not a substitute for validating external input such as sensor data. I validate at module boundaries, checking ranges, NaN values and timestamp monotonicity, and trust internal code. On a robot, a failed assertion must lead to a safe state, not leave actuators enabled.

（译：断言检查不应发生的内部不变量，发布版可能被关闭，不能代替对外部输入（传感器数据）的校验；在模块边界校验范围、NaN、时间戳单调性；断言失败应进入安全状态而不是让执行器保持使能。）

**追问方向**：NaN 传播的危害；看门狗与断言的配合。

### Q54 Mock、Stub、Fake、Spy 有什么区别？（Test doubles）
**优先级：★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- Stub：返回预设值的简单替身（假传感器总返回 0.5）。
- Fake：有真实但简化的行为实现（内存里的假电机，积分模拟速度响应）。
- Mock：预先设定**期望的调用**并在测试中验证是否发生（"controller 应调用 setTorque 一次，参数在 ±0.1 内"）。
- Spy：真实对象外加记录调用的包装，事后断言。
- 使用建议：优先用 fake 和状态验证（测结果），谨慎使用 mock（测实现细节，易让测试脆弱）；框架：GoogleMock、`unittest.mock`、pytest-mock。
- 机器人：用 fake 电机/传感器配合固定时钟，可确定性地测控制逻辑。

**English short answer**
A stub returns canned values, a fake has a simplified working implementation such as a simulated motor, a mock verifies that expected calls happened, and a spy records calls for later assertions. I prefer fakes with state-based verification because mock-heavy tests couple to implementation details and become brittle.

（译：Stub 返回预设值，Fake 有简化的真实行为（如模拟电机），Mock 验证期望的调用发生，Spy 记录调用供事后断言；优先 fake 加状态验证，过度 mock 会让测试与实现细节耦合而变脆。）

**追问方向**：如何让时间可控；GoogleMock 的 EXPECT_CALL。

### Q55 TDD 是什么？适合机器人开发吗？（Test-driven development）
**优先级：★★** · 对应基础知识：[测试策略_仿真在环_硬件在环_回归](../../02_基础知识/13_系统工程与安全/04_测试策略_仿真在环_硬件在环_回归.md)

**答案要点**
- 红–绿–重构循环：先写失败的测试→写最少代码让它通过→重构。
- 好处：接口先行（逼你设计易用 API）、回归保护、小步前进。
- 适合：纯算法与数据处理（滤波器、坐标变换、协议解析、状态机转移）——输入输出明确，容易写出断言（如已知解的卡尔曼滤波、旋转矩阵正交性）。
- 不太适合：强依赖硬件与物理的部分，可改为仿真/HIL 与现场验收。
- 实践折中：对核心算法与协议解析做 TDD，对其余部分做"先写验收用例"。

**English short answer**
Test-driven development loops through red, green and refactor: write a failing test, make it pass with minimal code, then clean up. It works very well for algorithms, coordinate transforms, protocol parsers and state machines, where expected outputs are clear. For hardware-dependent parts I rely on simulation, hardware-in-the-loop and acceptance tests instead.

（译：TDD 循环为红（失败测试）、绿（最小实现通过）、重构；非常适合算法、坐标变换、协议解析、状态机；硬件相关部分则依赖仿真、HIL 与验收测试。）

**追问方向**：如何给卡尔曼滤波写测试；性质测试（property-based）的用法。

### Q56 单体仓库（monorepo）与多仓库如何取舍？（Monorepo vs polyrepo）
**优先级：★★** · 对应基础知识：[Linux与Shell_Git](../../02_基础知识/12_机器人软件/01_Linux与Shell_Git.md)

**答案要点**
- Monorepo：所有包在一个仓库，原子提交跨包重构、统一版本与 CI、依赖可见；但仓库大、权限粒度粗、CI 需增量构建。
- Polyrepo：各包独立仓库，边界清晰、权限独立、发布节奏独立；跨仓库修改需要协调，依赖版本漂移。
- 机器人：ROS 工作区常是多个包的集合；用 `vcs import` + `repos` 文件或 Git 子模块固定多仓库版本；P3/P4 这类子模块式组织属于多仓库聚合。
- 选择：团队小、耦合紧→monorepo；包被多个项目复用、团队独立→polyrepo。

**English short answer**
A monorepo allows atomic cross-package changes and a unified CI but gets large and needs incremental builds. Separate repositories give clear boundaries and independent releases but make cross-repo changes harder and versions can drift. For ROS workspaces I pin multi-repo dependencies with vcs repos files or submodules.

（译：Monorepo 支持跨包原子提交与统一 CI，但仓库庞大需增量构建；多仓库边界清晰、独立发布，但跨仓修改难、版本易漂移；ROS 工作区用 repos 文件或子模块固定多仓依赖。）

**追问方向**：子模块的常见坑；如何做跨仓库的联合 CI。

### Q57 依赖管理：如何保证构建可复现？（Dependency management）
**优先级：★★★** · 对应基础知识：[Docker与部署_交叉编译_systemd](../../02_基础知识/12_机器人软件/12_Docker与部署_交叉编译_systemd.md)

**答案要点**
- 声明依赖：C++ 用 CMake `find_package`/Conan/vcpkg；ROS 2 用 `package.xml` + `rosdep`；Python 用 `requirements.txt`/`pyproject.toml` + 锁文件（`pip-tools`、`poetry`）。
- 可复现：固定版本（锁文件）、容器镜像固定基础系统（Docker）、记录编译器与工具链版本、离线缓存/镜像。
- 风险：传递依赖冲突（菱形依赖）、ABI 不兼容、上游删除包/改版（供应链）、许可证冲突。
- 实践：虚拟环境隔离 Python；ROS 工作区 `rosdep install` 的结果写入文档；CI 在干净环境构建验证。
- 安全：校验哈希、只使用可信源。

**English short answer**
I declare dependencies in package manifests, pin exact versions with lock files, and build inside a container image so the toolchain is fixed. Risks include diamond dependency conflicts, ABI mismatches and upstream changes, so CI builds in a clean environment, and I verify hashes and use trusted sources.

（译：在清单中声明依赖，用锁文件固定版本，在容器镜像内构建以固定工具链；风险有菱形依赖冲突、ABI 不兼容、上游变更，所以 CI 在干净环境构建并校验哈希、使用可信源。）

**追问方向**：菱形依赖怎么解决；rosdep 的工作方式。

### Q58 开源许可证的基本区别？（Open-source licenses）
**优先级：★**

**答案要点**
- 宽松型：MIT、BSD、Apache-2.0——允许商用与闭源衍生，保留版权声明；Apache-2.0 另含专利授权条款。
- 强 copyleft：GPL——衍生作品分发时必须以同样许可证开源；LGPL——允许动态链接到库而不强制自身开源；AGPL——网络服务也触发开源义务。
- ROS 2 核心多为 Apache-2.0；很多驱动、内核代码是 GPL。
- 工程注意：在商用或比赛项目中引入第三方库前确认许可证兼容；保留 NOTICE；以上为一般性概述，具体条款以许可证原文为准（未核对）。

**English short answer**
Permissive licenses such as MIT, BSD and Apache-2.0 allow commercial and closed-source use with attribution, and Apache adds a patent grant. GPL requires derivative works to be released under the same license, LGPL permits linking from non-GPL code, and AGPL extends the obligation to network services. Before using a third-party library I check that its license is compatible with my project.

（译：MIT/BSD/Apache-2.0 宽松、允许商用闭源，Apache 含专利授权；GPL 要求衍生作品同样开源，LGPL 允许非 GPL 代码链接，AGPL 延伸到网络服务；引入第三方库前确认许可证兼容。）

**追问方向**：动态链接 GPL 库的争议；ROS 2 的许可证。

### Q59 功能开关（Feature flag）与灰度发布在机器人中如何用？（Feature flags and staged rollout）
**优先级：★★** · 对应基础知识：[可靠性与故障诊断_FMEA_看门狗_降级策略](../../02_基础知识/13_系统工程与安全/03_可靠性与故障诊断_FMEA_看门狗_降级策略.md)

**答案要点**
- 功能开关：用配置决定是否启用新功能，使"部署"与"发布"分离；出问题可立即关闭而无需回滚版本。
- 灰度/分阶段发布：先仿真 → 单台测试机 → 小比例车队 → 全量；每阶段设定退出标准（指标、故障率）。
- 机器人应用：新的避障算法先在影子模式（shadow mode）下运行——只计算与记录输出而不控制执行器，与旧算法对比后再切换。
- 注意：开关数量过多造成组合爆炸；清理过期开关；开关状态要记录进日志以便复盘。

**English short answer**
Feature flags decouple deployment from release so a new behavior can be switched off quickly without rolling back. I roll changes out in stages, from simulation to one test robot to a small fleet, with explicit exit criteria. A new planner can first run in shadow mode, computing outputs that are logged but not executed, before it takes control.

（译：功能开关使部署与发布分离，出问题可快速关闭；分阶段发布从仿真到单台测试机到小范围车队并设退出标准；新规划器可先在影子模式运行，仅记录输出再接管控制。）

**追问方向**：影子模式的评估指标；开关清理策略。

### Q60 API 设计的基本原则（尤其是库与消息接口）？（API design principles）
**优先级：★★** · 对应基础知识：[C++现代特性与工程实践](../../02_基础知识/12_机器人软件/02_C++现代特性与工程实践.md)

**答案要点**
- 易用难错：类型表达单位与含义，参数顺序一致，避免布尔参数含义不清（用枚举）；最小惊讶原则。
- 稳定与演进：接口小而稳；新增而不修改；弃用（deprecate）流程；语义版本管理；消息只增字段。
- 错误语义明确：什么时候失败、返回什么；线程安全和重入性在文档中说明。
- 所有权与生命周期清晰：谁分配谁释放；返回值/引用的有效期；C 接口用不透明句柄。
- 机器人消息设计：带 `header`（时间戳+坐标系）、明确单位（SI）、状态/有效位、序号。

**English short answer**
A good API is easy to use and hard to misuse: types carry units, parameters are consistent, and enums replace ambiguous booleans. It stays small and stable, evolves by adding rather than changing, and documents errors, thread safety and ownership clearly. For robot messages I include a header with timestamp and frame, use SI units and carry validity flags.

（译：好的 API 易用难错：类型承载单位、参数一致、用枚举代替含义不清的布尔；小而稳定、靠新增演进，并说明错误、线程安全与所有权；机器人消息含时间戳与坐标系的 header、SI 单位及有效位。）

**追问方向**：弃用流程；消息中为什么要带有效位。

### Q61 并发设计原则：不可变性与消息传递的好处？（Immutability and message passing）
**优先级：★★★** · 对应基础知识：[ROS2_Humble核心概念与ROS1对比](../../02_基础知识/12_机器人软件/04_ROS2_Humble核心概念与ROS1对比.md)

**答案要点**
- 共享可变状态是并发 bug 的根源。三条出路：①不共享（每线程私有）；②共享但不可变（`const` 数据、发布后不再修改的消息）；③通过消息传递所有权（队列、`unique_ptr` 转移）。
- 不可变数据无需加锁，可被多线程安全读取；更新通过"创建新版本 + 原子替换指针"（copy-on-write / RCU 思想）。
- 机器人：传感器消息发布后只读；参数更新用快照；地图用双缓冲切换。
- 加锁时：锁粒度、锁顺序（避免死锁）、持锁时间尽量短，不在持锁时调用未知回调。
- Actor 模型/ROS 节点：每个节点内部串行处理（单线程 executor），靠消息交互，天然减少锁。

**English short answer**
Shared mutable state causes most concurrency bugs, so I try not to share, or to share immutable data, or to transfer ownership through queues. Immutable messages need no locks, and updates replace the whole object atomically, like swapping a pointer to a new map. When I do lock, I keep critical sections short, fix a lock order and never call unknown callbacks while holding a lock.

（译：共享可变状态是并发 bug 之源，所以尽量不共享、共享不可变数据或经队列转移所有权；不可变消息无需锁，更新靠原子替换整个对象（如换地图指针）；加锁时临界区要短、固定锁顺序、持锁时不调用未知回调。）

**追问方向**：RCU 的读写流程；ROS 2 executor 回调组的互斥。

## 本章要点速记
1. SOLID：单一职责、开闭、里氏替换、接口隔离、依赖倒置；依赖注入让硬件可被假对象替换。
2. 组合优于继承；继承主要用于抽象接口。
3. 模式选型：适配器（兼容接口）、策略（换算法）、观察者/发布订阅（解耦通知）、状态模式/FSM（模式管理）、命令（排队撤销）、责任链（安全过滤）。
4. 单例有隐藏依赖，优先注入；工厂+注册表使扩展不改核心。
5. 队列必须有界，队满策略要明确；命令要幂等并带 ID。
6. 重构依赖测试；控制代码重构用回放数据比对。
7. CI 门禁：编译、测试、静态分析；版本遵循 SemVer，固件/软件/协议有兼容矩阵。
