## 一、SQL 基础

### Q1 SQL 的基本语句与执行顺序？（SQL basics and logical order）
**优先级：★★★**

**答案要点**
- DDL：`CREATE/ALTER/DROP`；DML：`INSERT/UPDATE/DELETE`；DQL：`SELECT`；DCL：`GRANT`；事务：`BEGIN/COMMIT/ROLLBACK`。
- 查询的**逻辑执行顺序**：`FROM` → `JOIN ... ON` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`。所以 `WHERE` 里不能用 `SELECT` 的别名，`WHERE` 过滤行、`HAVING` 过滤分组。

```sql
-- 教学示例: 每个机器人最近 1 小时的平均电池电压
SELECT robot_id, AVG(voltage) AS avg_v, COUNT(*) AS n
FROM telemetry
WHERE ts >= NOW() - INTERVAL 1 HOUR
GROUP BY robot_id
HAVING COUNT(*) > 100
ORDER BY avg_v DESC
LIMIT 10;
```

**English short answer**
SQL statements are grouped into definition, manipulation, query and control. A query is logically evaluated as FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, then ORDER BY and LIMIT. That is why WHERE filters rows before grouping, while HAVING filters groups after aggregation.

**追问方向**：WHERE 与 HAVING；执行计划 `EXPLAIN`。

### Q2 几种 JOIN 的区别？（JOIN types）
**优先级：★★★**

**答案要点**：`INNER JOIN` 只保留两边都匹配的行；`LEFT JOIN` 保留左表全部行，右表无匹配补 `NULL`；`RIGHT JOIN` 反之；`FULL OUTER JOIN` 两边全保留；`CROSS JOIN` 笛卡尔积。`ON` 与 `WHERE` 对外连接语义不同：右表条件写在 `WHERE` 会把 `NULL` 行过滤掉，等同于内连接。

```sql
SELECT r.name, t.task_id
FROM robots r
LEFT JOIN tasks t ON t.robot_id = r.id AND t.status = 'running';
```

**English short answer**
An inner join keeps only matching rows, a left join keeps every row from the left table and fills missing right-side columns with NULL, and a cross join produces all combinations. A filter on the right table placed in WHERE can accidentally turn a left join into an inner join.

**追问方向**：自连接；`NULL` 的比较（`IS NULL`）；`EXISTS` vs `IN`。

### Q3 `NULL` 的处理有什么坑？（NULL semantics）
**优先级：★★**

**答案要点**：`NULL` 表示未知，任何与 `NULL` 的比较（`=`、`<>`）结果为未知，不是真；必须用 `IS NULL`。聚合函数（`SUM/AVG`）忽略 `NULL`，`COUNT(*)` 计行数，`COUNT(col)` 不计 `NULL`。`NOT IN (子查询)` 若子查询含 `NULL` 会返回空，应使用 `NOT EXISTS`。传感器"无效读数"应存 `NULL`+有效位，而不是 0，否则会污染平均值。

**English short answer**
NULL means unknown, so comparing with equals never succeeds and I must use IS NULL. Aggregates ignore NULLs, COUNT of a column does not count them, and NOT IN with a NULL in the subquery returns nothing. For invalid sensor readings I store NULL rather than zero so averages are not polluted.

**追问方向**：三值逻辑；`COALESCE`。

### Q4 `GROUP BY`、窗口函数是什么？（GROUP BY and window functions）
**优先级：★★**

**答案要点**：`GROUP BY` 把行归并为组再聚合。窗口函数保留每一行，同时计算跨行的值：`ROW_NUMBER() OVER (PARTITION BY robot_id ORDER BY ts DESC)` 取每个机器人最新一条记录；`LAG/LEAD` 取前后行（算差分）；`SUM() OVER` 做累计。

```sql
SELECT * FROM (
  SELECT t.*, ROW_NUMBER() OVER (PARTITION BY robot_id ORDER BY ts DESC) rn
  FROM telemetry t
) x WHERE rn = 1;   -- 每个机器人最新状态
```

**English short answer**
GROUP BY collapses rows into one per group, while a window function computes a value across related rows but keeps every row. For example ROW_NUMBER partitioned by robot and ordered by time descending lets me pick each robot's latest record.

**追问方向**：RANK vs DENSE_RANK。

### Q5 `DELETE`、`TRUNCATE`、`DROP` 的区别？（Delete, truncate, drop）
**优先级：★★**

**答案要点**：`DELETE` 按条件逐行删，可回滚，记录日志，较慢；`TRUNCATE` 清空表，重置自增，通常不可按行回滚，快；`DROP` 删除整个表结构及数据。更新/删除前先 `SELECT` 验证 `WHERE`，生产环境先在事务里执行。

**English short answer**
DELETE removes rows selectively and can be rolled back, TRUNCATE quickly empties the whole table, and DROP removes the table itself. Before running an update or delete I check the WHERE clause with a select.

**追问方向**：软删除（`deleted_at`）。

## 二、索引与查询优化

### Q6 索引是什么？为什么能加速查询？（Index）
**优先级：★★★**

**答案要点**
- 索引是为列额外维护的有序数据结构，让查询从全表扫描 $O(n)$ 变为 $O(\log n)$。常用 **B+ 树**：高度低（通常 3–4 层）、叶子有序且链表相连支持范围查询（见 [数据结构与算法](./01_数据结构与算法.md) Q14）。哈希索引适合等值查询，不支持范围。
- 代价：占存储；**写入变慢**（要维护索引）。所以不是越多越好，读多写少的列才建。
- **聚簇索引**（InnoDB 主键）：叶子节点存整行数据；**二级索引**：叶子存主键值，查询需要"回表"；**覆盖索引**：查询所需列都在索引里，免回表。
- **最左前缀原则**：联合索引 `(a,b,c)` 能用于 `a`、`a,b`、`a,b,c` 条件，不能跳过 `a` 直接用 `b`。

**English short answer**
An index is an extra ordered structure, usually a B-plus tree, that turns a full table scan into a logarithmic lookup and supports range queries. The cost is extra storage and slower writes. A composite index follows the leftmost-prefix rule, and a covering index contains all needed columns, so the database does not have to go back to the table.

**追问方向**：回表；索引选择性；主键为什么建议自增。

### Q7 哪些情况索引会失效？（When indexes are not used）
**优先级：★★★**

**答案要点**：①对索引列使用函数或运算：`WHERE DATE(ts) = ...`、`WHERE a+1 = 5`；②隐式类型转换（字符串列与数字比较）；③以通配符开头的 `LIKE '%abc'`；④违背最左前缀；⑤`OR` 连接不同列且部分无索引；⑥选择性很低（如性别列），优化器认为全表扫描更快；⑦`!=`、`NOT IN` 可能不走索引。排查：`EXPLAIN` 看 `type`（`ALL` 为全表扫描）、`key`、`rows`。改写：把计算移到常量侧，如 `ts >= '2025-01-01' AND ts < '2025-01-02'`。

**English short answer**
An index may be ignored if I wrap the column in a function or expression, rely on an implicit type conversion, use a LIKE pattern starting with a wildcard, skip the leading column of a composite index, or when the column has very low selectivity. I check the query plan with EXPLAIN and rewrite the condition so the column stands alone.

**追问方向**：EXPLAIN 字段含义；慢查询日志。

### Q8 如何优化一条慢查询？（Query optimization workflow）
**优先级：★★★**

**答案要点**：①定位（慢查询日志）；②`EXPLAIN` 看执行计划；③加合适索引（联合、覆盖）；④避免 `SELECT *`；⑤分页优化（深分页 `LIMIT 1000000,10` 改为基于上次主键的 keyset 分页 `WHERE id > last LIMIT 10`）；⑥拆分大事务、批量写入；⑦读写分离、分库分表（最后手段）；⑧缓存热点。时间序列数据（遥测）按时间分区，旧数据归档或降采样。

**English short answer**
I find the slow query from logs, inspect its plan with EXPLAIN, and add or adjust indexes. I avoid select star, replace deep offset pagination with keyset pagination, and batch writes. For time-series data I partition by time and archive or downsample old data.

**追问方向**：分库分表的分片键；冷热分离。

### Q9 主键怎么选？自增 ID 与 UUID？（Primary keys）
**优先级：★★**

**答案要点**：自增整数：紧凑、顺序插入对 B+ 树友好（页分裂少），但分布式场景需要号段/雪花算法。UUID：全局唯一、可离线生成（设备端生成方便），但无序导致随机插入、页分裂、索引变大；可用有序 UUID（UUIDv7）或雪花 ID。

**English short answer**
Auto-increment integers are compact and insert sequentially into a B-plus tree, but they are awkward across distributed nodes. Random UUIDs are globally unique and can be generated offline on a device, but they cause scattered inserts and a larger index; time-ordered IDs are a good compromise.

**追问方向**：雪花算法；业务主键 vs 代理主键。

## 三、事务与并发

### Q10 事务的 ACID 是什么？（ACID）
**优先级：★★★**

**答案要点**
- **原子性 Atomicity**：要么全做要么全不做（靠 undo log 回滚）。
- **一致性 Consistency**：事务前后数据满足约束（由原子性、隔离性、持久性与应用约束共同保证）。
- **隔离性 Isolation**：并发事务互不干扰（靠锁/MVCC）。
- **持久性 Durability**：提交后即使宕机也不丢（靠 redo log / WAL 预写日志，先写日志再改数据页）。
- 例：转账 A→B：扣 A、加 B 必须同事务。

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

**English short answer**
ACID stands for atomicity, consistency, isolation and durability. A transaction either fully happens or not at all, keeps constraints valid, appears isolated from concurrent transactions, and once committed survives a crash, thanks to write-ahead logging. The classic example is a money transfer, where debit and credit must succeed together.

**追问方向**：WAL；undo/redo 区别；两阶段提交。

### Q11 事务隔离级别与并发异常？（Isolation levels）
**优先级：★★★**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | 不会 | 可能 | 可能 |
| Repeatable Read | 不会 | 不会 | 可能（MySQL InnoDB 通过间隙锁基本避免） |
| Serializable | 不会 | 不会 | 不会 |

**答案要点**
- 脏读：读到别的事务未提交的数据；不可重复读：同一事务两次读同一行结果不同（被他人提交的 update）；幻读：两次范围查询行数不同（被他人提交的 insert/delete）。
- MySQL InnoDB 默认 Repeatable Read；PostgreSQL、Oracle 默认 Read Committed。
- 级别越高并发越低。选择取决于业务：对账用高级别，日志写入用低级别。

**English short answer**
The four isolation levels are read uncommitted, read committed, repeatable read and serializable. They progressively prevent dirty reads, non-repeatable reads and phantom reads, at the cost of concurrency. A dirty read sees uncommitted data, a non-repeatable read sees a row change between two reads, and a phantom read sees new rows appear in a range.

**追问方向**：MVCC；快照读与当前读。

### Q12 MVCC 是什么？（MVCC）
**优先级：★★**

**答案要点**：多版本并发控制：每行保留多个历史版本（用事务 ID 和 undo 链），读操作按事务开始时的一致性快照（read view）读取合适版本，**读不阻塞写、写不阻塞读**。提高并发。写写冲突仍用锁。Read Committed 每条语句生成新快照，Repeatable Read 在事务第一次读时生成。

**English short answer**
Multi-version concurrency control keeps several versions of each row, and readers use a consistent snapshot, so readers do not block writers and writers do not block readers. Write-write conflicts are still handled by locks.

**追问方向**：undo 链；长事务的危害。

### Q13 数据库的锁：行锁、表锁、乐观锁、悲观锁？（Locks）
**优先级：★★**

**答案要点**：行锁粒度细并发高，表锁简单；共享锁（读）与排他锁（写）；意向锁；死锁：两个事务互相等待，数据库检测后回滚其一——预防：按固定顺序更新、缩短事务、走索引（无索引更新会锁全表/多行）。乐观锁：不加锁，更新时用版本号 `UPDATE ... WHERE id=? AND version=?` 检查影响行数；悲观锁：`SELECT ... FOR UPDATE`。冲突少用乐观，冲突多用悲观。

```sql
UPDATE task SET status='done', version=version+1
WHERE id=42 AND version=7;     -- 影响行数为 0 说明被别人改过
```

**English short answer**
Row locks give high concurrency, table locks are simpler. Pessimistic locking uses select for update to block others, while optimistic locking checks a version number at update time and retries if it changed. Deadlocks are detected by the database and avoided by updating rows in a consistent order and keeping transactions short.

**追问方向**：和 CAS 的类比；分布式锁。

### Q14 范式（Normalization）与反范式？（Normal forms）
**优先级：★★**

**答案要点**：1NF 列原子；2NF 非主属性完全依赖主键（消除部分依赖）；3NF 消除传递依赖。范式减少冗余和更新异常；但查询要多表 JOIN。实际常在读多的场景适度**反范式**（冗余字段、宽表）换性能；日志/时序数据常用宽表+时间分区。

**English short answer**
Normalization removes redundancy and update anomalies by making columns atomic and ensuring each attribute depends only on the key. In practice I may denormalize read-heavy data to avoid expensive joins.

**追问方向**：设计表的例子；外键。

## 四、NoSQL 与存储选型

### Q15 SQL 和 NoSQL 如何选择？（SQL vs NoSQL）
**优先级：★★★**

| 类型 | 代表 | 特点 | 场景 |
|---|---|---|---|
| 关系型 | MySQL、PostgreSQL、SQLite | 强一致、事务、JOIN | 订单、账户、配置 |
| 键值 | Redis | 内存、极快 | 缓存、会话、排行榜 |
| 文档 | MongoDB | 灵活 schema | 内容、事件日志 |
| 列式/宽列 | Cassandra、HBase | 高写入、水平扩展 | 海量写入 |
| 时序 | InfluxDB、TimescaleDB | 按时间压缩/聚合 | 遥测、监控 |
| 图 | Neo4j | 关系遍历 | 知识图谱 |
| 向量库 | FAISS、Milvus | 近似最近邻 | 检索增强（RAG） |

**答案要点**：没有银弹，按访问模式选：需要事务与复杂查询 → 关系型；高并发简单读写 → KV；海量时间序列 → 时序库；语义检索 → 向量库。SQLite 是嵌入式单文件库，适合机器人本地存储配置和小规模日志（零运维）。

**English short answer**
I choose by access pattern. Relational databases suit transactions and complex queries, key-value stores like Redis suit fast simple access and caching, document stores suit flexible schemas, time-series databases suit telemetry, and vector stores suit semantic search. SQLite is a good embedded choice on a robot.

**追问方向**：CAP 定理；最终一致性。

### Q16 CAP 定理与 BASE？（CAP and BASE）
**优先级：★★**

**答案要点**：分布式系统在网络分区（P）发生时，一致性（C）与可用性（A）只能二选一：CP（拒绝部分请求保一致，如 ZooKeeper）或 AP（继续服务但可能读到旧数据，如 Dynamo 风格）。无分区时可同时满足。BASE：基本可用、软状态、最终一致。机器人集群里的状态同步（P6 的 state synchronisation，CV）也会面临：网络断了，各设备是否继续按本地状态运行？通常选择本地安全优先（可用）+ 重连后再同步。

**English short answer**
CAP says that when a network partition happens, a distributed system must choose between consistency and availability. Many systems accept eventual consistency, where replicas converge after some time. In a robot fleet I would typically let each robot keep running safely on its local state during a disconnect and resynchronize when the link returns.

**追问方向**：Raft/Paxos 概述；幂等同步。

### Q17 Redis 的数据结构与持久化？（Redis）
**优先级：★★**

**答案要点**：单线程命令执行（网络 IO 在 6.0+ 可多线程），基于内存和 IO 多路复用，故很快。类型：String、Hash、List、Set、ZSet（跳表）、Bitmap、Stream、HyperLogLog。持久化：RDB（快照）、AOF（追加日志）。过期策略：惰性删除 + 定期删除；内存淘汰策略（LRU/LFU 等）。典型用途：缓存、分布式锁（`SET key val NX PX`）、限流、排行榜、轻量消息队列。

**English short answer**
Redis keeps data in memory and executes commands on a single thread with IO multiplexing, which makes it very fast. It offers strings, hashes, lists, sets and sorted sets, and persists data with snapshots or an append-only log. It is used for caching, rate limiting, leaderboards and simple locks.

**追问方向**：为什么单线程仍然快；缓存与数据库一致性。

## 五、缓存

### Q18 缓存的作用与常见策略？（Caching strategies）
**优先级：★★★**

**答案要点**
- 作用：用更快的存储挡住对慢存储的重复访问，降低延迟与后端压力。依据**局部性原理**。
- 读策略：**Cache-Aside**（旁路缓存，最常用）：读时先查缓存，未命中查库并回填；写时**先更新库，再删除缓存**。Read-Through / Write-Through / Write-Back（写回，性能高但可能丢数据）。
- 淘汰：LRU、LFU、FIFO、TTL。
- 命中率 = 命中次数 / 总请求；平均访问时间 $T = h\,t_c + (1-h)\,t_m$（教学：$h=0.9,\ t_c=1\,\text{ms},\ t_m=20\,\text{ms}$ → $0.9+2=2.9\,\text{ms}$）。

**English short answer**
A cache keeps frequently used data in a faster store to reduce latency and backend load, relying on locality. The most common pattern is cache-aside: read from the cache first, fill it from the database on a miss, and on writes update the database and then invalidate the cache. Eviction policies such as LRU and TTL keep it bounded.

**追问方向**：缓存与数据库一致性；多级缓存。

### Q19 缓存穿透、击穿、雪崩？（Cache penetration, breakdown, avalanche）
**优先级：★★★**

**答案要点**
- **穿透**：请求不存在的数据，缓存和库都没有，每次打到库。→ 缓存空值（短 TTL）、布隆过滤器、参数校验。
- **击穿**：某个热点 key 过期瞬间大量并发打库。→ 互斥锁/单飞（只让一个请求回源）、热点永不过期（后台异步更新）。
- **雪崩**：大量 key 同时过期，或缓存宕机。→ 过期时间加随机抖动、多级缓存、限流降级、缓存高可用（集群）。

**English short answer**
Penetration is when requests for non-existent keys always hit the database; I cache empty results or use a Bloom filter. Breakdown is when a hot key expires and many requests hit the database at once; I let only one request rebuild it. Avalanche is when many keys expire together or the cache goes down; I add random jitter to TTLs and use rate limiting and replicas.

**追问方向**：双写一致性；延迟双删。

### Q20 缓存与数据库如何保持一致？（Cache consistency）
**优先级：★★**

**答案要点**：无法做到强一致，目标是最终一致。常用：先更新库、再删缓存（Cache-Aside），极少数并发下仍可能不一致，可用**延迟双删**或订阅数据库变更日志（binlog）异步失效缓存；设置合理 TTL 兜底。

**English short answer**
Strong consistency between a cache and a database is expensive, so I aim for eventual consistency: update the database first, then delete the cache entry, with a TTL as a safety net. For stricter needs I invalidate through the database's change log.

**追问方向**：为什么删除而不是更新缓存。

## 六、消息队列

### Q21 消息队列解决什么问题？（Message queues）
**优先级：★★★**

**答案要点**：①**异步**（调用方不等待）；②**解耦**（生产者不关心消费者）；③**削峰填谷**（缓冲突发流量）；④可靠投递与重试。代价：系统复杂度、一致性（最终一致）、消息顺序与重复处理。代表：Kafka（高吞吐日志流，分区有序）、RabbitMQ（灵活路由，AMQP）、RocketMQ、MQTT broker（IoT）。机器人领域的 ROS topic / DDS 本质是发布订阅，但与 MQ 不同在于通常不持久化、低延迟、无中心 broker（DDS）。

**English short answer**
A message queue decouples producers from consumers, makes calls asynchronous, smooths traffic bursts and supports retries. The trade-offs are extra complexity and eventual consistency. Kafka is built for high-throughput streams, RabbitMQ for flexible routing, and MQTT for IoT devices; robot middleware such as DDS is also publish-subscribe but brokerless and low latency.

**追问方向**：Kafka 与 RabbitMQ 区别；ROS topic 与 MQ 对比。

### Q22 消息投递语义：至多一次、至少一次、恰好一次？（Delivery semantics）
**优先级：★★★**

**答案要点**：至多一次（可能丢，不重复）；至少一次（不丢，可能重复）；恰好一次（理想，代价高，通常由"至少一次 + 消费端幂等"实现）。**幂等**：同一消息处理多次结果相同（用唯一消息 ID 去重、数据库唯一约束、"设置为某值"而非"加一"）。机器人指令同理：急停命令应幂等，重复发送无害。

**English short answer**
At-most-once delivery can lose messages, at-least-once can duplicate them, and exactly-once is usually achieved as at-least-once delivery plus an idempotent consumer. Idempotency is the practical key: I deduplicate by message id or design operations so that applying them twice has the same effect.

**追问方向**：如何保证顺序；死信队列；事务消息。

### Q23 如何保证消息不丢、不重复、有序？（Reliability, duplicates, ordering）
**优先级：★★**

**答案要点**：不丢：生产端确认（ack）+ 重试；Broker 持久化与多副本；消费端处理成功后再手动 ack。不重复：消费端幂等。有序：全局有序代价高，通常只保证**分区/队列内有序**（按业务 key，如机器人 ID，路由到同一分区），单个消费者处理。积压处理：扩容消费者、批量消费、降级。

**English short answer**
To avoid loss I use acknowledgements, persistence and replication, and only ack after processing. To handle duplicates I make consumers idempotent. For ordering I route by a key such as the robot id so that related messages land in the same partition and are consumed in order.

**追问方向**：消息积压；Kafka 分区与消费组。

## 七、系统设计思路

### Q24 系统设计题的通用回答框架？（System design framework）
**优先级：★★★**

**答案要点**：按步骤，边说边与面试官确认：
1. **澄清需求**：功能需求（做什么）、非功能需求（规模、延迟、可用性、一致性、成本）。
2. **估算量级**（back-of-envelope）：QPS、数据量、带宽、存储。
3. **接口与数据模型**：API、表结构。
4. **高层架构图**：客户端 → 接入 → 服务 → 缓存/队列 → 存储。
5. **深入关键组件**：瓶颈在哪、怎么扩展。
6. **权衡与故障**：单点、重试、降级、监控。
7. **演进**：先做简单可用版，再优化。
口头禅：先说假设，再说取舍（trade-off），不要一上来就堆组件。

**English short answer**
I start by clarifying functional and non-functional requirements, then estimate the scale: requests per second, data volume and storage. Next I define APIs and the data model, sketch a high-level architecture, and dive into the bottleneck components. I finish with trade-offs, failure handling and how the design would evolve. I state my assumptions out loud.

**追问方向**：如何估算；如何水平扩展；单点故障。

### Q25 常用估算数字与手算示例？（Back-of-envelope estimation）
**优先级：★★**

**答案要点**：常用：1 天 = 86400 s ≈ $10^5$ s；1 年 ≈ $3\times10^7$ s；内存访问 ~100 ns，SSD 随机读 ~100 μs，机械盘寻道 ~10 ms，同机房往返 ~0.5 ms，跨洲往返 ~100+ ms（量级数字）。

教学示例（假设数值，非项目数据）：100 台机器人，每台每秒产生 1 条 200 字节的遥测。
- 写入速率：$100\times 200\,\text{B/s}=20\,\text{KB/s}$。
- 每天：$20\,\text{KB/s}\times 86400 \approx 1.7\,\text{GB/天}$（$20\times10^3\times 86400=1.728\times10^9$）。
- 一年：约 $1.728\times365\approx 630\,\text{GB}$（未压缩，不含索引）。
结论：单机数据库即可承受，但需要按时间分区、保留策略与降采样。

**English short answer**
I use round numbers: a day is about 10 to the fifth seconds. For example, with a hypothetical 100 robots each sending a 200-byte message per second, the write rate is 20 kilobytes per second, about 1.7 gigabytes a day and around 630 gigabytes a year before compression. That fits on one machine, but needs time partitioning and a retention policy.

**追问方向**：峰值系数；副本倍数。

### Q26 设计一个机器人数据记录 / 日志系统。（Design: robot telemetry and logging system）
**优先级：★★★**

**题目背景**：多台机器人在现场运行，需要记录传感器数据、控制状态和事件，用于回放、调试和分析（教学设计题，非项目实现）。

**答案要点**

1. **需求**
   - 功能：本地高频记录（IMU、控制量、电机电流等），事件日志（模式切换、故障），事后上传并查询、回放。
   - 非功能：不影响实时控制（最重要）；断电不丢太多；存储有限；网络间断；可追溯（时间戳统一）。

2. **分层架构**

```text
 控制线程 --无锁SPSC队列--> 记录线程(低优先级) --批量--> 本地存储(环形文件/SQLite)
                                                        |
                                           网络可用时 | 压缩 + 断点上传
                                                        v
                                   接入服务 --> 消息队列(Kafka/MQTT) --> 存储
                                                        |
                                    时序库(热: 近期) + 对象存储(冷: 原始文件) --> 查询/回放/可视化
```

3. **关键设计点**
   - **不干扰控制**：控制线程只把固定大小的记录结构 push 进预分配的无锁队列，满则丢最旧并计数；记录线程负责格式化与写盘（见 [并发多线程与实时系统八股](./07_并发多线程与实时系统八股.md) 的 SPSC 队列）。
   - **统一时间戳**：每条记录带单调时钟（用于间隔）和墙钟/同步时间（用于跨机对齐）；记录坐标系/帧信息，与 CV 中 P6 的"timestamps, coordinate frames and validity checks"一致。
   - **数据格式**：高频数值用二进制 + 固定 schema（如 rosbag/MCAP 或自定义帧），带版本号；事件日志用结构化 JSON。
   - **分级与降采样**：全量（1 kHz 级）只保留短窗口 + 触发式保留（故障前后 N 秒，类似"黑匣子"）；长期保存降采样后的指标。
   - **本地存储**：环形缓冲式文件按大小/时间切片，防写满；掉电保护：定期 `fsync`，分片文件 + 索引。
   - **上传**：断点续传、幂等（分片带序号/哈希）、带宽限速；先传摘要，需要时再拉原始文件。
   - **存储与查询**：近期数据放时序库（按 `robot_id + 时间` 分区、索引），元数据（运行 ID、版本、硬件）放关系库；冷数据放对象存储，按生命周期删除。
   - **可观测**：丢帧计数、队列水位、磁盘占用、上传延迟本身也被监控。
   - **安全**：设备鉴权、传输加密、访问控制。

4. **取舍**：记录越多越有助于调试，但占 IO/存储并可能影响实时性——以"不影响控制"为底线，用触发式记录折中。

**English short answer**
I would keep logging completely off the real-time path: the control loop pushes fixed-size records into a preallocated lock-free queue, and a low-priority thread batches them to local storage using rotating files. Every record carries a monotonic timestamp and synchronized time, and I keep a short window of full-rate data around faults, while downsampling for long-term storage. When the network is available the files are uploaded in resumable chunks, indexed by robot id and time in a time-series database, with raw files in object storage. I would also monitor dropped records and disk usage, because the logging system itself can fail.

**追问方向**：数据量怎么估；怎么回放；怎么保证时间对齐；掉电怎么办。

### Q27 设计一个机器人设备状态与任务管理服务。（Design: robot state and task service）
**优先级：★★**

**题目背景**：服务端要查看多台机器人的在线状态、下发任务、记录执行结果（教学设计题；CV 中 P6 描述了设备发现、能力注册、状态同步、任务分发与"action-proposal → policy-check → execution → state-feedback"链，P4 描述了 Agent 决策与设备执行，本题只用其思想，不代表其实现）。

**答案要点**

1. **核心实体**：`robot`（id、能力、版本）、`state`（最新状态+时间戳+有效位）、`task`（id、类型、参数、状态机：created → queued → dispatched → running → succeeded/failed/cancelled）、`event`（审计日志）。

2. **关键流程**
   - 设备上线：注册能力 + 心跳；超时判离线。
   - 任务下发：服务端写任务（状态 queued）→ 经消息队列/长连接推送 → 设备 ack → 设备执行并上报状态 → 服务端更新。
   - **安全链**：任务先成为"提案"，经**策略检查**（权限、状态是否允许、限值）后才下发；设备端再做本地检查，执行器不直接信任网络命令。每一步记入事件日志，便于追溯。

3. **关键设计点**
   - **幂等**：任务带唯一 ID，设备重复收到同一任务不重复执行；命令用"目标状态"表达。
   - **状态存储**：最新状态放内存/Redis（读多写多），历史放时序库，任务和审计放关系库（事务保证状态机转换合法，乐观锁防并发改状态）。
   - **断线处理**：设备断线后保持本地安全行为；重连后对账（服务端对比任务状态，补发或取消）。
   - **扩展**：按 `robot_id` 分区；无状态接入层水平扩展。
   - **一致性**：任务状态以服务端为准，设备状态以设备上报为准（单一事实来源）。

4. **取舍**：强一致带来延迟与复杂度；机器人场景倾向"本地安全优先 + 最终一致 + 可追溯"。

**English short answer**
The core entities are robots, their latest state, tasks with an explicit state machine, and an event log. A task is first a proposal, checked against policy before being dispatched, and the robot also checks it locally before acting. Tasks carry unique ids so redelivery is harmless. Latest state lives in memory or a cache, history in a time-series store, and task and audit records in a relational database with transactional state transitions. If a robot disconnects it keeps running safely on its local state and reconciles with the server after reconnecting.

**追问方向**：任务状态机非法转换如何防；心跳间隔选择；重复下发。

### Q28 限流、降级、熔断是什么？（Rate limiting, degradation, circuit breaker）
**优先级：★★**

**答案要点**：限流：控制请求速率，算法有令牌桶（允许突发）、漏桶（平滑）、滑动窗口。降级：压力大时关闭非核心功能，保核心。熔断：下游持续失败时快速失败，避免拖垮调用方，一段时间后半开试探恢复。重试要带指数退避+抖动，并保证幂等。

```python
# 教学示例: 令牌桶
import time
class TokenBucket:
    def __init__(self, rate, cap): self.rate, self.cap = rate, cap; self.t = cap; self.ts = time.monotonic()
    def allow(self):
        now = time.monotonic(); self.t = min(self.cap, self.t + (now - self.ts) * self.rate); self.ts = now
        if self.t >= 1: self.t -= 1; return True
        return False
```

**English short answer**
Rate limiting caps request rates, commonly with a token bucket that allows short bursts. Degradation turns off non-essential features under load, and a circuit breaker fails fast when a downstream service keeps failing, then probes for recovery. Retries should use exponential backoff and idempotent operations.

**追问方向**：令牌桶 vs 漏桶；重试风暴。

### Q29 如何设计一个短链接 / 键值存储 / 排行榜这类经典题？思路模板？（Classic system design patterns）
**优先级：★**

**答案要点**：套用框架。短链接：ID 生成（自增 + base62 编码 / 雪花 ID）、KV 存储、缓存热点、301/302 跳转。KV 存储：哈希分片 + 一致性哈希、副本、WAL + LSM 树。排行榜：Redis ZSet（跳表）。这类题考察框架与取舍，不是背答案。

**English short answer**
For classic questions I reuse the same framework. A URL shortener needs unique ID generation encoded in base62, a key-value store with caching for hot links, and a redirect. A leaderboard fits a sorted set in Redis. The point is to show structured reasoning and trade-offs.

**追问方向**：一致性哈希；LSM 树。

### Q30 一致性哈希是什么？（Consistent hashing）
**优先级：★★**

**答案要点**：把节点和 key 都哈希到一个环上，key 归属顺时针第一个节点；增删节点只影响相邻区间的 key（平均 $1/n$），而取模 `hash % n` 会导致几乎全部 key 重新映射。用虚拟节点解决负载不均。应用：缓存集群、分布式存储分片。

**English short answer**
Consistent hashing places both nodes and keys on a ring, and each key belongs to the next node clockwise. When a node is added or removed only a small fraction of keys move, unlike modulo hashing where nearly everything moves. Virtual nodes balance the load.

**追问方向**：虚拟节点数量；热点。

### Q31 SQLite 在机器人上怎么用？有什么注意点？（SQLite on robots）
**优先级：★★**

**答案要点**：单文件嵌入式数据库，无服务进程，适合保存配置、标定参数、任务历史、小规模日志。注意：①开启 `WAL` 模式（`PRAGMA journal_mode=WAL`）提高并发读写；②写入批量放进事务（逐条提交每次 `fsync` 很慢）；③写满磁盘与掉电：定期检查、备份；④多进程写入要处理 `database is locked`（设置 busy timeout）；⑤高频原始数据不适合，用二进制日志文件。

```python
import sqlite3
con = sqlite3.connect("robot.db", timeout=5)
con.execute("PRAGMA journal_mode=WAL")
con.execute("CREATE TABLE IF NOT EXISTS events(ts REAL, level TEXT, msg TEXT)")
with con:                       # 事务批量提交
    con.executemany("INSERT INTO events VALUES (?,?,?)", rows)
```

**English short answer**
SQLite is a serverless, single-file database that is great for configuration, calibration parameters and task history on a robot. I enable write-ahead logging, batch inserts inside transactions to avoid a sync per row, and set a busy timeout for concurrent writers. For high-rate raw data I use binary log files instead.

**追问方向**：WAL 原理；并发限制。

### Q32 SQL 注入是什么？如何防御？（SQL injection）
**优先级：★★**

**答案要点**：把用户输入拼接进 SQL 导致输入被当作命令，如 `' OR '1'='1`。防御：**参数化查询/预编译语句**（占位符），不拼接字符串；最小权限账号；输入校验；ORM。对 Agent/LLM 应用同理：LLM 生成的内容不可信，不能直接拼进 SQL 或系统命令，要经过校验层——与 CV 中 P6 / PS 的"高层计划不能直接下发执行，须经 policy-check"思想相通。

```python
cur.execute("SELECT * FROM users WHERE name = ?", (name,))   # 正确
# cur.execute(f"SELECT * FROM users WHERE name = '{name}'")  # 错误: 注入风险
```

**English short answer**
SQL injection happens when user input is concatenated into a query and interpreted as SQL. The defence is parameterized queries, least-privilege accounts and input validation. The same principle applies to LLM output: it is untrusted input that must be validated before it reaches a database or a robot.

**追问方向**：XSS、CSRF；ORM 是否绝对安全。

## 本章要点速记
1. SQL 逻辑执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。
2. 索引用 B+ 树；最左前缀；函数/类型转换/前导通配符使索引失效；用 `EXPLAIN` 检查。
3. ACID：原子（undo）、一致、隔离（锁/MVCC）、持久（WAL）。
4. 隔离级别：读未提交 → 读已提交 → 可重复读 → 串行化，对应脏读 / 不可重复读 / 幻读。
5. 选型按访问模式：关系型、KV、文档、时序、向量。
6. 缓存：Cache-Aside，穿透（布隆/空值）、击穿（互斥）、雪崩（TTL 抖动）。
7. 消息队列：异步、解耦、削峰；至少一次 + 幂等 ≈ 恰好一次。
8. 系统设计：需求 → 估算 → 接口/数据 → 架构 → 瓶颈 → 取舍。
9. 机器人日志系统：不干扰控制、统一时间戳、触发式记录、降采样、断点上传。
