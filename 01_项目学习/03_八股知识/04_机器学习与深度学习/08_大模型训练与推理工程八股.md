## 一、训练的算力与显存估算

### Q1 如何估算训练一个模型的 FLOPs 与时间？（Training FLOPs estimation）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 经验公式：训练总 FLOPs $\approx6ND$（$N$ 参数量，$D$ 训练 token 数）。前向约 $2N$ FLOPs/token，反向约 $4N$。
- 例（教学）：7B 模型、1T token → $6\times7\times10^9\times10^{12}=4.2\times10^{22}$ FLOPs。
- 时间 $\approx\dfrac{6ND}{\text{GPU 数}\times\text{单卡峰值}\times\mathrm{MFU}}$；MFU（模型 FLOPs 利用率）大模型训练常见 30%–55%（量级，未核对）。若 1024 张峰值 300 TFLOPs（BF16 量级）的卡、MFU 40%：$4.2\times10^{22}/(1024\times3\times10^{14}\times0.4)\approx3.4\times10^5$ s ≈ 4 天。
- 带激活重计算时实际算力约 $8ND$，MFU 要区分"模型 FLOPs"与"硬件 FLOPs"。
- 用途：预算评估、选择模型规模 / 数据量（Chinchilla 式 $D\approx20N$ 的算力最优点，经验值）。

**English short answer**
Training cost is roughly six times parameters times tokens in FLOPs: two for the forward pass and four for the backward pass per token. Dividing by cluster peak throughput times model FLOPs utilization, typically thirty to fifty percent, gives wall-clock time. Activation recomputation raises the hardware FLOPs to about eight times parameters times tokens. This lets me budget runs and choose model and data size.

（译：训练总 FLOPs 约为 6×参数量×token 数（每 token 前向 2、反向 4）；除以集群峰值算力乘 MFU（通常 30%～50%）得挂钟时间；激活重计算使硬件 FLOPs 约为 8ND；据此做预算并选择模型与数据规模。）

**追问方向**：MFU 与 HFU 的区别；Chinchilla 最优的含义。

### Q2 训练时的显存都花在哪里？怎么估算？（Training memory breakdown）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 四大块：**参数、梯度、优化器状态、激活**。
- 混合精度 + Adam 的经验：每个参数约 **16 字节**（FP16/BF16 参数 2 + 梯度 2 + FP32 主权重 4 + Adam 一阶矩 4 + 二阶矩 4）。例：7B 模型 ≈ $7\times10^9\times16=112$ GB（未含激活）——单卡 80 GB 放不下，需要并行 / 分片。
- 激活显存与 batch、序列长度、层数、隐层维度成正比（带注意力 $O(s^2)$，FlashAttention 后为线性）；用**激活重计算**可显著降低，代价约 +33% 计算。
- 其他：通信缓冲、临时张量、碎片、框架开销（留 10%–20% 余量）。
- 优化：ZeRO / FSDP 分片、BF16/FP8、8-bit 优化器、梯度检查点、CPU / NVMe offload。

**English short answer**
Memory goes to parameters, gradients, optimizer states and activations. With mixed precision and Adam, a rule of thumb is sixteen bytes per parameter, so a 7B model needs over a hundred gigabytes before activations, which does not fit on one 80 GB GPU. Activations scale with batch size and sequence length and can be reduced by recomputation, and sharding the states with ZeRO or FSDP spreads the rest across GPUs.

（译：显存用于参数、梯度、优化器状态和激活；混合精度加 Adam 经验上每参数约 16 字节，7B 模型未含激活就需 100 多 GB，单张 80 GB 卡放不下；激活随批大小与序列长度增长，可用重计算降低，用 ZeRO/FSDP 分片把其余状态分摊到多卡。）

**追问方向**：16 字节的拆分；激活重计算的代价。

### Q3 梯度累积与有效批大小？（Gradient accumulation）
**优先级：★★★** · 对应基础知识：[神经网络与反向传播](../../02_基础知识/10_机器学习与深度学习/02_神经网络与反向传播.md)

**答案要点**
- 显存放不下大批量时，把一个大 batch 拆成 $k$ 个微批，依次前向反向并累加梯度，$k$ 次后再更新一次参数：有效批大小 $=$ 微批 × 累积步数 × 数据并行度。
- 注意：损失要除以累积步数（或使用 sum 归约并相应缩放）以保持梯度尺度；BatchNorm 统计量只对微批有效（LLM 用 LayerNorm 无此问题）；分布式时只在最后一个微批同步梯度（`no_sync`），避免重复通信。
- 学习率应按有效批大小调整（线性或平方根缩放经验，需验证）。
- 与激活显存：激活按微批大小计，故累积能以时间换显存。

**English short answer**
Gradient accumulation runs several micro-batches, adding their gradients before one optimizer step, so the effective batch size is micro-batch times accumulation steps times data-parallel degree. I scale the loss accordingly, skip gradient synchronization on all but the last micro-batch, and adjust the learning rate for the effective batch size. It trades time for memory because activations depend only on the micro-batch.

（译：梯度累积运行多个微批并累加梯度后才更新一次，有效批大小为微批×累积步数×数据并行度；需相应缩放损失、除最后一个微批外跳过梯度同步，并按有效批大小调整学习率；它以时间换显存，因为激活只取决于微批。）

**追问方向**：为何要 `no_sync`；有效批大小与学习率的关系。

### Q4 数据并行（DDP）的原理与通信开销？（Data parallelism）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 每张卡有完整模型副本，处理不同数据切片；反向后用 **All-Reduce** 对梯度求平均，各卡同步更新，保持参数一致。
- 通信量：每步每卡约 $2\times$ 参数字节（Ring All-Reduce 的带宽最优特性：与卡数几乎无关）。DDP 把梯度分桶（bucket），与反向计算**重叠**通信。
- 限制：每卡需放得下完整模型 + 优化器状态；模型大时显存不够。
- 扩展性：批大小随卡数增大，需调学习率；通信受互联带宽（NVLink、InfiniBand）限制。
- 对比参数服务器：同步 All-Reduce 在现代集群更主流。

**English short answer**
In data parallelism every GPU holds a full model replica and processes a different slice of data, then gradients are averaged with an all-reduce so replicas stay identical. Ring all-reduce moves about twice the parameter size per step regardless of the GPU count, and DDP overlaps it with backward computation by bucketing. It requires the full model and optimizer state to fit on each GPU, which is the limitation sharding addresses.

（译：数据并行中每卡持有完整模型副本、处理不同数据，反向后用 All-Reduce 平均梯度保持副本一致；Ring All-Reduce 每步传输量约为参数大小的两倍且与卡数无关，DDP 通过分桶把通信与反向计算重叠；每卡需放下完整模型和优化器状态，这正是分片要解决的限制。）

**追问方向**：Ring All-Reduce 的步骤；梯度分桶的作用。

### Q5 ZeRO 的三个阶段与 FSDP 是什么关系？（ZeRO and FSDP）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 数据并行中各卡冗余保存优化器状态、梯度、参数。**ZeRO** 把它们沿数据并行维度分片：**Stage 1** 分片优化器状态（显存 ≈ 4× 节省）；**Stage 2** 再分片梯度（≈ 8×）；**Stage 3** 再分片参数（随卡数线性下降），前向 / 反向时按需 All-Gather 参数、用后释放。
- 通信：Stage 1/2 与 DDP 相近；Stage 3 增加参数 All-Gather（约 1.5× 通信量）。
- **FSDP**（PyTorch）实现与 ZeRO-3 同样的思想（Fully Sharded Data Parallel），按层包装（wrap）分片，可混合精度、CPU offload；DeepSpeed ZeRO 是另一实现。
- 选择：显存不足 → ZeRO-3 / FSDP；通信带宽弱 → 更低阶段或结合 TP/PP；超大规模常 FSDP + TP + PP。
- 注意：分片使单步检查点保存 / 加载更复杂（分片 checkpoint、合并）。

**English short answer**
ZeRO removes the redundancy of data parallelism by sharding optimizer states in stage one, gradients in stage two and the parameters themselves in stage three, gathering parameters just in time per layer. FSDP in PyTorch implements the same idea as ZeRO-3. Memory per GPU falls roughly linearly with GPU count at the cost of extra all-gather communication, so I combine it with tensor or pipeline parallelism on very large models.

（译：ZeRO 通过分片消除数据并行的冗余：阶段 1 分片优化器状态，阶段 2 加梯度，阶段 3 连参数也分片并逐层按需聚合；PyTorch 的 FSDP 实现与 ZeRO-3 相同的思想；单卡显存随卡数近线性下降，代价是额外的 All-Gather 通信，超大模型常与张量/流水线并行组合。）

**追问方向**：ZeRO-3 的通信量分析；FSDP 的 wrap 策略。

### Q6 张量并行（TP）的做法？（Tensor parallelism）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 把单层内的矩阵乘拆到多卡。MLP：第一层权重**按列切**（每卡算一部分隐层，激活函数本地做），第二层**按行切**，输出做一次 **All-Reduce** 求和；注意力：按**头**切分，输出投影按行切再 All-Reduce（Megatron-LM 风格）。
- 每个 Transformer 层前向 / 反向各约 2 次 All-Reduce，通信频繁且位于关键路径 → 需要**高带宽低延迟互联**（单节点内 NVLink）；通常 TP 度数 ≤ 单节点 GPU 数（如 8）。
- 优点：降低单卡参数与激活显存，可加速单层计算；缺点：通信开销、实现复杂、需要张量维度整除。
- 序列并行（SP）：与 TP 配合，把 LayerNorm/Dropout 的激活沿序列维切分，进一步省显存。

**English short answer**
Tensor parallelism splits the matrices inside a layer across GPUs: the first MLP weight by columns and the second by rows with one all-reduce, and attention by heads. Each layer needs a couple of all-reduces on the critical path, so TP is usually confined to GPUs within one node over NVLink. It reduces per-GPU parameters and activations but costs communication, and sequence parallelism extends the sharding to normalization and dropout activations.

（译：张量并行把层内矩阵拆到多卡：MLP 第一层按列切、第二层按行切并做一次 All-Reduce，注意力按头切分；每层关键路径上有若干次 All-Reduce，因此 TP 通常限制在单节点内经 NVLink 进行；降低单卡参数与激活显存但付出通信代价，序列并行把分片扩展到归一化和 dropout 的激活。）

**追问方向**：为何第一层按列、第二层按行；TP 为何不跨节点。

### Q7 流水线并行（PP）与气泡（bubble）问题？（Pipeline parallelism）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 把模型按层切成若干**阶段（stage）**放在不同卡上，数据以微批形式在流水线中流动。只需在阶段边界传激活（点对点通信，量小），适合跨节点。
- **气泡**：流水线开头 / 结尾有设备空闲；朴素 GPipe 调度气泡占比 $\approx\dfrac{p-1}{m+p-1}$（$p$ 阶段数，$m$ 微批数）→ 微批数要远大于阶段数。
- 调度：**1F1B**（一前一反交替，降低激活驻留）、interleaved 1F1B（每卡多个小阶段，进一步缩小气泡，增加通信）、zero-bubble 类。
- 缺点：负载均衡（各阶段计算量需接近）、复杂度高、与 BatchNorm 类不兼容（LLM 不涉及）；激活存储随在途微批数增加。
- 组合：节点内 TP、节点间 PP、整体 DP（3D 并行）。

**English short answer**
Pipeline parallelism assigns consecutive groups of layers to different devices and streams micro-batches through them, communicating only boundary activations point to point, which suits cross-node links. The bubble fraction is roughly stages minus one over micro-batches plus stages minus one, so I use many micro-batches and schedules like 1F1B or interleaved 1F1B. The challenge is balancing stage compute and managing activation memory.

（译：流水线并行把相邻层组分配到不同设备并让微批流过，只需点对点传递边界激活，适合跨节点；气泡占比约 $\frac{p-1}{m+p-1}$，所以用大量微批和 1F1B/交错 1F1B 调度；难点是各阶段计算均衡与激活显存管理。）

**追问方向**：气泡公式的推导；1F1B 为什么省显存。

### Q8 3D 并行（DP × TP × PP）如何组合？（3D parallelism）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 组合原则按通信强度与互联层级匹配：**TP（通信最频繁）放在同节点 NVLink 内**；**PP 跨节点**（只传边界激活）；**DP / FSDP** 在最外层，对梯度做 All-Reduce / ReduceScatter。总卡数 $=\mathrm{TP}\times\mathrm{PP}\times\mathrm{DP}$。
- 例（教学）：1024 卡，TP=8（单机）、PP=8、DP=16。
- 加上序列 / 上下文并行（长序列）与专家并行（MoE）形成 4D / 5D。
- 选择流程：先用最小的并行度使模型"放得下"；再用 DP 扩吞吐；调整微批大小使气泡与通信可接受；用 profiler 验证。
- 实用框架：Megatron-LM、DeepSpeed、PyTorch FSDP + TP、Colossal-AI、TorchTitan 等（版本与功能未核对）。

**English short answer**
I map the most communication-hungry dimension to the fastest links: tensor parallelism inside a node over NVLink, pipeline parallelism across nodes where only boundary activations move, and data or FSDP parallelism outermost for gradient synchronization. The product of the three degrees equals the GPU count. I pick the smallest model-parallel degrees that make the model fit, scale throughput with data parallelism, and verify with a profiler.

（译：把通信最密集的维度映射到最快的链路：张量并行在节点内走 NVLink，流水线并行跨节点（只传边界激活），数据/FSDP 并行在最外层同步梯度；三者度数之积等于 GPU 数；先用最小的模型并行度让模型放得下，再用数据并行扩吞吐，并用 profiler 验证。）

**追问方向**：如何决定 TP、PP 度数；拓扑感知映射。

### Q9 集合通信原语（All-Reduce、All-Gather、Reduce-Scatter）是什么？（Collective communication）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- **All-Reduce**：每卡数据求和（或平均）后所有卡得到相同结果（梯度同步）；**All-Gather**：每卡拿到所有卡数据的拼接（FSDP 聚合参数）；**Reduce-Scatter**：先求和再把结果分片给各卡（FSDP 的梯度）；**All-to-All**：每卡向其他每卡发不同数据（MoE 专家路由、序列并行转换）；Broadcast：一卡到所有卡。
- 关系：All-Reduce = Reduce-Scatter + All-Gather。
- Ring 算法：每卡发送 $2\frac{p-1}{p}S$ 字节，几乎与 $p$ 无关（带宽最优），延迟 $O(p)$；树形 / 双二叉树降低延迟。
- 实现：NCCL（NVIDIA GPU）；性能看拓扑（NVLink/NVSwitch、PCIe、InfiniBand/RoCE）。
- 估算：通信时间 ≈ 数据量 / 有效带宽 + 延迟项。

**English short answer**
All-reduce sums data across GPUs and gives everyone the result, all-gather concatenates every GPU's shard on all GPUs, reduce-scatter sums and distributes shards, and all-to-all exchanges distinct data between every pair, as in MoE routing. All-reduce equals reduce-scatter followed by all-gather. Ring algorithms are bandwidth-optimal with traffic nearly independent of GPU count. NCCL implements them and performance depends on the interconnect topology.

（译：All-Reduce 在各卡间求和并让所有卡得到结果，All-Gather 让每卡获得所有分片的拼接，Reduce-Scatter 先求和再分发分片，All-to-All 在每对卡间交换不同数据（如 MoE 路由）；All-Reduce = Reduce-Scatter + All-Gather；Ring 算法带宽最优、流量几乎与卡数无关；NCCL 实现它们，性能取决于互联拓扑。）

**追问方向**：为什么 Ring All-Reduce 带宽最优；All-to-All 在 MoE 中的开销。

### Q10 如何隐藏通信延迟（计算–通信重叠）？（Overlapping communication and computation）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 原理：GPU 上计算与 NCCL 通信可使用不同 CUDA 流并行执行；反向传播中，后面层的梯度先算完就可立刻开始 All-Reduce，同时继续计算前面层。
- 技术：DDP 梯度分桶异步通信；FSDP 的预取（prefetch，下一层参数 All-Gather 与当前层计算重叠）；TP 的分块矩阵乘与通信流水（分块 GEMM + All-Reduce 重叠）；PP 的异步 P2P；梯度累积边界。
- 限制：通信量太大 / 带宽不足时无法完全隐藏；SM 资源与带宽竞争；需 profiler（Nsight、PyTorch Profiler）检查时间线上是否真的重叠。
- 度量：通信暴露时间（exposed communication）占步时间比例。

**English short answer**
Computation and communication can run on separate CUDA streams, so gradients of later layers start their all-reduce while earlier layers are still computing. DDP buckets gradients, FSDP prefetches the next layer's parameters, and tensor-parallel GEMMs can be chunked to pipeline with communication. I confirm the overlap in a profiler timeline and track exposed communication time as a fraction of step time.

（译：计算与通信可在不同 CUDA 流上并行，后面层的梯度算完即可开始 All-Reduce，同时前面层继续计算；DDP 梯度分桶、FSDP 预取下一层参数、TP 的 GEMM 分块与通信流水；在 profiler 时间线上确认重叠，并跟踪暴露的通信时间占步时间的比例。）

**追问方向**：为什么重叠仍有开销；如何读 profiler 时间线。

### Q11 激活重计算（gradient checkpointing）的权衡？（Activation recomputation）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 反向传播需要前向的激活；重计算只保存部分"检查点"（如每层输入），反向时重新计算被丢弃的中间激活，**用约 33% 额外算力换取激活显存大幅下降**（从随层数线性到约 $\sqrt{L}$ 或每层常数级）。
- 选择性重计算：只重算便宜但占显存大的部分（如注意力的 softmax 中间量、MLP 激活），保留昂贵的 GEMM 输出，效率更高。
- 与 FlashAttention 配合：注意力的 $O(s^2)$ 中间量本来就不存储，反向重新计算。
- 使用：长序列、大批量时几乎必开；`torch.utils.checkpoint`、DeepSpeed activation checkpointing。
- 注意：随机性（Dropout）需保存 RNG 状态以保证重算一致。

**English short answer**
Activation recomputation stores only selected checkpoints and recomputes the discarded intermediates during the backward pass, trading about a third more compute for a large cut in activation memory. Selective recomputation targets cheap but memory-heavy parts such as attention internals. It is almost always on for long sequences and large batches, and the random number generator state must be preserved so dropout is reproduced exactly.

（译：激活重计算只保存部分检查点，反向时重算被丢弃的中间量，以约三分之一的额外算力换取激活显存的大幅下降；选择性重计算针对注意力内部等便宜但占显存的部分；长序列和大批量时几乎必开，并需保存随机数状态以精确复现 dropout。）

**追问方向**：为什么保存的是 $\sqrt{L}$ 个检查点最优；选择性重计算保留哪些张量。

### Q12 序列并行与上下文并行（长上下文训练）？（Sequence and context parallelism）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 长序列时激活与注意力是瓶颈。**序列并行（SP，Megatron 意义）**：在 TP 基础上把 LayerNorm / Dropout 等不被 TP 切分的部分沿序列维切到各卡，省激活显存，通信由 All-Reduce 变为 Reduce-Scatter + All-Gather（总量不变）。
- **上下文并行（CP）/ Ring Attention / Ulysses**：把序列沿长度维分到多卡，注意力计算时用环形传递 K/V 块（Ring Attention）或在头维度做 All-to-All（DeepSpeed-Ulysses），使上下文长度随卡数线性扩展。
- 取舍：Ring Attention 通信可与计算重叠、对序列长度扩展好；Ulysses 受头数限制。
- 与推理：长上下文推理同样需要拆分 KV cache。

**English short answer**
Sequence parallelism, paired with tensor parallelism, shards the activations of layer norm and dropout along the sequence dimension to save memory. Context parallelism splits the sequence itself across GPUs: Ring Attention passes key-value blocks around a ring overlapped with computation, and Ulysses uses all-to-all over heads. Both let the context length scale with GPU count, and Ulysses is limited by the number of attention heads.

（译：序列并行与张量并行配合，把层归一化和 dropout 的激活沿序列维分片以省显存；上下文并行把序列本身分到多卡：Ring Attention 环形传递 K/V 块并与计算重叠，Ulysses 在头维度做 All-to-All；二者都使上下文长度随卡数扩展，Ulysses 受注意力头数限制。）

**追问方向**：Ring Attention 的在线 softmax；因果掩码下的负载均衡。

### Q13 MoE 训练中的专家并行与负载均衡？（Expert parallelism for MoE）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- MoE 层有 $E$ 个专家，每个 token 由门控选 top-k 专家；参数量大但每 token 激活参数少。**专家并行（EP）**把不同专家放在不同卡，token 通过 **All-to-All** 发送到对应专家再收回，通信是主要开销。
- 负载均衡：门控倾向少数专家（"赢者通吃"）导致部分卡过载 / 专家坍缩 → 加辅助均衡损失（auxiliary loss）、专家容量（capacity factor，超出丢弃或溢出）、无辅助损失的偏置调整方法。
- 稳定性：路由 logits 的 z-loss、路由噪声、FP32 路由。
- 推理：专家并行 / 专家卸载，批次小时专家利用率低。
- 与 3D 并行组合：EP 常与 DP/TP 交织（EP 度数 ≤ 专家数）。

**English short answer**
In an MoE layer each token is routed to a few experts, so total parameters are large but activated parameters per token are small. Expert parallelism places experts on different GPUs and uses all-to-all to dispatch and gather tokens, which dominates communication. Routing tends to collapse onto a few experts, so training adds auxiliary balancing losses, expert capacity limits and stabilizers like router z-loss and FP32 routing.

（译：MoE 层中每个 token 被路由到少数专家，总参数大但每 token 激活参数少；专家并行把专家放在不同卡，用 All-to-All 分发与收集 token，是主要通信开销；路由易坍缩到少数专家，训练需辅助均衡损失、专家容量限制以及 router z-loss、FP32 路由等稳定手段。）

**追问方向**：容量因子的取舍；MoE 推理为何难。

### Q14 训练中 loss spike（损失突刺）怎么处理？（Loss spikes）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 成因：学习率过高、Adam 二阶矩估计在罕见数据下异常、坏数据（异常长序列 / 乱码 / 重复）、数值溢出（FP16）、注意力 logits 过大、梯度范数突变。
- 排查：看梯度范数与 loss 曲线是否同时突刺；回溯对应批次数据；检查混合精度溢出计数、NaN/Inf。
- 缓解：梯度裁剪（全局范数 1.0 量级）、降低学习率 / 更长预热、BF16 替代 FP16、QK-Norm / logit soft-capping、调高 Adam $\epsilon$ 或降低 $\beta_2$、数据清洗与批次跳过、权重衰减调整。
- 应急：回滚到突刺前的 checkpoint，**跳过出问题的数据批次**重训；保存频繁 checkpoint。
- 监控：梯度范数、参数范数、每层激活统计、学习率、吞吐。

**English short answer**
Spikes come from too high a learning rate, unstable second-moment estimates, bad data batches, overflow in low precision or exploding attention logits. I check whether gradient norm spikes with the loss and trace the offending batch, then mitigate with gradient clipping, longer warm-up, BF16, QK-norm, tuned Adam betas and data cleaning. In an emergency I roll back to an earlier checkpoint and skip the bad batches.

（译：损失突刺源于学习率过高、二阶矩估计不稳、坏数据批次、低精度溢出或注意力 logits 爆炸；检查梯度范数是否与 loss 同时突刺并追溯问题批次，用梯度裁剪、更长预热、BF16、QK-Norm、调整 Adam beta 和数据清洗缓解；紧急时回滚到较早检查点并跳过坏批次。）

**追问方向**：QK-Norm 的作用；为何降低 $\beta_2$ 有帮助。

### Q15 学习率调度：预热、余弦与 WSD？（Learning rate schedules for LLMs）
**优先级：★★** · 对应基础知识：[神经网络与反向传播](../../02_基础知识/10_机器学习与深度学习/02_神经网络与反向传播.md)

**答案要点**
- 预热（数百到数千步）线性升至峰值，避免初期 Adam 统计不稳；随后**余弦衰减**到峰值的约 10%（经验）。
- **WSD（Warmup–Stable–Decay）**：长时间保持恒定学习率，最后一小段快速衰减；便于**随时从稳定阶段分叉**做退火评估或续训，不必预知总步数（连续预训练友好）。
- 峰值学习率随模型增大而减小（经验），批大小增大可适当提高；μP 等参数化可跨规模迁移超参。
- 退火阶段混入高质量数据可明显提升能力（常见做法，细节未核对）。
- 实务：训练前固定总 token 预算，余弦曲线才完整；变动预算建议用 WSD。

**English short answer**
I warm up the learning rate over a few thousand steps, then decay it with a cosine to about a tenth of the peak. The warmup-stable-decay schedule holds the rate constant and anneals at the end, so I can branch off at any time without knowing the total budget in advance, which suits continued pretraining. Larger models usually need a smaller peak rate, and annealing often benefits from higher-quality data.

（译：先用几千步预热，再按余弦衰减到峰值的约十分之一；WSD 调度长期保持恒定学习率、最后再退火，可在任意时刻分叉而无需预知总预算，适合持续预训练；更大模型通常需要更小峰值学习率，退火阶段使用更高质量数据常有收益。）

**追问方向**：μP 如何迁移学习率；WSD 的分叉做法。

### Q16 混合精度：BF16、FP16 与 FP8 训练的区别？（Mixed precision formats）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- **FP16**：5 位指数，范围窄（易上溢 / 下溢），必须 loss scaling；**BF16**：8 位指数（范围同 FP32）、7 位尾数，几乎不需 loss scaling，大模型默认；**FP8**（E4M3 / E5M2）：算力和带宽再翻倍，需要逐张量缩放（per-tensor / per-block scaling）与延迟缩放，稳定性要求高（H100 类硬件支持，细节未核对）。
- 做法：前向反向矩阵乘用低精度，主权重与优化器状态用 FP32，归约 / 归一化 / softmax / 损失用 FP32。
- 风险：累加精度不足（用 FP32 累加）、范围问题、梯度下溢；FP8 训练需验证不影响收敛。
- 收益：显存减半（相对 FP32）、吞吐提高；通信也可用低精度（梯度压缩，需谨慎）。

**English short answer**
FP16 has a narrow exponent range and needs loss scaling, BF16 keeps the FP32 range with fewer mantissa bits and is the default for large models, and FP8 doubles throughput again but needs careful per-tensor scaling. In all cases master weights, optimizer states, reductions, normalization and the loss stay in FP32, with matrix multiplications accumulating in higher precision. The gains are halved memory and higher throughput.

（译：FP16 指数范围窄需 loss scaling，BF16 保持 FP32 的范围、尾数更少，是大模型默认选择，FP8 再翻倍吞吐但需谨慎的逐张量缩放；各种情形下主权重、优化器状态、归约、归一化和损失都保持 FP32，矩阵乘用更高精度累加；收益是显存减半、吞吐提高。）

**追问方向**：E4M3 与 E5M2 的用途；为什么要延迟缩放。

### Q17 预训练数据处理：清洗、去重与质量过滤？（Pretraining data pipeline）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 流程：采集（网页、书籍、代码、论文等）→ 格式解析与抽取 → 语言识别 → **启发式过滤**（长度、符号比例、重复行）→ **质量分类器**（用高质量语料训练 fastText / 小模型打分）→ **去重**（精确哈希 + MinHash LSH 近重复；文档级与段落级）→ 敏感信息 / 版权 / 毒性过滤 → 去污染（与评测集 n-gram 重叠剔除）→ 配比与混合 → 分词。
- 去重的重要性：重复数据导致记忆、泛化下降、评测污染；MinHash 用 Jaccard 相似度近似。
- 配比：代码 / 数学 / 多语言 / 书籍占比影响能力；常通过小模型消融确定。
- 合成数据与课程：后期混入高质量与合成数据。
- 隐私与合规：PII 脱敏、许可证检查（具体法规未核对）。

**English short answer**
A pipeline extracts text, identifies language, applies heuristic filters and a learned quality classifier, deduplicates exactly and with MinHash locality-sensitive hashing, removes sensitive or toxic content, decontaminates against evaluation sets, and then sets the mixture of web, code, math and other sources, often by small-scale ablations. Deduplication matters because duplicates encourage memorization and distort evaluation.

（译：流程包括抽取文本、语言识别、启发式过滤和学习的质量分类器、精确与 MinHash LSH 近重复去重、敏感/有毒内容过滤、与评测集去污染，再通过小规模消融确定网页、代码、数学等来源的配比；去重重要，因为重复会促进记忆并扭曲评测。）

**追问方向**：MinHash 的原理；质量分类器的训练数据来源。

### Q18 序列打包（packing）与注意力掩码？（Sequence packing）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 问题：文档长度参差，填充到固定长度浪费算力。**打包**：把多个短文档拼接到同一序列（长度如 4096），用 EOS 分隔。
- 关键：为避免不同文档间的注意力污染，使用**文档级注意力掩码**（block-diagonal causal mask）并重置位置编码（varlen FlashAttention 接口支持，传入累积序列长度 `cu_seqlens`）；不做掩码则文档互相"看见"，影响质量（影响程度有争议，通常建议做）。
- 损失计算：只对有效 token 计损失；SFT 打包时 loss mask 要对齐样本边界。
- 好处：训练吞吐提高 1.2–2×（视数据长度分布，未核对）；注意负载均衡与批次内 token 数一致。
- 微调时可用"打包 + 动态批"以提高 GPU 利用率。

**English short answer**
Padding short documents wastes compute, so I pack several documents into one fixed-length sequence separated by end-of-sequence tokens. To avoid cross-document attention I use a block-diagonal causal mask and reset position ids, which variable-length FlashAttention supports via cumulative sequence lengths. Loss masks must respect sample boundaries, and packing can substantially increase throughput.

（译：为避免填充浪费算力，把多个文档拼接成定长序列并以 EOS 分隔；用分块对角因果掩码避免跨文档注意力并重置位置 id，变长 FlashAttention 可通过累积序列长度支持；损失掩码要尊重样本边界；打包可显著提升吞吐。）

**追问方向**：不做文档掩码的影响；packing 在 SFT 中的 loss mask 细节。

### Q19 检查点（checkpoint）、容错与弹性训练？（Checkpointing and fault tolerance）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 大规模训练硬件故障常见（GPU ECC 错误、网络抖动、节点宕机），平均无故障时间随规模急剧下降 → 必须频繁保存 checkpoint 并能自动恢复。
- 内容：模型参数、优化器状态、学习率调度器状态、**RNG 状态**、数据加载器位置（保证数据不重复不遗漏）、步数。分片训练存分片 checkpoint，并支持不同并行度下重新加载（resharding）。
- 优化：异步 checkpoint（先拷到 CPU 内存再后台写盘）、增量保存、分层存储（本地 NVMe + 远端对象存储）；保留多个版本防止损坏。
- 弹性：torchrun/elastic 在节点丢失后重启，健康检查、慢节点（straggler）检测与隔离、自动重启脚本。
- 校验：保存/加载后做 loss 一致性检查。

**English short answer**
At scale, failures are routine, so I save checkpoints frequently with model weights, optimizer and scheduler state, random seeds and the data loader position, often asynchronously to CPU memory first and then to storage, and keep several versions. Sharded checkpoints should be reloadable under a different parallel layout. Automatic restart, health checks and straggler detection keep long runs going.

（译：大规模训练中故障是常态，所以频繁保存检查点（权重、优化器与调度器状态、随机种子和数据加载位置），常先异步拷到 CPU 内存再写盘，并保留多个版本；分片检查点应能在不同并行布局下重新加载；自动重启、健康检查和慢节点检测保证长时间训练继续。）

**追问方向**：数据加载位置如何精确恢复；慢节点的成因。

### Q20 μP（最大更新参数化）和超参数迁移？（muP and hyperparameter transfer）
**优先级：★**

**答案要点**
- 问题：大模型一次训练昂贵，无法在大模型上网格搜索超参。
- μP：规定随宽度变化时各层初始化方差和学习率的缩放规则，使最优超参（学习率、初始化尺度等）在不同宽度下近似保持不变 → 在小模型上调参，**零样本迁移**到大模型。
- 对比标准参数化（SP）：最优学习率随宽度变化。
- 局限：需按规则修改实现；对深度、批大小等维度的迁移有额外经验；并非所有架构适用。
- 面试层面：知道"在小模型上调超参，迁移到大模型"的思路即可。

**English short answer**
Tuning hyperparameters directly on a huge model is too expensive. Maximal update parametrization specifies how initialization and per-layer learning rates should scale with width so that the optimal hyperparameters stay roughly constant, letting me tune on a small proxy and transfer to the large model. It requires implementing the scaling rules and does not cover every dimension.

（译：直接在巨型模型上调超参太昂贵；μP 规定初始化与逐层学习率如何随宽度缩放，使最优超参大致保持不变，从而在小代理模型上调参再迁移到大模型；需要按规则实现，且并不覆盖所有维度。）

**追问方向**：μP 与标准参数化的差异；迁移失败的表现。

### Q21 小规模消融与 scaling law 外推怎么用于决策？（Ablations and scaling extrapolation）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 做法：在多个小规模（如 50M–1B 参数、少量 token）上跑设计消融（数据配比、结构、学习率），拟合损失与算力的幂律 $L(C)=aC^{-b}+c$ 外推到目标规模，选择在目标算力下预测损失最低的方案。
- 注意：小规模结论不一定外推（涌现能力、质量过滤的影响随规模变化）；评测应使用平滑指标（loss / 困惑度）而不是离散的任务准确率；固定 token 预算与其他变量，单因素对比。
- 额外：多个种子估计噪声；记录算力成本；用同一评测集合避免污染。
- 与 Chinchilla：给定算力，参数与 token 数应按比例同步增长（经验约 20 token/参数，具体比例随研究和数据质量变化）；现代模型常"过训练"小模型以便推理便宜。

**English short answer**
I run design ablations at several small scales, fit a power law of loss against compute and extrapolate to the target scale to choose the best option. Results do not always transfer, and discrete downstream accuracies are noisy, so I rely on smooth metrics such as loss, change one factor at a time and use several seeds. Compute-optimal training balances parameters and tokens, although inference-aware practice often overtrains smaller models.

（译：在多个小规模上做设计消融，拟合损失对算力的幂律并外推到目标规模来选择最优方案；结果不一定可迁移且离散的下游准确率噪声大，所以用 loss 等平滑指标、一次只改一个因素并用多个种子；算力最优训练平衡参数与 token，但考虑推理成本时常对小模型"过训练"。）

**追问方向**：幂律拟合的不确定性；过训练小模型的动机。

## 三、注意力与算子优化

### Q22 FlashAttention 的原理：为什么既快又省显存？（FlashAttention）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 标准注意力把 $s\times s$ 的得分矩阵 $\mathbf{S}=\mathbf{Q}\mathbf{K}^\top$ 和 softmax 结果写回显存（HBM），**访存量 $O(s^2)$**，是带宽瓶颈。
- FlashAttention：**分块（tiling）**把 Q、K、V 分块载入片上 SRAM（共享内存），在块内计算得分、用**在线 softmax**（维护行最大值与归一化和，增量更新）累积输出，**不物化完整的 $s\times s$ 矩阵**；反向时重新计算而非存储。
- 效果：精确注意力（不近似）、显存从 $O(s^2)$ 降为 $O(s)$、HBM 访存减少 → 速度提升约 2–4×（量级，未核对）。
- 版本演进：v2 改进并行与分工，v3 针对新硬件（异步与低精度）；变长序列接口、因果掩码、滑动窗口、GQA 支持。
- 这是 **IO 感知**算法的典型：优化目标是减少慢存储访问，而非 FLOPs。

**English short answer**
Standard attention writes the full sequence-by-sequence score matrix to high-bandwidth memory, making it memory-bound. FlashAttention tiles queries, keys and values into on-chip SRAM, uses an online softmax to accumulate results without materializing the matrix, and recomputes in the backward pass. It is exact, uses linear memory in sequence length and reduces memory traffic, giving a multi-fold speedup. It is a classic IO-aware algorithm.

（译：标准注意力把完整的序列×序列得分矩阵写入高带宽显存，受带宽限制；FlashAttention 把 Q/K/V 分块载入片上 SRAM，用在线 softmax 累积结果而不物化该矩阵，并在反向时重算；它是精确的、显存随序列长度线性、访存减少从而数倍加速，是典型的 IO 感知算法。）

**追问方向**：在线 softmax 的递推公式；为什么反向重算更划算。

### Q23 算子融合与 torch.compile 的作用？（Kernel fusion and compilation）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 许多算子（逐元素运算、LayerNorm、激活、残差加）计算量小但**访存密集**；每个算子独立执行都要读写全局显存。**融合**把相邻算子合成一个内核，中间结果留在寄存器 / 共享内存，减少 HBM 往返。
- 工具：`torch.compile`（Inductor 生成 Triton 内核）、Triton 手写内核、CUDA / CUTLASS、XLA、TensorRT 图优化。
- 典型融合：bias + GELU、RMSNorm、RoPE、softmax + mask、交叉熵（避免物化巨大的 logits 张量）、优化器更新（fused Adam）。
- 注意：动态形状触发重编译、编译时间、调试难度；先 profile 找真正的瓶颈再优化。
- 度量：算术强度与屋顶线判断是否 memory-bound。

**English short answer**
Many operations such as normalization, activations and residual adds do little arithmetic but read and write whole tensors, so they are memory-bound. Fusing them into one kernel keeps intermediates on chip and cuts traffic to global memory. Tools include torch.compile with Triton kernels, hand-written Triton or CUDA, and graph compilers. I profile first, and watch for recompilation with dynamic shapes.

（译：归一化、激活、残差加等算子计算量小但要读写整张张量，属于访存受限；把它们融合成一个内核使中间结果留在片上，减少全局显存访问；工具有 torch.compile+Triton、手写 Triton/CUDA 和图编译器；先 profile，并注意动态形状引起的重编译。）

**追问方向**：融合交叉熵为何省显存；Triton 与 CUDA 的取舍。

### Q24 GPU 内存层级与"带宽瓶颈"如何影响 LLM 性能？（GPU memory hierarchy and bandwidth bound）
**优先级：★★★** · 对应基础知识：[计算机体系结构_缓存_流水线_SIMD_GPU](../../02_基础知识/14_计算机基础/04_计算机体系结构_缓存_流水线_SIMD_GPU.md)

**答案要点**
- 层级：寄存器 → 共享内存 / L1（片上，TB/s 级，容量 MB 级）→ L2 → HBM 显存（数 TB/s，GB 级）→ 主机内存 / NVMe（慢得多）。
- LLM 解码（生成）每步只处理 1 个新 token：对每层都要读取全部权重（和 KV cache），算术强度极低（约 1–2 FLOPs/字节量级）→ **受 HBM 带宽限制**，延迟 $\approx\dfrac{\text{参数字节}+\text{KV 字节}}{\text{带宽}}$。例（教学）：7B BF16 约 14 GB、带宽 2 TB/s → 每 token 下限约 7 ms。
- 预填充（prefill）并行处理整段 prompt，算术强度高 → 受算力限制。
- 推论：量化权重（INT4）使字节减少 → 解码近线性加速；批处理多请求摊薄权重读取 → 吞吐提高；GQA/MQA 减少 KV 字节。

**English short answer**
GPUs have a fast but small on-chip memory and a large but slower HBM. During decoding every token reads all weights and the KV cache, so arithmetic intensity is very low and latency is roughly bytes moved divided by memory bandwidth, about 7 ms per token for a 14 GB model on a 2 TB/s GPU. Prefill is compute-bound instead. Hence quantization, batching and grouped-query attention speed up decoding.

（译：GPU 有快而小的片上存储和大而较慢的 HBM；解码时每个 token 都要读取所有权重与 KV cache，算术强度很低，延迟约等于搬运字节数除以带宽（14 GB 模型在 2 TB/s 的 GPU 上约 7 ms/token）；预填充则受算力限制；因此量化、批处理和 GQA 能加速解码。）

**追问方向**：如何用屋顶线判断瓶颈；批大小增大后瓶颈如何转移。

### Q25 线性注意力、稀疏注意力与状态空间模型（SSM/Mamba）的取舍？（Efficient attention alternatives）
**优先级：★★** · 对应基础知识：[序列模型_残差网络_ViT与生成模型](../../02_基础知识/10_机器学习与深度学习/07_序列模型_残差网络_ViT与生成模型.md)

**答案要点**
- 标准注意力 $O(s^2)$。**稀疏 / 滑动窗口注意力**：每个 token 只看局部窗口 + 少数全局 token（Longformer、Mistral 的滑窗），复杂度 $O(sw)$。**线性注意力**：用核特征映射使 $\mathrm{softmax}$ 可分解，复杂度 $O(s)$，常有质量损失。
- **SSM / Mamba**：递推状态，$O(s)$ 训练（并行扫描）、推理每步 $O(1)$、无 KV cache 增长；对精确回忆（in-context retrieval）弱于全注意力，常与注意力层**混合**（Jamba 类混合架构，细节未核对）。
- 取舍：短上下文用全注意力 + FlashAttention 已足够；超长上下文 / 低延迟 / 端侧可考虑滑窗、SSM、混合。
- 评估要看长上下文检索任务（针堆测试）而不仅是困惑度。

**English short answer**
Full attention is quadratic in sequence length. Sliding-window and sparse attention restrict each token to a local neighborhood plus a few global tokens, linear attention factorizes the softmax with feature maps at some quality cost, and state-space models like Mamba keep a fixed-size recurrent state with constant per-token inference but weaker exact recall, so hybrids mix them with attention layers. For short contexts FlashAttention with full attention is usually enough.

（译：全注意力对序列长度二次复杂；滑窗/稀疏注意力让每个 token 只看局部邻域加少量全局 token；线性注意力用特征映射分解 softmax 但有质量损失；Mamba 等 SSM 保持固定大小递推状态、推理每 token 常数开销但精确回忆较弱，所以常与注意力层混合；短上下文用全注意力加 FlashAttention 通常足够。）

**追问方向**：针堆测试的含义；混合架构的比例选择。

### Q26 SFT 数据构造与 loss mask 的细节？（SFT data and loss masking）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 数据格式：多轮对话按**聊天模板**（chat template）拼接，包含 system / user / assistant 的特殊 token；训练与推理必须使用**完全一致**的模板，否则性能显著下降。
- **只对 assistant 回复计损失**（user / system 部分 mask 为 −100），避免模型学习"复述问题"；多轮时对每个 assistant 回合计损失。
- 质量优于数量：几千到几万条高质量、多样、格式一致的数据常足够（LIMA 类经验）；去重、去噪、难度与领域覆盖均衡；拒答与安全样本需要。
- 打包 / 动态批、截断策略（保留末尾 or 开头）、EOS 标记正确（否则生成停不下来）。
- 评估：留出集上的指令遵循与领域任务，同时检查通用能力是否退化。

**English short answer**
I format multi-turn conversations with the model's chat template, which must match between training and inference, and compute the loss only on assistant tokens by masking system and user text. Data quality, diversity and format consistency matter more than volume. I handle truncation and end-of-sequence tokens carefully, otherwise generation never stops, and I evaluate both the target skill and general abilities.

（译：用模型的聊天模板格式化多轮对话，训练与推理必须一致，通过 mask 掉 system 和 user 文本只对 assistant token 计算损失；数据质量、多样性与格式一致性比数量更重要；要仔细处理截断与 EOS，否则生成停不下来；同时评估目标技能与通用能力。）

**追问方向**：模板不一致的典型症状；多轮训练的 loss 计算。

### Q27 LoRA/QLoRA 微调的工程参数怎么选？（LoRA hyperparameters）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 参数：秩 $r$（8–64 常见）、缩放 $\alpha$（有效缩放 $\alpha/r$，常取 $\alpha=2r$ 或 $=r$）、dropout（0–0.1）、目标模块（仅 q/v 起步 → 全部线性层 q,k,v,o,gate,up,down 通常更好）。
- 学习率：LoRA 通常比全参微调高一个量级（1e-4～5e-4），余弦 + 预热；训练 1–3 个 epoch，过多易过拟合。
- 显存：基础权重冻结（可 4-bit 量化 = QLoRA：NF4 + 双量化 + 分页优化器），LoRA 参数 + 优化器状态很小；7B 模型 QLoRA 可在 24 GB 卡训练（量级，未核对）。
- 部署：可合并（merge）进基础权重零开销，或保留适配器热插拔（多租户服务）。
- 效果：数据量小 / 任务窄时与全参相当；需要大幅改变知识 / 能力时 LoRA 容量不足，可增大秩或全参。

**English short answer**
I choose rank 8 to 64, set the scaling alpha around the rank or twice it, and apply LoRA to all linear layers for better quality than attention-only. The learning rate is about ten times higher than for full fine-tuning, with one to three epochs. QLoRA freezes a 4-bit quantized base model and trains small adapters, fitting a 7B model on a consumer GPU. Adapters can be merged for zero overhead or hot-swapped per task.

（译：秩取 8～64，缩放 $\alpha$ 取秩的一到两倍，对所有线性层加 LoRA 效果优于仅注意力；学习率约为全参微调的十倍，训练 1～3 个 epoch；QLoRA 冻结 4 位量化的基座模型、只训练小适配器，可在消费级显卡上微调 7B 模型；适配器可合并实现零开销，或按任务热插拔。）

**追问方向**：$\alpha/r$ 的作用；LoRA 容量不足的信号。

### Q28 全参微调 vs PEFT：何时选哪个？（Full fine-tuning vs PEFT）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 全参：容量最大、可大幅改变能力；显存/算力成本高（约 16 字节/参数 + 激活）；灾难性遗忘风险高；每个任务存一份完整模型。
- PEFT（LoRA / 适配器 / prefix / IA³）：显存低、训练快、存储小（MB 级）、遗忘较少；容量有限，对新知识注入不如全参。
- 决策：数据少（<几万）、任务窄、算力有限、需多任务切换 → PEFT；需要继续预训练注入大量新领域知识、能力大幅改变 → 全参（或 PEFT + 高秩 + 持续预训练）。
- 实用折中：先 LoRA 验证数据和流程，再决定是否升级；使用数据回放（混入通用数据）缓解遗忘。
- 注意：评估通用基准回归。

**English short answer**
Full fine-tuning has the most capacity and can change behavior substantially, but needs sixteen-bytes-per-parameter memory, risks forgetting and stores a full copy per task. Parameter-efficient methods train tiny modules, so they are cheap, fast, easy to switch between tasks and forget less, but have limited capacity for injecting large amounts of new knowledge. I start with LoRA to validate data and pipeline and escalate only if needed.

（译：全参微调容量最大、可大幅改变行为，但需每参数 16 字节的显存、易遗忘且每任务存一份完整模型；参数高效方法只训练小模块，便宜快速、易切换任务、遗忘较少，但注入大量新知识的容量有限；先用 LoRA 验证数据与流程，必要时再升级。）

**追问方向**：持续预训练与 SFT 的分工；数据回放的比例。

### Q29 偏好优化：DPO、IPO、KTO 的数据与工程差别？（Preference optimization methods）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- **DPO**：需要成对偏好数据 $(x,y_w,y_l)$；损失 $-\log\sigma\!\big(\beta[\log\frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}-\log\frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}]\big)$；无需训练奖励模型和 RL，只需参考模型（可预计算参考 logprob 省显存）；$\beta$ 控制偏离参考策略的程度（常 0.1）。
- 常见问题：同时降低 chosen 与 rejected 的似然、生成变长（偏好长回答）、对数据质量敏感。**IPO** 改用平方损失避免过拟合偏好；**KTO** 只需单样本好 / 坏标签（不要求成对）；**ORPO / SimPO** 去掉参考模型。
- 工程：偏好数据质量（标注一致性、难度）、长度偏差控制、在 SFT 模型基础上做、学习率很小（5e-7～5e-6）、1–2 个 epoch。
- 与 RLHF 对比：更简单稳定，但探索能力有限（离线偏好）；在线 DPO / 迭代 DPO 采样新响应再标注。

**English short answer**
DPO optimizes a classification-like loss on preference pairs relative to a frozen reference model, with beta controlling how far the policy may drift, and needs no reward model or RL loop. It can lower the likelihood of both chosen and rejected answers and bias toward longer outputs. IPO, KTO and SimPO modify the loss to reduce overfitting, use unpaired labels or drop the reference model. I use small learning rates, start from an SFT model and control length bias.

（译：DPO 在成对偏好数据上相对冻结的参考模型优化类分类损失，$\beta$ 控制策略偏离程度，无需奖励模型和 RL 循环；可能同时降低好坏回答的似然并偏向更长输出；IPO、KTO、SimPO 分别改损失以减少过拟合、使用非成对标签或去掉参考模型；用很小的学习率、从 SFT 模型起步并控制长度偏差。）

**追问方向**：DPO 损失的推导思路；长度偏差如何缓解。

### Q30 RLHF 的工程难点：为什么要同时跑四个模型？（RLHF system design）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- PPO 式 RLHF 需要：**策略模型（actor）**、**参考模型（ref，计算 KL 惩罚）**、**奖励模型（RM）**、**价值模型（critic）**。四个大模型 → 显存和调度复杂。
- 流程每步：actor 采样生成（推理阶段，需高效生成引擎）→ RM 打分 + ref 算 KL → critic 估值 → 计算优势（GAE）→ PPO 更新 actor 与 critic；**生成与训练交替**，要在同一集群切换（hybrid engine）。
- 优化：共享骨干 / LoRA 减少模型数量、critic 与 actor 共享底座、offload 参考模型、生成使用 vLLM 加速、批量异步。
- 超参敏感：KL 系数、剪裁范围、学习率、奖励归一化；奖励黑客（模型钻奖励模型漏洞）、长度膨胀。
- 替代：GRPO（去掉 critic，用组内相对奖励估优势）、RLVR（可验证奖励，如数学 / 代码测试）。

**English short answer**
PPO-based RLHF needs a policy, a frozen reference model for the KL penalty, a reward model and a value model, so memory and scheduling are heavy. Each iteration samples responses with a fast generation engine, scores them, estimates advantages and updates the policy and critic, alternating generation and training on the same cluster. GRPO drops the critic by using group-relative rewards, and verifiable rewards avoid reward-model exploitation.

（译：基于 PPO 的 RLHF 需要策略模型、用于 KL 惩罚的冻结参考模型、奖励模型和价值模型，显存与调度开销大；每轮用高效生成引擎采样、打分、估优势并更新策略与 critic，在同一集群上交替生成与训练；GRPO 用组内相对奖励去掉 critic，可验证奖励则避免奖励模型被钻漏洞。）

**追问方向**：GRPO 的优势估计；奖励黑客的例子。

### Q31 奖励模型（RM）如何训练与评估？（Reward models）
**优先级：★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 训练：在 SFT 模型上加一个标量输出头，用成对偏好数据最小化 Bradley–Terry 损失 $-\log\sigma(r(x,y_w)-r(x,y_l))$。
- 评估：在留出偏好集上的**成对准确率**；与人类一致性；对分布外样本、长度、格式偏差的鲁棒性。
- 问题：RM 是人类偏好的有噪声代理 → 优化过度（Goodhart）：RM 分上升而真实质量下降；长度偏差、阿谀奉承（sycophancy）。
- 缓解：KL 惩罚、早停、RM 集成、过程奖励模型（PRM，对推理步骤打分）、可验证奖励（规则 / 单元测试）、迭代更新 RM（引入新策略样本）。
- LLM-as-judge 可作为廉价 RM 替代，但需防位置 / 长度偏差。

**English short answer**
A reward model is a language model with a scalar head trained on preference pairs with a Bradley-Terry loss and evaluated by pairwise accuracy on held-out data. Because it is a noisy proxy, optimizing against it too hard degrades true quality, which is reward hacking and length or sycophancy bias. I counter with KL penalties, early stopping, ensembles, process reward models and verifiable rewards where available.

（译：奖励模型是带标量头的语言模型，用成对偏好数据和 Bradley–Terry 损失训练，以留出数据上的成对准确率评估；它是有噪声的代理，过度优化会降低真实质量（奖励黑客，以及长度和阿谀偏差）；用 KL 惩罚、早停、集成、过程奖励模型和可验证奖励缓解。）

**追问方向**：过程奖励 vs 结果奖励；Goodhart 定律在 RLHF 中的体现。

### Q32 合成数据与蒸馏在微调中的作用与风险？（Synthetic data and distillation）
**优先级：★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 用强模型（教师）生成指令、回答、推理过程（思维链）来训练小模型（学生）：成本低、规模大、可控覆盖；Self-Instruct、Evol-Instruct、拒绝采样（多采样 + 验证器挑选）、数学 / 代码用可执行验证过滤。
- 蒸馏方式：序列级（SFT 在教师输出上）、logit 级（KL 对齐分布，需同词表）。
- 风险：继承教师错误与偏见；多样性坍缩（模型输出越来越同质，"模型坍塌"）；评测污染；**许可证 / 服务条款**限制（某些模型输出不得用于训练竞品，需核对）。
- 缓解：多源教师、验证器过滤、混入真实数据、去重与多样性度量。
- 评估：学生在留出真实数据上的表现，而非仅教师分布。

**English short answer**
Strong models can generate instructions, answers and reasoning traces to train smaller students cheaply and at scale, with rejection sampling and executable verifiers filtering for correctness. Risks include inheriting teacher errors, diversity collapse over generations, evaluation contamination and licensing restrictions on using model outputs. I mix in real data, deduplicate, measure diversity and evaluate on held-out real tasks.

（译：强模型可低成本大规模地生成指令、回答与推理轨迹来训练小学生模型，用拒绝采样和可执行验证器过滤正确性；风险包括继承教师错误、多代后多样性坍缩、评测污染及模型输出使用的许可限制；混入真实数据、去重、度量多样性，并在留出的真实任务上评估。）

**追问方向**：模型坍塌的机制；拒绝采样的验证器设计。

### Q33 微调后的灾难性遗忘如何检测与缓解？（Catastrophic forgetting in fine-tuning）
**优先级：★★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 现象：在窄任务数据上微调后，通用知识、指令遵循、安全对齐能力下降。
- 检测：微调前后在一套**保留基准**（通用问答、数学、代码、安全）上对比；监控困惑度变化。
- 缓解：①数据回放（混入通用 / 原 SFT 数据，5%–30%）；②PEFT / 低秩（改动小）；③更小学习率、更少 epoch；④正则（对基础模型的 KL / L2-SP / EWC）；⑤模型合并（权重平均 / 任务向量 / SLERP）把微调模型与基座插值；⑥分阶段训练。
- 经验：数据窄 + 学习率高 + 轮数多最易遗忘；对齐/安全能力尤其脆弱，需单独评估。
- 机器人应用：把领域 VLM 微调到机器人任务时同样需保持语义能力。

**English short answer**
Narrow fine-tuning can erode general knowledge, instruction following and safety behavior. I detect it by comparing before and after on a held-out suite, and mitigate with replay of general data, parameter-efficient updates, lower learning rates and fewer epochs, KL or weight-space regularization, and model merging by interpolating with the base weights. Safety alignment is particularly fragile and needs its own evaluation.

（译：窄任务微调会侵蚀通用知识、指令遵循和安全行为；对比微调前后在留出基准上的表现来检测，并通过通用数据回放、参数高效更新、更小学习率与更少 epoch、KL/权重空间正则、以及与基座权重插值的模型合并来缓解；安全对齐尤其脆弱，需单独评估。）

**追问方向**：任务向量与模型合并的原理；回放比例怎么定。

### Q34 LLM 推理为什么分 prefill 和 decode 两个阶段？（Prefill vs decode）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- **Prefill（预填充）**：一次性并行处理整段 prompt，计算所有 token 的 KV 并写入缓存，矩阵乘大、**算力受限（compute-bound）**，决定首 token 延迟（TTFT）。
- **Decode（解码）**：逐 token 自回归生成，每步只算 1 个新 token，要读全部权重与 KV cache，**带宽受限（memory-bound）**，决定每 token 延迟（TPOT / ITL）与吞吐。
- 影响：长 prompt 的 prefill 会"阻塞"同批次的 decode（抖动）→ chunked prefill、PD 分离。
- 优化方向不同：prefill 靠算力、融合、并行；decode 靠批处理、量化、投机解码、KV 压缩。
- 指标：TTFT、TPOT、吞吐（tokens/s）、P99 延迟、每百万 token 成本。

**English short answer**
Prefill processes the whole prompt in parallel and is compute-bound, setting the time to first token. Decode generates one token per step, reading all weights and the KV cache, so it is memory-bandwidth-bound and sets per-token latency and throughput. Long prefills can stall ongoing decodes, so serving systems use chunked prefill or separate the two phases, and I optimize them differently.

（译：Prefill 并行处理整段 prompt，受算力限制，决定首 token 时间；Decode 每步生成一个 token、需读取全部权重和 KV cache，受内存带宽限制，决定每 token 延迟与吞吐；长 prefill 会阻塞进行中的 decode，所以服务系统用分块预填充或分离两个阶段，并对二者采取不同优化。）

**追问方向**：TTFT 与 TPOT 的权衡；chunked prefill 的做法。

### Q35 vLLM 为什么快？核心机制有哪些？（How vLLM works）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- **PagedAttention**：把 KV cache 按固定大小的**块（页）**管理，通过块表映射逻辑位置到物理块，消除碎片、按需分配，显存浪费从 60%–80% 降到很小（量级，未核对），并支持前缀共享（写时复制）。
- **连续批处理（continuous / iteration-level batching）**：每个解码步骤都可以插入新请求、移除完成的请求，不必等整批结束，GPU 利用率高。
- 其他：前缀缓存、分块预填充、CUDA graph、融合内核（FlashAttention / FlashInfer）、量化支持、张量并行、投机解码。
- 调度：按 token 预算与显存块数做准入控制、抢占（swap / recompute）。
- 对比朴素静态批处理：需要等最长序列、预分配最大长度 KV → 浪费。

**English short answer**
vLLM manages the KV cache in fixed-size blocks like virtual memory pages, eliminating fragmentation and allowing prefix sharing, and uses continuous batching so requests join and leave the batch at every decoding step. It adds chunked prefill, CUDA graphs, optimized attention kernels, quantization and tensor parallelism. Static batching, in contrast, waits for the longest sequence and reserves maximum-length cache for each request.

（译：vLLM 像虚拟内存分页一样按定长块管理 KV cache，消除碎片并支持前缀共享，用连续批处理让请求在每个解码步加入或退出批次，并加入分块预填充、CUDA graph、优化注意力内核、量化和张量并行；静态批处理则要等最长序列并为每个请求预留最大长度的缓存。）

**追问方向**：块表的数据结构；抢占策略（swap 与 recompute）。

### Q36 前缀缓存（prefix caching）与 prompt 缓存？（Prefix caching）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 许多请求共享长前缀（系统提示、few-shot 示例、RAG 文档、多轮对话历史）。把前缀的 KV cache 保存并复用，新请求只需计算增量部分，**大幅降低 TTFT 与算力**。
- 实现：按 token 块哈希（链式哈希保证前缀一致）索引缓存块，LRU 淘汰；RadixAttention 用基数树管理共享前缀。
- 条件：前缀必须**逐 token 完全一致**（包括模板、空格），动态内容（时间戳、用户名）放到末尾；采样不影响缓存。
- 云 API 的"prompt caching"同理，按缓存命中计费折扣。
- 机器人 / Agent：系统提示 + 工具 schema 很长，缓存收益显著；注意缓存带来的显存占用与多租户隔离。

**English short answer**
When many requests share a long prefix such as a system prompt, tool schemas or conversation history, the server stores that prefix's KV cache and only computes the new suffix, cutting time to first token and compute. Blocks are indexed by chained token hashes or a radix tree with LRU eviction. The prefix must match token for token, so I put dynamic content at the end. Agents with long tool descriptions benefit greatly.

（译：当许多请求共享系统提示、工具 schema 或对话历史等长前缀时，服务端保存该前缀的 KV cache，只计算新增后缀，降低首 token 时间和算力；块按链式 token 哈希或基数树索引并用 LRU 淘汰；前缀必须逐 token 一致，因此动态内容放在末尾；带长工具描述的 Agent 受益显著。）

**追问方向**：RadixAttention 的结构；缓存与多租户隔离。

### Q37 LLM 权重量化：GPTQ、AWQ、SmoothQuant、FP8 有何区别？（LLM quantization methods）
**优先级：★★★** · 对应基础知识：[模型量化与边缘部署_RKNN](../../02_基础知识/10_机器学习与深度学习/04_模型量化与边缘部署_RKNN.md)

**答案要点**
- **权重量化（W4A16 / W8A16）**：只把权重量化为 INT4/INT8，激活保持 FP16；因为解码受带宽限制，减少权重字节几乎线性加速。**GPTQ**：基于二阶信息（近似 Hessian）逐层最小化量化误差并补偿；**AWQ**：保护对激活重要的少数"显著通道"（按激活幅度缩放），无需反传，效果好、速度快。
- **权重+激活量化（W8A8）**：矩阵乘用 INT8 计算，吞吐更高；激活存在异常值（outlier），**SmoothQuant** 把激活的量化难度通过数学等价缩放迁移到权重。
- **FP8**：新硬件原生支持，W8A8 精度损失小，简单稳健。
- **KV cache 量化**（INT8/FP8/INT4）：长上下文大批量时降 KV 显存。
- 评估：困惑度 + 任务指标；对小模型、推理 / 数学任务敏感；校准数据集选择。

**English short answer**
Weight-only quantization to INT4 or INT8 cuts the bytes read in the memory-bound decode phase almost proportionally, with GPTQ compensating errors layer by layer using second-order information and AWQ protecting salient channels identified from activations. W8A8 schemes quantize activations too for higher compute throughput, where SmoothQuant migrates activation outliers into the weights, and FP8 is a simple option on newer hardware. KV cache quantization saves memory for long contexts.

（译：INT4/INT8 的仅权重量化减少解码阶段读取的字节数，几乎按比例加速；GPTQ 用二阶信息逐层补偿误差，AWQ 保护由激活识别的显著通道；W8A8 同时量化激活获得更高算力吞吐，SmoothQuant 把激活离群值迁移到权重；新硬件上 FP8 是简单选择；KV cache 量化节省长上下文显存。）

**追问方向**：为什么激活更难量化；校准数据的选择。

### Q38 推理时的张量并行与流水线并行如何用？（Parallelism for inference）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 模型太大放不下一张卡（如 70B BF16 约 140 GB）：用**张量并行**（单节点内 2/4/8 卡）把每层切开，降低单卡权重与 KV，**同时降低每 token 延迟**（每卡读更少权重），代价是每层 All-Reduce；NVLink 下效率好，PCIe 下收益有限。
- **流水线并行**用于跨节点超大模型，提高可放入的模型规模，但不降低单请求延迟（气泡），靠多请求并行提高吞吐。
- 另有**专家并行**（MoE）、**数据并行副本**（多副本负载均衡，扩吞吐）。
- 选择：延迟敏感 → TP；吞吐优先 → 更多副本 + 小 TP；显存不足优先量化再考虑增大 TP。
- 注意：KV cache 在 TP 下按头切分，GQA 的 KV 头数限制 TP 度数。

**English short answer**
When a model does not fit on one GPU, tensor parallelism within a node splits each layer, lowering per-GPU weight reads and thus per-token latency at the cost of an all-reduce per layer, so it relies on NVLink. Pipeline parallelism enables very large models across nodes but does not reduce single-request latency. For throughput I add data-parallel replicas, and I try quantization before raising the tensor-parallel degree.

（译：模型单卡放不下时，节点内张量并行切分每层，降低每卡权重读取量从而降低每 token 延迟，代价是每层一次 All-Reduce，因而依赖 NVLink；流水线并行支持跨节点超大模型但不降低单请求延迟；吞吐靠数据并行副本，且先试量化再提高张量并行度。）

**追问方向**：GQA 头数对 TP 的限制；副本数与批大小的权衡。

### Q39 投机解码的变体：Medusa、EAGLE、n-gram 查找？（Speculative decoding variants）
**优先级：★★** · 对应基础知识：[模型量化与边缘部署_RKNN](../../02_基础知识/10_机器学习与深度学习/04_模型量化与边缘部署_RKNN.md)

**答案要点**
- 基本思想：廉价地"猜"若干后续 token，再用大模型**一次并行验证**，接受匹配的前缀；通过拒绝采样保证输出分布与原模型一致（无损）。
- 变体：**草稿小模型**（需同词表，较小的同族模型）；**Medusa**（在主模型上加多个预测头并行猜多个位置，树形验证）；**EAGLE**（在特征层自回归预测草稿）；**Prompt lookup / n-gram**（从输入文本中查找重复片段，对摘要、代码改写、RAG 引用效果好，零额外模型）。
- 收益：加速 2–3× 常见（取决于接受率与批大小，未核对）；批较大时 decode 已较少带宽受限，收益下降。
- 注意：草稿成本、接受率、树结构的验证开销；与量化、批处理叠加。

**English short answer**
Speculative decoding cheaply guesses several future tokens and verifies them in a single parallel pass of the large model, accepting the matching prefix and preserving the exact output distribution. Drafts can come from a small model, extra heads as in Medusa, feature-level prediction as in EAGLE, or n-gram lookup in the prompt. Gains depend on acceptance rate and shrink at large batch sizes where decoding is less bandwidth-bound.

（译：投机解码廉价地猜测若干后续 token，并让大模型一次并行验证、接受匹配前缀，同时保持输出分布不变；草稿可来自小模型、Medusa 的额外预测头、EAGLE 的特征层预测或 prompt 中的 n-gram 查找；收益取决于接受率，大批量时解码较少受带宽限制，收益下降。）

**追问方向**：无损性的证明思路；树形验证的注意力掩码。

### Q40 PD 分离（Prefill-Decode disaggregation）与推理调度？（Disaggregated serving）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 动机：预填充（算力密集）与解码（带宽密集）资源需求和 SLO 不同（TTFT vs TPOT），放在同一批会互相干扰（decode 被长 prefill 卡住）。
- 做法：用不同 GPU 池分别做 prefill 和 decode，prefill 完成后把 **KV cache 通过高速网络传输**给 decode 实例；各池独立扩缩容、选择不同并行度 / 硬件。
- 代价：KV 传输开销（需 NVLink / RDMA）、调度复杂；在 prompt 很长或 SLO 严格时收益明显。
- 替代：chunked prefill（把长 prefill 切块与 decode 混批，实现简单）。
- 其他调度技术：基于优先级 / SLO 的调度、抢占、负载均衡到副本、前缀亲和路由（命中缓存）。

**English short answer**
Prefill is compute-heavy and decode is bandwidth-heavy, with different latency objectives, and mixing them makes decodes stall behind long prefills. Disaggregated serving runs them on separate GPU pools and transfers the KV cache between them over a fast network, allowing independent scaling and tuning at the price of transfer cost and scheduling complexity. Chunked prefill is a simpler alternative, and prefix-affinity routing improves cache hits.

（译：预填充重算力、解码重带宽，延迟目标不同，混在一起会让解码被长预填充卡住；分离式服务在不同 GPU 池上运行二者并经高速网络传输 KV cache，可独立扩缩容与调优，代价是传输开销和调度复杂度；分块预填充是更简单的替代方案，前缀亲和路由可提高缓存命中。）

**追问方向**：KV 传输带宽需求估算；何时 PD 分离不划算。

### Q41 长上下文推理的 KV cache 压缩方法？（KV cache compression）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- KV cache 大小 $=2\times L\times n_{kv}\times d_{head}\times s\times b\times\text{字节数}$，随序列长度与批大小线性增长，长上下文时常超过权重。
- 方法：**GQA / MQA**（减少 KV 头数）、**MLA**（多头潜在注意力：把 KV 压缩到低维潜向量，DeepSeek 系列，细节未核对）、**KV 量化**（INT8/FP8/INT4）、**滑动窗口 + 注意力汇聚点（sink）**（StreamingLLM）、**token 驱逐/稀疏化**（H2O、SnapKV：保留累计注意力高的 token）、**分页 + 卸载**到 CPU/磁盘。
- 取舍：压缩会损失长程检索精度，需要在针堆等任务上验证。
- 例（教学）：7B 模型 32 层、KV 头 8、头维 128、FP16：每 token KV 约 $2\times32\times8\times128\times2=131$ KB；32K 上下文单序列约 4.3 GB。

**English short answer**
The KV cache grows linearly with sequence length and batch size and can exceed the weights for long contexts. I shrink it with grouped-query or latent attention that reduce stored heads, quantize it to INT8 or FP8, evict or sparsify tokens by attention importance while keeping attention sinks, use sliding windows, or offload cold blocks. Each reduces long-range recall to some degree, so I validate on retrieval-style benchmarks.

（译：KV cache 随序列长度和批大小线性增长，长上下文时可能超过权重；通过 GQA 或潜在注意力减少存储的头、量化到 INT8/FP8、按注意力重要性驱逐/稀疏化 token 并保留注意力汇聚点、使用滑动窗口或卸载冷块来缩减；每种都会在一定程度上损害长程召回，需在检索类基准上验证。）

**追问方向**：每 token KV 大小的计算；StreamingLLM 的汇聚点现象。

### Q42 多 LoRA 服务与适配器热切换？（Multi-LoRA serving）
**优先级：★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 场景：一个基础模型服务多个租户 / 任务各自的 LoRA 适配器（MB 级）；若每个任务合并成独立完整模型，显存与成本爆炸。
- 做法：基础权重共享，请求携带适配器 ID；对同一批内不同适配器用**分组/批量 LoRA 内核**（如 Punica / S-LoRA 思路）并行计算 $\mathbf{x}\mathbf{A}\mathbf{B}$ 增量；适配器热加载 / 淘汰（LRU），放在 CPU/显存分层。
- 取舍：运行时多一次小矩阵乘（延迟略增）；合并权重则无额外开销但失去共享；适配器数量大时调度与缓存是关键。
- 机器人：同一 VLA 骨干 + 每个机器人 / 任务一个适配器，是节省存储的做法（概念）。

**English short answer**
A single base model can serve many tenants or tasks by keeping small LoRA adapters separately and applying them per request. Batched LoRA kernels compute different adapters for different requests in one batch, and adapters are loaded and evicted on demand. Compared with merging weights it adds a small extra matrix multiply but avoids storing a full model per task. A robot fleet could share one backbone with per-task adapters.

（译：一个基础模型可通过单独保存的小 LoRA 适配器并按请求应用来服务多个租户/任务；批量 LoRA 内核在同一批中为不同请求计算不同适配器，适配器按需加载与淘汰；相比合并权重会多一次小矩阵乘，但避免为每个任务存一份完整模型；机器人车队可共享一个骨干并按任务使用适配器。）

**追问方向**：S-LoRA 的显存管理；合并与不合并的延迟差。

### Q43 如何做 LLM 服务的容量规划与成本估算？（Capacity planning and cost）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 输入：请求速率、平均输入 / 输出 token 数、延迟 SLO（TTFT、TPOT）、模型规格、GPU 型号。
- 估算：①显存：权重 + KV cache（并发数 × 平均上下文 × 每 token KV）+ 激活余量，决定每卡并发上限；②吞吐：解码阶段带宽受限，tokens/s ≈ 带宽 / 每步字节 × 批大小（受批大小增大趋向算力上限）；③GPU 数 = 总 token 吞吐需求 / 单 GPU 吞吐，并留冗余（N+1、峰值余量）。
- 成本：单 GPU 小时价格 / 每小时 token 数 = 每百万 token 成本；利用率（批处理、前缀缓存、量化）决定成本。
- 对比托管 API：按 token 计费，适合低利用率；自建适合稳定高负载 / 数据本地化。
- 验证：压测（并发扫描）绘制延迟–吞吐曲线，找拐点。

**English short answer**
From request rate, token counts and latency targets I estimate memory for weights plus KV cache per concurrent request to find the concurrency per GPU, estimate decode throughput from memory bandwidth and batch size, and compute the number of GPUs with headroom. Cost per million tokens is GPU hourly price over tokens per hour, and quantization, batching and prefix caching raise utilization. I validate with load tests that sweep concurrency to find the latency-throughput knee.

（译：由请求速率、token 数和延迟目标估算权重加每并发请求 KV cache 的显存以得到每卡并发上限，按内存带宽和批大小估算解码吞吐并加冗余算出 GPU 数；每百万 token 成本等于 GPU 小时价格除以每小时 token 数，量化、批处理、前缀缓存提高利用率；用扫描并发的压测验证并找到延迟–吞吐拐点。）

**追问方向**：自建与托管 API 的盈亏点；N+1 冗余如何设置。

### Q44 结构化输出（JSON/语法约束）的解码引擎怎么实现？（Constrained decoding engines）
**优先级：★★** · 对应基础知识：[Transformer_LLM与Agent_LangGraph](../../02_基础知识/10_机器学习与深度学习/05_Transformer_LLM与Agent_LangGraph.md)

**答案要点**
- 目标：保证输出符合 JSON Schema / 正则 / 上下文无关文法，减少解析失败，对 Agent 工具调用尤其重要。
- 做法：解码每步根据**有限状态机 / 下推自动机**当前状态，计算允许的下一个 token 集合，把其余 token 的 logits 设为 −∞（logit mask）；预编译文法为词表级别的 token 掩码以加速（Outlines、XGrammar、llama.cpp GBNF、vLLM guided decoding 等，细节未核对）。
- 注意：分词边界（一个 token 可能跨文法符号）、掩码计算开销（预计算与缓存）、约束可能降低回答质量（强制格式时模型"被迫"给出错误内容）→ 允许"思考后再输出结构化结果"。
- 与"提示 + 重试"对比：约束解码保证语法正确，但不保证语义正确，仍需校验层。

**English short answer**
Constrained decoding tracks a grammar automaton during generation and, at each step, masks logits of tokens that would violate the schema, so output is always syntactically valid. Engines precompile grammars into token-level masks for speed and must handle tokens that span grammar symbols. It guarantees syntax but not semantics, so tool arguments still need validation, and forcing structure can hurt answer quality unless the model may reason first.

（译：约束解码在生成过程中跟踪文法自动机，每步屏蔽会违反 schema 的 token 的 logits，使输出始终语法有效；引擎把文法预编译为 token 级掩码以加速，并需处理跨文法符号的 token；它保证语法而非语义，工具参数仍需校验，强制结构还可能损害回答质量，除非允许模型先推理。）

**追问方向**：分词边界问题；约束与"思维链后输出"的结合。

### Q45 端侧大模型推理（llama.cpp / GGUF / NPU）要点？（On-device LLM inference）
**优先级：★★** · 对应基础知识：[模型量化与边缘部署_RKNN](../../02_基础知识/10_机器学习与深度学习/04_模型量化与边缘部署_RKNN.md)

**答案要点**
- 约束：内存小（几 GB）、带宽低（LPDDR 几十 GB/s，远低于 HBM）、功耗 / 散热、算力有限 → 解码速度 ≈ 内存带宽 / 模型字节数；7B INT4（约 4 GB）在 50 GB/s 带宽下上限约 12 token/s（教学估算）。
- 技术：低比特量化（Q4_K、Q5、INT4 组量化）、mmap 加载与 KV cache 量化、小模型（1–3B）、投机解码、算子针对 ARM NEON / NPU / GPU（Metal、Vulkan、OpenCL）优化；llama.cpp + GGUF 格式是常用方案。
- NPU（如瑞芯微 RK3588 的 NPU）：支持 INT8 为主，算子覆盖受限，需要转换工具链（RKNN）；LLM 在 NPU 上需要专门的量化与分块支持（未核对）。
- 部署考虑：首 token 延迟（prefill 在端侧更慢）、热降频、电池、模型更新（OTA）。

**English short answer**
On-device inference is limited by memory size and bandwidth, so decode speed is roughly bandwidth divided by model bytes, about 12 tokens per second for a 4 GB INT4 7B model at 50 GB/s. I use low-bit group quantization, memory-mapped weights, quantized KV cache and smaller models, with kernels tuned for NEON, GPU or NPU. NPUs mostly support INT8 and need a conversion toolchain, and thermal throttling and prefill latency matter.

（译：端侧推理受内存容量与带宽限制，解码速度约等于带宽除以模型字节数（4 GB 的 INT4 7B 模型在 50 GB/s 下约 12 token/s）；用低比特分组量化、内存映射权重、量化 KV cache 和小模型，并针对 NEON、GPU 或 NPU 调优内核；NPU 多支持 INT8 并需转换工具链，需关注热降频和预填充延迟。）

**追问方向**：为什么端侧 prefill 更痛；RKNN 对 Transformer 算子的支持情况。

### Q46 LLM 评测流水线怎么搭建？（Evaluation pipeline）
**优先级：★★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 分层：**自动指标**（困惑度、选择题准确率 MMLU 类、代码 pass@k、数学 GSM8K 类）→ **LLM-as-judge**（成对比较，注意位置 / 长度 / 自偏好偏差，用交换顺序与多评委缓解）→ **人工评测**（偏好、细粒度打分）→ **线上指标**（任务成功率、用户反馈、拒答率、延迟成本）。
- 工程：固定评测集与版本、固定解码参数（温度 0 或多次采样均值）、随机种子、保存模型输出以便复核；回归套件在每次训练 / 部署前自动运行；评测数据保密与去污染。
- 任务特定评测集（领域问答、工具调用、机器人指令执行）比通用基准更能指导迭代。
- 报告：均值 ± 置信区间；显著性检验；不同能力维度雷达图。

**English short answer**
I layer automatic metrics such as multiple-choice accuracy, pass@k and perplexity, LLM-as-judge pairwise comparison with position swapping and multiple judges, human evaluation, and online metrics like task success and cost. I fix datasets, versions and decoding parameters, store outputs for audit, and run a regression suite automatically before each release. Task-specific sets such as tool-call accuracy matter more than generic benchmarks for decisions.

（译：分层使用自动指标（选择题准确率、pass@k、困惑度）、带位置交换和多评委的 LLM 裁判成对比较、人工评测和线上指标（任务成功率、成本）；固定数据集、版本和解码参数，保存输出以便复核，每次发布前自动运行回归套件；任务特定评测集（如工具调用准确率）比通用基准更能指导决策。）

**追问方向**：LLM-as-judge 的偏差来源；pass@k 的计算。

### Q47 评测污染（data contamination）怎么发现与避免？（Benchmark contamination）
**优先级：★★** · 对应基础知识：[机器学习基础](../../02_基础知识/10_机器学习与深度学习/01_机器学习基础.md)

**答案要点**
- 污染：评测题或其变体出现在训练语料中，使成绩虚高；网络爬取的数据很容易包含公开基准。
- 检测：训练集与评测集的 n-gram（如 13-gram）重叠；模型对题目逐字补全的"记忆测试"；对题目做改写 / 变量替换后成绩是否大幅下降；比较旧 / 新版本（发布时间晚于训练截止的新题，如动态基准）。
- 避免：训练前对语料做去污染过滤；评测集不公开或持续更新；使用私有留出集；报告是否做了去污染处理。
- 对用户的启示：公开基准分数只是参考；自己建业务评测集。
- 机器人：评测场景若出现在示教数据中同理构成"污染"。

**English short answer**
Contamination happens when benchmark items appear in the training data and inflate scores. I detect it with n-gram overlap, memorization probes where the model completes a question verbatim, and by checking whether performance drops on rephrased or newly written items. I prevent it by decontaminating training data, keeping private or continuously refreshed test sets and reporting the procedure.

（译：污染指评测题出现在训练数据中使分数虚高；用 n-gram 重叠、让模型逐字补全题目的记忆测试，以及检查改写或新写题目上成绩是否下降来检测；通过训练数据去污染、保留私有或持续更新的测试集并报告处理流程来避免。）

**追问方向**：动态基准的优缺点；n-gram 重叠阈值的选择。

### Q48 LLM 服务的可观测性指标有哪些？（Observability for LLM services）
**优先级：★★** · 对应基础知识：[数据与日志_可观测性_回放与复盘](../../02_基础知识/13_系统工程与安全/05_数据与日志_可观测性_回放与复盘.md)

**答案要点**
- 性能：QPS、并发数、排队时间、TTFT、TPOT / ITL、端到端延迟分位数（P50 / P95 / P99）、吞吐 tokens/s、GPU 利用率 / 显存 / KV cache 占用率、批大小、前缀缓存命中率、抢占次数。
- 质量：拒答率、格式错误率（JSON 解析失败）、工具调用成功率、用户反馈（赞 / 踩）、人工抽检评分、幻觉抽检；离线评测回归。
- 成本：每请求 token 数、每百万 token 成本、GPU 小时。
- 稳定性：错误率、超时率、OOM、重启次数、模型版本。
- 工具：Prometheus + Grafana、OpenTelemetry 追踪（每个请求的 prompt、检索、工具调用、模型调用）；日志需要脱敏。
- 告警：SLO 违约、KV cache 接近满载、队列长度异常增长。

**English short answer**
I monitor latency percentiles including time to first token and per-token latency, throughput, queueing, GPU and KV cache utilization and prefix cache hit rate, plus quality signals such as format error rate, tool-call success, refusal rate and sampled human ratings. Tracing each request across retrieval, tools and model calls makes debugging possible, logs are redacted for privacy, and alerts fire on SLO violations or a saturated cache.

（译：监控包括首 token 与每 token 延迟等分位数、吞吐、排队、GPU 与 KV cache 利用率、前缀缓存命中率，以及格式错误率、工具调用成功率、拒答率和抽样人工评分等质量信号；对每个请求在检索、工具、模型调用间做追踪便于排障，日志脱敏，SLO 违约或缓存饱和时告警。）

**追问方向**：P99 延迟与排队的关系；如何追踪一次 Agent 多步调用。

### Q49 LLM 应用的安全工程：提示注入、越狱与数据泄露？（LLM application security）
**优先级：★★★** · 对应基础知识：[信息安全与权限_DDS-Security_OTA安全](../../02_基础知识/13_系统工程与安全/06_信息安全与权限_DDS-Security_OTA安全.md)

**答案要点**
- 威胁：**直接提示注入**（用户指令覆盖系统提示）、**间接提示注入**（网页 / 文档 / 工具返回内容中嵌入恶意指令）、越狱、训练数据 / 系统提示泄露、工具滥用（越权操作）、不安全输出（XSS、SQL 注入、命令执行）、拒绝服务（超长输入 / 昂贵调用）。
- 防御：①不信任任何模型输入输出——把外部内容当数据，用分隔符 / 结构化通道隔离；②**最小权限**（工具白名单、参数校验、只读优先）；③输出校验与沙箱执行；④高风险动作人在回路确认；⑤输入输出过滤与内容审核模型；⑥速率限制与预算上限；⑦日志审计与红队测试。
- 原则：安全不依赖模型"听话"，而依赖**确定性控制层**；对机器人，LLM 输出的动作必须经安全层校验后才能执行。

**English short answer**
Threats include direct and indirect prompt injection, jailbreaks, leakage of system prompts or data, tool misuse and unsafe outputs that reach interpreters. I treat all model inputs and outputs as untrusted, isolate external content from instructions, enforce least-privilege tools with parameter validation, sandbox execution, require human confirmation for risky actions, rate-limit, and audit and red-team regularly. Security must rest on deterministic controls, not on the model complying.

（译：威胁包括直接/间接提示注入、越狱、系统提示或数据泄露、工具滥用以及传到解释器的不安全输出；把所有模型输入输出视为不可信，隔离外部内容与指令，最小权限的工具加参数校验，沙箱执行，高风险动作需人工确认，限流，并定期审计和红队测试；安全必须建立在确定性控制上，而非依赖模型听话。）

**追问方向**：间接注入的真实例子；如何在 RAG 中隔离不可信文档。

### Q50 推理结果的可复现性与采样确定性？（Reproducibility of LLM outputs）
**优先级：★★** · 对应基础知识：[Transformer_LLM与Agent_LangGraph](../../02_基础知识/10_机器学习与深度学习/05_Transformer_LLM与Agent_LangGraph.md)

**答案要点**
- 温度 0（贪心）理论上确定，但实际仍可能不同：①GPU 浮点运算并行归约顺序不同（非结合律）；②批大小不同导致不同内核与累加顺序（batch invariance 问题）；③不同硬件 / 驱动 / 库版本；④MoE 路由的微小差异放大；⑤分布式 TP 的 All-Reduce 顺序。
- 提升可复现：固定种子、固定批大小（或使用批不变内核）、固定版本与硬件、确定性算子模式；仍可能差异。
- 工程影响：评测需多次采样取均值；日志保存完整请求和采样参数；回归测试允许容差（语义等价而非逐字相同）。
- 机器人决策链：对关键决策用温度 0 + 规则校验；记录 trace 以便重放。

**English short answer**
Even at temperature zero outputs can differ because floating-point reductions are not associative, so batch size, kernels, hardware, library versions and tensor-parallel reduction order change low-order bits that can flip a token. I fix seeds and versions, use deterministic or batch-invariant kernels where possible, average multiple samples in evaluation, and log full requests so decisions can be replayed. Regression tests should compare semantics with tolerance, not exact strings.

（译：即使温度为 0，输出也可能不同，因为浮点归约不满足结合律，批大小、内核、硬件、库版本和张量并行归约顺序会改变低位比特并可能翻转某个 token；固定种子和版本，尽量用确定性或批不变内核，评测时对多次采样取平均，记录完整请求以便重放决策；回归测试应按语义容差比较而非逐字比对。）

**追问方向**：批不变性为何难；如何设计对非确定性鲁棒的回归测试。

## 七、补充：分词、优化器、长上下文与排障

### Q51 分词器（tokenizer）的训练与词表大小怎么权衡？（Tokenizer design）
**优先级：★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 主流为子词算法：**BPE**（反复合并最高频相邻对）、WordPiece、Unigram（SentencePiece）；字节级 BPE 保证任意文本可编码（无 UNK）。
- 词表大小权衡：词表大 → 同一文本 token 更少（序列短、训练推理更快、上下文更能装），但嵌入层和输出层 softmax 变大（参数与显存、小语种 token 训练不足）；词表小 → 序列长、算力增。常见范围数万到十几万（量级，未核对）。
- 多语言与代码：用多语料训练分词器，否则中文 / 代码被拆成很多字节 token（效率低）；数字切分策略影响算术能力。
- 工程：特殊 token（BOS/EOS/聊天角色）、训练后不要随意更换词表；"token 数"决定成本与上下文长度。
- 评估：压缩率（字节/token）、对各语言的公平性。

**English short answer**
Subword tokenizers such as byte-level BPE or Unigram balance sequence length against vocabulary size. A larger vocabulary shortens sequences and speeds up training and inference, but enlarges the embedding and output layers and leaves rare tokens undertrained. The tokenizer must be trained on the actual language and code mix, otherwise Chinese or code fragments into many tokens and costs rise. Special tokens must be consistent between training and serving.

（译：字节级 BPE、Unigram 等子词分词器在序列长度与词表大小间权衡；词表大则序列短、训练推理快，但嵌入层和输出层变大、稀有 token 训练不足；分词器须用真实的语言与代码混合训练，否则中文或代码会被拆成很多 token 使成本上升；特殊 token 在训练和服务间必须一致。）

**追问方向**：BPE 的合并过程；数字分词对算术的影响。

### Q52 大模型训练常用优化器及内存优化（8-bit Adam、Lion、Muon 等）？（Optimizers for LLMs）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- **AdamW** 是默认：每参数两个 FP32 状态（8 字节），占显存大头。常见 $\beta_1=0.9,\beta_2=0.95$（大模型常用 0.95 提高稳定）、$\epsilon=10^{-8}$、权重衰减 0.1（量级）。
- 省显存：**8-bit Adam / 分页优化器**（量化状态）、Adafactor（因子化二阶矩）、将优化器状态卸载到 CPU / NVMe、ZeRO 分片。
- 其他：**Lion**（只用符号动量，状态少）、**Sophia**（二阶近似）、**Muon**（对矩阵参数做正交化更新，近期研究，效果与适用性未核对）。
- 选择：稳妥用 AdamW + 合理调度；资源紧用 8-bit 状态或 LoRA；尝试新优化器需在小规模验证并比较相同算力下的 loss。
- 权重衰减不应用于偏置和归一化参数。

**English short answer**
AdamW is the default and keeps two FP32 states per parameter, which dominates memory. To save memory I use 8-bit or paged optimizer states, Adafactor's factorized second moment, CPU offload or ZeRO sharding. Newer optimizers such as Lion or Muon promise better efficiency but should be validated at small scale against AdamW at equal compute. Weight decay is typically excluded from biases and norm parameters.

（译：AdamW 是默认选择，每参数两个 FP32 状态，占显存大头；用 8 位或分页优化器状态、Adafactor 的因子化二阶矩、CPU 卸载或 ZeRO 分片节省显存；Lion、Muon 等新优化器宣称效率更高，但应在小规模、相同算力下与 AdamW 对比验证；权重衰减通常不用于偏置和归一化参数。）

**追问方向**：为什么大模型 $\beta_2$ 取 0.95；Adafactor 的因子化。

### Q53 如何用 profiler 找到训练/推理的瓶颈？（GPU profiling）
**优先级：★★★** · 对应基础知识：[日志_诊断_性能剖析_perf_tracing](../../02_基础知识/12_机器人软件/13_日志_诊断_性能剖析_perf_tracing.md)

**答案要点**
- 工具：PyTorch Profiler（算子级时间线、TensorBoard 插件）、NVIDIA Nsight Systems（系统级时间线：CPU/GPU/通信重叠）、Nsight Compute（单内核指标：占用率、带宽、算术强度）。
- 步骤：①测整体步时间与吞吐，算 MFU；②时间线看 GPU 是否有空洞（数据加载 / CPU 瓶颈 / 同步点 / 小内核发射开销）；③看通信是否暴露；④找占时最长的内核，判断是 memory-bound 还是 compute-bound；⑤改一个因素再测。
- 常见发现：数据加载慢（GPU 等待）、频繁 `.item()`/同步、内核太小（用 CUDA graph / 融合）、通信未重叠、负载不均衡（慢卡）、显存碎片。
- 习惯：预热几步再计时；多次测量；记录基线。

**English short answer**
I compute throughput and utilization first, then use a system-level timeline to look for GPU idle gaps caused by data loading, host synchronization, tiny kernels or exposed communication, and a kernel-level profiler to see whether hot kernels are memory- or compute-bound. I change one thing at a time and re-measure after warm-up. Typical fixes are faster data loading, fewer sync points, CUDA graphs, kernel fusion and better overlap.

（译：先算吞吐和利用率，再用系统级时间线查找由数据加载、主机同步、小内核或暴露的通信造成的 GPU 空闲间隙，并用内核级 profiler 判断热点内核是访存受限还是算力受限；一次只改一个因素并在预热后重新测量；常见修复有加速数据加载、减少同步点、CUDA graph、内核融合和更好的重叠。）

**追问方向**：CUDA graph 的作用；如何判断 CPU 发射瓶颈。

### Q54 训练 OOM（显存溢出）怎么排查？（Debugging out-of-memory）
**优先级：★★★** · 对应基础知识：[日志_诊断_性能剖析_perf_tracing](../../02_基础知识/12_机器人软件/13_日志_诊断_性能剖析_perf_tracing.md)

**答案要点**
- 先分解显存：参数 / 梯度 / 优化器状态是固定的（按模型规模估算），**激活**随批大小与序列长度变化；用 `torch.cuda.memory_summary` / `memory_snapshot` 看峰值分配与碎片。
- 处理顺序：①降批大小 + 梯度累积；②开激活重计算；③混合精度（BF16）；④ZeRO/FSDP 分片、CPU offload；⑤FlashAttention、融合交叉熵（避免物化巨大 logits：$b\times s\times V$）；⑥缩短序列 / 打包；⑦检查泄漏（保留了含计算图的张量，如累加 loss 未 `.item()` / `.detach()`）；⑧碎片化：`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。
- 峰值常出现在**第一步反向**或**优化器步骤**、评估时（忘记 `no_grad`）。
- 多卡不均衡：不同卡峰值不同（最慢 / 最大那张决定 OOM）。

**English short answer**
I split memory into the fixed part, namely parameters, gradients and optimizer states, and the activation part that depends on batch and sequence length, and inspect a memory snapshot for peaks and fragmentation. Then I reduce micro-batch with accumulation, enable recomputation and BF16, shard with ZeRO or FSDP, use FlashAttention and fused cross-entropy to avoid huge logits, and check for leaks such as keeping graph-attached losses. Evaluation without no_grad is a classic cause.

（译：把显存分为固定部分（参数、梯度、优化器状态）和随批大小与序列长度变化的激活部分，查看显存快照找峰值与碎片；然后用梯度累积减小微批、开启重计算与 BF16、用 ZeRO/FSDP 分片、用 FlashAttention 与融合交叉熵避免巨大的 logits，并检查保留计算图的 loss 等泄漏；评估时忘记 no_grad 是经典原因。）

**追问方向**：为什么 logits 张量会很大；碎片化的表现与缓解。

### Q55 长上下文训练与位置编码外推（RoPE scaling、YaRN）？（Long-context training）
**优先级：★★** · 对应基础知识：[大语言模型预训练_微调_RAG与VLA](../../02_基础知识/10_机器学习与深度学习/08_大语言模型预训练_微调_RAG与VLA.md)

**答案要点**
- 直接在长序列上从头训练代价极高（注意力与激活）。常用**分阶段**：先在短上下文（如 4K）预训练，再用少量长文本数据**继续训练**扩展上下文。
- RoPE 外推问题：超出训练长度的位置使旋转角度分布外，性能骤降。方法：**位置插值（PI）**把位置压缩到训练范围；**NTK-aware / YaRN** 按频率分段缩放（高频保持、低频插值）并调整注意力温度；调基频 $\theta$ 增大（如 10k→1M 量级）；再用少量步数微调适应。
- 数据：需要真实的长依赖数据（长文档、代码仓库）而不只是拼接短文；评估用针堆、长文问答、多文档检索，而不仅是困惑度。
- 系统：需要上下文并行 / 序列并行、KV cache 压缩支撑长序列推理。

**English short answer**
Training long sequences from scratch is expensive, so models are usually pretrained at a short context and then extended with a small amount of continued training on long data. Rotary embeddings fail beyond the trained length, so I use position interpolation, NTK-aware or YaRN scaling and a larger rotary base, followed by brief fine-tuning. Data needs genuine long-range dependencies, and evaluation should include needle-in-a-haystack and long-document tasks, not just perplexity.

（译：从头训练长序列代价高昂，所以通常先在短上下文预训练，再用少量长数据继续训练扩展；RoPE 超出训练长度会失效，用位置插值、NTK-aware/YaRN 缩放和更大的旋转基频，并短时微调；数据需要真正的长程依赖，评估应包含针堆和长文档任务，而非仅困惑度。）

**追问方向**：YaRN 为什么按频率分段；长上下文数据如何构造。

### Q56 数据加载为什么常成为训练瓶颈？怎么优化？（Data loading bottlenecks）
**优先级：★★** · 对应基础知识：[日志_诊断_性能剖析_perf_tracing](../../02_基础知识/12_机器人软件/13_日志_诊断_性能剖析_perf_tracing.md)

**答案要点**
- 现象：GPU 利用率周期性掉到 0%，时间线显示 GPU 等数据。原因：磁盘 / 网络读取慢、解码 / 增强在 CPU 上慢、小文件过多、预处理（分词）在线进行、worker 数不够、数据在远端对象存储。
- 优化：预先分词并存成**二进制连续格式**（memmap、Arrow、WebDataset/tar 分片、MosaicML streaming）；多 worker 并行 + `prefetch_factor` + `pin_memory` + 非阻塞传输；GPU 端增强（DALI、Kornia）；本地 NVMe 缓存；数据按分片顺序读 + 分片内随机（平衡随机性与 IO）；确定性可恢复的数据顺序（记录 shard 与偏移）。
- 机器人数据：多相机视频解码是主要瓶颈 → 预解码成图像分片 / 用硬件解码；HDF5 小块读取慢可改用 Zarr / LeRobot 格式（未核对）。
- 度量：数据加载等待时间占比。

**English short answer**
When GPU utilization periodically drops to zero, the data pipeline is starving it. I pre-tokenize into contiguous binary shards, use several workers with prefetching and pinned memory, move augmentation to the GPU, cache on local NVMe, and shuffle at shard level plus within-shard. The loader's position must be deterministic and resumable. For robot data, video decoding of multiple cameras is usually the bottleneck, so I pre-decode or use hardware decoders.

（译：GPU 利用率周期性降到零说明数据管道供不上；预先分词存成连续二进制分片、多 worker 加预取和锁页内存、把增强搬到 GPU、本地 NVMe 缓存，并用分片级加分片内随机打乱；加载器位置须确定且可恢复；机器人数据中多相机视频解码通常是瓶颈，应预解码或使用硬件解码器。）

**追问方向**：分片级打乱对随机性的影响；视频解码的硬件加速。

### Q57 分布式训练卡死（hang）或 NCCL 超时怎么排查？（NCCL hangs and timeouts）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 症状：训练停住无输出、NCCL watchdog 超时、某些 rank 退出而其余等待。
- 常见原因：①各 rank 执行的集合通信**顺序或数量不一致**（某 rank 因条件分支少调用了一次 All-Reduce，例如不同卡的数据导致跳过某层 / 未使用参数）；②某个 rank 崩溃 / OOM 后其余卡永远等待；③网络问题（IB/RoCE 配置、防火墙、网卡选择错误）；④数据不均衡导致某卡处理更久（慢节点）；⑤死锁（线程 / 数据加载进程）。
- 手段：设置 `NCCL_DEBUG=INFO`、`TORCH_DISTRIBUTED_DEBUG=DETAIL`；缩小规模（2 卡）复现；检查每个 rank 日志找最先出错的；`find_unused_parameters` 的使用；给集合通信设置合理的超时并开启异步错误处理；用 `py-spy dump` 查看卡住进程的栈。
- 预防：确保所有 rank 的控制流一致；对数据长度做平衡；健康检查脚本（all-reduce 小测试）。

**English short answer**
A hang usually means ranks disagree on collective calls, for example one rank skipped an all-reduce because of a conditional branch or unused parameters, or one rank crashed and the others wait forever. I enable NCCL and distributed debug logs, reproduce on two GPUs, look for the first failing rank, and dump stacks of stuck processes. I also verify network configuration and keep control flow identical across ranks.

（译：卡死通常意味着各 rank 对集合通信调用不一致（如某 rank 因条件分支或未使用参数少调了一次 All-Reduce），或某 rank 崩溃而其余无限等待；开启 NCCL 与分布式调试日志、用两卡复现、找出最先出错的 rank 并导出卡住进程的栈，同时核对网络配置并保证各 rank 控制流一致。）

**追问方向**：未使用参数为何导致 DDP 卡死；如何定位慢节点。

### Q58 推理时的采样参数与 logits 处理器有哪些？（Sampling parameters and logits processors）
**优先级：★★★** · 对应基础知识：[Transformer_LLM与Agent_LangGraph](../../02_基础知识/10_机器学习与深度学习/05_Transformer_LLM与Agent_LangGraph.md)

**答案要点**
- **温度**：logits 除以 $T$，$T\to0$ 趋近贪心，$T>1$ 更随机；**top-k**：只保留概率最高 k 个；**top-p（核采样）**：保留累计概率达 p 的最小集合；**min-p**：相对最大概率设阈值。
- **重复惩罚 / 频率 / 存在惩罚**：对已出现 token 降低 logits，缓解循环重复，过强会伤害正确性（代码、专有名词）。
- 约束：logit bias、禁用词、语法约束、`max_tokens`、停止序列。
- 确定性任务（工具调用、结构化抽取、机器人动作指令）用低温（0–0.2）；创意用较高温。
- 多样性：n 个采样 + 重排序 / 多数投票（self-consistency）。
- 实现顺序：logits → 惩罚 → 温度 → top-k/top-p → 归一化 → 采样；顺序影响结果。

**English short answer**
Temperature rescales logits, top-k and top-p truncate the candidate set, and min-p thresholds relative to the top probability. Repetition and frequency penalties reduce loops but can hurt exact outputs such as code or names. Logit bias, stop sequences and grammars constrain output. For tool calls and robot commands I use low temperature, and for reasoning I may sample multiple answers and take a majority vote.

（译：温度缩放 logits，top-k/top-p 截断候选集，min-p 按相对最大概率设阈值；重复/频率惩罚缓解循环但可能损害代码或专有名词等精确输出；logit bias、停止序列和文法约束输出；工具调用和机器人命令用低温，推理任务可多次采样后多数投票。）

**追问方向**：top-p 与温度的作用顺序；self-consistency 的原理。

### Q59 模型文件格式与加载：safetensors、GGUF、ONNX、TensorRT？（Model formats）
**优先级：★★** · 对应基础知识：[模型量化与边缘部署_RKNN](../../02_基础知识/10_机器学习与深度学习/04_模型量化与边缘部署_RKNN.md)

**答案要点**
- **safetensors**：安全（不执行代码，不同于 pickle 的 `.bin`/`.pt`）、零拷贝 mmap 加载、跨框架，Hugging Face 权重主流格式。PyTorch `.pt` 基于 pickle，加载不可信文件有任意代码执行风险。
- **GGUF**：llama.cpp 的单文件格式，含权重（多种量化）、分词器与元数据，适合 CPU / 端侧推理。
- **ONNX**：跨框架的计算图中间表示，配合 ONNX Runtime / TensorRT / 各 NPU 工具链转换（算子覆盖与动态形状是常见坑）。
- **TensorRT 引擎**：针对特定 GPU 和精度编译的优化引擎，**不可跨 GPU 型号 / TensorRT 版本移植**；**RKNN**（瑞芯微）、**TFLite/CoreML** 面向端侧。
- 实务：训练用 PyTorch + safetensors；部署时转换并**校验转换前后输出一致**（容差内），保存校准数据与转换脚本版本。

**English short answer**
Safetensors is a safe, memory-mappable weight format, unlike pickle-based checkpoints that can execute arbitrary code on load. GGUF packages quantized weights, tokenizer and metadata for llama.cpp, ONNX is a portable graph format for runtimes and NPU toolchains, and TensorRT engines are compiled for a specific GPU and version. After any conversion I verify that outputs match the original within tolerance and record the toolchain versions.

（译：safetensors 是安全、可内存映射的权重格式，不同于加载时可能执行任意代码的 pickle 检查点；GGUF 为 llama.cpp 打包量化权重、分词器与元数据，ONNX 是供运行时和 NPU 工具链使用的可移植计算图格式，TensorRT 引擎针对特定 GPU 与版本编译；任何转换后都要验证输出与原模型在容差内一致并记录工具链版本。）

**追问方向**：pickle 的安全风险；ONNX 导出动态形状的坑。

### Q60 如何做 MoE 模型的推理部署？有什么挑战？（MoE inference）
**优先级：★★** · 对应基础知识：[大模型训练与推理工程](../../02_基础知识/10_机器学习与深度学习/15_大模型训练与推理工程.md)

**答案要点**
- 总参数大（需放下全部专家），每 token 仅激活 top-k 专家 → 计算量小但**显存和带宽占用按总参数计**；小批量时每个专家被少量 token 命中，专家利用率低，权重读取摊销差，解码阶段仍是带宽受限。
- 挑战：专家并行的 All-to-All 通信延迟、负载不均衡（热门专家成瓶颈）、批内不同 token 路由到不同专家导致小矩阵乘。
- 对策：专家并行 + 张量并行混合、专家复制热点、通信与计算重叠、大批量提升专家利用率、专家量化、冷专家卸载 CPU（小批量场景）。
- 选择：高吞吐大批量服务适合 MoE；端侧 / 低并发更适合稠密小模型。

**English short answer**
An MoE model activates few experts per token but all experts must stay in memory, so memory and weight traffic follow the total parameters. At small batch sizes each expert sees few tokens, hurting efficiency, and expert parallelism adds all-to-all latency and load imbalance. Remedies include mixing expert and tensor parallelism, replicating hot experts, overlapping communication, larger batches and quantization. MoE suits high-throughput serving more than on-device use.

（译：MoE 模型每 token 只激活少数专家，但所有专家都必须驻留内存，因此显存与权重流量按总参数计；小批量时每个专家分到的 token 很少，效率差，专家并行还带来 All-to-All 延迟和负载不均；对策是专家并行与张量并行混合、复制热门专家、通信重叠、增大批量与量化；MoE 更适合高吞吐服务而非端侧。）

**追问方向**：为什么 MoE 解码仍是带宽受限；热点专家复制的权衡。

### Q61 训练 / 推理中的随机性与种子管理（实验可复现）？（Seed management）
**优先级：★★**

**答案要点**
- 需要固定的随机源：Python、NumPy、PyTorch（CPU/CUDA）、数据加载 worker 的种子与洗牌顺序、dropout、数据增强、采样、权重初始化、分布式各 rank 的种子。
- 确定性算子：`torch.use_deterministic_algorithms(True)`、`cudnn.deterministic`，会损失部分速度；某些操作（如 atomicAdd 的 scatter）天然非确定。
- 实践：每次实验记录种子、代码 commit、配置、数据版本、环境（依赖锁）；多个种子重复实验报告均值方差，**差异小于种子方差的改进不可信**。
- 分布式：各 rank 的数据顺序要不同但可复现（`seed + rank`）；dropout 种子在 TP 组内需一致 / 不一致的区分（实现细节未核对）。
- 机器人：仿真随机化（物体位姿、噪声）也需可复现种子，便于复现失败案例。

**English short answer**
I seed Python, NumPy, PyTorch on CPU and GPU, the data loader and shuffling, and each distributed rank, and enable deterministic algorithms when I need exact reproducibility, accepting some slowdown. I log seed, commit, configuration and data version, and run several seeds, because improvements smaller than the seed-to-seed variance are not reliable. Simulation randomization should also be seeded so failures can be replayed.

（译：固定 Python、NumPy、CPU/GPU 上的 PyTorch、数据加载与洗牌以及各分布式 rank 的种子，需要精确复现时启用确定性算法并接受一定变慢；记录种子、commit、配置与数据版本，并用多个种子运行，因为小于种子间方差的改进不可信；仿真的随机化也要设种子以便重放失败。）

**追问方向**：为什么有些 CUDA 操作不确定；多种子实验的统计报告方式。

## 本章要点速记
1. 训练 FLOPs ≈ $6ND$；显存（混合精度 + Adam）≈ 16 字节/参数 + 激活；MFU 衡量利用率。
2. DP 靠 All-Reduce；ZeRO/FSDP 分片优化器/梯度/参数；TP 切层内矩阵（节点内）；PP 切层组（跨节点，有气泡）；3D 并行按通信强度匹配互联。
3. 激活重计算以约 33% 算力换大量显存；FlashAttention 分块 + 在线 softmax 避免物化 $s\times s$ 矩阵。
4. 稳定性：梯度裁剪、预热、BF16、QK-Norm；loss spike 回滚并跳过坏数据；频繁 checkpoint + 容错。
5. 数据：清洗、质量分类、MinHash 去重、去污染、配比；打包要配文档级掩码。
6. 微调：聊天模板一致、只对 assistant 计损失；LoRA 对所有线性层；DPO/KTO 简化 RLHF；防遗忘用回放与低秩。
7. 推理：prefill 算力受限、decode 带宽受限；vLLM = PagedAttention + 连续批处理；前缀缓存、量化、投机解码、PD 分离。
8. 评测与安全：固定评测协议并去污染；把外部内容当不可信数据，用确定性控制层兜底。
