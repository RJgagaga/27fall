### B. 围绕 PS 的追问

#### Q5. Give one example where a software problem, not the control law, was the real cause.

**中文：** 举一个真正原因是软件问题而不是控制律的例子。

> **参考回答（English）**
>
> On the car-like robot, the pose drifted and jumped. It looked like an estimator problem, but the causes were inconsistent timing, coordinate frames and motion direction between the sensors. The control law and the filter were fine once the inputs were consistent. The same pattern appeared at Kaihong: motion-control code could not be reused across hardware until timestamps, frames and validity checks were standardised. In both cases the fix was not a cleverer algorithm but a clearer contract about what data means. For example, a timestamp field and a frame identifier on every state message, so that every consumer knows when and in which frame a value was measured. I cannot share internal interface names.
>
> **中文译文：** 在车式机器人上，位姿漂移和跳变。看起来像估计器问题，但原因是各传感器之间时间、坐标系和运动方向不一致。输入一致之后，控制律和滤波器都没问题。同样的模式在深开鸿再次出现：在时间戳、坐标系和有效性检查被统一之前，运动控制代码不能跨硬件复用。两次的解决办法都不是更聪明的算法，而是关于「数据含义」的更清晰的约定。 例如在每条状态消息上统一加上时间戳字段和坐标系标识，让每个使用方都知道数值是何时、在哪个坐标系下测得的。内部接口名称我不便透露。


#### Q6. What makes a good interface for a robot platform?

**中文：** 什么样的接口算是好的机器人平台接口？

> **参考回答（English）**
>
> I look for four things. First, it hides hardware details but not important limits, such as the actuator's maximum value. Second, every message carries what a consumer needs to judge it: timestamp, frame and validity. Third, it is stable and versioned, so code above it does not break when a driver changes. Fourth, it is testable: I can run the upper layers against a fake device. This is how I think about the capability model at Kaihong, though I should say I learned it by doing, and I want to study design methods properly.
>
> **中文译文：** 我看四点。第一，隐藏硬件细节，但不隐藏重要限制（如执行器最大值）。第二，每条消息都带着使用者判断它所需的信息：时间戳、坐标系和有效性。第三，稳定且有版本，驱动变化时上层代码不被破坏。第四，可测试：我能用假设备运行上层。这是我对深开鸿能力模型的思考方式，但需要说明，这些是我边做边学的，我想系统学习设计方法。


#### Q7. What does robot state management mean in your work?

**中文：** 你工作中的“机器人状态管理”指什么？

> **参考回答（English）**
>
> Perception and actuator feedback come from many sources, with different clocks, coordinate frames and quality. I standardised the timestamps, coordinate frames and validity checks across them, so the motion-control layer and the task layer see one consistent, trusted robot state. In plain words: before a number is used to make a decision, it should say when it was measured, in which frame, and whether it is still valid. Typical rules are: reject data older than a time limit, reject values outside a physically possible range, and flag a source that has stopped updating. The exact limits are internal to the platform, so I describe the principle.
>
> **中文译文：** 感知和执行器反馈来自多个来源，时钟、坐标系和质量各不相同。我统一了它们的时间戳、坐标系和有效性检查，让运动控制层和任务层看到一致、可信的机器人状态。通俗地说：一个数字被用来做决策之前，应该说明它是什么时候测的、在哪个坐标系下、现在是否仍然有效。 典型规则包括：超过时限的数据拒绝、超出物理可能范围的数值拒绝、停止更新的来源要标记。具体限值属于平台内部信息，我只讲原则。


#### Q8. How would you secure task dispatch in a multi-robot fleet?

**中文：** 如何保障多机器人系统中任务派发的安全？

> **参考回答（English）**
>
> I would think in layers. Authentication: every device and every controller proves who it is, for example with certificates. Authorisation: each identity has permissions for specific actions. Integrity and confidentiality: messages are signed and, where needed, encrypted so they cannot be tampered with or replayed; including a nonce or timestamp helps against replay. Then a policy check before execution, as in my Kaihong chain, so even an authorised but unsafe command is refused. Finally, logging and auditing. I should be honest that I have not formally studied security design; I know these as principles, and this is an area I want to learn properly.
>
> **中文译文：** 我会分层考虑。认证：每个设备和控制端都要证明身份，例如使用证书。授权：每个身份只拥有特定动作的权限。完整性与机密性：消息签名，必要时加密，防止篡改和重放；加入 nonce 或时间戳可抵御重放。然后在执行前做策略检查（如深开鸿那条链），即使是被授权但不安全的命令也会被拒绝。最后是日志与审计。需要坦诚地说，我没有系统学过安全设计，这些是我知道的原则，也是我想认真学习的领域。


#### Q9. In a distributed robot system, how do you keep state consistent?

**中文：** 在分布式机器人系统里，如何保持状态一致？

> **参考回答（English）**
>
> Perfect consistency is expensive, so I first ask which state truly needs it. A common approach is to have one owner for each piece of state, publish changes with a version or timestamp, and let others treat their copy as a cache with an expiry. For commands, make them idempotent or give each an id, so duplicates caused by retries are harmless. Clocks should be synchronised, or at least the offset known, because ordering by timestamp is meaningless otherwise. Then add validity checks so that stale data is not used for decisions. This matches the standardisation of timestamps, frames and validity I did on the Kaihong platform.
>
> **中文译文：** 完美一致代价很高，所以我先问：哪些状态真的需要一致。常见做法是每份状态只有一个所有者，用版本号或时间戳发布变化，其他节点把自己的副本当作带有效期的缓存。对于命令，要让它们幂等或为每条命令分配 id，使重试造成的重复无害。时钟应当同步，至少要知道偏移，否则按时间戳排序毫无意义。再加上有效性检查，避免用过期数据做决策。这与我在深开鸿平台上统一时间戳、坐标系和有效性检查的工作一致。


### C. 项目深挖：P6 及相关

#### Q10. What is the unified capability model you built at Kaihong?

**中文：** 你在深开鸿做的统一能力模型是什么？

> **参考回答（English）**
>
> On the M-Robots platform, different robots have different sensors, actuators and controllers. I built a unified capability model in C++ on OpenHarmony that describes all of them in the same way, and I mapped ROS and ROS2 motion commands onto the low-level drivers. The benefit is reuse: motion-control code does not have to be rewritten for each piece of hardware, because it talks to the capability interface instead of the specific driver. A capability description states what a device can do, such as the kind of sensor or actuator and the commands it accepts, in one common format. I worked on the sensor, actuator and controller side of this model; hardware details are internal, so I describe the design rather than list products.
>
> **中文译文：** 在 M-Robots 平台上，不同机器人有不同的传感器、执行器和控制器。我在 OpenHarmony 上用 C++ 建立统一能力模型，用同一种方式描述它们，并把 ROS 和 ROS2 的运动指令映射到底层驱动。好处是复用：运动控制代码不需要为每种硬件重写，因为它面向的是能力接口，而不是具体驱动。 能力描述用统一格式说明设备能做什么，例如传感器或执行器的类型和接受的指令。我负责这个模型中传感器、执行器和控制器这一侧；硬件细节属于内部信息，我讲设计而不列产品。


#### Q11. Explain the action-proposal, policy-check, execution and state-feedback chain.

**中文：** 讲讲“动作提议、策略检查、执行、状态反馈”这条链。

> **参考回答（English）**
>
> A high-level task plan, for example from a planner or an AI model, is never sent straight to the robot. First it becomes an action proposal. Then a policy check decides whether the action is allowed in the current state. Only if it passes does it go to execution. Finally, the state feedback tells the system what actually happened, which closes the loop. The idea is that an AI decision and a physical action are different things, and the checks sit between them. Typical checks in such a chain cover the speed limit, the allowed area, the device state and the permission of the requester. If a proposal fails, it is rejected, the reason is reported back through state feedback, and nothing moves.
>
> **中文译文：** 高层任务计划（例如来自规划器或 AI 模型）绝不会直接发给机器人。它先成为一个动作提议；然后由策略检查判断在当前状态下是否允许；通过后才进入执行；最后状态反馈告诉系统实际发生了什么，闭合回路。思想是：AI 的决策和物理动作是两回事，检查就放在它们之间。 这类链条里典型的检查包括速度限制、允许的区域、设备状态和请求方的权限。提议未通过时会被拒绝，原因通过状态反馈返回，执行器不会动。


#### Q12. What did you implement over M-DDS?

#### Q13. If the vehicle behaved badly, how would you find out which module is responsible?

#### Q15. What safeguards did you add to keep the hardware loop safe?

### D. CS 基础与工程

#### Q16. What is the difference between a process and a thread?

**中文：** 进程和线程有什么区别？

> **参考回答（English）**
>
> A process is an instance of a program with its own address space and resources; a thread is a unit of execution inside a process, and threads in the same process share memory. Creating and switching threads is cheaper, and sharing data is easy, but that makes data races possible, so shared data needs synchronisation, such as mutexes. Processes are isolated: one crash does not usually bring down another, but communication needs IPC. On a robot, I would put safety-critical or crash-prone components into separate processes, and use threads inside one component.
>
> **中文译文：** 进程是拥有独立地址空间和资源的程序实例；线程是进程内的执行单元，同一进程的线程共享内存。线程创建和切换开销更小，共享数据也方便，但这会带来数据竞争，所以共享数据需要互斥锁等同步手段。进程之间相互隔离：一个崩溃通常不会拖垮另一个，但通信需要 IPC。在机器人上，我会把安全关键或容易崩溃的组件放进不同进程，在单个组件内部使用线程。


#### Q17. What is a deadlock? How do you prevent it?

**中文：** 什么是死锁？如何预防？

> **参考回答（English）**
>
> A deadlock is when a set of threads are each waiting for a resource held by another, so none can proceed. The four conditions are mutual exclusion, hold and wait, no pre-emption and circular wait. Preventing it means breaking one of them. In practice the simplest is a global lock ordering, so everyone acquires locks in the same order, plus using try-lock with timeouts, keeping critical sections short, and avoiding calling unknown code while holding a lock. In real-time systems, there is also priority inversion, which RTOS mutexes with priority inheritance address.
>
> **中文译文：** 死锁是指一组线程各自等待对方持有的资源，导致都无法继续。四个必要条件是互斥、占有并等待、不可抢占和循环等待。预防就是打破其中之一。实践中最简单的是规定全局加锁顺序，让所有人按同样顺序加锁，再配合带超时的 try-lock、缩短临界区、持锁时不调用未知代码。在实时系统中还有优先级反转，RTOS 的优先级继承互斥量可以解决。


#### Q18. TCP versus UDP: which would you use for robot control messages, and why?

**中文：** TCP 与 UDP：机器人控制消息你会用哪个？为什么？

> **参考回答（English）**
>
> TCP is reliable and ordered, using acknowledgements and retransmission, but retransmission can add delay and head-of-line blocking. UDP is connectionless with no delivery guarantee, but low overhead and low latency. For high-rate state or control streams, where the newest value matters more than an old lost one, UDP-like transports with timestamps are often preferred; for configuration, commands that must arrive, or file transfer, TCP or a reliable mode is better. DDS lets you choose per topic through QoS, such as best-effort versus reliable, which fits both cases.
>
> **中文译文：** TCP 可靠且有序，使用确认和重传，但重传可能带来延迟和队头阻塞。UDP 无连接、不保证送达，但开销小、延迟低。对高频的状态或控制流，最新的值比丢失的旧值更重要，常选用带时间戳的类 UDP 传输；对配置、必须送达的命令或文件传输，则更适合 TCP 或可靠模式。DDS 可以通过 QoS 按主题选择（best-effort 或 reliable），两种情形都能覆盖。


#### Q19. What is publish-subscribe, and how is DDS different from a simple socket?

**中文：** 什么是发布-订阅？DDS 与普通 socket 有什么区别？

> **参考回答（English）**
>
> In publish-subscribe, publishers send data to a named topic and subscribers receive it, so the two sides are decoupled in space and time: they do not need to know each other's address. DDS is a data-centric middleware standard built on this: it provides automatic discovery, typed topics, and QoS policies such as reliability, durability, deadline and history. A plain socket gives you only a byte stream between two known endpoints; discovery, serialisation, retries and many-to-many routing would all have to be written by hand. ROS2 uses DDS underneath, and at Kaihong I worked with device discovery and task dispatch over M-DDS.
>
> **中文译文：** 发布-订阅中，发布者把数据发到有名字的主题，订阅者接收，两端在空间和时间上解耦，不需要知道彼此地址。DDS 是建立在此基础上的数据中心中间件标准：提供自动发现、带类型的主题，以及可靠性、持久性、截止时间、历史等 QoS 策略。普通 socket 只提供两个已知端点之间的字节流；发现、序列化、重试和多对多路由都得手写。ROS2 底层用 DDS，我在深开鸿用 M-DDS 做过设备发现和任务派发。


#### Q20. Explain RAII and smart pointers in C++. Why do they matter for robot software?

**中文：** 解释 C++ 中的 RAII 和智能指针。对机器人软件为什么重要？

> **参考回答（English）**
>
> RAII means a resource is acquired in an object's constructor and released in its destructor, so cleanup is automatic, even when exceptions or early returns happen. Smart pointers apply this to memory: unique_ptr has a single owner, shared_ptr uses reference counting for shared ownership, and weak_ptr observes without owning, which avoids cycles. Locks like lock_guard follow the same idea. For long-running robot software, leaks, double frees and forgotten unlocks are dangerous, so RAII makes the ownership explicit. In real-time loops, I would also avoid dynamic allocation in the hot path. The example I would use: a lock held in a scoped guard such as std::lock_guard, and a device handle held in a unique_ptr, so both are released on every exit path.
>
> **中文译文：** RAII 指资源在对象构造时获取、在析构时释放，因此即使发生异常或提前返回，清理也是自动的。智能指针把它用于内存：unique_ptr 单一所有者，shared_ptr 用引用计数共享所有权，weak_ptr 只观察不拥有，可避免循环引用。lock_guard 等锁也是同一思想。对长时间运行的机器人软件，泄漏、重复释放和忘记解锁都很危险，RAII 让所有权变得明确。在实时循环中，我还会避免在热路径上动态分配内存。 我会举的例子：用 std::lock_guard 这样的作用域守卫持有锁，用 unique_ptr 持有设备句柄，这样在任何退出路径上都会自动释放。

> **中文译文：** 我计划在大湾区做机器人平台与运动算法的软件工程师，之后负责机器人产品的软件部分。

> **中文译文：** 短期目标是机器人平台或运动软件工程。我想成为能把控制或 AI 算法安全地接到硬件上的人：接口清晰、数据可信、执行路径安全。长期来看，我希望承担机器人产品的软件架构责任。学位是为此打基础：我要掌握设计、测试、数据和安全的正规方法，而不是每次重新摸索。

## 六、5 道模拟题

每题限时 60–90 秒，用白板（纸）画一个简单示意图再讲，更贴近技术面。

**模拟题 1.** Design the interface between a motion-control module and a new robot's drivers. What would you put in it?

**中文：** 设计运动控制模块与新机器人驱动之间的接口，你会放什么？（要点：能力描述、时间戳/坐标系/有效性、限制、版本、可测试；连 P6）

**模拟题 2.** Two robots have clocks that differ by 40 ms. What problems can that cause and what would you do?

**中文：** 两台机器人时钟相差 40 ms，会引起什么问题？你怎么办？（数字是练习假设）（要点：排序错误、状态外推、融合误差；同步/偏移估计、容忍窗口、有效期）

**模拟题 3.** Explain TCP versus UDP using a robot example.

**中文：** 用机器人的例子解释 TCP 与 UDP。（要点：状态流与关键命令的取舍；DDS QoS）

**模拟题 4.** How would you test a task-dispatch component without real robots?

**中文：** 没有真实机器人时，怎么测试任务派发组件？（要点：单元、回放、模拟设备、故障注入、日志）

**模拟题 5.** What is the main thing you do not yet know about distributed systems?

**中文：** 关于分布式系统，你最不懂的是什么？（要点：安全模型、一致性协议、数据工程；诚实 + 学习计划）

## 七、本章要点速记

1. 主线：机器人先暴露的是软件问题（时间戳、坐标系、有效性、接口），不是控制律。
2. P6 四件事：能力模型、状态管理、M-DDS 协调、动作提议→策略检查→执行→反馈。
3. 承认训练最不系统的领域：安全模型、数据工程、系统设计方法。
4. CS 基础题要能不看资料讲：进程/线程、死锁、TCP/UDP、RAII、复杂度。
5. 对 AI 申请的口径：同一目标（智能机器人），CS 看软件基础。
6. 公司内部细节不说；只讲 CV 与通用设计思路。
7. 2027 细节待官网确认，不报学费和日期。

## 八、自测题

1. 用一句话说明 PS 的主线。
