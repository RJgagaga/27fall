## 二、这份 PS 的主线与可能的追问

### 2.1 PS 主线（引用原句）

P53 的 PS 用园艺系统开头，核心论点是：「可靠的物理行为取决于连接感知、算法和执行器的计算机系统」。这决定了你要把软件工程与数据工程当作主角，AI 与控制只是背景。

> "In the smart gardening system I built on OpenHarmony, a YOLOv5 detector running on an RK3588 board decides when a pump runs. Making that loop trustworthy turned out to depend less on the model than on everything around it…"
>
> **中文：** 在我基于 OpenHarmony 搭建的智能园艺系统中，运行在 RK3588 上的 YOLOv5 检测器决定水泵何时运行。事实证明，让这个闭环可信，更多取决于模型周围的一切，而不是模型本身……

> "…reliable physical behaviour depends on the computer systems connecting perception, algorithms and actuators, on dependable interfaces, consistent state representations and execution paths that remain safe when conditions are abnormal."
>
> **中文：** ……可靠的物理行为取决于连接感知、算法和执行器的计算机系统，取决于可靠的接口、一致的状态表示，以及在异常情况下仍然安全的执行路径。

> "Software Engineering and Data Engineering are where I want to strengthen my methods for designing and validating larger software systems, and the Artificial Intelligence Stream, starting from Machine Learning: Principles and Practice, is where I want to replace practical familiarity with a principled understanding of machine learning."
>
> **中文：** 软件工程和数据工程是我想加强设计与验证更大软件系统的方法的地方；人工智能方向从《机器学习：原理与实践》开始，是我想用有原则的理解取代实践上的熟悉的地方。

> "I would then use the Project course for a robotics project in perception, navigation or platform software."
>
> **中文：** 然后我会用 Project 课程做一个感知、导航或平台软件方向的机器人项目。

> "Compared with a programme tied to one particular robot mechanism, its computer-science training is better suited to building algorithms and software foundations that transfer across robot platforms."
>
> **中文：** 与绑定某种具体机器人机构的项目相比，其计算机科学训练更适合构建可跨机器人平台迁移的算法与软件基础。

**推荐信与 CV 如何呼应：** 傅向华老师在 P53 版信中写：你的 OpenHarmony 智能园艺系统是独立设计与构建、并向其演示过的完整闭环（YOLOv5/RK3588 → LangGraph → Hi3861）。这是 P4 真实性的外部证据，你要保证每个技术细节都能解释。陈淡生工程师的信聚焦 AIRS 平衡控制，在 P53 里只作为「工程习惯」的佐证。

### B. 围绕 PS 的追问

#### Q6. In your gardening system, what does 'everything around the model' consist of?

**中文：** 园艺系统里「模型周围的一切」包括什么？

> **参考回答（English）**
>
> Four things. First, every observation carries a confidence and a timestamp, so the decision layer can judge it. Second, a rule-based fast path overrides the agent in extreme states, so the pump does not wait for an uncertain decision. Third, a Hi3861 state machine with separate start and stop thresholds and manual priority keeps the pump safe and stable locally. Fourth, the system state is traceable: observation, recommendation, command and device feedback are recorded as different things. Together, they make the loop trustworthy even when the model is wrong. 【待你补全：每一项在代码/配置中的真实位置，不确定的删掉】
>
> **中文译文：** 四件事。第一，每个观测都带着置信度和时间戳，决策层才能判断它。第二，规则快速通道在极端状态下覆盖 Agent，使水泵不必等待不确定的决策。第三，Hi3861 上有独立启停阈值和手动优先的状态机，在本地保持水泵安全稳定。第四，系统状态可追溯：观测、建议、命令和设备反馈被作为不同的东西记录。它们合起来，即使模型出错，闭环仍然可信。


#### Q7. How does the LangGraph decision chain work, and why a rule-based fast path?

**中文：** LangGraph 决策链怎么工作？为什么还要规则快速通道？

> **参考回答（English）**
>
> I built an environment and vision-event decision chain with LangGraph. It takes sensor and vision observations and issues structured recommendations, or constrained requests, to the execution layer. For extreme states, for example very dry soil, a rule-based fast path acts directly without waiting for the agent. The reason is predictability: an LLM-based step can be slow or uncertain, and some situations should have a simple, known response. 【待你补全：LangGraph 的节点/边设计、用的是哪个模型及调用方式——没有就写“未确认”】
>
> **中文译文：** 我用 LangGraph 搭了环境与视觉事件的决策链，输入传感器和视觉观测，向执行层输出结构化建议或受约束的请求。对于极端状态（比如土壤非常干），由规则快速通道直接处理，不等待 Agent。原因是可预测性：基于 LLM 的环节可能慢或不确定，而有些情况应该有简单、确定的响应。


#### Q8. Describe the irrigation state machine on the Hi3861.

**中文：** 讲讲 Hi3861 上的灌溉状态机。

> **参考回答（English）**
>
> It is a soil-moisture-driven pump state machine with independent start and stop thresholds, plus a manual-priority override. Independent thresholds create hysteresis, so the pump does not chatter around one single threshold. Manual priority means a user command wins over automatic logic. The result is a stable local closed loop that still works if the decision layer is uncertain. 【待你补全：两个阈值的取值依据、最长运行时间等保护——如果没有就不要说有】
>
> **中文译文：** 这是一个由土壤湿度驱动的水泵状态机，启动和停止阈值相互独立，并带有手动优先覆盖。两个独立阈值形成滞回，避免水泵在单一阈值附近反复开关。手动优先意味着用户指令高于自动逻辑。结果是一个稳定的本地闭环，即使决策层不确定也能工作。


#### Q9. What does robot state management mean in your work?

**中文：** 你工作中的“机器人状态管理”指什么？

> **参考回答（English）**
>
> Perception and actuator feedback come from many sources, with different clocks, coordinate frames and quality. I standardised the timestamps, coordinate frames and validity checks across them, so the motion-control layer and the task layer see one consistent, trusted robot state. In plain words: before a number is used to make a decision, it should say when it was measured, in which frame, and whether it is still valid. 【待你补全：有效性检查的具体规则（超时、范围、来源）】
>
> **中文译文：** 感知和执行器反馈来自多个来源，时钟、坐标系和质量各不相同。我统一了它们的时间戳、坐标系和有效性检查，让运动控制层和任务层看到一致、可信的机器人状态。通俗地说：一个数字被用来做决策之前，应该说明它是什么时候测的、在哪个坐标系下、现在是否仍然有效。

#### Q12. How did you integrate vision, environment data and user commands into one system?

**中文：** 你怎么把视觉、环境数据和用户指令整合成一个系统？

> **参考回答（English）**
>
> I unified visual observations, environment state and user commands into one traceable system state. A server-side agent orchestrates the decisions, and the loop closes through web interaction and device-side irrigation. I kept the stages separate: an observation, a recommendation, a command and the device feedback are different things, and each should be recorded. That is how I could trace why the pump ran. 【待你补全：状态存储方式、日志/追溯的具体做法、服务器端与设备端的通信协议】
>
> **中文译文：** 我把视觉观测、环境状态和用户指令统一成可追溯的系统状态，由服务器端 Agent 编排决策，通过网页交互和设备端灌溉闭合回路。我把各阶段分开：观测、建议、命令和设备反馈是不同的东西，每一种都应该记录。这样我才能追溯水泵为什么运行。


#### Q13. What is the unified capability model you built at Kaihong?

**中文：** 你在深开鸿做的统一能力模型是什么？

> **参考回答（English）**
>
> On the M-Robots platform, different robots have different sensors, actuators and controllers. I built a unified capability model in C++ on OpenHarmony that describes all of them in the same way, and I mapped ROS and ROS2 motion commands onto the low-level drivers. The benefit is reuse: motion-control code does not have to be rewritten for each piece of hardware, because it talks to the capability interface instead of the specific driver. 【待你补全：能力描述的字段/接口形式、你支持过的具体硬件种类、哪些部分是你独立完成的】
>
> **中文译文：** 在 M-Robots 平台上，不同机器人有不同的传感器、执行器和控制器。我在 OpenHarmony 上用 C++ 建立统一能力模型，用同一种方式描述它们，并把 ROS 和 ROS2 的运动指令映射到底层驱动。好处是复用：运动控制代码不需要为每种硬件重写，因为它面向的是能力接口，而不是具体驱动。


#### Q14. Explain the action-proposal, policy-check, execution and state-feedback chain.

**中文：** 讲讲“动作提议、策略检查、执行、状态反馈”这条链。

> **参考回答（English）**
>
> A high-level task plan, for example from a planner or an AI model, is never sent straight to the robot. First it becomes an action proposal. Then a policy check decides whether the action is allowed in the current state. Only if it passes does it go to execution. Finally, the state feedback tells the system what actually happened, which closes the loop. The idea is that an AI decision and a physical action are different things, and the checks sit between them. 【待你补全：策略检查具体检查哪些规则（如速度/区域/设备状态/权限）、被拒绝时的处理】
>
> **中文译文：** 高层任务计划（例如来自规划器或 AI 模型）绝不会直接发给机器人。它先成为一个动作提议；然后由策略检查判断在当前状态下是否允许；通过后才进入执行；最后状态反馈告诉系统实际发生了什么，闭合回路。思想是：AI 的决策和物理动作是两回事，检查就放在它们之间。


#### Q15. How did you build the localisation for the car-like robot, and what went wrong?

**中文：** 车式机器人的定位是怎么做的？遇到过什么问题？

> **参考回答（English）**

### D. CS 基础与 ML 入门

#### Q16. What is the time complexity of A*, and what data structures does it use?

**中文：** A* 的时间复杂度是多少？用了哪些数据结构？

> **参考回答（English）**
>
> A* keeps an open set, usually a priority queue (binary heap) ordered by f = g + h, and a closed set, usually a hash set or array. In the worst case, with a poor heuristic, it behaves like Dijkstra and visits O(b to the power d) nodes, or O((V + E) log V) with a heap on a graph. A good admissible heuristic can reduce the expansions a lot. If the heuristic is also consistent, each node is expanded at most once and the path is optimal. Memory use is often the real limit in large maps.
>
> **中文译文：** A* 维护一个开集合，通常是按 f = g + h 排序的优先队列（二叉堆），以及一个闭集合，通常是哈希集合或数组。最坏情况下，如果启发函数很差，它会退化成 Dijkstra，访问 O(b^d) 个节点，或在图上用堆实现为 O((V+E) log V)。好的可采纳启发函数能大幅减少扩展次数。若启发函数同时一致，每个节点最多扩展一次且路径最优。大地图中真正的限制往往是内存。


#### Q17. What is the difference between a process and a thread?

**中文：** 进程和线程有什么区别？

> **参考回答（English）**
>
> A process is an instance of a program with its own address space and resources; a thread is a unit of execution inside a process, and threads in the same process share memory. Creating and switching threads is cheaper, and sharing data is easy, but that makes data races possible, so shared data needs synchronisation, such as mutexes. Processes are isolated: one crash does not usually bring down another, but communication needs IPC. On a robot, I would put safety-critical or crash-prone components into separate processes, and use threads inside one component.
>
> **中文译文：** 进程是拥有独立地址空间和资源的程序实例；线程是进程内的执行单元，同一进程的线程共享内存。线程创建和切换开销更小，共享数据也方便，但这会带来数据竞争，所以共享数据需要互斥锁等同步手段。进程之间相互隔离：一个崩溃通常不会拖垮另一个，但通信需要 IPC。在机器人上，我会把安全关键或容易崩溃的组件放进不同进程，在单个组件内部使用线程。


#### Q18. TCP versus UDP: which would you use for robot control messages, and why?

**中文：** TCP 与 UDP：机器人控制消息你会用哪个？为什么？

> **参考回答（English）**
>
> TCP is reliable and ordered, using acknowledgements and retransmission, but retransmission can add delay and head-of-line blocking. UDP is connectionless with no delivery guarantee, but low overhead and low latency. For high-rate state or control streams, where the newest value matters more than an old lost one, UDP-like transports with timestamps are often preferred; for configuration, commands that must arrive, or file transfer, TCP or a reliable mode is better. DDS lets you choose per topic through QoS, such as best-effort versus reliable, which fits both cases.
>
> **中文译文：** TCP 可靠且有序，使用确认和重传，但重传可能带来延迟和队头阻塞。UDP 无连接、不保证送达，但开销小、延迟低。对高频的状态或控制流，最新的值比丢失的旧值更重要，常选用带时间戳的类 UDP 传输；对配置、必须送达的命令或文件传输，则更适合 TCP 或可靠模式。DDS 可以通过 QoS 按主题选择（best-effort 或 reliable），两种情形都能覆盖。


#### Q19. What is publish-subscribe, and how is DDS different from a simple socket?

**中文：** 什么是发布-订阅？DDS 与普通 socket 有什么区别？

> **参考回答（English）**
>
> In publish-subscribe, publishers send data to a named topic and subscribers receive it, so the two sides are decoupled in space and time: they do not need to know each other's address. DDS is a data-centric middleware standard built on this: it provides automatic discovery, typed topics, and QoS policies such as reliability, durability, deadline and history. A plain socket gives you only a byte stream between two known endpoints; discovery, serialisation, retries and many-to-many routing would all have to be written by hand. ROS2 uses DDS underneath, and at Kaihong I worked with device discovery and task dispatch over M-DDS.
>
> **中文译文：** 发布-订阅中，发布者把数据发到有名字的主题，订阅者接收，两端在空间和时间上解耦，不需要知道彼此地址。DDS 是建立在此基础上的数据中心中间件标准：提供自动发现、带类型的主题，以及可靠性、持久性、截止时间、历史等 QoS 策略。普通 socket 只提供两个已知端点之间的字节流；发现、序列化、重试和多对多路由都得手写。ROS2 底层用 DDS，我在深开鸿用 M-DDS 做过设备发现和任务派发。


#### Q20. How would you test robot software, given that hardware is not always available?

**中文：** 硬件不总是可用，你怎么测试机器人软件？

> **参考回答（English）**
>
> I use several layers. Unit tests for pure logic such as kinematics, state machines and message validation. Simulation or replay for integration: record real data into a bag and replay it so the same inputs reproduce a bug; run the stack against a simulator such as MuJoCo. Hardware-in-the-loop tests on a bench with safety limits before free motion. And on the real robot, a staged approach: low gains and limits first, with an emergency stop. I would also log enough to reconstruct a failure. 【待你补全：你实际用过的测试/回放手段，没有就说明“我主要靠真机和日志”】
>
> **中文译文：** 我分几层。对纯逻辑（运动学、状态机、消息校验）做单元测试；集成时用仿真或回放：把真实数据录成包再回放，使同样的输入复现问题，或在 MuJoCo 之类的仿真器里运行整个栈；在台架上做带安全限制的硬件在环测试，然后才让机器人自由运动；在真机上分阶段推进：先用低增益和限位，并准备急停。我还会记录足够的日志以复原故障。


#### Q21. What is data engineering, and why does a robot platform need it?

**中文：** 什么是数据工程？机器人平台为什么需要它？

> **参考回答（English）**
>
> Data engineering is about collecting, storing, cleaning, versioning and serving data reliably, so that others can analyse it or train models. A robot platform produces a lot of time-series data: sensor streams, states, commands and logs. Without a schema, consistent timestamps and quality checks, the data is hard to use for debugging, evaluation or learning. A good pipeline records data with clear metadata, such as device, frame and time, and keeps logs queryable. This is where I see the gap in my own experience: I standardised timestamps, frames and validity at runtime, but I have not designed a full data pipeline.
>
> **中文译文：** 数据工程是可靠地采集、存储、清洗、版本管理和提供数据，使他人能分析数据或训练模型。机器人平台会产生大量时序数据：传感器流、状态、命令和日志。如果没有模式定义、一致的时间戳和质量检查，这些数据很难用于调试、评估或学习。好的流水线会带着清楚的元数据（设备、坐标系、时间）记录数据，并让日志可查询。这正是我经验中的缺口：我在运行时统一了时间戳、坐标系和有效性，但没有设计过完整的数据流水线。

## 六、5 道模拟题

每题 60 秒，注意：先结论，再例子，再收获。

**模拟题 1.** Walk me through what happens in your gardening system from a camera frame to water in the soil.

**中文：** 请讲讲园艺系统中，从摄像头一帧到水进入土壤的全过程。（要点：推理链、观测、决策、快速通道、状态机、反馈；区分建议与命令）

**模拟题 2.** What would you do if two sensors on a platform disagree about the same quantity?

**中文：** 如果平台上两个传感器对同一个量不一致，你怎么办？（要点：时间对齐、坐标系、有效性检查、融合、报警）

**模拟题 3.** Why is testing hard for robot software, and what would you do?

**中文：** 为什么机器人软件的测试困难？你会怎么做？（要点：硬件、实时、环境；单元、回放、仿真、故障注入）

**模拟题 4.** Explain overfitting using your detector as an example.

**中文：** 用你的检测器举例解释过拟合。（要点：训练/验证；数据分布；增强；诚实说明没有训练过则讲概念）

**模拟题 5.** Why did you choose this programme over a robotics programme?

**中文：** 为什么选这个项目而不是机器人项目？（要点：可迁移的软件基础；系统是训练最不系统的部分）
