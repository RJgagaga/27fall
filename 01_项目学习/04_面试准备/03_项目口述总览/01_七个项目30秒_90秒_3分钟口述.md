# 七个项目的 30 秒 / 90 秒 / 3 分钟英文口述

> **一句话定位**：这是你面试时"讲项目"的台词本。每个项目准备三种长度——30 秒（被问"简单介绍一下"）、90 秒（常规追问的第一轮）、3 分钟（教授说"Tell me more about this one"）——每段都附中文译文、关键词提示和易说错点。所有内容严格取自 CV 的 bullet，不含任何未经证实的实测数字。

**本章学完你能……**

- 对 P1–P7 中任意一个项目，在 30 秒、90 秒、3 分钟三个长度间自由切换而不丢主线；
- 根据面试官身份（AI / 控制 / CS / HR）决定先讲哪几个项目、每个讲多长；
- 避开"把团队成果说成个人成果""把 CV 没写的数字当事实"这类高频踩坑；
- 一边讲一边留"钩子"，把追问引向你准备过的地方。

**前置知识**：[七个项目总览与技能矩阵](../../00_申请画像/03_七个项目总览与技能矩阵.md)、[口径与事实基线](../../00_申请画像/04_口径与事实基线.md)、[技术口述方法：如何讲清一个项目](../01_面试总指南/08_技术口述方法_如何讲清一个项目.md)。

## 1. 使用方法与总规则

### 1.1 三种长度分别回答什么问题

| 长度 | 英文词数（口语约 130 词/分钟） | 面试官问法 | 必须包含的结构 |
|---|---|---|---|
| 30 秒 | 约 65–75 词 | "Briefly, what was this project?" | 做什么 → 你负责什么 → 一句结果 |
| 90 秒 | 约 190–210 词 | "Tell me about your work on X." | 背景 → 你的 2–3 个模块 → 一个难点 → 结果 |
| 3 分钟 | 约 380–420 词 | "Walk me through it in detail." | 背景 → 系统结构 → 各模块方法与理由 → 一个真实排错故事 → 局限与反思 |

> **提示**：口语里"130 词/分钟"是舒适语速。你的雅思口语偏弱，建议练到 **110–120 词/分钟**，宁可慢一点、清晰一点。后文的词数就是按这个来估的，练习时用手机计时。

### 1.2 总规则（每个项目都适用）

1. **先背 CV 的一句 Overview，再展开。**面试官手里有 CV，你的第一句话和 CV 对得上，他立刻信任你。
2. **动词有分寸。**P1/P3/P5/P7 说 "I was responsible for …"；P4 说 "I independently built …"；P6 说 "I independently developed and integrated …"。不要升级。
3. **团队项目只讲自己的模块。**P3（战队）、P7（实验室）说 "our team" 讲成绩，说 "I" 讲模块。
4. **没有数字就别说数字。**CV 没有增益、频率、误差、成功率。需要量级感时用"能用语言描述的现象"：stable, noticeably less, still saturated。必须用数时说 "I'd need to check the exact number"（见 [口径与事实基线](../../00_申请画像/04_口径与事实基线.md)）。
5. **每段结尾留钩子。**钩子 = 一个你准备好深挖的词，例如 "singularity"、"state inconsistency"、"sliding-mode"、"policy check"。面试官最容易追他刚听到的最后一个技术词。
6. **`【待你补全】`**表示面试官很可能追问、但 CV 没写的细节。你必须把它们补进各项目 README 的「实机细节自查表」，再回来改口述。

### 1.3 读法约定

- 英文段落是你要说出口的话；`中文：` 是译文，仅供核对，不要背中文。
- `关键词提示` 是卡壳时的"提词卡"——只记这几个词，其余现场组织。
- `易说错点` 是这个项目最常见的口径风险。

## 2. 按面试官类型选项目的策略表

面试官的专业背景决定了他听得懂什么、关心什么。同一个人 3 分钟，讲给不同的人，选的项目和先后应不同。

### 2.1 总表

| 面试官类型 | 他关心什么 | 第一选择（讲最久） | 第二选择 | 第三选择（简短带过） | 不要主动展开 |
|---|---|---|---|---|---|
| **AI / 机器学习教授**（如 CUHK-SZ AI&Robotics、CityU(DG) AI、UM AI、MUST AI、HKUST(GZ) 具身智能） | 数据、模型、部署、AI 如何落到物理世界、你对理论的态度 | **P6**（AI 决策→物理动作的安全链） | **P4**（YOLOv5/RKNN INT8 + LangGraph） | P5（估计+规划+MPC 整链）；P7 提一句"模型 vs 学习"的对比 | P3 的功率细节；P2 的 URDF 细节 |
| **控制 / 机器人教授**（PolyU IRE、CUHK Robotics、UM RAS） | 建模、稳定性、状态反馈、真机调参 | **P1**（PID→模型分析→LQR→质心前馈） | **P7**（增益调度 LQR + VMC） | P3（嵌入式闭环、滑模迭代）；P5 的 MPC；P2 的奇异与 IK | P4 的 Web 交互；P6 的 DDS 细节 |
| **CS 教授**（CUHK-SZ CS、CityU(DG) CS、CityU P53） | 系统设计、并发、数据结构/算法、软件工程 | **P6**（抽象层、状态管理、分布式协同） | **P5**（Hybrid-A*、图搜索、EKF/AMCL 的工程链） | P3（FreeRTOS 任务/CAN）；P4（端云分层架构） | P1 的 LQR 数学细节 |
| **HR / 招生办 / 综合面试官**（可能非技术） | 动机、沟通、团队、成长、是否"靠谱" | **P6**（正在进行的实习，最新） | **P3**（团队、奖项、迭代） | P1（"返回模型分析"的成长故事） | 所有数学与缩写密集的内容 |

> **面试要点**：表里的"第一选择"是你的**主推项目**，如果面试官没限定，开场就从它讲起，其余作为备选。AI 方向把 P6 + P4 放前面，不是因为它们"最强"，而是 PS 主线（"AI 决策如何变成物理动作"）与它们一致。

### 2.2 按"问题关键词"即时切换

| 面试官一句话里出现 | 你立刻想到 |
|---|---|
| "stability", "tuning", "model" | P1 → P7 |
| "real-time", "RTOS", "CAN" | P3 → P7 → P1 |
| "estimation", "sensor fusion", "localisation" | P5（EKF/AMCL），带一句 P1/P7 的状态一致性 |
| "planning", "path", "navigation" | P5（Hybrid-A* → TEB → MPC） |
| "kinematics", "singularity", "IK" | P2（约束 IK），P7（闭链运动学） |
| "AI", "LLM", "agent", "safety" | P6 → P4 |
| "teamwork", "competition", "pressure" | P3 |
| "most challenging", "debugging" | P7（状态不一致、力矩限幅、触地切换）或 P5（位姿跳变） |
| "what would you do differently" | 统一回到"更早建模 / 更早做日志与一致性检查"（见 [核心叙事线](../01_面试总指南/03_核心叙事线_为什么读研_为什么这个方向.md)） |

### 2.3 一个 3 分钟自由开场的三种配方

| 配方 | 顺序 | 总时长 | 适用 |
|---|---|---|---|
| A（AI 向） | P6 30 秒 → P4 60 秒 → P5 45 秒 → 一句话连 P1/P7 | 约 3 分钟 | AI 项目申请的开场 |
| B（控制向） | P1 90 秒 → P7 60 秒 → P3 30 秒 → P5 一句 | 约 3 分钟 | 机器人/控制项目 |
| C（通用） | 用七项目主线的 90 秒版（见 [七个项目总览](../../00_申请画像/03_七个项目总览与技能矩阵.md)） | 90 秒 | 时间紧、面试官不限定 |

## 3. P1 AIRS 球形机器人平衡控制

> 详细讲义：[P1 README](../../01_项目课程/P1_AIRS球形机器人平衡控制/README.md)；深挖问答：[P1 英文面试口述与深挖问答](../../01_项目课程/P1_AIRS球形机器人平衡控制/99_英文面试口述与深挖问答.md)。

**CV 事实锚点**：Robotics Software Intern，AIRS，Sep 2025 – Mar 2026；三全向轮 ballbot + 双臂上身；负责平衡控制开发与机上整定；双臂沿固定轨迹运动时底盘保持动态平衡。四条 bullet：级联 PID（IMU + 轮速反馈，位置外环给有界姿态参考，内环输出经运动学分配到三个轮）；四状态线性化倒立摆 + LQR 分析状态权重的"稳定性—控制量"权衡；URDF/Pinocchio 估计质心偏移并做 roll/pitch 重力前馈，用开关补偿验证效果；ROS 状态处理 + CAN 电机执行，状态初始化、输出限幅、跌倒恢复保护。

### 3.1 30 秒版

> "At AIRS I was responsible for the balance control of a ballbot — a robot balancing on three omni wheels, with a dual-arm upper body. I deployed a cascaded PID on IMU and wheel-speed feedback, then went back to a linearised four-state inverted-pendulum model and used LQR to understand the trade-offs behind my gains. I also added centre-of-mass feedforward from the arm joints, so the chassis stayed balanced while both arms moved along fixed trajectories."

中文：在 AIRS 我负责一个 ballbot（三个全向轮、带双臂上身）的平衡控制。我基于 IMU 和轮速反馈部署了级联 PID，然后回到线性化的四状态倒立摆模型，用 LQR 去理解增益背后的权衡；还根据手臂关节加了质心前馈，所以双臂沿固定轨迹运动时底盘保持平衡。

- **关键词提示**：ballbot / three omni wheels / cascaded PID / four-state / LQR analysis / CoM feedforward。
- **易说错点**：① 不要说 "I used LQR to control the robot"——CV 写的是 *LQR modelling and analysis*，LQR 是**分析与参考**，部署的是级联 PID；② 不要说 "I designed the robot"；③ 不要说"球"，要说 ballbot/three-omni-wheel（CV 原词）。

### 3.2 90 秒版

> "My internship at AIRS was on a ballbot with a dual-arm upper body. The robot sits on three omni wheels, so it's a real inverted-pendulum problem: it is unstable by itself, and I was responsible for the balance control and the on-robot tuning.
> First I built a cascaded PID. The inner loop controls the attitude from the IMU; the outer loop looks at position and wheel speed and gives the inner loop a bounded attitude reference — bounded so that the outer loop can never ask for a dangerous lean. The output is then allocated to the three wheels through the kinematics.
> When tuning alone couldn't explain what I saw on the robot, I went back to the model. I linearised it as a four-state inverted pendulum and used LQR to study how the state weights trade off stability and control effort. I didn't deploy that LQR as the main controller; I used it as a reference to explain the gains I had deployed, and to find out when an actuator was saturating.
> Because the arms move, the centre of mass moves too. I estimated the offset from the arm joint states with URDF and Pinocchio, and fed roll and pitch gravity feedforward into the balance loop. To check it really helped, I switched the compensation on and off under the same fixed arm trajectory.
> Finally, I integrated ROS state processing with CAN motor execution and added state initialisation, output limiting and fall-recovery safeguards."

中文：（译文要点）AIRS 实习做带双臂上身的 ballbot，三全向轮上是真正的倒立摆问题，本身不稳，我负责平衡控制与机上整定。先做级联 PID：内环用 IMU 控姿态，外环看位置与轮速并给内环一个**有界**姿态参考（保证外环不会要求危险的倾角），输出经运动学分配到三轮。调参解释不了现象时回到模型：线性化为四状态倒立摆，用 LQR 研究状态权重如何权衡稳定性与控制量——它不是主控制器，而是解释已部署增益、发现执行器饱和的参考。手臂运动使质心移动，用 URDF/Pinocchio 由关节状态估计质心偏移，把 roll/pitch 重力前馈加入平衡环，并在同一固定轨迹下开关补偿验证。最后把 ROS 状态处理与 CAN 电机执行集成，加了状态初始化、输出限幅与跌倒恢复保护。

- **关键词提示**：bounded attitude reference / return to the model / weights vs effort / saturation diagnosis / toggle compensation / output limiting。
- **易说错点**：① "bounded" 是 CV 里的原词，要保留；② 验证方式是**开关补偿对比**，不要说成"测出了 X% 的提升"；③ 不要说"我做了硬件"。

### 3.3 3 分钟版

> "Let me tell you about my balance-control work at AIRS. The platform is a ballbot: a body balancing on three omni wheels, with a dual-arm upper body. The chassis has to keep dynamic balance even when both arms move along fixed trajectories. My responsibility was the balance control development and the on-robot tuning.
> I'll go through it in four steps.
> Step one: the cascaded PID. We had IMU and wheel-speed feedback. I designed a position outer loop that outputs an attitude reference, and an attitude inner loop that computes the torque-like command. The reference is bounded, which keeps the outer loop from commanding an unsafe lean when the position error is big. The inner output is then allocated to the three wheels using the omni-wheel kinematics. This got the robot balancing, and it's what was deployed.
> Step two: going back to the model. With PID you can tune for a long time and still not know why something happens. So I wrote the robot as a linearised four-state inverted pendulum — position, velocity, tilt and tilt rate — and used LQR to see how the weights on those states trade off stability against control effort. I want to be clear about the role: it was an analysis tool and a model reference for the PID tuning. It helped me explain the deployed gains, and diagnose when the motors were hitting saturation.
> Step three: arm motion. When the arms move, the centre of mass shifts, and the balance loop sees that as a disturbance. From the arm joint states, I estimated the CoM offset using URDF and Pinocchio, and fed a roll and pitch gravity feedforward into the balance controller. To verify it, I toggled the compensation on and off under the same fixed arm trajectory and compared the behaviour.
> Step four: the safety loop. I connected the ROS state processing to the CAN motor execution, and added state initialisation, output limiting and fall-recovery safeguards, so the chassis stayed balanced under arm motion and failed safely when it couldn't.
> If I look back, the main lesson is that PID gets you running, but a model tells you why. If I did it again, I'd build the simple model earlier, so that the tuning is guided from the start."

中文：（译文要点）四步：① 级联 PID（外环位置→有界姿态参考；内环姿态；输出经全向轮运动学分配三轮），这是部署的控制器；② 回到模型，线性化四状态（位置、速度、倾角、倾角速率），LQR 分析权重对稳定性与控制量的权衡，角色是分析工具与整定参考，用于解释增益与诊断饱和；③ 手臂动使质心偏移成为扰动，用 URDF/Pinocchio 由关节状态估计偏移并做 roll/pitch 重力前馈，固定手臂轨迹下开关补偿验证；④ 安全回路：ROS 状态处理接 CAN 电机执行，状态初始化、输出限幅、跌倒恢复。反思：PID 让它跑起来，模型告诉你为什么；再做一次会更早建简单模型。

- **关键词提示**：position/velocity/tilt/tilt rate / bounded reference / model reference / saturation / CoM offset / toggle / fall-recovery。
- **易说错点**：① 四状态一定按 CV：position、velocity、tilt、tilt-rate（推荐信写法）；② 不要给出具体增益/权重矩阵 Q、R 的数值，除非你补全了 `【待你补全：Q/R 的取值与调参过程】`；③ "跌倒恢复"只说 "safeguards"，不要描述成复杂的自主起身。

## 4. P2 未来动力：VR 遥操作 / 主从示教 / 差速底盘

> 详细讲义：[P2 README](../../01_项目课程/P2_未来动力双臂遥操作与差速底盘/README.md)；深挖问答：[P2 英文面试口述与深挖问答](../../01_项目课程/P2_未来动力双臂遥操作与差速底盘/99_英文面试口述与深挖问答.md)。

**CV 事实锚点**：Robotics Software Intern，Shenzhen Future Power，Mar 2026 – May 2026；双臂 + 底盘控制，VR 遥操作、主从示教、底盘运动控制，通过 ROS2-CAN 执行链在真机上验证。三条 bullet：VR 手柄运动→末端目标，MuJoCo/Mink 约束逆运动学，抑制奇异点附近速度放大；URDF/KDL 双臂动力学，leader 臂重力补偿 + follower 位置-速度跟踪，低阻力手拖示教；差速运动学把车体速度指令映射为轮目标，编码器反馈闭环 PID，轮运动并入里程计，用于遥操作与自主模式。

### 4.1 30 秒版

> "At Future Power I worked on dual-arm and chassis control: VR teleoperation, leader–follower teaching, and wheel-speed control, all validated on real hardware through a ROS2-CAN chain. For the VR part, I mapped controller motion to end-effector targets and solved constrained inverse kinematics with MuJoCo and Mink, so the arm tracked the target without velocity spikes near singularities."

中文：在未来动力，我做双臂和底盘控制：VR 遥操作、主从示教、轮速控制，全部通过 ROS2-CAN 链在真机上验证。VR 部分，我把手柄运动映射为末端目标，用 MuJoCo/Mink 求解带约束的逆运动学，使手臂跟踪目标时在奇异点附近不出现速度尖峰。

- **关键词提示**：VR controller → end-effector target / constrained IK / singularity / ROS2-CAN。
- **易说错点**：CV 是 "suppressing velocity amplification near singularities"（抑制速度放大），不要说"消除奇异"或"解决奇异"——奇异是几何性质，只能避开、阻尼或限制。

### 4.2 90 秒版

> "At Future Power I had three pieces of work on a dual-arm robot with a mobile chassis, and everything was validated on real hardware through the ROS2-CAN execution chain.
> The first was VR teleoperation. I mapped the motion of the VR controller to end-effector targets, and solved constrained inverse kinematics using MuJoCo and Mink. The point of the constraints is that near a singularity a small Cartesian motion can demand a huge joint velocity; the solver suppresses this velocity amplification, so the arm tracks the operator smoothly.
> The second was leader–follower teaching. I built the dual-arm dynamics from URDF and KDL. On the leader arm I designed gravity compensation, so that a person can push the arm with very little resistance. On the follower, I designed position–velocity tracking, so it moves synchronously with the leader.
> The third was the chassis. I mapped body velocity commands to wheel targets with differential-drive kinematics, closed a PID loop with encoder feedback, and integrated the wheel motion into odometry, for both teleoperated and autonomous modes."

中文：（要点）三块：VR 遥操作（手柄→末端目标，MuJoCo/Mink 约束 IK，奇异点附近速度放大被抑制，跟随平滑）；主从示教（URDF/KDL 动力学，leader 重力补偿使人手拖动阻力小，follower 位置-速度跟踪同步运动）；底盘（差速运动学把车体速度映射为轮目标，编码器反馈 PID，轮运动并入里程计，用于遥操作与自主模式）。全部经 ROS2-CAN 链在真机验证。

- **关键词提示**：singularity / velocity amplification / gravity compensation / position–velocity tracking / differential drive / odometry。
- **易说错点**：① 不要说 VR "延迟低于 X 毫秒"（CV 无数字）；② 主从示教里 follower 是"位置-速度跟踪"，不是"力控/阻抗"；③ 不要说做了 MuJoCo 里的"学习"——MuJoCo 在这里是建模/IK 工具链。

### 4.3 3 分钟版

> "I'll describe my three modules at Future Power. The platform was a dual-arm robot on a differential-drive chassis; my work was control software that runs on the real hardware through a ROS2 to CAN chain.
> Module one is VR dual-arm teleoperation. The operator holds a VR controller. I take the controller's motion, and map it to end-effector targets for the arm. Then I have to turn those targets into joint commands, which is an inverse kinematics problem. I solved it as a constrained problem with MuJoCo and Mink: joint limits and other constraints are part of the problem, instead of being clipped afterwards. The part I care about most is the singularity behaviour. Near a singularity, the Jacobian loses rank, so a small end-effector motion can ask for a very large joint velocity. The solver I used suppresses that amplification, so the arm keeps tracking, but without wild joint motion.
> Module two is leader–follower teaching. I built the dual-arm dynamics from the URDF with KDL. On the leader arm, I computed gravity compensation, so when a human guides the arm by hand it feels light and low-resistance. The follower arm uses position–velocity tracking of the leader's joint state, so it moves synchronously.

中文：（要点）平台：双臂 + 差速底盘，控制软件经 ROS2→CAN 在真机运行。模块一：手柄运动→末端目标→逆运动学，约束作为问题的一部分（而非事后裁剪）；奇异处雅可比失秩，小末端运动会要求巨大关节速度，求解器抑制该放大。模块二：URDF + KDL 动力学，leader 重力补偿让人手拖动轻，follower 位置-速度跟踪同步。模块三：车体速度（前进速度、转向率）→差速运动学→各轮目标，编码器反馈 PID，并入里程计，兼用于遥操作与自主。总结：三者共同点是把模型的限制（关节限位、奇异、轮饱和）放进控制器。

### 7.3 3 分钟版

> "I'd like to walk through my car-like robot navigation project, from June to October 2025. I was responsible for the algorithm chain: multi-sensor localisation, obstacle-aware planning and MPC tracking. The result was autonomous navigation on the real vehicle.
> I'll follow the data. First, localisation. Wheel encoders give odometry, the IMU gives rotation, the 2D LiDAR gives map matching. > Second, global planning. A car can't turn on the spot, so plain grid A* gives paths it can't follow. I used Hybrid-A*, which keeps heading as part of the search state and uses kinematic motion primitives, so the path respects the vehicle footprint and minimum turning radius, with an obstacle cost.
> Third, local planning with TEB. It takes the global path and the local costmap and optimises a time-parameterised trajectory; as the local obstacles change, it keeps giving continuous pose and curvature references to the controller.
> Fourth, tracking with MPC. The model is a car-like kinematic model. At each step it solves a finite-horizon problem with constraints on position, heading, speed and steering, applies the first control, and repeats. That closes the loop from the planned trajectory to real vehicle motion.
> The lesson I carry to other projects is this: when a robot misbehaves, check the consistency of time, frames and direction first. It's the same lesson I met again on the wheel-legged robot, and it's why I now work on state management at Kaihong."

中文：（要点）顺着数据流讲。定位：编码器里程计、IMU 旋转、2D 激光地图匹配；EKF 融合 IMU 与编码器，AMCL 用激光做地图定位。初期出现漂移和位姿突跳，花很长时间查算法后才发现算法没错，输入不一致：传感器时间戳未对齐、坐标系不匹配、前进/倒车方向处理不一致；修复后输出连续状态，下游平静很多。全局：车不能原地转向，网格 A* 的路径车跟不了；Hybrid-A* 把航向放进搜索状态并用运动学基元，路径满足轮廓与最小转弯半径及障碍代价。局部：TEB 在全局路径和局部代价地图下优化时间参数化轨迹，障碍变化时持续输出连续位姿与曲率参考。跟踪：车式运动学模型的 MPC，每步解有限时域问题，位置/航向/速度/转向约束，只应用第一步控制并重复。教训：机器人行为异常，先查时间、坐标系、方向的一致性；在轮腿机器人上又遇到，也是我现在在 Kaihong 做状态管理的原因。

- **关键词提示**：drift and jumps / inputs inconsistent / motion primitives / footprint / continuous references / receding horizon。
- **易说错点**：① "A* 路径车跟不了""Hybrid-A* 用运动学基元"是通用算法事实，可以讲；但不要说你们的网格分辨率、搜索步长（无依据）；② "I spent a long time" 的"多久"不要给数字；③ 不要把"后来在 Kaihong 做状态管理"说成直接因果，说 "one reason" 即可。

## 8. P6 深开鸿 M-Robots 平台

> 详细讲义：[P6 README](../../01_项目课程/P6_深开鸿M-Robots平台软件/README.md)；深挖问答：[P6 英文面试口述与深挖问答](../../01_项目课程/P6_深开鸿M-Robots平台软件/99_英文面试口述与深挖问答.md)。

**CV 事实锚点**：Robotics Platform Intern，Shenzhen Kaihong Digital Industry Development，Jun 2026 – Present；M-Robots OpenHarmony 多机器人平台；独立开发并集成设备抽象、状态管理、分布式协同、安全执行链。三条 bullet：C++ 统一能力模型（传感器/执行器/控制器），把 ROS/ROS2 运动指令映射到底层驱动，使运动控制代码跨硬件复用；时间戳、坐标系、有效性检查标准化，给运动控制层与任务层一致可信的机器人状态；基于 M-DDS 的设备发现、能力注册、状态同步、任务派发，任务计划经 action-proposal → policy-check → execution → state-feedback 链放行。

### 8.1 30 秒版

> "I'm currently a robotics platform intern at Kaihong, working on the M-Robots multi-robot platform on OpenHarmony. I independently developed and integrated four things: a unified device abstraction in C++, robot state management, distributed coordination over M-DDS, and a safe-execution chain, where a task plan has to pass proposal, policy check, execution and state feedback before an actuator moves."

中文：我目前在深开鸿做机器人平台实习，负责 OpenHarmony 上的 M-Robots 多机器人平台。我独立开发并集成了四块：C++ 统一设备抽象、机器人状态管理、基于 M-DDS 的分布式协同、安全执行链——任务计划必须经过提案、策略检查、执行、状态反馈，执行器才会动。

- **关键词提示**：unified capability model / state management / M-DDS / action-proposal → policy-check → execution → state-feedback。
- **易说错点**：① 不要说"我开发了整个 M-Robots 平台"，是 "device abstraction and motion coordination" 的四块；② 实习仍在进行，用现在时；③ 不要提公司内部细节（保密）。

### 8.2 90 秒版

> "At Kaihong, I work on device abstraction and motion coordination for the M-Robots platform, which is a multi-robot platform on OpenHarmony. I developed four parts myself.
> First, a unified motion interface. In C++ I built a capability model that describes sensors, actuators and controllers in one way, and I mapped ROS and ROS2 motion commands to the low-level drivers. So the same motion-control code can be reused across different hardware.
> Second, robot state management. Sensors and actuator feedback arrive with different timestamps and in different coordinate frames. I standardised timestamps, frames and validity checks, so the motion-control layer and the task layer get one consistent, trusted robot state.
> Third, coordination over M-DDS: device discovery, capability registration, state synchronisation and task dispatch.
> Fourth, and this is the part I care most about, the safe-execution chain. A task plan is never sent straight to a robot. It goes through an action proposal, a policy check, execution, and state feedback. That's how a high-level, possibly AI-generated, decision becomes a physical action in a controlled way."

中文：（要点）四块：统一运动接口（C++ 能力模型 + ROS/ROS2 指令映射到底层驱动，运动控制代码跨硬件复用）；状态管理（时间戳、坐标系、有效性检查标准化，给运动控制与任务层一致可信状态）；M-DDS 协同（发现、注册、同步、派发）；安全执行链（计划不能直发机器人，须经提案、策略检查、执行、状态反馈——AI 决策受控变成物理动作）。

- **关键词提示**：capability model / reuse across hardware / consistent trusted state / dispatch / policy check。
- **易说错点**：① 策略检查具体检查什么 `【待你补全：policy-check 的规则类型，如限速、工作空间、设备状态】`——只有你确认才能说；② 不要夸大"多机协同"规模（几台机器人）；③ 不要说"AI 生成的计划"是平台的现状，应说"高层计划（包括可能由 AI 生成的）"。

### 8.3 3 分钟版

> "My current internship is at Shenzhen Kaihong, on the M-Robots multi-robot platform running on OpenHarmony. My scope is device abstraction and motion coordination, and I developed and integrated four parts independently. I'll go through them in the order the data flows.
> One: the unified motion interface. Different robots have different sensors, actuators and controllers. In C++ I built a capability model that gives them a common description. Then I mapped ROS and ROS2 motion commands onto the low-level drivers. The practical result is that motion-control code written once can be reused across hardware, because it talks to capabilities, not to a specific driver.
> Two: state management. A robot's state comes from many sources: perception, actuator feedback, with different timestamps and different coordinate frames, and some of it may be invalid. I standardised the timestamps and frames and added validity checks. The motion-control layer and the task layer then see one consistent and trusted state. This comes straight from my navigation and wheel-legged projects, where I learned that many mysterious control problems are really state-inconsistency problems.
> Three: distributed coordination. Over M-DDS, I implemented device discovery, capability registration, state synchronisation and task dispatch. So the platform knows which device exists, what it can do, what state it is in, and can send tasks to it.
> Four: the safe-execution chain. This is the core of my statement of purpose. A high-level task plan can't be sent directly to a robot. It's first an action proposal; then a policy check decides whether it's allowed given the current state; only then is it executed, and the resulting state is fed back, so the next decision sees what really happened. Even if the plan comes from a learning-based or language-model planner, the physical side stays controlled.
> What I'm learning is that the hard part of putting AI on robots isn't the model alone — it's the interface between a decision and a physical action. That's what I'd like to study more deeply in a master's programme."

中文：（要点）按数据流讲四块。1 统一运动接口：能力模型 + ROS/ROS2 指令映射到底层驱动，运动控制代码面向"能力"而非具体驱动，因此跨硬件复用。2 状态管理：多源感知与执行器反馈，时间戳/坐标系不同、可能无效；标准化并加有效性检查，上层看到一致可信状态——这来自导航与轮腿项目的教训（许多控制怪问题其实是状态不一致）。3 分布式协同：M-DDS 上设备发现、能力注册、状态同步、任务派发。4 安全执行链：高层任务计划不能直发；先是提案，策略检查依据当前状态判断是否允许，再执行，并把状态反馈给下一次决策；即使计划来自学习/语言模型规划器，物理侧仍受控。总结：AI 上机器人的难点不只是模型，而是决策与物理动作之间的接口——这是我想在硕士阶段深入学习的。

- **关键词提示**：capabilities not drivers / consistent trusted state / discovery–registration–sync–dispatch / allowed given current state / feedback to next decision。
- **易说错点**：① "policy check decides whether it's allowed given the current state" 是对 CV 的合理口语化；若被追问规则内容，如实说你需补全的部分；② 不要涉及公司保密的代码、协议细节；③ PS 里"AI 决策→物理动作"是你的叙事主线，但不要说这个链已被用于某个具体 AI 产品。

## 9. P7 可变腿长轮腿机器人

> 详细讲义：[P7 README](../../01_项目课程/P7_可变腿长轮腿机器人/README.md)；深挖问答：[P7 英文面试口述与深挖问答](../../01_项目课程/P7_可变腿长轮腿机器人/99_英文面试口述与深挖问答.md)。

**CV 事实锚点**：Lab project · LQR/VMC balance control，Nov 2025 – Mar 2026；实验室轮腿平台；负责平衡控制算法与机上整定；腿长变化时机身保持平衡并跟踪速度指令。三条 bullet：增益调度 LQR（IMU、轮速、关节反馈建立机体俯仰与运动状态，按腿长调度增益，把平衡与运动误差转成轮毂与髋关节力矩）；VMC 力矩控制（闭链运动学算虚拟腿长与姿态，雅可比把支撑力与俯仰力矩映射到关节，腿长 PID + 力前馈协调伸缩）；机上整定（STM32H7/FreeRTOS + FDCAN，追踪平衡异常到状态不一致、力矩限制、触地切换，并在机上调参）。

### 9.1 30 秒版

> "In a lab project I was responsible for the balance control and on-robot tuning of a wheel-legged robot with variable leg length. I built a gain-scheduled LQR, where the gains change with leg length, and virtual model control that turns support force and pitch torque into joint torques through the Jacobian of the closed-chain leg. The robot kept its body balanced and tracked velocity commands while the legs changed length."

中文：在实验室项目中，我负责可变腿长轮腿机器人的平衡控制和机上整定。我做了增益随腿长调度的 LQR，以及虚拟模型控制：通过闭链腿的雅可比把支撑力和俯仰力矩变成关节力矩。腿长变化时机身保持平衡并跟踪速度指令。

- **关键词提示**：gain-scheduled LQR / leg length / VMC / closed-chain / Jacobian / on-robot tuning。
- **易说错点**：① 这里 LQR 是**部署的主控制器**（与 P1 不同），别混；② 不要说"我设计了五连杆机构"，是用闭链运动学算虚拟腿；③ 不要讲具体腿长范围。

### 9.2 90 秒版

> "The platform is a wheel-legged robot: two wheels on legs whose length can change. I was responsible for the balance algorithms and the on-robot tuning.
> The first part is a gain-scheduled LQR. From IMU, wheel-speed and joint feedback I build the body pitch and motion states. Because the dynamics change with leg length, one fixed gain can't be good everywhere, so I schedule the LQR gains by leg length. The controller turns balance and motion errors into torques for the wheel hubs and the hips.
> The second part is VMC — virtual model control. The leg is a closed-chain mechanism. I compute a virtual leg length and posture from the closed-chain kinematics, and use the Jacobian to map a support force and a pitch torque to the joint torques. A leg-length PID with force feedforward coordinates the extension.
> The third part is on-robot tuning on an STM32H7 with FreeRTOS and FDCAN. When something went wrong, I traced the balance anomalies to state inconsistency, torque limits and ground-contact transitions, then tuned the parameters on the robot."

中文：（要点）轮腿机器人：腿长可变。增益调度 LQR：由 IMU、轮速、关节反馈建机体俯仰与运动状态，动力学随腿长变化，故按腿长调度增益；输出轮毂与髋关节力矩。VMC：闭链运动学算虚拟腿长和姿态，雅可比把支撑力与俯仰力矩映射到关节；腿长 PID + 力前馈协调伸缩。机上整定：STM32H7/FreeRTOS/FDCAN，把平衡异常追到状态不一致、力矩限制、触地切换，并机上调参。

- **关键词提示**：schedule by leg length / virtual leg / support force / Jacobian / state inconsistency / torque limits / ground-contact transition。
- **易说错点**：① "两个轮子"属于轮腿机器人的常见构型，CV 未写数量；若你的平台不是两轮 `【待你补全：轮/腿数量与自由度】`；② 增益调度的实现方式（查表/拟合多项式）`【待你补全】`；③ 不要给力矩限幅数值。

### 9.3 3 分钟版

> "Let me tell you about the wheel-legged robot, a lab project from November 2025 to March 2026. The robot keeps its body balanced and tracks velocity commands while its leg length changes. I was responsible for the balance algorithms and the on-robot tuning.
> Start with why the leg length matters. A wheel-legged robot is like an inverted pendulum on wheels, and its pendulum length is the leg length. If the leg is long, the dynamics are different from when it's short, so a single LQR gain is a compromise. I built the body-pitch and motion states from IMU, wheel speed and joint feedback, designed LQR gains at different leg lengths, and scheduled them by leg length. The controller converts balance and motion errors into wheel-hub torque and hip torque.
> Then the leg. Each leg is a closed-chain mechanism, so the foot position isn't a simple function of motor angles. Using the closed-chain kinematics I compute a virtual leg — its length and its posture. Then virtual model control: I decide the support force along the virtual leg and the pitch torque I want, and map them to the joint motors using the Jacobian. A leg-length PID, with force feedforward, handles the extension and retraction.
> The real learning was in the on-robot tuning, on an STM32H7 with FreeRTOS and FDCAN. Balance anomalies often looked like 'bad gains', but when I traced them, there were three typical sources. One: state inconsistency, where the states fed to the controller weren't from the same moment or the same frame. Two: torque limits, where the controller commanded more than the motors could deliver. Three: ground-contact transitions, where the robot changes between in-air and on-ground. I fixed the root cause first, and only then tuned the parameters.
> The lesson is to separate three questions: is the state right, is the output achievable, and is the mode right — and only then ask whether the gain is right. I started to ask these same questions in my navigation work and now in my platform work at Kaihong."

中文：（要点）轮腿像"轮上的倒立摆"，摆长就是腿长；长腿与短腿动力学不同，单一 LQR 增益是折中，所以由 IMU/轮速/关节反馈建机体俯仰与运动状态，在不同腿长设计 LQR 增益并按腿长调度，输出轮毂与髋力矩。每条腿是闭链机构，足端位置不是电机角的简单函数；用闭链运动学算虚拟腿长度与姿态；VMC：定义沿虚拟腿的支撑力与想要的俯仰力矩，经雅可比映射到关节电机；腿长 PID + 力前馈负责伸缩。机上整定：平衡异常常像"增益不好"，追下去有三个典型来源——状态不一致、力矩限制、触地切换（腾空/着地）；先修根因再调参。教训：先问状态对不对、输出能不能实现、模式对不对，再问增益对不对；此习惯带到导航与 Kaihong 的平台工作中。

- **关键词提示**：pendulum length = leg length / closed chain / virtual leg / three root causes / fix the cause, then tune。
- **易说错点**：① "三个典型来源"在 CV 中是 "state inconsistency, torque limits and ground-contact transitions"，不要增加第四个；② "不同腿长设计 LQR 增益"的具体操作（离线算还是在线）`【待你补全】`；③ P7 仓库是公开课程代码，不要说成自己的原创开源；你讲的是自己的机上实现与整定。

## 本章要点速记

1. 先背 CV 的 Overview 一句话，再展开；动词保持分寸：responsible for / independently built / developed and integrated。
2. 三种长度的结构：30 秒 = 做什么+你负责什么+结果；90 秒 = 背景+2–3 模块+难点；3 分钟 = 加系统结构+排错故事+反思。
3. P1 的 LQR 是**分析与参考**，部署的是级联 PID；P7 的 LQR 才是主控制器（增益调度）。
4. P2 的奇异：说"抑制速度放大"，不说"消除奇异"。
5. P3 的迭代：PID → 变增益 PID → 滑模，需能解释"为什么"（负载变化、固定增益的取舍）。
6. P4/P6 的共同线：AI 决策只发"建议/提案"，设备端/策略检查有自己的底线。
7. P5/P7/P6 的共同线：状态一致（时间、坐标系、方向、有效性）先于算法。
8. AI 面试官：P6 + P4 在前；控制面试官：P1 + P7 在前；CS：P6 + P5；HR：P6 + P3。
9. 没有数字就用语言描述；`【待你补全】` 先补进各项目 README 的自查表。
