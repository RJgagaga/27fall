# 第一部分：P4 整体概述

## Q1：P4 是什么？

P4 是一个**分布式 IoT / 边缘视觉与决策系统**，用于智能园艺。它有三层：

| 层 | 设备 | 职责 |
|---|---|---|
| 本地控制 | Hi3861 | 读土壤湿度，本地控制水泵 |
| 边缘视觉 | RK3588 | 摄像头采集，YOLO/RKNN 推理，输出检测事件 |
| 服务决策 | Python 服务器 | 汇聚数据，WebSocket 展示，Agent 建议，执行策略 |

**核心原则**：

> P4 不是“AI 看一眼，然后直接浇水”。本地控制、边缘视觉、服务决策各在不同设备上运行，消息经过网络。五类信息不能互相替代。

## Q2：五类信息是什么？

| 类型 | 含义 | 例子 |
|---|---|---|
| 传感读数 | 土壤探头给出 ADC 数值 | moisture=55 |
| 模型观测 | 摄像头模型说“可能有某类病斑” | class=病斑, confidence=0.9, bbox |
| 建议 | 服务/Agent 提出需要浇水或提醒 | action=start |
| 命令请求 | 软件向设备请求开泵、关泵 | hardware_command=on |
| 设备反馈 | 设备回报水泵现在的状态 | reported_state=on |

**关键**：

> 网页出现“请求已发送”不等于设备收到，更不等于水已经流出来。

## Q3：为什么分本地和服务器？

**中文理解**：

本地处理及时灌溉和人工开关，服务器处理视觉、解释、界面；断网不能让最基本执行逻辑依赖 LLM。

**英文参考**：

> Local control handles immediate irrigation and manual operation. The server handles visual observations, richer decisions and user interaction. Basic actuator behavior should have a defined local policy during network loss.

## Q4：完整数据链是什么？

```text
Hi3861:
  ADC → 源标定 → 湿度 → manual/滞回 → 低触发 GPIO → sensor JSON → 网络上报

RK3588:
  采集/预处理 → RKNN 推理 → 后处理 → class/conf/bbox/location/time → JSON/JPEG 分段 TCP

服务:
  解析 → DataStore 快照 → Web 广播与 Agent 事件
  → sensing 规则 fast path 或 supervisor/care/alert
  → execution 白名单与硬件请求
  → 显示/设备反馈
```

## Q5：源码文件职责是什么？

| 文件 | 职责 |
|---|---|
| `smart_plant_client.c` | 湿度/滞回/manual/GPIO |
| `rknn_plant_disease_tcp.cpp` | 视觉 JSON 与发送 |
| `onnx2rknn.py` | INT8 转换 |
| `plant_graph.py` | 当前图与事件去重 |
| `rule_engine.py` | 规则阈值 |
| `server.py` | 汇聚/广播/执行接口 |
| `app.js` | 前端状态 |

# 第二部分：本地灌溉控制

## Q6：滞回是什么？

**中文理解**：

低于启动阈值开，高于停止阈值关，中间保持之前状态；源码 56/65 配置不等于所有土壤通用阈值。

**英文参考**：

> Different start and stop thresholds prevent rapid switching near one boundary. Between the thresholds, the previous pump state is retained. The source values are configuration values, not universal soil thresholds.

## Q7：滞回怎么工作？

源码用两个阈值：

- 湿度 < 56：开泵
- 湿度 > 65：关泵
- 56 到 65 之间：保持上次状态

举例：

```text
初始 off
m=55 → on
m=60 → 保持 on
m=64 → 保持 on
m=66 → off
m=60 → 保持 off
```

## Q8：边界条件是什么？

源码使用**严格**比较：

- `m < 56` 才开
- `m > 65` 才关
- `m = 56` 或 `m = 65`：保持

## Q9：为什么不能单阈值？

**中文理解**：

噪声在阈值两侧跳使继电器频繁开关；滞回消除小波动触发，但还可需最短开关时间和水量限制。

**英文参考**：

> Noise near a single threshold can repeatedly toggle the actuator. Hysteresis provides a dead band, while minimum dwell time and water limits address additional concerns.

## Q10：ADC 值是湿度真值吗？

**中文理解**：

源码线性映射并截 0 到 100 是标定表示；传感器、电压、土壤条件影响，需要参考测量，百分号不自动是体积含水量。

源码：

```c
moisture = adc * (-0.05) + 147.52
clip 到 [0, 100]
```

手算：

```text
ADC = 2000
moisture = 2000 × (-0.05) + 147.52 = -100 + 147.52 = 47.52
int16 截断 → 47
```

## Q11：GPIO 低有效什么意思？

**中文理解**：

GPIO 低电平启用，高电平关闭，逻辑 pump_on 与电平需转换，不能把 true 直接输出高电平。

源码：

- 初始化 GPIO_HIGH 关闭。
- 开泵设 GPIO_LOW。
- 继电器是**低触发**。
- 逻辑 `watering=1` 与物理引脚电平 0 同时成立。

## Q12：人工控制如何优先？

**中文理解**：

显式模式与优先级，manual_off 可即时覆盖；源码某些语音 off 会回自动，随后低湿度可重开，要读实际状态转换。

源码 `g_manual_control` 和命令字符串控制模式。

- 手动模式下，`ControlWaterPump` 直接 return，不执行自动逻辑。
- 语音关闭函数可恢复自动。
- 关闭后低湿可能下周期再启动。

不能说所有“off”都永久保持。

## Q13：语音触发怎么工作？

```text
CheckVoiceTrigger 激活后:
  开泵并进入手动
  等待信号消失后关泵、恢复自动
```

等待循环会影响该线程其他工作。不能把这段行为改说成永久手动模式。

## Q14：本地控制的失败条件有哪些？

| 现象 | 可能原因 |
|---|---|
| start≥stop 无正确滞回 | 阈值配置错 |
| GPIO 反向 | 低触发理解错 |
| 传感断线读假干 | 传感器故障 |
| manual 恢复 auto 立刻重启 | 状态转换错 |
| ADC 标定不适用 | 探头不匹配 |

# 第三部分：边缘视觉

## Q15：整体流水线是什么？

```text
摄像头
  ↓ V4L2 取帧
原始帧（YUYV/MJPEG）
  ↓ 颜色转换 + resize/letterbox + 归一化
模型输入（640×640×3）
  ↓ RKNN 推理
模型原始输出（候选框 + 类别分数）
  ↓ 后处理：置信度过滤 + NMS 去重
  ↓ 坐标恢复到原图
  ↓ 结构化事件（class/conf/bbox/location/time）
  ↓ JSON + JPEG 分段 TCP 发送
```

## Q16：V4L2 是什么？

V4L2 = Video for Linux 2，是 Linux 下摄像头采集的标准接口。

它负责：

- 打开摄像头设备。
- 设置分辨率、像素格式、帧率。
- 请求缓冲区。
- 取帧。

## Q17：常见像素格式有哪些？

| 格式 | 含义 | 每像素字节 |
|---|---|---|
| YUYV | YUV 4:2:2 打包 | 2 |
| MJPEG | JPEG 压缩帧 | 可变 |
| RGB24 | RGB 各 8 位 | 3 |
| BGR24 | BGR 各 8 位 | 3 |

## Q18：V4L2 完整流程是什么？

```text
open → QUERYCAP → S_FMT → REQBUFS → QUERYBUF → mmap
→ QBUF（全部入队） → STREAMON
→ 循环：DQBUF → 处理 → QBUF
→ STREAMOFF → munmap → close
```

### 打开设备

```c
int fd = open("/dev/video0", O_RDWR | O_NONBLOCK, 0);
```

### 查询设备能力

```c
struct v4l2_capability cap;
ioctl(fd, VIDIOC_QUERYCAP, &cap);
```

### 设置像素格式和分辨率

```c
struct v4l2_format fmt;
fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
fmt.fmt.pix.width = 1280;
fmt.fmt.pix.height = 720;
fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_YUYV;
ioctl(fd, VIDIOC_S_FMT, &fmt);
```

### 申请缓冲区

```c
struct v4l2_requestbuffers req;
req.count = 4;
req.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_MMAP;
ioctl(fd, VIDIOC_REQBUFS, &req);
```

### 查询并映射缓冲区

```c
struct v4l2_buffer buf;
buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
buf.memory = V4L2_MEMORY_MMAP;
buf.index = i;
ioctl(fd, VIDIOC_QUERYBUF, &buf);

buffers[i].start = mmap(NULL, buf.length, PROT_READ | PROT_WRITE,
                        MAP_SHARED, fd, buf.m.offset);
```

### 将缓冲区入队

```c
for (int i = 0; i < n_buffers; i++) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = i;
    ioctl(fd, VIDIOC_QBUF, &buf);
}
```

### 启动流

```c
enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
ioctl(fd, VIDIOC_STREAMON, &type);
```

### 取帧循环

```c
while (1) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    
    ioctl(fd, VIDIOC_DQBUF, &buf);
    process_image(buffers[buf.index].start, buf.bytesused);
    ioctl(fd, VIDIOC_QBUF, &buf);
}
```

### 停止与清理

```c
ioctl(fd, VIDIOC_STREAMOFF, &type);
// munmap 每个缓冲区
// close(fd)
```

## Q19：取帧循环详解

### 为什么需要队列

摄像头**持续**采集，程序**间歇**处理。如果只有一个缓冲区，摄像头写的时候程序不能读，程序读的时候摄像头不能写。所以需要多个缓冲区。

### 类比：餐厅传菜

- 厨房 = 摄像头，不断做菜。
- 服务员 = 驱动程序。
- 餐桌 = 程序，不断吃菜。
- 盘子 = 缓冲区。

盘子有 4 个，放在两个区域：

```text
[空盘区]                     [已装菜区]
盘1                          盘2
盘3                          盘4
```

- 厨房把菜装到空盘上，放到已装菜区。
- 服务员从已装菜区拿盘子，给餐桌。
- 餐桌吃完，盘子洗好，放回空盘区。

### 两个队列

| 队列 | 谁放 | 谁取 | 含义 |
|---|---|---|---|
| 输入队列 | 程序 | 驱动 | 空缓冲区，等待驱动填充 |
| 输出队列 | 驱动 | 程序 | 已填充的缓冲区，等待程序处理 |

### 启动阶段

程序先把**所有**缓冲区放入输入队列：

```c
for (int i = 0; i < n_buffers; i++) {
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = i;
    ioctl(fd, VIDIOC_QBUF, &buf);
}
```

翻译：

```text
盘1 → 空盘区
盘2 → 空盘区
盘3 → 空盘区
盘4 → 空盘区
```

### 启动流

```c
ioctl(fd, VIDIOC_STREAMON, &type);
```

翻译：厨房开始做菜。

### 循环阶段

```c
while (1) {
    // 1. 从输出队列取一个填好的缓冲区
    ioctl(fd, VIDIOC_DQBUF, &buf);
    
    // 2. 处理这个缓冲区里的图像
    process_image(buffers[buf.index].start);
    
    // 3. 处理完，把缓冲区放回输入队列
    ioctl(fd, VIDIOC_QBUF, &buf);
}
```

### 时间线举例

假设有 4 个缓冲区，摄像头 30 fps（每 33 ms 一帧），程序处理一帧 50 ms。

```text
t=0 ms:
  输入队列: [1,2,3,4]
  输出队列: []
  程序: 等待

t=33 ms:
  驱动填充盘1 → 输出队列
  输入队列: [2,3,4]
  输出队列: [1]
  程序: DQBUF 拿到盘1，开始处理

t=50 ms:
  程序还在处理盘1
  驱动填充盘2 → 输出队列
  输入队列: [3,4]
  输出队列: [2]

t=66 ms:
  驱动填充盘3 → 输出队列
  输入队列: [4]
  输出队列: [2,3]

t=83 ms:
  程序处理完盘1 → QBUF 放回输入队列
  输入队列: [4,1]
  输出队列: [2,3]
```

### 常见困惑

**为什么要 4 个缓冲区，不是 1 个？**

1 个缓冲区：驱动写的时候程序不能读，程序读的时候驱动不能写，效率极低。多个缓冲区让驱动和程序并行。

**DQBUF 会阻塞吗？**

取决于模式：阻塞模式没数据就等；非阻塞模式立即返回 `EAGAIN`。

**处理太慢会怎样？**

输出队列积压。如果 4 个缓冲区都在输出队列，驱动没空盘可用，可能丢弃新帧。

**QBUF 之后还能用这块内存吗？**

不能。QBUF 之后缓冲区交还给驱动，驱动可能立刻用新数据覆盖。

## Q20：预处理做什么？

把摄像头原始帧变成模型输入需要的格式：

| 步骤 | 目的 |
|---|---|
| 颜色转换 | YUYV → RGB/BGR |
| resize | 缩放到模型输入尺寸 |
| letterbox | 保持比例，补边到正方形 |
| 归一化 | 数值缩放到模型期望范围 |
| 维度变换 | HWC → CHW 或加 batch 维 |

## Q21：resize vs letterbox

**直接 resize**：把 1280×720 直接缩到 640×640，图像被拉伸变形。

**letterbox**：按比例缩放，短边补边，宽高比保持。

举例：

```text
原图 1280×720
按比例缩到 640×360
上下各补 140 像素
变成 640×640
```

## Q22：letterbox 后的坐标逆变换

模型输出框是在 640×640 上的，要恢复到原图：

```text
模型框 y=200
减去上边补边 140
得到 y=60（在 640×360 上）
除以缩放比例 0.5
得到原图 y=120
```

公式：

\[
y_{\text{原图}} = \frac{y_{\text{模型}} - \text{pad\_top}}{\text{scale}}
\]

其中：

\[
\text{scale} = \frac{640}{1280} = 0.5
\]

**忘记撤销补边，框会整体偏移。**

## Q23：归一化参数

源码配置：

```python
config mean=0, std=255
```

意思是：

\[
x_{\text{norm}} = \frac{x - 0}{255}
\]

把 0–255 的像素值缩到 0–1。

不同模型可能用不同的 mean/std，必须和训练时一致。

## Q24：颜色顺序为什么重要？

- OpenCV 默认 BGR。
- PIL 默认 RGB。
- 摄像头可能输出 YUYV。

如果训练用 RGB，推理时给 BGR，红色和蓝色通道互换，模型可能检测变差。

## Q25：INT8 量化是什么？

YOLO 模型通常是 FP32，RK3588 的 NPU 更适合 INT8。

量化：

- 减少模型大小。
- 加速推理。
- 降低功耗。

代价：

- 可能损失精度。

## Q26：量化公式

浮点转整数：

\[
q = \text{clip}\left(\text{round}\left(\frac{x}{s}\right) + z,\ q_{\min},\ q_{\max}\right)
\]

反量化：

\[
x \approx s \cdot (q - z)
\]

- \(s\)：scale，步长。
- \(z\)：zero point，零点。

## Q27：手算量化例子

```text
s = 0.1, z = 0
x = 0.26
q = round(0.26 / 0.1) + 0 = round(2.6) = 3
反量化 = 0.1 × (3 - 0) = 0.3
误差 = |0.26 - 0.3| = 0.04
```

误差 0.04 ≤ s/2 = 0.05。

## Q28：饱和误差

```text
x = 20
s = 0.1
q = round(20 / 0.1) = 200
但 INT8 最大 127
clip 到 127
反量化 = 0.1 × 127 = 12.7
误差 = |20 - 12.7| = 7.3
```

误差 7.3 远大于 s/2。**饱和时误差可以很大。**

## Q29：对称量化 vs 非对称量化

**对称量化**：\(z = 0\)，浮点范围对称。

**非对称量化**：\(z \neq 0\)，浮点范围可以不对称。非对称量化通过引入零点参数，使数据可以平移，从而完全利用 8 位整数的表示范围。

## Q30：逐通道量化是什么？

卷积层的权重张量形状是 \([C_{\text{out}}, C_{\text{in}}, K_h, K_w]\)。不同输出通道的权重分布可能差异很大。

**逐层量化**：整个张量共享一个 scale，小范围的通道被“稀释”，精度损失大。

**逐通道量化**：每个输出通道有独立的 scale 和 zero point。

\[
q_c = \text{clip}\left(\text{round}\left(\frac{x_c}{s_c}\right) + z_c\right)
\]

**RKNN 采用 Per-Channel 量化处理权重信息**，能更好地保存各通道信息，有效缓解通道参数差异引起的量化误差。

**关键**：在 RKNN3-Toolkit 中，Per-Channel 和 Group 量化仅针对**权重**；**激活值和中间值仍采用 Per-Layer 量化**。

## Q31：逐通道量化手算

假设一个卷积层有 2 个输出通道：

**通道 1 权重范围**：\([-0.5, 0.5]\)

\[
s_1 = \frac{0.5}{127} \approx 0.00394
\]

**通道 2 权重范围**：\([-2.0, 2.0]\)

\[
s_2 = \frac{2.0}{127} \approx 0.01575
\]

**逐层量化**（全局范围 \([-2.0, 2.0]\)）：

\[
s = \frac{2.0}{127} \approx 0.01575
\]

通道 1 的权重 0.1：

\[
q = \text{round}(0.1 / 0.01575) = \text{round}(6.35) = 6
\]

反量化：\(0.01575 \times 6 = 0.0945\)，误差 0.0055。

**逐通道量化**（通道 1 用自己的 scale）：

\[
q = \text{round}(0.1 / 0.00394) = \text{round}(25.4) = 25
\]

反量化：\(0.00394 \times 25 = 0.0985\)，误差 0.0015。

逐通道量化误差更小。

## Q32：校准集为什么重要？

量化需要校准集来估计激活范围。

- 校准集要有代表性。
- 光照、背景、植物条件要像真实使用。
- 如果校准集偏差大，量化范围失配。
- RKNN 推荐 20–200 张图片。

## Q34：转换 vs 训练

| | 训练 | 转换 |
|---|---|---|
| 输入 | 数据 + 标签 | 已有权重 |
| 输出 | 权重 | 设备格式 |
| 做什么 | 学习参数 | 格式转换 |
| 需要 | 损失、优化、验证 | 校准集 |

**关键**：

> ONNX 转 RKNN 是部署转换，不等于训练 YOLO。当前转换脚本不能单独证明本人从头训练模型。

# 第四部分：YOLO 面试必备知识

## Q35：YOLO 是什么？

YOLO = You Only Look Once。

一句话：

> 只看一次图像，就直接输出所有目标的类别和位置。

对比传统方法：

| 方法 | 做法 | 速度 |
|---|---|---|
| 两阶段（R-CNN） | 先找候选区域，再分类 | 慢 |
| 单阶段（YOLO） | 一次前向传播直接输出 | 快 |

## Q36：YOLO 的核心思想是什么？

### 网格划分

把图像分成 \(S \times S\) 个网格。每个网格负责检测**中心落在该网格内**的目标。

### 每个网格预测什么

- **B 个边界框**：每个框有 \((x, y, w, h)\)。
- **框的置信度**：这个框包含目标的概率。
- **C 个类别概率**：属于每个类别的概率。

### 边界框的表示

- \((x, y)\)：框中心相对网格的偏移，归一化到 [0, 1]。
- \((w, h)\)：框的宽高，相对整张图归一化到 [0, 1]。

## Q37：YOLO 的演进

| 版本 | 年份 | 关键改进 |
|---|---|---|
| YOLOv1 | 2016 | 单阶段检测，网格划分 |
| YOLOv2 | 2017 | 锚框、Batch Norm |
| YOLOv3 | 2018 | 多尺度预测、残差网络 |
| YOLOv4 | 2020 | CSPDarknet、Mish |
| YOLOv5 | 2020 | 工程优化、易用 |
| YOLOv8 | 2023 | 无锚框、C2f 模块 |

**面试重点**：

- YOLOv1 到 v3 用**锚框**。
- YOLOv8 用**无锚框**。

## Q38：锚框是什么？

不同目标的形状不同：人高瘦，车扁宽。如果只用一种框，很难覆盖所有形状。锚框就是**预设的几种框形状**。

每个网格预测相对于锚框的偏移量，而不是直接预测框的绝对大小。

锚框通常用 **K-means 聚类**在训练集上得到。

YOLOv8 不用锚框，直接预测框的中心和宽高。

## Q39：YOLO 输出张量是什么？

YOLOv8 输出：

\[
(1, C, A)
\]

- 1：batch size。
- \(C = 4 + \text{类别数}\)。
- \(A\)：锚点数量（如 8400）。

前 4 个通道：\(c_x, c_y, w, h\)。

其余 \(C-4\) 个通道：每个类别一个分数。

举例：80 类，8400 个锚点：

\[
(1, 84, 8400)
\]

## Q40：解码怎么做？

模型输出的是**归一化值**，需要解码成**像素坐标**。

1. \(c_x, c_y, w, h\) 是归一化的 [0, 1]。
2. 乘以图像宽高：

\[
x_1 = (c_x - w/2) \times W
\]

\[
y_1 = (c_y - h/2) \times H
\]

\[
x_2 = (c_x + w/2) \times W
\]

\[
y_2 = (c_y + h/2) \times H
\]

手算：

```text
c_x = 0.5, c_y = 0.4, w = 0.2, h = 0.3
W = 640, H = 640

x1 = (0.5 - 0.1) × 640 = 256
y1 = (0.4 - 0.15) × 640 = 160
x2 = (0.5 + 0.1) × 640 = 384
y2 = (0.4 + 0.15) × 640 = 352
```

框：`[256, 160, 384, 352]`

## Q41：置信度是什么？

每个框有一个置信度，表示：

> 这个框包含目标的概率 × 类别概率。

**置信度不是准确率**：

- confidence=0.9 不是“90% 准确率”。
- 它是模型对**这一次**检测的分数。
- 未必是校准概率。

## Q42：NMS 是什么？

NMS = 非极大值抑制，用于**去重复框**。

步骤：

1. 按分数从高到低排序。
2. 取最高分框。
3. 计算它与其他框的 IoU。
4. 删除 IoU 超过阈值的框。
5. 重复直到没有框。

通常按类别分别做 NMS。

## Q43：IoU 怎么算？

\[
\text{IoU} = \frac{\text{交集面积}}{\text{并集面积}}
\]

手算：

```text
框 A = [0,0,10,10]，面积 100
框 B = [5,0,15,10]，面积 100
交集 = [5,0,10,10]，面积 50
并集 = 100 + 100 - 50 = 150
IoU = 50/150 = 1/3
```

## Q44：评估指标有哪些？

### Precision（精确率）

\[
\text{Precision} = \frac{\text{TP}}{\text{TP} + \text{FP}}
\]

### Recall（召回率）

\[
\text{Recall} = \frac{\text{TP}}{\text{TP} + \text{FN}}
\]

### mAP（平均精度均值）

- AP：Precision-Recall 曲线下的面积。
- mAP：所有类别 AP 的平均。

**面试重点**：mAP 是数据集级别的指标，confidence 是单次检测的分数。

### FPS

每秒处理多少帧。**不等于端到端延迟**。

## Q45：YOLO 后处理在量化空间做什么？

**关键优化**：

- 先在量化整数空间做阈值过滤。
- 避免反量化整个张量（数千个元素）。
- 只对存活值反量化，节省时间和内存。

```python
# 错误做法：先反量化整个张量
# 正确做法：量化阈值，在整数空间比较
t = quantize(model, self.threshold)
score_indices = threshold(score_block, t, find_max=True)
```

## Q46：YOLO 面试常见问题

**Q：YOLO 输出是什么？**

> 候选框 + 类别分数。形状是 \((1, C, A)\)，前 4 通道是框，其余是类别分数。

**Q：置信度是准确率吗？**

> 不是。它是模型对单次检测的分数，不等于数据集级别的准确率。

**Q：NMS 做什么？**

> 去重复框。按分数排序，保留最高分，删除 IoU 超过阈值的框。

**Q：IoU 怎么算？**

> 交集面积除以并集面积。

**Q：锚框是什么？**

> 预设的几种框形状。模型预测相对于锚框的偏移量。YOLOv8 用无锚框。

**Q：YOLO 为什么快？**

> 单阶段检测，一次前向传播直接输出所有框。

**Q：INT8 量化影响？**

> 模型变小、速度提升，但精度可能下降。校准集要覆盖真实分布。

**Q：空检测能说明什么？**

> 不能说明健康。可能遮挡、失焦、光照差、模型漏检。

**Q：转换和训练的区别？**

> 训练是学习权重，需要数据、标签、损失、验证。转换是部署格式转换。

**Q：mAP 是什么？**

> 所有类别 AP 的平均。AP 是 Precision-Recall 曲线下的面积。

## Q47：YOLO 中间过程有必要学吗？

**P4 项目需要**：接口层 + 后处理层。

**不需要**：网络内部细节、训练、损失函数。

**面试会问**：输出是什么、NMS、坐标恢复、量化影响、转换 vs 训练。

**不会问**：YOLO 网络结构、损失函数设计。

**一句话**：P4 是**用模型**，不是**做模型**。懂接口和后处理就够了。

## Q57：TCP 是字节流，为什么不能一次 recv 当一条消息？

TCP 是**字节流**，不是消息流。

发送端一次写 108 字节：

```text
[长度头 8 字节][JSON 100 字节]
```

接收端可能：

- 第一次 recv 拿到 20 字节。
- 第二次 recv 拿到 88 字节。
- 也可能一次拿到 108 字节。
- 甚至两条消息粘在一起。

## Q58：长度前缀怎么用？

源码 `tcp_send_data`：

```text
1. 发送 length（8 字节）
2. 发送 payload（length 字节）
```

接收端：

```text
1. 先读 8 字节长度头
2. 解析出 length
3. 循环读取直到收满 length 字节
4. 拼接成完整消息
```

手算：

```text
JSON = 100 字节
长度头 = 8 字节
总 = 108 字节

recv 先到 20 字节
还需 108 - 20 = 88 字节
不能把 20 当完整 JSON
```

## Q59：DataStore 是什么？

服务器有多个线程：

- TCP 接收线程。
- WebSocket 广播。
- Agent 事件处理。
- 执行层。

它们需要访问**同一份**最新状态。DataStore 就是共享状态容器。

### 存什么

| 数据 | 来源 | 含义 |
|---|---|---|
| 传感器快照 | Hi3861 | 湿度、温度、光照、泵状态 |
| 视觉事件 | RK3588 | 类别、置信度、框、位置、时间 |
| 执行状态 | 执行层 | 命令请求、设备反馈 |

### 并发保护

文档说：

> DataStore 共享快照需短锁；阻塞 LLM/网络调用不能卡住所有 Web 连接。

翻译：

- 状态更新要加短锁。
- 锁内不要做耗时操作。
- 否则会阻塞其他线程。

## Q60：WebSocket 是什么？

WebSocket 是**双向**通信协议：

- 服务器可以主动推送。
- 网页可以主动发送。

对比：

| 协议 | 方向 | 用途 |
|---|---|---|
| HTTP | 请求-响应 | 网页加载 |
| WebSocket | 双向 | 实时推送 |

**WebSocket 不是硬实时内环**，用于展示，不用于关键控制。

# 第七部分：asyncio

## Q63：asyncio 是什么？

asyncio 是 Python 标准库里的**异步 I/O 框架**。

核心思想：

> 一个线程里，用**事件循环**调度多个任务。当某个任务在等 I/O 时，切换到其他任务。

一句话：

> asyncio 让单线程也能“同时”处理多个 I/O 操作。

## Q64：核心概念有哪些？

### 事件循环

事件循环是 asyncio 的**调度中心**。

```python
import asyncio

async def main():
    print("hello")

asyncio.run(main())
```

`asyncio.run()` 做三件事：

1. 创建事件循环。
2. 运行 `main()`。
3. 关闭事件循环。

### 协程

用 `async def` 定义的函数叫**协程**。

```python
async def fetch_data():
    print("start")
    await asyncio.sleep(1)
    print("done")
    return 42
```

### await

`await` 表示：

> 我在这里等一个操作完成，但我等的时候，让出 CPU 给其他任务。

### 任务

把协程包装成**任务**，可以让它并发运行。

```python
async def main():
    task1 = asyncio.create_task(fetch_data())
    task2 = asyncio.create_task(fetch_data())
    await task1
    await task2
```

## Q65：asyncio vs 多线程

| | asyncio | 多线程 |
|---|---|---|
| 并发单位 | 协程 | 线程 |
| 调度 | 事件循环 | 操作系统 |
| 切换开销 | 小 | 大 |
| 共享状态 | 单线程，安全 | 需要锁 |
| 适合 | I/O 密集 | CPU 密集 + I/O |
| 编程难度 | 需要异步思维 | 需要锁思维 |

## Q66：多个协程怎么并发运行？

### 错误理解

很多人以为协程是“同时运行”的。不是。

**协程是单线程的，同一时刻只有一个协程在运行。**

那为什么看起来像同时？因为协程在**等待 I/O 时会主动让出 CPU**。

### 生活例子

想象你是一个人在厨房做菜。

**同步做法**（没有 asyncio）：

```text
烧水 → 等水开（站着不动，10 分钟）
→ 切菜 → 炒菜
```

等水开的 10 分钟，你**什么都不做**。

**协程做法**（有 asyncio）：

```text
烧水 → 等水开的时候去切菜
→ 水开了 → 回来炒菜
```

等水开的时候，你去做别的事。

### 代码示例

```python
import asyncio

async def task_a():
    print("A: 开始")
    await asyncio.sleep(2)
    print("A: 结束")

async def task_b():
    print("B: 开始")
    await asyncio.sleep(1)
    print("B: 结束")

async def main():
    await asyncio.gather(task_a(), task_b())

asyncio.run(main())
```

输出：

```text
A: 开始
B: 开始
（等 1 秒）
B: 结束
（再等 1 秒）
A: 结束
```

### 逐步执行过程

```text
第 1 步：事件循环启动
  事件循环：我有两个任务 A 和 B，先运行 A。

第 2 步：运行 A
  A: 打印 "A: 开始"
  A: 遇到 await asyncio.sleep(2)
  A: 我要等 2 秒，先让出 CPU

第 3 步：事件循环切换
  事件循环：A 在等，我看看还有谁可以运行。
  事件循环：B 还没跑过，运行 B。

第 4 步：运行 B
  B: 打印 "B: 开始"
  B: 遇到 await asyncio.sleep(1)
  B: 我要等 1 秒，先让出 CPU

第 5 步：事件循环等待
  事件循环：A 在等 2 秒，B 在等 1 秒。
  事件循环：我先睡一会儿，等有任务唤醒我。

第 6 步：1 秒后
  事件循环：B 的 1 秒到了，唤醒 B。
  B: 打印 "B: 结束"
  B: 任务完成。

第 7 步：又过 1 秒
  事件循环：A 的 2 秒到了，唤醒 A。
  A: 打印 "A: 结束"
  A: 任务完成。
```

### 关键理解

| 概念 | 含义 |
|---|---|
| 单线程 | 同一时刻只有一个协程在运行 |
| 并发 | 多个协程在时间上重叠 |
| await | 挂起自己，让出 CPU |
| 事件循环 | 决定下一个运行谁 |

**协程不是真的并行，是“交替执行”。**

## Q67：为什么 WebSocket 用 asyncio？

### WebSocket 的特点

WebSocket 服务器要同时处理**多个客户端**。

假设有 100 个网页连接，服务器要做：有数据时推送给所有客户端，客户端发消息时接收，客户端断开时清理。

### 如果用同步阻塞

```python
def handle_client(ws):
    while True:
        data = ws.recv()      # 阻塞，等客户端发消息
        process(data)

# 100 个客户端 = 100 个线程
for ws in clients:
    threading.Thread(target=handle_client, args=(ws,)).start()
```

问题：

- 100 个线程。
- 每个线程大部分时间在阻塞等待。
- 线程开销大（每个线程约 1MB 栈）。
- 上下文切换开销大。

### 用 asyncio

```python
async def handle_client(ws):
    async for msg in ws:
        await process(msg)

async def main():
    async with websockets.serve(handle_client, "localhost", 8765):
        await asyncio.Future()
```

好处：

- 一个线程处理所有客户端。
- 每个客户端是一个协程。
- 等待时不占 CPU。
- 切换开销极小。

### 对比

| | 线程 | asyncio |
|---|---|---|
| 100 客户端 | 100 线程 | 1 线程 + 100 协程 |
| 内存 | 约 100 MB | 约几 MB |
| 切换 | 操作系统调度，微秒级 | 事件循环调度，纳秒级 |
| 共享状态 | 需要锁 | 单线程，天然安全 |

## Q68：跨线程调用怎么做？

### 问题从哪里来

P4 服务器有两类线程：

```text
线程 A（TCP 接收）:
  阻塞式 socket.recv()

线程 B（asyncio 事件循环）:
  管理 WebSocket
```

线程 A 收到数据，想通知线程 B 广播。

**直接调用行不行？**

```python
# 在线程 A 里
asyncio.create_task(broadcast(msg))    # 错！
```

因为 `asyncio.create_task` 只能从事件循环所在的线程调用。

### 类比

两个人在两个房间，不能直接对话，只能通过**门缝递纸条**。

`run_coroutine_threadsafe` 就是那个“门缝”。

### 正确做法

```python
loop = asyncio.get_event_loop()

# 在线程 A 里
asyncio.run_coroutine_threadsafe(
    broadcast(msg),
    loop
)
```

### 底层发生了什么

1. 加锁（保护队列）。
2. 把 `coro` 包装成回调。
3. 放入 `call_soon` 队列。
4. 唤醒事件循环（如果它在睡）。
5. 解锁。

### 完整例子

```python
import asyncio
import threading
import time

loop = None
clients = []

async def broadcast(msg):
    print(f"广播: {msg}")
    await asyncio.sleep(0.1)
    print(f"广播完成: {msg}")

def tcp_thread():
    time.sleep(1)
    for i in range(3):
        msg = f"消息 {i}"
        print(f"TCP 线程收到: {msg}")
        future = asyncio.run_coroutine_threadsafe(broadcast(msg), loop)
        future.result()
        time.sleep(0.5)

async def main():
    global loop
    loop = asyncio.get_running_loop()
    threading.Thread(target=tcp_thread, daemon=True).start()
    await asyncio.sleep(5)

asyncio.run(main())
```

## Q69：通知线程 B 广播时，怎么知道是哪个任务？

### 哪条数据由参数决定

```python
data = socket.recv()
parsed = parse(data)

asyncio.run_coroutine_threadsafe(
    broadcast(parsed),    # parsed 作为参数传进协程
    loop
)
```

关键：

- `parsed` 是**具体的数据**。
- `broadcast(parsed)` 创建一个**绑定了参数的协程对象**。
- 这个协程对象被调度到事件循环。
- 事件循环执行 `broadcast(parsed)` 时，`parsed` 就是当时传入的那个值。

### 广播给谁

广播通常是发给**所有** WebSocket 客户端。

```python
clients = []

async def broadcast(data):
    for ws in clients:
        try:
            await ws.send(json.dumps(data))
        except:
            clients.remove(ws)
```

### 客户端怎么区分

消息内容本身带 `type` 字段：

```json
{
  "type": "sensor",
  "moisture": 55,
  "time": 1000
}
```

### 需要发给特定客户端

```python
clients = {
    "client_1": {"topics": ["sensor"]},
    "client_2": {"topics": ["vision"]},
}

async def broadcast(data):
    for client_id, info in clients.items():
        if data["type"] in info["topics"]:
            await info["ws"].send(json.dumps(data))
```

# 第八部分：Agent 与 LangGraph

## Q70：Agent 是什么？

在 AI/机器人领域，“Agent”有很多含义：

| 含义 | 例子 | P4 里是哪个 |
|---|---|---|
| 智能体（通用） | 能感知和行动的实体 | 不是 |
| 强化学习 Agent | 学习策略的智能体 | 不是 |
| LLM Agent | 用大模型做决策 | 接近 |
| 工作流 Agent | 按流程图执行步骤 | 是 |

**P4 里的 Agent 指的是**：

> 一组按 LangGraph 流程图执行的节点，某些节点可能调用 LLM，某些只做规则判断。

## Q71：LangGraph 是什么？

**中文理解**：

共享状态、节点、条件边和执行路径组织工作流；不是单靠名字就有自治能力或安全保证。

**英文参考**：

> LangGraph organizes stateful nodes and conditional transitions. It makes the workflow explicit, but the graph name alone does not guarantee autonomy, correctness or safe execution.

## Q72：LangGraph 和神经网络的区别？

| | 神经网络 | LangGraph |
|---|---|---|
| 参数 | 权重 | 无权重 |
| 学习 | 训练 | 不训练 |
| 节点 | 层 | 函数 |
| 边 | 连接 | 条件跳转 |
| 输出 | 张量 | state 更新 |

**关键**：

> LangGraph 不是训练出来的。它是一张人工设计的流程图。

## Q73：六个节点分别做什么？

| 节点 | 职责 | 是否调用 LLM |
|---|---|---|
| sensing | 纯规则判断 fast_path | 否 |
| supervisor | 决定后续走向 | 可能 |
| care | 护理建议 | 可能 |
| alert | 告警 | 可能 |
| execution | 执行策略 | 否 |
| skip | 跳过 | 否 |

## Q74：state 是什么？

state 是一个字典，包含：

```python
{
    "sensor_snapshot": {...},
    "detections": [...],
    "soft_thresholds": {...},
    "history": [...],
    "rag_context": ...,
    "advice": ...,
    "hardware_commands": [...],
}
```

每个节点读取 state，返回一个字典，LangGraph 把它合并到 state 里。

## Q75：完整流程是什么？

```text
初始 state
  ↓
sensing 节点
  ├─ fast_path=True → execution 节点 → 结束
  └─ fast_path=False → supervisor 节点
        ├─ care 节点 → 结束
        ├─ alert 节点 → 结束
        └─ skip 节点 → 结束
```

## Q76：fast path 和 skip 的区别？

### Fast Path

**定义**：简单明确的条件满足时，直接走短流程去执行。

触发条件：

```python
if mode == "auto" and moisture < 56:
    return {"fast_path": True, "action": "start"}
```

去向：直接去 `execution` 节点。

结果：执行硬件命令（如开泵）。

**Fast path 是“赶紧去做”。**

### Skip

**定义**：条件不满足，或者不需要处理时，跳过所有动作和建议。

触发条件：`supervisor` 节点判断后决定没有传感器异常、没有视觉事件、不需要处理。

去向：去 `skip` 节点，然后结束。

结果：**不执行任何动作，也不生成建议。**

**Skip 是“没事，不用管”。**

### 对比表

| | Fast Path | Skip |
|---|---|---|
| 触发节点 | sensing | supervisor |
| 触发条件 | 简单明确的条件满足 | 没有需要处理的情况 |
| 去向 | execution | skip |
| 结果 | 执行硬件命令 | 什么都不做 |
| 目的 | 快速响应 | 避免无意义处理 |
| 例子 | 湿度低 → 开泵 | 湿度正常 → 不管 |

## Q77：fast path 与 fallback

```text
sensing 调用 check_fast_path
  ↓
命中 → 直接 execution
未命中 → supervisor
  ↓
分 care / alert / skip
```

- LangGraph 缺失/异常有 `fallback_rule`。
- 硬规则直接 `execution`。
- 其他 `supervisor` 再分。

## Q78：LLM 节点做什么？

输入：state 的一部分。

输出：建议文本或结构化动作。

例子：

```python
async def care_node(state):
    prompt = f"""
    传感器: {state['sensor_snapshot']}
    检测: {state['detections']}
    请给出护理建议。
    """
    response = await llm.generate(prompt)
    return {"advice": response}
```

LLM 输出可能格式不对、内容错误、与规则冲突。所以 LLM 输出要经过解析和验证，不能直接执行。

## Q79：执行边界是什么？

`execution` 将 commands：

1. 白名单验证。
2. 构造硬件命令。
3. Web 广播。

**建议不等于执行成功**，`execution_summary` 文本也不自动是设备实测回执。

白名单只允许特定命令：

```python
ALLOWED_COMMANDS = ["water_on", "water_off", "set_duration"]
```

除白名单外，还要检查：

| 检查项 | 含义 |
|---|---|
| 能力 | 设备是否支持 |
| 权限 | 是否有权执行 |
| 范围 | 参数是否在允许范围 |
| 新鲜度 | 数据是否过期 |
| 模式 | 当前是 auto 还是 manual |

## Q80：人工 off 能被建议覆盖吗？

**不能**。

教学 `decision_step` 返回：

```python
action
reason
requires_policy_check=True
```

- 不调用 LLM。
- 不发送命令。
- 调用方再检查模式、新鲜度和规则才模拟执行。

模型说 start 不能越过人工 off。

## Q81：事件去重怎么做？

源码做法：

```python
processed = {}    # key: event_id:scope, value: timestamp

def is_processed(event_id, scope):
    key = f"{event_id}:{scope}"
    now = time.time()
    
    if key in processed and now - processed[key] < 60:
        return True
    
    processed[key] = now
    return False
```

- key：`event_id:scope`。
- 窗口：约 60 秒。
- 源码在**执行分析前**标记 processed。

**这主要防重复分析，不能自动称端到端 exactly-once 执行。**

原因：

- 先标记后执行，如果执行失败，标记还在。
- 内存去重不持久，重启后失效。
- 不保证设备端不重复执行。

## Q82：执行摘要是硬件回执吗？

**不是。**

- 服务器选择或广播命令不证明 GPIO/泵动作。
- 需要设备确认、关联 ID 和实际反馈。
- 当前摘要不能直接当完成。

# 第九部分：记忆、历史、RAG

## Q83：记忆是什么？

**记忆** = 系统把过去发生的事情**存下来**，下次决策时**拿出来参考**。

存的可能是：

| 存什么 | 例子 |
|---|---|
| 上次泵的状态 | 开 / 关 |
| 最近几次湿度读数 | 55, 60, 55 |
| 最近的动作 | 什么时候开的泵 |
| 最近的事件 | 什么时候检测到病斑 |

## Q84：没有记忆会怎样？

假设系统每 10 秒读一次湿度，然后决定要不要浇水。

```text
时间    湿度    决策
t=0s    55     开泵
t=10s   60     ？
t=20s   55     ？
```

**t=10s 湿度 60，要不要开泵？**

如果系统**没有记忆**，它只能看当前值 60：60 在 56 到 65 之间，没有规则说 60 要开还是关，系统不知道 t=0s 已经开过泵，可能重复开泵，或者错误关泵。

## Q85：有记忆会怎样？

系统记住过去发生的事：

```text
记忆:
  t=0s  湿度55 → 开泵
```

到了 t=10s，湿度 60：

- 系统查记忆：刚才开过泵。
- 滞回规则：56 到 65 之间保持上次状态。
- 上次是开 → 保持开。

到了 t=20s，湿度 55：

- 系统查泵已经开着。
- 不需要再开。

**结果**：泵不会频繁开关。

## Q86：P4 里记忆的三种用法？

### 用法 1：滞回控制需要记住泵状态

```python
if moisture < 56:
    pump = "on"
elif moisture > 65:
    pump = "off"
else:
    pump = last_pump_state    # 用记忆
```

**作用**：避免泵在阈值附近频繁开关。

### 用法 2：避免重复浇水

```python
def should_water(state):
    history = state["history"]
    now = time.time()
    
    for event in history:
        if event["action"] == "water_on" and now - event["time"] < 300:
            return False    # 刚浇过，不要重复
    
    return True
```

**作用**：防止同一件事做两次。

### 用法 3：判断趋势

```python
def check_trend(state):
    history = state["history"]
    moistures = [h["moisture"] for h in history[-5:]]
    
    if all(moistures[i] > moistures[i+1] for i in range(4)):
        return "declining"
    return "stable"
```

**作用**：预测未来，提前准备。

## Q87：记忆的三种类型？

### 工作记忆

**当前推理需要的信息。**

```python
state = {
    "moisture": 55,
    "detections": [...],
    "mode": "auto",
}
```

**作用**：当前这一刻决策需要的数据。

**类比**：你现在手里拿的东西。

### 短期记忆

**当前会话/最近一段时间的事件。**

```python
state["history"] = [
    {"time": 1000, "moisture": 55, "action": "water_on"},
    {"time": 1060, "moisture": 60, "action": None},
    {"time": 1120, "moisture": 65, "action": "water_off"},
]
```

**作用**：避免重复、判断趋势。

**类比**：你今天做了什么。

### 长期记忆

**跨会话保留的信息。**

```python
db.save({
    "user_preference": "喜欢早上浇水",
    "plant_type": "多肉",
    "last_fertilized": "2024-01-15",
})
```

**作用**：跨天/跨周保留的信息。

**类比**：你的病历、过敏史。

## Q88：P4 里记忆存在哪？

### 工作记忆

存在 `state` 字典里，节点读写。

### 短期记忆

也在 `state["history"]` 里。每次新事件到来，追加到 history。

### 长期记忆

**文档没有说明**。可能：存数据库、存文件、不持久化。

**不能声称已实现**。

## Q89：长期记忆是自己存数据库，还是 Agent 自己学习生成？

这是两个**不同层次**的问题。

### 谁决定要记住什么

可以是程序员写规则，也可以是 Agent 用 LLM 判断。

### 存在哪里

可以是数据库、文件或内存。

### 四种组合

| | 程序员决定 | Agent 决定 |
|---|---|---|
| 存数据库 | 规则写死，存库 | Agent 判断，存库 |
| 存内存 | 规则写死，内存 | Agent 判断，内存 |

### 做法一：程序员写规则，存数据库

```python
def save_event(event):
    if event["type"] == "watering":
        db.insert("watering_log", event)
    elif event["type"] == "detection":
        db.insert("detection_log", event)
```

特点：可预测、可控、不会存奇怪的东西、但不够灵活。

### 做法二：Agent 自己判断，存数据库

```python
def agent_decide_memory(state):
    prompt = f"""
    当前事件: {state['event']}
    这个事件值得长期记住吗？
    """
    response = llm.generate(prompt)
    
    if response != "skip":
        db.insert("long_term_memory", {
            "time": now,
            "content": response,
        })
```

特点：灵活、Agent 能判断什么重要、但不可预测、可能存错东西或漏存。

### 做法三：混合

程序员定义**类别**，Agent 决定**内容**：

```python
MEMORY_CATEGORIES = ["user_preference", "plant_health", "system_config"]

def agent_extract_memory(event, category):
    if category not in MEMORY_CATEGORIES:
        return None
    
    prompt = f"""
    事件: {event}
    类别: {category}
    提取这个事件中关于 {category} 的关键信息。
    """
    return llm.generate(prompt)
```

## Q90：Agent 自己判断有什么风险？

### 可能存错

```text
用户说: "今天天气不错"
Agent 判断: 值得记住
存入: "用户喜欢天气"
```

其实是误判。

### 可能漏存

```text
用户说: "我的植物好像不太喜欢阳光"
Agent 判断: 不值得记
漏掉: 这是一个重要的偏好
```

### 可能存太多

```text
Agent 把每条传感器读数都存
→ 数据库爆炸
```

### 可能忘记

```text
长期记忆存了，但检索时没找到
→ 等于没存
```

## Q91：RAG 是什么？

RAG = Retrieval-Augmented Generation，检索增强生成。

**核心问题**：LLM 的知识来自训练数据，训练数据可能没有最新信息、没有专业知识、有错误。

**解决方案**：在 LLM 生成回答前，先从外部知识库检索相关信息。

## Q92：RAG 流程是什么？

```text
用户问题/检测事件
  ↓
生成检索 query
  ↓
从知识库检索相关文档
  ↓
把检索结果 + 原问题拼成 prompt
  ↓
LLM 生成回答
  ↓
返回结果
```

## Q93：检索方式有哪些？

### 关键词检索

```python
def keyword_retrieve(query, docs):
    results = []
    for doc in docs:
        if any(kw in doc for kw in query.split()):
            results.append(doc)
    return results
```

优点：简单、快。缺点：不能理解语义。

### 向量检索

```python
import numpy as np

def vector_retrieve(query, docs, model):
    query_vec = model.encode(query)
    doc_vecs = model.encode(docs)
    
    similarities = np.dot(doc_vecs, query_vec) / (
        np.linalg.norm(doc_vecs, axis=1) * np.linalg.norm(query_vec)
    )
    
    top_k = np.argsort(similarities)[-3:]
    return [docs[i] for i in top_k]
```

优点：理解语义。缺点：需要嵌入模型、向量库。

### 混合检索

结合关键词和向量。

## Q94：RAG 在 P4 里怎么用？

### 假设的知识库

```text
knowledge_base/
  ├── plant_diseases.txt
  ├── watering_guide.txt
  └── sensor_calibration.txt
```

### care 节点里的 RAG

```python
def care_node(state):
    detections = state["detections"]
    
    query = f"{detections[0]['class']} 处理建议"
    rag_context = retrieve(query, knowledge_base)
    
    prompt = f"""
    检测结果: {detections}
    参考资料:
    {rag_context}
    请根据以上资料给出护理建议。
    """
    
    advice = llm.generate(prompt)
    
    return {
        "advice": advice,
        "rag_context": rag_context
    }
```

## Q95：RAG 的边界是什么？

### 检索质量决定回答质量

- 检索不到相关文档 → LLM 只能靠训练数据。
- 检索到错误文档 → LLM 可能给出错误建议。

### LLM 可能忽略 RAG

即使给了参考资料，LLM 也可能忽略资料、编造信息、格式错误。

### RAG 不是万能的

- 需要维护知识库。
- 需要更新文档。
- 需要评估检索质量。

## Q96：P4 里能确认什么？

### 能确认

| 内容 | 证据 |
|---|---|
| state 含 history/RAG 字段 | 文档明确说 |

| 内容 | 原因 |
|---|---|

| 记忆是否持久化 | 未说明 |
| RAG 知识库内容 | 未说明 |

> 文档只提到 state 有 history/RAG 字段，不能证明 RAG 已完整实现或运行。

## Q98：自测题答案

1. **为什么湿度 56 到 65 之间要保留上次泵状态？**  
   避免读数在单一门槛附近波动时让继电器反复开关。

2. **ADC、湿度标定值、模型置信度分别是什么？**  
   ADC 是原始数值；湿度标定值是软件映射；置信度是模型对单次检测的分数。

3. **ONNX 转 RKNN 和训练模型有什么区别？**  
   转换是部署格式转换；训练是学习权重，需要数据、标签、损失、验证。

4. **为什么高置信旧图也要拒绝？**  
   旧图描述的是过去状态，置信度高不代表新鲜。

5. **LangGraph 里的规则节点和设备执行分别做什么？**  
   规则节点做确定判断；执行层检查设备、模式、权限和命令范围。

6. **为什么一次 TCP recv 不保证拿到完整 JSON？**  
   TCP 是字节流，可能分包或粘包。

## Q99：最直白的总结

1. **三层**：Hi3861 本地控制、RK3588 边缘视觉、Python 服务决策。
2. **五类信息**：传感读数、模型观测、建议、命令请求、设备反馈。
3. **滞回**：低于 56 开，高于 65 关，中间保持。
4. **GPIO 低触发**：逻辑 on 对应引脚 LOW。
5. **ADC 不是真湿度**：软件标定近似。
6. **视觉链**：V4L2 → 预处理 → YOLO/RKNN → 后处理 → 结构化事件。
7. **INT8**：整数近似浮点，校准集重要。
8. **置信度不是准确率**，旧图即使高分也要拒绝。
9. **时间戳**：源 Hi3861 为 0，RK 用系统时间，服务有接收时间。
10. **LangGraph**：规则 fast path + 可选推理节点。
11. **执行边界**：建议不等于执行，白名单只是其中一项。
12. **TCP**：字节流，需要长度前缀重组。
13. **回执**：发送 ≠ 收到 ≠ 物理动作。
14. **去重**：防重复分析，不等于端到端 exactly-once。
15. **训练 vs 部署**：转换不等于训练。
16. **asyncio**：单线程异步 I/O，事件循环调度。
17. **跨线程调用**：用 `run_coroutine_threadsafe`。
18. **记忆**：避免重复、判断趋势、提供上下文。
19. **RAG**：检索增强生成，先检索再让 LLM 回答。
20. **边界**：字段存在不等于实现，实现不等于运行。
